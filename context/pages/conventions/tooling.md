# Tooling

The harness, in place since 2026-10-21, is sh + jq hooks with case-matrix self-tests, one pipeline skill, a review workflow and an in-repo context folder. Root `CLAUDE.md` names this page; the `scout-pipeline` skill dispatches by it.

## Model routing (owner, 2026-10-21)

The session model does every survey, plan and check; Opus implements and reviews the write contract and credentials, Sonnet reviews the rest (owner, 2026-11-11); Sonnet does the simple work; Haiku runs the gates.

| Who | Model, effort | Writes code? |
|---|---|---|
| **The manager** (the session thread): classifies, reads the context folder, states the six-part plan, dispatches, checks the result against the plan line by line, owns `context/index.md`, `context/log.md`, the conventions and the process ADRs. | session model | Context folder, docs, `.claude/**`, fast-path one-liners only. |
| **`scout-implementer`**: implements a non-trivial change from the plan (adapters, providers, plugins, skills, control-plane commands, knowledge indexing, hosts, tests), Rule B per edit, and proves gate 5 itself: a targeted mutation per `new behaviour` entry with the failure quoted, the file restored from a backup copy and rebuilt; behaviour locks green before and after. | opus, high | **Yes**: `src/**`, `tests/**`, `ui/**` of the named project(s), plus the context folder pages the plan names. Never git history. |
| Any simple, mechanical, well-specified task (`general-purpose` on `model: sonnet`). | sonnet, medium | **Yes**, the named files only. |
| **`scout-mechanic`**: runs build, format, diagnostics and test commands exactly as dispatched, reports per project with skipped counts, never fixes; on the manager's explicit request it runs a `.prove-red` on the commit the branch started from (the dispatch's base commit, or `git merge-base HEAD origin/main` after a fetch) and names that commit in its report. | haiku, low | No. |
| **`scout-reviewer`**: gate 6, dispatched by the `scout-review` workflow one instance per lens (`read-only`, `secrets`, `boundaries`, `invariants`); checks the gate 5 evidence and the test-quality results the dispatch carries; each finding then faces a refute pass. | opus, high on the `read-only` and `secrets` lenses, which judge the write contract and credentials; sonnet, high on `invariants` and `boundaries` (owner, 2026-11-11); refute pass: sonnet, high | No. |

| **`scout-meter`**: runs `tools/dev/token-usage.sh` on a session, reads every Markdown document a model loads here, and says where the tokens went and what would lower the spend; on request, never part of a change. | sonnet, medium | No. |

## `.claude/skills/scout-pipeline`

Since 2026-11-06 the skill opens with gate 0 (`.claude/skills/scout-pipeline/SKILL.md:17`): classification starts from `git status --porcelain` and `git diff HEAD --stat`, written as an instruction and never as a dynamic shell block, because a skill that shells out while loading fails to load wherever Bash is denied.

The single source of the pipeline: classification (fast path or full), the never-list, the ladder (`ponytail` after the context folder, before the edit), the six-part plan, the nine gates, the two dispatch templates. Lane files `feature.md`, `bugfix.md`, `refactor.md`, `diagnose.md` carry only the stage order. `evals/` holds four `claude plugin eval` cases (a provider bug is the bugfix lane, a doc typo is the fast path, a one-line outbound call is never the fast path and names the `read-only` lens, a Contracts edit resolves to every test project and the four ui commands, `bun run typecheck`, `bun run lint`, `bun run format` and `bun run test`, each of which the answer must name literally). Every grader of the bugfix, outbound-call and Contracts cases rejects an answer that names the thing it looks for only to deny it, such as "not a Bug", "the full pipeline does not apply", "this is not an executive write", "no read-only lens is needed", "do not run every test project" or "bun run test is not needed", and anchors on the affirmative statement; `tests/Scout.ArchTests/PipelineEvalGraderTests.cs` feeds each a denying and an affirming answer, and the outbound-call and Contracts graders also the final answers of two with-skill eval runs of their case, kept whole (the `result` field of the `type: "result"` record in the run's `out/trace.jsonl`) (`TheBugfixGradersAcceptTheClassificationAndRejectItsDenial`, `TheOutboundCallGradersAcceptTheSafeguardsAndRejectTheirDenial`, `TheContractsSurfaceGradersAcceptTheWideSurfaceAndRejectItsDenial`). The test-project grader also accepts a Markdown-emphasised quantifier (`**every** test project`), the form that held the Contracts case at 0.75 until 2026-11-11, and `Every .NET test project under tests/`, the heading the with-skill answers write; the two not-fast-path graders reject a denial of the never-list ("it isn't on the 'never fast path' list"), which names the words they look for. The doc-only case's grader has its own rows (`TheDocOnlyGraderAcceptsTheFastPathAndRejectsItsDenial`), and `EveryGraderOfEveryEvalCaseHasAnAcceptedAndARejectedRowInTheTable` reads every `graders/*.md` under `evals/` and fails, naming it, on a grader whose case has no table or whose table holds no answer it must accept and none it must reject, so a new case or grader cannot land untested. A pattern is read by the eval runner and by .NET, so it uses lookahead and no lookbehind. These graders are keyword patterns and have a ceiling: they reject only the denials their lists carry, so an answer that denies the safeguard in other words ("a read-only review would be excessive", "the shape is the quick one") still passes, and only a reader of the answer catches it; a SKILL.md edit that changes what a grader asserts updates the eval in the same diff.

**The gate is the table, the live eval is advisory** (owner, 2026-11-12). Gate 4's row for `.claude/skills/scout-pipeline/**` is `dotnet test tests/Scout.ArchTests`, which runs `PipelineEvalGraderTests` locally and in CI's test step (`tools/checks/test-per-project.sh` runs every test project; `.github/workflows/ci.yml:67`), and `HarnessDocumentTests.TheGateForThePipelineSkillIsTheGraderTableAndTheLiveEvalIsAdvisory` pins that row. The live `claude plugin eval .claude/skills/scout-pipeline` is not the gate and is not run in CI: it needs a signed-in Claude Code and spends model calls on the owner's credential, and its answers vary from run to run, so a keyword grader that is right on the table can still miss a correctly worded answer at the suite's threshold. Run it before merging a change that alters the wording of a lane file or of `SKILL.md`, read every failing case, and record the result in the PR body; a failing case is a finding to judge (the answer was wrong, or the grader missed a right answer and gets a row and a fix), not an automatic block.

The four cases cover the classification of a provider bug, of a doc typo and of a one-line outbound write, the write's classification and its `read-only` lens, and gate 4's widest surface. No case covers a new LLM-invocable function (judged by what it can reach, never by its description), a credential or configuration-binding change (the `secrets` lens, nothing in `appsettings*.json`), or a write outside Scout's own folders (forbidden: stop and report); they are a follow-up ([[pages/roadmap/followups]], Eval cases for the write contract's other decision paths).

## `.claude/workflows/scout-review.js`

Gate 6 as a `Workflow` script: `Workflow({ name: "scout-review", args: { module: "<Scout.Project>", lenses, dispatch, range? } })`. `invariants` always runs and also owns regression coverage, Rules H and J and generic correctness; the other lenses come from the gate 6 table, each on its own `scout-reviewer`: opus for `read-only` and `secrets`, sonnet for `invariants` and `boundaries`, which `.claude/workflows/scout-review.test.sh` pins. A lens reports at most five findings and an empty list on a sound diff is the right answer; the reviewer first reads [[pages/conventions/decisions-that-look-like-defects]], so behaviour recorded there as intended is not reported again, and its correctness check names a guard that cannot fire and a failure answered as success ([[pages/invariants/a-guard-must-be-able-to-fire]]). Every finding then goes to an independent `scout-reviewer` on sonnet whose only job is to refute it; a finding survives only when the refuter reads the cited line and the cited page and cannot. The reviewer gives each path relative to the reviewed tree's root, and the refuter gets the dispatch's opening lines (`Project: ... Diff: ...`, up to the first blank line or a `Lenses:` line in any case and indentation, at most three lines and 600 characters, never the map or the evidence) and, with a range other than `HEAD`, the range itself, with the instruction to read the cited file in that tree and never in the session's working directory, which may be another checkout on another commit; its verdict carries `located`, and a finding it could not locate there is not refuted. The result is `{ confirmed, refuted, unresolved, unresolvedLenses, checked, uncited }`: `refuted` holds only findings whose refuter answered `refuted: true` with `located: true`, and a finding whose refuter returned nothing, or answered `located: false`, goes to `unresolved` with the refuter's reason when it gave one, which the manager verifies and treats like `confirmed` (the gate fails closed); a lens whose review returned nothing is named in `unresolvedLenses` and blocks until it is run again. `.claude/workflows/scout-review.test.sh` runs the real script under node with stub agents, one refuter answering nothing, one refuted, one upheld and one that could not locate its finding, and checks the three lists, that the refute prompt names the reviewed tree from the dispatch and not the rest of it (with a lowercase or indented `Lenses:` line, with a dispatch of another shape, with a 1000-character first line), that it names a range other than `HEAD`, that an unresolved finding keeps its refuter's reason, and that the review prompt asks for paths relative to the tree's root, then a run whose `read-only` lens returns nothing, which must come back in `unresolvedLenses`; CI runs it beside the hook self-tests. Both agents read `git diff HEAD` plus `git status --porcelain`. The `dispatch` arg is the reviewer template from the skill, filled in; the script builds neither the map nor the evidence. Without the Workflow tool the fallback is the direct `scout-reviewer` dispatch.

## `.claude/skills/stryker-project`

On-demand mutation testing of one project with Stryker.NET, a local tool pinned in `.config/dotnet-tools.json` (`dotnet-stryker` 5.1.0, `rollForward: false`) and run with `dotnet tool restore` then `dotnet tool run dotnet-stryker` from the project's test project, never installed globally (`HarnessDocumentTests.NoRecipeInstallsADotnetToolGloballyAndTheMutationToolIsPinnedInTheManifest`), `disable-model-invocation: true` so only the owner starts it. Survivors on a read-only guard, a tool or plugin allow-list, credential handling, a fail-closed branch or a provider selection are findings with `file:line` and the invariant page; logging, text and mapping survivors are a count. Not a gate: gate 5's targeted mutation per requirement stays the proof.

## `.claude/hooks/`

All seven fail open: a missing `jq`, malformed JSON, or any error exits 0 having written nothing, so a broken hook can never block work. That is why the first one exists.

| Hook | Event | What it does |
|---|---|---|
| `session-start.sh` | SessionStart | Proves the hook runtime works, loudly: checks `jq` is on PATH and pipes `git commit -m x` through `pre-git-guard.sh`; when either fails it emits a `systemMessage` saying the hooks are dead and which gates are silent. |
| `prompt-router.sh` | UserPromptSubmit | One line reminding that a code task routes through `scout-pipeline` first and that a new outbound call is a review lens, never a fast path. |
| `pre-git-guard.sh` | PreToolUse (Bash) | Turns Rule E into a permission **ask**: history-writing git (`commit`, `push`, `merge`, `rebase`, `revert`, `cherry-pick`, `pull`, `am`, a moving `reset`, `tag` creation or deletion, `branch -D/-m`, an alias, a `git stash` that moves work: bare `stash`, `push`, `save`, `pop`, `apply`, `drop`, `clear`, `branch`), every `gh` command that writes to GitHub (every `gh issue`, `gh pr`, `gh release`, `gh workflow`, `gh run`, `gh label`, `gh secret`, `gh variable`, `gh gist`, `gh repo`, `gh cache`, `gh project`, `gh codespace`, `gh ssh-key`, `gh gpg-key`, `gh extension`, `gh alias` and `gh config` subcommand except their reads, aliases included; a `gh api` call with a method other than GET, with fields (`-f`, `-F`, `--field`, `--raw-field`, `--input`) and no explicit GET, or a `graphql` call carrying a `mutation` or a query it cannot read inline; and a `gh` subcommand it does not know, with a reason saying so), `docker push`, `wrangler deploy/publish/secret`, `dotnet ef database update/drop`. "Ask" not "deny": "commit this for me" still works, it cannot happen silently. Each `gh` command is judged on its own words, up to the next `|`, `&&`, `||`, `;`, newline or subshell bound outside quotes, so a flag of a command piped after it never counts; the text of a quoted `bash -lc "..."` is split the same way. Read-only git passes, `git stash list` and `git stash show` included; so do the `gh` reads (`issue view/list/status`, `pr view/list/status/diff/checks/checkout`, `release view/list/download/verify`, `workflow view/list`, `run view/list/watch/download`, `repo view/list/clone/set-default`, the `list` and `view` of the groups added above, `list` as `ls`, `auth`, `browse`, `status`, `help`, `search`, a `gh api` GET and a `graphql` query). |
| `post-edit-rule-b.sh` | PostToolUse (Edit\|Write) | On `src/**/*.cs`: the edit needs its test now, the gates are build + diagnostics + ArchTests + whitespace format, and Rule A for any new outbound call. On `ui/packages/**/*.ts` (not a spec): a spec now, then typecheck, lint, format, test and build in `ui/`. |
| `post-edit-build-rules-note.sh` | PostToolUse (Edit\|Write) | On `Directory.Build.props`, `Directory.Packages.props`, `.editorconfig`, `global.json` and `.github/workflows/**`: the build strictness grades a change and is not part of it; the reply must say why the task needed the edit. |
| `stop-review-gate.sh` | Stop | **Blocks** the turn once when the session edited `src/**/*.cs` without dispatching `scout-reviewer` (an `Agent` call or a `Workflow` run of `scout-review`). `stop_hook_active` passes on the continuation, so no loop. Keyed on what *this* session edited, in `<session>.jsonl` and every `<session>/subagents/*.jsonl`, not on working-tree dirtiness. |
| `session-end-metrics.sh` | SessionEnd | Appends one JSON line per session to `.claude/metrics/sessions.jsonl` (gitignored): src and test edits, reviewer dispatches, review workflow runs, pipeline invocations, agents, tool calls, `endedUnreviewed`. |

All seven hooks carry a case-matrix self-test (`<hook>.test.sh`, prints `ALL CASES PASS`); CI runs all seven plus `.claude/workflows/scout-review.test.sh`, `tools/checks/check-context-refs.test.sh`, `tools/checks/test-per-project.test.sh`, `tools/release/next-version.test.sh`, `tools/release/with-test-version.test.sh`, `tools/release/release-workflow.test.sh`, `tools/checks/check-diagnostics.test.sh`, `tools/dev/install-git-hooks.test.sh` (both since 2026-11-11) and a real `check-context-refs.sh` run in its first step, before .NET is set up (`.github/workflows/ci.yml:18`). `HarnessDocumentTests.EveryHookTheSettingsRunExistsHasASelfTestAndCiRunsEverySelfTestUnderClaude` reads `.claude/settings.json` and fails when a registered hook command runs anything but a script under `.claude/hooks/`, when that script or its `.test.sh` is missing, or when a `.test.sh` under `.claude/hooks/` or `.claude/workflows/` is not run by `ci.yml`. `EveryWorkflowDeclaresATopLevelReadOnlyToken` fails on a workflow with no top-level `permissions: contents: read`.

## `tools/checks/check-diagnostics.sh`

`tools/checks/check-diagnostics.sh <csproj|slnx|-> [info|warning|error]`. The build already enforces code style, but test projects generate no documentation file and without it IDE0005 (unused usings) is never emitted (dotnet/roslyn#41640); info-level diagnostics never fail a build either. The script forces both on, rebuilds the target at detailed verbosity with `MSBUILDDISABLENODEREUSE=1`, and fails on any `CS/CA/IDE/SA/MSB` diagnostic at or above the minimum severity (default `info`). A line with no file coordinates counts too when it has the canonical `origin : error|warning|message|info CODE:` shape, the same severity words the coordinate form accepts, such as `x.csproj : warning NU1603: ...`, `MSBUILD : error MSB1009: ...` or `CSC : info IDE0005: ...` (a `message` counts as `info`); build summary lines, a `NoWarn` property dump, a compiler switch and a `name : warning text` line without a code are not diagnostics. `tools/checks/check-diagnostics.test.sh` pins every severity with and without coordinates in stdin mode (`-`). A third argument picks the configuration (default Debug). Pass one `.csproj` locally; CI runs it on `Scout.slnx` in Release as the build itself, once, and the tests run on its output (owner decision 2026-11-06; `.github/workflows/ci.yml:62`), so a diagnostic the agent gate missed still fails the PR.

## `tools/checks/check-hidden-text.sh`

`tools/checks/check-hidden-text.sh [file-or-directory ...]` finds text a person does not see on screen but a model still reads, which is how an instruction can be planted in a page, a skill file or a source file without a reviewer noticing. With no argument it scans the text files of the repo; CI runs it that way and fails on any finding. Given paths, it checks those, which is the way to check a file from outside before a model is asked to read it, for example a source dropped in `context/raw/` before an ingest.

| Kind | What it finds | Where |
|---|---|---|
| `invisible` | zero-width and formatting code points, direction overrides, tag characters, variation selectors, filler letters, soft hyphens | every text file |
| `control` | control characters other than tab, line feed and carriage return | every text file |
| `comment` | an HTML comment, or a link definition used as a comment; neither is rendered | Markdown |
| `hidden` | HTML styled or marked not to show | Markdown |
| `lookalike` | a word mixing Latin letters with Cyrillic or Greek ones | Markdown |
| `gap` | a run of 120 or more spaces inside a line, which pushes text off screen | Markdown |

Allowed: a byte order mark at the start of a file, padding inside a table row, and HTML comments in the issue and pull request forms under `.github`, which are notes to the person filling in the form. A character that code needs is written as an escape (`\u001F`), never as the character. It prints `file:line: kind: detail` per finding and exits 1 on any, 0 on none, 2 when it finds nothing to read. It needs `perl`. `tools/checks/check-hidden-text.test.sh` is its self-test, run by CI.

## `tools/dev/token-usage.sh`

`tools/dev/token-usage.sh [transcript.jsonl]` prints the tokens one Claude Code session used, one row for the main session and one per agent type it started (agents a workflow started included): runs, requests, input, cache write, cache read, output and the largest context a request carried. A response is stored once per content block, so it is counted once per message id. With no argument it reads the newest transcript of this checkout. Below the table it totals the Markdown documents a model reads, grouped by when they load.

`tools/dev/token-usage.sh docs` lists those documents by file, largest first in each group, in characters and in tokens estimated as characters divided by four:

| Group | Documents |
|---|---|
| every session | `CLAUDE.md`, `context/CLAUDE.md`, the `description` of each agent and skill |
| every task | `context/index.md` |
| each run of the agent | `.claude/agents/*.md` |
| when the skill or command is used | the Markdown under `.claude/skills` and `.claude/commands`, eval fixtures left out |
| when the task needs it | `AGENTS.md`, `context/wiki-config.md`, `context/wiki-schema.md` |
| Scout's own model, per skill | `src/Scout.Skills/skills/*.md` |

The script reads only. `tools/dev/token-usage.test.sh` is its self-test, run by CI. The `scout-meter` agent reads both outputs and the documents themselves.

## `tools/checks/test-per-project.sh`

`tools/checks/test-per-project.sh [dotnet test args]` runs every `tests/**/*.csproj` one at a time and fails when a project fails, skips a test, runs nothing, or prints a summary line it cannot parse; a solution-wide `dotnet test` reports one green total, which has hidden a project that did not compile and a suite that was skipped entirely. It is the pipeline's gate 4 ("`N passed` per project, Skipped 0") in one command, and the CI test step since 2026-11-06 (`.github/workflows/ci.yml:67`). It also fails, `DID-NOT-RUN  no test project found`, when `tests/` is missing or holds no project. `tools/checks/test-per-project.test.sh` runs it against a fake `dotnet` for the six verdicts, the Docker filter, and a tree with no test project.

## `tools/release/next-version.sh` and `tools/release/with-test-version.sh`

`tools/release/next-version.sh [--notes] release | prerelease <channel> | test` prints the next version from the latest `vX.Y.Z` tag reachable from `HEAD` (prerelease tags are never the base) and the commit subjects since it, read as conventional commits: a `!` after the type or a `BREAKING CHANGE:` footer bumps the major, or the minor while the major is 0 (the script says so on stderr); any `feat` bumps the minor; anything else, a subject with no type included, bumps the patch. `release` prints `X.Y.Z`; `prerelease beta` prints `X.Y.Z-beta.N`, `N` one above the highest existing `vX.Y.Z-beta.*` tag; `test` prints `X.Y.Z-test.<UTC yyyymmddHHMM>.g<short sha>`, which sorts above the last release and below `X.Y.Z`. The `g` keeps a short sha made only of digits from starting with a zero, which semver forbids in a numeric identifier. With nothing committed since the tag, `release` and `prerelease` exit 1 with a sentence; `test` still prints a patch above the release. `--notes` prints the subjects grouped under Features, Fixes and Other instead. Owner request of 2026-11-08: the version changes by itself on every build, and the owner decides what reaches users ([[pages/runbooks/release]]).

`tools/release/with-test-version.sh <command...>` sets `ui/package.json`'s version to `next-version.sh test`, runs the command in `ui/`, and copies the original `package.json` back byte for byte on exit, failure, Ctrl+C or a kill. `bun run dist:linux:test` in `ui/` is `bash ../scripts/with-test-version.sh bun run dist:linux`, so every local test AppImage carries its own version and the updater never offers to replace it with an older release.

`tools/release/next-version.test.sh` runs the bump rules, the prerelease counter, the test stamp and the notes in throwaway repositories; `tools/release/with-test-version.test.sh` runs the wrapper with a fake build that records the version it saw and checks the restore after a pass, a failure and a kill. `tools/release/release-workflow.test.sh` extracts the bodies of the check job's version step and the publish step from `.github/workflows/release.yml`, runs them in throwaway repositories with each trigger's `GITHUB_*` environment and a fake `gh` that logs its arguments, and checks the computed version and the publish call: a release and a prerelease from `main`, an override that does not fit its kind, an existing tag, another branch refused, a pushed tag with `--verify-tag --generate-notes`, and a rerun with `--clobber`. It also reads the three workflow files and fails when the `build` job does not need a job that calls `ci.yml` and one that calls `ui-ci.yml`, or when either of those lost its `workflow_call`, `push` or `pull_request` trigger, or when UI CI's concurrency group lacks `github.workflow` or its push and pull_request path filters lack `doc/**`. Since 2026-11-11 it walks the jobs of every file under `.github/workflows/` and fails, naming the file, the job and the reference, on a `uses:` that is neither local (`./...`) nor `owner/repo@` a commit of 40 lowercase hex characters, or that has no trailing comment naming the version it was pinned from. Since 2026-11-08 the Release workflow's `build` waits for `verify` (it calls `ci.yml`) and `verify-ui` (it calls `ui-ci.yml`), so no tag or dispatch packages a commit whose .NET build, tests, diagnostics, UI lint, typecheck, format, tests or end-to-end tests fail; both workflows keep their own triggers, and UI CI's concurrency group carries the calling workflow's name, so a release run and a push to `main` never cancel each other. No secret is passed to them. It needs `python3` with PyYAML, which ubuntu runners ship. The three run in CI's first step.

## Repository settings

`main` is held by a repository ruleset named `main`: a change reaches it only through a pull request whose conversations are resolved and whose `build` check (`.github/workflows/ci.yml`) is green on a branch up to date with `main`; force pushes and deletion are refused for everyone. A pull request needs one approval from a code owner, and `.github/CODEOWNERS` names the owner for every path; a push after the approval dismisses it, and whoever pushed last cannot approve. A repository admin may merge their own pull request without that approval, since GitHub lets nobody approve their own, and may do so only through a pull request, never by a direct push. UI CI's jobs are not required, because its path filters leave a pull request that touches no UI file without them. A second ruleset, `release-tags`, lets only a repository admin create, move or delete a `v*` tag, since pushing one starts the Release workflow, whose `publish` job holds `contents: write`. That `publish` job runs in the `release` environment, which only `main` and `v*` tags may deploy to and which waits for the owner to approve each run. The repository allows only actions owned by GitHub and `oven-sh/setup-bun`, requires every action to be pinned by commit, and asks the owner to approve the workflow runs of every pull request from a fork; a pull request from a fork never receives a secret, and no workflow runs on `pull_request_target`. The wiki and projects are off; a pull request is merged by squash only, can be brought up to date from its page, and its branch is deleted after the merge; a commit made in the web editor needs a sign-off. `.github/workflows/codeql.yml` runs CodeQL on `actions`, `csharp` and `javascript-typescript` without a build, on each push and pull request to `main` and weekly; its results are on the repository's Security tab.

## Workflow actions are pinned by commit

Every external action in `.github/workflows/` is referenced by a full commit, with the release it was taken from in a trailing comment: `uses: actions/checkout@<40-hex> # v4.4.0`. A tag such as `@v4` can be moved to another commit by whoever controls the action's repository, and the release workflow's `build` legs receive `SCOUT_GOOGLE_CLIENT_SECRET` while `publish` holds `contents: write`; a commit cannot be moved. One action has one commit in every workflow. The commits were taken on 2026-11-11 from each action's newest release in the major the workflows already used (`checkout` v4.4.0, `setup-dotnet` v4.3.1, `setup-node` v4.4.0, `cache` v4.3.0, `upload-artifact` v4.6.2, `download-artifact` v4.3.0, `setup-bun` v2.2.0), and on 2026-11-13 `github/codeql-action` v4.39.1, one commit for its `init` and `analyze`, read from the repository's own `git/ref/tags/<tag>`; on that day each moving major tag pointed at the same commit. `tools/release/release-workflow.test.sh` fails on any reference that is not pinned that way. That case is the only check of the commit; two others read an action reference by name only, the part before `@`, so a pin update never needs them edited: the .NET setup step comparison in the same script (`actions/setup-dotnet@`) and the media-tools cache case of `ui/packages/main/test/release-workflow.test.ts` (`actions/cache`).

`.github/dependabot.yml` asks Dependabot weekly for `github-actions` updates, one pull request per action, and for NuGet (`Directory.Packages.props`) and Bun (`ui/bun.lock`) updates, where minor and patch are grouped into one pull request per ecosystem. `@playwright/test` is ignored there, since its pin moves only by the rule in the Playwright section below. An update pull request changes the commit and the version comment together, and is reviewed like any other change: read the action's release notes, check the commit is the one the action's own tag names (the `git/ref/tags/<tag>` read below; the commits endpoint alone also answers for a commit that only exists in a fork), and let CI run on it. A pull request that moves an action to a new major is a change of its own, not taken with a pin update. To update one by hand: find the release, read its commit with `gh api repos/<owner>/<repo>/git/ref/tags/<tag>` (an annotated tag is dereferenced through `git/tags/<sha>`), and replace the commit and the comment on every line that uses the action.

## `tools/checks/check-context-refs.sh`

Resolves every `path:line` citation in `context/pages` (paths under `src`, `tests`, `ui`, `scripts`, `.claude`, `.github`) against the working tree; fails on a missing file, a line 0 or a line past the end, and when `context/pages` is missing or cannot be listed, so a lost tree never reports "0 citations resolve". It proves the line exists, never that it still describes the claim; that part is read. Pages whose `status` marks them as a record are skipped. Runs in gate 7b and in CI.

## `graphify-out/graph.json` and the git hooks that refresh it

An AST knowledge graph of the repo (graphify 0.9.73), built locally and gitignored, never committed. `tools/dev/install-git-hooks.sh` copies the three versioned hooks from `tools/dev/git-hooks/` (`post-commit`, `post-checkout`, `post-merge`) into the clone's common hooks directory, so every worktree refreshes the graph after a commit, a checkout or a pull. It keeps a copy of what it installed as `<name>.scout` and replaces that hook without a backup; any other hook it finds is backed up as `<name>.bak`, or `<name>.bak.2` and up when a backup already exists, so no install overwrites a backup of the owner's own hook (`tools/dev/install-git-hooks.test.sh`, run in a throwaway repository); `post-merge` is hand-written because a fast-forward pull fires neither of the other two, and it depends on the `GRAPHIFY_DIFF_BASE` line in `post-commit`, which `graphify hook install` would rewrite, so re-apply it after upgrading graphify. `.graphifyignore` excludes `src/old/` and `tests/old/` (the archived first cut would otherwise duplicate every live label, and `graphify affected` needs a unique one). First build 2026-10-21: 6655 nodes, 13988 edges, AST only. Manual refresh: `graphify update . --no-cluster`. The querying rules (which commands, what never to run) live once, in the owner's global `~/CLAUDE.md`; in this pipeline `graphify affected "<Symbol>" --depth 2` gives the starting Files list of the plan and `god-nodes --top 10` says whether the change lands on a hub.

## Playwright in `ui/e2e`

`@playwright/test`, pinned to the exact version `1.64.1` in `ui/e2e/package.json`, drives the built desktop app through its Electron support ([[pages/decisions/0051-desktop-end-to-end-tests]]); it downloads no browser. Bun does not run Electron's install script, so a fresh worktree fetches the Electron binary once with `node packages/main/node_modules/electron/install.js` in `ui/`. `bun run test:e2e` in `ui/` runs `ui/e2e/run.sh`, which needs `dbus-run-session`, `gnome-keyring-daemon` and `xvfb-run` (Linux only): a private D-Bus session from `ui/e2e/session-bus.conf`, with no service activation so no desktop portal starts on it, a keyring daemon in a temporary folder unlocked with a fixed password, and the tests under a virtual 1920x1080 display, so the owner's keyring and screen are never touched; the fixture refuses to launch the app outside `run.sh`. ## Claude Code compatibility

Last validated with Claude Code **2.1.322** (2026-11-12): under that version one live `claude plugin eval .claude/skills/scout-pipeline` run loaded the skill and scored each of its four cases 1.00 with the skill; the hook self-tests, the workflow self-test and `tests/Scout.ArchTests` were green the same day, but they do not run Claude Code (table below), and the live-session hook check below was not done that day. That is the version this harness was checked on, not a proven minimum: no older version has been tried, and none is claimed.

What the harness depends on, read from the files:

- **Settings** (`.claude/settings.json`): the hook events `SessionStart`, `UserPromptSubmit`, `PreToolUse` with matcher `Bash`, `PostToolUse` with matcher `Edit|Write`, `Stop` and `SessionEnd`; `type: "command"` hooks with a `timeout`, run through `sh` with `$CLAUDE_PROJECT_DIR`; `permissions.allow` entries in the `Bash(<command>:*)` form.
- **Hook input and output**: the hooks read `tool_input.command`, `tool_input.file_path`, `stop_hook_active`, `transcript_path` and `session_id` from stdin, and answer with `hookSpecificOutput` (`permissionDecision: "ask"` with its reason, `additionalContext`), `systemMessage`, or a Stop `decision`; `stop-review-gate.sh` and `session-end-metrics.sh` also read the session transcript and its `subagents/*.jsonl` for `Agent`, `Workflow` and `Skill` tool calls.
- **Agents and skills**: the frontmatter keys `name`, `description`, `tools`, `model` and `effort` in `.claude/agents/*.md`, and `name`, `description`, `argument-hint`, `metadata` and `disable-model-invocation` in the skills.
- **The `Workflow` tool**: `.claude/workflows/scout-review.js` exports `meta` and calls the globals `args`, `agent`, `pipeline`, `parallel` and `log`; without the tool, gate 6 falls back to the direct `scout-reviewer` dispatch.
- **`claude plugin eval`**: a case is `prompt.md` (frontmatter `name`, `runs`, `max_turns`, `timeout_seconds`, `tags`, `plugins`) plus `graders/*.md` (`type: regex`, `pattern`, `flags`, `match: contains`, `target: last_message`); results go to the gitignored `evals/results/`.

After an upgrade of Claude Code, run:

| Check | What it catches | What it cannot catch |
|---|---|---|
| every `.claude/hooks/*.test.sh` (`ALL CASES PASS`) | a hook's own logic, and a missing `jq` (`session-start.test.sh`) | the self-tests feed fixed JSON, so a renamed event, payload field or output key in Claude Code passes them; only a live session shows it, for example the `systemMessage` that `session-start.sh` prints when the guard does not answer |

| `claude plugin eval .claude/skills/scout-pipeline` | a skill that no longer loads, a case or grader format the runner rejects, and drift in what the model answers | it is advisory and noisy: read each failing case before acting on it |

Then start one session in the repository and check that the session-start hook stays silent (a message there means the hooks are dead) and that `git commit` asks for permission. Record the new validated version here.

## Permissions

`.claude/settings.json` allows without a prompt the read-only commands the gates need: `dotnet build|test|format`, read-only git, `tools/checks/check-diagnostics.sh`, `tools/checks/check-context-refs.sh` and its self-test, and five of the seven hook self-tests; any other command asks under the normal permission rules. Everything Rule E covers, as listed for `pre-git-guard.sh` in the hook table above, is a permission ask whatever the allow list says: history-writing git, a `git stash` that moves work, every `gh` command that writes to GitHub (an issue, a comment, a review, a pull request, a release, a workflow run, a `gh api` write), `docker push`, `wrangler deploy/publish/secret` and `dotnet ef database update/drop`. Reads such as `gh release list/view/download`, `gh workflow list/view` and `gh run list/watch` pass.
