## How it works

**Write gate.** `WriteGateService` is what the worker reaches through the WorkerGate service ([[pages/services/host-control-plane]]); it never grants a permission and never approves an action, and since 2026-11-08 it rejects, and logs, a claimed action whose grant is gone (below). `RequestAsync` looks the scope up among the catalog rows of the feature by exact, case-sensitive scope text (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:540`) and answers, in order: an unknown feature or a scope the feature does not declare is `Refused` with "<scope> is not declared by <feature>"; a `Read` row is `Refused` with "<scope> is a read"; a feature whose state is not `Granted` is `Refused` with "The owner has not allowed <feature> to write; allow it on the Features screen of Scout Desktop."; a `Write` row is `Allowed` with an empty reason; an `IrreversibleWrite` row enqueues a pending action (feature, the scope as the action, target, summary) and is `Queued` with its id and "Waiting for the owner's approval on the Review screen of Scout Desktop." (`:360`). The grant is read from the state store on every request (`:343`), so a grant or a revocation on the Features screen applies to the next request without a restart. `RecordAsync` appends a `WriteLogEntry` with the time, feature, scope, target and outcome; it refuses an undeclared scope or a read row, refuses an `IrreversibleWrite` row recorded without an action id with "<scope> is irreversible; it is recorded only with an action the owner approved.", even under the grant (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:435`), and reads the grant live like a request (`:429`): a reversible `Write` row without it is refused with the same "has not allowed" text, and an irreversible one with "The owner revoked <feature>'s write permission before this action ran.", even when the owner approved the action before revoking; an approved action no worker claimed is refused and logs nothing (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:300`), while an action a worker claimed (`executing`) already ran on YouTube, so it is logged once with its outcome followed by " after revoke", approved by `owner`, marked executed under the queue's gate, and then refused, so it is never handed out again (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:461`, `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:277`). With an action id it requires an action the owner approved for the same feature, scope and target (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:378`); since 2026-11-11 a record that names another target than the approved action is refused with "Action '<id>' was approved for <target>, not <target>.", logs nothing and leaves the action approved (`:456`, `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:844`), then, inside the queue's `ExecuteAsync` (`:396`), looks the action id up in the write log, reading it back with `ListSinceAsync` only to the first entry older than the action's request (`:400`, `src/Scout.ControlPlane/Actions/JsonLinesWriteLog.cs:72`, `tests/Scout.ControlPlane.Tests/Actions/WriteLogTests.cs:53`), appends the entry with `ApprovedBy` `owner` when it is not there (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:435`), and only then marks the action executed. A failed append leaves the action approved, so the worker's retry records it once (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:318`); a failed mark after the append is reported to the caller with the log line kept and the action still approved, and the next record finds the line, marks the action executed and is refused with "Action '<id>' is already recorded in the write log." (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:485`, `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:339`). A worker does not record again after a failed record, it only logs the failure, so the control plane settles such an action itself, in `SettleRecordedAsync` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:216`), which looks the action's id up in the write log the same way and marks it executed with the logged outcome. It runs in two places. Before an action is handed out, in `ClaimUnrecordedAsync` (`:150`), so the next action is claimed instead and a write that ran is never sent again once its claim lapses (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:365`; the YouTube claim, where the thumbnail that waited on the upload is handed out, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:560`); an action its late record marks executed meanwhile is skipped the same way (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:430`). In the same read the claim looks for the owner's approval of the action: an irreversible action is never handed to the worker unless its approval is in the write log (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:193`). The three places that queue an approved action, the Approve of a waiting action, a card verdict and the operator's approve, save the approval in the queue and log it right after, in the same call, so an approval can be saved and not yet logged when a claim arrives. An action the owner approved is therefore never rejected for a missing entry while that entry is still being written: for one minute after its approval, `ApprovalLogWindow`, read on the injected `TimeProvider` against the action's `DecidedAt` (`:66`, `:198`), the claim returns such an action to the queue as approved through `IActionQueue.ReleaseAsync` (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:377`, `tests/Scout.ControlPlane.Tests/Actions/ActionQueueTests.cs:494`), hands it to no one on this poll and claims the next one, and the following poll finds the entry and hands it out, for each of the three (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:742`). While it waits it still counts as the oldest open action of its project, so a thumbnail never runs ahead of its upload (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:1199`). From one minute on, an approved action still without its entry is rejected with "its approval is not in the write log; approve it again" (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:59`), the rejection logged, and the next action claimed; it is never handed out (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:791`, `:679`). So an approval the log never took never reaches GitHub or YouTube, whatever its project or comment reads, as after an adopted winner whose approval and whose rejection both failed and a second adoption, where one change reaches the worker and its approval is in the log (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:1108`). A queue that cannot be written when the action is returned fails the claim: nothing is handed out, the action stays claimed, and after its lease it is handed out if its approval was logged meanwhile (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:814`). And before a claimed action is rejected, in `RejectAndLogAsync` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:269`), so a write that ran is never rejected as never finished, or as revoked, and asked for again (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:401`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:589`). When no claimed action matches, it returns after that one read of the queue, so a poll with nothing to settle or reject reads the queue twice, once here and once for the claim, as before this lookup existed, and that holds while another action runs within its lease (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:274`, `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:469`). A queue that cannot be written while a logged write is settled fails the claim: nothing is handed out, the action stays claimed and is settled after its lease (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:703`). A write log that cannot be read fails the claim and hands out nothing; the action stays claimed and is offered again after the lease (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:488`). A worker that stops after the call and before any record leaves no log line: a YouTube action is then still handed out again after the lease ([[pages/roadmap/followups]]), and a GitHub action, since 2026-11-10, is recorded as `failed: not confirmed` and never handed out again (Approved actions and the claim, below). A second record with the same action id, sequential or concurrent, fails as not approved, so an approval covers one write. So every logged irreversible write carries the owner as its approver; the WorkerGate service answers each refusal with `FailedPrecondition` and the log is left untouched. Since 2026-11-08 `RecordAsync` takes the optional `signedAs`, the login that signed the write, and the entry keeps it as `WriteLogEntry.SignedAs` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:408`, `src/Scout.ControlPlane/Actions/WriteLogEntry.cs:17`; [[pages/decisions/0044-scout-acts-on-github-as-its-own-app]]); the already-recorded lookup skips the owner's approval entry with or without a reason, `approved` or `approved: <reason>` (`IsApproval`, `src/Scout.ControlPlane/WriteGate/WriteGateService.cs:526`, `tests/Scout.ControlPlane.Tests/Integration/ApprovalsGrpcTests.cs:495`). Since 2026-11-11 `RequestAsync` also takes the request's group id and repository, as the worker's request names them, and queues an irreversible write with both; it never reads either from the payload, so a model argument named `groupId`, `group` or `repository` places nothing in another group (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:359`, `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:860`). Since review round 1 a worker request whose group id or repository is empty or whitespace is queued as one without that field, so no action lands in a group no set call can name (`src/Scout.Host.ControlPlane/Services/WorkerGateGrpcService.cs:45`, `tests/Scout.ControlPlane.Tests/Integration/WorkerGateGrpcTests.cs:224`). `CloseGroupAsync` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:562`) is the worker's report that a request ended; it stamps that group id's actions and approves, rejects or logs nothing (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:876`).
