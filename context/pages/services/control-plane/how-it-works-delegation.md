## How it works

**Delegation.** The owner's "delegate" on a project ([[pages/roadmap/youtube-channel-operator]], phase 7) is the control plane chaining the project's reversible stages; the worker is unchanged. `DelegateProjectAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:662`) takes the owner's narration voice, direction and motion and checks them first with the rules `ProduceProjectAsync` uses, the same private helpers and the same sentences, then asks the write gate for the `youtube` grant like `ProduceProjectAsync` and refuses, as `OperatorValidationException`, a project that is not `script_ready`, `media_ready`, or `failed` with a script ("Only a project with its script ready, its media ready, or a failed one with a script is delegated; this one is <status>.", `:693`). Otherwise it sets the init-only `OperatorProject.Delegated` (`src/Scout.ControlPlane/Operator/OperatorModels.cs:63`, `src/Scout.ControlPlane/Operator/OperatorService.cs:705`) and stores the voice, the direction and the motion on the project (`:706`, `:707`, `:708`): the request's voice always wins, empty meaning Scout's choice, so a project delegated from `script_ready` narrates in the voice the owner chose rather than always in Scout's; an empty motion means `gentle`, and the direction may be empty. It clears the error and queues the next stage (`:696`): a `media_ready` project with scenes, every one `ready`, goes to `assembly_queued` with its package started again as `AssembleProjectAsync` does, unless a scene still has a part the worker could make under the readiness the control plane stores (absent readiness means nothing is available): audio source `none` while `SpeechAvailable`, or visual source `text_card` while `ImagesAvailable` in a project that is not `own_pictures` (`src/Scout.ControlPlane/Operator/OperatorService.cs:699`), whose text cards stand for a picture the owner has not attached and which the worker never draws (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Format.cs:180`), or visual source `presenter` while `ImagesAvailable` in an `animated_character` project that has no `PresenterFile` yet, since the worker makes the presenter picture first; the rule reads the stored name, not the disk, as it reads the sources (`src/Scout.ControlPlane/Operator/OperatorService.cs:700`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Format.cs:198`), so a project produced before the voices existed is narrated rather than assembled mute (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:139`, `:157`); any other goes to `production_queued`, without the pending-claims check of `ProduceProjectAsync`, because in a delegated project unresolved claims block only the package approval. On a delegated project a worker save of `media_ready` whose scenes are all `ready` is stored as `assembly_queued`, its package started again, after every check the save already passes, so the worker's next take assembles it; a save with a scene not ready stays `media_ready`, and a save of `assembled` or `failed` is stored as sent (`src/Scout.ControlPlane/Operator/OperatorService.cs:469`). The worker can never set or clear `Delegated`: a save keeps the stored value whatever it sends, and a project the worker creates is never delegated (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:2874`). `ApprovePackageAsync` is unchanged, so a pending or unsupported claim still blocks the approval, and nothing in delegation approves a package or creates a YouTube action; a delegated project stops at `assembled` for the owner (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:2655`, `:2682`, `:2710`, `:2729`, `:2742`, `:2756`, `:2773`, `:2797`, `:2812`).

**Publication.** `PublishPackageAsync` takes the owner's privacy, `public`, `private` or `unlisted` ("A video is published as public, private or unlisted."), an optional publish time that must be in the future ("The publish time must be in the future.") and is accepted only with `private`, the status YouTube's `status.publishAt` needs ("A video with a publish time is uploaded as private; YouTube makes it public at that time."), and the made-for-kids and synthetic-media declarations (`src/Scout.ControlPlane/Operator/OperatorService.cs:1433`). It asks the write gate for the `youtube` grant like `ApprovePackageAsync`, then refuses a project and package that are not both `approved` ("Only an approved package is published; this one is <status>."), a project already on YouTube ("The video of this project is already on YouTube.") one whose publication is anything but `failed` without a video, `publish_approved` included, so a second click while the upload is queued is refused ("The video of this project is <status>; wait for the upload to end.", `:1422`). It also refuses while a YouTube action of the project is `executing` and not stale ("A YouTube action of this project is running; wait for it to end.", `:1402`). Otherwise the publication becomes `publish_approved` with the owner's four settings, no video id, upload time or error, keeping any earlier proposals and experiment, and the upload, `videos.insert` with the project id as its target, and, when the package has a thumbnail, `thumbnails.set` with the same target are queued already approved (`:1450`): the desktop's publish dialog listed them and the owner confirmed, which is the per-action consent Google's policy asks for. Each is one write-log entry, the scope as the action, outcome `approved`, approved by `owner`, with the action id (`:2008`). The upload's summary names the title and the privacy, or the UTC time a private video is made public. Before queuing them it rejects every action of the project still approved from an earlier publish, reason "superseded by a new publish", each logged with outcome `rejected: <reason>` (`:1461`), so an old thumbnail action can never sit before the new upload as the project's oldest open action. When the actions cannot be queued, or an approval cannot be logged, `ApproveOrRestoreAsync` returns the project to what it was before the call, unless it was saved again meanwhile, so the publication never stays `publish_approved` with nothing to run and the owner publishes again, queued once (`src/Scout.ControlPlane/Operator/OperatorService.cs:2040`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:611`, `:639`); a return that fails too is a warning in Scout's log, the owner is shown the first failure, and the project stays as the call saved it, for a publish, an experiment start and an adopted winner alike (`:1151`). When the rejection of the unlogged actions failed as well, they are still approved while the project is back to what it was; the next publish rejects them as superseded before it queues its own, so one upload is left to run (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:1077`); they would not run in any case, since the claim hands out no action whose approval is not in the write log (Write gate, above).

**Proposals and experiments.** The worker adds proposals, `title`, `thumbnail`, `topic` or `strategy`; `DecideProposalAsync` marks one `proposed` proposal `accepted` or `rejected` ("Proposal '<id>' is already <status>.", "Unknown proposal '<id>' in project '<id>'."), with no grant, like a claim decision. `StartExperimentAsync` takes the arm hours, 24 to 168, 0 meaning 48 ("Each arm runs 24 to 168 hours."), asks for the grant, and needs a video `published` or `scheduled` with its id ("Only a published or scheduled video is tested; this one is <status>."), no experiment `running` ("An experiment is already running on this video.") and an accepted `title` or `thumbnail` proposal ("Accept a title or thumbnail proposal first."). The kind is that of the newest accepted one; the arms are `control`, the package's title or thumbnail file ("The package has no <kind> to come back to." without it), then `variant-a` and `variant-b` from the first two accepted proposals of that kind, at most three arms, and those proposals become `tested` so no later experiment uses them again (`:1530`). The experiment starts `running` with `ArmHours`, and one `videos.update` (title) or `thumbnails.set` (thumbnail) action per arm, in order, then one more back to the control, are queued approved and logged like the publish, each targeting `<project id>:<experiment id>:<arm id>` with a summary that names the title or file and the hours (`:1883`). `AdoptExperimentWinnerAsync` asks for the grant, refuses an experiment already `adopted` ("The winner of this experiment is already adopted."), needs one `concluded` with a winner ("Only a concluded experiment with a winner is adopted."), sets it `adopted`, and, in the same store update, makes the winner the package's current value, `Title` for a title experiment and `ThumbnailFile` for a thumbnail one (`src/Scout.ControlPlane/Operator/OperatorService.cs:1631`), so a later experiment's control and restore action use it instead of putting the old value back; then it queues and logs one approved action to the winning arm. Both the start and the adoption return the project to what it was when their actions cannot be queued or an approval cannot be logged, as the publish does, so the experiment is started, or the winner adopted, again and queued once (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:664`, `:688`).
