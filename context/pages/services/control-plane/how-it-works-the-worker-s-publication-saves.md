## How it works

**The worker's publication saves.** The worker saves a publication through `SaveProjectFromWorkerAsync`. Without the grant it may still read a project, and save it, while a YouTube action of that project is `executing`, so what a write that already ran did is not lost after a revoke; that save may change only the publication's status, video id, upload time and error and the experiment arms' start and end, and anything else, or no executing action, is refused with the gate's sentence (`src/Scout.ControlPlane/Operator/OperatorService.cs:2297`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:1015`, `:1029`, `:1044`). A presenting save is never what a running action did, so it is refused with the gate's sentence without the grant even while a YouTube action of the project is executing, and nothing is stored, deleted or logged (`src/Scout.ControlPlane/Operator/OperatorService.cs:382`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Presenter.cs:165`). On a project the store holds as `approved` it sends `approved` back, the one status outside its own set it may send and only there; any other status, or any change to the script, claims, scenes, package or error, is refused with "The project is no longer assembling." (`src/Scout.ControlPlane/Operator/OperatorService.cs:427`, `:1947`), and `approved` on any other project is the status validation error. `PublicationRules.MergeFromWorker` (`src/Scout.ControlPlane/Operator/PublicationRules.cs:43`) keeps the stored publication when the worker sends none and refuses, as `OperatorTamperingException`: a publication on a project the owner has not published ("Only the owner publishes project '<id>'."), a different privacy, publish time or declaration ("Only the owner sets the privacy, the publish time and the declarations of project '<id>'."), `publish_approved` the store does not hold ("Only the owner sets the publication of project '<id>' to publish_approved."), a changed video id once one is stored ("Project '<id>' is on YouTube as '<video id>'; the worker may not change its video id."), a decided proposal changed or dropped, a new proposal or a `proposed` one sent decided (`:115`), and, in an experiment (`:134`), a new one, a different id or kind, or arms whose ids, labels or values differ ("Only the owner starts an experiment on project '<id>' and chooses its arms."), any change once it is not `running` ("The experiment of project '<id>' is over; the worker may not change it."), and a running one sent other than `running`, `concluded` or `inconclusive`. It refuses as `OperatorValidationException` a status outside `publish_approved`, `uploading`, `uploaded`, `scheduled`, `published` and `failed`, snapshots without a window of their own, proposals without an id of their own or outside the kinds and statuses, a thumbnail proposal without a safe thumbnail file, and a winner that is not an arm. The worker sets the status after `publish_approved`, the video id while it is unset, the upload time, the error, the arms' start, end and numbers, the winner, the result and the end. Snapshots merge by window: a window the worker sends replaces the stored one, the others stay (`:77`). `ArmHours` always comes from storage.

**Old research and the disconnect purge.** `ClearOldResearchAsync` clears the topic candidates of every project created more than 30 days ago and writes `projects.json` only when one had candidates; it needs no grant, so it runs with writes off or only an API key set (`src/Scout.ControlPlane/Operator/OperatorService.cs:1749`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:1060`); the host runs it at start and every 6 hours ([[pages/services/host-control-plane]]). The worker can no longer clear candidates on an approved project (refused as "The project is no longer assembling."); on a project created more than 30 days ago it may still empty the source links of claims, the owner's decided ones included (`src/Scout.ControlPlane/Operator/OperatorService.cs:403`, `:2165`); on a younger one the decided claim's links are refused as before. `PurgeYouTubeDataAsync` removes every publication's snapshots, every experiment arm's impressions, clicks and average view percentage (`src/Scout.ControlPlane/Operator/OperatorService.cs:1806`), and every project's topic candidates and claim source links, keeps scripts, scenes, media, packages, proposals, video ids and the experiments' arms, windows, winners and results, and needs no grant (`src/Scout.ControlPlane/Operator/OperatorService.cs:1788`); the host runs it when the desktop deletes the YouTube credentials, before deleting them ([[pages/services/host-control-plane]]).

**Comments.** The stored comments are the top-level comments the worker read on the owner's channel; `ListCommentsAsync` answers them newest first by `PublishedAt` with the ideas and the sync's state and needs no grant. A comment has a *live* action when the queue holds an approved or executing action on its `comment:<id>` target that is not stale; the comment's own status never stands in for one. `RequestCommentSyncAsync` asks the gate for the `youtube` grant, row "Scout's data folder", and stamps `SyncRequestedAt`. In a worker save, a `SyncedAt` at or after the request answers it (`src/Scout.ControlPlane/Operator/CommentRules.cs:82`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:302`); a non-empty `SyncError` with no newer `SyncedAt` is a failed sync, which sets the error and also answers the request, so the worker does not retry every minute (`:778`); a null or empty `SyncError` keeps the stored error, and a newer `SyncedAt` clears it, so a drafts-only run never answers or hides anything (`src/Scout.ControlPlane/Operator/CommentRules.cs:79`, `:84`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:908`). `DecideCommentAsync` takes `draft`, `dismiss`, `not_spam` or `hold`, anything else "A comment is decided as draft, dismiss, not_spam or hold.": `draft` needs the grant, refuses a comment with a reply on YouTube, "This comment already has a reply on YouTube." (`src/Scout.ControlPlane/Operator/CommentService.cs:59`), and moves a `new`, `drafted`, `failed` or `dismissed` comment that is not `spam` to `draft_requested`, clearing its approved text and error (`tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:316`); `dismiss` needs no grant and is refused, "A YouTube action on this comment is running; wait for it to end.", while the comment's action is executing or the comment is `replying` with a live action (`src/Scout.ControlPlane/Operator/CommentService.cs:289`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:763`); otherwise it rejects the comment's approved reply or hold with "dismissed by the owner", each rejection logged (`src/Scout.ControlPlane/Operator/CommentService.cs:78`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:737`), and a `replying` comment whose action is no longer live can be dismissed (`:795`); `not_spam` needs no grant and returns a `quarantined` comment to `new` with kind `other`; `hold` needs the grant, accepts only a `quarantined` comment, "Only a quarantined comment is held for review on YouTube; this one is <status>." (`tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:125`), moves it to `hold_approved` and queues one approved `comments.setModerationStatus` action on `comment:<id>` with the summary `Hold for review on YouTube: <author> on "<video title>": "<first 120 characters>"`, logged as the owner's approval like a publish (`:101`); when that action cannot be queued, or its approval cannot be logged, the comment goes back to what it was, so it can be held again (`tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:356`, `:428`). Every decision stamps `DecidedAt`. `ApproveReplyAsync` trims the text and refuses an empty one or one over 1000 characters, "A reply is 1 to 1000 characters.", and any control character but a new line, "A reply carries no control character other than a new line." (`:159`); it needs the grant, refuses a `quarantined`, `hold_approved` or `held` comment, "A quarantined comment gets no reply; mark it not spam first.", a `replied` one or any with a reply id, "This comment already has a reply on YouTube." (`src/Scout.ControlPlane/Operator/CommentService.cs:297`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:172`, `:862`), a `replying` one with a live action and one with an action executing, stores the text as `ApprovedText` with `reply_approved`, queues one approved `comments.insert` action with the summary `Reply to <author> on "<video title>": "<first 200 characters of the approved text>"` (`:138`), and only then rejects every other approved action on the same target as "superseded by a new reply", each rejection logged (`:214`); when the new action cannot be queued, or its approval cannot be logged, the comment goes back to what it was and the earlier reply stays approved (`:386`, `:404`). An approval that cannot be logged never leaves its action to run: `OperatorService.ApproveAsync` rejects what it queued with "its approval could not be logged; approve it again" (`src/Scout.ControlPlane/Operator/OperatorService.cs:1994`, `:197`), for a hold, a reply, a publish and an experiment alike (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:611`); the rejection is itself logged, `rejected: its approval could not be logged; approve it again`, when the log takes it, as after a cancelled call (`tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:478`), and when that rejection, its log entry or the comment's return fails too the owner still gets the first failure and Scout's log carries a warning (`:450`). Two approved replies can still stand on one comment after a superseded reply whose rejection could not be saved: the claim hands out one action per comment at a time, oldest first (`:565`), and the worker posts nothing for a comment that already carries a reply id (`src/Scout.Operator/ActionExecutor.cs:419`, `tests/Scout.Operator.Tests/ActionExecutorTests.cs:772`), so YouTube gets one reply, the text stored on the comment. `DecideIdeaAsync` decides a `proposed` idea once, "Idea '<id>' is already <status>.": used first checks the grant, so a refusal writes nothing (`src/Scout.ControlPlane/Operator/CommentService.cs:191`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:552`), then claims the idea as `used`, then starts a project on the idea's text through `StartProjectAsync`, the same grant and topic rules, and keeps the project's id; not used dismisses it without a grant (`tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:337`). A project that cannot be started returns the idea to `proposed`, so it can be used again (`tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:506`), and a return that fails too never hides why the project did not start, though that idea then stays `used` with no project and cannot be used again (`:523`); a claim that cannot be saved starts no project (`:593`), and two uses at once start one project and refuse the other as already used (`:607`).
