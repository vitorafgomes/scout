## How it works

**Approved actions and the claim.** `NextApprovedActionAsync` is the YouTube worker's only way to an approved action; a feature that runs its own approved actions names itself in the request and the host claims through `WriteGateService.ClaimNextApprovedAsync` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:118`, `src/Scout.Host.ControlPlane/Services/WorkerGateGrpcService.cs:164`; an empty id is the YouTube path): under the feature's grant only, the oldest approved action requested under the current grant, or an executing one whose 30-minute claim lapsed (`ClaimLease`, `src/Scout.ControlPlane/WriteGate/WriteGateService.cs:118`), with no origin reference and no project rule. Since 2026-11-10 `ClaimUnrecordedAsync` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:150`), the one claim GitHub and YouTube actions are handed out through, settles each action it takes in a fixed order: one whose write is already in the write log is marked executed with the logged outcome and is not handed out (`:174`); else one whose claim had lapsed, on a feature that declares `UnrecordedClaimMayHaveBeenSent` (`src/Scout.ControlPlane/Features/FeatureMetadata.cs:49`; GitHub does, `src/Scout.ControlPlane/Features/FeatureCatalog.cs:154`), is recorded as `failed: not confirmed` with "Scout stopped before it recorded this, so it may already be on GitHub: look there before asking for it again.", logged and never handed out again, because the worker that stopped between the send and the record may have sent it (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:179`, `:69`; the claim notes under the queue's gate that the action it takes was executing, `:156`); else it is handed out, and only when the write log holds the owner's approval of it (`:193`). YouTube does not declare it (`src/Scout.ControlPlane/Operator/OperatorService.cs:1679` is its call into the same claim), so a YouTube action whose claim lapsed with no record is still handed out again ([[pages/roadmap/followups]]). Both claims reject through `RejectAndLogAsync` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:269`), which marks an action whose write is logged executed instead of rejecting it (Write gate, above). A claim that lapsed across a revoke or a new grant is rejected, for such a feature, with the same sentence in place of `NeverFinished` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:124`; `tests/Scout.ControlPlane.Tests/Integration/ApprovalsGrpcTests.cs:148`, `:176`), and a not-confirmed record that cannot be written fails the claim and hands out nothing (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:551` the log, `:583` the queue). Tests: `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:519` (one row per case: each of the five GitHub rows not confirmed, a GitHub write already in the log settled first, a YouTube write in the log settled, a YouTube claim with no record handed out again) and `tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs:163` (through the worker's executor: nothing is sent).
 Since 2026-11-08 the claim first rejects, even while the feature holds no grant at all, every executing action of the feature whose claim lapsed and that was asked before the current grant or has no grant to run under, through `IActionQueue.RejectExecutingAsync` (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:401`), with `NeverFinished`, "Scout was running it when writes were revoked and it never finished; ask again" (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:56`, `:125`), and logs each, so such an action never stays running forever (`tests/Scout.ControlPlane.Tests/Integration/ApprovalsGrpcTests.cs:148`, `:176`); a claim that has not lapsed is left running, since the worker may still record it (`:203`). The rejection writes the queue, then the log: a queue that cannot be written leaves the action executing, a log that cannot be written leaves it rejected with no log entry, and either way the worker's `CheckActionGrant` and `NextApprovedAction` fail, so the worker is never told the grant holds and gets no action (`:274`). `CheckGrantAsync` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:241`) is the worker's grant read just before it sends a claimed action: true while the action is executing for the feature and was asked under the current grant; otherwise, when the grant is gone or was given again after the request, it rejects the action with `writes were revoked`, logs it and answers false, and an action no longer executing answers false untouched (`tests/Scout.ControlPlane.Tests/Integration/ApprovalsGrpcTests.cs:420`, `:441`). The GitHub executor in the worker calls it right before it sends a verdict and sends nothing when the answer is false or the read fails (`src/Scout.Host.Console/GitHubActionExecutor.cs:128`, `tests/Scout.Host.Console.Tests/GitHubActionExecutorTests.cs:254`, `:288`), and records the verdict with the login that signed it (`src/Scout.Host.Console/GitHubActionExecutor.cs:172`). Without the `youtube` grant it answers null and claims nothing (`src/Scout.ControlPlane/Operator/OperatorService.cs:1671`). Since 2026-11-08 it first rejects, with `NeverFinished`, and logs every executing YouTube action whose claim lapsed and that is stale or has no grant to run under, through the same `WriteGateService.RejectAndLogAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:1662`, `src/Scout.ControlPlane/WriteGate/WriteGateService.cs:269`), so no YouTube action stays running forever either; a claim that has not lapsed is left running (`tests/Scout.ControlPlane.Tests/Integration/ApprovalsGrpcTests.cs:224`, `:253`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:983`, where the late record of such an action is now refused as not approved). Otherwise `JsonFileActionQueue.ClaimNextAsync`, under the queue's gate, takes the `youtube` actions that are `Approved`, or `Executing` with a claim older than 30 minutes (`src/Scout.ControlPlane/Operator/OperatorService.cs:118`, `src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:162`), oldest first, and claims the first one the operator accepts: it must be the oldest open action of its project, the first part of its target, so a thumbnail waits for its upload and an experiment's switches run in order, and an arm of a running experiment waits until the arm live before it, started and not ended, has run the experiment's hours (`src/Scout.ControlPlane/Operator/OperatorService.cs:1683`, `:1940`). An action is stale when it was approved, or, executing, claimed, before the owner's current grant began (`GrantedAt`): it is never handed out again and never holds back its project, so an action running when the owner revoked cannot run again under a later grant (`src/Scout.ControlPlane/Operator/OperatorService.cs:1924`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:983`); the worker may still record it. Granting a feature already granted keeps the time the grant began, and since 2026-11-08 so does enabling it again while granted (`src/Scout.ControlPlane/Features/FeaturesService.cs:314`, `tests/Scout.ControlPlane.Tests/Integration/ApprovalsGrpcTests.cs:339`), so only a revoke and a new grant make older approvals stale (`src/Scout.ControlPlane/Features/FeaturesService.cs:362`, `tests/Scout.ControlPlane.Tests/Features/FeaturesServiceTests.cs:375`). The claim sets `Executing` and `ClaimedAt` and writes the file; when none is eligible the file is not written. `ExecuteAsync` and `RecordAsync` take an `Approved` or `Executing` action, so the worker's `RecordWrite` consumes a claimed action (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:530`, `src/Scout.ControlPlane/WriteGate/WriteGateService.cs:467`); the already-recorded lookup skips the owner's `approved` entry of the same action id (`:501`, `:537`), so the first record logs the worker's outcome beside it and a second is refused as not approved. The queue keeps `Executing` actions whatever their age, and `ListPendingAsync` lists them with the pending ones and, since 2026-11-08, the approved ones no worker claimed yet, oldest first, so the Review screen shows what waits to run and what is running (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:450`); an approval or rejection of one fails as already decided, "Action '<id>' is already executing.". When a worker save ends a running experiment (`concluded` or `inconclusive`), its arm actions still approved are rejected, reason "The experiment ended before this arm ran.", except the last action back to the control, the restore, which still runs (`src/Scout.ControlPlane/Operator/OperatorService.cs:487`). `CancelApprovedYouTubeActionsAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:1712`), which the host runs when the owner revokes the YouTube write grant, disables YouTube or deletes its credentials ([[pages/services/host-control-plane]]), rejects every approved YouTube action with "The owner revoked YouTube writes before this action ran.", each logged, so no stale approval runs under a later grant, leaves `executing` ones to their record, and ends every running experiment `inconclusive` with that sentence as its result. `JsonFileActionQueue.RejectApprovedAsync` does each rejection under the queue's gate (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:180`). `OriginReferenceForWorkerAsync` answers the origin reference of the project an action targets, the first part of its target, or null (`src/Scout.ControlPlane/Operator/OperatorService.cs:1692`). Built for the GitHub executor of [[pages/decisions/0038-code-quality-assistant-on-the-write-gate]] phases 2 and 3 and unused since its v1.3 the same day (the review and the issue became direct writes under the grant); kept as the capability for a future irreversible action of another feature, with its tests on the YouTube feature.
