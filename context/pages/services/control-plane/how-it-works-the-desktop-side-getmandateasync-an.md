## How it works

The desktop side: `GetMandateAsync` answers the empty mandate when none is saved. `SaveMandateAsync` trims every field, drops blank pillars and blocked topics, stamps `UpdatedAt`, and refuses an empty objective or language, more than 5 pillars or a pillar over 80 characters, joining the messages ("The objective is required.", "At most 5 pillars.", "Each pillar is at most 80 characters.", "The language is required."). The mandate carries no narration voice: the owner moved that choice from the channel to the video on 2026-11-03, so it is the project's (Production and scenes, below); a mandate file saved before then still loads, its voice ignored, and the next save drops it (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:122`). `ListProjectsAsync` returns the newest first; a limit of 0 or less means 50 and at most 200 are returned. `StartProjectAsync(topic, format, direction)`, and since phase 8c-A its overload `StartProjectAsync(topic, format, direction, presenter)`, which also takes the presenter description of the animated character below (`src/Scout.ControlPlane/Operator/OperatorService.cs:220`, `:229`), trims the topic, refuses one outside 3 to 200 characters ("The topic must be 3 to 200 characters."), takes the format, trimmed, `generated_pictures` (`OperatorService.GeneratedPictures`), `own_pictures` (`OwnPictures`), since phase 8b `own_video` (`OwnVideo`) or, since phase 8c-A, `animated_character` (`AnimatedCharacter`), an empty one meaning `generated_pictures` and any other, `ai_presenter` and a differently cased one included, refused as "The format is generated_pictures, own_pictures, own_video or animated_character." (`src/Scout.ControlPlane/Operator/OperatorService.cs:741`, `:752`), and the owner's direction under the rules of `ProduceProjectAsync` below, every refusal before the grant is asked and with nothing stored or logged (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Format.cs:19`, `:39`, `:91`), then asks the write gate for the `youtube` grant like a worker save and, without it, refuses with the gate's text as `OperatorWriteRefusedException` (`src/Scout.ControlPlane/Operator/OperatorService.cs:220`), which the desktop receives as `PERMISSION_DENIED`; with it, it stores a project of origin `desktop` with that format and that direction, `queued`, or `recording_waiting` in `own_video`: a project of the owner's own video waits for the owner's recording, and no worker takes it until the recording is attached (`src/Scout.ControlPlane/Operator/OperatorService.cs:237`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.OwnVideo.cs:56`). The format never changes after: no desktop call takes it again, a worker save of an existing project builds it from the stored one and never takes the format or the direction it sends (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Format.cs:105`). Since phase 8d, superseding the 8a rule that a chat project is `generated_pictures` with no direction, a project the worker creates from chat takes the format and the direction the owner asked for in the chat, under the same rules and sentences as `StartProjectAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:354`, `:355`): an empty format is `generated_pictures` (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Format.cs:124`), a format Scout does not make is refused with nothing stored or logged (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Format.cs:148`), a chat project in `own_video` is refused with "A video of your own recording is started in Scout Desktop, Production, where you attach the recording.", nothing stored or logged, because the recording is attached only on the desktop (`src/Scout.ControlPlane/Operator/OperatorService.cs:359`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Format.cs:165`), and a direction over 1000 characters is refused by the same `DirectionOf` before anything is stored (`src/Scout.ControlPlane/Operator/OperatorService.cs:355`). A comment idea the owner uses starts a `generated_pictures` project with no direction. `DecideClaimAsync` takes `supported`, `unsupported` or `waived`, anything else being "A claim is decided as supported, unsupported or waived.", needs a note for `waived` ("A waived claim needs a note saying why."), and stamps the claim's `DecidedAt`, which marks it as the owner's decision. An unknown project or claim is `OperatorNotFoundException`. No desktop method returns a project's `OriginReference` (`src/Scout.ControlPlane/Operator/OperatorService.cs:2082`).

The worker side: `SaveProjectFromWorkerAsync`, `GetProjectForWorkerAsync`, `ListProjectsForWorkerAsync` and `NextQueuedProjectAsync` first ask `WriteGateService.RequestAsync` for the `youtube` feature's `Write` row "Scout's data folder", so the grant is read live and a refusal carries the gate's own text, "The owner has not allowed youtube to write; allow it on the Features screen of Scout Desktop." (`src/Scout.ControlPlane/Operator/OperatorService.cs:2274`). The mandate read is not gated: it is a read of the owner's brief. The two reads return what the desktop sees, owner-decided claims with their status and note included, with the desktop's limit rules except that a worker list returns up to 5000 projects, so its data hygiene reaches older ones, and without the origin reference on the wire, so the worker can send an owner's decision back unchanged. A save then refuses, as `OperatorValidationException`, a status other than `researching`, `scripting`, `transcribing`, `script_ready`, `producing`, `media_ready`, `assembling`, `assembled` or `failed`, a claim without an id, duplicate claim ids and a claim status outside `pending`, `unsupported`, `supported` and `waived` (`:328`, `:2132`), a scene that breaks the scene rules below (`:329`), and a package that breaks the package rules below; and, as `OperatorTamperingException`, a claim the worker marks `supported` or `waived` unless the stored claim already has that status (`:2152`), a claim the owner decided that comes back changed in text, status, note, risk or source links (the links compared in order) or does not come back (`:2166`), a different topic or origin on an existing project (`:378`), and a scene change only the owner may make (`:405`). On a project the owner queued for production again (`production_queued`), every worker save is refused, a `failed` one included; on any other project the store no longer holds as `producing`, because the owner regenerated a scene or produced it again between the worker's read and its save, a save that sends `producing` or `media_ready`, or whose merged scenes differ from the stored ones, is refused as `OperatorTamperingException`, `FAILED_PRECONDITION` on the wire, with "The project is no longer producing." (`:455`), and the owner's change stays; the worker stops on those words ([[pages/services/operator]]). Each save that succeeds appends one `WriteLogEntry` to `writes.log` as a reversible write under [[pages/decisions/0032-per-feature-write-permissions]]: feature `youtube`, action "Scout's data folder", the project id as target, outcome `saved <status>`, no approver (`:2262`); a refused save appends nothing. An empty id creates a project of origin `chat` that stores the origin reference; an existing project keeps its topic, origin, creation time, owner decisions and reference, and its `BackgroundFile` and `RecordingFile` exactly as stored, whatever the worker sends (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:1394`); it takes the worker's `RecordingMs`, the recording's length the worker measures, only while the stored project is `transcribing`, and keeps the stored one otherwise (`src/Scout.ControlPlane/Operator/OperatorService.cs:418`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.OwnVideo.cs:166`); a save of `transcribing` on a project that is no longer `transcribing`, a late progress save after the project failed, is refused as `OperatorTamperingException` with "The project is no longer transcribing; the worker's transcript was not saved.", nothing stored, the sentence the worker stops quietly on (`src/Scout.ControlPlane/Operator/OperatorService.cs:398`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.OwnVideo.cs:375`, `tests/Scout.Host.Console.Tests/OperatorContractTests.cs:529`). `NextQueuedProjectAsync` takes the oldest `queued` project and moves it to `researching`, or to `transcribing` when it is `own_video`, whose recording the owner attached (`src/Scout.ControlPlane/Operator/OperatorService.cs:1877`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.OwnVideo.cs:74`), and never takes a `recording_waiting` one; when none is queued, a project with a presenter request, as the automatic presenter below says; else the oldest `production_queued` project and moves it to `producing`; when neither waits, the oldest `assembly_queued` project and moves it, and its package, to `assembling` (`src/Scout.ControlPlane/Operator/OperatorService.cs:1893`, `:558`); when none of those waits, the oldest project left in `researching`, `scripting`, `transcribing`, `producing` or `assembling` whose `UpdatedAt` is more than 15 minutes old, back in `researching` or, for `transcribing`, `producing` and `assembling`, in the same status (`:117`, `:1899`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.OwnVideo.cs:195`); the pipeline saves at every stage, so a live run is never that stale, and a run a worker shutdown cut short is taken again. It moves the project with a fresh `UpdatedAt` inside one `UpdateProjectsAsync`, so two callers never take the same project, appends `saved <status>` for it to the write log, and returns it with its reference. It first reads the list outside the store's write path and returns null when nothing waits, and the change answers null under the gate when another caller took it first, so an idle poll never rewrites `projects.json`.
