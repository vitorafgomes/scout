## How it works

`RemovePresenterVersionAsync(projectId, versionId)` removes a presenter version the owner made by mistake, a duplicate, from the desktop only (`src/Scout.ControlPlane/Operator/OperatorService.cs:2878`, [[pages/roadmap/production-screen]]). Inside the store update it refuses, as `OperatorValidationException` with nothing stored, a `presenting` project with "The project is making its presenter; wait for it to finish.", since the job's save may change no version it has, and the current version, the one whose picture and preview are the project's `PresenterFile` and `PresenterPreviewFile`, with "The current presenter cannot be removed; choose another version first."; an id the project has no version for, an empty one or one an earlier removal took included, is `OperatorNotFoundException` with "That presenter version is no longer there.", and the version found is dropped by its position (`:2888`, `:2891`, `:2897`, `:2915`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Presenter.cs:688`); the current version is refused only while it is the last version naming the current picture and preview, so a duplicate of a built-in presenter, whose twin carries the same pair, is removed and the last of them is then refused (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Presenter.cs:671`); comparing the preview as well as the picture is what lets the owner remove one of two versions of the same built-in presenter, which share one picture, and a version that shows the project's picture with another preview, whose picture then stays (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Presenter.cs:721`). It drops the version and keeps the project's presenter, mouth box, preview, source, status and package, so an approved video stays approved; once the store holds the change, the removed version's picture and preview are deleted from the media directory through `DeleteForgotten` unless the current pointers or another version still name them, as the pruning past 10 versions does, a file that cannot be deleted logged and left with the store already changed (`:2783`, `:2724`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Presenter.cs:706`). No grant is asked for and no write-log entry is written; it has no chat variant (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Presenter.cs:640`).

A media file name is a plain name: not empty, at most 120 characters, no leading dot, no `..`, no backslash, no character the platform forbids in a file name (the folder separator among them), and an audio extension `.mp3`, `.wav`, `.m4a`, `.ogg` or a visual one `.png`, `.jpg`, `.jpeg`, `.webp`, or, for the owner's recording, `.mp4`, `.mkv`, `.webm` or `.mov`, compared without case (`src/Scout.ControlPlane/Operator/SceneRules.cs:36`, `:32`); it is checked wherever a name is accepted, from the desktop's attach and from a worker save. The media directory is `<folder of features.json>/operator/<project id>`; the id must be 32 hex digits, the store's own id format, so no path can escape (`src/Scout.ControlPlane/Operator/OperatorService.cs:2193`), the project must exist, and the folder is created with the default permissions of its parent; when it cannot be created (a file in the way, no permission) the `IOException` propagates, which `OperatorMapping.Guard` does not map, so the desktop receives gRPC `UNKNOWN`. The desktop's `GetMediaDirectoryAsync` and the worker's `GetMediaDirectoryForWorkerAsync`, which needs the grant, return its absolute path. The voice samples directory is `<folder of features.json>/operator/voice-samples`, a fixed name beside the project directories that is never a 32-digit project id, so a project's media directory and its deletion never reach it; it holds one sample per bundled voice, which the worker makes ([[pages/services/operator]]). The desktop's `GetVoiceSamplesDirectoryAsync` answers its absolute path, created when missing, with no grant, like the desktop's project media directory, and the worker's `GetVoiceSamplesDirectoryForWorkerAsync` answers it with no grant either, because the samples are Scout's own data and the desktop's Preview must work before the owner grants YouTube writes (`src/Scout.ControlPlane/Operator/OperatorService.cs:2322`, `:2331`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.VoiceSamples.cs:11`).

A worker save checks the scenes it sends: ids present and unique, `Status` one of `planned`, `generating`, `ready`, `failed`, `AudioSource` one of `generated`, `owner`, `none`, `recording`, `VisualSource` one of `generated`, `owner`, `text_card`, `stock`, `recording`, `presenter` (`src/Scout.ControlPlane/Operator/SceneRules.cs:26`, `:27`), a duration not below 0, and every file name (`:62`); a `stock` visual, a freely licensed picture the worker fetched from Openverse ([[pages/services/operator]]), must carry its `VisualFile` and a `VisualCredit` that is not blank, else the save is refused with "Scene '<id>' shows a stock picture; it needs the picture's file and its credit." (`:83`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.StockPictures.cs:16`). A scene whose audio or visual source is `recording`, a clip of the owner's recording, needs a `ClipStartMs` not below 0 and a `ClipEndMs` after it, else the save is refused with "Scene '<id>' shows the recording; it needs a clip that ends after it starts." (`src/Scout.ControlPlane/Operator/SceneRules.cs:88`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.OwnVideo.cs:294`); the worker sets both, and the owner's edits never change them. The worker also sets `VisualQuery`, the search terms it planned, kept as sent. When the project has no scenes the worker adds its own, none locked and none with an `owner` source. Once scenes exist it can neither add nor drop one, and a worker that claims an `owner` source the stored scene does not have is refused; each of those is `OperatorTamperingException`. Otherwise the save is merged with the stored scenes, in their stored order (`src/Scout.ControlPlane/Operator/SceneRules.cs:112`): the worker sets a scene's status, error, generated sources and files, duration and visual prompt, and what the owner owns comes from storage whatever the worker sends, the `Order`, `Locked` and `Narration` of every scene (`src/Scout.ControlPlane/Operator/SceneRules.cs:143`), so a save read before the owner's text edit cannot bring the old text back (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:1413`), and the worker sets a scene's text only when it plans the scenes; a locked scene whole (`src/Scout.ControlPlane/Operator/SceneRules.cs:136`), and the owner's audio or visual with its file (`src/Scout.ControlPlane/Operator/SceneRules.cs:144`, `:154`), an owner visual always without a credit, so a worker save read before the owner's attach over a stock picture cannot bring its credit back (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.StockPictures.cs:30`); the attach itself clears it (`src/Scout.ControlPlane/Operator/OperatorService.cs:942`). The duration of an owner audio stays the worker's only when the worker sent that same owner file; else the stored one stays. So an owner reorder, lock or attach between the worker's read and its save never fails the run.

**The owner's edits from the chat.** Since phase 8d ([[pages/roadmap/youtube-channel-operator]], [[pages/decisions/0033-channel-operator-architecture]]) the worker may ask, for the owner in a chat, for the scene edits, the production and the delegation the desktop makes, through seven methods the WorkerGate service reaches with the worker token alone ([[pages/services/host-control-plane]]): `EditSceneTextFromChatAsync`, `RegenerateNarrationFromChatAsync`, `RegenerateSceneFromChatAsync`, `SetSceneLockedFromChatAsync`, `ReorderScenesFromChatAsync`, `ProduceProjectFromChatAsync` and `DelegateProjectFromChatAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:2337`, `:2342`, `:2347`, `:2352`, `:2357`, `:2365`, `:2373`). Each runs through `ViaChatAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:2379`): it asks the write gate for the `youtube` grant on the project id like a worker save, then makes the desktop's change with the desktop's rules and sentences (a locked scene, a text outside 1 to 700 characters, an order that does not name every scene once, a project production or delegation does not take, an unknown project or scene), and only then, when the stored project differs from the one read before the change, its `UpdatedAt` and origin reference aside, appends one write-log entry: feature `youtube`, action "Scout's data folder", the project id as target, no approver and no action id, and the outcome `edited the text of scene <id> via chat`, `asked for the narration of scene <id> again via chat`, `asked for scene <id> again via chat`, `locked scene <id> via chat`, `unlocked scene <id> via chat`, `reordered the scenes via chat`, `queued production via chat` or `delegated via chat`. A change that changes nothing, a reorder to the order the scenes have or a lock of a locked scene, answers the project and logs nothing (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Chat.cs:179`); a write log that cannot be appended after the change was stored leaves the change standing, answers the project and writes a warning with no project text to the control plane's log (`:165`). A refusal, the grant's or a rule's, stores nothing and logs nothing; no action is queued, and nothing but `projects.json` and `writes.log` changes (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Chat.cs:51`, `:77`, `:98`, `:147`). The scene id in an outcome is that of a scene the change found, so an id that names no scene ends as `NOT_FOUND` before anything is logged. The chat's production and delegation pass a blank voice, direction or motion to the core as null, so the project keeps its own, and check a non-blank one with the desktop's sentences before storing it (`src/Scout.ControlPlane/Operator/OperatorService.cs:2376`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Chat.cs:113`); delegation's core is `DelegateAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:682`). The desktop's own scene edits still need no grant and write no write-log entry (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.SceneText.cs:134`). Deleting a project, attaching media, deciding a claim, assembling, approving, publishing and every comment decision have no chat variant.
