## How it works

**Deletion.** `DeleteProjectAsync` (`src/Scout.ControlPlane/Operator/OperatorService.cs:1122`) is the owner's edit of Scout's own state, so it needs no grant, like a scene edit. It answers NOT_FOUND for an unknown id and refuses, as `OperatorValidationException`, a project that is researching, scripting, transcribing, producing, assembling, presenting or whose publication is uploading ("A project that is researching, scripting, transcribing, producing, assembling, presenting or uploading cannot be deleted; wait for it to finish or fail.", `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.OwnVideo.cs:227`), and one with an approved or executing YouTube action on the project or its `<projectId>:` arms ("The project has pending YouTube actions; finish or cancel them first."). Otherwise it removes the project from the store under the gate, logs `deleted project` as the owner's, and only then deletes the project's directory; a log that cannot be appended puts the project back where it was in the list, unless one with its id is stored again meanwhile, leaves its folder untouched and fails with the log's exception, so a deletion is never left without its record (since 2026-11-11, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:2995`). A deletion and an owner call that queues a project's approved actions never overlap: one operator-wide gate (`src/Scout.ControlPlane/Operator/OperatorService.cs:128`, taken through `HoldProjectActionsAsync`, `:2071`) is held by the delete from before its open-actions read to its end (`:1125`), and by the publish, the experiment start and the adopted winner from before their project save to the end of their queueing, the restore of a failed queueing included (`:1406`, `:1524`, `:1606`). So either the approval queues first and the delete then finds its action open and is refused, or the delete runs first and the approval then finds no project (NOT_FOUND); an approved action never names a deleted project, and a deleted media folder never has one. Nothing awaited under the gate takes it again; the wait honours the caller's token, so a cancelled delete leaves the project, its folder and the write log as they were. Comment actions name no project and stay outside the gate (since 2026-11-11, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.DeletionRace.cs:109`, `:131`, `:152`, each order parked deterministically at the action queue for each of the three approvals). The directory under the operator media root, which `MediaDirectoryOf` builds from a 32-digit id alone so it cannot leave the root; if the folder cannot be deleted it throws `OperatorStoreException` ("Scout removed the project but could not delete its media folder.") without a path. Nothing leaves the process: a video already on YouTube stays there (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs`, the `Delete_` tests).

**Assembly and the package.** `AssembleProjectAsync` asks the write gate for the `youtube` grant like `ProduceProjectAsync`, then refuses, as `OperatorValidationException`, a project that is not `media_ready`, `assembled` or `failed` ("Only a project with its media ready, an assembled one, or a failed one with every scene ready is assembled; this one is <status>."), one without scenes ("The project has no scenes to assemble.") and one with a scene not `ready` ("1 scene is not ready; regenerate it or attach its media before assembly.", "<n> scenes are not ready; regenerate them or attach their media before assembly."); otherwise it sets `assembly_queued`, clears the project's error and starts the package again (`src/Scout.ControlPlane/Operator/OperatorService.cs:1242`): status `assembly_queued`, no video, Shorts, thumbnail, checks, duration or error, rights not confirmed, not approved, and the title, description and tags kept, with `MetadataEdited` and `MetadataSavedAt`, only when the owner edited them, else empty for the worker to fill (`src/Scout.ControlPlane/Operator/PackageRules.cs:35`). The package's own status is `assembly_queued`, `assembling`, `assembled`, `approved` or `failed`; the owner sets `assembly_queued` and `approved`, the worker the other three.

A worker save that carries a package is checked first (`src/Scout.ControlPlane/Operator/PackageRules.cs:48`): a status in that set, no duration, Shorts duration or Shorts start below 0, a title, description and tags within YouTube's limits once any of them is written (empty, the package is still unwritten), every check named with a result `pass`, `warn` or `fail`, and safe file names, the video and each Shorts cut `.mp4`, the thumbnail `.png` or `.jpg`, under the scene file name rule (`src/Scout.ControlPlane/Operator/SceneRules.cs:36`). A worker cannot start a project already `assembling` or `assembled` or with a package (`src/Scout.ControlPlane/Operator/OperatorService.cs:341`). The merge (`src/Scout.ControlPlane/Operator/PackageRules.cs:96`) keeps the stored package when the worker sends none, so a save from a stage that does not know the package leaves it as it is; otherwise the worker's package stands, and it is `OperatorTamperingException` when the worker confirms the rights ("Only the owner confirms the media rights of project '<id>'."), sets or changes `ApprovedAt` ("Only the owner approves the package of project '<id>'."), sends `assembly_queued` or `approved` the store does not hold ("Only the owner sets the package of project '<id>' to <status>."), changes `MetadataEdited` ("Only the owner edits the package metadata of project '<id>'."), or changes the title, description or tags once the owner edited them ("The owner edited the package metadata of project '<id>'; the worker may not change it."). Until then the worker sets them, and always `AssembledAt` and `ThumbnailDescription`, refused with an `OperatorValidationException` when an `AssembledAt` comes on a package still `assembly_queued` or `assembling` or the description is over 300 characters; the merge keeps the stored `MetadataSavedAt` and `RightsConfirmedAt` whatever the worker sends (`src/Scout.ControlPlane/Operator/PackageRules.cs:139`). A save that sends `assembling` or `assembled`, or a package that differs from the stored one, its lists compared item by item (`:143`), is refused with "The project is no longer assembling." unless the store holds the project as `assembling` and the save leaves the scenes as stored, and every worker save on a project the store holds as `assembly_queued` or `approved` is refused with the same words (`src/Scout.ControlPlane/Operator/OperatorService.cs:447`), so a stale run never overwrites a new assembly or the owner's approval. This check comes before the production one, so an assembler whose project the owner sent back to production, by regenerating a scene, reads "no longer assembling", the words it stops on ([[pages/services/operator]]). A save that reports `assembled` needs the package's video file, and every file it names, the video, the thumbnail and each Shorts cut, must be in the project's media directory ("An assembled package needs its video file.", "'<name>' is not in the project's media folder.", `:459`, `src/Scout.ControlPlane/Operator/PackageRules.cs:158`).

The owner's package edits need a package ("Project '<id>' has no package yet; assemble it first.", `src/Scout.ControlPlane/Operator/OperatorService.cs:2253`) and answer the project without its origin reference. `EditPackageMetadataAsync` trims the title, description and each tag and refuses, joining the messages, a title outside 1 to 100 characters, a description over 5000, a tag outside 1 to 100 and tags over 500 characters together, YouTube's limits, the tags counted YouTube's way, two more for a tag with a space and a comma between tags, as the worker counts them ("The title is 1 to 100 characters.", "The description is at most 5000 characters.", "Each tag is 1 to 100 characters.", "The tags are at most 500 characters together.", `src/Scout.ControlPlane/Operator/PackageRules.cs:175`, `:233`); it is allowed on an `assembled` or `approved` project ("Only the metadata of an assembled or approved package is edited; this one is <status>."), sets `MetadataEdited` and `MetadataSavedAt` (`src/Scout.ControlPlane/Operator/OperatorService.cs:1301`), and sends an approved package back to `assembled` without its `ApprovedAt`; the rights confirmation stays. It runs the `metadata` and `discoverability` checks again over the owner's values, the project's topic and the mandate's pillars, with the worker's rules and sentences, and drops the worker's two: `metadata` fails outside YouTube's limits, `discoverability` warns when the title shares no word of three letters or more with the topic or the pillars, or the description has no `0:00` chapter line (`src/Scout.ControlPlane/Operator/OperatorService.cs:1298`, `src/Scout.ControlPlane/Operator/PackageRules.cs:203`); the other checks stay, so the approval reads checks that match the metadata it approves. `ConfirmMediaRightsAsync` sets `RightsConfirmed` and `RightsConfirmedAt`, a repeat confirmation keeping the first time (`src/Scout.ControlPlane/Operator/OperatorService.cs:1258`) on an `assembled` project only ("Media rights are confirmed on an assembled package; this one is <status>."); a new assembly clears it. Neither needs the grant, like the scene edits. `ApprovePackageAsync` asks the write gate for the grant, refuses a project that is not `assembled` ("Only an assembled package is approved; this one is <status>."), then refuses, joining every cause, a package whose rights are not confirmed ("Confirm the media rights first."), one with a failed check ("1 check failed.", "<n> checks failed.") a project with a claim neither `supported` nor `waived` ("1 claim is not supported or waived.", "<n> claims are not supported or waived."), and metadata outside YouTube's limits, with the same sentences as the edit (`src/Scout.ControlPlane/Operator/OperatorService.cs:1346`); otherwise it sets the project and the package `approved` with `ApprovedAt` and appends a write-log entry, outcome `approved package`, approved by `owner` (`src/Scout.ControlPlane/Operator/OperatorService.cs:1317`, `:1360`).

An owner scene edit that changes the video, an attach, a regenerate or a reorder into a new order, on an `assembled` or `approved` project takes the approval back (`src/Scout.ControlPlane/Operator/OperatorService.cs:2084`, `src/Scout.ControlPlane/Operator/PackageRules.cs:189`): the package goes back to `assembled` without its rights confirmation, `RightsConfirmedAt` or `ApprovedAt`, and the project to `media_ready`, or to `production_queued` for a regenerate as before. The package files stay on disk, but neither the rights nor the approval can be given again until the owner assembles the project again. The same edit on a project `assembly_queued` or `assembling` sends the project and the package back to `assembly_queued`, the project to `production_queued` for a regenerate, so a running assembly reads that it is no longer assembling and its save is refused with those words, and the next take assembles the edited scenes. A lock or unlock, and a reorder into the order the scenes already have, do not change the video: they leave the status, the rights and the approval as they are, anywhere (`src/Scout.ControlPlane/Operator/OperatorService.cs:795`, `:809`).
