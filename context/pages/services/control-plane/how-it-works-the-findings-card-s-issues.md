## How it works

**The findings card's issues** (2026-11-11, commit C of [[pages/roadmap/approve-together]] phase 1, the owner's answer 3; keyed per issue since review round 1). `CardIssuesService` (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:25`, a singleton, `src/Scout.ControlPlane/ControlPlaneServiceCollectionExtensions.cs:80`) takes the desktop's `ApproveCardIssues`: the click on a findings card's Open issues is the owner's approval of exactly the issues the card sent. `ApproveAsync` (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:63`) trims each title and body once and from then on checks, stores, summarises, keys and sends the trimmed text, so padding can neither pass the check and then fail the queue's payload bound nor make the same issue another key (`:67`; `tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:181`). It refuses, as `FeatureValidationFailedException` with its dotted path and before anything is read, a blank card id or one over 200 characters, a repository that is not `owner/repo` under the GitHub plugin's name rule, anchored at the end of the text so a trailing newline does not pass (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:51`), no issue or more than `ActionDecisionService.MaxGroupSize`, 50, refused whole and never split, and a title that is not 1 to 256 characters or a body that is not 1 to 10,000, the plugin's own bounds, so an issue the owner approved is never refused at the send (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:168`; each refusal fired by its own input, `tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:154`; the largest issue queued, `:168`). Clicks run one at a time, so a second click that arrives while the first is still logging its approvals waits and answers the first click's rows, never a missing approval (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:74`, `tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:259`). It then needs the GitHub grant, `WriteNotGrantedException` otherwise (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:92`), rejects and logs an approved row of one of the click's issues asked before the current grant, which no worker would claim (`:105`), and queues each issue through `EnqueueApprovedOnceEachAsync` (`:116`) already approved on the declared `New issues` row with target `GitHubActions.create_issue` and, as payload and summary, exactly what a chat request for that issue queues, so the unchanged executor sends it (`:204`; `tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:108`). Each issue has its own key, kept on its row: the card's id and the SHA-256 of the repository and the issue's trimmed title and body (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:216`). A later click on the same card answers an issue whose row is waiting, approved, being sent, sent, recorded as `failed: not confirmed`, or, since review round 2, rejected by the claim path with `NotConfirmed` after a claim that lapsed across a revoke or a new grant, both of which may already be on GitHub, and queues again, approved in a new group, only an issue whose rows all failed or were rejected otherwise: for writes revoked before a claim or before the send, for an approval not in the log, or for any other reason (`:162`). The rejected row is recognised by `WriteGateService.IsNotConfirmed` (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:78`), built from the same two parts as `NotConfirmed` (`:72`), so it holds for the feature's name the claim path puts between them (`tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:389`; the opposite rows, `tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:325`; through the worker's real executor, no second POST for that issue, `tests/Scout.Host.Console.Tests/GitHubSetApprovalTests.cs:191`); so a repeat click retries exactly the failed ones, an issue sent is never sent again whatever else the set holds, and an issue whose text changed is a new issue (`tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:325`, `:413`; through the worker's real executor, ten issues with one answered 502, a second click sends only that one and a third sends nothing, `tests/Scout.Host.Console.Tests/GitHubSetApprovalTests.cs:161`). The same set in another order answers the same rows, in the click's order, and another repository or card queues its own (`tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:120`). The answer lists one row per issue, each with its own group, status, reason and outcome, and names as its group the group the click queued its issues in or, when it queued none, the first row's group (`ActionSetDecision.GroupId`, `src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:158`, `tests/Scout.ControlPlane.Tests/Integration/ActionSetGrpcTests.cs:297`), chosen by construction, not by the rows' request times; one `approved` entry per issue queued goes to the write log with the group id, none for an answered one, and an answered row whose approval is not in the log is named as a mismatch, `ApprovalNotInLog`, never as approved (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:153`; the table of grant by 0, 1, 50 and 51 issues by one or two clicks, `tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:72`; `:231`). A log that cannot take one of the approvals rejects every issue the click queued, and only those, with `ApprovalNotLogged`, "its approval could not be logged; open the issues again from the card", each rejection logged when the log takes it, and fails the call (`src/Scout.ControlPlane/WriteGate/CardIssuesService.cs:131`, `tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:199`). A row written by the set-level key of commit C is recognised by its card id and its text while that text is whole, waiting, approved or being sent; an executed one lost its text, so a click over it queues that issue again; nothing throws (`tests/Scout.ControlPlane.Tests/WriteGate/CardIssuesServiceTests.cs:449`). Through the worker's real executor and a fake GitHub, an issue at the plugin's bounds opens once across two clicks (`tests/Scout.Host.Console.Tests/GitHubSetApprovalTests.cs:140`). Nothing new is declared: the issues are the `New issues` row's irreversible writes, approved by the click, claimed, paced and recorded one by one as any approved action.

**Operator state.** The control plane is the only writer of the channel operator's state ([[pages/decisions/0033-channel-operator-architecture]]); the desktop reaches it through the `Operator` gRPC service and the worker through the operator methods of `WorkerGate`, the owner's chat edits among them ([[pages/services/host-control-plane]]). `JsonFileOperatorStore` keeps the mandate in `mandate.json` and every project, in creation order, in `projects.json`, both beside `features.json`. `UpdateProjectsAsync` reads the list, runs the caller's check-and-change and writes the list back under one gate (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:30`, `:142`); when the change throws or answers null, nothing is written (`:151`). A file that does not parse, or that holds the JSON literal `null` (since 2026-11-11, for all four operator files, `tests/Scout.ControlPlane.Tests/Operator/JsonFileOperatorStoreTests.cs:362`), is moved aside to `<name>.corrupt-<UTC yyyyMMddHHmmss>`, never overwritten, with `-1`, `-2` and so on appended while that name is taken, as the queue's is (`src/Scout.ControlPlane/CorruptFile.cs:13`, `tests/Scout.ControlPlane.Tests/Operator/JsonFileOperatorStoreTests.cs:157`), logged once as "Operator file at <path> is malformed; moved it to <aside> and started empty", and read as empty (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:231`, `:233`); a file that cannot be opened fails the call and stays where it is. A `projects.json` written before scenes existed reads with no scenes.
