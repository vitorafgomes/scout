## Scout bot (optional)

Below Connect the card offers "Use a Scout bot on GitHub (optional)" ([[pages/decisions/0044-scout-acts-on-github-as-its-own-app]]): the owner's own GitHub App, so the reviews, verdicts, comments and issues Scout posts show as its bot. `GitHubBot` (`ui/packages/main/src/oauth/github-bot.ts:103`) owns it in main: **Create** (`ui/packages/main/src/oauth/github-bot.ts:188`), on the owner's click, for their account or an organization: a loopback listener on a random free port from 49152 for one request and 5 minutes, a random `state`, and a local page that posts the manifest to `https://github.com/settings/apps/new` or `organizations/<org>/settings/apps/new`. The manifest names the App `Scout (<login>)`, not public, webhook inactive, with exactly Metadata, Contents, Checks and Commit statuses read and Pull requests and Issues write (`ui/packages/main/src/oauth/github-bot.ts:37`). The callback page is served through the shared `awaitCallback`'s `pages` option (`ui/packages/main/src/oauth/loopback-server.ts:74`). A wrong or missing `state` or the timeout stores nothing; then `POST /app-manifests/{code}/conversions` once (`ui/packages/main/src/oauth/github-bot.ts:318`), and the App id, client id, slug, account and private key go into the vault under the main-only key `github.bot`, writes all switched to the bot; the client secret and the webhook secret are discarded. A conversion that times out or answers 401, 422 or 5xx says why on the card and stores nothing. Cancel stops waiting, and a signal already aborted when `awaitCallback` is called rejects at once as cancelled and opens no listener (`ui/packages/main/src/oauth/loopback-server.ts:41`). **Token** (`ui/packages/main/src/oauth/github-bot.ts:369`): a JSON Web Token signed with `node:crypto`, RS256, issued 60 seconds in the past, valid 9 minutes, issued by the client id (`ui/packages/main/src/oauth/github-bot.ts:627`); `GET /app/installations`, the first installation's `POST /app/installations/{id}/access_tokens`, written as `{"access_token"}` to `<userData>/github-bot-token.json` through a temporary file and a rename, mode `0600`, then `GET /installation/repositories` for the list on the card, 100 a page, page after page until a page holds fewer than 100, at most 50 pages (5,000 repositories) (`ui/packages/main/src/oauth/github-bot.ts:496`); a failed listing, a later page that fails, or a listing still full at the 50th page keeps the token and the last full list, with one warn line and no token in it, and a token file that cannot be written leaves the worker on the owner's identity with "Scout could not write the bot's token file; it will try again.". Refreshed when less than 5 minutes remain, every minute and on wake, through one serial queue; a failed refresh keeps the current file and retries. An uninstalled App removes the file. The worker is restarted when the bot is created, first gets a token, loses its installation, is removed or has its writes switched, when a token refresh finds the installation covers a different set of repositories, and when the card loads and the re-read list differs, so "Change repositories" on GitHub takes effect when the owner comes back to the card (`ui/packages/main/src/oauth/github-bot.ts:177`; a failed re-read keeps the last list and restarts nothing, `ui/packages/main/test/oauth-github-bot.test.ts:458`, `:490`) (compared as a set; `ui/packages/main/src/oauth/github-bot.ts:637`, test `ui/packages/main/test/oauth-github-bot.test.ts:419`); at launch a worker built while the first token is being minted waits for it instead of being restarted (`ui/packages/main/src/oauth/github-bot.ts:149`). **Worker:** `buildEnv` adds `SCOUT__PLUGINS__GITHUB__BOTTOKENFILE`, `SCOUT__PLUGINS__GITHUB__BOTWRITES` (a comma list of `review`, `verdict`, `comment`, `issue`) and `SCOUT__PLUGINS__GITHUB__BOTLOGIN` (`<slug>[bot]`) only while the bot has a token (`ui/packages/main/src/worker/build-env.ts:84`); without a bot it emits exactly what it did before ([[pages/services/plugin-github]] reads them). **Card** (`ui/packages/renderer/src/app/features/github-connect.component.ts:193`; while GitHub is not connected the section still shows, as the prototype draws it: since 2026-11-12 its select is on, "An organization" shows the Organization field, and only Create is off, with "Connect GitHub first to create the bot." describing it; the account or organization chosen and the name typed there are kept when GitHub connects, because both selects and both fields show the same `botTarget` and `botOrg` (`:477`, `:484`, `:210`); the card asks main nothing about the bot, `ui/packages/renderer/src/app/features/github-connect.component.ts:462`, tests `ui/packages/renderer/src/app/features/github-connect.component.spec.ts:831`, `:1451`, `:1718`, `ui/e2e/tests/features-loaded.spec.ts:230`), through `scout:github.bot.status`, `create`, `cancel`, `remove` and `setWrites` (`ui/packages/main/src/ipc/github.ts:35`): none (help, account or organization, Create the bot on GitHub), creating (finish on GitHub, Cancel), created (Install the bot, Remove), installed (the repositories, folded behind "Repositories: N (<login> can post in these)" in the collapsible list of [[pages/services/desktop-ui]], one switch per action: Post reviews, Give verdicts, Comment on pull requests and issues, Open issues; an action switched off is signed as the owner; Change repositories, Remove), and the last error. The card polls the status every 3 s while creating or not installed. Remove asks first ("Remove the Scout bot?", Cancel focused), then deletes the key and the token file, shows the notice "Scout no longer uses the bot" once main answered (`ui/packages/renderer/src/app/features/github-connect.component.ts:881`) and links to the App's settings page on GitHub, where only the owner can delete the App; a refused removal shows main's sentence and no notice. The artboard draws Remove removing at once; the confirmation and the line with its link are drawn there as Preview states waiting for the owner ([[pages/roadmap/prototype-migration]], Features). **Notices on a change GitHub reports** (2026-11-12, as the artboard draws them): when a read of the bot answers `created` after `none` or `creating`, "<login> was created on GitHub"; when it answers `installed` after any other state, "<login> is installed on <n> repositories" ("1 repository", the plural rule of "Connected as"), so a bot that goes from creating straight to installed gets the installation notice only (`announceBot`, `ui/packages/renderer/src/app/features/github-connect.component.ts:999`, called before each read is kept, `:985`). The state must have changed while the card was watching: the first read when the screen opens, the first one after GitHub reconnects and the first one after a failed read have nothing to compare with and say nothing, and a read with no change says nothing (tests `ui/packages/renderer/src/app/features/github-connect.component.spec.ts:1645`, the four bot states by creation completes, installation appears, reloaded with no change, Remove confirmed, Remove cancelled and the removal failing; `:1664`, `:1689`, `:1699`). Ceiling: a change that happens between a failed read and the next good one is not announced. **Custody:** the private key and the installation token never reach the renderer, a log line or a file other than the token file (`ui/packages/main/test/oauth-github-bot.test.ts:501`, `ui/packages/main/test/ipc-github.test.ts:421`). Tests: the manifest, state, timeout, single conversion and failing conversions (`ui/packages/main/test/oauth-github-bot.test.ts:49`, `:120`, `:150`, `:183`), the token, refresh and their failures (`:226`, `:248`, `:280`, `:305`, `:326`, `:345`, `:374`, `:392`, `:418`), switches and Remove (`:467`, `:484`); the card's state-by-action matrix (`ui/packages/renderer/src/app/features/github-connect.component.spec.ts:792`); the worker variables (`ui/packages/main/test/worker-build-env.test.ts:490`, `:506`).

**Picture** (the owner approved the button with the side panel, 2026-11-08). GitHub's App manifest has no image field, so the bot's picture is uploaded on the App's settings page. Once the bot exists, created or installed, the bot section ends with "Add a picture on GitHub" and its icon, the line "GitHub shows this picture on everything the bot signs. Actions you sign yourself keep your own picture." and the page's address (`ui/packages/renderer/src/app/features/github-connect.component.ts:384`, `pictureUrl` `:915`). The button opens `settingsUrl` from the bot status, which main builds from the stored slug and account: `https://github.com/settings/apps/<slug>` for an App on the owner's account, `https://github.com/organizations/<org>/settings/apps/<slug>` for one on an organization (`toStatus`, `ui/packages/main/src/oauth/github-bot.ts:600`). It only opens that page in the browser through `scout:app.openExternal`, whose allow-list already takes any https `github.com` page (`ui/packages/main/src/ipc/app.ts:10`), so main did not change and nothing is written; a refused open shows main's sentence under the GitHub section. Tests: `ui/packages/renderer/src/app/features/github-connect.component.spec.ts:861` (shown only for created and installed), `:876` (the user and the organization page opened through main, the line, the address, no bot write), `:904` (a refused open).

**Name and slug follow a rename** ([[pages/decisions/0044-scout-acts-on-github-as-its-own-app]], amended 2026-11-08). The slug kept at creation is what the worker signs as (`<slug>[bot]`), what the card's links are built from and what the bell watches for, and the owner may rename the App on GitHub. So `GitHubBot` reads the App with its JSON Web Token, `GET /app`, and keeps its `slug` and its display `name` (the name is first kept from the creation's conversion): at start, before the first token check, so a worker built at launch already gets the new login without a restart (`ui/packages/main/src/oauth/github-bot.ts:132`), and on every bot status the card asks for, which is when the card opens and its 3-second poll while the bot is not installed (`:179`). A different slug is saved in the `github.bot` vault entry, logged at info with the old and the new slug, and restarts a running worker so `BOTLOGIN` follows; a different name is saved and logged at info and restarts nothing, since the worker never uses it. A read that times out or is refused keeps the kept slug and name, logs the failure at warn, leaves the card's error untouched and gives the status a `nameError`, "Scout could not refresh the bot's name from GitHub; this is the last name it read.", until a read answers (`rereadApp`, `:433`; `:598`). `mentionTarget()` gives the bell the slug and the account the installation is on, read from `GET /app/installations` with each token, only while the bot has an installation token, and at launch waits for the first token as the worker does, so the first read after a start, the one that looks back 24 hours, already searches for the mention (`:165`, `:407`). Tests: `ui/packages/main/test/oauth-github-bot.test.ts:724` (a rename followed and restarting the worker), `:782` (at start, no restart), `:804` (GET /app times out, 401, 503: the kept slug), `:830` (the mention target only while installed), `:859` (at launch the bell waits for the first token), `:875` (a new name kept, shown and logged, no restart), `:908` (a failed read keeps the last name and says so, the next answer clears it), `:934` (a rename at start that the vault cannot store keeps the kept slug, and the worker and the bell still get the bot). A vault that cannot be read or written while following a rename is logged and keeps the kept bot status; it never fails the start, so the worker and the bell are never left without the bot for the session.
