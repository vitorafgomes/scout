## Verdict from the review card

ADR 0043 v1.1: the card's Approve or Request changes click is the owner's approval of that one action, so there is no confirmation dialog and no chat turn. `scout:github.giveVerdict` answers only the main and quick-ask windows, each on Scout's own page and from its main frame; any other sender, a sub-frame or another page included, is refused with `github/not-verdict-window` before any control-plane call and logged with the channel and the sender kind, never the payload (`ui/packages/main/src/ipc/github-verdict.ts:187`, `ui/packages/main/test/ipc-github-verdict.test.ts:407`). Since 2026-11-09 the card's Post sends the same request with the verdict `comment` and no tests line, the owner's approval of that one review. It takes `{repository, number, verdict: approve | request_changes | comment, body, comments: [{path, line, body}], commit, testsLine}`, checks every field before any call (`ui/packages/main/src/ipc/github-verdict.ts:73`: `owner/name`, a positive number, one of the three verdicts, a body of at most 65,000 characters, at most 50 comments each with a path, a line and a body, a hex commit of 7 to 40 characters, a tests line of at most 4,000 characters), and refuses anything else with "Scout could not read that verdict.". It then calls the control plane's `GiveVerdict` through the gRPC client (`ui/packages/main/src/control-plane/client.ts:1042`), which enqueues an approved `github` action with that payload and answers its id. One pull request at one reviewed commit gets one action (`ui/packages/main/src/ipc/github-verdict.ts:233`): a click from either window while that key's action is queued, running or given answers the same `actionId` without calling the control plane again, two clicks at the same moment share one call, and a failed action lets the next click give a new one; after main restarts its map is empty and the control plane's `GiveVerdict`, idempotent on the same key, answers the existing action. Main records the new action as queued and follows it with `GetVerdict` every 2 seconds (`ui/packages/main/src/ipc/github-verdict.ts:178`), and pushes `scout:github.verdict` with `{actionId, state: queued | running | given | failed, url, reason, repository, number, commit, verdict}` to every open window (`pushToWindows`) only when it changes, until it is given or failed, after five failed reads in a row, or when main shuts down. `scout:github.verdictStatus` reads one action main gave ("Scout has no verdict with that id." for any other), and `scout:github.verdictFor` with `{repository, number, commit}` answers the last status main holds for that key, or null, so a window opened later shows the verdict (`ui/packages/main/src/ipc/github-verdict.ts:311`); it reads main's map only, because the control plane has no lookup by key. The `GiveVerdict` and `GetVerdict` RPC names are the desktop's side of the contract; until the control plane offers them, the client answers "The control plane does not offer GiveVerdict yet.". The log carries the repository, the number and the verdict, never the body or the comments.

**Approve when the checks pass** ([[pages/decisions/0059-approve-when-the-checks-pass]], 2026-11-15). The card judges the review's checks with `checksOutcome` (`ui/packages/renderer/src/app/core/review-findings.ts:86`), the worker's rule: with a failed check it offers no approval and says "<name> did not pass. Scout approves only when every check passed."; with checks still running the button reads "Approve when the checks pass" and the click goes to `scout:github.approveWhenChecksPass` (`ui/packages/main/src/ipc/github-verdict.ts:319`), guarded as the verdict's channel is. `WaitingApprovals` (`ui/packages/main/src/github/waiting-approvals.ts:128`) keeps the request under the vault key `github.waiting-approvals`, reads the pull request, its check runs and its statuses every minute (`WAIT_POLL_MS`), and gives the request through the verdict's own `give` once nothing runs, failed or is unread, marking its statuses `afterChecks`. It ends as `check-failed`, `new-commit`, `closed` or `timed-out` after two hours (`WAIT_MAX_MS`), each a bell entry (`waitingApprovalNotification`, `ui/packages/main/src/notifications/sources.ts:271`) and a line on the card; Cancel, on the card through `scout:github.cancelWaitingApproval` or on the bell's entry through its `cancel-waiting-approval` action, ends it silently, and both are refused from a window that may not give a verdict (`refuseUnlessVerdictWindow`, `ui/packages/main/src/ipc/github-verdict.ts:105`, wired at `ui/packages/main/src/main.ts:501`). A Cancel that arrives while the approval is being given changes nothing: it ends as approved. A change of the GitHub connection ends every waiting approval (`cancelAll`, `ui/packages/main/src/github/waiting-approvals.ts:177`, `ui/packages/main/src/main.ts:576`). `scout:github.waitingApprovalFor` answers a key's waiting or ended state and `scout:github.waitingApproval` pushes each change. An approval does not start waiting once a verdict or a review was sent on that commit (`github/verdict-exists`), and a verdict sent from the card ends the one that waits. A read that fails, or an answer that is not in GitHub's shape, leaves it waiting.
