## Verdict from the review card

ADR 0043 v1.1: the card's Approve or Request changes click is the owner's approval of that one action, so there is no confirmation dialog and no chat turn. `scout:github.giveVerdict` answers only the main and quick-ask windows, each on Scout's own page and from its main frame; any other sender, a sub-frame or another page included, is refused with `github/not-verdict-window` before any control-plane call and logged with the channel and the sender kind, never the payload (`ui/packages/main/src/ipc/github-verdict.ts:232`, `ui/packages/main/test/ipc-github-verdict.test.ts:407`). Since 2026-11-09 the card's Post sends the same request with the verdict `comment` and no tests line, the owner's approval of that one review. It takes `{repository, number, verdict: approve | request_changes | comment, body, comments: [{path, line, body}], commit, testsLine}`, checks every field before any call (`ui/packages/main/src/ipc/github-verdict.ts:126`: `owner/name`, a positive number, one of the three verdicts, a body of at most 65,000 characters, at most 50 comments each with a path, a line and a body, a hex commit of 7 to 40 characters, a tests line of at most 4,000 characters), and refuses anything else with "Scout could not read that verdict.". It then calls the control plane's `GiveVerdict` through the gRPC client (`ui/packages/main/src/control-plane/client.ts:1042`), which enqueues an approved `github` action with that payload and answers its id. One pull request at one reviewed commit gets one action (`ui/packages/main/src/ipc/github-verdict.ts:287`): a click from either window while that key's action is queued, running or given answers the same `actionId` without calling the control plane again, two clicks at the same moment share one call, and a failed action lets the next click give a new one; after main restarts its map is empty and the control plane's `GiveVerdict`, idempotent on the same key, answers the existing action. Main records the new action as queued and follows it with `GetVerdict` every 2 seconds (`ui/packages/main/src/ipc/github-verdict.ts:223`), and pushes `scout:github.verdict` with `{actionId, state: queued | running | given | failed, url, reason, repository, number, commit, verdict}` to every open window (`pushToWindows`) only when it changes, until it is given or failed, after five failed reads in a row, or when main shuts down. `scout:github.verdictStatus` reads one action main gave ("Scout has no verdict with that id." for any other), and `scout:github.verdictFor` with `{repository, number, commit}` answers the last status main holds for that key, or null, so a window opened later shows the verdict (`ui/packages/main/src/ipc/github-verdict.ts:361`); it reads main's map only, because the control plane has no lookup by key. The `GiveVerdict` and `GetVerdict` RPC names are the desktop's side of the contract; until the control plane offers them, the client answers "The control plane does not offer GiveVerdict yet.". The log carries the repository, the number and the verdict, never the body or the comments.

**Approve when the checks pass** ([[pages/decisions/0059-approve-when-the-checks-pass]], 2026-11-15). The card judges the review's checks with `checksOutcome` (`ui/packages/shared/src/review-findings.ts:71`), the worker's rule: with a failed check it offers no approval and says "<name> did not pass. Scout approves only when every check passed."; with checks still running the button reads "Approve when the checks pass" and the click goes to `scout:github.approveWhenChecksPass` (`ui/packages/main/src/ipc/github-verdict.ts:369`), guarded as the verdict's channel is. `WaitingApprovals` (`ui/packages/main/src/github/waiting-approvals.ts:129`) keeps the request under the vault key `github.waiting-approvals`, reads the pull request, its check runs and its statuses every minute (`WAIT_POLL_MS`), and gives the request through the verdict's own `give` once nothing runs, failed or is unread and GitHub's `mergeable` on the pull request is `true` (`ui/packages/main/src/github/waiting-approvals.ts:365`), marking its statuses `afterChecks`; while `mergeable` is null, absent or not a boolean it stays waiting and reads again the next minute. It ends as `check-failed`, `new-commit`, `closed`, `conflict` or `timed-out` after two hours (`WAIT_MAX_MS`), each a bell entry (`waitingApprovalNotification`, `ui/packages/main/src/notifications/sources.ts:434`) and a line on the card. `conflict` is the pull request read answering `mergeable` false or `mergeable_state` `dirty` (`ui/packages/main/src/github/waiting-approvals.ts:343`): the approval ends at that read, before any check is read and also while checks still run; the bell says "Not approved: <pr> has conflicts with its base branch" over "Scout approves only a pull request that can be merged" (`ui/packages/main/src/notifications/sources.ts:469`), and the card "Not approved: the pull request has conflicts with its base branch." with no approve button (`ui/packages/renderer/src/app/core/review-findings.component.ts:1383`). Cancel, on the card through `scout:github.cancelWaitingApproval` or on the bell's entry through its `cancel-waiting-approval` action, ends it silently, and both are refused from a window that may not give a verdict (`refuseUnlessVerdictWindow`, `ui/packages/main/src/ipc/github-verdict.ts:158`, wired at `ui/packages/main/src/main.ts:501`). A Cancel that arrives while the approval is being given changes nothing: it ends as approved. A change of the GitHub connection ends every waiting approval (`cancelAll`, `ui/packages/main/src/github/waiting-approvals.ts:178`, `ui/packages/main/src/main.ts:576`). `scout:github.waitingApprovalFor` answers a key's waiting or ended state and `scout:github.waitingApproval` pushes each change. An approval does not start waiting once a verdict or a review was sent on that commit (`github/verdict-exists`), and a verdict sent from the card ends the one that waits. A read that fails, or an answer that is not in GitHub's shape, leaves it waiting. Tests: `ui/packages/main/test/github-waiting-approvals.test.ts`, `ui/packages/main/test/ipc-github-verdict.test.ts:447`, `:467`, `ui/packages/main/test/notifications-voice.test.ts:382`, `ui/packages/renderer/src/app/core/review-findings.component.spec.ts:2155` (one row per state of the card, the conflict at `:2031`), `ui/e2e/tests/approve-when-checks-pass.spec.ts`; a conflict ending the wait at once, `ui/packages/main/test/github-waiting-approvals.test.ts:354`, mergeability GitHub has not said yet, `:400`, and the conflict's bell entry, `ui/packages/main/test/notifications-sources.test.ts:486`.

## Since the review notes (2026-11-20)

- **What a click sends.** Approve, Request changes and Post send the chosen findings with the owner's edits, the review job's coverage and notes, the commit and the tests line (`verdictRequest`, `ui/packages/renderer/src/app/core/review-findings.ts`); the worker composes the note ([[pages/decisions/0063-what-scout-writes-on-a-pull-request-follows-the-templates]]).
- **After a verdict.** The given line names the verdict the control plane reports, the commit, the signer and "See the review on GitHub"; under it the card says "You can still give another verdict or post other comments at this commit; each waits for your approval." and still offers the Verdict group and Post. A second verdict is named as given after the earlier one; a click the control plane answers with the action already given shows "Nothing new was sent: this verdict with these findings is already on PR #<n> at commit <commit>." (`ui/packages/renderer/src/app/core/review-findings.component.ts`).
- **The preview.** "See how it reads on the PR" asks `scout:github.previewVerdict` for the verdict the card offers first, "Preview of the note for Approve, as Scout would post it on PR #<n>", again when the selection or an applied edit changes, never on a keystroke: the first ask when the panel opens goes at once, and a burst of changes is sent as its last request 400 ms after the last change (`PREVIEW_QUIET_MS`, `ui/packages/renderer/src/app/core/review-findings.store.ts:97`); no answer is cached, so the head and the checks are read again each time. A card that leaves the view drops its waiting request (`forgetPreview`, `ui/packages/renderer/src/app/core/review-findings.store.ts:291`). A refusal shows "The preview could not be composed: <sentence>" and the verdict stays enabled. The note is rendered through the markdown pipe, which escapes raw HTML.

## The one action (2026-11-21)

- **One action.** The card's verdict row shows the one action the worker offers, labelled by its verdict, with the offer's reason under it (`ui/packages/renderer/src/app/core/review-findings.component.ts:450`, `:460`); a review with no offer reads "Comment" as before. Scout does not approve on its own: a clean review is offered a comment, whose reason says a person approves the pull request on GitHub ([[pages/decisions/0070-one-verdict-decision-and-no-approval-on-its-own]]).
- **Send as a comment instead** shows only beside a request for changes, when the offer allows it (`:465`).
- **No Post button** on a review card: the one action replaces Approve, Request changes and Post.
- **A changed selection is asked about.** When the owner changes the chosen findings, the card asks the worker what it offers for that selection; while it asks, the button reads "Waiting for Scout's offer", disabled, and the reason "Asking Scout what it offers for this selection." (`:476`, `:1350`).

## Earlier findings (2026-11-22)

[[pages/decisions/0076-a-review-checks-the-findings-scout-posted-on-earlier-reviews]]; the Main artboard's "Earlier findings" states, drawn first.

- **The section.** Above the new findings, what became of each finding Scout posted before (`ui/packages/renderer/src/app/core/review-findings.component.ts:146`): its severity mark, its title, its outcome (Fixed, Still open, Answered by the author, Could not be decided) on the check tones (passed, pending, not run; `:49`, `:55`), its reason, and a link to its conversation opened as the card's other links. Read-only, not part of the selection sent; the worker's offer already counts the open ones. Nothing to list, no section; the counts and the not-checked and not-every-conversation sentences are the worker's notes.
- **The parser** (`ui/packages/shared/src/review-findings.ts:211`, `:228`) keeps it only from a worker notice; an item with an unknown outcome or severity, a reason that is not text, or an address that is not an https address on github.com (`:25`) is not shown and is counted as unreadable.
- **MCP.** `get_review` answers the section as parsed (`ui/packages/main/src/mcp/mcp-tools.ts:264`).
