## Verdict from the review card

ADR 0043 v1.1: the card's Approve or Request changes click is the owner's approval of that one action, so there is no confirmation dialog and no chat turn. `scout:github.giveVerdict` answers only the main and quick-ask windows, each on Scout's own page and from its main frame; any other sender, a sub-frame or another page included, is refused with `github/not-verdict-window` before any control-plane call and logged with the channel and the sender kind, never the payload (`ui/packages/main/src/ipc/github-verdict.ts:147`, `ui/packages/main/test/ipc-github-verdict.test.ts:377`). Since 2026-11-09 the card's Post sends the same request with the verdict `comment` and no tests line, the owner's approval of that one review. It takes `{repository, number, verdict: approve | request_changes | comment, body, comments: [{path, line, body}], commit, testsLine}`, checks every field before any call (`ui/packages/main/src/ipc/github-verdict.ts:65`: `owner/name`, a positive number, one of the three verdicts, a body of at most 65,000 characters, at most 50 comments each with a path, a line and a body, a hex commit of 7 to 40 characters, a tests line of at most 4,000 characters), and refuses anything else with "Scout could not read that verdict.". It then calls the control plane's `GiveVerdict` through the gRPC client (`ui/packages/main/src/control-plane/client.ts:1036`), which enqueues an approved `github` action with that payload and answers its id. One pull request at one reviewed commit gets one action (`ui/packages/main/src/ipc/github-verdict.ts:198`): a click from either window while that key's action is queued, running or given answers the same `actionId` without calling the control plane again, two clicks at the same moment share one call, and a failed action lets the next click give a new one; after main restarts its map is empty and the control plane's `GiveVerdict`, idempotent on the same key, answers the existing action. Main records the new action as queued and follows it with `GetVerdict` every 2 seconds (`ui/packages/main/src/ipc/github-verdict.ts:139`), and pushes `scout:github.verdict` with `{actionId, state: queued | running | given | failed, url, reason, repository, number, commit, verdict}` to every open window (`pushToWindows`) only when it changes, until it is given or failed, after five failed reads in a row, or when main shuts down. `scout:github.verdictStatus` reads one action main gave ("Scout has no verdict with that id." for any other), and `scout:github.verdictFor` with `{repository, number, commit}` answers the last status main holds for that key, or null, so a window opened later shows the verdict (`ui/packages/main/src/ipc/github-verdict.ts:264`); it reads main's map only, because the control plane has no lookup by key. The `GiveVerdict` and `GetVerdict` RPC names are the desktop's side of the contract; until the control plane offers them, the client answers "The control plane does not offer GiveVerdict yet.". The log carries the repository, the number and the verdict, never the body or the comments.
