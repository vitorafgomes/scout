## GitHub activity for the bell

ADR 0045 v1.1: while GitHub is connected, main searches the owner's GitHub activity for the bell in the top bar ([[pages/services/desktop-ui]], Notification center). It uses `GET https://api.github.com/search/issues`, which the device-flow App user token and a fine-grained token can call without any extra permission, because `GET /notifications` accepts only a classic token. `GitHubActivityPoll` (`ui/packages/main/src/notifications/github-activity.ts:109`) gets the token from `GitHubAuth.accessToken()` (`ui/packages/main/src/oauth/github-auth.ts:155`, the browser session's token or the pasted token, the same custody as the worker's; a browser token that is due is refreshed first, and one that has expired and could not be refreshed is never handed out, so a tick after the machine wakes waits for the refresh instead of ending on a 401) and the login from `GitHubAuth.login()` (`:146`) on every tick; without both it sends nothing and checks again five minutes later. A read is five searches (`QUERIES`, `ui/packages/main/src/notifications/github-activity.ts:54`), each naming `is:pr` or `is:issue` because a GitHub App user token gets a 422 for a query without one, each with `updated:>=` the start of the last complete read (the last 24 hours at first), sorted by update, 100 results a page, every page up to the `total_count` GitHub reports (at most the search API's 1,000), so a busy account's 51st item is recorded too:

| Search | Entry detail |
|---|---|
| `is:pr is:open review-requested:<login>` | "Review requested on acme/api#41" |
| `is:pr mentions:<login>`, `is:issue mentions:<login>` | "You were mentioned in acme/api#41" |
| `is:pr author:<login> comments:>0` | "New activity on your pull request acme/shop#5" |
| `is:issue author:<login> comments:>0` | "New activity on your issue acme/shop#9" |

GitHub allows 30 searches a minute on the owner's account and a read of every page can need 50 (five searches of ten pages), so the poll sends at most 20 searches in any 60 seconds, counted across ticks, including the one a reconnect or a token refresh starts at once (`ui/packages/main/src/notifications/github-activity.ts:201`); the other 10 are left for the owner's own GitHub clients on the same account. A read that needs more keeps the pages it read and its window and goes on from the next page five minutes later, so a busy account's first read completes over two or three ticks instead of reaching the limit and starting again from page 1. A resume by page number has one ceiling: an item that leaves a search between two ticks of the same read (a review answered, a pull request closed) moves the later items up one place, and the one at the page boundary is missed until it is updated again. An item found by more than one search keeps the first one's reason; each item becomes one `github` entry, `github:<item id>`, so a later read updates it in place: the item's title, the detail above, the item's `updated_at` as its time, its comment count, and its `html_url` when that is a `https://github.com/<owner>/<repo>/pull/<n>` or `/issues/<n>` page (`ui/packages/main/src/notifications/github-activity.ts:438`). An entry the owner read stays read when the item comes back with the same reason and no more comments, after a push or a label; more comments or another reason make it unread again ([[pages/services/desktop-ui]], Notification center). Entries are recorded only when every page of all five searches answered, over however many ticks that took, and only then does the window move forward, to the start of the read's first tick (`ui/packages/main/src/notifications/github-activity.ts:240`, `:242`). Outcomes: a 401 stops the poll until GitHub is connected again or the token is refreshed (`:324`); a 403 or 429 waits the longest of five minutes, `Retry-After` and, when `X-RateLimit-Remaining` is 0, until `X-RateLimit-Reset` (`:329`, `:365`); a timeout, a network failure, a 422 or a 5xx keeps the entries, drops the pages that read had gathered and reads the same window from its first page on the next tick (`:317`, `:338`). `onConnectionChanged` calls `reconnected()`, which clears the stop and reads the last 24 hours again, and when the change left GitHub disconnected removes every GitHub entry from the bell; a read still running from before the change records nothing (`ui/packages/main/src/notifications/github-activity.ts:128`, `:209`, `ui/packages/main/src/main.ts:560`, ADR 0045 v1.3). A successful token refresh calls the poll's `tokenRefreshed()` through `onTokenRefreshed`, never `onConnectionChanged`, so a poll a rejected token stopped reads again from where it was without restarting the worker (`ui/packages/main/src/oauth/github-auth.ts:388`, `ui/packages/main/src/notifications/github-activity.ts:143`, `ui/packages/main/src/main.ts:579`). The log carries the status or the error's name, never the token, and the poll never stores the token. The read is declared on the GitHub feature's `Notifications` row (Read) in the catalog, "Search your GitHub activity every five minutes for the bell: mentions, review requests and replies on your pull requests and issues", with two more reads named on the same row since 2026-11-08: "When your Scout bot is installed, search the open pull requests on its account for a mention of the bot, and read the description, the comments, the review comments and the reviews of each pull request found, to confirm the mention before the bell shows it" and "When your Scout bot exists, read its GitHub App's own name and handle at start and whenever the GitHub card reads the bot, so a rename on GitHub is followed" (`src/Scout.ControlPlane/Features/FeatureCatalog.cs:80`; test `tests/Scout.ControlPlane.Tests/Features/FeatureCatalogTests.cs:64`); the Features screen shows the row from the catalog, since 2026-11-12 as its one sentence, "Search every five minutes for your mentions, review requests and replies; read the pull requests that mention your Scout bot and the bot's own name", which the artboard draws too; the PAT helper asks for no extra permission.
