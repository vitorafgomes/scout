## Mentions of the Scout bot

ADR 0045 v1.4: a team asks Scout for a review by mentioning the owner's bot by name in a pull request, with no label and no workflow change ([[pages/roadmap/future-improvements]], F21). GitHub's `mentions:` qualifier does not find an App's bot (a 422 "users cannot be searched", or nothing), and Scout creates its App private, so `GET /apps/<slug>` and `GET /users/<slug>` answer 404 to anyone else's token; the poll therefore searches the phrase and confirms every hit against the slug the desktop keeps. While `mentionTarget()` answers (an installed bot, wired at `ui/packages/main/src/main.ts:621`), each read adds one search after the five, `"@<slug>" in:comments,body is:pr is:open user:<login>` or `org:<org>` for the account the installation is on, with the same `updated:>=` window, paging and 20-searches-a-minute budget, resumed from its page on the next tick like the others (`ui/packages/main/src/notifications/github-activity.ts:188`). Phrase search is tokenised, so once every search answered, each candidate pull request is confirmed (`confirm`, `:313`): its body from the search result, its issue comments and review comments updated since the window, `GET /repos/<owner>/<repo>/issues/<n>/comments` and `/pulls/<n>/comments` with `since`, and its review summaries, `GET /repos/<owner>/<repo>/pulls/<n>/reviews`, which takes no `since`, so a review counts only when its `submitted_at` is in the window (`:347`); 100 a page, up to 10 pages each, with the owner's token. These reads are not searches and do not count toward the 20. A text counts when it names `@<slug>` as a whole handle in any case, not inside an address or a longer handle (`@<slug>-two`, `@<slug>s`, `me@<slug>` do not; `mentionsBot`, `:463`), and never when its author is the bot itself (`<slug>[bot]`, any case); the owner's own mention counts. Each confirmed text is one `mention` entry, `mention:issue-comment:<id>`, `mention:review-comment:<id>`, `mention:review:<id>` or `mention:body:<pull request id>` (`mentionEntry`, `:476`): "@<author> mentioned @<slug> on <owner>/<repo>#<n>: <first non-empty line, trimmed, at most 140 characters>", the pull request's title as detail, the comment's `created_at` (a review's `submitted_at`) as its time, a link to the comment or review (`…/pull/<n>#issuecomment-<id>`, `#discussion_r<id>` or `#pullrequestreview-<id>`) or to the pull request for its body, the action Review it, source `github`. A later read of the same comment updates that entry in place, so an edit is never a second entry and a read entry stays read; a mention in another comment is a new entry. A comment read that times out, answers a 5xx or is rate limited is handled as a failed search: nothing from that read is recorded, the window does not move and the next tick reads it again; a 401 stops the poll as a search's does (`:342`). Disconnect removes the mention entries with the other GitHub entries. Review it is the window's ([[pages/services/desktop-ui]], Notification center): it asks the chat to review that pull request through the existing code-review flow, and nothing is written on GitHub by the entry or the poll. Ceilings: a review summary edited after it was submitted is not read again, since the reviews list has no update time; and a resume by page number can miss one candidate at a page boundary, as the other searches can. Tests: `ui/packages/main/test/github-activity.test.ts:930` (the extra query, user and organization, none without a bot), `:950` (the owner's own "@ScoutBot review" on a lowercase slug: the entry, its link, Review it and the two comment reads with `since`), `:985` (a review comment and the body), `:1024` (whole handle, table of eleven texts), `:1040` (the bot's own comments), `:1056` (one entry per comment, an edit, a new comment), `:1090` (Disconnect), `:1113` (the mention search fails), `:1142` (a comment read times out or answers 502: no entry, the window kept), `:1170` (a 401 on a comment read), `:1182` (the budget with the extra query, comment reads not counted), `:1246` (a review summary in the window, an older one, the bot's own and a phrase without the handle), `:1269` (a review read again stays one entry, a new review is a new one).

**Starting by itself** ([[pages/decisions/0057-the-owners-mention-starts-the-review]], 2026-11-15). Every entry the poll records goes through `MentionReviews` (`ui/packages/main/src/notifications/mention-review.ts:36`, wired at `ui/packages/main/src/main.ts:604`). A mention whose title starts with the owner's own login, written within the last hour and linking to a pull request, is queued; the queue asks the chat "Review the pull request <url>", the question Review it asks (`ui/packages/shared/src/review-question.ts:5`), through `askWhenIdle` (`ui/packages/main/src/quick-ask/quick-ask.ts:1826`), which asks only while the worker runs and no turn is running and answers the turn's id. One mention is asked at a time; one that cannot be asked waits for the chat to go idle (`ui/packages/main/src/main.ts:1178`) or the next minute, and keeps Review it once it is an hour old; one the owner asked about meanwhile is marked started and asked nothing (`askedSince`, `ui/packages/main/src/quick-ask/quick-ask.ts:1846`). A question the chat refuses ends a turn of its own, and that end asks nothing: the mention waits for the retry. A mention that was asked is recorded with the detail "Review started by the mention. The answer is in the chat." and no action, and an entry with that detail is never asked again, so an edit of the comment and a restart ask nothing. Beside it the bell keeps `review:<mention id>`: running with the sweeping bar, "Reviewing <owner>/<repo>#<n>", while the turn runs; done, "Review of <owner>/<repo>#<n> is ready", when it completes (`ui/packages/main/src/notifications/mention-review.ts:131`); failed, "Review of <owner>/<repo>#<n> did not finish", with Review it back on the mention, when the turn stopped or failed (`:152`), checked only for the review that was running when the chat went idle. Disconnect drops the waiting mentions (`:174`). Another login's mention, an older one, one with no pull request link and one whose login could not be read are recorded as they came. Tests: `ui/packages/main/test/notifications-mention-review.test.ts`, `ui/packages/main/test/quick-ask.test.ts:72`, `:97`.

**A pull request that needs no review.** After each read `settle` (`ui/packages/main/src/notifications/github-activity.ts:258`) takes the mentions the bell keeps that still offer Review it (`reviewable`, `ui/packages/main/src/main.ts:625`), groups them by pull request and reads `GET /repos/<owner>/<repo>/pulls/<n>` for at most 20 of them (`MAX_SETTLED_PULLS`, `ui/packages/main/src/notifications/github-activity.ts:20`). A closed pull request's mentions are recorded without Review it and with "Merged. Nothing to review." or "Closed. Nothing to review."; for an open one, with a bot, it reads `.../pulls/<n>/reviews` and an `APPROVED` review by `<slug>[bot]` whose `commit_id` is the head's reads "Approved by the Scout bot at this commit.". A 401 stops the poll as on a search; a 403 or 429 ends the settling and the next read waits what GitHub asks; an unreachable GitHub or an unreadable answer ends it until the next read; any other error status leaves that pull request as it is and the next one is read. A mention without Review it is never queued for its review. Tests: `ui/packages/main/test/github-activity.test.ts:132` to `:293`.
