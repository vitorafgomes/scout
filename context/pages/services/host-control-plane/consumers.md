## Consumers

Two clients, each with its own token. The desktop main process starts the host when the app starts and stops it on quit; the Features and Review screens call the `Features` service through it, and since 2026-11-07 so do the approval cards in the chat and the quick-ask window, which reach `ListPendingActions`, `ApproveAction` and `RejectAction` through main's `scout:actions.*` channels ([[pages/services/desktop-quick-ask]], Approval cards); a second decision on an action is refused with FAILED_PRECONDITION, which main shows as Already decided. `Providers` is only exercised by tests, and nothing calls `Models` yet. The worker, `Scout.Host.Console`, calls `WorkerGate` only, with the socket path and the worker token the desktop passes it ([[pages/services/host-console]], [[pages/services/desktop-ui]]).

- **Lifecycle.** `connectControlPlane` (`ui/packages/main/src/control-plane/launcher.ts:231`), called from `ui/packages/main/src/main.ts:635`, launches the host, waits up to 10 s for the socket file (`ui/packages/main/src/control-plane/launcher.ts:190`) and opens the client. Every failure becomes `ControlPlaneUnavailableError`, and the Features screen then says the control plane is not running. A failure after the spawn, such as a socket that never appears, kills the host it launched. When the host exits mid-session the client is closed, so the next Features call fails at once as unavailable instead of waiting out its deadline; `dispose()` closes the client and kills the host. `workerGate()` (`ui/packages/main/src/control-plane/launcher.ts:268`) gives the socket path and the worker token from the moment the host is launched, before its socket exists, and `null` when the launch was unsupported or failed or the host exited (`:240`, `:252`); main passes it to every worker start (`ui/packages/main/src/main.ts:841`). There is no restart policy and no parent-death watchdog (`ui/packages/main/src/control-plane/launcher.ts:139`).
- **Launcher.** `launchControlPlane` (`ui/packages/main/src/control-plane/launcher.ts:106`) spawns the host and sets three environment variables on the child: `Scout__ControlPlane__SocketPath`, a per-process socket `controlplane-<pid>.sock` under `$XDG_RUNTIME_DIR/scout` or a per-uid `scout-<uid>` folder under the temp directory (`ui/packages/main/src/control-plane/launcher.ts:97`, `:144`), `SCOUT_CONTROLPLANE_TOKEN`, a fresh 64-hex-character token (`ui/packages/main/src/control-plane/launcher.ts:136`), and `SCOUT_CONTROLPLANE_WORKER_TOKEN`, a second token minted by a separate call of the same strength (`:137`, `:146`) and returned as `workerToken`. The desktop token travels only in the host's environment and in the desktop's call metadata; the worker token reaches the worker only as `SCOUT__WORKERGATE__TOKEN` ([[pages/services/desktop-ui]]); neither is set on the desktop's own `process.env`, and the launcher never logs either (`ui/packages/main/test/control-plane-launcher.test.ts:127`). Because the explicit socket path makes the host skip its own directory setup, the launcher secures the socket directory itself before it mints the token or spawns: it refuses a symbolic link, a non-directory or a directory owned by another uid, and tightens a directory open to group or others to `0700` (`ui/packages/main/src/control-plane/launcher.ts:75`). The child inherits the parent environment minus every variable that could move its listener or override its socket path or token (`ui/packages/main/src/control-plane/launcher.ts:67`): `SCOUT_CONTROLPLANE_TOKEN`, `SCOUT_CONTROLPLANE_WORKER_TOKEN` (`:47`), `Scout__ControlPlane__SocketPath`, `URLS`, `HTTP_PORTS`, `HTTPS_PORTS` and every `Kestrel__` key, matched in any casing, with `:` or `__`, and with or without the `ASPNETCORE_` or `DOTNET_` prefix. `extraEnv` applies next and the launcher's own socket path and two tokens last. Without that filter an inherited `Kestrel__Endpoints__Http__Url` made the real host listen on TCP beside the socket; `ui/packages/main/test/control-plane-integration.test.ts` checks that the port now refuses connections.
- **Binary.** `resolveControlPlaneBinary` (`ui/packages/main/src/worker/resolve-binary.ts:51`) honours `SCOUT_CONTROLPLANE_BIN`, then the packaged `worker/<rid>/` folder beside the console worker, then `src/Scout.Host.ControlPlane/bin/Release/net10.0/` and `bin/Debug/net10.0/` under the repository root. `ui/build/scripts/publish-worker.sh:14` publishes the host into that packaged folder.
- **Client.** `createControlPlaneClient` (`ui/packages/main/src/control-plane/client.ts:837`) dials `unix:<absolute path>` with `@grpc/grpc-js` and insecure channel credentials, waits for the channel before each call under the same deadline (`ui/packages/main/src/control-plane/client.ts:886`), and sends the token as `x-scout-token` metadata on every call (`ui/packages/main/src/control-plane/client.ts:909`). It maps `UNAVAILABLE`, `DEADLINE_EXCEEDED` and a channel that never becomes ready to `ControlPlaneUnavailableError`, `UNAUTHENTICATED` to `ControlPlaneUnauthenticatedError`, and `UNIMPLEMENTED` to `ControlPlaneNotImplementedError` (`ui/packages/main/src/control-plane/client.ts:489`); other codes pass through as the raw gRPC error. It loads `providers.proto` and `features.proto` with `@grpc/proto-loader` at runtime (camelCase field names, enums as strings), from `resources/protos` when packaged (`ui/build/electron-builder.yml:45`). It maps `Feature` messages onto the renderer's `FeatureDto` (`ui/packages/main/src/control-plane/client.ts:527`): an unset optional string becomes `null`, `has_scope_matrix` and `has_setup_steps` decide between a list and `null`, and an `UNSPECIFIED` status becomes `error`. `setupFeature` splits the renderer's settings into upserts and `cleared_settings` for the keys set to `null` (`ui/packages/main/src/control-plane/client.ts:969`).
- **What the host does with Features today.** `ListFeatures` returns `github`, `kubernetes`, `youtube`, `desktop` in that order (`src/Scout.ControlPlane/Features/FeatureCatalog.cs:339`; test `tests/Scout.ControlPlane.Tests/Features/FeatureCatalogTests.cs::The_catalog_lists_github_kubernetes_youtube_and_desktop_in_that_order`). `SetCredentials` keeps the values in `InMemoryCredentialStore`, because no host registers a keyring store, and validates nothing, because no host registers a credential validator. `Enable` answers `UNIMPLEMENTED` because `NullFeatureActivator.CanActivate` is false (`src/Scout.ControlPlane/Features/IFeatureActivator.cs:31`, `src/Scout.ControlPlane/Features/FeaturesService.cs:283`); for a feature with write rows the missing `confirm_writes` answers `FAILED_PRECONDITION` first. `Disable`, `DeleteCredentials` and a `Setup` that carries settings write the feature state file, `Scout/features.json` under the user's local application data folder unless `Scout:Features:StateStore:FilePath` is set. Gaps in [[pages/roadmap/followups]].
- **Tests.** `ui/packages/main/test/control-plane-integration.test.ts` launches the real host binary with the feature state file in a temp folder and checks, among others: `ListProviders` returns `OLLAMA` then `LM_STUDIO`; a wrong token is rejected as `UNAUTHENTICATED`; the worker token the launcher handed the host gets `PERMISSION_DENIED` on `ListFeatures` and `SetWriteGrant` and leaves YouTube ungranted (`ui/packages/main/test/control-plane-integration.test.ts:300`); `ListFeatures` returns GitHub and Kubernetes; `SetCredentials` with a `pat` moves GitHub from `needs-credentials` to `disabled` while `Enable` fails with `ControlPlaneNotImplementedError`. It also checks that the state file lands in the temp folder and that the developer's own `features.json` is unchanged. `ui/packages/main/test/control-plane-client.test.ts` runs the Features client against an in-process grpc-js server on a temp socket. CI builds the host before the UI tests (`.github/workflows/ui-ci.yml:110`).
- **Windows.** The host listens on the named pipe `scout-controlplane` on Windows. The launcher returns `unsupported` on `win32` and spawns nothing (`ui/packages/main/src/control-plane/launcher.ts:118`), and the client refuses before creating a channel (`ui/packages/main/src/control-plane/client.ts:844`), so on Windows the Features screen says the control plane is not running. `@grpc/grpc-js` documents no named-pipe target. Its `unix:` resolver passes the path to Node's `net.connect`, which accepts `\\.\pipe\` names on Windows, so a pipe target may work, but nobody has run it on Windows. The choice between dialling the pipe through the `unix:` target, a named-pipe shim and a stdio fallback is pending.
