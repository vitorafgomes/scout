## How it works

- **Blocks a function hands to the reply** ([[pages/decisions/0040-review-findings-as-cards-in-chat]] v1.1): the conductor begins `TurnAttachments` ([[pages/services/llm]], `src/Scout.Llm/Abstractions/TurnAttachments.cs:9`) beside `TurnProgress` (`src/Scout.Conversation/ConversationConductor.cs:167`); on the normal completion the pump takes the blocks, removes from the model's text every fenced block that opens like an attached one (its opening line to its closing fence, or to the end of the text when unclosed), so a model that still writes its own `scout-findings` fence leaves exactly one block in the reply and keeps the prose around it, and the final text becomes that trimmed text, a blank line and each block in the order attached (`src/Scout.Conversation/Streaming/StreamPump.cs:211`, `:316`). A block always arrives whole: the blocks that fit the chat's body length go in, a block that does not fit whole is dropped, and the model's text is cut to what the kept blocks leave, with the usual tail-preserving marker (`src/Scout.Conversation/Streaming/StreamPump.cs:331`), so on Slack's 3,000 characters the review's prose is cut, never the JSON; when no block fits, the prose gets the whole length as before. Without an attached block the model's text is left as it is. Interim updates never carry a block; a failed, timed-out, cancelled, rate-limited, quota, sign-in, missing-model or vision turn appends nothing, and the blocks die with the turn. At most four blocks of 64,000 characters each; a block whose first line matches an attached one replaces it. Memory keeps the streamed tokens only, so the block never enters the history. Tests: `tests/Scout.Conversation.Tests/Streaming/StreamPumpTests.cs:296`, `:313`, `:330`, `:348`, `:366`, `:379`, `:395`, `:408`, `tests/Scout.Conversation.Tests/ConversationConductorTests.cs:64`, `tests/Scout.Llm.Tests/Abstractions/TurnAttachmentsTests.cs:8`.

- **Voice messages:** after the allowed-users check, a message with `Audio` opens the sink and is transcribed before routing (`src/Scout.Conversation/ConversationConductor.cs:142`, `:279`). With no `IAudioTranscriber` the reply is exactly "Voice messages need a Whisper model. Download one in the Scout app under Models, Transcription." and nothing is downloaded. A reported size over 25 MB or duration over 5 minutes is refused before the download (`:288`, `:292`); the download reads at most 25 MB and refuses more (`:357`), and the whole download, body included, is cancelled after 30 s (`AudioDownloadTimeout`, `:301`), because the HTTP client's own timeout stops at the response headers. A failed or timed-out download, a failed transcription and a transcript with no speech each complete the reply with a fixed sentence, logged with the channel id only (`:304`, `:333`, `:343`); no speech means fewer than two letters once the transcriber's markers in brackets, parentheses or asterisks (`[BLANK_AUDIO]`, `(silence)`, `*music*`), punctuation and filler sounds (`uh`, `um`, `hmm`, `ah`, `er`, `hã`, `ahn` and the like) are taken out (`HeardSpeech`, `:402`, used at `:343`), so a near-silent push-to-talk recording gets "Scout heard no speech in that voice message." and never reaches the model, while a one-word answer such as "ok" still does, and a transcriber busy with a recording with "Scout is transcribing a recording right now; try the voice message again in a few minutes." (`:59`, `:323`, `tests/Scout.Conversation.Tests/ConversationConductorVoiceTests.cs:269`), and a speech runtime that did not load on this computer (`TranscriptionUnavailableException`) with "Scout cannot transcribe on this computer: the speech runtime did not load. The reason is in Scout's logs.", logged as a warning with the exception (`:60`, `:328`, `tests/Scout.Conversation.Tests/ConversationConductorVoiceNoticeTests.cs:113`, since 2026-11-12); a successful transcription logs the transcript length and the duration in ms, never the text. Otherwise the transcript becomes the message text, so the router, memory and model see what was said, and the sink is wrapped in `VoiceReplySink` (`src/Scout.Conversation/Streaming/VoiceReplySink.cs:10`), which prefixes every rendered body with `> (voice) ` and the transcript's first 200 characters on one line, and turns the pump's Begin into a no-op because the reply is already open ([[pages/decisions/0024-voice-messages-transcribed-locally]]).

- **The desktop dictates** (2026-11-07): the desktop's hold to talk streams the microphone to the live transcriber and sends what it heard as an ordinary text question with `IsLocalOwner` ([[pages/services/desktop-quick-ask]], Microphone), so the conductor never transcribes it and its reply never starts with the "> (voice)" quote; Discord and Slack still send audio, which is transcribed here and quoted. Test: `A_Question_The_Desktop_Dictated_Arrives_As_Text_And_Its_Reply_Carries_No_Voice_Quote` in `tests/Scout.Conversation.Tests/ConversationConductorLocalOwnerTests.cs`.

- **Voice message without a model, to the desktop:** right after the no-model reply completes, and only then, the conductor calls `IVoiceNoticeSignal.NoSpeechModel(platform)` (`src/Scout.Conversation/Abstractions/IVoiceNoticeSignal.cs:10`, `src/Scout.Conversation/ConversationConductor.cs:152`, `src/Scout.Conversation/ConversationConductor.cs:242`), an optional seam resolved like `IPairingSignal`. The platform is `desktop` for the local owner, else the adapter prefix of `OriginReference` (`discord`, ...), else `chat`; the message, its sender and its conversation never leave. A signal that throws is logged as a warning and the reply stays the only answer. The host's `StdoutVoiceNotice` (`src/Scout.Host.Console/StdoutVoiceNotice.cs:11`, registered at `src/Scout.Host.Console/HostComposition.cs:53`) writes `SCOUT_LOCAL {"id":null,"event":"voice-no-model","platform":...}`, which the desktop turns into a notification with the base model's download ([[pages/services/desktop-ui]], Notification center). Tests: `tests/Scout.Conversation.Tests/ConversationConductorVoiceNoticeTests.cs` (the notice with each platform, never with a model whatever the outcome, never for a typed message or a refused sender, a throwing signal), `tests/Scout.Host.Console.Tests/StdoutVoiceNoticeTests.cs`.

- **Origin and later posts:** `HandleAsync` enters `ChatOrigin` with the message's `OriginReference`, its conversation key, and whether the sender is the owner, `IsLocalOwner` or `AccessPolicy.IsOwner` (`src/Scout.Conversation/Access/AccessPolicy.cs:48`), an allowed id also listed in `OwnerUserIds`, compared ordinally after trimming, before anything else runs and leaves it when the turn ends (`src/Scout.Conversation/ConversationConductor.cs:113`); both come from the platform event, never from the message text or a function parameter, so a prompt can make the model call a function but cannot make the caller the owner; the value lives in an `AsyncLocal`, so a function the model calls while the reply streams reads its own turn's reference and owner flag and never another concurrent turn's, and once the turn ends nothing sees it any more: the `AsyncLocal` holds a holder shared by every task the turn started, and leaving the turn clears that holder before it gives the flow back the turn it entered from, so a task the turn started and that outlives it (`Task.Run`, fire and forget) reads null, not the owner and no marks, the caller reads the same, a nested turn's end gives the outer turn back to the outer flow, and a task left over from an ended turn never sees a later turn on another flow (`src/Scout.Conversation/Abstractions/ChatOrigin.cs:102`, `:120`; since 2026-11-11, `tests/Scout.Conversation.Tests/Abstractions/ChatOriginTurnEndTests.cs:22`, `:45`, `:60`, `:82`). The voice rewrite keeps the reference (`:156`). `OriginNotifier` splits a reference at its first colon and hands the rest to the poster whose `Kind` is the prefix: `discord`, `slack` or `local` ([[pages/services/adapter-discord]], [[pages/services/adapter-slack]], [[pages/services/adapter-local]]). A null or empty reference, no prefix, a prefix no running adapter registered (Teams registers none) or a poster that throws returns false with a Warning that carries no reference contents; it never throws for a closed or missing channel, and only a cancellation of the caller's own token propagates (`src/Scout.Conversation/OriginNotifier.cs:18`). A post the poster made is logged once at Information, "Posted <n> characters to the originating <kind> conversation.", with the reference's prefix and the text's length, never the text or an id (`:44`, since 2026-11-11, `tests/Scout.Conversation.Tests/OriginNotifierTests.cs:83`): the callers log only a failed post and the write log does not cover a post to the originating channel ([[pages/invariants/no-executive-writes]]), so this line is its record for every adapter. Each poster caps the text to its platform's limit. Rules: the reference is never shown to the model or logged, and `ChatMessage`'s generated `ToString` omits it (`src/Scout.Conversation/Abstractions/ChatMessage.cs:72`); the target of a later post comes only from a reference an adapter captured (through `ChatOrigin.Current` or stored with the job), never from an argument the model supplies; the post is plain text into that same conversation, a descriptive write ([[pages/invariants/no-executive-writes]]).

- **Sign-in required:** an `LlmSignInRequiredException` from the provider completes the reply with `StreamPumpOptions.SignInRequiredMessage` (`src/Scout.Conversation/Streaming/StreamPumpOptions.cs:84`, caught at `src/Scout.Conversation/Streaming/StreamPump.cs:156`), so the chat user is told to sign in again instead of seeing a generic error.

- **No text from the model:** an `LlmNoAnswerException`, which the gateway throws when Claude ends an answer with no text ([[pages/services/llm]]), completes the reply with its own message, a sentence naming why: cut by the output limit, the context window full, a refusal, a paused turn, a silent end, or a model still asking for functions. Like the rejected key, it is logged as one warning without the exception (`tests/Scout.Conversation.Tests/Streaming/StreamPumpFailureTests.cs`, the "no answer" rows over every partial text and sink limit; on the desktop, `tests/Scout.Adapter.Local.Tests/LocalChatAdapterTests.cs`, `An_Answer_The_Model_Ended_With_No_Text_Completes_With_The_Sentence_That_Says_Why`). Discord, Slack and Teams receive it through the same terminal Complete call.

- **Rejected key:** an `LlmKeyRejectedException`, a key-based provider's HTTP 401 ([[pages/services/llm]]), completes the reply with `StreamPumpOptions.KeyRejectedMessage`, "The AI Source rejected its key; check it in Scout Desktop." (`src/Scout.Conversation/Streaming/StreamPumpOptions.cs:91`, caught at `src/Scout.Conversation/Streaming/StreamPump.cs:163`; `tests/Scout.Conversation.Tests/Streaming/StreamPumpFailureTests.cs:274`), logged as one warning without the exception.
