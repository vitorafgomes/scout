## Overview

- **Floating button.**
  - A 64 by 64 window of its own (`ui/packages/main/src/quick-ask/quick-ask.ts:971`), created at startup unless the owner turned it off: transparent, frameless, always on top, out of the taskbar, not resizable, not focusable, no shadow, `acceptFirstMouse` so a click on the inactive window reaches the page on macOS, the same sandboxed web preferences as the quick-ask window, shown with `showInactive` so it never takes focus. It loads `#/floating-button`, `FloatingButtonComponent` (`ui/packages/renderer/src/app/floating-button/floating-button.component.ts:174`): one 56 px round button with Scout's mark in `--sc-accent-strong`, labelled "Ask Scout", on a page whose background it makes transparent and whose margin it removes (`:194`); its title adds the quick-ask shortcut, "Ask Scout (Ctrl+Alt+Space)" (Cmd on macOS), once `scout:local.getShortcut` reports it registered, and stays "Ask Scout" otherwise. From the conversation main sends to every window, the floating one included (`LocalConversation`), it shows two more states (`ui/packages/renderer/src/app/floating-button/bubble-state.ts:44`): while a turn runs a ring around the circle moves (still when the owner asks for reduced motion) and the label reads "Ask Scout, answering"; when the last turn failed for any reason but the owner's stop, the worker not running included, a "!" badge shows beside the circle, `--sc-on-danger` (white) on `--sc-danger` since 2026-11-10 (on `--sc-error` before, pale pink in the dark theme), and the label reads "Ask Scout, the last answer failed"; the title says the same in a sentence. **Listening** (since 2026-11-07): main pushes `{ listening }` on `scout:local.listeningChanged` to every window, the floating one included, when the first live listen (the microphone or the system audio, a meeting included) starts and when the last one stops, whether the owner, the worker, a worker exit or a refused restart ends it (`pushListening`, `ui/packages/main/src/quick-ask/quick-ask.ts:1441`); the button also asks `scout:local.listening` when it opens, and a push that arrives first wins (`ui/packages/renderer/src/app/floating-button/bubble-state.ts:65`). While a listen is open the button shows a ring and a dot in `--sc-recording` (light `#b3261e`, dark `#e5534b`, the artboard's recording colour), the label "Ask Scout, listening" and the title "Scout is listening. Open to see the transcript.", ahead of answering and failed, so an open microphone is never hidden; when the listen stops the button shows what the conversation shows. Tests: the push over start, complete, fail, stop the worker cannot take, worker exit, a second listen on a lane, two lanes ending one by one, and refused listens (`ui/packages/main/test/quick-ask.test.ts`), and the button's table over listening, answering and a failed answer, as pushed, as read on open, and with the listen starting and stopping (`ui/packages/renderer/src/app/floating-button/floating-button.component.spec.ts`). A click opens the quick-ask window in every state. The window is a 64 px square around the 56 px circle, so it takes clicks only in that square.
  - **The card** (since 2026-11-10, as `FloatingButton.dc.html` draws it). While the pointer is on the button, the button asks main for its card on `scout:local.bubbleCard` `{ shown }` (`ui/packages/shared/src/ipc-contract.ts:165`; `showCard`, `ui/packages/renderer/src/app/floating-button/floating-button.component.ts:202`), and leaving the button asks main to hide it. The card is a hover affordance: the button's window is not focusable, so it never takes the keyboard, and focus, blur and Esc ask for nothing. Only the floating button may call that channel: main registers quick ask through the sender check with `QUICK_ASK_GUARDS` (`ui/packages/main/src/ipc/sender-check.ts:160`, `ui/packages/main/src/main.ts:1092`), and any other sender gets `ipc/not-floating-button`. Main shows the card in a window of its own (`bubbleCard`, `cardBounds`, `CARD_SIZE`, `ui/packages/main/src/quick-ask/quick-ask.ts:1021`, `:1004`, `:119`): 244 by 200, transparent, frameless, always on top, not focusable, shown with `showInactive` so it never takes focus from another application, and ignoring every mouse event, so a click or hover on it reaches whatever is under it; the window is hidden whenever the card is not showing, so it never leaves a dead zone, and the button's own 64 px window is unchanged. The card window sits on the button's display, above the button for a bottom corner and below it for a top one, flush with the button's outer edge, and is not shown when the work area cannot hold it; then the button keeps its native title. The card window loads `#/floating-card` (`FloatingCardComponent`, `ui/packages/renderer/src/app/floating-button/floating-card.component.ts:84`), which draws the title and the line of the button's state (`BubbleStateStore`, `ui/packages/renderer/src/app/floating-button/bubble-state.ts:44`, shared with the button) 10 px from the button on the side the corner pushed on `scout:local.bubbleChanged` says; a new corner setting is pushed to every window since that date. While main reports the card shown the button has no native title, so no second tooltip covers the card; the card's text is the button's description (`aria-describedby`, `ui/packages/renderer/src/app/floating-button/floating-button.component.ts:53`), and its name stays. A card window that cannot be made, or a screen that cannot say where the button is, answers not shown with a warning. Tests: `ui/packages/main/test/quick-ask.test.ts` ("quick ask: the floating button card, a second window that shows beside the button and never takes a click", "quick ask: the card learns the side to draw on"), `ui/packages/main/test/sender-check.test.ts`, `ui/packages/renderer/src/app/floating-button/floating-button.component.spec.ts` ("the card beside the button"), `floating-card.component.spec.ts`. Only fakes prove the window calls: that Electron ignores mouse events on the card window under X11, Wayland, Windows and macOS, and that hover reaches the unfocusable button window, is not measured.
  - A click calls `scout:local.open` (`:67`), which runs the quick-ask `open()` (`ui/packages/main/src/quick-ask/quick-ask.ts:1095`); the bubble hides while the quick-ask window is shown (`:1133`).
  - `placeInCorner` (`ui/packages/main/src/quick-ask/placement.ts:18`) gives the point 16 px inside a corner of a display's work area; `place` (`ui/packages/main/src/quick-ask/quick-ask.ts:861`) puts the window there on the display `chosenDisplay` (`:819`) resolves: the display nearest the mouse cursor, the primary display, or one monitor by its display id. A chosen monitor that is not connected falls back to the primary display, with one notice turn and a warning per disconnection, "The monitor chosen for the floating button is not connected; the button is on the primary display until it is back." (`MISSING_MONITOR_HINT`, `:83`); when it comes back the button returns to it. Each placement of the floating button logs at info "quick-ask: floating button placed" with the display id, the chosen work area, the number of displays, the cursor point and the setting. It positions on Wayland too. On Linux in a Wayland session that also has XWayland (`DISPLAY` set), main relaunches Scout once with `--ozone-platform=x11` before anything else starts (`ui/packages/main/src/shell/x11-relaunch.ts:12`, `ui/packages/main/src/main.ts:179`), exiting only once the new process has started and otherwise staying a native Wayland client with a warning (`ui/packages/main/src/shell/x11-relaunch.ts:41`), the AppImage from `APPIMAGE` when the app is packaged, and never when an ozone platform is already on the command line; the position and always-on-top then go through XWayland. COSMIC's X window manager overrides the position, always-on-top and frame of every window it manages and leaves unfocusable windows alone, but an unmanaged window never gets the keyboard there, so only the bubble is created with `focusable: false`; the quick-ask window is focusable on every platform (`ui/packages/main/src/quick-ask/quick-ask.ts:1099`), and on COSMIC it opens where the window manager places it, with a frame. Without XWayland Scout stays a native Wayland client and the compositor places the windows. A runtime `appendSwitch('ozone-platform', 'x11')` from main does not change the browser process's platform and crashes the GPU process, hence the relaunch. On macOS both windows join every Space and stay above full-screen apps (`ui/packages/main/src/quick-ask/quick-ask.ts:813`).
  - **Following the cursor** (since 2026-11-08). While the floating button shows with "Display with the mouse cursor", main checks the cursor's display every 500 ms (`followCursor`, `checkCursor`, `:898`, `:889`, `CURSOR_POLL_MS`, through the injected `setTimer`, `ui/packages/main/src/main.ts:1105`) and moves the button only when the display id changes. Only one check is armed at a time; it stops when the quick-ask window opens and hides the button, when the setting leaves the cursor, when the button is turned off, and on dispose. Main also listens to the screen's `display-added`, `display-removed` and `display-metrics-changed` (`displaysChanged`, `ui/packages/main/src/quick-ask/quick-ask.ts:962`, registered at `:1807`, removed on dispose): the button shown is placed again, so a removed display moves it to a live one, and the status below is pushed to every window.
  - **Why the cursor may not be followed.** Under `--ozone-platform=x11` Chromium reads the pointer from its own pointer events while the pointer is over one of its windows and otherwise asks the X server with `XQueryPointer` on the root window (`X11ScreenOzone::GetCursorScreenPointPx` and `IsCachedCursorLocationCurrent`, `ui/ozone/platform/x11/x11_screen_ozone.cc` at Chromium 156.0.8078.80, the Chromium of Electron 45.2.3). Xwayland learns the pointer position only from `wl_pointer` motion events, which the Wayland compositor sends while the pointer is over one of Xwayland's own surfaces; on `pointer_handle_leave` (`hw/xwayland/xwayland-input.c`) it stops being told, so the root position stays where the pointer last left an X window. That the root position is stale outside X windows is inferred from those two sources, not measured; Electron's own typings for `screen.getCursorScreenPoint()` say "Not supported on Wayland (Linux)" for the native Wayland platform, and Electron issue 53794 (closed) reports it always answers `{x: 0, y: 0}` there; issue 42519 (closed) reports, on Linux under X11, a point that stopped following the pointer outside the app's window from Electron 28 on. The owner's probe on 2026-11-08 under XWayland read a live point while the pointer was over Scout's window. So on Linux in a Wayland session with two or more displays, when the cursor point has not changed for 60 checks (30 s), main logs at info, once per run, "quick-ask: the cursor has not moved for 30 s; the system may not report the pointer outside Scout windows (Wayland/XWayland), so the floating button cannot follow it" and the status carries the hint "Your desktop (Wayland) does not tell Scout where the pointer is outside Scout's own windows, so the button follows the cursor only when the pointer passes over one of them." (`watchCursor`, `:873`, `STALE_CURSOR_HINT`, `:81`). The hint clears, and the cleared status is pushed, at the first check that reads a different point; it comes back after another 30 s still. The last point is kept while the button is hidden, so hiding and showing it does not clear the hint. The log is the proof in the owner's Logs: a moving pointer that never changes the logged point is this case. Outside a Wayland session an idle mouse is not reported.
  - **Primary display.** `getPrimaryDisplay` under X11 is the RandR primary output when one is set; otherwise the display of the monitor RandR lists first, otherwise the first output (`GetDisplayList`, `ui/base/x/x11_display_util.cc` at Chromium 156.0.8078.80). On the owner's COSMIC desktop `xrandr --listmonitors` marks no primary, and the probe returned the 3440 by 1440 external monitor at 1920,0, not the laptop panel at 0,190: the choice is deterministic, and Settings names it.
  - Settings, "Floating button and quick ask" (`ui/packages/renderer/src/app/wizard/settings/settings.component.ts:333`), has the "Show the floating button" slide toggle at the right of its row (`:343`), "Corner" with Top left, Top right, Bottom left and Bottom right, and, with two or more monitors connected, one "Display" row (`:371`): "Follow the mouse cursor", then one button per monitor by name and size (`:385`), Electron's `display.label` when it gives one, else "Built-in display" or "External display", then width × height, the primary one followed by "(primary)", for example "Built-in display 1920×1080" and "External display 3440×1440 (primary)", each with `aria-pressed`. With one monitor the row is not drawn. The stored value keeps its three meanings: the primary monitor's button is pressed for `primary` or for its id (`onMonitor`, `:941`) and stores `primary`, so the choice follows whichever monitor is primary; another monitor's button stores its id; "Follow the mouse cursor" stores `cursor`; a chosen monitor that is not connected presses nothing. The status's hint shows under the row, and stays when one monitor is left and the row is gone (`:334`). Every change sends exactly `{ enabled, corner, display }` through `scout:local.setBubble` and shows what main returned, or main's refusal; the page follows the status main pushes on `scout:local.bubbleChanged` (`:887`).
  - Main validates the three fields, `display` being `cursor`, `primary` or an integer display id (otherwise `quick-ask/invalid-bubble`, `toBubbleSettings`, `ui/packages/main/src/quick-ask/quick-ask.ts:646`), stores the JSON under the main-only vault key `quick-ask.bubble` (`ui/packages/main/src/vault/safe-storage-vault.ts:24`) and applies it: off destroys the window, on creates it if missing, a new corner or display moves it (`setBubble`, `ui/packages/main/src/quick-ask/quick-ask.ts:1212`). `scout:local.getBubble` and `setBubble` answer `LocalBubbleStatus` (`ui/packages/shared/src/ipc-contract.ts:1884`): the settings, the connected `monitors` (id, name, whether it is the primary) and `hint`, null unless the cursor cannot be followed or the chosen monitor is not connected (`bubbleStatus`, `ui/packages/main/src/quick-ask/quick-ask.ts:883`). An unreadable or malformed stored value means the default, bottom-right on the cursor's display, with a warning (`:1147`).
  - Tests (2026-11-08, on the owner's layout: a 1920 by 1080 laptop panel at 0,190 listed first and a 3440 by 1440 primary at 1920,0): `ui/packages/main/test/quick-ask.test.ts`, "quick ask: the display choice works on the owner layout" (the button moves to the monitor the pointer moved to at the next 500 ms check and not within the same monitor; one check while the button shows and none while the quick-ask window is open, after a switch to the primary display or after dispose; the primary display listed second wins; a chosen monitor holds the button and is saved by id; an unplugged chosen monitor gives the primary with one notice and the hint and returns when back; a removed monitor and a changed work area re-place the button; dispose removes the display listeners; a fractional, string or null display is refused; each placement is logged; the stale-cursor log fires once after 30 s on Wayland with two monitors and not otherwise; the hint clears when the pointer is reported moving and stays through a hide and show; the quick-ask window reopens at bounds saved on any connected monitor and shows again where it was after the pointer moved, and opens in the chosen monitor's corner only with no saved bounds or bounds off every monitor). `ui/packages/renderer/src/app/wizard/settings/settings.component.spec.ts` (the monitor list by name and size and a click that saves the id, the primary's button, the hint, the pushed list, and "Settings: the floating button display is one row": stored `cursor`, `primary`, the primary's id, another monitor's id and an unplugged monitor's id over one, two and three monitors with the primary first or second, and every button pressed).
  - `--ask` opens quick ask: a second launch with it calls `onAsk` instead of showing the main window (`ui/packages/main/src/shell/app-lifecycle.ts:162`). On a first launch `launchWindow` opens quick ask at once when the launch is hidden, and otherwise only when the main window emits `show` (`:77`, `:78`), so the main window's show does not take the focus and hide quick ask. This is the command the Wayland hint tells the owner to bind.
