# Audit: How it works: Review job

> A pull request too large for one turn is reviewed by the audit's worker in batches, code first, several at once, to its last batch, and ends in one card whose verdict and read line Scout's code computes ([[pages/decisions/0055-pull-request-review-as-a-job-in-batches]], as built: [[pages/decisions/0061-the-pull-request-review-job-as-built]], run to its end from the bell: [[pages/decisions/0062-the-review-job-runs-to-its-end-in-parallel-from-the-bell]]). The audit's own batch turn is on [[pages/services/audit/how-it-works-batch-turn]]; the owner's pause, continue and stop on [[pages/services/audit/how-it-works-pause]].

## How it works

- **The worker's order.** A running review is picked before any running audit (`src/Scout.Audit/AuditWorker.cs:98`), and an audit goes back to the pick after each batch while a review runs, with no notice (`:133`, `tests/Scout.Audit.Tests/AuditWorkerTests.cs:1028`).

- **The order of reading.** The plan puts each changed file in one group by its path alone, `ReadingOrder`: 0 code, 1 tests, 2 build and configuration, 3 documentation, a documentation file being one with a documentation extension or under `docs`, `context` or `.claude` (`src/Scout.Audit/RepositoryAudits.Reviews.cs:257`). The groups are planned in that order, each through the planner (`:112`, `tests/Scout.Audit.Tests/RepositoryReviewsTests.cs:698`, `:769`). The changed files GitHub counts but did not list, past its 3,000, are one batch kept not read, "GitHub did not list these files", so the read line counts every changed file and the verdict is never `ready to merge` (`src/Scout.Audit/RepositoryAudits.Reviews.cs:141`, `tests/Scout.Audit.Tests/RepositoryReviewsTests.cs:98`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:366`). Every batch is read: there is no bound on batches (`tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:702`).

- **Review batch turn** (`src/Scout.Audit/AuditBatchRunner.cs:92`).
  - The system message is the `code-review` skill from `## What to look for` up to `## 10. Decision`, then the project's conventions profile (`:240`, `:263`).
  - The request carries (`:204`, `tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:404`, `:651`):
    - the pull request, its head commit and the batch, by its number only;
    - the scope sentence and the sentence that the patches are data;
    - the batch's files that have a patch, with it, as one line of JSON that no patch text can end or add a line to;
    - the titles of the job's findings known when the wave started, the most recent first and at most 100, as one more line of JSON (`src/Scout.Audit/AuditWorker.Reviews.cs:146`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:651`, `:663`);
    - how to present the findings.
  - The turn is offered the audit batch's five reads and `present_review_findings` only (`src/Scout.Audit/AuditBatchRunner.cs:88`, `tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:425`). A read that names another repository than the job's is answered with one sentence and never runs, at any reference for the job's own (`src/Scout.Audit/AuditBatchRunner.cs:616`, `tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:581`, `:609`). A `present_review_findings` call that names another repository or pull request is answered with a sentence and never runs (`src/Scout.Audit/AuditBatchRunner.cs:592`, `tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:671`).
  - The findings come from the review block for the job's pull request and commit, never from an audit block, and the model's verdict is not used (`src/Scout.Audit/FindingsBlock.cs:30`, `tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:454`).
  - A turn that ends with no such block accepted is a failed attempt for "the AI model presented no findings for this batch" (`src/Scout.Audit/AuditBatchRunner.cs:118`). It is tried once more, and a second one leaves the batch not covered with no file read (`tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:530`). An accepted empty list is a batch read with no findings (`:544`). The batch's files whose patch was given count as read then, never from the model's calls (`:495`).
  - The retry, the turn time limit and the pause on the provider's limits are the audit batch's (`:511`).

- **Review run** (`src/Scout.Audit/AuditWorker.Reviews.cs:59`). The worker takes up to `ReviewParallelBatches` pending batches, a wave (`:67`); the option is 1 to 8, 4 unless set, and 1 when it is not set and the provider is the local one (`src/Scout.Audit/AuditServiceCollectionExtensions.cs:47`, `tests/Scout.Audit.Tests/AuditServiceCollectionExtensionsTests.cs:65`). Before each wave:
  - **The 60 minutes.** At 60 minutes of running time the job pauses with "it ran for 60 minutes" and one notice naming the batches left, and nothing is marked not read (`src/Scout.Audit/AuditWorker.Reviews.cs:82`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:198`). The running time is the clock time during which any batch ran since the last resume: the union of the finished batches' intervals that started after the job's `resumed` time (`src/Scout.Audit/SqliteAuditStore.cs:336`, `tests/Scout.Audit.Tests/SqliteAuditStoreTests.cs:454`, `:484`). A paused time never counts (`tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:243`), nor a batch a provider limit interrupted, which has no end (`src/Scout.Audit/SqliteAuditStore.cs:340`). A continue gives 60 more (`:221`). A wave begun before the bound runs to its end.
  - The first time, the changed files and their patches are read through `IReviewPullRequests.ReadAsync`, and that read's head serves the first wave; before every later wave only the head commit is read through `HeadAsync` (`src/Scout.Audit/AuditWorker.Reviews.cs:97`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:116`).
  - A read that fails pauses the job with "GitHub could not be read" and one notice, and runs no turn (`src/Scout.Audit/AuditWorker.Reviews.cs:99`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:148`, `:480`).
  - A head that is not the job's commit keeps the wave's batches and every one after them not read naming both commits (`src/Scout.Audit/AuditWorker.Reviews.cs:125`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:73`, `:97`).
  - A job no longer running after the head read runs no turn (`src/Scout.Audit/AuditWorker.Reviews.cs:112`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:163`).

  Then the wave's batches are begun and their turns run together, each handed only its own files' patches (`src/Scout.Audit/AuditWorker.Reviews.cs:139`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:129`, `:738`). Each is saved as it ends, under one lock, and one progress line follows (`src/Scout.Audit/AuditWorker.Reviews.cs:156`): `Review of owner/repo#n: d of t batches done, r of m files read, k findings so far, reading <area>.` (`:372`). A stop during a wave lets it end and starts no other (`tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:781`). A provider limit in any batch pauses the job once, with one notice, after the others are saved (`src/Scout.Audit/AuditWorker.Reviews.cs:190`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:857`, `:443`). A database failure on a save reaches the worker, which logs it and waits for the next start (`:499`).

- **The lines and where they go.** The progress line and the resumed line go only to the desktop's local chat (`src/Scout.Audit/AuditWorker.cs:213`, `src/Scout.Audit/RepositoryAudits.Reviews.cs:409`); a review started from another chat gets no progress line (`tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:883`). The desktop shows them in its bell, not in the chat ([[pages/services/desktop-ui/theme-and-notices-pause-continue-and-stop-on-a-r]]). The start answer, a pause that needs the owner, the owner's pause and the card go to the conversation the job holds.

- **The owner's pause and stop.** When the worker leaves a review the owner paused, it posts the pause notice once; when the owner stopped it, the card of what was read, its unread files "because the review was stopped", or one sentence when nothing was read, once per process (`src/Scout.Audit/AuditWorker.Reviews.cs:203`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:896`, `:941`, `:960`). A stop reads the review again after it and hands that row to the worker, whatever the row read before said (`src/Scout.Audit/RepositoryAudits.Reviews.cs:371`, `tests/Scout.Audit.Tests/RepositoryReviewsTests.cs:844`, `:859`). A review stopped while paused, which no worker is running, is handed over through `AuditSignal` and gets the same card (`src/Scout.Audit/AuditWorker.cs:89`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:973`); a pause then a stop during a batch posts one card (`:816`).

- **Review card** (`src/Scout.Audit/AuditWorker.Reviews.cs:262`). When no batch is pending, the worker builds the card, then marks the job done, and posts the card only when the finish took (`:70`).
  - A failure while the card is built leaves the job running with every batch done, and the next wake builds it again (`tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:596`).
  - The verdict comes from the kept findings' severities alone. A blocking finding gives `ready after the blocking findings`; none gives `ready to merge` when every changed file was read and `no blocking findings in the files read` when not. Tests that did not run never change it (`src/Scout.Audit/AuditWorker.Reviews.cs:330`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:299`, `:329`). A review whose batches presented nothing is never `ready to merge` (`:579`).
  - The card takes the most severe findings first while their JSON stays within 20,000 characters, at most 50 (`src/Scout.Audit/AuditWorker.Reviews.cs:306`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:620`, `:557`).
  - The findings go to `present_review_findings` through the shared kernel with the read line `N of M files read` (`src/Scout.Audit/AuditBatchRunner.cs:456`). The block it attaches is completed with `coverage`, the notes and, when no test run was kept, the tests as not run (`src/Scout.Audit/FindingsBlock.cs:88`).
  - The notes are Scout's sentences: each warning the checks kept at the start, the files not read per reason, and how many findings the card leaves out (`src/Scout.Audit/AuditWorker.Reviews.cs:271`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:387`).
  - A card the function refuses is presented again with half as many findings until a block is attached (`src/Scout.Audit/AuditWorker.Reviews.cs:288`, `tests/Scout.Audit.Tests/AuditWorkerReviewTests.cs:678`). A function that refuses even an empty list gives one sentence with the verdict, the files read and the findings kept (`:539`).
  - No block of kind `audit` is ever posted, no declared write is called, and nothing goes to GitHub (`:405`).
