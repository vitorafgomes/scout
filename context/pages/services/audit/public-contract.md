## Public contract

- **Entry point:** `AddAudit(IServiceCollection, IConfiguration)` (`src/Scout.Audit/AuditServiceCollectionExtensions.cs:26`), called by [[pages/services/host-console]] only when the GitHub plugin registered its client (`src/Scout.Host.Console/HostComposition.cs:96`). It registers the store, the batch runner, one `RepositoryAudits` as both `IRepositoryAudits` and `IPullRequestReviews` (`src/Scout.Audit/AuditServiceCollectionExtensions.cs:53`, `:63`, `:64`) and the hosted `AuditWorker` (`:65`); no host adapter and no chat function reaches `IPullRequestReviews` yet. In the same place the host registers its three adapters (`src/Scout.Host.Console/HostComposition.cs:99`, `:100`, `:101`): `AuditSnapshotsAdapter`, this project's `IAuditSnapshots` over the plugin's `IRepositorySnapshots` (`src/Scout.Host.Console/AuditSnapshotsAdapter.cs:7`), `ReviewEnvironmentAdapter`, this project's `IReviewEnvironment` over the `Scout:Sandbox:Enabled` value the host reads once (`src/Scout.Host.Console/ReviewEnvironmentAdapter.cs:9`, `tests/Scout.Host.Console.Tests/HostAuditTurnTests.cs:277`), and `RepositoryAuditsAdapter`, the plugin's `IRepositoryAudits` over this project's (`src/Scout.Host.Console/RepositoryAuditsAdapter.cs:9`), so the plugin's `start_repository_audit`, `pause_repository_audit`, `stop_repository_audit` and `get_repository_audit_status` reach the job and neither library references the other.
- **Abstractions:** `IAuditJobStore` (`src/Scout.Audit/IAuditJobStore.cs:46`), internal, the job's fourteen use cases (create, running jobs, job, latest job, batches, next batch, findings, begin, complete, not covered, stop, pause, resume, finish), where create, latest job and stop take the pull request a review is of, null for an audit, and create takes the checks a review ran before it started, null for an audit, which is what `RepositoryAudits` passes for an audit and the pull request's number for a review, over the records `AuditJob`, `AuditBatch` and `AuditFinding` and the status words of `AuditStatus` (`:4`); `RepositoryAudits`, `AuditWorker` and the registration see only it (`src/Scout.Audit/AuditServiceCollectionExtensions.cs:44`). `IRepositoryAudits` (`src/Scout.Audit/RepositoryAudits.cs:17`) with `StartAsync`, `PauseAsync` (`:26`), `ContinueAsync` (`:33`), `StopAsync` and `StatusAsync`, each `(owner, repo, ct)`, and `ControlAsync(owner, repo, action, ct)` (`:40`) for Scout Desktop, which answers `AuditControlAnswer(Applied, Sentence)` (`:50`) and each answering one sentence the model relays, the same shape as the plugin's. `IPullRequestReviews` (`src/Scout.Audit/RepositoryAudits.Reviews.cs:13`), internal, with `StartAsync(owner, repo, number, headSha, files, diffsLeftOut, checks, ct)`, `files` every changed file as `ReviewFile(Path, Patch)` (`:30`), the patch null when GitHub returned no diff for it, and `checks` the head commit's check counts the caller read, null when it could not, answering a `ReviewStart` with the checks it ran (`src/Scout.Audit/ReviewPreflight.cs:41`), and `StatusAsync(owner, repo, number, ct)`, answering one sentence; the patches and the check counts arrive as arguments, so this project reads nothing of the GitHub plugin to get them. `IReviewEnvironment.ContainerRunsOn` (`src/Scout.Audit/IReviewEnvironment.cs:7`), the fact of this computer a review is checked against, which the host adapts. `IAuditSnapshots.Find(owner, repo, commitOrShortSha)` and `AuditSnapshot(Owner, Repo, Commit, Root, TakenAt)` (`src/Scout.Audit/IAuditSnapshots.cs:7`), the shape of the plugin's `IRepositorySnapshots`. The implementation resolves the kernel on use (`src/Scout.Audit/RepositoryAudits.cs:59`), because the plugin that calls it is built into that kernel; the host composes the real plugin with the adapter and resolves the kernel without a cycle (`tests/Scout.Host.Console.Tests/HostAuditTurnTests.cs:252`).
- **Configuration keys:** `Scout:Audit:DbPath` (default `Scout/audit.db` under the user's local application data, beside the snapshots), `Scout:Audit:MaxBatchFiles` (40), `Scout:Audit:MaxBatchCharacters` (60,000, `src/Scout.Audit/AuditOptions.cs:22`) and `Scout:Audit:TurnTimeout` (10 minutes, `:25`) (`src/Scout.Audit/AuditOptions.cs:7`, defaults applied at `src/Scout.Audit/AuditServiceCollectionExtensions.cs:33`). A `TurnTimeout` that is not above zero fails validation when the host starts (`src/Scout.Audit/AuditServiceCollectionExtensions.cs:40`, `ValidateOnStart`), with `Scout:Audit:TurnTimeout must be above zero; every batch turn would end before the model answers.`, instead of ending every batch turn at once and leaving every area not covered. Paths and numbers only; `appsettings.json` names none of them.
- **Packages:** `Microsoft.EntityFrameworkCore.Sqlite` 10.0.15 (`Directory.Packages.props:43`), which brings `Microsoft.Data.Sqlite` and the SQLite bundle at the versions [[pages/services/meetings]] pins, and `Microsoft.SemanticKernel`.
- **External boundaries:** the database file and its WAL companions; the model through the kernel's `IChatCompletionService`; the GitHub plugin's functions through the kernel and its snapshots through `IAuditSnapshots`; `IOriginNotifier` for the posts. No HTTP client and no file read of the plugin's own.
