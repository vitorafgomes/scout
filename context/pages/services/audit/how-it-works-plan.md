## How it works

- **Plan** (`src/Scout.Audit/AuditPlanner.cs:43`): only the files the project index reads (`ProjectFileFilter.IsIndexable`, [[pages/services/knowledge]]), so build output, dependencies and credentials files never enter; `.editorconfig` has no extension the index reads and is not planned either. First the manifests, configuration and top-level files (`:68`: every root-level file, `.github/`, build and package manifests anywhere); then each top-level folder, whole when it fits the caps, otherwise split by its subfolders, its own files chunked last as `area (i/n)`, neighbouring small folders packed together up to the caps (`:91`, `:126`, `:138`); test and generated folders and files last (`:77`). Characters are counted as bytes on disk. Ordinal order, so the same snapshot always gives the same plan. The folder plan lists the files and their sizes and hands them to the plan over a list (`src/Scout.Audit/AuditPlanner.cs:55`), which applies the same order, caps and areas to exactly the files it is given and filters none of them, so a caller that already chose its files, as a review does with each file's patch length (Review start, below), gets the batches a folder of those files would (`tests/Scout.Audit.Tests/AuditPlannerTests.cs:97`, `:123`). A file over 20,000 characters, where the GitHub plugin's read cuts a file (`src/Scout.Audit/AuditPlanner.cs:24`), is marked as partly readable on its batch. The 60,000-character default bounds the request: every file the model reads is sent again on each round trip of the turn, and a full batch of 40 files of 1,450 characters on the Ollama connector peaks at 88,082 characters in its largest request, the last of 42 (`tests/Scout.Host.Console.Tests/HostAuditTurnTests.cs:189`, which holds it under 300,000).

- **Rows** (`src/Scout.Audit/Storage/AuditDbContext.cs:6`): through Entity Framework Core, the internal `AuditDbContext` and its `Initial`, `JobKind` and `ReviewPreflight` migrations, never SQL in code ([[pages/decisions/0052-persistence-behind-stores-on-entity-framework]]). `audit_job (number, id, owner, repo, commit_sha, origin, started, finished, status, paused_reason, kind, pull_request, preflight)` with status running, paused, stopped or done and the reason of a pause, cleared when the job resumes or stops, `kind` `audit` or `review` and `pull_request` the number of the pull request a review is of (since 2026-11-13, [[pages/decisions/0055-pull-request-review-as-a-job-in-batches]]; the `JobKind` migration gives every row already in a file the kind `audit` and no pull request, `tests/Scout.Audit.Tests/SqliteAuditStoreTests.cs:362`, and a file that refuses it fails the call with SQLite error 8 and keeps its rows, `:375`; a review is created only by the review start below, which nothing calls yet; `preflight`, nullable, holds a review's checks before it started as JSON, written once in the job's save and never updated, null for an audit and for every row written before the `ReviewPreflight` migration, `src/Scout.Audit/Storage/Migrations/20261113051343_ReviewPreflight.cs:13`, `src/Scout.Audit/SqliteAuditStore.cs:62`), `owner` and `repo` compared without case (`NOCASE`, `:25`), `number` keeping the order jobs were started in when two share a start time; `audit_batch (job_id, seq, area, files, status, started, finished, files_read, failure, partial)` with status pending, done or not covered, a batch the plan gives a failure kept not covered with it from the start, in the job's one save (`src/Scout.Audit/SqliteAuditStore.cs:70`, `tests/Scout.Audit.Tests/SqliteAuditStoreTests.cs:398`), the file lists as JSON arrays; `audit_finding (job_id, id, merge_key, seq, severity, title, path, line, context, why, fix, rule, state, issue_url, dismissed_reason)`, state `open` until the desktop records more. Times are the injected clock's UTC. The job's `origin` column is not in the ADR's list; the worker needs it to post after a restart. One context per call, the parent folder created on first use (`src/Scout.Audit/SqliteAuditStore.cs:245`); a SQLite or file-system failure, a write refused inside `SaveChanges` included, is an `AuditStoreException` naming the operation and the SQLite code only (`:254`, `:258`, `src/Scout.Audit/IAuditJobStore.cs:39`). `PauseAsync` and `ResumeAsync` move a job between running and paused in one `UPDATE` each (`src/Scout.Audit/SqliteAuditStore.cs:173`, `:179`); `PauseAsync` answers whether it paused, and pauses only a running job, so a job already paused keeps the reason it was paused with (`src/Scout.Audit/IAuditJobStore.cs:100`); stopping applies to a running or a paused job (`src/Scout.Audit/SqliteAuditStore.cs:166`). The worker asks for the first pending batch and the batch count only (`:97`), not every row, on each step. Each lookup that filters and sorts has its index, so none reads the table end to end or sorts on its own: the running jobs on `IX_audit_job_status_started`, the latest job of a repository and the stop on `IX_audit_job_owner_repo_kind_pull_request_started`, which is also the latest review of a pull request, because each looks a repository up by kind and pull request: an audit is kind `audit` with no pull request and a review kind `review` with its number, so an audit never finds or stops a review of the same repository and a review never finds another pull request's (`src/Scout.Audit/SqliteAuditStore.cs:201`, `tests/Scout.Audit.Tests/SqliteAuditStoreTests.cs:311`, `:328`); its `owner` and `repo` keep the column's `NOCASE` collation so the case-blind comparison uses it, and a job's findings in order on `IX_audit_finding_job_id_seq` (`src/Scout.Audit/Storage/AuditDbContext.cs:21`, `:22`, `:60`; the queries `RunningJobs`, `LatestJobs`, `Stoppable` and `Findings`, `src/Scout.Audit/SqliteAuditStore.cs:192` to `:206`); the batches come in order from their primary key `(job_id, seq)`. `tests/Scout.Audit.Tests/SqliteAuditStoreTests.cs:288` reads SQLite's plan for each query's own SQL. On the store's first call the file is opened for writing, the migrations it lacks are applied and WAL mode is set (`src/Scout.Audit/SqliteAuditStore.cs:292`); a file with tables and no migration history, which an older build wrote, is deleted with its `-wal` and `-shm` and created again (`:301`), its jobs lost, but only when every table it holds is one the store knows: the model's, Entity Framework's own and those of the schema before Entity Framework. A file with any other table is never deleted and the call fails with `Scout could not <read|save> the audit database: it holds tables Scout did not create, so Scout left it as it is.`; a file Scout cannot delete, in a folder it cannot write to, fails with the exception type and stays where it is (`tests/Scout.Audit.Tests/SqliteAuditStoreTests.cs:189`, `:208`).

- **Merge** (`src/Scout.Audit/SqliteAuditStore.cs:119`): in one transaction with marking the batch done, a finding whose path and title, trimmed and upper-cased with the invariant culture (`:209`), are already in the job is not added, with a unique index on `(job_id, merge_key)` behind it (`src/Scout.Audit/Storage/AuditDbContext.cs:59`); a new finding whose id another finding of the job holds gets `id-2`, `id-3`, within the desktop's 40-character id rule (`src/Scout.Audit/SqliteAuditStore.cs:212`), because the desktop merges cards by id.
