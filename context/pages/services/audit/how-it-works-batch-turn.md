## How it works

- **Batch turn** (`src/Scout.Audit/AuditBatchRunner.cs:52`): the instructions are the `code-audit` skill from `## Pass 2` up to `## Opening the issues` (`:135`), so the batch never reads the snapshot, conventions-writing or issue-opening steps, followed by the conventions profile read through `GitHubActions.get_project_conventions` (`:155`); the worker builds them once per job (`:148`), so the system message is the same text in every batch. The request names the repository, the commit (the reads' `reference`, so they hit that snapshot), the area, the batch's files, the titles of earlier findings in those files (a file belongs to one batch, so this is usually empty) and the sentence that the scope is this list and nothing else (`:110`). The turn runs on a copy of the kernel holding only `GitHub.get_file_contents`, `search_code`, `list_repository_files`, `present_audit_findings` and `ProjectKnowledge.search_project`, `find_symbol` (`:41`), built by `KernelScope.Only` ([[pages/decisions/0054-functions-scoped-per-skill-and-job]], `:177`), the same helper the chat's turns use, so no write is offered and the shared kernel's filters stay on the copy; automatic function choice is sent only when the copy holds one of them (`:182`), so a host without the GitHub or Knowledge plugin never sends a placeholder tool (`tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:59`); after the turn, every function call in its history that names none of the six is logged as a Warning, `Audit <id> batch <n>: the model called <Plugin.function>, which the batch does not offer; it did not run.`, never with its arguments (`src/Scout.Audit/AuditBatchRunner.cs:195`, `tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:72`, and on the Ollama connector, where Semantic Kernel appends the call and its error result to the turn's history, `tests/Scout.Host.Console.Tests/HostAuditTurnTests.cs:163`, which also shows the write gate is never asked); a filter on that copy counts a `get_file_contents` call as a file read only once the call returned the file's content: it opens a `ReadOutcome` scope around the call ([[pages/services/llm]]), and a read that threw, or one the function marked as not the content, is not coverage. When the turn ends without error, the outcome carries the files read and the batch's files that are not among them, `Unread` (`src/Scout.Audit/AuditBatchRunner.cs:18`, `:74`), in the batch's order through `AuditBatchRunner.Unread` (`:95`), the one rule the last post also applies to the kept rows; an outcome with no unread file is a batch read in full. The GitHub plugin marks every answer of `get_file_contents` that is not the file's text: a file it did not find, a directory, a symlink or submodule, a binary, a refused name and an error line ([[pages/services/plugin-github]]); the audit never reads the answer's text to tell, and the file is then named among the unread files of its area in the last post. A read counts only when the path is one of the batch's files and the owner, repository and reference (the full commit or a prefix of at least seven characters) are the job's (`src/Scout.Audit/AuditBatchRunner.cs:210`, `:227`, `:229`; on the Ollama connector with the real plugin and a snapshot that lacks one of the two files, `tests/Scout.Host.Console.Tests/HostAuditTurnTests.cs:141`). The findings come from the `scout-findings` block `present_audit_findings` attached in the turn (`TurnAttachments`; a second call in the turn replaces the first block); a block for another repository, or naming a commit that is not the job's (a block that names no commit is taken as the job's), is dropped whole, and a finding in a file outside the batch, compared without case like the merge, is dropped, with one Warning per batch, `Audit <id> batch <n> dropped <count> findings outside its files, its repository or its commit.` (`src/Scout.Audit/FindingsBlock.cs:27`, `src/Scout.Audit/AuditBatchRunner.cs:64`, `:69`). Each attempt has the turn time limit (`src/Scout.Audit/AuditBatchRunner.cs:62`) and, since 2026-11-11, its own files read: a failed attempt hands the retry an empty set (`:85`), so a file read only in the failed attempt is named unread in the retry's outcome (`tests/Scout.Audit.Tests/AuditBatchRunnerTests.cs:369`). A failure first goes through `LlmFailures.Translate` (`src/Scout.Llm/Abstractions/LlmFailures.cs:18`), the rule the gateway uses, with the chat service's model id, because this turn reaches the chat service without the gateway and a provider's HTTP 429, 402, 401 or a missing model's 404 arrives as the SDK's `HttpOperationException` or `ClientResultException` (`src/Scout.Audit/AuditBatchRunner.cs:78`). A usage limit or billing refusal (a 402 included), rate limit, expired sign-in, rejected key or a model the AI Source does not have (`LlmQuotaExceededException`, `LlmRateLimitException`, `LlmSignInRequiredException`, `LlmKeyRejectedException`, `LlmModelNotFoundException`, `:79`) is not run again and asks the job to pause, a rejected key with the reason "the AI Source rejected its key" (`:104`), a missing model with "the AI Source does not have the model <id>" (`:105`), so the pause post names the model the owner has to install or finish downloading, and the quota code `credit_balance_too_low` with "the AI provider's account has run out of credit" (`:100`); any other failure, the time limit included, is run once more, and a second failure leaves the batch not covered with a reason in words (`:98`), never the provider's message; a turn cut short by shutdown leaves the batch pending.

- **Worker** (`src/Scout.Audit/AuditWorker.cs:34`): oldest running audit first, a running review left as it is, its batches pending, while the audit behind it runs (`:68`, `tests/Scout.Audit.Tests/AuditWorkerTests.cs:1028`), the first pending batch next (`:109`), until no batch is pending or the job is no longer running (`:81`), so a stop or the owner's pause takes effect after the batch in progress, whose findings are kept and posted; every post goes to the conversation the job holds when it is posted, read once before each batch's posts (`src/Scout.Audit/AuditWorker.cs:172`), so a job paused in one chat and continued from another posts there from the next post on; on start it reads the running jobs before waiting for a wake (`:59`), which is how a job Scout closed in the middle resumes, and a paused job is not among them, so a restart resumes no paused job, whoever paused it (`tests/Scout.Audit.Tests/AuditWorkerTests.cs:964`). A database failure or any other error in a job is logged and the worker waits for the next start, the job still running, so the host keeps running (`src/Scout.Audit/AuditWorker.cs:78`); a start of that same repository, answered as already running, is such a start and wakes it, and the job then runs to its end (`tests/Scout.Audit.Tests/AuditWorkerTests.cs:988`). A batch that asks to pause leaves the job paused, the batch still pending, makes no further call, and posts one sentence, only when its own pause took (`src/Scout.Audit/AuditWorker.cs:119`), so a job the owner paused or stopped while the batch ran keeps its row and gets the owner's notice below, never the AI Source's (`:253`): `The audit of owner/repo paused: <reason>. Ask Scout to continue the audit of owner/repo when the AI Source has capacity again.`; the worker leaves a paused job until a start resumes it. When the worker leaves a job because the owner paused or stopped it, it posts one notice (`src/Scout.Audit/AuditWorker.cs:154`): for a pause `The audit of owner/repo paused: you paused it. Ask Scout to continue the audit of owner/repo to resume it from the first area not done.` (`:256`), which the desktop's bell reads as the audit paused, and for a stop `The audit of owner/repo ended at your request: k of n areas done, f findings kept on the cards.` (`:259`); a pause the owner lifted before the area ended posts nothing. The last post is posted only when `FinishAsync` marked the job done (`:100`): `FinishAsync` answers false, and writes nothing, for a job no longer running, so a pause or stop landing between the last area and the finish gets its own notice and the last post comes once, when a start continues the job (`tests/Scout.Audit.Tests/AuditWorkerTests.cs:916`, `:948`). A batch whose findings are new to the job posts `Audit of owner/repo, area (i of n, f findings so far):`, f being the job's findings after the batch (`1 finding so far` for one), and a block with only those findings, kind `audit`, the commit, the turn's verdict and `area: k of n files read`; when one block would pass 30,000 characters (`src/Scout.Audit/AuditWorker.cs:42`), under the 32,000 at which the local poster and the desktop cut a message and leave the fence open, the findings are shared over several posts, each a complete block with the same repository, commit, verdict and read line and the heading `…, part k of m:` (`:192`). The last post (`:268`), cut between lines and then between list items when it is longer (`:232`), carries the verdict and the counts by severity: `incomplete` when any area was not read in full or not covered (`src/Scout.Audit/AuditWorker.cs:45`, `:282`), whatever was found, because a reader who stops at the first line must never read a clean verdict for code nobody read; otherwise sound, or sound after the High findings when one is High (`:302`). The verdict word is the job's: the model's vocabulary (`code-audit` and `present_audit_findings`) still offers sound, sound after the High findings and needs rework, and the batch card of an area whose outcome names an unread file says `incomplete` whatever the model said (`:195`). Then how many areas were covered, the files read in full, the files only partly read (`Partly read (first 20,000 characters): …`, not counted as read), the areas the model answered without reading every file, `Not fully read: area (not read: a, b).`, which keep their findings but are not counted as covered (`src/Scout.Audit/AuditWorker.cs:270`, `:291`), and the areas not covered with why; `Every area was covered.` closes it only when no area failed and none was read in part (`:296`). A batch answered without reading every file is kept done with the files it read and its findings (`:134`) and never run again: a model that keeps skipping a file would otherwise run the same area in a loop and spend the provider's budget without end, so the last post names the files instead and the owner decides whether to audit again. A batch with no new findings posts `Audit of owner/repo, area (i of n, f findings so far): no new findings.` only when the job's origin is the desktop's local chat (`local:`, `src/Scout.Audit/AuditWorker.cs:53`, `:142`, `:221`), so the desktop's bell moves with every area; any other origin gets nothing for it, as before (the owner's decision of 2026-11-14, `tests/Scout.Audit.Tests/AuditWorkerTests.cs:52`, `:85`). An area not covered posts nothing. A post that fails or throws is logged and the job goes on (`:305`); a job started outside a chat posts nothing.
