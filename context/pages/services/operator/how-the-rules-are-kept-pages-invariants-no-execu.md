## How the rules are kept

- [[pages/invariants/no-executive-writes]]: the operator writes nothing outside the control plane's state, the project's media directory and the operator media root's `voice-samples` folder, the last only through `MediaFiles` and only for the bundled voices' samples (`tests/Scout.Operator.Tests/VoiceSamplesTests.cs:120`), and refuses a file name that would leave it or starts with a dot, nothing written in the media directory or its parent (`tests/Scout.Operator.Tests/MediaFilesTests.cs:18`, `tests/Scout.Operator.Tests/ProductionTests.cs:390`); its one model-callable write, `youtube_make_video`, is declared to the write gate and lands on a `Write` row of the catalog (`tests/Scout.Host.Console.Tests/WriteDeclarationCatalogTests.cs:13`); the research and script requests offer the model no function, so a title in a search result cannot make it call one (`tests/Scout.Operator.Tests/TopicResearcherTests.cs:109`).

- Every write goes through the gate: a composed chat turn that calls `youtube_make_video` asks the gate with `youtube | Scout's data folder | youtube_make_video(topic=...)` before the project is saved (`tests/Scout.Host.Console.Tests/HostOperatorTurnTests.cs:50`), a save the control plane refuses is recorded as failed, never succeeded (`:72`), and a chat edit by someone who is not the owner is asked for, refused before any control-plane call and recorded as `failed: InvalidOperationException` (`:92`). The statuses and the claim status the operator sends, and its scope text, are the ones the control plane accepts (`tests/Scout.Host.Console.Tests/OperatorContractTests.cs:53`, `:208`).

- The owner's direction reaches the model only as data in the one script request and the one scene request, which offer no function (`tests/Scout.Operator.Tests/ScriptWriterTests.cs:66`, `tests/Scout.Operator.Tests/ScenePlannerTests.cs:87`), and never an ffmpeg command (`tests/Scout.Operator.Tests/AssemblerTests.cs:418`); the format and the direction are the owner's, chosen on the desktop or, since phase 8d, given by the owner to `youtube_make_video` from the chat, and refused with nothing started from anyone else (`tests/Scout.Operator.Tests/YouTubeOperatorPluginTests.cs:506`, `:537`).

- Owner only from the chat: who the owner is never comes from a function parameter, only from the turn the conductor entered (`tests/Scout.Conversation.Tests/ConversationConductorOriginTests.cs:145`, `:155`, `:167`, `:175`); every owner-only function refuses anyone else before any control-plane call (`tests/Scout.Operator.Tests/YouTubeOperatorPluginTests.cs:354`); a change runs only after a state read of the same project in the same conversation within 10 minutes (`:611`, `:622`); the project state and the list keep the topic, the direction and the scene texts after the data sentence and never show candidates, claims, sources or the package description (`:367`, `:479`).

- Progress only to the origin: the only posts are the start, ready and failure notices, to the reference the turn carried; a project without one posts nothing (`tests/Scout.Operator.Tests/OperatorPipelineTests.cs:30`, `:68`).

- The owner's claim decisions are never changed or dropped by the worker (`tests/Scout.Operator.Tests/OperatorPipelineTests.cs:149`).

- A locked scene and the owner's own media are never regenerated and go back exactly as read (`tests/Scout.Operator.Tests/ProductionTests.cs:316`); the production statuses and every scene value the operator sends pass the control plane's worker validation (`tests/Scout.Host.Console.Tests/OperatorContractTests.cs:76`), and a scene save from a read older than the owner's reorder keeps the owner's order, while after a regenerate it is refused with exactly the words the pipeline stops on, "The project is no longer producing." (`:164`).

- Media only from the connected provider's Semantic Kernel services, never a link fetched from the provider (`tests/Scout.Operator.Tests/VisualGeneratorTests.cs:129`); the one link the operator fetches is the `url` of an Openverse result of an allowed licence, a GET whose answer must be an image of at most 20 MB, written only through `MediaFiles` into the media directory, nothing left when it is refused (`tests/Scout.Operator.Tests/OpenversePicturesTests.cs:33`, `:117`, `:208`), and the YouTube feature declares that read (`tests/Scout.Host.Console.Tests/WriteDeclarationCatalogTests.cs:40`).

- The mandate's blocked topics hold from the first step: `youtube_make_video` and the pipeline refuse a blocked topic before any search (`tests/Scout.Operator.Tests/YouTubeOperatorPluginTests.cs:115`, `tests/Scout.Operator.Tests/OperatorPipelineTests.cs:101`).

- The owner's own video stays on the machine: the recording is read and its sound written only inside the media directory, through `MediaFiles`, and the WAV is removed when the transcription ends, also when it fails (`tests/Scout.Operator.Tests/TranscriptionStageTests.cs:68`, `:113`, `:140`); the transcript is sent only as data in the one chapter request, which offers no function and calls it data, never instructions (`tests/Scout.Operator.Tests/ScenePlannerTests.cs:175`); production asks no speech, image or stock service (`tests/Scout.Operator.Tests/ProductionTests.cs:508`) and the thumbnail no image service (`tests/Scout.Operator.Tests/ThumbnailMakerTests.cs:148`). The transcription calls nothing over the network ([[pages/invariants/local-first-default]]).

- The screenshot text reader writes no file and passes no path but the language data folder; the image goes in on standard input and the text comes out on standard output (`tests/Scout.Operator.Tests/ScreenText/TesseractScreenReaderTests.cs:97`).

- Assembly writes only inside the media directory, through the same confinement, and reads only scene files that resolve inside it (`tests/Scout.Operator.Tests/AssemblerTests.cs:246`, `tests/Scout.Operator.Tests/MediaProbeTests.cs:44`); ffmpeg gets an argument list, never a shell string, and no standard input, and piper only the narration (`tests/Scout.Operator.Tests/ProcessRunnerTests.cs:10`, `:19`, `:31`); piper runs with exactly its argument list, writes only inside the media directory and leaves no file when it fails or times out (`tests/Scout.Operator.Tests/PiperSpeechTests.cs:90`, `:145`), and a voice id it did not find runs nothing (`:191`); a failed assembly leaves no partial package file, even when a Short fails while the thumbnail is still being made (`tests/Scout.Operator.Tests/AssemblyTests.cs:264`, `:393`).

- The owner's package fields, `rights_confirmed`, `approved_at`, `metadata_edited`, `metadata_saved_at`, `rights_confirmed_at` and edited metadata, go back exactly as read (`tests/Scout.Operator.Tests/AssemblyTests.cs:205`, `tests/Scout.Host.Console.Tests/GrpcOperatorControlPlaneTests.cs:453`), and a last-resort failed save keeps them too (`tests/Scout.Operator.Tests/OperatorWorkerTests.cs:145`).

- The first metadata always fits YouTube's limits, whatever length the model gives the title or the owner gives the topic, and both sides count tags the same way (`tests/Scout.Operator.Tests/AssemblyTests.cs:161`, `tests/Scout.Host.Console.Tests/OperatorContractTests.cs:235`).

- Writes to YouTube only as actions the owner approved ([[pages/decisions/0032-per-feature-write-permissions]]): the model's `youtube_publish_video` and `youtube_delete_project` are no declared writes and queue nothing; only `youtube_make_video` and the owner's eight changes, `youtube_change_presenter` among them, all into Scout's data folder, are declared (`tests/Scout.Operator.Tests/YouTubeOperatorPluginTests.cs:216`, `:241`, `:587`), and a project without the owner's publish settings is never uploaded (`tests/Scout.Operator.Tests/ActionExecutorTests.cs:214`).

- A video is uploaded once: a project with a video id is only recorded, an upload whose save failed is saved on the next run without a second upload, an action handed out again after a crash between the upload and the record is recorded without a second upload, a publication found `uploading` after a restart is failed rather than uploaded again, and an interrupted upload resumes its own session (`tests/Scout.Operator.Tests/ActionExecutorTests.cs:160`, `:142`, `:390`, `:575`, `:588`); an upload or an arm switch the owner revoked during is saved, then recorded after revoke once, never failed and never repeated, against a fake that refuses what the control plane refuses after a revoke (`:407`, `:429`); a write YouTube took whose save is refused is still recorded succeeded (`:448`, `:464`); any other refusal saves no revoke sentence (`:613`); the session ends with its action (`:478`); an arm switch after the experiment ended changes nothing on YouTube (`:627`, `:640`).

- The owner's publish settings and decisions go back as read: the upload carries the owner's privacy, schedule and declarations (`tests/Scout.Operator.Tests/ActionExecutorTests.cs:82`, `:102`), and proposals the owner decided are kept next to new ones (`tests/Scout.Operator.Tests/LearningLoopTests.cs:155`); no experiment is ever adopted by the worker (`tests/Scout.Operator.Tests/ExperimentRunnerTests.cs:92`).

- Comments are data written by strangers: the sort and draft requests and the research offer the model no function and call the comments data, never instructions (`tests/Scout.Operator.Tests/CommentDeskTests.cs:114`, `tests/Scout.Operator.Tests/TopicResearcherTests.cs:194`); a sync never writes to YouTube, against a write client that throws on any call (`tests/Scout.Operator.Tests/CommentDeskTests.cs:257`); a reply posts the owner's approved text once and never the draft, a reply found `replying` after a restart is failed rather than posted again, and a hold sets held for review only (`tests/Scout.Operator.Tests/ActionExecutorTests.cs:747`, `:760`, `:896`); the comment kinds, statuses and saves the worker sends are the ones the real comment service accepts (`tests/Scout.Host.Console.Tests/OperatorContractTests.cs:263`).

- The owner's comment decisions are never changed: a decision made while the model drafts is kept (`tests/Scout.Operator.Tests/CommentDeskTests.cs:306`), and an idea the mandate blocks is never proposed (`:240`).

- The presenter job writes only inside the media directory, through `MediaFiles`: the generated or copied picture, the preview's narration and video; it deletes only the preview narration of presenter versions the control plane no longer keeps, a generated picture it replaced with a built-in one and the narration of a failed preview, and leaves a dropped version's picture and video to the control plane (`tests/Scout.Operator.Tests/PresenterStageTests.cs:310`, `:255`, `:282`). The face models run in the process on local files, so finding the mouth calls nothing over the network, and every presenter picture is one request of the declared picture call, counted in the day's 40 ([[pages/invariants/no-executive-writes]]). The image service gets the owner's prompt or feedback only as text before the safety tail, which is always last (`tests/Scout.Operator.Tests/PresenterStageTests.cs:80`, `:169`).

- The face models are an external boundary of their own (Rule I): a runtime that throws, a model that is missing or will not load, and an ffmpeg decode that fails each answer null and are logged once, and the presenter job goes on with Scout's own presenter, never a failed project or scene (`tests/Scout.Operator.Tests/FaceMouthTests.cs:171`, `:193`, `:212`, `tests/Scout.Operator.Tests/PresenterStageTests.cs:255`).
