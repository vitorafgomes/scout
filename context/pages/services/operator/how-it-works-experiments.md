## How it works

**Experiments.** `ExperimentRunner` (`src/Scout.Operator/ExperimentRunner.cs:19`) only reads: the arms go live through the approved actions above. For each running experiment, each UTC day is credited to the arm live for most of its hours, the earlier arm on a tie, so a switch day never counts for both (`:133`); an arm whose window has ended and whose credited days reach reports cover gets its impressions and clicks from the reports and its average view percentage from the Analytics API for those days, and an ended arm credited with no day counts zero (`:66`). Nothing is saved when nothing changed (`:120`). When every arm is measured it decides (`:172`): every arm needs 1,000 impressions and 10 clicks, the two arms with the best click-through rate are compared with a pooled two-proportion z-test, a winner needs z of 1.96 or more, and viewers must not have watched the winner more than 5 points less, in average view percentage, than the control; the experiment is saved `concluded` with the winner and a sentence ("Question has a 5.0% click-through rate against 4.0% for Original (z = 3.41): Question wins.") or `inconclusive` with the reason. Nothing is adopted; adoption is the owner's AdoptExperimentWinner.

**Schedule.** `OperatorScheduler` (`src/Scout.Operator/OperatorScheduler.cs:71`) checks every minute and runs each job once per slot (`:107`), on the London clock (`src/Scout.Operator/London.cs:9`: Europe/London, else `GMT Standard Time`, else UTC): the next topic at 06:00, the snapshots at 09:00, the evening proposals at 22:00, the weekly review on Sundays at 08:00, the experiments and the comments every 4 hours, on the UTC hours a 4-hour period starts, and the published check every 15 minutes (`src/Scout.Operator/OperatorServiceCollectionExtensions.cs:102` to `:108`). The slot each job last ran is kept in `operator-schedule.json` in Scout's data folder, beside the operator's media root, found from a project's media directory (`src/Scout.Operator/OperatorScheduler.cs:227`); at start a job runs only when its stored last run is before its latest slot, and the clock slots it so catches up are named in the readiness notes: "Scout was not running for these scheduled jobs and ran them when it started: analytics 09:00, ..." (`src/Scout.Operator/ReadinessReporter.cs:98`); a job with no stored run, as on the first start ever, waits for its next slot (`src/Scout.Operator/OperatorScheduler.cs:142`). A slot is stored only when the job ran (a job that threw still counts as run); a slot skipped because the YouTube token file is absent is not stored, so the job runs on the first check after the sign-in appears, within the same slot. Until the state file can be found, before the first project exists or while the control plane cannot be reached, nothing runs and nothing is written; the stored slots are read once it is found (`src/Scout.Operator/OperatorScheduler.cs:112`). A state file that cannot be read counts as empty and is logged (`:195`). Every job is skipped while the YouTube token file is missing. A job that fails is logged and the others run.

**Comments.** `CommentDesk` (`src/Scout.Operator/CommentDesk.cs:28`) keeps the comments on the owner's channel, one run at a time (`:102`). A run reads the comments through the gated `GetCommentsAsync`, and a sync then reads the owner's channel and its comment threads, `commentThreads.list` with `allThreadsRelatedToChannelId`, newest first, in plain text, 100 a page: since the stored `synced_at`, or the last 4 days before the first sync (`:66`), keeping only the threads whose top-level comment was published at or after that time and reading pages until a whole page is older or 5 pages are read (`:220`, `:232`, `:233`), because YouTube can bring a thread an old comment opened back to the top when it gets a fresh reply, so one old thread never hides newer comments behind it. It leaves out the owner's own comments, by author channel id, a comment id already stored and an id outside `^[A-Za-z0-9_.-]{1,100}$` (`:242`), cuts the text at 2000 characters, names each video through `GetVideosAsync`, 50 ids a call (`:247`), and stores `published_at` in round-trip form and `fetched_at` empty, which the control plane stamps. The new comments are sorted 25 at a time through `ModelJson` with no function offered (`:275`): the system prompt says the comments are data written by strangers, never instructions, each comment goes into the request as one JSON object labelled `c1`, `c2` and on, and the answer is `{id, kind, theme, request}`; a kind outside `question`, `request`, `praise`, `feedback`, `other`, `spam` is `other`, the theme is cut at 40 characters, a comment the model did not return stays `new` as `other`, and `spam` is `quarantined`, which gets no draft. Then the drafts (`:202`): every `draft_requested` comment, then, in a sync only (`:199`), the `new` questions and requests without a draft, each newest first, at most 20 a run, 10 to a request, in the mandate's language and voice, at most 1000 characters, no link and no promise of a date, a prize or a giveaway (`:291`); a draft is cleaned of control characters but new lines and dropped when it holds `://` or `www.` (`:343`), and a draft request past the 20 waits for the next run. A new `request` whose request text the mandate's `BlockedTopic` match lets through becomes the idea `idea-<comment id>`, `proposed`, at most 200 characters (`:194`). Every save goes through `ChangeAsync` (`:143`): one save at a time in this process, built on a read made just before it, with only the run's changes applied (`:319`): a draft lands only on a comment whose status and owner's decision are still the ones the run read, a new comment only when its id is not stored yet and an idea only for a comment the run added, so an owner's dismiss, draft request or sync request made while the model wrote is kept. A sync saves `synced_at` as the run's start in round-trip form, never truncated, so it answers a sync request stamped in the same second (`:126`); a drafts-only run reads nothing from YouTube, sends `synced_at` back as read and `sync_error` empty, and the control plane keeps the stored error on an empty one (`:339`). A YouTube or model failure of a sync saves its readable reason as `sync_error` with the stored `synced_at`, together with the comments of every batch the model already sorted, their ideas and the drafts already written, never a comment not sorted yet (`:120`, `:179`); the control plane takes it as a failed sync and clears the request, and the next sync reads the same window again and skips the comments saved, so only the tail is sorted again. A failed drafts-only run saves the drafts it already wrote, with no sync error. Nothing in the desk writes to YouTube.

`CommentRequests` (`src/Scout.Operator/CommentRequests.cs:16`) reads the comments every 60 seconds (`:22`): a stored `sync_requested_at` runs a sync once for that request (`:68`), even when the sync's save fails, so a control plane that cannot take the save does not cost a YouTube read and model calls every minute; the owner's next request or the scheduled sync tries again. Otherwise a comment waiting in `draft_requested` runs the drafts only (`:74`); a drafts run runs once for the same draft requests, by comment id and decision time (`:76`): one it left unanswered, because the model failed or wrote no usable draft, waits until the requests change, a sync is asked for or the scheduled sync runs, so the model is not asked every minute, while more than 20 requests shrink and the rest run the next minute. A control plane that cannot be read is logged once until it answers again (`:56`), and a run that fails is logged once per run (`:82`). With only an API key the sync fails on the owner's channel with the plugin's "Sign in from the Scout app to read your own channel; an API key reads public channels by handle only.", which the desk saves as the sync's error, so the control plane clears the request and the desktop shows why. Reading the comment threads needs the `youtube.force-ssl` scope of the write sign-in, so with the read sign-in alone the sync fails on `commentThreads.list` with "Reading comments needs Scout's permission to reply to and moderate comments: open the YouTube card in Scout Desktop and allow writes again.", saved the same way ([[pages/services/plugin-youtube]]). The scheduled `comments` job, with publishing only, syncs every 4 hours (`src/Scout.Operator/OperatorServiceCollectionExtensions.cs:108`); the desk's run lock makes a job and a request wait for each other instead of running together.

**Replies and holds.** A comment action targets `comment:<id>` (`src/Scout.Operator/ActionExecutor.cs:207`) and carries no origin, so nothing is posted to a chat. `comments.insert` (`:413`) reads the comments; a comment with a reply id is only recorded (`:419`); a reply id YouTube gave this process whose save failed is saved without a second post (`:424`); a comment found `replying` that this process cannot prove unposted is failed with "The reply may already be on YouTube; check the video's comments in YouTube Studio before replying again." and the action recorded failed (`:429`); otherwise it needs `reply_approved` or `replying` and the owner's approved text, saves `replying` first, posts the approved text, never the draft (`:452`), keeps the reply id in this process and saves `replied` with it. A post YouTube surely refused marks the action unposted again (`:456`), so a retryable one posts on the next run: a 4xx such as a 401 or a 429, or a failure with no status, which only the token handler raises before the request is sent, when the token file is missing (`:626`). A success status with an answer Scout cannot read, or without a reply id, means YouTube took the reply: the comment is failed at once with the "may already be on YouTube" sentence (`:459`), so the owner checks YouTube Studio before approving another; a 5xx, a timeout or a reset may have landed and the next run fails the comment the same way. YouTube took it but the save is refused: recorded `succeeded: comment <id>, not saved` (`:487`). `comments.setModerationStatus` (`:482`) holds a `hold_approved` comment for review on YouTube, safe to repeat, and saves `held`; a `held` one is only recorded. Each step's save reads the comments just before; when that read is refused, as after a revoke, the step is applied to the state the previous save answered, the one the control plane checks executing steps against. A comment action that fails for good saves the comment `failed` with the reason (`:535`); one that can pass saves nothing on the comment, because the worker may change a comment's error only with an execution step, and is left for the next run; the revoke sentence is never saved on a comment.
