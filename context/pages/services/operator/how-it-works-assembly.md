## How it works

**Assembly.** A project taken as `assembling` (`src/Scout.Operator/OperatorPipeline.cs:104`) posts "Assembling <topic>..." and runs `AssembleAsync` (`:384`): it asks `FfmpegToolset` for the tools and fails with the readiness note when there are none, reads the media directory and the project, stops without saving when the project is no longer `assembling`, reads the mandate, renders through `AssemblyStage` (`src/Scout.Operator/AssemblyStage.cs:24`), which hands the project's `BackgroundFile`, as read, to the assembler (`:55`), and saves once through `SaveStageAsync` (`src/Scout.Operator/OperatorPipeline.cs:338`), the same gated save production uses: the project read immediately before, `assembled`, the package built on that read (`:399`). The chat then hears "Video ready to review for <topic>: open Scout Desktop, YouTube operator." A save the control plane refuses with "The project is no longer assembling.", or a read that shows another status, stops the run without a failed save and without a notice (`:351`). Any other failure saves the project `failed` with the reason and the package `failed` with the same error, no files, no checks and no duration, the owner's rights, approval and metadata as read (`src/Scout.Operator/AssemblyStage.cs:157`), and the chat hears "The video project on <topic> stopped: <reason>". A package the control plane cannot take removes the rendered files before that failure is saved (`src/Scout.Operator/OperatorPipeline.cs:407`). When that failed save itself fails, the worker's last-resort save of an `assembling` project fails the package too, keeping the owner's fields, so it is never left `assembling` (`src/Scout.Operator/OperatorPipeline.cs:464`).

`AssemblyStage.RenderAsync` measures every scene's audio file that is on disk, the owner's and the generated, with `MediaProbe` (`src/Scout.Operator/MediaProbe.cs:18`: `ffmpeg -hide_banner -nostdin -i <file>`, read from the `Duration: HH:MM:SS.xx` line ffmpeg writes about its input, its exit code ignored because ffmpeg exits with an error when given no output (`:55`); a file with no length fails the project with "Scout could not read the length of <file>."), and uses those lengths for the video, the chapters, the Shorts and the package duration; the scenes go back to the control plane as read, because it refuses scene changes on a project that is not producing (`src/Scout.Operator/AssemblyStage.cs:49`). Then the video, and the Shorts, the thumbnail and the loudness measure at the same time (`:61`); a render that fails waits for all three to end, then removes `video.mp4`, the Shorts and `thumbnail.png` (`:79`) and keeps the scene segments. Once the package is saved, only the segments the saved video was not joined from and the `short-<n>.mp4` past the ones it cut are removed, best effort, a folder that cannot be listed left as it is (`:93`, `src/Scout.Operator/OperatorPipeline.cs:413`), so the next assembly after one scene changed renders only that scene again, as long as no scene moved: a picture's zoom in or out follows the parity of its position, so a reorder renders again every scene whose position parity changed, and a new motion preset renders again every scene whose command it changes: every picture scene, and the text cards too when the switch is to or from `dynamic`, whose cards slide 48 px instead of 24 (`src/Scout.Operator/Assembler.cs:227`, `:536`, `tests/Scout.Operator.Tests/AssemblerTests.cs:403`).

`Assembler` (`src/Scout.Operator/Assembler.cs:44`) renders one 1920x1080 segment per scene in order and joins them with the concat demuxer: `ffconcat version 1.0` and one `file 'segment-<key>.mp4'` line each, plain names resolved next to the list, the video copied with `-c:v copy` and the audio encoded again with the render's audio settings, then `-movflags +faststart` (`:524`, `:527`), because copying each segment's padded last AAC frame overlaps the next segment and ffmpeg logs a non-monotonic DTS at every join; the segments themselves carry no `+faststart` (`:271`). A scene lasts its measured length, at least 2 s (`:50`). The project's `motion`, the preset the owner chose on produce or delegate ([[pages/services/control-plane]]), which `AssemblyStage` passes in, chooses how pictures and text cards move: `still`, `gentle` or `dynamic`, any other value reading as `gentle`. The preset only picks between the assembler's own constant filter chains, so no text of it reaches the command, and the project's direction never reaches the assembler at all. Under `gentle`, a picture, when the file is in the media directory, is read as one frame (`-i <picture>`, no `-loop`), scaled to fit and padded black to 3840x2160 once, then moved slowly by `zoompan`, which turns that one frame into every frame of the scene, `d` = the scene's length times 30 rounded up, at 30 fps and 1920x1080 (`src/Scout.Operator/Assembler.cs:220`, `:536`): the first, third and every other scene by its position in the video zooms in from 1 to 1.08 while the framing drifts toward the centre, the others zoom out from 1.08 to 1 around the centre; the zoom depends only on the output frame index `on` and `d`, so the command, and the segment's name, are the same on every assembly. Under `dynamic` the zoom goes to 1.16 and the drift is twice as wide, from a quarter to three quarters of the margin. Under `still` there is no `zoompan`: the picture is looped at one frame a second for the scene's length (`-loop 1 -framerate 1 -t <length>`), scaled to fit and padded black to 1920x1080, and held at 30 fps (`src/Scout.Operator/Assembler.cs:213`), with the same fades and captions. Without one, the project's `BackgroundFile` when the media directory holds it, rendered exactly like a picture (the same chain and captions, no first-sentence text; `src/Scout.Operator/Assembler.cs:109`, `:123`), else a text card, a `color` source of `0x14181f` with the first sentence of the narration, wrapped at 32 characters, in white at 64 px, each line fading in over 0.6 s (`alpha=if(lt(t,0.6),t/0.6,1)`) while it rises 24 px into place, 48 px under `dynamic` (`:548`). A picture scene fades in from black over 0.4 s (`fade=t=in:st=0:d=0.4`, `:259`); every scene of 2 s or more, the card too, fades out to black over its last 0.4 s (`:264`), which, with the 2 s minimum, is every assembled scene; both fades come after the captions, so the whole frame fades. Its audio is the narration file, or `anullsrc` silence, resampled to 48 kHz and padded to the scene's length; the output stops at that length. Its narration is burned in as caption lines wrapped at 42 characters (`:52`), white at 44 px on a dark box near the bottom, each shown for an equal share of the scene through `enable=between(t,from,to)`; drawing uses `drawtext` with the font passed by path, so there is no fontconfig and no libass dependency. Every text and the font path go through `FilterText.Escape` (`src/Scout.Operator/FilterText.cs:14`), escaped for the filter option and again for the filter graph, with text expansion off (`:72`) and control characters turned to spaces, so no narration can change the graph; the card's `y` and `alpha` expressions go through it too, so their commas reach ffmpeg as `\,`, and the `zoompan` expressions hold no comma or colon (`tests/Scout.Operator.Tests/AssemblerTests.cs:153`). A scene's file name is resolved through `MediaFiles.PathFor`, so a name that would leave the media directory fails the project before ffmpeg reads anything (`src/Scout.Operator/Assembler.cs:561`). A segment is named after a hash of its exact command, with the font's folder left out, and the length and write time of its inputs (`:160`, `:574`) and is rendered only when that file is not there yet (`:161`); the preset is part of the command, so a changed motion renders again every scene whose command it changes, every picture scene and, between `dynamic` and the others, every text card, so an assembly that failed after some segments continues from them, and a later assembly reuses every scene that did not change and kept an odd or even place; a reorder (`ReorderScenesAsync` renumbers the scenes and changes their positions) flips the zoom of every later picture scene, which then renders once more, about 0.2 s of wall time per second of flipped scene on the development machine. The font is passed to ffmpeg by its whole path, but the name hashes only the font's file name in its place, because Scout Desktop mounts the bundled font at a new folder on every launch and a name over the whole path would render every segment again after a relaunch (`tests/Scout.Operator.Tests/AssemblerTests.cs:808`); the name of a text card is pinned in a test with a font path without a folder, whose value is the one the same scene had before phase 8c-A (`:392`), while with the bundled font, which sits in a folder, every segment named before this change renders once more on the first assembly after the upgrade. A scene that is not `ready`, or whose picture or narration file is missing, is still assembled (the background, a text card or silence) and marked a placeholder for the checks; a missing picture shown over the background is not one. The background's name goes through `MediaFiles.PathFor` once, before the first segment, so a name that would leave the media directory fails the project before any segment is rendered (`tests/Scout.Operator.Tests/AssemblerTests.cs:361`), and the background stands in a segment's hash like the scene's own picture, by its path, length and write time, so a changed background renders those scenes again (`:375`). The three presets' graphs, the motion in the segment's name, the stage passing the project's motion, and a direction with quotes, colons, brackets and a newline that appears in no argument of any ffmpeg call are each tested (`tests/Scout.Operator.Tests/AssemblerTests.cs:66`, `:403`, `:418`, `tests/Scout.Operator.Tests/AssemblyTests.cs:145`). The motion costs little: on the development machine, with the bundled ffmpeg and `libopenh264`, a 10 s picture scene renders in about 2 s and a 6 s one in about 1.4 s (2026-11-04). Peak memory is about 110 MB per segment whatever its length. The move has a measured limit: at 30 fps and an 8% zoom the crop origin moves less than one working pixel per frame beyond about 10 s of scene at 3840, so a long scene shows the move in small steps (72% repeated frames at 60 s), accepted for now.

Every file ffmpeg writes goes through `MediaFiles.RenderAsync` (`src/Scout.Operator/MediaFiles.cs:91`): ffmpeg writes a hidden `.<guid>.<name>` with the same extension in the media directory, which is moved over the target only when it exists after a zero exit and holds at least 1 KB; a smaller file, such as a 261-byte mp4 with no frames in it, fails with the step's sentence and "(the file came out empty)", for example "Scout could not join the scenes into the video (the file came out empty)"; any failure deletes it and leaves the target as it was. `FfmpegToolset.RunAsync` (`src/Scout.Operator/FfmpegToolset.cs:132`) turns an exit other than zero into the step's sentence followed by ffmpeg's last error line, for example "Scout could not render scene 2 (ffmpeg: ...)" or "Scout could not join the scenes into the video (ffmpeg: ...)", with a timeout of 2 minutes plus four times the media's length, twelve times with VP9 (`:146`). Every render is H.264 through `libopenh264`, else `h264_videotoolbox`, at 6 Mbit/s, `yuv420p`, 30 fps, with AAC at 192 kbit/s, 48 kHz, stereo; with neither H.264 encoder, `libvpx-vp9` with Opus, still in `.mp4`, at its real-time speed: `-deadline realtime -cpu-used 8 -row-mt 1` (`:54`).
