## How it works

- **.NET, Node, Bun, Python and Go versions.** The same rule as Java: the repository names a version, read as text, JSON or XML (`DtdProcessing.Prohibit`) and never by running anything; a version file that does not parse is skipped and the next source is read; a declared version an image has runs exactly that line; a range runs the newest pinned image inside it, tested against each image's full version; nothing declared runs the default and says so; a version no image has runs nothing and the reason names both. Every note has the shape "<file> asks for <tool> <version>; ran on <tool> <full version>." or "No <tool> version was declared; ran on <tool> <full version>." (`src/Scout.Sandbox/SandboxStacks.cs:178`), and every refusal "This project asks for <tool> <version>; Scout runs <tool> <lines>." (`:184`).

  - **.NET** (`src/Scout.Sandbox/SandboxDotNet.cs:58`). With `sdk.version` in the root's `global.json` (comments and trailing commas allowed), the image is the one whose SDK the `rollForward` policy accepts (`:170`), the policy `latestPatch` when absent or unknown: `disable` needs the exact version; `patch`/`latestPatch` the same major, minor and feature band and a patch at or above; `feature`/`latestFeature` the same major and minor and at or above; `minor`/`latestMinor` the same major and at or above; `major` the oldest pinned SDK at or above, `latestMajor` the newest. Otherwise: "This project's global.json asks for SDK 9.0.100 with rollForward latestPatch; Scout runs SDK 8.0.427, 9.0.320 and 10.0.403." (`:82`); a `global.json` asking for 9.0.100 with the default policy is refused because the 9.0 image carries the 3xx feature band, which `dotnet` itself would refuse. Note: "global.json asks for SDK 9.0.300 with rollForward latestPatch; ran on SDK 9.0.320." Without a readable `sdk.version`, the SDK is the major of the highest `TargetFramework`/`TargetFrameworks` (`net5.0` and later, compared as numbers, a platform suffix such as `-windows` dropped, `net4x`, `netstandard` and `netcoreapp` ignored) across the projects the solution lists, or the root's `*.csproj` files (`:222`); a listed path is read only when it stays under the snapshot, is not rooted and is not a symbolic link, and a project that is not XML reads as declaring nothing. A project that declares no framework takes the nearest `Directory.Build.props` that declares one, from its own folder up to the snapshot's root and never above it (`:263`); the project's own value wins, a props file that is a symbolic link is skipped, it is read with `DtdProcessing.Prohibit`, and what it imports is never read. Nearest-that-declares is looser than MSBuild, which imports only the nearest props file. A highest framework no image builds: "This project targets net7.0; Scout runs .NET 8, 9 and 10." (`:96`). Note: "No SDK was declared; ran on the .NET 10 SDK; net8.0 and net9.0 tests ran on the .NET 10 runtime (roll-forward)." (the clause after the second semicolon only when lower frameworks are there); with no framework either, "No SDK was declared; ran on the .NET 10 SDK.". `DOTNET_ROLL_FORWARD=Major` is set without a `global.json` SDK, so a lower framework's tests run on the image's runtime, and with one only when its policy is `major` or `latestMajor` (`:88`, `:102`), when the note adds the same clause.
  - **Node** (`src/Scout.Sandbox/SandboxNode.cs:170`): `.nvmrc`, then `.node-version` (the first line that is not blank or `#`: `20`, `v18.19.0`, `lts/<codename>` from argon to krypton, `lts/*`, `node`, `latest`, `current` or `stable`, the last five running the newest line), then `engines.node` in `package.json` as an npm range (`>=`, `>`, `<=`, `<`, `=`, `^`, `~`, `x`/`*` wildcards, `A - B`, `||`, spaces between comparators; only those characters, up to 100, so other text never reaches a note) (`:221`), then `volta.node`. Note: ".nvmrc asks for Node 20; ran on Node 20.20.2.", "package.json's engines.node asks for Node >=20; ran on Node 26.13.0.". Refusal: "This project asks for Node 16; Scout runs Node 18, 20, 22, 24 and 26.".
  - **Bun** (`src/Scout.Sandbox/SandboxNode.cs:125`): `packageManager` `bun@<version>` (a `+sha...` suffix dropped), then `engines.bun` as a range; `.nvmrc` and the Node fields are not read. Note: "package.json's packageManager asks for Bun 1.1.38; ran on Bun 1.4.4.". Refusal: "This project asks for Bun 2.0.0; Scout runs Bun 1.".
  - **Python** (`src/Scout.Sandbox/SandboxPython.cs:87`): `.python-version` (`3.12` or `3.12.1`; `pypy3.10` is skipped), then `requires-python` in `pyproject.toml` as a PEP 440 specifier set (`~=`, `==`, `!=`, `<=`, `>=`, `<`, `>`, `===`, `.*`; `==3.12` means 3.12.0 exactly) (`:114`), then `runtime.txt` (`python-3.11.6`). Note: "pyproject.toml's requires-python asks for Python >=3.10; ran on Python 3.14.10.". Refusal: "This project asks for Python 3.9; Scout runs Python 3.10, 3.11, 3.12, 3.13 and 3.14.".
  - **Go** (`src/Scout.Sandbox/SandboxGo.cs:29`): with `GOTOOLCHAIN=local` the image's Go must be at or above the `go` line's full version. A `toolchain` directive runs that minor ("go.mod's toolchain asks for Go 1.24.3; ran on Go 1.24.13."); else the `go` line is a minimum and the oldest pinned Go at or above it runs ("go.mod asks for Go 1.21 or newer; ran on Go 1.23.12."); neither runs Go 1.25. Refusal, listing full versions because the patch decides: "This project asks for Go 1.27 or newer; Scout runs Go 1.23.12, 1.24.13, 1.25.14 and 1.26.10." (`:62`).

Resolved on 2026-11-07 with `docker buildx imagetools inspect` under `DOCKER_CONTEXT=default`: `mcr.microsoft.com/dotnet/sdk:10.0@sha256:212fe4cb...`, `node:22@sha256:7702d8aa...`, `python:3.13@sha256:ecbe213f...`, `golang:1.25@sha256:699337d6...`, and `oven/bun:1@sha256:1d22548f...` (Bun 1.4.4) (`src/Scout.Sandbox/SandboxStacks.cs:27` to `:31`). The thirteen added for the version tables (`src/Scout.Sandbox/SandboxStacks.cs:47` to `:59`), resolved on 2026-11-07: `sdk:8.0` and `sdk:9.0` with `imagetools`, their SDK and runtime versions read from `DOTNET_SDK_VERSION` and `DOTNET_VERSION` in each pinned image's linux/amd64 configuration; `node:18`, `:24`, `:28`, `:30`, `python:3.10`, `:3.11`, `:3.12`, `:3.14`, `golang:1.23` and `:1.24` with `imagetools`, each digest equal to Docker Hub's tags API (`hub.docker.com/v2/repositories/library/<repo>/tags/<tag>`), their versions read from `NODE_VERSION`, `PYTHON_VERSION` and `GOLANG_VERSION` in the pinned digest's configuration; `golang:1.26` from the tags API first and, once Docker Hub let `imagetools` through again, cross-checked with it (equal digests), its version and Go 1.25's from the API's per-image layer instructions (`ENV GOLANG_VERSION=...`), and the existing pins' versions (Node 22.23.4, Python 3.13.18) the same way as the new ones. Docker Hub answered 429 midway, which is why some fall back to the API. The fifteen Java images of the table above (`src/Scout.Sandbox/SandboxStacks.cs:32` to `:46`) were resolved on 2026-11-07, their tool versions read from each image (`GRADLE_VERSION` in the image's configuration, `mvn -v` in each Maven image), with `docker buildx imagetools inspect` under `DOCKER_CONTEXT=default`, and `gradle:9-jdk21` and `gradle:9-jdk25`, after Docker Hub answered 429, through Docker Hub's tags API, whose digests matched `imagetools` on every tag both answered; `gradle:8-jdk25`, `gradle:9-jdk8` and `gradle:9-jdk11` do not exist, and `gradle:7-jdk21` is a stale tag (Gradle 7.6.4) left out. A new digest is a code change.

- **Layout:** `WorkDirectory/<id>/` is mounted at `/work`; the copy is `/work/src` (the working directory) and every cache is under `/work/cache`. The log `WorkDirectory/<id>.log` and the record `WorkDirectory/<id>.run.json` are beside it, outside the mount.
