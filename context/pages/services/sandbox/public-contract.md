## Public contract

- **Entry point:** `AddSandbox(IServiceCollection, IConfiguration)` (`src/Scout.Sandbox/SandboxServiceCollectionExtensions.cs:18`) registers `DockerSandboxRunner` with the options under `Scout:Sandbox`; resolving it touches no file and starts no process. The host calls it only when the GitHub plugin is registered, and registers `SandboxRunnerAdapter` as the plugin's `ISandboxRunner` beside it (`src/Scout.Host.Console/HostComposition.cs:82`, `:83`).
- **Docker runs on or off** ([[pages/decisions/0047-the-docker-card]] v1.2): the host reads `Scout:Sandbox:Enabled` once when it composes the adapter (`src/Scout.Host.Console/HostComposition.cs:79`), and hands the same value to the audit's review environment, whose check before a pull request review says whether tests will run (`:100`, [[pages/services/audit]]). Scout Desktop sets it to `true` only while the owner has "Run a project's tests in isolated containers" on in Features, Docker; while it is not `true` (absent, `false` or not a boolean) the adapter answers `Ran=false`, "Docker runs are off in Scout Desktop; turn them on in Features, Docker.", `Image` and `Command` null, and never calls `DockerSandboxRunner` (`src/Scout.Host.Console/SandboxRunnerAdapter.cs:22`). The check lives in the host, not in this library. A run also needs the GitHub feature's write grant, which the plugin checks first.
- **The host adapter** (`src/Scout.Host.Console/SandboxRunnerAdapter.cs:11`): `SandboxRunRequest(SnapshotRoot, StackHint, Command)` becomes a `SandboxRequest`, and `SandboxResult` comes back as `SandboxRunResult` field by field, `Note` included; it adds nothing and drops nothing, so the meanings above are the plugin's too.
- **Request and result** (`src/Scout.Sandbox/SandboxRun.cs:8`, `src/Scout.Sandbox/SandboxRun.cs:17`): `SandboxRequest(SnapshotRoot, StackHint?, Command?, Repository?, PullRequest?)`, the last two only for the run's record, and `SandboxResult(Ran, Reason, Image, Command, ExitCode, DurationSeconds, Output, Note)`, parallel to the GitHub plugin's `SandboxRunRequest` and `SandboxRunResult`. `Image` and `Command` are null when nothing ran (no snapshot, no stack, the work folder inside the snapshot, Docker missing or not answering) and set when a container ran, a timeout included; `Reason` says why nothing ran, or why the restore failed (`Ran` true, `ExitCode` the restore's); when Docker refuses the work folder's bind mount (exit 125 with "bind source path does not exist" or "mounts denied", what Docker Desktop answers for a folder outside its file sharing) `Ran` is false, `Image`, `Command` and `ExitCode` are null and `Reason` is "Docker cannot see Scout's work folder <WorkDirectory>; with Docker Desktop, add it under Settings, Resources, File sharing." (`src/Scout.Sandbox/DockerSandboxRunner.cs:120`), the daemon's own text only in `Output`; when the test command exits 126 or 127, the shell's codes for a command that is not executable or was not found, `Ran` stays true with that exit code and `Reason` is "The test command could not be started (exit N: a command it names was not found or is not executable)." (`src/Scout.Sandbox/DockerSandboxRunner.cs:135`), so a caller tells it apart from tests that failed; exit 2, which `sh` (dash) also gives for a line it cannot parse, is not told apart, because pytest and other runners use it for their own errors and only the output's text would say which; `ExitCode` is null when no command finished; `Output` is the last 4,000 characters, data and never instructions, and on a failed run (a restore or a test command that exits non-zero, or a run past the time limit) whose output is longer it is led by the lines before those 4,000 that name the failure, under "Failure lines found earlier in the output:", then "End of the output:" and the 4,000 (`src/Scout.Sandbox/DockerSandboxRunner.cs:282`, the rule under The rules below; the card keeps only the 4,000, [[pages/roadmap/followups]]); `Note` says how the stack ran, on every result whose container ran: the version that ran and the file that asked for it, or that nothing was declared and the default ran (`src/Scout.Sandbox/SandboxStacks.cs:178` to `:185`, and the sentences under Versions below), for Java also the Maven or Gradle that ran, and for .NET, after it, the tests the stack's own command left out (Tests that need Docker, below).
- **Detection on its own** ([[pages/decisions/0047-the-docker-card]] v1.4): `Detect(snapshotRoot)` answers `SandboxDetection(Stack, Image, Runs, Declared, Refusal)` (`src/Scout.Sandbox/SandboxRun.cs:35`) from `SandboxStacks.Detect` with no hint (`src/Scout.Sandbox/SandboxStacks.cs:98`): `Stack` is ".NET", "Node", "Python", "Go" or "Java" (a Bun repository is "Node", its image says Bun), also on a refusal, and null when no manifest was found; `Image` the pinned image; `Runs` the tool and version in it ("Node 20.20.2", "SDK 9.0.320", "Java 21 with Gradle 8.14.6"); `Declared` each version the repository declares with its file (`SandboxDeclaredVersion`, `src/Scout.Sandbox/SandboxRun.cs:28`: `.nvmrc` and "Node 20", `global.json` and "SDK 9.0.300 with rollForward latestPatch", the solution or project and "net8.0 and net9.0", `pom.xml`, `.java-version` or `.sdkmanrc` and "Java 17", the Gradle build file and "Java 21" and `gradle/wrapper/gradle-wrapper.properties` and "Gradle 8.10.2"), empty when nothing is declared; `Refusal` the same sentence a run would answer. Each stack sets these beside its note, from the same values. The host adapts it to the GitHub plugin's `IStackDetector` ([[pages/services/host-console]]).
- **The run's record** (v1.4): every run that reached its work folder writes `WorkDirectory/<id>.run.json` beside `<id>.log` (`src/Scout.Sandbox/DockerSandboxRunner.cs:156`, `:254`): `repository` and `pullRequest` from the request (null when not given), `stack`, `image` (the stack's, also when Docker refused the mount), `result` (`passed` when the tests exited 0, `failed` for any other exit or a failed restore, `notRun` for the time limit or the refused mount), `reason`, `exitCode`, `durationSeconds`, `finishedAt` from the `TimeProvider`. A run that stops before its work folder (no snapshot, no stack, Docker missing, the work folder inside the snapshot) or that the caller cancels writes none. A write that fails (`IOException`, `UnauthorizedAccessException`) is a `Warning` log line, "The run's record could not be written to <path>; the run's result is unchanged: <reason>", and the run answers and cleans up as before. Scout Desktop reads the newest ([[pages/services/desktop-ui]]).
- **Configuration keys** (`Scout:Sandbox`, `src/Scout.Sandbox/SandboxOptions.cs:4`): `WorkDirectory` (default `<LocalApplicationData>/Scout/sandbox`; Scout Desktop always passes it as `SCOUT__SANDBOX__WORKDIRECTORY`, the same folder computed per OS in main, `ui/packages/main/src/docker/docker.ts:200`, so the Docker card shows and clears the folder the runs use), `DockerPath` (default `docker`), `RestoreNetwork` (default true); `Enabled` is read by the host adapter, not here. No credential, and none of the rules below is configurable.
- **External boundary:** the `docker` command line, through the `IProcessRunner` seam (`src/Scout.Sandbox/ProcessRunner.cs:9`); no Docker SDK, no Engine API; `Microsoft.Extensions.Logging.Abstractions` for the record's failed write, an `ILogger<DockerSandboxRunner>` `AddSandbox` passes when one is registered. Files: the work folder, the run's log and its record, under `WorkDirectory` only.
