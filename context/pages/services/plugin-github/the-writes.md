## The writes (ADR 0038 v1.3, ADR 0043, 2026-11-07)

- **Plugin `GitHubActions`** (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs`) with `submit_pull_request_review` (`:117`), `create_issue` (`:499`), `comment_on_pull_request` (`:302`), `comment_on_issue` (`:322`) and `reply_to_review_comment` (`:343`), each declared with `AddWriteFunction` on its row of the `github` feature, `Pull request reviews`, `New issues`, `Pull request comments` (both the comment and the reply) and `Issue comments` (`src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:136`, `:138`, `:142`, `:144`, `:146`), so the `WriteGateFilter` refuses them before anything is sent while GitHub writes are not granted, and records each run. Since 2026-11-09 ([[pages/decisions/0032-per-feature-write-permissions]]) `create_issue`, the two comments and the reply are on `IrreversibleWrite` rows and declared with `carriesPayload`, so a call by the model is queued with its arguments for the owner's approval of that one issue, comment or reply and sends nothing; the approved action is run by `GitHubWriteRunner` (`src/Scout.Plugin.GitHub/GitHubWriteRunner.cs:21`; `RunAsync`, `:52`), which the host's `GitHubActionExecutor` calls with the action's target, the function's name, and its payload, and which goes through the same checks and the same post as the function (`OpenIssueAsync`, `CommentAsync`, `ReplyAsync`, `src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:514`, `:361`, `:375`), answering the link and the login that signed it; a payload it cannot read is refused with "The action's data could not be read; ask for it again in chat." Each function's description tells the model the call is queued and promises no URL. `submit_pull_request_review` is the same since the owner's decision of 2026-11-09: a call by the model is queued with its arguments and posts nothing, and an approved review, whether the owner clicked Post on a review card (the verdict `comment`, [[pages/decisions/0043-the-verdict-on-a-pull-request]]) or approved the model's request, is posted by the runner's `PostReviewAsync` (`src/Scout.Plugin.GitHub/GitHubWriteRunner.cs:89`) through the function's own checks, the comments read from the card's array or the function's text. No GitHub write runs under the grant alone. The function, or the runner for the four, checks names and caps (50 review comments, 10,000 characters of review body, 2,000 per review comment, a title of 256; a comment or a reply is refused when empty, "The comment is empty.", or over GitHub's 65,000 characters, "The comment is over 65,000 characters.", before any call, `src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:393`), anchors every review comment to a right-side line of the diff and names the ones it dropped (`:814`, `src/Scout.Plugin.GitHub/DiffLines.cs:18`), posts exactly the body given through `IGitHubWriteClient` (`src/Scout.Plugin.GitHub/GitHubWriteClient.cs:47`, `:91`, `:55`, `:67`: `POST pulls/{n}/reviews` with event `COMMENT` and side `RIGHT`, `POST issues`, `POST issues/{n}/comments`, `POST pulls/{n}/comments/{id}/replies`) and answers with the URL GitHub gave. A refusal before sending, a refusal from GitHub or a transport failure is a `WriteFailedException` (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:839`, `:845`) the `WriteGateFilter` turns into the sentence the model gets and records as `failed: <outcome>` (`refused`, `github 403`, `HttpRequestException`); after the request left, the sentence says the write may already be there (`:835`). A 422 names what GitHub rejected whether its errors are texts or objects (`src/Scout.Plugin.GitHub/GitHubWriteClient.cs:121`).
- **The verdict** (`give_pull_request_verdict(owner, repo, number, verdict, body, comments_json, commit)`, `src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:171`) is irreversible like the five functions above: declared on `Pull request verdicts` (`IrreversibleWrite`) with `carriesPayload` (`src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:141`), so the gate never runs it in the turn: it queues it with the function's arguments as the action's payload for the owner's approval ([[pages/services/control-plane]]). The review card's Approve and Request changes go to the control plane directly, already approved, and never through chat. Either way the host's `GitHubActionExecutor` (`src/Scout.Host.Console/GitHubActionExecutor.cs:22`, registered when the gate is open and the plugin is wired, `src/Scout.Host.Console/HostComposition.cs:89`) claims the approved actions every 10 seconds, one after the other until none is left or one cannot be recorded, each claimed once and never handed out again ([[pages/services/control-plane]]), waiting one second on the injected clock after each action it sent to GitHub before it takes the next, as GitHub asks of requests that create content, a wait that ends at once when the worker stops and that an action refused before anything was sent does not cause (`BetweenSends`, `src/Scout.Host.Console/GitHubActionExecutor.cs:36`, `:64`; `tests/Scout.Host.Console.Tests/GitHubActionExecutorTests.cs:530`, `:565`, `:584`), and runs a verdict through `GitHubVerdictRunner` (`src/Scout.Plugin.GitHub/GitHubVerdictRunner.cs:24`), which reads both payload shapes and calls the same checks as the function (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:188`): the pull request moved past the reviewed commit is refused, "The pull request changed since the review; review it again." (`:217`); an approval by the identity that opened it is refused (`:224`); a verdict the signer already gave with that event on that commit is answered with its link and never posted again, which keeps a verdict whose answer was lost from being sent twice across a crash (`:252`; the reviews are read newest first, from the last page named by the `Link` header backwards, at most ten pages of a hundred, `src/Scout.Plugin.GitHub/GitHubClient.Reads.cs:86`); otherwise `POST pulls/{n}/reviews` with `APPROVE` or `REQUEST_CHANGES` and `commit_id` the head commit (`src/Scout.Plugin.GitHub/GitHubWriteClient.cs:51`). The executor records the action at once with the review's link or the failure sentence as its result, and only once recorded posts the card's tests line on the conversation, signed as the verdict was (`src/Scout.Plugin.GitHub/GitHubVerdictRunner.cs:62`); for a verdict found already given it first reads the conversation's latest page of comments, newest first, and posts nothing when a comment by the signer already carries the line; a failure there, the read included, is logged and never fails the verdict. A card click on a commit whose chat verdict still waits for the owner rejects that verdict, "Replaced by the owner's verdict from the review card.", and queues the card's own, so the verdict, body, comments and tests line that run are exactly what the card showed ([[pages/services/control-plane]]). Once executed, the action keeps only which pull request, commit and verdict it was, not the body or the comments, and a verdict left approved by a revoke and re-grant is rejected at the next click so it ages out ([[pages/services/control-plane]]). The executor keeps no note of what it sent: an action is handed to it once, and one it sent and could not record ends as `failed: not confirmed` when its claim lapses ([[pages/services/control-plane]]; `tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs:163`).
- **Who signs** ([[pages/decisions/0044-scout-acts-on-github-as-its-own-app]]): every read uses the owner's token; a write whose kind (`review`, `verdict`, `comment`, `issue`) the owner switched to the bot, on a repository listed in `BotRepos`, goes through the bot's client (`src/Scout.Plugin.GitHub/GitHubWriteClient.cs:203`); a switched write on any other repository is signed as the owner and its answer ends "Signed as you: the Scout bot is not installed on owner/repo." (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:292`). Without a bot token file every call is the owner's, exactly as before. The self-approval check and the already-given check use the bot's configured login when the bot signs, the owner's `GET user` otherwise (`:273`); a verdict the bot would sign while its login is unknown is refused before any call, "The Scout bot's login is unknown; give the verdict as yourself or recreate the bot." No message or log line carries either token (`tests/Scout.Plugin.GitHub.Tests/GitHubBotIdentityTests.cs`).
- **Catalog:** the `github` feature is `WriteClass.Executive` with the write rows `Scout's data folder` (the conventions profile, the repository snapshot and the audit job), `Pull request reviews`, `Pull request verdicts`, `Pull request comments`, `New issues`, `Issue comments` (the five from `Pull request reviews` to `Issue comments` are `IrreversibleWrite`, all but the verdict since 2026-11-09), `Local container` and `Scout bot on GitHub (optional)`, the writes switched to the bot, beside the five reads, the fifth being `Notifications`, the desktop's bell search and the bot's name (`src/Scout.ControlPlane/Features/FeatureCatalog.cs:90`, `:100`, `:105`, `:110`, `:119`, `:124`, `:129`, `:137`); enabling GitHub on a host without the desktop card confirms the writes like YouTube, and the Features screen shows the grant button and the write rows generically ([[pages/services/desktop-ui]]). Since 2026-11-12 each row also carries the one sentence the GitHub panel shows for it, the approved artboard's or a covering one where the artboard left an action out (`Contents` names the languages, `Pull requests` the account Scout signs in as, `Pull request verdicts` and `New issues` the card click that approves them, the bot row the bot's creation on GitHub's page), while the Allow writes confirmation still lists every action of a write row in full ([[pages/services/control-plane]]).
- **Enforcement:** `tests/Scout.Plugin.GitHub.Tests/GitHubTokenFileHandlerTests.cs:142` every read function sends only GETs; `:199` the only non-GETs come from the write client; `:221` the review and issue functions post only to their endpoints and answer with the URL; `tests/Scout.Plugin.GitHub.Tests/GitHubActionsPluginCommentsTests.cs` the comments, their refusals and a 403, 404, 422 and timeout; `tests/Scout.Plugin.GitHub.Tests/GitHubActionsPluginVerdictTests.cs` the verdict's checks and failures; `tests/Scout.Host.Console.Tests/GitHubActionExecutorTests.cs` the executor; `tests/Scout.ControlPlane.Tests/Features/GitHubWriteRowsGateTests.cs` the verdict, a new issue and each comment wait for an approved action and the container run runs under the grant; `tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs` the model's `create_issue` and comment calls through the kernel's gate, over the real catalog with GitHub granted, each leave a waiting action with its payload and send nothing, and the executor over the same queue sends each of the five only after the owner's approval, once; `tests/Scout.Host.Console.Tests/GitHubActionExecutorTests.cs` also an approved issue, comment and reply run from their payload, a 502, a timeout, a lost record, an unreadable payload and a grant gone or unreadable; `tests/Scout.Plugin.GitHub.Tests/GitHubActionsPluginVerdictTests.cs:268` the four descriptions; `tests/Scout.Host.Console.Tests/WriteDeclarationCatalogTests.cs:13` every declared write names a write row; `tests/Scout.Plugin.GitHub.Tests/GitHubServiceCollectionExtensionsTests.cs:102` the declarations and no hosted service.
