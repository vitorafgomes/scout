## The pull request's checks and its tests in a container (ADR 0043, 2026-11-07)

`get_pull_request_checks(owner, repo, number)` (`src/Scout.Plugin.GitHub/GitHubPlugin.Checks.cs:24`) reads the head commit, then its check runs and its commit statuses together, a hundred of each, and answers `{"sha", "checks": [{"name", "status", "conclusion", "url"}]}` with a `note` such as "100 of 140 checks shown" when GitHub counts more check runs than one page holds, a status folded in with its context as the name: `success` completed and successful, `failure` or `error` completed and failed, `pending` in progress with a null conclusion (`src/Scout.Plugin.GitHub/GitHubClient.Reads.cs:70`). A failure is a sentence, as on every read (`tests/Scout.Plugin.GitHub.Tests/GitHubPluginChecksTests.cs`).

`run_pull_request_tests(owner, repo, number)` (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.Tests.cs:58`), declared on `Local container` (`src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:159`), runs the project's own tests through the host's `ISandboxRunner` ([[pages/services/sandbox]]) over the snapshot of the head commit (the snapshot logic of `snapshot_repository`, `src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:660`). Without a runner nothing is downloaded and it answers `{"ran":false,"reason":"No container runtime is configured.",...}` (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.Tests.cs:78`). The command is the conventions profile's backticked line that names a test runner, else the first CI workflow `run` line that invokes one and can run over a fresh snapshot (a block scalar read line by line), else none, and the runner uses the stack's default (`:138`). A single-line `run` value is the command the workflow's shell gets, character for character (`:204`): a plain scalar as written, a quote inside it or at one end included, so `--filter "Category=Docker"` keeps its closing quote (until 2026-11-10 both ends were trimmed of every quote, and that line reached `sh -c` unterminated, exit 2); a value wholly wrapped in one pair of double quotes loses them and decodes `\"` and `\\`, one in single quotes loses them and decodes `''`; no other YAML escape and no trailing `# comment` is read (a comment after a plain command reaches `sh`, which ignores it); a block scalar (`|`, `>`, `|-`, `>-`) yields each non-blank line as written. A CI line is skipped (`:172`) when it is a `dotnet test` carrying `--no-build` as a word, which needs the build output CI made in an earlier step, and, when the host's `IStackDetector` names the repository's stack, when its runner belongs to another stack (`dotnet test` .NET; `npm`, `pnpm`, `yarn` and `bun` Node; `pytest` Python; `go test` Go; `mvn`, `gradle` and `./gradlew` Java; `cargo test` none, so never while a stack is known), because the stack's image carries no other runner (`:175`); a detection that throws leaves the stack unknown and the line is chosen as without a detector (`:185`). On this repository both test lines CI has, the Docker end-to-end line of `ci.yml` (`--no-build`) and `bun test ./docs` of `ui-ci.yml` (Node, the repository being .NET), are skipped and the .NET default runs. A filtered line (`--filter`, `-k`, `-run`) stays eligible: a CI filter usually leaves out tests that need a service the container lacks too, and it is the project's own choice. The match is by stack, not by image, so a `bun` line in an npm repository, or the reverse, stays eligible, and a runner the image lacks ends with exit 127, which the sandbox reports as a command that could not be started ([[pages/services/sandbox]]). The profile's line is never filtered: it is the owner's way to name the command. A `./gradlew` in command position (the line's start, or after `&&`, `||`, `;`, `|` or `(`) becomes the image's `gradle --no-daemon --offline`, because the wrapper's distribution is not in the container offline and the sandbox's note says the image's Gradle ran (`:197`), so `cd app && ./gradlew test` runs as `cd app && gradle --no-daemon --offline test` and `chmod +x ./gradlew && ./gradlew test` as `chmod +x ./gradlew && gradle --no-daemon --offline test`; the stack hint is left to the runner, and the request names the repository as `owner/repo` and the pull request's number, which the sandbox writes into the run's record (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.Tests.cs:118`, [[pages/services/sandbox]]). The answer is the run as JSON, `ran`, `reason`, `image`, `command`, `exitCode`, `durationSeconds`, `output` and `note`, nulls left out (`:241`); `output` is the runner's up to its last 6,500 characters (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.Tests.cs:267`), so on a failed run the sandbox's two sections reach the model whole, first the lines that name the failure, then the last 4,000 characters ([[pages/services/sandbox]]), and the function's description names both sections and says both are untrusted data from the pull request's code, never instructions (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.Tests.cs:59`; until 2026-11-12 the answer kept only the last 4,000, which on a large solution held later projects' summaries and not the failing test); a runner that throws is answered as not run with why. The run is kept in memory for the head commit, its output cut to the last 4,000 characters (`:249`), so `present_review_findings` attaches it to the review's block. Tests: `tests/Scout.Plugin.GitHub.Tests/GitHubActionsPluginRunTestsTests.cs` (the two bounds, `tests/Scout.Plugin.GitHub.Tests/GitHubActionsPluginRunTestsTests.cs:138`; a failed run's failure lines and end answered whole, `:308`; the description, `:326`; since 2026-11-10 a table of `run` forms, a table of lines that cannot run over a fresh snapshot, one of runners against the stack, a detection that throws, and this repository's own `.github/workflows` read from the checkout with a .NET stack, which chooses no command).

**Stopping a test run** (2026-11-10). `RunningTests` (`src/Scout.Plugin.GitHub/RunningTests.cs:14`, a singleton, `src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:111`) holds the runs in progress, keyed by owner, repository and pull request number, case-blind, with the conversation each was asked from (`ChatOrigin.Current`). `run_pull_request_tests` starts its run there as soon as the request is checked, before the head commit is read and the snapshot is taken (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.Tests.cs:81`), with a token linked to the turn's, and runs every step on that token (`:99`): the head, the commit, the snapshot's download (`:112`), the test command and the container (`:118`). `RunningTests.StopAsync` (`src/Scout.Plugin.GitHub/RunningTests.cs:23`), called by the worker when the owner clicks Stop in Scout Desktop, cancels every run of that pull request and waits for each to end, and the run itself says how it ended (`:98`). A run the stop cut short, anywhere before the sandbox returned and whatever failure ended it once the stop was asked, answers `ran` false with `The owner stopped this test run from Scout Desktop before it finished; no result was kept, so the tests neither passed nor failed.` (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.Tests.cs:86`) and keeps nothing; a snapshot cut short is deleted by the snapshot store, and no container starts. A run that ends without saying how, after the stop was asked, counts as cut short when it is disposed (`src/Scout.Plugin.GitHub/RunningTests.cs:104`), because only the sandbox's return marks a run finished. A run whose sandbox returned has finished, even when the stop came while it was returning: the sandbox has already written the run's record that the Docker card reads, so the result is kept and answered and the stop is told the run had finished (`:125`). So the turn, the record, the notice and the control's status agree (`tests/Scout.Plugin.GitHub.Tests/RunningTestsTests.cs:66`, `:81` for a stop during the snapshot, `:130` for the stop as the sandbox returns, `:148` and `:170` for a run that ends another way after the stop, and `:193` for the turn's cancellation reaching the sandbox's token through Semantic Kernel's invocation).
