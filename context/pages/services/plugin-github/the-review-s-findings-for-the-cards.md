## The review's findings for the cards (ADR 0040 v1.1, 2026-11-06)

`present_review_findings(repository, number, verdict, findings_json, commit, read)` (`src/Scout.Plugin.GitHub/GitHubPlugin.Findings.cs:31`) is how the `code-review` skill hands its findings to the desktop's cards: the model calls a function, which it does reliably, instead of writing a fenced block at the end of its answer, which it did not. `ReviewFindings.Parse` (`src/Scout.Plugin.GitHub/ReviewFindings.cs:65`) applies the rules of the desktop's parser (`ui/packages/renderer/src/app/core/review-findings.ts`): `owner/repo` by the name grammar, a positive number, since 2026-11-07 the head commit reviewed, which the card pins the verdict to and without which the call is refused with a sentence (`src/Scout.Plugin.GitHub/ReviewFindings.cs:91`), a non-blank verdict, a JSON array of at most 50 findings, each with an id of 1 to 40 letters, digits or hyphens unique in the list, a severity of `block`, `fix` or `nit`, a title of 1 to 200 characters, a relative path without a leading slash or `..`, a positive whole line, an optional text context, a non-blank why and fix, and an optional `rule` of at most 300 characters (`:192`, the rule at `:240`). Since 2026-11-07 Scout adds what the model never copies into the call: the checks read at the commit reviewed while it is still the pull request's head, written as `checks` with a running check's conclusion as null; the last container run of the tests kept in memory for that commit (`src/Scout.Plugin.GitHub/TestRuns.cs`, the last 20 runs by repository and commit), written as `tests`; and `selfAuthored: true` when the identity that would sign a verdict (the bot's login when the bot signs verdicts on that repository, the owner's otherwise) opened the pull request, so the card offers no approval GitHub would refuse. The head, the signer and the two checks reads run together, and what cannot be read is left out without failing the findings (`src/Scout.Plugin.GitHub/GitHubPlugin.Findings.cs:57`). The first problem answers one sentence naming it and attaches nothing; valid findings are written as one line of JSON in a `scout-findings` fence (`src/Scout.Plugin.GitHub/ReviewFindings.cs:59`; a blank commit, read, context or rule is left out, never written as null, which the desktop would refuse), a block over 24,000 characters refused with a sentence that tells the model to send fewer findings, the ten that matter most (`src/Scout.Plugin.GitHub/GitHubPlugin.Findings.cs:17`; the desktop carries a reply of at most 32,000 characters, and the review text sits around the block), and handed to `TurnAttachments` ([[pages/services/conversation]]), so the reply ends with the block whatever the model wrote; the answer to the model is "Findings recorded: N. End your answer with the verdict; the cards show the findings." Since 2026-11-12 a review that found nothing is called with `[]` and recorded as "Findings recorded: 0.", a block whose `findings` is an empty array, so the card still shows what was checked and the owner gives the verdict from it; a review's malformed array answers "The findings must be a JSON array of at most 50 findings; [] when the review found nothing.", and an audit still needs 1 to 50 findings and answers "The findings must be a JSON array of 1 to 50 findings." (`src/Scout.Plugin.GitHub/ReviewFindings.cs:113`). A second call in the same turn replaces the first block. Nothing is written; the only calls are the two reads for `selfAuthored`, GETs (`tests/Scout.Plugin.GitHub.Tests/GitHubTokenFileHandlerTests.cs:142` invokes it with the rest and still sees only GETs).
