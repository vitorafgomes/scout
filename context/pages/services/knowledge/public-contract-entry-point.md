## Public contract

- **Entry point:** `AddProjectKnowledge(IServiceCollection, IConfiguration)` at `src/Scout.Knowledge/KnowledgeServiceCollectionExtensions.cs:30`.

- **Abstractions:** `IProjectKnowledgeStore` (`src/Scout.Knowledge/IProjectKnowledgeStore.cs:4`) implemented by `SqliteProjectKnowledgeStore` (`src/Scout.Knowledge/SqliteProjectKnowledgeStore.cs:16`); `IChunker` (`src/Scout.Knowledge/IChunker.cs:4`) implemented by `FileChunker`, a Roslyn chunker for C# with a line-window fallback (`src/Scout.Knowledge/FileChunker.cs:11`); `ProjectIndexer.IndexAsync` (`src/Scout.Knowledge/ProjectIndexer.cs:29`); `ProjectKnowledgeService` (`src/Scout.Knowledge/ProjectKnowledgeService.cs:16`); `ProjectResolutionService` (`src/Scout.Knowledge/ProjectResolutionService.cs:13`); `ProjectDiscoveryService` (`src/Scout.Knowledge/ProjectDiscoveryService.cs:12`).

- **Model tools:** plugin `ProjectKnowledge` with `search_project`, `find_symbol`, `list_projects` (`src/Scout.Knowledge/ProjectKnowledgePlugin.cs:26,41,53`), always on the kernel since ADR 0039 (`src/Scout.Knowledge/KnowledgeServiceCollectionExtensions.cs:72`), because a project may arrive at run time: `ProjectResolutionService.Register` (`src/Scout.Knowledge/ProjectResolutionService.cs:83`) adds or replaces an entry and marks it stale, so `ResolveAsync` indexes it on its next use even when the store already holds that name (`:124`); the GitHub snapshot registers `owner/repo` this way through the host ([[pages/services/host-console]], [[pages/decisions/0039-repository-snapshot-under-the-data-folder]]).

- **Store:** one SQLite file holds two indexes of the same chunks, in WAL mode (`PRAGMA journal_mode = WAL` in the schema batch every connection runs, `src/Scout.Knowledge/SqliteProjectKnowledgeStore.cs:25`; the mode is kept in the file, so the sqlite-vec connections use it too), so a read never waits on a write in progress. The SqliteVec collection `project_chunks` keeps only the chunks that carry a vector, each of 768 values (`ChunkRecord.EmbeddingDimensions`, `src/Scout.Knowledge/ChunkRecord.cs:44`; `src/Scout.Knowledge/SqliteProjectKnowledgeStore.cs:281`). Since 2026-11-11 a replace reads every id the project (or the file) already has in the collection, page after page in id order (`:258`, `:277`), writes the new vectors, and only then removes the earlier ids it no longer holds (`:300`); a failed write removes only the rows it added, never an earlier one (`:288`), so a re-index whose vector write fails keeps the vectors the project had and the vector search still answers, and a project with more vectors than one read returns keeps none of them stale (`tests/Scout.Knowledge.Tests/SqliteProjectKnowledgeStoreTests.cs:814`, `:832`, the second with a read of two rows through the store's internal constructor, `src/Scout.Knowledge/SqliteProjectKnowledgeStore.cs:54`). Before, the earlier vectors were deleted first and a failed write removed the new ids too, so a failed re-index left text rows and no vector, and a read capped at 100,000 rows left the surplus behind. The FTS5 table `chunk_fts` (`:26`, tokenizer `unicode61`, the bundled `e_sqlite3` has FTS5) keeps every chunk and is rewritten in one transaction by `ReplaceProjectAsync` and `ReplaceFileAsync` (`:213`) after the vector write, so a failed vector write on a project's first index leaves no text rows and `HasProjectAsync` false, and the project is indexed again on its next use. Existence (`HasProjectAsync`, `src/Scout.Knowledge/SqliteProjectKnowledgeStore.cs:71`) reads the text table; when it holds nothing for the project but the vector collection does and `project_source` has no row for the project (a database written before G3), it fills `chunk_fts` from the stored chunks and answers true (`:102`), with no embedding call and no re-index. A row there changes the answer (`:83`): `ReplaceProjectAsync` writes one with an empty path before the vectors (`:136`), never over a path already recorded, so vectors with no text rows beside a row are a first index that stopped between the two writes, a process that ended or a text write that failed. `HasProjectAsync` then answers false and the next resolve indexes the project again; filled from the vectors instead, the project would have stayed without its field chunks, which have no vector, and would never have been indexed again. `FindSymbolAsync` (`:193`) is one query: the symbol contains the name (`symbol LIKE` with `%`, `_` and `\` escaped, `:200`; case-insensitive for ASCII only, SQLite's `LIKE`), the kind filter `COLLATE NOCASE` when given, exact matches first (`ORDER BY (symbol = $symbol COLLATE NOCASE) DESC`, `:202`) and `LIMIT` the top (unbounded when not positive). `SearchTextAsync` (`:169`) keeps the question's words of three characters or more (`:360`, so "is" and "to" match nothing), at most twelve, quotes each so no operator reaches FTS5, joins them with `OR`, and orders by `bm25` (`:185`).

- **Without embeddings:** when the chosen provider has no embedding generator (any provider; today the ChatGPT plan, [[pages/roadmap/chatgpt-plan-provider]]) the indexer stores every chunk without a vector, asks the embedder no more for the rest of the process, and logs once per indexed project that it did so (`src/Scout.Knowledge/ProjectIndexer.cs:92`, the catch at `:175`); `search_project` answers from `SearchTextAsync` instead of the vector search (`src/Scout.Knowledge/ProjectKnowledgeService.cs:61`, the catch at `:150`), and with no match it says "No content in project '<name>' matches the question." rather than asking for a re-index (`:63`); `find_symbol` answers as it does with embeddings. With embeddings the vector search comes first and is unchanged; when it finds nothing, as on a project indexed before the provider had embeddings, the text search answers (`:70`); there is no hybrid ranking. The file watcher re-indexes a changed file the same way, without a vector. Since 2026-11-07 an embedding model whose vectors are not 768 long (OpenAI's `text-embedding-ada-002`, or any model the OpenAI-family factories cannot ask for 768, [[pages/services/llm]]) is treated the same way instead of failing the vector write and leaving the project unindexed: the indexer drops the vectors of the first batch that has another size, stores the text, asks the embedder no more for the rest of the process (`src/Scout.Knowledge/ProjectIndexer.cs:167`) and warns once per indexed project "Vectors are off for <project>: the embedding model returns N dimensions, the index stores 768." (`:84`); `search_project` treats a question vector of another size as no vector and answers from the text (`src/Scout.Knowledge/ProjectKnowledgeService.cs:148`). A database from before G3 is not re-indexed: its text table is filled from the vector collection on the first existence check. Both tools resolve the project inside their error handling (`:52`, `:115`), so a database that cannot be opened or stays locked answers the clean "Could not ..." sentence instead of throwing; a cancellation the caller asked for is the one exception that leaves both tools (`:81`, `:131`). The filter reads the caller's token and not only the exception type: an HTTP client that times out throws a `TaskCanceledException` nobody asked for; during the question's embedding call it is logged as a warning and answered with the same "Could not ..." sentence, and during an index run it is an indexing failure like any other (Freshness, below).

- **Chunks and ids:** a C# file yields one chunk per type (class, record, interface, struct, enum, delegate) and per member (method, constructor, property, event, field; `src/Scout.Knowledge/FileChunker.cs:34`). A field or a field-like event that declares several names yields one chunk per name, each carrying the whole declaration (`:49`); a local variable or a parameter is never a chunk (`:41`). A field is in the text table only: `find_symbol` finds it by name, the embedder is never asked for it and it has no vector (`src/Scout.Knowledge/ProjectIndexer.cs:215`, `:132`), so one-line fields never take one of `search_project`'s five vector hits, and a file with nothing to embed makes no embedding call (`:133`). The text sent for embedding is cut at 16,000 characters, header included, never in the middle of a surrogate pair (`:17`, `:221`); the stored content is whole. 16,000 characters stays under the 8,191 tokens OpenAI's embedding models accept even at two characters per token; without the cut, one class of 146,592 characters in Scout's own tree made the request fail and, since a failed embedding now stops the index, the whole project unindexable on such a provider. The id is `{project}:{path}:{startLine}:{ordinal}`, the ordinal being the chunk's position among its file's chunks (`src/Scout.Knowledge/ProjectIndexer.cs:142`), because the vector collection is keyed by id and refuses a whole replace when two chunks share one: before 2026-11-09 the id ended at the start line, so one line holding two embedded declarations (`class Pair { void Swap() { } }`) left its project unindexed on a provider with embeddings (`tests/Scout.Knowledge.Tests/SqliteProjectKnowledgeStoreTests.cs:408` pins what the store does with a shared id). An index written with the old ids needs no migration: both replace paths delete by project or by path, never by id (`tests/Scout.Knowledge.Tests/ProjectIndexerTests.cs:214`, `:228`).

- **Failures while indexing:** a file that cannot be read (`IOException`, `UnauthorizedAccessException`) is skipped with one warning in a full index (`src/Scout.Knowledge/ProjectIndexer.cs:43`), and since 2026-11-11 so is a folder below the root that cannot be listed, "Skipping directory that could not be read: <path>", the rest of the repository indexed (`src/Scout.Knowledge/ProjectIndexer.cs:182`, `:194`; `tests/Scout.Knowledge.Tests/ProjectIndexerTests.cs:473`, the Rule I test of the walk), where one such folder used to abort the whole index; a root that cannot be listed still throws, so a missing repository never replaces an index with nothing; an embedding call that fails for any reason but "no embeddings" throws before `ReplaceProjectAsync`, so the index the project had is intact. The per-file builder the watcher uses throws on both (`:108`), so the watcher logs "Failed to re-index" and leaves the file's rows as they were (`src/Scout.Knowledge/ProjectWatchService.cs:174`); it deletes a file's rows only when the file is gone. The host's `index <project>` command logs "Indexing failed for project '<name>'." and exits 1 (`src/Scout.Host.Console/IndexEntryPoint.cs:51`), an embedding request that times out included: the Ollama connector surfaces it as a `TaskCanceledException`, which leaves the command only when the caller's token is cancelled, and the OpenAI connector as an `AggregateException` after its own retries. Before 2026-11-09 every per-file failure became an empty chunk list, which the two replace paths read as "delete": a full index with the embedder down replaced the project with nothing ([[pages/history/knowledge]]).
