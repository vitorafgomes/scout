## Control plane

**Error codes across IPC.** Electron forwards only the message of an error thrown in an `ipcMain.handle` handler; a `code` property set in main never reaches the renderer (checked on Electron 41.3.0: the renderer receives `Error invoking remote method '<channel>': Error: <message>` with no `code`). The Features handlers therefore write the code into the message through `encodeIpcErrorMessage` (`ui/packages/shared/src/errors.ts:238`), and the store reads it back with `readIpcError` (`ui/packages/shared/src/errors.ts:246`). The other handlers still rely on the `code` property, so their code-based renderer branches never fire in the running app; see [[pages/roadmap/followups]]. A control plane that is down crosses as `control-plane/unavailable` with one sentence, "The Scout control plane did not answer." (`serializeError`, `ui/packages/shared/src/errors.ts:182`), whatever it was raised with: the spawn error with the binary's path, the socket path or the gRPC call details never reach a window and stay in main's log, in the launcher's `control-plane: unavailable` line (`ui/packages/main/src/control-plane/launcher.ts:261`) and each handler's failure line (`ui/packages/main/src/ipc/features.ts:221`, `ui/packages/main/src/ipc/operator.ts:367`, `ui/packages/main/src/ipc/github-verdict.ts:240`, `:256`). Every screen that shows a control-plane error therefore shows that sentence (Production, the other operator pages, the approval strip in the chat and in quick ask, a verdict card), Approvals its own below. Production shows it once, in its page banner: a mandate or readiness read that fails because the control plane did not answer goes there, and the mandate, Channel and readiness banners keep their own other failures (`ui/packages/renderer/src/app/production/production.component.ts:3408`); the poll reads a failed mandate or readiness again, and the mandate form shows only once the mandate has been read ([[pages/services/desktop-operator]]). Tests: `ui/packages/shared/test/errors.test.ts` ("a control plane that is down reaches the renderer as one sentence"), `ui/packages/main/test/ipc-features.test.ts` ("the spawn failure goes to the log only"), `ui/packages/renderer/src/app/production/production.component.spec.ts` ("opened while the control plane host is missing") and the second test of `ui/e2e/tests/opens-on-chat.spec.ts`, which runs the app with no control-plane binary.

Main has no HTTP client for the worker and no provider lifecycle channel: nothing lists, starts, stops or restarts a local server or sets its autostart from the desktop, and the LLM Server panel and the Ollama card read Ollama's model list through `scout:llm.listOllamaModels` (`ui/packages/main/src/ipc/llm.ts:248`; [[pages/roadmap/ollama-local-models]], lane G), which is `GET /api/tags` and, for each listed model whose capabilities are not known yet, one `POST /api/show` (2 s, a read; [[pages/architecture/desktop-models-system]]). The one channel left in the providers group is `scout:providers.validateKey`, the cloud key check (`ui/packages/main/src/ipc/provider-keys.ts:70`). Main also asks Ollama to unload Scout's own loaded models when the provider in use moves away from it (`scout:llm.unloadOllamaModels`, `ui/packages/main/src/ipc/llm.ts:322`; see Ollama models on the Ollama card above). The main process also still pulls Ollama models (`ui/packages/main/src/ipc/llm-pull.ts`) and downloads Whisper weights (`ui/packages/main/src/ipc/whisper.ts`) itself, from Node. At every worker start `chooseWhisperModel` (`ui/packages/main/src/worker/whisper-model.ts:106`, called at `ui/packages/main/src/main.ts:442`) picks a verified model from `userData/whisper-models` (see Whisper models below), and `buildEnv` passes it as `SCOUT__TRANSCRIPTION__MODELPATH` (`ui/packages/main/src/worker/build-env.ts:110`), nothing when none is verified, so Discord voice messages and live listening are transcribed locally ([[pages/decisions/0024-voice-messages-transcribed-locally]]). A model downloaded while the worker runs is used from the next worker start.

### Worker restarts

The worker reads its provider, models, connections and Whisper model only as it starts, so each of those changes needs a restart, and since 2026-11-08 every restart goes through one path in main, because the owner decided on 2026-11-07 that a restart never cuts a running answer or a live listen and that the card asking for it says so: `createWorkerRestart` (`ui/packages/main/src/worker/worker-restart.ts:83`), created once in `main.ts`. `restart(reason)` and `modelChanged()` are handled one at a time (`attempt`, `:113`): with no worker running or starting the answer is `none`; while a quick-ask answer runs (a question held for the worker included) or a live listen is open, the restart waits and the answer is `deferred`, and one restart runs once the last of them ends (`ended`, `:175`, fed by quick ask's `onListeningChanged` and `onAnsweringChanged`, `ui/packages/main/src/main.ts:1115`, with `answering` at `:1116`); otherwise it stops and starts the worker and answers `now`, or `failed` with the reason a stop or a start threw; it never throws. A deferred restart that finds the worker stopped is dropped (`moot`, `:101`). While a restart runs, `restarting()` is true, and quick ask holds a question asked between its stop and its start; once the restart settles, whatever its outcome, the path calls `onRestartSettled` (`ui/packages/main/src/worker/worker-restart.ts:155`, wired to quick ask's `restartSettled` at `ui/packages/main/src/main.ts:872`), so a question held through a restart that a Stop cut short is refused instead of waiting, and is never sent on a later Start ([[pages/services/desktop-quick-ask]]).

Three callers use it: the renderer's `scout:worker.restart` (`registerWorkerRestartHandler`, `ui/packages/main/src/ipc/worker.ts:52`, wired at `ui/packages/main/src/main.ts:958`), which trims the renderer's reason to 80 characters for the log and answers with what the path did (`WorkerRestartResponse`, `ui/packages/shared/src/ipc-contract.ts:380`); `restartWorkerIfRunning` (`ui/packages/main/src/ipc/github.ts:19`), which every connection change in main calls (Discord token, GitHub, the Scout bot, YouTube, Kubernetes, pairing, Slack, a write grant) with `announce` (`:23`); and the Whisper model changes below. A restart no card asked for goes to the bell under the fixed id `worker-restart` (`WORKER_RESTART_ENTRY_ID`, `ui/packages/main/src/worker/worker-restart.ts:20`), one entry replaced in place: "Scout restarts once the running answer or the live listen ends." while it waits, then "Scout restarted.", "Scout stopped; it reads the change when it next starts." or "Scout could not restart." with the reason. A deferred restart a card asked for, a provider switch for one, records only its failure there, since the card already said it waits.

A card that asked shows main's answer. AI Sources and Models show their restarting line ("Restarting Scout to use <source>.") while main restarts, then the outcome, which on Models is no line at all once Scout has restarted, and with two requests pending the answer to the latest one, except that a failure answered to the earlier one is shown when the latest answers `none`, since Scout is then down (`restartIfRunning`, `ui/packages/renderer/src/app/sources/sources.component.ts:2112`; `ui/packages/renderer/src/app/models/models.component.ts:1858`); `deferred` reads "Scout waits for the running answer or the live listen to end, then restarts." (`RESTART_DEFERRED_LINE`, `ui/packages/shared/src/ipc-contract.ts:385`) there, under Settings, Scout worker (`ui/packages/renderer/src/app/wizard/settings/worker-settings.component.ts:249`), under the Discord Disconnect in Chat connections (`ui/packages/renderer/src/app/wizard/settings/chat-clients.component.ts:380`), under the Docker card's switch (`ui/packages/renderer/src/app/features/docker-card.component.ts:1173`) and on the Ready step (`ui/packages/renderer/src/app/wizard/ready/ready.component.ts:419`, whose Restart on a crashed worker starts it, since main has no running worker to restart); `failed` keeps each screen's failed-restart line with the reason. Since 2026-11-08 a first Discord token restarts a running worker in main, as a replaced one does (`ui/packages/main/src/ipc/discord.ts:77`), so the Settings modal asks for no restart of its own and moves straight on to the step that adds the bot to a server (`finishDiscord`, `ui/packages/renderer/src/app/wizard/settings/chat-connection-dialog.component.ts:502`); a deferred or failed restart goes to the bell, and Launch starts no second worker. Tests: the main boundary, `scout:worker.restart` over the real path, a real supervisor with fake worker processes and quick ask's own gates, table-driven over an answer running, a live listen open, both, neither, the worker stopped and a start that fails, the bell over who asked and how the deferred restart ended, and a Stop that lands in a restart's start half ("main restart path: a restart waits for the running answer and the live listen", `ui/packages/main/test/worker-restart.test.ts:22`); two requests one after the other answered `now` then `now`, or `failed` then `none` with the worker crashed (`ui/packages/main/test/worker-restart.test.ts:446`); a stop or a start that throws answered `failed` (`ui/packages/main/test/ipc-worker.test.ts:225`); the wiring in `main.ts` (`ui/packages/main/test/whisper-restart.test.ts:398`); the consumer checks on each screen ("a provider switch waits for the running answer and the live listen", `ui/packages/renderer/src/app/sources/sources.component.spec.ts:2941`; `ui/packages/renderer/src/app/models/models.component.spec.ts:1886`; `ui/packages/renderer/src/app/wizard/settings/settings.component.spec.ts:537`; `ui/packages/renderer/src/app/wizard/settings/chat-clients.component.spec.ts:773`; `ui/packages/renderer/src/app/features/docker-card.component.spec.ts:341`; `ui/packages/renderer/src/app/wizard/ready/ready.component.spec.ts:212`).
