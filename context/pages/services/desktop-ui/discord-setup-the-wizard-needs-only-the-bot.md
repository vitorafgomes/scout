## Discord setup

The wizard needs only the bot token ([[pages/decisions/0022-discord-setup-from-the-bot-token]]). Its Discord steps are the routes `provision` (open the Developer Portal), `token` and `oauth` (add the bot to a server). The stepper lists the six entries of `WIZARD_STEPS` with their names from `WIZARD_STEP_LABELS` (Chat app, Create bot, Bot token, Add to server, Launch, Ready; `ui/packages/renderer/src/app/core/wizard.store.ts:257`), and the setup header's "Step N of M · Name" comes from `wizardStepCounter` over the same list and names (`ui/packages/renderer/src/app/core/wizard.store.ts:267`, shown by `stepCounter`, `ui/packages/renderer/src/app/shell/shell.component.ts:164`), so the Chat app step reads Step 1 of 6 · Chat app and Create bot Step 2 of 6 · Create bot, matching the stepper, and no page repeats the count under its title; a table spec checks the header's number, total and name against the stepper on every page (`ui/packages/renderer/src/app/shell/step-indicator.component.spec.ts`). The first step is the prototype's Chat app step (`ui/packages/renderer/src/app/wizard/welcome/welcome.component.ts:41`): "Choose where you chat with Scout" and "Pick the chat app Scout joins. You can add another one later in Settings.", then the three chat apps as one radio group labelled Chat app (`:52`), each a card with its status chip, a helper line and a radio reading "Choose Discord" or "Chosen" (Teams is coming soon and has none), and "No chat app?" with "Use on this computer" under its text while nothing is set up (`:71`). Discord is chosen at first; Continue sets up the chosen one through the same Discord card states as before (provision, resume, Settings, start the worker) or the Slack setup (`continueWithChosen`, `:183`). Every step from Chat app to Add to server ends with `sc-wizard-footer` (`ui/packages/renderer/src/app/wizard/wizard-footer.component.ts:173`): Back on the left, a hint, Continue with its arrow on the right, and, while the step cannot continue, Continue disabled and described by its reason (Bot token "Save a token Discord accepts to continue.", Add to server "Add Scout to a server, or pick one it is already in."). On Create bot, Continue always works ("Continue works whether or not the portal opened here.", `ui/packages/renderer/src/app/wizard/provision/provision.component.ts:75`) and is the main action once the portal opened; "Already have a bot token? Continue straight away." sits beside the portal button, so an owner who already has a bot, or whose browser did not open, is not stuck. Bot token's Back returns to Create bot and keeps the setup (it no longer resets the wizard as Cancel did). All Discord HTTP lives in `ui/packages/main/src/discord/discord-setup.ts`, which takes `fetch` as a parameter so tests can fake it:

- `checkBotToken` reads `GET /applications/@me` (`:66`).

- `enableMessageContent` adds `GATEWAY_MESSAGE_CONTENT_LIMITED` to the existing flags with one PATCH when the application is in under 100 servers. It returns the portal bot page otherwise (`:81`).

- `inviteUrl` builds a `scope=bot` invite with the permissions integer `309237730304` from six named constants, including Create Public Threads for the reply thread per conversation (`:29`, `:55`).

- `listGuilds` reads `GET /users/@me/guilds` (`:113`).

The handlers in `ui/packages/main/src/ipc/discord.ts` work as follows:

- The token arrives once through `scout:discord.checkToken` (`:81`).

- The token is stored only once Message Content Intent is on: at once when the check finds it on, otherwise when `scout:discord.enableIntent` turns it on for that token, held in main's memory until then (`:62`, `:96`), so a setup the owner abandons at the intent step, the Settings modal's Cancel included, stores, deletes and restarts nothing. Storing (`keep`, `:64`) writes `discord.bot-token` and the application id as `discord.client-id`; when the application differs from the stored one, it first deletes `discord.guild-id` and `discord.guild-name`. Every token the worker does not have yet, a first one or one that replaces a different stored token, restarts a running worker through `restartWorkerIfRunning`, which does nothing while no worker runs (`:77`; tests `ui/packages/main/test/ipc-discord.test.ts:112`, `:145`, `:166`).

- The other handlers read the token from the vault, so the renderer never sends it again and never receives it.

The `token` step continues only once Message Content is on. The `oauth` step polls the bot's servers every 3 s, at most 100 times, until a new one appears. It then stores `discord.guild-id` and `discord.guild-name` (`ui/packages/renderer/src/app/wizard/oauth-install/oauth-install.component.ts:323`, stored at `:276`). The invite opens only after the first server list has loaded, so a server the bot was already in is never taken for the new one, and a second click on Add Scout to a server while the invite opens or the step waits does nothing, so one invite opens and one poll chain runs (`openInvite`, `:247`).

Discord counts as set up only once a server is chosen: `hasDiscord` needs the bot token, or the application id of this session, and a server, read from the vault (`discord.guild-id`) by `loadFromVault` or chosen in this session (`ui/packages/renderer/src/app/core/wizard.store.ts:81`, `:184`). So a token saved by an owner who quits before Add to server neither opens the main shell nor starts the worker on the next launch. The localStorage mirror of the application id and the server name (`scout:discord-provisioning`) is read only while the vault holds the server and is wiped once the vault says it holds none, so after a token for another application, whose server main deletes, the next launch shows no old server; a vault that cannot answer leaves Discord not set up for that launch and keeps the mirror (`:207`, `:232`). `goTo` and `setClientId` remember the open step and the application id in `localStorage` (`scout:wizard-step`, `scout:wizard-client-id`; `:140`, `:146`), and `takeLandingUrl` reopens the app on Create bot, Bot token or Add to server only while nothing can run yet, so a first-run owner resumes the setup while a Slack or local-only owner who left the step keeps their usual landing, Chat for local-only as [[pages/decisions/0028-local-quick-ask-assistant]] says (`:39`, `:108`); Reprovision and `reset` forget both. A bot token the vault keeps without a server reads as `discordNeedsServer` (`:96`): releases v0.1.0 and v0.2.0 stored the token at the Bot token step, before the intent and before a server was chosen, so an install that stopped there or replaced the bot with another application's keeps such a token. It does not count as set up for the wizard, Welcome still starts the worker for Slack or this computer, Settings' Discord card reads "Needs a server" with Add to server and Disconnect (`ui/packages/renderer/src/app/wizard/settings/chat-clients.component.ts:91`, `addDiscordToServer`, `:330`), and Welcome's Continue on Discord opens Add to server instead of Create bot (`ui/packages/renderer/src/app/wizard/welcome/welcome.component.ts:213`). Both take the application id from this session or read `discord.client-id`, which the renderer may read back (`prepareAddToServer`, `ui/packages/renderer/src/app/core/wizard.store.ts:120`); a read that fails says why under the cards. Bot token reached again with the application id known and the token in the vault shows "The bot token is saved and Message Content Intent is on" and lets Continue through, since main stores the token only once the intent is on and Discord shows a token only once (`showSavedBot`, `ui/packages/renderer/src/app/wizard/token-paste/token-paste.component.ts:389`); the keyring banner clears once a later check finds the keyring (`:432`). Launch takes a start that resolves as running, since main answers a start only once the worker runs, so a worker that already runs shows running and moves on to Ready once (`running`, `ui/packages/renderer/src/app/wizard/worker-launch/worker-launch.component.ts:270`); a Launch that opens while the worker is known to run starts nothing (`:254`), and the Launch the shell replaces at the handover clears its pending move to Ready, so the worker starts once and Ready opens once; its AI Source row names the provider from `LlmConfigStore` by its card's name, Ollama while none is chosen, as `buildEnv` falls back, and "No AI Source" when the owner chose none (`aiSource`, `:209`). The shell keeps the wizard frame and stepper through Launch and hands over to the main shell once the worker reports running, no longer as soon as a server is chosen (`showPostConnectShell`, `ui/packages/renderer/src/app/shell/shell.component.ts:170`). Tests: `ui/packages/renderer/src/app/core/wizard.store.spec.ts` ("a bot token saved before any server was chosen does not count as Discord set up when the app reopens", the mirror rows, the resume rows), `ui/packages/renderer/src/app/wizard/welcome/welcome.component.spec.ts` ("reopening the app after quitting on Add to server resumes on Add to server", over the real routes and guards), `ui/packages/renderer/src/app/wizard/worker-launch/worker-launch.component.spec.ts` ("Launch when the worker already runs, and what it says it starts"), `ui/packages/renderer/src/app/wizard/oauth-install/oauth-install.component.spec.ts` (the two double-click rows), `ui/packages/renderer/src/app/wizard/token-paste/token-paste.component.spec.ts` and `ui/packages/renderer/src/app/shell/shell.component.spec.ts` ("a server just chosen, on Launch with the worker ...", "starts the worker once and opens Ready once, though Launch mounts again in the main shell"), and `ui/packages/renderer/src/app/wizard/settings/chat-clients.component.spec.ts` ("Settings chat connections: a Discord bot token kept without a server").

The `ready` step's Start over (the button the code still names `reprovision`) asks first through the shared confirmation, Cancel focused, with the approved prototype's title "Start over with another bot?", Start over (`ui/packages/renderer/src/app/wizard/ready/ready.component.ts:458`); on yes it forgets Discord only, as Disconnect Discord in Settings does: it clears the provisioning and, while Slack or the local-only choice still counts, restarts the worker through `scout:worker.restart` (a deferred or failed answer shows as a notice), else stops a running worker, then goes back to the first step (`reprovision`, `:456`; tests "Reprovision forgets Discord only and keeps Scout running for the chat that still counts", `ui/packages/renderer/src/app/wizard/ready/ready.component.spec.ts`). The wizard's pages paint with the theme tokens and follow the light and dark theme, before setup inside the wizard frame and after it inside the main window's ([[pages/architecture/desktop-ui-design-system]]).
