## YouTube connection

The YouTube side panel holds `sc-youtube-connect` (`ui/packages/renderer/src/app/features/youtube-connect.component.ts:260`) and gets a `connection` state like the GitHub card (`ui/packages/renderer/src/app/features/features.component.ts:245`), so it has no toggle and not the catalog's credential dialog (`ui/packages/renderer/src/app/features/features.component.spec.ts:203`); Add an API key opens its own Connect YouTube dialog (below). The panel keeps 10 px between its parts. It calls six channels, `scout:youtube.signIn`, `status`, `cancelSignIn`, `signOut`, `saveApiKey` and `clearApiKey` (`ui/packages/shared/src/ipc-contract.ts:119`), handled in `ui/packages/main/src/ipc/youtube.ts:69`, and polls the status 3 s after each answer while a sign-in waits for the browser, never with two requests in flight and never after the card is gone.

`GoogleAuth` (`ui/packages/main/src/oauth/google-auth.ts:109`) owns both credentials, one at a time: a sign-in removes a saved key and a saved key signs out (revoking first), as on the GitHub card. [[pages/decisions/0030-youtube-plugin-read-only-with-browser-sign-in]].

- **Sign in with Google** (`ui/packages/main/src/oauth/google-auth.ts:159`): reads the OAuth client, finds a loopback port from 8765 (ten fallbacks), starts the listener on `127.0.0.1` with `/auth/callback` and only then opens the system browser at `accounts.google.com/o/oauth2/v2/auth` with PKCE S256, a `state`, `access_type=offline`, `prompt=consent` and the scopes `youtube.readonly` and `yt-analytics.readonly` (`ui/packages/main/src/oauth/google-auth.ts:26`). The session keeps the scopes Google granted, split from the token response's space-separated `scope` (`:788`), and a refresh keeps them unless Google's answer names its own (`:555`); a session saved before scopes were kept has none. The call returns at once with `pending: true`; the answer completes in the background: main checks the state, exchanges the code at `oauth2.googleapis.com/token` with the client id and secret, reads the channel with `GET youtube/v3/channels?part=snippet&mine=true` (`:422`; an account without a channel is still connected, titled "No channel on this account"), and only then stores the session under `youtube.session` and writes the token file. A failure on the way stores nothing and lands in the status `error`.

- **OAuth client** (`ui/packages/main/src/oauth/google-auth.ts:582`): in this order: `SCOUT_GOOGLE_CLIENT_ID` and `SCOUT_GOOGLE_CLIENT_SECRET` when both are set; else `<userData>/google-oauth-client.json`, either the file Google Cloud Console downloads for a Desktop app client as it is (`{"installed": {"client_id": ..., "client_secret": ..., ...}}`) or the flat `{"client_id": ..., "client_secret": ...}`; else the client file packaged with the app, `packages/main/resources/google-client.json` under `app.getAppPath()` (`ui/packages/main/src/main.ts:688`; read once; written at package time from `SCOUT_GOOGLE_CLIENT_SECRET` by `ui/build/scripts/write-google-client.mjs`, gitignored, and in a release from the repository secret of the same name, see [[pages/runbooks/release]]); else the Desktop client built into Scout, `DEFAULT_GOOGLE_CLIENT_ID` and `DEFAULT_GOOGLE_CLIENT_SECRET` (`ui/packages/main/src/oauth/google-auth.ts:16`, passed from `ui/packages/main/src/main.ts:695`), when both are non-empty; the id ships in source, the secret stays empty and never enters the repository, so this last step only applies to a build that fills both. The status says which one is in use (`source`: `env`, `file`, `bundled`, `embedded` or null). Read at sign-in, at refresh and for the status; never logged, never stored in the vault, never sent to the renderer. With none of the three the status says `configured: false` and the card reads "Sign in needs a Google OAuth client: enable the YouTube Data API, create an OAuth client of type Desktop app, then download its JSON as it is to <path> (or write {"client_id": ..., "client_secret": ...} there). Or use an API key below.", with Sign in with Google disabled and two links opened through `scout:app.openExternal`: "Enable the YouTube Data API" (`https://console.cloud.google.com/apis/library/youtube.googleapis.com`) and "Open Google Cloud Console credentials" (`https://console.cloud.google.com/apis/credentials`, where both the Desktop OAuth client and an API key are created). A Web application client file (`{"web": ...}`) is not accepted: the card also says "The Google OAuth client in the file is a Web application; Sign in with Google needs an OAuth client of type Desktop app."

- **Token file**: `<userData>/youtube-token.json` as `{"access_token": ..., "expires_at": <unix ms>}`, mode `0600`, written to a `.tmp` file then renamed (`ui/packages/main/src/oauth/google-auth.ts:659`); a failed write keeps the session and is retried on the next refresh tick (`ui/packages/main/test/oauth-google.test.ts:631`). The worker gets its path as `SCOUT__PLUGINS__YOUTUBE__TOKENFILE`, or the key as `SCOUT__PLUGINS__YOUTUBE__APIKEY`, and either one turns on `SCOUT__ACCESS__REQUIREALLOWLIST` (`ui/packages/main/src/worker/build-env.ts:82`, `:101`, wired at `ui/packages/main/src/main.ts:829`).

- **Refresh** (`ui/packages/main/src/oauth/google-auth.ts:488`): every minute and when the system wakes from sleep, through one serial queue, once less than 5 minutes remain, with the client secret; Google's answer usually has no new refresh token, so the first one is kept. `invalid_grant` ends the session: the token file goes first, the vault entry second (`:639`), and the card says "Google no longer accepts the saved sign-in. Sign in with Google again." A 5xx or a network failure keeps the session for the next check.

- **Disconnect** (`ui/packages/main/src/oauth/google-auth.ts:212`): a best-effort `POST oauth2.googleapis.com/revoke` of the refresh token, then the token file, then the vault entry; if the file cannot be removed the owner stays connected and sees "Could not remove the YouTube token file, so Scout is still connected. Try Disconnect again." On a pasted key, Disconnect calls `clearApiKey`, which removes only the key. Connect and disconnect call `restartWorkerIfRunning` (`ui/packages/main/src/ipc/github.ts:19`). Once the sign-out has removed the session, or the key that was the only credential is gone, main also calls the control plane's `DeleteCredentials('youtube')` so it deletes the YouTube data it keeps (`ui/packages/main/src/ipc/youtube.ts:32`, `:104`, `:115`); a sign-out that could not remove the token file deletes nothing, and a control plane that does not answer is logged with the error code only and never fails the Disconnect.

- **Allow writes** (`ui/packages/main/src/oauth/google-auth.ts:164`): Scout signs in for reads only and asks for more only when the owner allows YouTube's writes, because Google offers installed apps no incremental authorization. After the write confirmation, `scout:features.writeGrant` with `granted: true` runs main's check for the feature before `SetWriteGrant` (`ui/packages/main/src/ipc/features.ts:185`, wired by `youTubeWriteGrantHooks`, `ui/packages/main/src/ipc/youtube.ts:39`, `ui/packages/main/src/main.ts:983`), and so does `scout:features.enable` with `confirmWrites: true` (`ui/packages/main/src/ipc/features.ts:148`); a grant the control plane then refuses drops the write scopes again, as Revoke writes does. When the stored session lacks `youtube.upload` or `youtube.force-ssl`, as with a read-only sign-in, a key or no connection, main runs the same PKCE loopback sign-in with `youtube.readonly`, `yt-analytics.readonly`, `youtube.upload` and `youtube.force-ssl` (`:30`) and waits for it, the card's Allow writes button busy meanwhile; the grant reaches the control plane only once the new session holds both write scopes. A cancelled or refused sign-in grants nothing; when the owner unticks a permission on Google's page, nothing is granted; if Google granted one write scope without the other, that token is revoked at Google and the session cleared, and a sign-in with the read scopes only opens, so the worker's token file never carries a write scope while writes are off (`ui/packages/main/src/oauth/google-auth.ts:177`); a grant with neither write scope keeps the read-only sign-in as it is; the card says "Google did not grant youtube.force-ssl, so writes stay off. Click Allow writes again and allow every permission on Google's page." naming each scope missing.

- **Revoke writes** (`ui/packages/main/src/oauth/google-auth.ts:185`): `SetWriteGrant(false)` first, then, when the session holds a write scope, the token is revoked at Google, the token file and the session are removed, the worker restarts, and a new sign-in with the read scopes only opens in the browser (`ui/packages/main/src/ipc/features.ts:162`); if the owner cancels it, denies it on Google's page, lets it time out, or the browser cannot be opened, YouTube stays signed out with Sign in with Google, and because that is a revocation made in the app, main then calls `DeleteCredentials('youtube')` the same best-effort way Disconnect does (`ui/packages/main/src/ipc/youtube.ts:43`, `:47`); a read-only sign-in that succeeds keeps the data. A failure of that step is logged with its code and the revoked grant is still returned.
