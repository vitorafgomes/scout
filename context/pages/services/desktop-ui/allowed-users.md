## Allowed users

Settings has a "Who can use Scout" section (`ui/packages/renderer/src/app/wizard/settings/settings.component.ts:245`): the lede "People listed here can ask Scout from Discord or Slack. Chat on this computer never needs the list.", three bullets (`:251`), "Discord: turn on Developer Mode, right-click a person, Copy User ID.", "Slack: open their profile, More, Copy member ID." and "Teams: the user's Bot Framework user ID, which starts with 29:.", a field labelled "User ID" with the hint "A Discord user ID or a Slack member ID." and Add (`:264`), and the list, "Allowed people", with Remove per id. Remove first asks "Remove <id>?" ("This user can no longer ask Scout anything. You can add them again later.") with Cancel focused, through the shared confirmation (`removeUser`, `ui/packages/renderer/src/app/wizard/settings/settings.component.ts:1767`); Cancel saves nothing. Add and a confirmed Remove send the whole list through `scout:access.set`; a refused list shows main's reason and keeps the typed id. Main (`ui/packages/main/src/ipc/access.ts:73`) trims each id, accepts 1 to 64 characters from `[A-Za-z0-9._:@-]`, de-duplicates, caps the list at 50, stores it under `access.allowed-users` (deleted when empty) and restarts a running worker through `restartWorkerIfRunning` only when the list changed. `buildEnv` passes each id as `SCOUT__ACCESS__ALLOWEDUSERIDS__<n>` and sets `SCOUT__ACCESS__REQUIREALLOWLIST=true` when GitHub is connected, a Kubernetes selection exists or `llm.provider` is `ChatGptPlan` (`ui/packages/main/src/worker/build-env.ts:96`, `:99`), so the worker refuses everyone until ids are added ([[pages/decisions/0021-allowed-users]], [[pages/services/conversation]]). While the list is empty, the connected GitHub, Kubernetes and YouTube cards (`ui/packages/renderer/src/app/features/features.component.ts:252`) and the ChatGPT plan card while it is the provider in use (`ui/packages/renderer/src/app/sources/sources.component.ts:515`) say "Nobody can use this connection from chat until you add allowed users in Settings."

"Pair from chat" in the same section (`ui/packages/renderer/src/app/wizard/settings/settings.component.ts:286`) calls `scout:access.startPairing`. Main draws a 6-digit code with `crypto.randomInt`, valid for 10 minutes, keeps it in memory only and restarts a running worker (`ui/packages/main/src/ipc/access.ts:114`). The renderer shows "Send `pair 482913` to Scout in a direct message on Discord." beside the button (`ui/packages/renderer/src/app/wizard/settings/settings.component.ts:294`), with the real code, the artboard's wording; the worker accepts the code with or without `pair` and burns it in either form ([[pages/decisions/0021-allowed-users]]); a refusal shows main's reason. While the code is pending, `buildEnv` adds `SCOUT__ACCESS__PAIRINGCODE` and `SCOUT__ACCESS__PAIRINGEXPIRESAT` (`ui/packages/main/src/worker/build-env.ts:107`). When the worker prints `SCOUT_PAIRED=<userId>`, the supervisor's `onPaired` (`ui/packages/main/src/main.ts:850`) calls `paired` (`ui/packages/main/src/ipc/access.ts:124`). That handler ignores the line unless an unexpired code is pending, clears the code, and adds the id through the same validation and storage as `scout:access.set`, which restarts the worker. On `SCOUT_PAIRING_BURNED` (the worker burned the code after it was sent outside a direct message or after five wrong codes) main drops the pending code (`ui/packages/main/src/ipc/access.ts:157`), and Settings, which listens to the worker's stdout events, replaces the code with "Pairing expired. Start again." (`ui/packages/renderer/src/app/wizard/settings/settings.component.ts:1420`); it does the same when the code's 10 minutes pass on screen, from the `expiresAt` main answered (`:1784`, test `ui/packages/renderer/src/app/wizard/settings/settings.component.spec.ts:1997`). On `SCOUT_PAIRED=<userId>` Settings takes the code off the screen and reads the list again (`ui/packages/renderer/src/app/wizard/settings/settings.component.ts:1421`). Because main stores the paired id after that line reaches the renderer, Add and Remove read the stored list again before they send it, so a paired id, or a list that could not be read when Settings opened, is never overwritten (`saveAllowedUsers`, `:1814`; tests `ui/packages/renderer/src/app/wizard/settings/settings.component.spec.ts:1967`, `:1591`, `:1643`). No main log line carries the code ([[pages/decisions/0021-allowed-users]]).
