## How the rules are kept

- [[pages/invariants/secrets-never-in-source]] - `ui/packages/main/src/vault/safe-storage-vault.ts:165` encrypts with the OS keychain; the renderer never receives a secret back, only `has`, `isAvailable` and the two non-secret keys of `scout:vault.getPublic`. A cloud API key leaves the machine only in the header of the key check and of the model list (`ui/packages/main/src/ipc/provider-keys.ts:89`, `:254`) and in the worker's environment.
- [[pages/invariants/secrets-never-in-source]] - GitHub tokens and the device code stay in main: the status and sign-in payloads carry the user code, the login and flags only, and no log line carries a token (`ui/packages/main/test/oauth-github.test.ts:523`, `ui/packages/main/test/ipc-github.test.ts:72`). The token file is the one copy on disk, mode `0600`.
- [[pages/invariants/secrets-never-in-source]] - the kubeconfig stays where it is: main stores only its path and the allowed context names, and no detect, use, status or disconnect payload and no log line carries a token, key, certificate, password or exec env value (`ui/packages/main/test/ipc-kubernetes.test.ts:223`, `ui/packages/main/test/kubeconfig.test.ts:114`).
- [[pages/invariants/secrets-never-in-source]] - the Slack tokens travel renderer to main once, in `scout:slack.save`; the status answer carries the team and bot user names only, and no log line, answer or error message carries a token or the Socket Mode URL `apps.connections.open` returns (`ui/packages/main/test/ipc-slack.test.ts:133`, `:149`, `:189`).
- [[pages/invariants/no-executive-writes]] - main's calls to Slack are `auth.test` and `apps.connections.open`, a read and a handshake whose URL is dropped unopened ([[pages/decisions/0023-slack-setup-from-a-manifest]]).
- [[pages/invariants/no-executive-writes]] - main sends only GETs to `api.github.com` (`/user`, `/user/installations`, `/user/installations/{id}/repositories`) and POSTs only to GitHub's two sign-in endpoints (`ui/packages/main/test/oauth-github.test.ts:497`).
- [[pages/invariants/no-executive-writes]] - main POSTs only to Google's token and revoke endpoints and sends only GETs under `www.googleapis.com/youtube/v3/`; `accounts.google.com` is only opened in the browser (`ui/packages/main/test/oauth-google.test.ts:880`).
- [[pages/invariants/secrets-never-in-source]] - the Google OAuth client secret, the authorization code, the code verifier, the tokens and a pasted key stay in main: no log line, status or IPC answer carries one, and a rejected key's message never quotes it (`ui/packages/main/test/oauth-google.test.ts:846`, `ui/packages/main/test/oauth-google-key.test.ts:43`, `ui/packages/main/test/ipc-youtube.test.ts:220`). The token file is the one copy on disk, mode `0600`.
- [[pages/invariants/secrets-never-in-source]] - feature credentials travel renderer to main to gRPC and are never logged: the Features handlers log the feature id and the error only, and the launcher never logs the session token or the worker token, nor sets either on its own environment (`ui/packages/main/test/ipc-features.test.ts`, `ui/packages/main/test/control-plane-launcher.test.ts`).
- [[pages/invariants/no-executive-writes]] - the login item and `~/.config/autostart/scout.desktop` are Scout's own startup entry, never reachable from the worker or chat ([[pages/decisions/0027-desktop-presence]]). Only the owner's toggle in Settings creates or deletes it; turning the toggle off deletes that file and nothing else in the folder. At start, an entry that already exists is rewritten when it names another executable, always with Scout's own path from `ownExecutable` (`ui/packages/main/src/shell/own-executable.ts:16`), so an `APPIMAGE` inherited from another program never lands in it (`ui/packages/main/test/shell-login-item.test.ts`).
- [[pages/invariants/no-executive-writes]] - a quick-ask reply is shown only in the owner's quick-ask window and Chat screen, which share one conversation held in main; main's stdin line and the microphone capture are reads the owner starts ([[pages/decisions/0028-local-quick-ask-assistant]]).
- [[pages/invariants/secrets-never-in-source]] - quick-ask recordings stay in renderer memory until sent and are never written to disk; `SCOUT_LOCAL` lines, which carry the question and the reply, never enter the log ring or the log viewer (`ui/packages/main/test/worker-log-stream.test.ts`).
- [[pages/invariants/secrets-never-in-source]] - live listening keeps no audio: each chunk goes from the renderer to the worker's stdin and is dropped, no main log line carries a chunk or a transcript, and the transcripts reach the windows on `scout:local.transcript` only, never the conversation's turns (`ui/packages/main/test/quick-ask.test.ts`, the listening block). The microphone runs only while the Listen indicator shows and the system audio only while "Listening to system audio" shows; both stop on their Stop, Stop all, Escape and Close, and while either runs the window stays up on blur. The transcript of both lanes stays in renderer memory, is never written by the desktop, and reaches the worker only inside a question the owner sends or a meeting the owner keeps, which the worker stores ([[pages/services/desktop-quick-ask]], Meeting mode).
- [[pages/decisions/0032-per-feature-write-permissions]] - a screenshot is a declared read of the owner's screen: one frame, on the owner's click, after the system dialog where the system has one, with "Choose what Scout may see..." showing while the picker is open and every track stopped after the frame. `allowScreenCaptureOnlyForApp` answers display-media requests on the default session only for the app's own page and only for video, beside the microphone rule (`ui/packages/main/src/quick-ask/quick-ask.ts:248`, `ui/packages/main/src/main.ts:1120`). The image travels renderer to main to the worker's stdin once, on the ask line; the turn keeps only `screenshot: true`, no main log line carries it, and nothing is written to disk; the CSP is unchanged (`ui/packages/main/test/quick-ask.test.ts`, the screen capture block; [[pages/services/desktop-quick-ask]]).
- [[pages/invariants/local-first-default]] - the only network call for transcription is the model download from `huggingface.co/ggerganov/whisper.cpp`, and a download is kept only at the pinned size and SHA-256; its only writes are the model, its `.partial` and its `.sha256` sidecar under `userData/whisper-models` (`ui/packages/main/test/ipc-whisper.test.ts`, `ui/packages/main/test/worker-whisper-model.test.ts`).
- [[pages/invariants/no-executive-writes]] - the update check and the list of versions are each one unauthenticated GET of public release metadata that carries only the version in the User-Agent and no credential, and their only writes are Scout's own `update.*` vault keys. The one write to Scout's own installation is an install on the user's click only: Update and restart through `scout:update.install`, or a listed version through `scout:update.installVersion`, an older one after a confirmation, both out of reach of the worker and the model, with the updater's automatic download and install off and no token set ([[pages/decisions/0031-desktop-self-update]], `ui/packages/main/test/update-notice.test.ts`).
- [[pages/decisions/0032-per-feature-write-permissions]] - the desktop is the only approval surface: a write grant and an action decision reach the control plane only through the Features and Review screens over the token-authenticated socket, and the channels that carry them change Scout's own feature state and approval queue, nothing outside Scout (`ui/packages/main/test/ipc-features.test.ts`, `ui/packages/renderer/src/app/review/review.component.spec.ts`). The worker holds only its own token, which the host lets reach the WorkerGate service and nothing else, so it can ask for a write but never grant or approve one (`ui/packages/main/test/control-plane-integration.test.ts:301`).
- [[pages/decisions/0033-channel-operator-architecture]] - the operator window and its `scout:operator.*` channels change only Scout's own operator state and media folder, see [[pages/services/desktop-operator]].
- [[pages/invariants/no-executive-writes]] - a meeting is written only to the worker's meetings database in Scout's own data folder, and only when the owner ticks Keep this meeting and clicks Done; an export is written only to the file the owner picks in the save dialog; a delete runs only on the owner's confirm. The renderer never sends or receives a path, and nothing of a meeting leaves the machine (`ui/packages/main/test/quick-ask.test.ts`, the meetings block; [[pages/decisions/0037-meetings-kept-locally-in-sqlite]]).
- [[pages/invariants/pluggable-boundaries]] - the UI reaches the console worker only through environment variables, stdout markers and quick-ask JSON lines on stdin, and the control plane only through gRPC; no .NET type crosses, and `@grpc/grpc-js` stays under `ui/packages/main/src/control-plane/` (ADR 0011: the renderer never sees it).
