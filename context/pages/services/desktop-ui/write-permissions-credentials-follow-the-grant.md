## Write permissions

- **Credentials follow the grant.** Any change or loss of the YouTube credential revokes the `youtube` write grant on the control plane before the worker restarts: sign-out and removing the only API key (`ui/packages/main/src/ipc/youtube.ts:102`, `:115`), a completed sign-in, a saved key and Google refusing the saved sign-in on refresh (`ui/packages/main/src/oauth/google-auth.ts:368`, `:246`, `:535`). GitHub follows the same rule ([[pages/services/desktop-github]]): Disconnect, a saved token, a completed browser sign-in and GitHub refusing the saved sign-in on refresh revoke the `github` grant before the connection change restarts the worker (`ui/packages/main/src/oauth/github-auth.ts:261`, `:190`, `:314`, `:375`, wired at `ui/packages/main/src/main.ts:564`). The revoke never blocks the credential change (`revokeFeatureWriteGrant`, `ui/packages/main/src/ipc/write-grant-revoke.ts:59`, which `revokeYouTubeWriteGrant` calls, `ui/packages/main/src/ipc/youtube.ts:19`): a control plane that does not answer is logged with the error code only (`ui/packages/main/test/ipc-github.test.ts:219`), and the revoke is kept as pending in main's vault under the main-only key `features.pending-revokes` (`vaultPendingRevokes`, `ui/packages/main/src/ipc/write-grant-revoke.ts:18`, `:70`; test `ui/packages/main/test/ipc-github.test.ts:339`), so a grant never carries over to the next account. Main sends the pending revokes again as soon as the control plane connects (`replayPendingRevokes`, `ui/packages/main/src/ipc/write-grant-revoke.ts:85`, wired at `ui/packages/main/src/main.ts:663`) and before every worker start reads the grants, and a feature whose revoke is still pending never counts as granted for the worker (`readGrantedWriteFeatures`, `ui/packages/main/src/worker/build-env.ts:201`, `:222`); a replay the control plane refuses stays pending (tests `ui/packages/main/test/ipc-github.test.ts:272`, `:312`). The two hooks this rule depends on are required, so a build without them does not compile: `GitHubAuthDeps.revokeWriteGrant` and `FeaturesHooks.windowOf` with `FeaturesHooks.isAppPage`; a source-text test pins their wiring in `main.ts` (`ui/packages/main/test/ipc-github.test.ts:359`). Once the control plane confirms a revoke, main pushes `scout:features.changed` to every window (`ui/packages/main/src/ipc/write-grant-revoke.ts:78`, `ui/packages/main/src/main.ts:659`, `ui/packages/shared/src/ipc-contract.ts:62`), and `FeaturesStore` reloads the features on it (`ui/packages/renderer/src/app/core/features.store.ts:48`), so the YouTube card stops showing writes allowed without the owner reopening the screen (`ui/packages/main/test/ipc-youtube.test.ts:283`, `ui/packages/renderer/src/app/core/features.store.spec.ts:103`); a revoke that failed pushes nothing. Deleting a feature's credentials restarts the worker so the revoked grant leaves it (`ui/packages/main/src/ipc/features.ts:141`). Every call that clears a grant on the control plane (revoke, disable, deleting the credentials, an enable whose activation fails) also rejects that feature's actions still waiting in Approvals with the reason "writes were revoked" ([[pages/services/host-control-plane]]). The owner allows writes again after reconnecting.

- **The worker.** At every worker start `readGrantedWriteFeatures` (`ui/packages/main/src/worker/build-env.ts:182`) lists the features and `buildEnv` passes the granted ids as `SCOUT__FEATURES__GRANTEDWRITES`, comma-separated, and always sets it, empty when nothing is granted, so a value inherited from the desktop's environment cannot grant writes (`:111`); the worker's guard reads it. A worker started while the control plane is still connecting waits for its client up to 10 s, the same bound as the socket wait, and then gets the grants (`ui/packages/main/src/worker/build-env.ts:197`, `ui/packages/main/src/main.ts:836`, `ui/packages/main/test/worker-build-env.test.ts:984`); one that does not connect in that time, is not launched, or does not answer starts with no grants and one `warn` line (`ui/packages/main/test/worker-build-env.test.ts:1008`). A grant, a revocation, and enabling or disabling a write-capable feature push `scout:features.changed` to every window and restart a running worker so the guard sees the change (`ui/packages/main/src/main.ts:976`). An enable with `confirmWrites: true` that fails restarts it too, because the host clears the grant when the activation fails (`ui/packages/main/src/ipc/features.ts:132`, `ui/packages/main/test/ipc-features.test.ts:271`). The host records a grant on `Enable` only after the feature's activation succeeds, so the phase 1 "not available yet" answer leaves no grant behind. The same `buildEnv` always sets `SCOUT__WORKERGATE__SOCKETPATH` and `SCOUT__WORKERGATE__TOKEN` from `workerGate()` (`ui/packages/main/src/worker/build-env.ts:112`, `ui/packages/main/src/main.ts:841`), empty strings while the control plane is not launched, so values inherited from the desktop's environment cannot point the worker elsewhere; the worker asks the control plane through that gate before a declared write ([[pages/services/host-console]]). Overwriting the exact upper-case names is not enough on its own, because the worker's configuration reads a key in any casing, with ':' or '__', and with a `DOTNET_` prefix: the supervisor builds the child environment from `workerInheritableEnv(process.env)` (`ui/packages/main/src/worker/supervisor.ts:290`, `:491`), which drops every inherited key that normalizes (lower case, ':' to '__', a leading `dotnet_` or `aspnetcore_` removed) to `scout__workergate__*`, `scout__features__grantedwrites`, `scout_controlplane_token` or `scout_controlplane_worker_token`, and then applies `buildEnv`'s values (`ui/packages/main/test/worker-supervisor.test.ts:573`). The worker's environment never carries `SCOUT_CONTROLPLANE_TOKEN` or `SCOUT_CONTROLPLANE_WORKER_TOKEN`, and no value in it holds the desktop token (`ui/packages/main/test/worker-build-env.test.ts:1219`); the empty values are pinned at `:1295`. Main connects the control plane before it creates the worker supervisor, so no worker start, the tray's Start Scout included, can run before the connection exists: each one waits for the client within the bounded wait above and gets the grants and the gate (`ui/packages/main/src/main.ts:635`, `:812`, `ui/packages/main/test/tray.test.ts:273`, `:319`); only an unsupported or failed launch leaves them empty.
