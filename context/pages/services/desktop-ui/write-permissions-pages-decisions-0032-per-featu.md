## Write permissions

[[pages/decisions/0032-per-feature-write-permissions]] on the desktop side. The client maps each scope row's `access` (0 read, 1 write, 2 irreversible) and the feature's `write_class` (0 none, 1 descriptive, 2 executive), `granted` and `granted_at` onto `FeatureScopeRowDto.access` and `FeatureDto.writeClass`, `granted`, `grantedAt` (`ui/packages/shared/src/ipc-contract.ts:636`, `:656`; `ui/packages/main/src/control-plane/client.ts:499`); an unknown value maps to the stricter `irreversible` or `executive`.

- **The panel's permissions** (first drawn 2026-11-06 on the owner's prototype, "hide the permissions so it does not get big; to see them you would just click"; moved off the card into the side panel on 2026-11-08). `sc-feature-details` (`ui/packages/renderer/src/app/features/feature-details.component.ts:414`) sits in each feature's panel under its connection section. Every feature lists its declared read rows in a Reads section (`data-test="reads-<id>"`, `ui/packages/renderer/src/app/features/feature-details.component.ts:43`), as `Features.dc.html` draws it: a line above it, a 14 px heading with the count (`data-test="reads-summary-<id>"`, `:52`), and each read a row with its label over the row's one sentence, the `summary` the catalog carries since 2026-11-12, never its actions joined (`data-test="label-<scope>"` and `what-<scope>`, `:59`, `:62`), so the This computer panel shows Screen, Microphone and System audio with no toggle for them. The label is the scope as the catalog writes it, except the YouTube API method names, which the renderer shows in words from `SCOPE_LABELS` (`:9`, `scopeLabel` `:28`): `channels.list` reads Channel overview, `videos.insert` Upload a video, and so on; the scope string itself stays the key the write gate looks up. A feature whose `writeClass` is not `none` shows a Permissions section the same way (`data-test="permissions-<id>"`, `:73`, its heading `permissions-summary-<id>` with the count): one row per scope row with its label (`:86`), a Write or Cannot be undone chip (`:93`) and the row's one sentence, its `summary` (`:97`), then the grant box on the page colour with a line border (`:101`): the chip "Write permission: not granted" on the second surface or "Write permission: granted on <yyyy-MM-dd>" on the ok pair (`data-test="grant-<id>"`, `:102`), "Allow writes" as a filled button, disabled until the feature is connected (a Google sign-in or a key) and described by the line under it, "You review the list before anything is allowed." or "Connect <feature> first to allow writes.", or, once granted, "Revoke writes" as an outlined one; a grant error shows under the box. Neither section folds (until 2026-11-10 both were native `details` closed by default; the artboard draws them open). The Enabled toggle of a control-plane feature is a switch at the foot of its panel (`:162`); Clear credentials asks first through the confirmation dialog, Cancel focused, "Clear the <feature> credentials?" (`ui/packages/renderer/src/app/features/features.component.ts:767`). Today the Permissions block is the YouTube and the GitHub panels; the catalog declares both as `executive`. Tests: `ui/packages/renderer/src/app/features/feature-details.component.spec.ts:88` ("Reads and Permissions are open sections, as Features.dc.html draws them", "since when writes are allowed is in the grant chip, not the heading", "a read is a row with its label and the row's one short sentence, never its actions joined", "a permission row shows its access pill and the row's one short sentence, never its actions joined", and the "Feature details as in the prototype" rows: reads as rows, permissions in words); the chip per feature and connection moved with the chip to `ui/packages/renderer/src/app/features/feature-card.component.spec.ts:116`. The four panels against the artboard, with fixtures that copy the control plane's catalog word for word (`ui/packages/renderer/src/app/features/feature-catalog.testing.ts:20`): the card's chips, the description, "Reads n" with each row's label and sentence, "Permissions n" with each row's label, chip and sentence, and the YouTube Allow writes list in full (`ui/packages/renderer/src/app/features/features.prototype.spec.ts:662`, `:822`); a write with two actions shows each on its own line, in order, for GitHub's Pull request verdicts and New issues, and a write with one action one line (`:934`, `:953`; `ui/packages/renderer/src/app/features/write-confirmation-dialog.component.spec.ts:86`, `:95`); over the real control plane host, the GitHub, YouTube and Desktop chips and the first and last row of each section (`ui/e2e/tests/features-loaded.spec.ts:96`).

- **Write-verb allow-list.** Two channels carry "write" in their names and are allowed by the contract test's write-verb scan (`ui/packages/shared/test/ipc-contract.test.ts`): `scout:writes.list` reads the log of writes Scout already made and changes nothing; `scout:features.writeGrant` records the owner's grant or revocation in Scout's own feature state and calls no external system. `scout:local.deleteMeetings` carries "delete" and is on the same allow-list: it deletes meetings the owner kept from Scout's own meetings database, on the owner's confirmed click on the Meetings screen, and calls no external system.

- **The grant.** "Allow writes" opens `sc-write-confirmation-dialog` (`ui/packages/renderer/src/app/features/write-confirmation-dialog.component.ts:265`), which lists the write rows only, each named as the card names it, with the panel's `scopeLabel` (`ui/packages/renderer/src/app/features/feature-details.component.ts:28`: Upload a video, not `videos.insert`) and a Write or Cannot be undone chip, takes the focus on Cancel when it opens (`ngAfterViewInit`, `ui/packages/renderer/src/app/features/write-confirmation-dialog.component.ts:289`), holds it inside (`cdkTrapFocus`, `:42`), closes on Esc as Cancel does, never as Allow (`onEscape`, `:302`), and says "Scout will be allowed to perform these writes on your behalf. Actions marked irreversible will still wait for your approval, one by one, in Approvals." with Cancel and "Allow these writes": the artboard's 520 px card 64 px from the top, 14 px corners, a 17 px title, the writes as rows with what each does, and the sentence as the dialog's description (`aria-describedby`). Each row lists every action the catalog declares for it in full, each action on its own line in a list inside the row, in the muted colour of the old sentence, 4 px apart and with no bullet (`:211`), so a row with one action looks as it did and the actions of a longer row, whole sentences with their own commas, are never run together; never the panel's one sentence, so the owner reads every write before allowing it (since 2026-11-12, when the panel took the short sentence; the artboard's own dialog draws the short sentence, a difference kept on purpose and listed for the owner on [[pages/roadmap/prototype-migration]]). It no longer shares the credential dialog's `DIALOG_STYLES`. Its footer stays in place while the list scrolls, as drawn, so "Allow these writes" turns on only once every write row has been in view: at once when the list fits, otherwise when it has been scrolled to its end (`checkSeen`, `ui/packages/renderer/src/app/features/write-confirmation-dialog.component.ts:295`); until then it is off, described by "Scroll to the end of the list to allow these writes.", and a row added while it is open turns it off again (`seenAll`, `:280`). The list is a focusable region named "The writes to allow" (`:55`), so Tab and the arrow keys scroll it; Esc and Cancel still cancel. Only "Allow these writes" calls `scout:features.writeGrant` with `{ granted: true, confirmWrites: true }`, which maps onto the `SetWriteGrant` rpc; "Revoke writes" sends `{ granted: false, confirmWrites: false }` with no dialog (`ui/packages/renderer/src/app/features/features.component.ts:795`, `ui/packages/renderer/src/app/core/features.store.ts:105`). Main forwards `granted` and `confirmWrites` only when they are the boolean `true` (`ui/packages/main/src/ipc/features.ts:198`). Only the main window may grant ([[pages/decisions/0053-electron-fuses-and-ipc-sender-check]]): `scout:features.writeGrant` (grant and revoke), `scout:features.enable`, `scout:features.disable` and `scout:features.deleteCredentials` answer only the main window's own page, and from any other sender (the quick-ask window, the floating button, the operator window, a renderer that is none of Scout's, a sub-frame, or a main frame on another page) they are refused before main's own check or the control plane with `features/not-main-window`, "Writes can be allowed only from the Scout window." (`onlyMainWindow`, `ui/packages/main/src/ipc/features.ts:74`; the sender is classified by `senderCheck`, `ui/packages/main/src/ipc/sender-check.ts:42`, from `windowOf` and `isAppPage` wired at `ui/packages/main/src/main.ts:425`). `scout:features.setCredentials` and `scout:features.setup` answer only the main window too, refused with the same code and "Credentials can be entered only in the Scout window." (`ui/packages/main/src/ipc/features.ts:110`, `:124`). `scout:actions.approve` and `scout:actions.reject` answer the main, quick-ask and operator windows, the three that show approval cards (the operator window's Approvals page is this screen filtered to YouTube), and refuse every other sender with `actions/not-approval-window` (`ui/packages/main/src/ipc/features.ts:230`). A refusal logs `ipc: call refused for its sender` at warn with the channel and the sender kind only (`ui/packages/main/src/ipc/sender-check.ts:54`); tests `ui/packages/main/test/ipc-features.test.ts:854`, one per channel and sender. When main's own check succeeded (for YouTube, the Google sign-in with the write scopes) but the control plane then refuses or does not answer, main undoes the check through the feature's revoke step, so the session drops the write scopes again (`undoPreparedGrant`, `ui/packages/main/src/ipc/features.ts:85`, `:211`, `:162`; tests `ui/packages/main/test/ipc-youtube.test.ts:629`, `:665`); an undo that fails in turn (Google unreachable, a token file that cannot be removed) is logged as "features: undoing the grant check failed" with its code, and the renderer still gets the control plane's error (`ui/packages/main/test/ipc-features.test.ts:889`).

- **A toggle feature.** The same dialog guards the toggle of a write-capable feature that has no main-owned connection: turning it on opens the dialog and only "Allow these writes" calls `scout:features.enable` with `confirmWrites: true`; cancelling leaves the checkbox off, because the panel resets the checkbox to the feature's state before it asks (`ui/packages/renderer/src/app/features/feature-details.component.ts:162`, `ui/packages/renderer/src/app/features/features.component.ts:776`). A read-only feature toggles as before, with `confirmWrites: false`.

- **A refusal.** The control plane answers `FAILED_PRECONDITION` "Confirm the writes of <id> before enabling it" or "... before granting them", followed by the write rows. The client turns exactly that message into `ControlPlaneWriteConfirmationError` (`control-plane/write-confirmation-required`, `ui/packages/shared/src/errors.ts:125`, `ui/packages/main/src/control-plane/client.ts:918`); a `FAILED_PRECONDITION` for missing credentials stays as it was. The card shows the message.
