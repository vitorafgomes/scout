## Contract

- **Provider `Ollama`**: the default provider ([[pages/invariants/local-first-default]]). Chat goes to Ollama's native `POST {endpoint}/api/chat` through the Ollama client (OllamaSharp 5.5.2, which the Semantic Kernel Ollama connector already brought in) and its `Microsoft.Extensions.AI` chat client, built in `CreateChatCompletionService` (`src/Scout.Llm/Providers/Ollama/OllamaLlmProviderFactory.cs:123`) and registered by a factory, so the read-only guard can wrap it; `AddToKernel` and a translation model both go through it, as with Anthropic ([[pages/decisions/0012-llm-communication-through-semantic-kernel]], amendment of 2026-11-12). The OpenAI-compatible `/v1` path it replaced has no field for a context length, so the server loaded the model with its own default of 4,096 tokens and cut a longer prompt without saying so ([[pages/roadmap/ollama-local-models]], finding 5.3). Every request now carries `options.num_ctx`, set once on the pipeline (`:138`) from `Scout:Llm:Ollama:Chat:ContextLength` (`OllamaChatOptions`, `src/Scout.Llm/Configuration/LlmOptions.cs:319`; environment `SCOUT__LLM__OLLAMA__CHAT__CONTEXTLENGTH`), 16384 by default (`:328`); a value under 4096 fails the start with "OllamaOptions.Chat.ContextLength must be >= 4096." (`src/Scout.Llm/Providers/Ollama/OllamaLlmProviderFactory.cs:72`), and there is no upper bound and no cap at the model's own limit. The pipeline is `OllamaChatClient` under the context-length option and `UseKernelFunctionInvocation`, so every function call passes the kernel's filters and the write gate (`tests/Scout.Llm.Tests/Guard/WriteGateCompositionTests.cs`), an undeclared call never runs (`tests/Scout.Llm.Tests/ChatGatewayFunctionScopeTests.cs`), and every model call of a function round trip asks for the same context length (`tests/Scout.Llm.Tests/Providers/Ollama/OllamaContextLengthTests.cs`). The function-invoking client includes a failing function's exception message in the result (`src/Scout.Llm/Providers/Ollama/OllamaLlmProviderFactory.cs:141`), as the OpenAI connector did, so the model still hears why a write was refused (`tests/Scout.Host.Console.Tests/HostOperatorTurnTests.cs`). On the wire a turn sends `model`, `messages`, `stream`, `options` (`num_ctx`, and the turn's `temperature` and output limit as `num_predict`), the declared functions as `tools` named `Plugin_function` and no `tool_choice`, which the native API does not have, plus an empty `CustomHeaders` object the client serialises; a live translation sends `stream` false and `num_predict` 400 (`tests/Scout.Llm.Tests/ProviderRequestSettingsTests.cs`, the Ollama rows). A tool result reaches the model as `{"CallId":...,"Result":...}`. `OllamaChatClient` (`src/Scout.Llm/Providers/Ollama/OllamaChatClient.cs:24`) turns the client's `HttpRequestException` with a status into `HttpOperationException` with that status and the message "Ollama answered HTTP <status>.", never the server's text; a 404 carries Scout's own `{"error":{"code":"model_not_found"}}` (`:26`), so the gateway and the live translator say the missing model by name; a 401 or a 429 from a proxy in front of the server is a rejected key or a rate limit; a 400, which the client raises as its own `OllamaException` carrying the server's sentence (`ModelDoesNotSupportToolsException` when the server says the model does not support tools), is `HttpOperationException` with status 400 and the same status-only message, the client's exception kept only as the inner one, so no Ollama client type reaches the caller and the chat ends with the generic failure sentence as on the `/v1` path; an answer that ends without the server's done line is `HttpOperationException` with status 502 and no server text; a failure with no status (a refused connection, a reset, a timeout) passes through unchanged; and a stream the caller cancels before it ends throws `OperationCanceledException`, because the client's reader stops on a cancelled token as if the answer had ended, which a Stop or the pump's overall timeout would otherwise take for a finished answer and report its usage (`tests/Scout.Llm.Tests/Providers/Ollama/OllamaHttpBoundaryFailureTests.cs`). A one-reply call reads its whole body under the token before it parses, so it was left as it is. The client makes one request and does not retry; neither did the `/v1` path, whose Semantic Kernel OpenAI connector, always handed an `HttpClient`, sets the retry policy to zero retries and no network timeout of its own. The `HttpClient` timeout is the .NET default 100 s on both paths: on a one-reply call (an audit batch round, the operator's JSON, the live translator) it bounds the whole answer of each model call, which a slow CPU-only host can exceed with a long prompt, and on a streamed call only the wait for the response headers. Whether to give the client an `HttpClient` with no timeout of its own, so each caller's bound governs, is an open owner decision ([[pages/roadmap/ollama-local-models]]). After three consecutive failing function rounds the function-invoking client stops passing errors back to the model (`MaximumConsecutiveErrorsPerRequest`, default 3), as on the Anthropic and ChatGPT plan paths. Embeddings are unchanged, on the Semantic Kernel Ollama connector. No `OllamaSharp` type is referenced outside `Scout.Llm.Providers.Ollama` (`tests/Scout.ArchTests/ArchitectureTests.cs:188`). Media: none, and no vision.
