## Hot spots

- `src/Scout.Llm/Providers/ProviderSettings.cs:19` builds `OpenAIPromptExecutionSettings` for every provider, and each connector reads it its own way: the OpenAI connector (OpenAI, OpenRouter, Mistral, Hugging Face) sends `temperature` and `max_completion_tokens`, Ollama `options.temperature` and `options.num_predict` beside `num_ctx`, Azure OpenAI and Azure AI Inference `temperature` and `max_tokens`, Anthropic `max_tokens` and never `temperature`, and the ChatGPT plan neither; Gemini converts it through the base type and sends neither of the request's values, the live translator's cap included. On the agent path the turn's temperature and limit reach no provider. The base `PromptExecutionSettings` with the two values as extension data would start sending them to Gemini, so the settings keep the connector type inside `Providers/`; `tests/Scout.Llm.Tests/ProviderRequestSettingsTests.cs` pins every provider's body, set and unset, direct and agent path, and the translation.
- `src/Scout.Llm/Providers/ProviderUsage.cs:14` chooses a usage reader by the shape of the metadata: a connector upgrade that changes its usage type, or a new connector with a shape no reader knows, counts nothing without an error until a reader is added there; `tests/Scout.Llm.Tests/ChatGatewayUsageTests.cs` drives each real connector and goes red on such an upgrade.
- `src/Scout.Llm/KernelScope.cs:19` relies on `Kernel.Clone` copying the invocation filters; a Semantic Kernel upgrade that stops doing so would run declared writes ungated on every turn, which `tests/Scout.Llm.Tests/KernelScopeTests.cs:46` and `tests/Scout.Llm.Tests/Guard/WriteGateCompositionTests.cs:55` catch.
- `src/Scout.Llm/ChatGateway.cs:44` builds the request log label per provider (Ollama, OpenAI, Gemini, ChatGptPlan, Anthropic; `unknown` fields for the others) and never reads an API key; the configured endpoint is logged as its scheme, host, port and path only, never its user-info, query or fragment, and as `unknown` when it is not an absolute URL with a host, through the same `PlainHttpEndpoint.Shown` the providers use (`src/Scout.Llm/Providers/PlainHttpEndpoint.cs:21`, `tests/Scout.Llm.Tests/ChatGatewayTargetLogTests.cs:142`).
- `src/Scout.Llm/LlmServiceCollectionExtensions.cs:76` is the closed provider switch.
- `src/Scout.Llm/LlmServiceCollectionExtensions.cs:138` adds the write gate filter only when a write function is declared; a new connector that invokes functions without passing through `KernelFunction.InvokeAsync` on the shared kernel would bypass it. The Ollama chat-client path, the Gemini connector, the ChatGptPlan `IChatClient` path, the Azure OpenAI connector, the OpenAI connector on Mistral and on Hugging Face and the Azure AI Inference connector each have a composition test (`tests/Scout.Llm.Tests/Guard/WriteGateCompositionTests.cs:55`, `tests/Scout.Llm.Tests/Guard/WriteGateProviderPathTests.cs:28`, `:61`, `:99`, `:133`, `:165`, `:199`); the Mistral one and the Hugging Face one each fail with `_publishRan should be False but was True` when the filter is not registered (2026-11-12). The Anthropic path's function round trip is asserted to pass the kernel's function filters (`tests/Scout.Llm.Tests/Providers/Anthropic/AnthropicProviderTests.cs:112`).
- `src/Scout.Llm/Providers/Mistral/MistralLlmProviderFactory.cs:20`: Mistral through the OpenAI connector is not verified against the live Mistral API: no key was available; the request tests state what is sent, not what Mistral accepts. Fields the old Mistral connector never sent, each a request Mistral may reject or ignore: `max_completion_tokens` where the Mistral connector's own request type names `max_tokens` (read from its 1.82.0-alpha assembly) (on every translation and on any turn with a limit; ignored, the limit is lost; rejected, those calls fail); `stream_options` `{"include_usage":true}` on every streamed turn; `tools` entries carrying `"strict":false` and an empty `description`, with Scout's `Plugin-function` names; `tool_choice` `auto`; on the second request of a function round trip an assistant message with `"content":""` beside its `tool_calls` and a `tool` message with `tool_call_id` and no `name`; and on embeddings `encoding_format` `base64` instead of `float` (a float-array answer is still read). No longer sent: `safe_prompt` false, the old default `temperature` 0.7 and `top_p` 1, so a turn without a temperature now gets Mistral's own default. A 429, a 5xx or a reset is now retried three times by the client before it fails, where the old connector made one request, and a reset now surfaces as `AggregateException`. Recorded in [[pages/roadmap/followups]].
- `src/Scout.Llm/Providers/HuggingFace/HuggingFaceLlmProviderFactory.cs:20`: HuggingFace chat through the OpenAI connector is not verified against the live API: no key was available; the request tests state what is sent, not what a Hugging Face endpoint accepts, and the endpoint behind the key decides (the serverless host, an Inference Endpoint or a self-hosted text-generation-inference server). Fields the HuggingFace connector never sent, each a request the endpoint may reject or ignore: `max_completion_tokens` where the HuggingFace connector's own request type names `max_tokens` (read from its 1.82.0-preview assembly) (on every translation and on any turn with a limit; ignored, the limit is lost; rejected, those calls fail); `stream_options` `{"include_usage":true}` on every streamed turn (ignored, usage counts nothing); `tools` entries carrying `"strict":false` and an empty `description`, with Scout's `Plugin-function` names, and `tool_choice` `auto`, which only a model and server with tool calling honour; on the second request of a function round trip an assistant message with `"content":""` beside its `tool_calls` and a `tool` message with `tool_call_id` and no `name`. No longer sent: `temperature` 1 on every request, so a turn without a temperature now gets the server's default, and `stream` false on a translation. A 429, a 5xx or a reset on chat is now retried three times by the client before it fails, where the old connector made one request, and a reset now surfaces as `AggregateException`. The default host is still `https://api-inference.huggingface.co`, and a configured endpoint ending in `/v1` still posts chat to `/v1/v1/chat/completions`, both as the old connector did. Recorded in [[pages/roadmap/followups]].
- `src/Scout.Llm/Providers/Ollama/OllamaChatClient.cs:24` gives every 404 of the chat endpoint the code `model_not_found`, because the client drops the body: a plain `404 page not found` from an endpoint that is not Ollama is told as a missing model, where the `/v1` path let it propagate. An `{"error":...}` line inside a 200 answer (the model runner stopped, memory ran out after the headers) is not read as a failure by the client, which ends the stream with no done line or, on a one-reply call, throws `InvalidOperationException`; `OllamaChatClient` turns both into `HttpOperationException` with status 502 and "Ollama stopped answering before the answer was complete.", so the text already streamed stays and no finished answer or usage is reported (`tests/Scout.Llm.Tests/Providers/Ollama/OllamaHttpBoundaryFailureTests.cs`). Not verified against a real server or model: the long prompt through the built worker, a model whose own limit is under 16384, the agent path with several tool calls, an audit batch, a cold first prompt against the 100 s timeout, the memory a model takes at 16384, and whether the server ignores `CustomHeaders` and reads the wrapped tool results ([[pages/roadmap/ollama-local-models]]).
- `src/Scout.Llm/Providers/Anthropic/AnthropicChatClient.cs:19` translates only `AnthropicApiException`, an HTTP status before the stream starts. The credit refusal is recognised by the words "credit balance" in the API's sentence, whose wording the client's documentation says can change; a reworded refusal falls back to the generic failure, whose log still carries the sentence. An `error` event inside a 200 stream (Anthropic's `overloaded_error` can arrive that way) surfaces as the client's own `Anthropic.Exceptions.AnthropicSseException`, whose message carries the event's JSON, and reaches the gateway untranslated; observed over the recording handler on 2026-11-07, mapping not decided.
- `src/Scout.Llm/Providers/ChatGptPlan/ChatGptPlanLlmProviderFactory.cs:109`: replacing `UseKernelFunctionInvocation` with Microsoft.Extensions.AI's `UseFunctionInvocation` keeps tool calls working and silently bypasses the write gate.
- `src/Scout.Llm/LlmServiceCollectionExtensions.cs:197` depends on each connector registering exactly one unkeyed, factory-built `IChatCompletionService`; a Semantic Kernel upgrade that changes that shape fails startup when a guard key is set, and `tests/Scout.Llm.Tests/LlmServiceCollectionExtensionsTests.cs:269` catches it for all ten providers with a model (every one but `None`).
