## Contract

- **Write gate seam:** `IWriteGate` with `RequestAsync` and `RecordAsync` (`src/Scout.Llm/Abstractions/IWriteGate.cs:8`), its answer `WriteGateDecision` (allowed, queued or refused, a reason, an action id; `src/Scout.Llm/Abstractions/IWriteGate.cs:128`), and `WriteFunctionDeclaration` (plugin, function, feature id, catalog scope row; `src/Scout.Llm/Abstractions/IWriteGate.cs:139`), registered with `AddWriteFunction` (`src/Scout.Llm/LlmServiceCollectionExtensions.cs:231`). No gRPC or vendor type crosses this seam; the host supplies the implementation ([[pages/services/host-console]]).

## How it works

**Read-only guard** ([[pages/decisions/0016-jev-read-only-guard]]), a pre-filter on the request; writes are enforced by the write gate below. When `Scout:Guard:TypeSafe:ApiKey` is set, `AddReadOnlyGuard` (`src/Scout.Llm/LlmServiceCollectionExtensions.cs:197`) removes the provider's single chat-service registration from the kernel builder, registers `ReadOnlyGuardChatCompletionService` around it, and removes the connector's separate `ITextGenerationService`; it throws at startup if the kernel holds anything other than one unkeyed, factory-registered chat service. Since [[pages/decisions/0032-per-feature-write-permissions]], the guard refuses a write intent only while no feature holds a write grant: when `Scout:Features:GrantedWrites` names at least one feature, every request goes to the model unjudged and TypeSafe is not called (`src/Scout.Llm/Guard/ReadOnlyGuardChatCompletionService.cs:92`). The first feature that writes, the channel operator's `youtube_make_video` ([[pages/services/operator]]), did not change this: with any one grant every request still goes to the model unjudged, the guard does not match the intent to the granted feature, and the write gate below, which asks the control plane at the call of every declared function, is the enforcement. Deferred: matching the intent to the granted feature. The list is read once when the worker starts, so a grant the owner changes reaches the guard only when the desktop restarts the worker with the new variable. With nothing granted, the guard (`src/Scout.Llm/Guard/ReadOnlyGuardChatCompletionService.cs:89`) sends Jev a structured state, `recent_turns` (up to 12 user and assistant messages (six exchanges, the default conversation memory) before the latest user message, oldest first, each cut to its last 1000 characters; tool messages never; system messages never) and `latest_user_message` (its last 4000 characters), so a short "ok, do it" after a proposed change is judged in context; at p >= threshold it returns the fixed refusal "Scout can act only through features the owner turned on. No feature with write permission is on; the owner enables one on the Features screen of the Scout app." (`src/Scout.Llm/Guard/ReadOnlyGuardChatCompletionService.cs:25`) without calling the model, below it delegates with the same history, settings and kernel, and on a TypeSafe failure it logs a Warning and delegates (fail-open). Both gateway paths, direct chat and the Project Expert agent, resolve the chat service from the kernel and so pass through the guard; the live translator does not, it is handed the service the guard wraps (above). Tool calls made inside a model turn are not judged. With provider `None` no model answers, so no guard is registered and TypeSafe is never called (`src/Scout.Llm/LlmServiceCollectionExtensions.cs:67`, `tests/Scout.Llm.Tests/Guard/ReadOnlyGuardCompositionTests.cs:60`); ChatGptPlan registers its chat service through a factory (`src/Scout.Llm/Providers/ChatGptPlan/ChatGptPlanLlmProviderFactory.cs:78`) so the guard can wrap it like the others.

**Write gate** ([[pages/decisions/0032-per-feature-write-permissions]]). The enforcement point for writes is the moment a function runs, not the request. When at least one `WriteFunctionDeclaration` is registered, the kernel factory adds `WriteGateFilter` to the kernel builder's services as an `IFunctionInvocationFilter` (`src/Scout.Llm/LlmServiceCollectionExtensions.cs:140`) and resolves the registered `IWriteGate`, so the kernel fails to build when a write is declared and no gate exists (`tests/Scout.Llm.Tests/Guard/WriteGateCompositionTests.cs:74`). Semantic Kernel 1.78.0 reads `IFunctionInvocationFilter` services when the kernel is built (`Kernel.AddFilters`), and every `KernelFunction` invocation on that kernel passes through them: the OpenAI connector's auto-invocation (which OpenRouter, Mistral and Hugging Face use) calls the function after its auto-invocation filters, so does the Google connector (Gemini), and so does an `IChatClient` built with `UseKernelFunctionInvocation` (`KernelFunctionInvokingChatClient`; ChatGptPlan, Anthropic and Ollama). Microsoft.Extensions.AI's own `UseFunctionInvocation` does not: it invokes the function as an `AIFunction` outside the kernel's filters, so a declared write would run without asking the gate; the ChatGptPlan provider therefore builds with `UseKernelFunctionInvocation`, and `tests/Scout.Llm.Tests/Guard/WriteGateProviderPathTests.cs:61` fails with the other builder. `IFunctionInvocationFilter` is used instead of `IAutoFunctionInvocationFilter` because it is the one point every invocation path shares. A function declares only its feature and catalog scope row, never its own access. For a declared function the filter (`src/Scout.Llm/Guard/WriteGateFilter.cs:37`) asks `RequestAsync` with the target `Plugin.function` and a summary of the function name and its arguments built from an allow-list: only an argument the declaration names in `SummaryArguments` (`src/Scout.Llm/Abstractions/IWriteGate.cs:145`, empty by default, set through `AddWriteFunction`'s `summaryArguments`) shows its value, cut to 200 characters, and every other parameter of the function shows its name only, while an argument the function does not declare shows nothing and is left out of the payload (2026-11-10, `src/Scout.Llm/Guard/WriteGateFilter.cs:135`), so a credential under any name (`authorization`, `body`, `headers`) never reaches `actions.json` or the Review screen (`src/Scout.Llm/Guard/WriteGateFilter.cs:112`, `tests/Scout.Llm.Tests/Guard/WriteGateFilterTests.cs:133`, `:148`). Allowed runs the function and records `succeeded` or `failed: <exception type>` against the id the allowed answer carried, which since 2026-11-12 (issue #323) is the id of the `started` entry the control plane wrote to its write log before answering ([[pages/services/control-plane]]; `tests/Scout.Llm.Tests/Guard/WriteGateFilterTests.cs:250`, over the real gRPC client `tests/Scout.Host.Console.Tests/GrpcWriteGateTests.cs:271`, and the YouTube reach reporting job `tests/Scout.Operator.Tests/ReachReportsTests.cs:114`), so a worker that stops between the function's return and its record leaves the write in the log; a request the control plane fails, as when that entry cannot be written, runs nothing (`tests/Scout.Host.Console.Tests/GrpcWriteGateTests.cs:286`); a record that fails leaves the function's result and logs one Warning naming the function and the exception type, never an argument, and the `started` entry stays in the log ([[pages/conventions/decisions-that-look-like-defects]]) (`:67`, `:100`, `:104`; `tests/Scout.Llm.Tests/Guard/WriteGateFilterTests.cs:169`, and over the real gRPC client with a `FAILED_PRECONDITION` reply at `tests/Scout.Host.Console.Tests/GrpcWriteGateTests.cs:206`); queued never runs it and returns "Queued for the owner's approval: an Approve card is waiting in the chat and in Approvals of Scout Desktop (action <id>)." (`:70`), so the model tells the owner the card is right there in the chat and never sends them to another menu (test `The_Bot_No_Longer_Sends_The_Owner_To_Another_Menu_To_Approve`); refused never runs it and returns the control plane's reason (`:73`); a gate that throws or does not answer never runs it, returns "Scout could not reach its control plane, so this write was not performed." and logs a Warning naming the function and the exception type, never the arguments (`:56`). A cancelled request still cancels. Undeclared functions run unchanged (`:42`). The model reads the returned text as the tool result, on the direct chat path and on the Project Expert agent path alike (`tests/Scout.Llm.Tests/Guard/WriteGateCompositionTests.cs:55`). Deferred to phase 5 of [[pages/roadmap/youtube-channel-operator]]: executing an action the owner approved on the Review screen; until then a queued write is only recorded by the control plane. One function is declared today, `YouTubeOperator.youtube_make_video` on feature `youtube`, row "Scout's data folder", with `topic` as its only summary argument (`src/Scout.Operator/OperatorServiceCollectionExtensions.cs:51`), registered only when YouTube is configured, so the production kernel carries the write filter exactly then.
