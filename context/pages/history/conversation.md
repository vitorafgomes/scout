# Conversation - history

> Dated changes to [[pages/services/conversation]]; the service page states how it works now.

## 2026-11-11 - A model the AI Source does not have is said in the chat, not as a failure

- **Asked for:** a chat message sent while Ollama was still downloading the chat model got the generic mid-flight failure; the owner's rule from the credit fix is that the chat says what happened ([[pages/history/llm]]).
- **What changed:** the pump catches the new `LlmModelNotFoundException` before its generic catch and completes the reply through the same bounded terminal write as the other provider endings, with the new `StreamPumpOptions.ModelNotFoundMessage`, "The AI Source does not have the model {0}. A local model is not installed yet or is still downloading: check AI Sources in Scout Desktop.", formatted with the model id. It is logged as one Warning naming the model, without the stack. No new status, contract or control-plane message.
- **Tests:** `StreamPumpFailureTests.When_The_Provider_Does_Not_Have_The_Model_The_Reply_Names_It_And_Says_Where_To_Look_Not_An_Error`, and a `model not found` row in the two error-ending tables (every partial text, every sink that never finishes).

## 2026-11-11 - A task the turn started keeps no owner authority after the turn

- **Asked for:** the automated audit's finding "Owner context survives the turn in captured tasks". Leaving a turn set the `AsyncLocal` to null only on the flow that left it; a task the turn started (`Task.Run`, fire and forget) had copied the execution context and kept the turn, so `ChatOrigin.IsOwner`, `Current` and `Remembers` still answered the owner, the origin and the marks there after the turn ended. No production path started such a task, so this hardens the owner-authority boundary of [[pages/invariants/no-executive-writes]].
- **What changed:** the `AsyncLocal` holds a holder every task of the turn shares; leaving the turn clears the holder, so a captured context sees the turn end, and puts back the holder the flow had before, so a nested turn's end gives the outer turn back where it used to leave nothing. Every reader goes through the holder. Inside a live turn nothing changes, concurrent turns included.
- **Tests:** `tests/Scout.Conversation.Tests/Abstractions/ChatOriginTurnEndTests.cs` (a task held until the turn ended, a nested turn, two concurrent turns, a task of an ended turn read while a later owner turn runs on another flow); `ConversationConductorOriginTests` and `ChatOriginMarksTests` unchanged and green before and after.

## 2026-11-11 - The Claude API account out of credit is said as the balance running out

- **Asked for:** every message to the Claude API was answered "Scout could not answer that; see Scout logs."; the cause was the account's credit balance. The owner asked that the reply not show an error but say the balance ran out.
- **What changed:** an `LlmQuotaExceededException` with code `credit_balance_too_low` ([[pages/history/llm]]) completes the reply with the new `StreamPumpOptions.CreditExhaustedMessage`, "The AI provider's account has run out of credit. Add credit with the provider, or choose another AI Source in Scout Desktop.", as `PlanUsageLimitMessage` does for the ChatGPT plan's limit. Every other quota code keeps `QuotaExceededMessage`. The Warning naming the code is unchanged.
- **Tests:** `StreamPumpFailureTests.When_The_Claude_Api_Account_Has_No_Credit_Left_The_Reply_Says_The_Balance_Ran_Out_Not_An_Error`, and a `credit ran out` row in the two error-ending tables (every partial text, every sink that never finishes); `Quota_Exceeded_MidStream_Tells_The_User_The_Account_Has_No_Credit` unchanged and green.

## 2026-11-11 - A successful later post is logged once, for every adapter

- **Asked for:** the rework of the earlier fix for "Successful origin posts have no audit log", which logged only Discord's posts ([[pages/history/adapter-discord]]).
- **What changed:** `OriginNotifier.PostAsync` logs one Information line when the poster reports the post made, "Posted <n> characters to the originating <kind> conversation.", the kind being the reference's prefix (`discord`, `slack`, `local`); never the text, never an id. A refused or failed post logs as before.
- **Tests:** `A_Successful_Origin_Post_Leaves_A_Record_In_The_Log_With_The_Channel_Kind_And_Length_Never_The_Text_Or_An_Id` in `OriginNotifierTests.cs`.

## 2026-11-11 - A turn that runs a skill with functions is not capped at the chat limit; an answer with no text says why

- **Asked for:** a Claude code review of a large pull request gave no answer ([[pages/history/llm]]). Every chat turn carried `Scout:Conversation:MaxTokens`, 800, and Claude counts its always-on thinking against that limit, which left almost nothing for a turn that reads a pull request and then writes its findings.
- **What changed:**
  - **The output limit:** the router sends the chat limit only when none of the turn's skills declares functions. A review, an audit, the issues skill or the operator, whether selected, carried from the previous turn or set by a desktop marker, sends none, and the provider's own limit applies. The pages give no cost reason to bound those turns.
  - **No text from the model:** the pump completes a reply ended by `LlmNoAnswerException` with that exception's sentence, as it does with a rejected key, so the desktop, Discord, Slack and Teams show why instead of a generic failure or an empty reply.
  - **Still open:** a plain chat answer at 800 can still be cut while Claude thinks. The owner is then told so, and the smallest fix is to drop `MaxTokens` from `appsettings.json` and leave length to the system prompt.
- **Tests:** `tests/Scout.Conversation.Tests/Routing/LlmStreamingRouterOutputLimitTests.cs`, the "no answer" rows of `tests/Scout.Conversation.Tests/Streaming/StreamPumpFailureTests.cs`, and `tests/Scout.Adapter.Local.Tests/LocalChatAdapterTests.cs` `An_Answer_The_Model_Ended_With_No_Text_Completes_With_The_Sentence_That_Says_Why`.

## 2026-11-10 - Error endings within the sink's length limit, and a terminal write that cannot outlive the timeout

- **Asked for:** Scout's own audit of this repository (issues "Error terminal bodies ignore the sink length limit" and "Provider-error completion can run past the hard timeout"). Both were reproduced on this tree before anything changed: with a 300-character sink, a rate-limit ending after a partial text of 300 characters was 381 characters long and a failed stream handed `FailAsync` all 900 characters of its partial text; with a sink whose terminal write never returned, the run never returned either.
- **What changed:**
  - `StreamPump` renders every provider-error ending through one capped body: the room for the blank line and the sentence is taken first and the partial text is cut to what is left, from its start, or dropped when it does not fit and what is left cannot hold more than the truncation marker. Before, the partial text was cut to the whole limit and the sentence was appended after it, so the body exceeded the limit by the sentence's length, and a sentence longer than the limit was never cut.
  - `FailAsync` receives the first part of the partial text that fits the limit, ending in `... (truncated)` when it was cut. Before, it received the whole buffer. The first part and not the newest: Slack and Teams cut the text again from its end for their own footer, and a text the pump had cut from its start came out with a marker at both ends and without the newest text the pump had kept. Cut from the same end, the sink's cut removes the pump's mark, and the owner sees what they saw before this change: the first part, one marker, the footer.
  - Every terminal write of a run that ended on an error is bounded: what remains of the overall timeout while it has not fired, `StreamPumpOptions.TerminalWriteGrace` (new, 10 seconds by default, on the injected clock) once it has. The pump stops waiting at the bound even when the sink ignores its token; the write is left to finish on its own and a failure it ends in later is observed. Before, the five provider-error endings and `FailAsync` ran on a token that never cancels and were awaited without a bound.
  - A terminal write the sink rejects or does not finish in time is logged once as a Warning with "timed out" or the exception's type name, and the run returns normally. Before, a rejection escaped the pump into the conductor and a write that never finished held the run for ever.
  - When the caller has already cancelled and the stream failed for another reason, the pump stops with the cancellation and makes no terminal call; before, it called `FailAsync` or `CompleteAsync`. Kept on purpose: the conductor marks a turn that ends in the caller's cancellation as cancelled and rethrows, exactly as for a cancellation mid-stream, where the pump has always made no terminal call. The other outcome wrote "the AI provider returned an error" into the chat for a turn that was stopped, which is what a provider connection torn down by the stop looks like, and with a bounded token it would be a call into the sink on a token that is already cancelled.
  - The pump refuses to be built with a negative or infinite `TerminalWriteGrace`.
- **Not changed:** the begin, the updates and the completing write of a stream that ended well still end only when the sink honours their token, and the completing write still propagates its failure to the conductor. No adapter was edited. What the real sinks do with the bodies the pump sends was checked by driving the real pump into each of them:
  - Slack (3,000) and Teams (28,000) pass a terminal body of exactly their limit whole, so an error ending now arrives with its whole sentence; before, both kept the head and cut the sentence off the end.
  - Slack's interim body disagrees with the pump's by one character, Discord declares no limit although it keeps at most five parts, and the single marker of a failed reply rests on each sink's footer being longer than the pump's mark: all three are in [[pages/roadmap/followups]].
- **Tests:** in `tests/Scout.Conversation.Tests/Streaming/StreamPumpFailureTests.cs`: `Every_Error_Ending_Is_Delivered_Within_The_Sinks_Length_Limit_With_Its_Whole_Sentence` (28 cases), `The_Partial_Text_Gives_Way_To_The_Sentence_And_Keeps_Its_Newest_Part`, `A_Failed_Stream_Hands_The_Sink_The_First_Part_Of_The_Partial_Text_With_One_Marker_At_Its_End`, `A_Limit_Smaller_Than_The_Sentence_Cuts_The_Sentence_And_Drops_The_Partial_Text`, `A_Limit_With_No_Room_For_A_Cut_Partial_Text_Delivers_The_Sentence_Alone`, `A_Short_Partial_Text_That_Fits_The_Room_The_Sentence_Leaves_Exactly_Is_Kept_Whole`, `An_Error_Ending_The_Sink_Never_Finishes_Ends_The_Run_Once_The_Overall_Timeout_Has_Passed` (seven endings, each with a sink that honours its token and one that ignores it), `A_Terminal_Write_That_Starts_After_The_Timeout_Ends_The_Run_Once_The_Terminal_Write_Grace_Has_Passed`, `The_Callers_Cancellation_Stops_A_Run_Whose_Terminal_Write_The_Sink_Never_Finishes`, `A_Caller_Already_Cancelled_When_The_Stream_Fails_Gets_Its_Cancellation_And_No_Terminal_Call`, `A_Write_Abandoned_At_The_Bound_That_Fails_Later_Is_Never_Reported_As_Unobserved`, `A_Negative_Or_Infinite_Terminal_Write_Grace_Is_Refused_When_The_Pump_Is_Built`, `A_Terminal_Message_The_Sink_Throws_On_Before_Returning_A_Task_Is_Logged_Once_And_The_Run_Ends` and `A_Terminal_Message_The_Transport_Rejects_Is_Logged_Once_And_The_Run_Ends`. The timeouts run on a fake clock with continuations run inline; no test waits on real time. Through the real sinks: `Driven_Through_Real_StreamPump_A_Failed_Reply_Over_The_Limit_Shows_Its_First_Part_One_Truncation_Marker_And_The_Footer` in `tests/Scout.Adapter.Slack.Tests/Streaming/SlackSinkBoundaryTests.cs` and `Pump_A_Failed_Reply_Over_The_Limit_Shows_Its_First_Part_One_Truncation_Marker_And_The_Footer` in `tests/Scout.Adapter.Teams.Tests/Streaming/TeamsSinkStreamPumpTests.cs`.
- **Invariants:** [[pages/invariants/pluggable-boundaries]] holds; the pump reads only the limit and the duration a sink declares. [[pages/invariants/no-executive-writes]] holds; no call was added, the terminal message is the reply through the sink as before. The first chunk still reaches the channel before the stream is collected ([[pages/decisions/0013-conversation-core-streaming-sink]], amended on this date); nothing more is buffered.
- **Open:** the registered pump has no `OverallTimeout`, so only a Teams reply has a ceiling, and on Discord, Slack and the desktop the bound on an error ending does not apply yet ([[pages/roadmap/followups]]).

## 2026-11-09 - Memory budget in whole pairs, an append that survives an expiry, keys that cannot collide, a pairing code given back

- **Asked for:** Scout's own audit of this repository (issues "Conversation keys can collide across channel/user pairs", "Character trimming can replay an orphaned assistant turn", "Expired-entry removal can discard a concurrent append" and "A failed pairing notification permanently consumes the code").
- **What changed:**
  - `InMemoryConversationMemoryStore` spends the character budget on whole user/assistant pairs, newest first, and keeps the newest pair whole even when it alone is over the budget. Before, the budget was applied one turn at a time, so a load could return an answer without its question.
  - `Append` checks, once it holds the entry's lock, that the dictionary still maps the key to that entry, and starts again on the entry now there when it does not. `Load` removes an expired entry by key and entry together, so it never removes a newer entry stored under the same key while it waited. Before, an append that had taken its entry before a load or a sweep removed it wrote the turn to the detached entry and the turn was lost.
  - `ConversationKeyProvider` prefixes the channel id with its length before the unit separator, so two channel and user pairs whose ids contain the separator no longer derive the same key. Keys live only in the worker's memory, so nothing stored changes shape.
  - `ConversationConductor` holds the pairing code while it reports the pairing to the host, marks it spent once the report returned, and gives it back when the report throws, unless a burn spent it meanwhile. Before, a report that threw left the code spent and the owner could not send it again. An attempt that arrives while a report is in flight is refused and never reported.
- **Not changed:** the sweep an append runs already removed an expired entry by key and entry together, so only `Load` and `Append` changed. Two more audit claims were checked and are not defects in Scout as composed:
  - "A cursor longer than the body cap crashes interim rendering": the pump's options are built in code and no configuration section binds them, so the cursor is always the one-character default, and a sink cannot declare a cap below one character.
  - "A long voice quote makes every wrapped response oversized": the quote is the transcript's first 200 characters on one line, 212 characters with its markers, against a smallest sink cap of 3,000, so the pump always has room left and every body stays within the cap.
- **Tests:** `The_Character_Budget_Trims_Whole_Pairs_So_No_Answer_Is_Replayed_Without_Its_Question`, `Load_Keeps_The_Newest_Pair_Whole_Even_When_It_Exceeds_Budget`, `An_Append_Racing_The_Removal_Of_Its_Expired_Conversation_Keeps_The_Turn` and `A_Load_Dropping_An_Expired_Conversation_Never_Removes_The_Newer_One_Under_The_Same_Key` in `tests/Scout.Conversation.Tests/InMemoryConversationMemoryStoreTests.cs`; `DeriveKey_Cannot_Collide_When_An_Id_Contains_The_Separator` in `tests/Scout.Conversation.Tests/ConversationKeyProviderTests.cs`; `A_Failed_Pairing_Notification_Leaves_The_Code_Usable_So_A_Retry_Pairs` and `A_Pairing_Attempt_While_A_Report_Is_In_Flight_Is_Refused_And_Never_Reported` in `tests/Scout.Conversation.Tests/ConversationConductorPairingTests.cs`. The two claims that are not defects are pinned by `The_Registered_Pump_Draws_The_One_Character_Cursor_Whatever_The_Configuration_Says` in `tests/Scout.Conversation.Tests/ConversationServiceCollectionExtensionsTests.cs`, which also runs the registered pump into a sink with a one-character cap, and `A_Long_Voice_Quote_Keeps_Every_Rendered_Body_Within_The_Smallest_Sink_Cap` in `tests/Scout.Conversation.Tests/ConversationConductorVoiceTests.cs`. `A_Sink_Whose_Begin_And_Fail_Both_Throw_Never_Crashes_The_Host` in `tests/Scout.Conversation.Tests/ConversationConductorTests.cs` and `The_Voice_Attachment_Stream_Is_Disposed_Once_The_Turn_Has_Read_It` in `ConversationConductorVoiceTests.cs` pin what the Slack and Discord entries of the same day rely on ([[pages/history/adapter-slack]], [[pages/history/adapter-discord]]).
- **Invariants:** [[pages/invariants/pluggable-boundaries]] holds; no adapter or vendor type entered this project. [[pages/invariants/no-executive-writes]] holds; the memory is in the worker's RAM and the only write is still the reply through the sink.
