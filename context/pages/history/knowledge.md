# Knowledge - history

> Dated changes to [[pages/services/knowledge]]; the service page states how it works now.

## 2026-11-11 - An unreadable folder, a failed vector replace and the 100,000-row read

- **Asked for:** three findings of the second automated audit: one unreadable directory aborted the whole project index; a failed replacement destroyed the previous vector index; the 100,000-row read left stale vectors behind on a larger project. The `index` command's cooperative stop is in [[pages/services/host-console]].
- **What changed:** `ProjectIndexer` walks the repository one folder at a time, so a folder below the root that cannot be listed is skipped with a warning while the root itself still throws. `SqliteProjectKnowledgeStore` reads every earlier vector id page by page, writes the new vectors, and removes the earlier ids it no longer holds only after the write; a failed write removes only the ids it added. The page size is an internal constructor parameter, 100,000 by default, so a test reproduces the cap with two rows.
- **Not changed:** a skipped folder's chunks from an earlier index are dropped by the full replace, the same trade-off the follow-up on an unreadable file records ([[pages/roadmap/followups]]); the existence check's fill from the vectors keeps its single 100,000-row read.
- **Tests:** `IndexAsync_Skips_A_Directory_It_Cannot_Read_With_One_Warning_And_Indexes_The_Rest` in `ProjectIndexerTests.cs`; `ReplaceProjectAsync_WhoseVectorWriteFails_Leaves_The_Previous_Vector_Index_Usable` and `ReplaceProjectAsync_On_A_Project_With_More_Vectors_Than_One_Read_Returns_Leaves_No_Stale_Vector_Behind` in `SqliteProjectKnowledgeStoreTests.cs`.

## 2026-11-10 - The root listing inside the guarded block

- **Asked for:** Scout's own finding "Root enumeration errors escape the documented warning path": the enumeration of the root was opened inside the `try` and read by the loop outside it, so an error raised while the entries are read escaped `DiscoverAsync`.
- **What changed:** the root's folders are listed whole inside the guarded block, and the loop runs over that array; the per-folder handling is as before. The summary names a root that cannot be listed beside one that cannot be opened. The listing is an internal `ListDirectories` property whose default is `Directory.EnumerateDirectories`, materialised with `ToArray()` inside the `try`; only tests set it, and the public constructor and the DI registration are unchanged.
- **Tests:** `An_Error_While_A_Roots_Entries_Are_Read_Returns_An_Empty_List_With_A_Warning` in `ProjectDiscoveryServiceTests.cs`, two rows, a listing that yields one repository folder and then throws `IOException`, and one that throws `UnauthorizedAccessException`: the result is empty, there is one warning carrying that exception, and nothing is thrown. Red on the code before the fix (the lazy listing assigned inside the `try` and read by the loop outside it): both rows threw out of `DiscoverAsync` from the loop. Proved by a test: an error while a root's entries are read returns an empty list with a warning. Still not arranged against a real file system: a listing that fails after a successful open on Linux. `DiscoverAsync_On_An_Existing_Root_That_Cannot_Be_Read_Returns_Empty_And_Logs_One_Warning` stays green as the lock.

## 2026-11-09 - Seven findings of Scout's own audit on the project index

- **Asked for:** the Knowledge findings of the audit Scout ran on its own repository, triaged against the tree first: six confirmed, one refuted.
- **An embedding failure no longer empties the index.** `ProjectIndexer` caught every exception per file and returned no chunks, and both replace paths read "no chunks" as "delete": with the embedder down a full index replaced the project with nothing, and the watcher deleted the rows of each changed file. Now only the file read is caught in a full index (`IOException`, `UnauthorizedAccessException`, one warning, the file skipped); an embedding failure throws before anything is replaced. The watcher's per-file builder throws on both, the watcher logs and keeps the rows. The `index <project>` command logs "Indexing failed for project '<name>'." and exits 1 where it used to end on an unhandled exception.
- **A project whose path changed is indexed again.** Rows persist across runs keyed by project name, and nothing compared the path, so a configured project pointed at another repository answered from the old one. The store gains the table `project_source (project, repo_path)`, written by the indexer after the chunks and read on each resolve. The alternative, marking every project stale at start, was rejected: it re-embeds every project in every process. A database from before this change gets the empty table on its first connection and each project adopts its configured path on its first resolve, without a re-index.
- **An old run does not clear the stale mark of a new registration.** The mark was removed by name after indexing; a project registered at another path while the old path was indexing lost its mark when the old run ended. It is now removed only when the path registered at that moment is the one that was indexed.
- **A failed index is said as such.** Resolution returned null for an unknown project and for a failed index alike, so an embedder outage reached the user as "Unknown project". A project whose chunks were indexed from the path it has now still resolves, with an error logged, and is indexed again on its next use; one whose path changed is never answered from the old path's chunks, and it, like one with no chunks, answers "Indexing project '<name>' failed, so it cannot be searched yet. Try again later."
- **A cancellation the caller asked for propagates; a timeout nobody asked for does not.** Both tools' catch-alls took `OperationCanceledException` and answered "Could not ..."; they now let it through when the caller's token is cancelled. The first version of this change let every `OperationCanceledException` through, and the review found the hole: an HTTP client that times out throws a `TaskCanceledException` nobody asked for, which then left both tools and the `index` command unlogged, where the tool used to answer "Could not search project". The four filters, the one around the index run in `ResolveAsync` among them, read the caller's token, so a timeout during an index run is an indexing failure like any other: the project answers from an index of the same path, or says that indexing failed. Measured through the real connectors on an endpoint that never answers: the Ollama connector surfaces the timeout as a `TaskCanceledException`, the OpenAI connector as an `AggregateException` after four tries, so only the first ever escaped.
- **A first index that did not finish is indexed again.** The store writes a project's vectors, then its text rows. A run that stopped between the two left vectors only, which the existence check took for a database from before the text table: it filled the text rows from the vectors, the resolve adopted the configured path, and the project stayed without its field chunks, which have no vector, and was never indexed again. `ReplaceProjectAsync` now writes the project's row in `project_source`, with an empty path, before the vectors and never over a recorded path; vectors with no text rows beside such a row are an unfinished write, and the project counts as not indexed. Two smaller rules were rejected. Counting every project with vectors only and no recorded path as not indexed would also re-embed every database written before the text table existed, at the owner's cost on a paid provider. Recording the path in the transaction of the text rows changes nothing here: an unfinished write and such a database would still both show vectors, no text rows and no path. A complete index from before the path was recorded, with or without text rows, is still adopted with no embedding call.
- **A failed write of the recorded path does not take the index with it.** The indexer and the adoption on resolve both let that write's exception out, so an index that was intact answered "Indexing project ... failed" or "Could not ... right now". Both now log a warning and carry on; a later resolve records the path.
- **Every C# member kind has a symbol chunk.** Only methods, classes, records and interfaces had one, so `find_symbol` never found a struct, an enum, a constructor, a property, a field, an event or a delegate by name. On Scout's own `src/` (487 indexable files, 402 of them C#): 3,071 chunks before, 5,241 after (1,558 fields, 507 properties, 78 constructors, 15 enums, 6 structs; no delegate and no event in the tree), the largest file from 118 chunks to 223, chunk text from 3.77 to 4.00 million characters (+6%). A second count, taken after the cut and the field rule below had added two constants and one method of their own to the tree, gave 5,244 chunks and 1,560 fields; the figures that follow, and the follow-up entry, are from that count. Fields are found by name and never embedded: `find_symbol` reads the text table only, and the 1,560 one-line fields would have taken vector hits from the types and methods that explain them and added 4.8 MB of vectors. Inputs sent to the embedder for the whole tree: 3,071 before, 3,684 after (properties, constructors, enums and structs), at most 118 per file as before.
- **The text sent for embedding is cut at 16,000 characters.** Once an embedding failure stops the index, one input the provider always rejects makes the whole project unindexable, and every tool call starts a full index again. Twenty inputs in Scout's own `src/` were over 16,000 characters, the largest a class of 146,592. The stored chunk is whole; only the embedded text is cut. Embedding input for the tree: 4,444,218 characters with every chunk sent whole, 3,911,289 with fields left out and the cut.
- **The chunk ordinal is part of the id.** The id ended at the start line, and the vector collection is keyed by id: two declarations starting on one line made the vector write fail with `UNIQUE constraint failed` and the whole project unindexed on a provider with embeddings. Rare, but it took the whole project with it. No migration: both replace paths delete by project or path.
- **Refuted:** discovery on a root that exists but cannot be read was reported as an unhandled exception. The enumeration opens the directory inside the `try`; a test with the root at mode 000 was green before any edit and stays as the lock.
- **Tests:** `tests/Scout.Knowledge.Tests` from 217 to 280 cases; three tests that pinned the old swallow were rewritten (`ProjectIndexerTests`, `ProjectWatchServiceTests`, `IndexHostOpenAIEmbeddingsTests`). Each new behaviour failed its test with the change taken out in a backup copy. The watcher tests on the fake clock await a signal the clock gives when the service arms its next timer, where they polled against a five-second real deadline; the three tests that make a file unreadable by its mode return at once on Windows and for a privileged process, which reads the file anyway.
- **Cost:** per resolve, one more point read (30 to 40 microseconds measured, against 38 to 45 for the existence check beside it) and one more `CREATE TABLE IF NOT EXISTS` in the schema batch of every connection (3 to 7 microseconds); per full index, two more statements, each on a connection of its own: the project's row inserted before the vectors and the path written after the chunks; per existence check of a project that has no text rows (one not indexed yet, or a database from before the text table), one more point read; neither of these was timed; per file, the larger chunk list and at most one string cut per chunk.
- **Not changed:** a file that exists but cannot be read still loses its rows in a full re-index; the watcher does not retry a failed file; two index runs of one project are not serialised; `search_project` still fails when the question's embedding call fails; the text-ranked path with the new member chunks is not measured; the Ollama and Gemini providers send a file's inputs in one request whatever `MaxBatchSize` says; a project whose index run fails every time is indexed again on every tool call; an index adopted from before this change gains the new member chunks only when it is next indexed, and offering that re-index is the owner's decision because it embeds every file again; a re-index, unlike a first index, that stops between the vector write and the text write is not repaired; with the watcher on, one file saved in a project whose first index did not finish makes it count as indexed. All ten are in [[pages/roadmap/followups]].
- **Invariants:** [[pages/invariants/no-executive-writes]] holds: the new writes are rows in Scout's own database. [[pages/invariants/pluggable-boundaries]] holds: the new SQL is in the store, behind two methods of `IProjectKnowledgeStore`.
