# Desktop UI - history

> Dated changes of [[pages/services/desktop-ui]]; the service page states how it works now.

## 2026-11-14 - Disconnect on the Ollama card

The AI Sources artboard drew Disconnect on the Ollama card and the app had none: the only way off Ollama was choosing another source, and Ollama's models stayed in Models, Analysis. Now Disconnect asks "Disconnect Ollama?" first; confirmed, Scout switches to a connected cloud provider or writes `llm.provider=None` when Ollama was in use or nothing was saved, asks Ollama to free its memory, and keeps the choice in `localStorage`: the card reads Not connected with "Scout does not use Ollama. Connect to use it again.", Analysis lists no Ollama model, and only Connect undoes it. The owner chose on 2026-11-14 that Scout stays with no source rather than block the Disconnect, and the drawn state for a disconnected Ollama that still answers. Tests changed on purpose: the Ollama card's actions now end with Disconnect.

## 2026-11-14 - Docker: the logs of the runs and the command on the Stack tile

Two items the Features artboard draws in the Docker panel and the app lacked ([[pages/roadmap/prototype-migration]], Features). The work folder line read "<size> used · each run's copy of the code is deleted after it" because nothing counted the runs; main's `workFolder()` now counts the `<id>.run.json` records (0 when the folder is missing or cannot be listed), `DockerWorkFolder` carries `runs`, and the line reads "184 MB used · the logs of 12 runs; each run's copy of the code is deleted after it", "the logs of 1 run" for one, without the count when no record is there; "Empty · run logs are deleted" is unchanged. The last run's Stack tile read ".NET" because the record did not carry the command; the sandbox now writes `command` ([[pages/history/sandbox]]), main's `toRun` copies it, an older record without one reading as null, `DockerRun` carries it, and the tile reads ".NET (dotnet test)", or the stack alone when the record has none. Nothing new is written and no call leaves the process: the count is a listing of Scout's own work folder in main. Tests changed on purpose: every work folder fixture carries `runs`, every run fixture `command`, and the folder line expected at 184 MB and in the prototype spec's Clear refused state names the logs of 12 runs.

## 2026-11-14 - Updates: install a version the owner picks

The owner asked to choose which version to install, an older one included, to test it. Before, Scout installed only the release the notice offered and never went down. Now Settings, Updates has "Install a specific version": the published versions on the owner's channel, Install on each (Download where the package cannot replace itself), a confirmation before an older one, and the install's progress in the list. Main installs only a version it listed, through that release's own metadata, lets the updater go down only for that install, and points it back at the GitHub feed after. Governed by [[pages/decisions/0056-install-a-version-the-owner-picks]]. Tests changed on purpose: the updater fake gains `allowDowngrade` and `setFeedURL`, and the flags asserted at a normal install now include `allowDowngrade: false`; the IPC contract and preload tests list the two new channels.

## 2026-11-14 - Updates: a Beta channel

The owner asked for beta versions to test with. Before, the update check read `releases/latest` and dropped any pre-release, so no installed Scout was ever offered one. Now Settings, Updates has a Channel row, Stable (the default) or Beta; Beta reads the release list and offers the highest version that is not a draft, a pre-release included, and lets electron-updater take pre-releases for that install. Neither channel offers an older version, and Settings says so when the owner goes back to Stable on a pre-release. A pre-release build already writes `latest*.yml`, the metadata the release workflow keeps, so the release side is unchanged. Governed by [[pages/decisions/0031-desktop-self-update]], amendment of 2026-11-14. Tests changed on purpose: the full-state assertions of `ui/packages/main/test/update-notice.test.ts` and the Settings and update-notice specs carry `channel: 'stable'`, the IPC contract and preload tests list `scout:update.setChannel`.

## 2026-11-13 - The ChatGPT sign-in cancel test waits for the browser to return

The test "cancelling a sign-in that waits for the browser" in `ui/packages/main/test/oauth-chatgpt.test.ts` failed once on the macOS runner with "still waiting for the browser" after 1 s, and passed on the same code before and on Linux. It cancelled as soon as the fake browser had recorded the authorize URL, while the fake was still probing the loopback listener; `ChatGptAuth.signIn` rejects only after `openExternal` returns, so a probe that outlasted the cancel, most likely slowed by the listener closing under it (not measured on the runner), held the rejection past the test's one second. The test now cancels once the fake browser has returned (`listenerUpWhenBrowserOpened` is set), which is the state its name describes. With a fake browser that waits 1.5 s when the cancel arrives during it, the old wait fails with the CI message and the new one passes. The sign-in code is unchanged.

## 2026-11-12 - Ollama frees Scout's models when Scout stops using it

The owner, translated: "when I stop using the Ollama service it should stop running on the machine". The owner deferred the server controls on 2026-11-11, so Scout does not stop the server, which the computer runs and other programs may use; Scout asks Ollama to unload only the models Scout uses. Until now a switch to a cloud provider left the chat model in Ollama's memory for Ollama's own keep-alive, about five minutes, because Scout never asked. Now, when the owner's click saves a provider other than Ollama while Ollama, or no saved provider, was in use, the renderer asks main on the new `scout:llm.unloadOllamaModels`; main reads from its own vault the Ollama endpoint configured in Scout (localhost by default, the one chat uses) and Scout's models (the chat model, the translation model when its provider is Ollama, and `nomic-embed-text`), reads what that Ollama has loaded and asks it to unload each loaded model under one of those tags with a zero keep-alive, never the server. Ollama keeps no record of which program loaded a model, so a model under one of Scout's tags is unloaded whoever loaded it and the next request from any program loads it again; a model under any other tag stays loaded. The Ollama card says "Ollama freed its models from memory. It keeps running for other programs.", or "Scout could not ask Ollama to free its memory. Ollama frees it by itself after a few minutes without use." when Ollama refused a model or the call failed while Ollama was in use, and nothing when Ollama could not be reached and no provider had been saved before, since the owner may never have used Ollama; a failure never undoes the switch. The unload is a reviewed local write on the owner's click, with no grant, logged by name in main's log ([[pages/decisions/0032-per-feature-write-permissions]], bullet of 2026-11-12). The Sources artboard drew the two lines first, with the Preview states "Ollama freed its memory" and "Ollama not asked to free memory", and its Disconnect Ollama confirmation gained "Ollama frees its memory and keeps running."; the app has no Disconnect on the Ollama card yet ([[pages/roadmap/prototype-migration]]).

## 2026-11-12 - The dead worker-HTTP plumbing is deleted

With the LLM Server panel and the Ollama card reading Ollama's own model list since 2026-11-11, nothing called the `scout:providers.*` lifecycle channels any more, and their path could never work: the main handlers asked the worker over an HTTP endpoint that only the retired worker announced with a `SCOUT_HTTP=` line, so every call failed with "Worker HTTP endpoint not available". The six channels (`list`, `status`, `start`, `stop`, `restart`, `setAutostart`) left the shared contract with their request, status and list types, the preload bridge, the renderer's bridge service and the fallback bridge it uses when a window has no preload bridge; main lost their handlers, the worker HTTP client, the `SCOUT_HTTP=` marker parse in the log stream and the supervisor's `httpEndpoint`; the shared package lost the six provider error classes only that client raised. A `SCOUT_HTTP=` line from a worker would now be an ordinary log line. `scout:providers.validateKey`, the cloud key check, is a separate handler and stays, and the `worker/http-unavailable` code stays because the features store still reads it. Nothing moved to the control plane: the .NET Providers service and its RPCs, and the desktop client's `listProviders`, are untouched ([[pages/roadmap/control-plane-client]], phase 3; [[pages/roadmap/ollama-local-models]], lane G). The tests of the deleted code went with it: the handler and client tests in main and the supervisor test that pinned an empty `httpEndpoint`; the spec fakes for the deleted bridge members were dropped from the Models, Ollama dialog and AI Sources specs.

## 2026-11-10 - the vault refuses a Linux store with no keyring service

Scout's audit reported that the vault decided on `safeStorage.isEncryptionAvailable()` alone, in four places, and never asked which password store Electron had selected, so on Linux a `basic_text` store, which protects data with a fixed, publicly known password, would have been used if Electron ever reported it as available. How the vault decides now is on [[pages/services/desktop-ui]] ("Credential vault").

- **After.** One `availability` answers all of them, and `store`, `get` and `has` pass it before touching the file; on Linux only `gnome_libsecret`, `kwallet`, `kwallet5` and `kwallet6` are accepted, anything else is refused with the new reason `insecure-store` and its own sentence. `has` is now refused whenever the vault is, `no-keyring` included, so no screen reports a saved credential the vault will not read; every renderer caller of `scout:vault.has` already handled a refusal. `delete` stays ungated.
- **Electron 45.2.3 observed.** `basic_text` reports encryption unavailable unless plain-text encryption is turned on, which Scout never did, so no Scout build on this Electron wrote a `basic_text` file; the refusal is a second line. Builds before 2026-10-22 shipped Electron 41, which was not probed.
