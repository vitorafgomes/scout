# Llm - history

> Dated changes to [[pages/services/llm]]; the service page states how it works now.

## 2026-11-12 - Ollama chat on the native API with a context length

- **Asked for:** the whole Ollama flow must work, and "the model must see the whole prompt". Scout reached Ollama through its OpenAI-compatible `/v1` path, which has no field for a context length, so the server loaded the model with its own default of 4,096 tokens and cut a 10,020-token prompt to about 2,050 without saying so (finding 5.3 of [[pages/roadmap/ollama-local-models]]).
- **What the tests established first:** a prompt of about 40,000 characters with a marker on its first line and the question on its last, sent through the kernel's chat service streamed and as one reply and through a chat service on another model, went to `/v1/chat/completions` with no context length; a function round trip and a live translation did the same; a 404 shaped as the native API answers it (`{"error":"model 'llama3.1' not found"}`) propagated as the OpenAI client's exception instead of the missing-model one. Each new test was red on that code on the request path.
- **What changed:** `OllamaLlmProviderFactory` builds the Ollama client's chat client over the native `POST {endpoint}/api/chat`, wraps it in `OllamaChatClient`, which turns an HTTP status into `HttpOperationException` (a 404 carries the code `model_not_found`, so the missing model is still said by name), sets `options.num_ctx` on every request from `Scout:Llm:Ollama:Chat:ContextLength` (default 16384, refused at start below 4096), and hands it to the kernel through `UseKernelFunctionInvocation`, so function calls still pass the kernel filters and the write gate. A 400, which the Ollama client raises as its own exception with the server's sentence (a model that does not support tools among them), is turned into the same `HttpOperationException` with status 400, so no Ollama client type reaches a caller. An answer that ends without the done line, which is what an `{"error":...}` line after a 200 leaves (observed over the recording handler: the streams ended normally with the gateway reporting a finished answer, the one-reply call threw the client's `InvalidOperationException`), is `HttpOperationException` with status 502. A stream cancelled before its end throws `OperationCanceledException`, because the client's reader stopped silently on a cancelled token and a Stop would have read as a finished answer. The function-invoking client includes the function's error in the result, as the OpenAI connector did, so the model still hears why a call failed. The chat service is registered by a factory, so the read-only guard still wraps it. Embeddings, the HTTP seam and every other provider are unchanged; the `SKEXP0010` suppression and the `/v1` endpoint are gone. ADR 0012 has an amendment for chat clients built behind the chat-completion service.
- **On the wire now:** `options` carries `num_ctx` beside `temperature` and `num_predict` (the request's output limit, the live translator's 400); a one-reply call sends `stream` false; every body carries an empty `CustomHeaders` object, which the client serialises; there is no `tool_choice` field on the native API; tool names are `Plugin_function`; a tool result reaches the model as `{"CallId":...,"Result":...}`; usage comes from the done line's `prompt_eval_count` and `eval_count`, and a done line without them is reported as zero tokens, where `/v1` reported none.
- **Tests:** `Providers/Ollama/OllamaContextLengthTests.cs` and `Providers/Ollama/OllamaApiStub.cs` are new; `OllamaHttpBoundaryFailureTests.cs` gains the failing calls through the gateway and the translator (a missing model said by name, a 429 or a 401 from a proxy, a 400 with and without the no-tools sentence, a 500, a reset, a timeout, a stream that breaks after its first text, a stream cancelled mid-answer, an error line inside a started answer); `OllamaLlmProviderFactoryValidationTests.cs` the bound. The Ollama fixtures of the gateway, guard, write gate, translation, usage and host turn tests answer in the native shape; `ArchitectureTests` gains `No_OllamaSharp_type_is_referenced_outside_the_ollama_provider_folder`.

## 2026-11-12 - Hugging Face chat on the OpenAI connector

- **Asked for:** stage 3 of the gateway migration, one provider per change; after Mistral, this change is Hugging Face's.
- **What the tests established first:** on the old connector, a chat request went to `<endpoint>/v1/chat/completions`, the endpoint being `https://api-inference.huggingface.co` or the configured one, joined with a `/` only when its path does not end in one, so a configured `https://hf.example.com/v1`, with or without a trailing slash, posted chat to `https://hf.example.com/v1/v1/chat/completions`; an embedding request went to `<endpoint>/pipeline/feature-extraction/<model>` with `{"inputs":["hello"]}` and read a bare `[[...]]` back; the key travelled as `Authorization: Bearer`. A turn was `{"model":...,"stream":true,"messages":[...],"temperature":1}` whatever the request asked, and a translation the same with `"stream":false`. A 401 was `LlmKeyRejectedException` without the key after one request, a 429 one request, a reset `HttpOperationException`, and a 500 on an embedding request `HttpOperationException` with its status after one request.
- **What changed:** `HuggingFaceLlmProviderFactory` registers chat on the OpenAI connector over an `OpenAIClient` whose endpoint is the `v1` path built by the old connector's rule, with the same options, validation messages, plain-http warning, public constructor and test seam; the four URL pins stayed green unedited. Embeddings stay on the HuggingFace connector, because the feature-extraction pipeline is not the OpenAI embeddings shape, so the `Microsoft.SemanticKernel.Connectors.HuggingFace` package stays and their pins stayed green unedited. On the wire Hugging Face now gets the turn's declared functions as `tools` with `tool_choice` `auto`, the turn's `temperature` and `max_completion_tokens`, the translation's 400 as `max_completion_tokens`, and `stream_options` asking for usage, which the OpenAI reader counts; it no longer gets `temperature` 1 or `stream` false. A 429 or a reset on chat is now retried three times by the client. A call to a declared write on this path is gated: with the filter unregistered the Hugging Face write gate fact fails with `_publishRan should be False but was True`. Not verified against a live Hugging Face endpoint: no key was available ([[pages/roadmap/followups]]).
- **Tests:** `Providers/HuggingFace/HuggingFaceProviderWireTests.cs` is new: the URL and key pins, the embedding request and its vector, a 401, a 429 after four requests, a reset after four attempts and a 500 on an embedding request after one. The HuggingFace rows of `ProviderRequestSettingsTests` now state the OpenAI connector's body. `WriteGateProviderPathTests.On_The_Hugging_Face_Path_The_Model_Is_Offered_No_Tools_So_A_Call_To_A_Declared_Write_Never_Runs_And_The_Gate_Is_Asked_Nothing` became `On_The_Hugging_Face_Path_A_Model_Initiated_Call_To_A_Declared_Write_Is_Gated_And_The_Model_Is_Told_It_Is_Queued`, and `ChatGatewayUsageTests.A_Hugging_Face_Answer_Streams_No_Usage_So_It_Counts_Nothing` became `A_Hugging_Face_Answer_Asks_For_Usage_On_The_Stream_And_Counts_The_Usage_Chunk`.

## 2026-11-12 - Mistral on the OpenAI connector

- **Asked for:** "having to use other SDKs stops centralising things; N SDK models means headaches". Stage 3 of the gateway migration moves providers off their own preview connectors onto the OpenAI connector Scout already uses for OpenAI and OpenRouter, one provider at a time; this change is Mistral's.
- **What the tests established first:** on the old connector, a chat request went to `https://api.mistral.ai/v1/chat/completions` and an embedding request to `/v1/embeddings`; a configured endpoint was the base those paths are appended to, with or without a trailing slash and with or without `/v1`; the key travelled as `Authorization: Bearer`. The embedding body was `{"model":"mistral-embed","input":["hello"],"encoding_format":"float"}`. A 401, a 429, a 500 or a reset was one request, thrown as `HttpOperationException`.
- **What changed:** `MistralLlmProviderFactory` registers chat and embeddings on the OpenAI connector over an `OpenAIClient` whose endpoint is `https://api.mistral.ai/v1` or the configured one, the OpenRouter factory's shape, with the same options, validation messages, plain-http warning, public constructor and test seam. The four URL pins stayed green. `MistralChatUsageReader` and the `Microsoft.SemanticKernel.Connectors.MistralAI` package are removed. On the wire Mistral now gets the turn's declared functions as `tools` with `tool_choice` `auto`, the turn's `temperature` and `max_completion_tokens`, the translation's 400 as `max_completion_tokens`, `stream_options` asking for usage, and on embeddings `encoding_format` `base64`; it no longer gets `safe_prompt`, `temperature` 0.7 or `top_p` 1. A 429, a 5xx or a reset is now retried three times by the client, as on OpenAI and OpenRouter. A call to a declared write on this path is gated: with the filter unregistered the Mistral write gate fact fails with `_publishRan should be False but was True`. Not verified against the live Mistral API: no key was available ([[pages/roadmap/followups]]).
- **Tests:** `Providers/Mistral/MistralProviderWireTests.cs` is new: the URL and key pins, the embedding request and its vector, a 401 as `LlmKeyRejectedException` without the key after one request, and a 429 as `LlmRateLimitException` after four. The Mistral rows of `ProviderRequestSettingsTests` now state the OpenAI connector's body; its two theories are renamed `..._Its_Connector_Sends` from `..._It_Sent_Before`, every other row unchanged. `WriteGateProviderPathTests.On_The_Mistral_Path_The_Model_Is_Offered_No_Tools_So_A_Call_To_A_Declared_Write_Never_Runs_And_The_Gate_Is_Asked_Nothing` became `On_The_Mistral_Path_A_Model_Initiated_Call_To_A_Declared_Write_Is_Gated_And_The_Model_Is_Told_It_Is_Queued`. `ChatGatewayUsageTests.A_Mistral_Answer_Counts_The_Usage_On_Its_Last_Chunk` is unchanged, its Mistral-shaped stream now read by the OpenAI reader.

## 2026-11-12 - The gateway names no connector type

- **Asked for:** finish moving connector types out of the gateway, so that it and the rest of `src/Scout.Llm` outside `Providers/` name none, and guarantee it breaks nothing. `ChatGateway.cs` still read the OpenAI SDK's `ClientResultException` to translate provider failures, the Responses API's streaming updates to read how a stream ended, and built `OpenAIPromptExecutionSettings`; `LiveTranslator.cs` built them too.
- **What the tests established first:** before any code moved, the request body every provider is sent was pinned over a recording handler under the real connector, composed through `AddScoutLlm`, for all ten providers with a model: a turn with a temperature, an output limit and a declared function, a turn with none, both on the direct and the agent path, and a live translation. Only the OpenAI connector (OpenAI, OpenRouter, Ollama), Azure OpenAI and Azure AI Inference send the turn's temperature and limit; Anthropic sends the limit and never a temperature; the ChatGPT plan neither; Gemini, Mistral and Hugging Face send neither of them, the translation's 400-token cap included, because they convert the OpenAI settings through the base type; on the agent path no provider gets them. The failure translation's unpinned branches were pinned too (a 429 naming an account refusal stays a rate limit, a 401 or a 404 naming one is a quota refusal, a failure with no status, unreadable bodies), and a Responses failure without a code named `unknown`.
- **What changed:** the translation moved unchanged to `ProviderFailures`, the reading of the stream's end to `ProviderStreamEnd` with its experimental-API suppression, and the settings to `ProviderSettings`, all in `src/Scout.Llm/Providers/`; the gateway, the live translator and `LlmFailures` call them. The settings stay the OpenAI connector's type: built as Semantic Kernel's base `PromptExecutionSettings` with the temperature and the limit as extension data, six pins went red, Gemini, Mistral and Hugging Face starting to receive the values (Gemini `generationConfig` `{"temperature":0.25,"maxOutputTokens":256}` where it had been `{}`), so that variant was not kept.
- **Tests:** `ArchitectureTests.The_Gateway_Names_No_Connector_Type_Outside_The_Provider_Folders`, renamed from the usage-only fact, now also fails on `ClientResultException`, a Responses streaming update, a connector settings type, `System.ClientModel`, a `Microsoft.SemanticKernel.Connectors.` namespace and the `OpenAI.` or `Azure.` SDK namespaces. The pins are `ProviderRequestSettingsTests`, `ProviderFailureTranslationTests` and `ProviderStreamEndTests`; every existing test passed before and after, two of them edited only to call `ProviderSettings.BuildSettings` instead of `ChatGateway.BuildSettings`.

## 2026-11-11 - The gateway reads no connector's usage type

- **Asked for:** for the usage count, the gateway should know only Scout types, and the change must break nothing. `StreamTrace` in `ChatGateway.cs` read four connector types to count tokens: the OpenAI SDK's `ChatTokenUsage`, Microsoft.Extensions.AI's `UsageContent`, the Mistral connector's `MistralUsage` and the Google connector's `GeminiMetadata`.
- **What the tests established first:** before any code moved, every branch of the usage code was mapped to a test that fails without it. Four branches had none, and were pinned on the untouched code: a Gemini stream whose last chunk carries no finish reason still counts its last running count when the answer is reported; a usage without a total counts the prompt plus the completion tokens, and no total when neither is known (the Anthropic client sets its own total, so no connector test reached that branch); the costs of the calls of an answer are summed and a call without a cost adds none; and an update with no metadata, no `Usage` key, a null `Usage` or a usage of a type no connector reports counts nothing.
- **What changed:** the reading moved, unchanged, into `src/Scout.Llm/Providers/`: one static reader per shape (`OpenAIChatUsageReader` with the OpenRouter cost, `UsageContentReader`, `MistralChatUsageReader`, `GeminiUsageReader` with the pending running count and its commit on a finish reason) and one entry point, `ProviderUsage.Count`, which `StreamTrace.Observe` calls once per update. Dispatch is still by the shape of the metadata, Gemini's first, then the `Usage` key, never by the provider's name. The sums and the pending count live in `UsageTally` beside the gateway, which holds only numbers. `ChatGateway.cs` names none of the four types; the finish reason, the failure codes, the error translation and `OpenAIPromptExecutionSettings` stay where they were.
- **Tests:** `ArchitectureTests.The_Gateway_Names_No_Connector_Usage_Type_Outside_The_Provider_Folders` scans `src/Scout.Llm` outside `Providers/` for the four names, and fails with the file and line when one is put back. The pinning tests in `ChatGatewayUsageTests` are `A_Gemini_Answer_Whose_Last_Chunk_Carries_No_Finish_Reason_Still_Counts_Its_Last_Running_UsageMetadata`, `A_Usage_Without_A_Total_Counts_The_Prompt_Plus_The_Completion_Tokens_And_No_Total_When_Neither_Is_Known`, `The_Costs_Of_The_Model_Calls_Of_An_Answer_Are_Summed_And_A_Call_Without_A_Cost_Adds_None` and `An_Update_Without_A_Usage_Of_A_Known_Shape_Counts_Nothing`. Every existing usage fact, and the Anthropic usage facts, passed unedited before and after the move. A reader that counted nothing failed the facts of its connectors.

## 2026-11-11 - A model the AI Source does not have is said as the model missing

- **Asked for:** with Ollama as the AI Source, a chat message sent while the local chat model was still downloading failed with `HTTP 404 (not_found_error) model 'qwen2.5:3b' not found`, and the chat got the generic mid-flight failure. The owner's rule from the credit fix applies: the chat does not answer with a generic error, it says what happened.
- **What the tests established:** a local Ollama answers a chat request for a model it does not have on its OpenAI-compatible `/v1` with `404 {"error":{"message":"model '<id>' not found","type":"not_found_error","param":null,"code":null}}` (read on 2026-11-11 with a model name that does not exist; nothing was downloaded); the streaming OpenAI connector raises it as `ClientResultException`, the non-streaming one as `HttpOperationException`. `GetModelId()` on the chat service names the model for every provider except Azure OpenAI, read through the read-only guard as well, because the guard hands on the inner service's attributes.
- **What changed:** `TranslateProviderFailure` maps a 404 whose error type is `not_found_error` or whose code is `model_not_found` (OpenAI's shape) to the new `LlmModelNotFoundException`, which names the model the call asked for and never the provider's text; the gateway's two stream loops and the live translator pass the chat service's model id, and `LlmFailures.Translate` takes it as an optional argument. A 404 of any other shape still propagates as before. The chat and quick ask say the model is missing ([[pages/history/conversation]]); the live translation and the audit too ([[pages/services/adapter-local]], [[pages/history/audit]]).
- **Tests:** `ChatGatewayRateLimitTests.A_404_For_A_Model_The_Provider_Does_Not_Have_Is_LlmModelNotFoundException_Naming_The_Model` (both shapes translated on both gateway paths through the real OpenAI connector; a plain-text 404, a 404 of another type and a 400 `not_found_error` not translated), `A_Model_Not_Found_Failure_Never_Carries_The_Providers_Text`, a 404 row in the `LlmFailures` theory, and `LiveTranslatorTests.A_404_For_A_Missing_Model_Is_LlmModelNotFoundException_With_The_Translation_Model`. `TranslationModelTests.A_Translation_Model_The_Provider_Rejects_Fails_The_Line_Without_Falling_Back_To_The_Chat_Model`, which expected the raw `HttpOperationException` for OpenAI's `model_not_found`, now expects `LlmModelNotFoundException` naming the translation model; its one-request assertion is unchanged.

## 2026-11-11 - Why the Claude API refused a request, and a credit balance refusal

- **Asked for:** with the Claude API as the AI Source every message, even "Hi", was answered "Scout could not answer that; see Scout logs.", and the log said only `HttpOperationException: The Anthropic API answered HTTP 400 (invalid_request_error).` The request body Scout sent was captured and well-formed, so the cause was on the account's side, and nothing said which. The owner then confirmed the cause: the Anthropic account's credit balance was too low; the other account-side hypothesis, a model refusing the organisation, was not it. The owner approved carrying the API's error sentence, which never holds the key, into the log, and telling a credit balance refusal as a billing refusal.
- **What the tests established:** the Claude API answers a credit balance too low as an HTTP 400 `invalid_request_error` whose `error.message` begins "Your credit balance is too low", not as a 429 or a 402, so the gateway's quota mapping, which reads 429 and 402 bodies in the OpenAI shape, treated it as a generic failure. `AnthropicChatClient` kept only the status and the error type, so the reason was lost before the log. The pump already logs a generic failure with its exception, and no sink renders the failure reason in the chat.
- **What changed:**
  - **The rule "never the response body", for the Anthropic provider:** the exception now carries the API's `error.message`, read through the client's `ApiMessage`, after the status and the type. The configured key is replaced by `[redacted]`, the whitespace is collapsed to one line, then the sentence is cut to 500 characters. The raw body is still never carried, and the chat reply never shows the sentence.
  - **The credit refusal:** a sentence that contains "credit balance", compared without regard to case, gives the exception the response content `{"error":{"code":"credit_balance_too_low"}}`; the gateway's `TranslateProviderFailure`, still the one mapping point, maps a 400 with that code to `LlmQuotaExceededException("credit_balance_too_low")`, so the chat, the live translator and an audit batch all get the quota refusal; in the chat and quick ask the pump says the credit ran out ([[pages/history/conversation]]). It is not reported to the usage sink, which hears only the ChatGPT plan's usage limit. The Anthropic client 13.6.0 has no `error.details.error_code` for this refusal (its typed codes include `enforced_spend_limit_reached` and `organization_on_hold`, not a credit balance), so the sentence is the only signal; "credit balance" is the two words that name the cause, kept short so a rewording of the rest of the sentence still matches.
  - **The other account refusals, same day:** the client also writes the API's `error.details.error_code` (the 13.6.0 client's string `ErrorCode`) and `error.type` into Scout's content, and the gateway maps any status it does not already map to `LlmQuotaExceededException` when that code or type is `enforced_spend_limit_reached`, `billing_frozen`, `organization_on_hold` or `billing_error`, by the API's own fields and never by wording. A 402 `billing_error` keeps `payment_required`; a details code outside the list stays a generic failure. The live translator and the audit say the credit ran out for `credit_balance_too_low` ([[pages/history/audit]], [[pages/services/adapter-local]]).
- **Tests:** `tests/Scout.Llm.Tests/Providers/Anthropic/AnthropicErrorReasonTests.cs` is new, with `A_Spend_Limit_A_Frozen_Billing_Or_An_Organisation_On_Hold_Is_A_Quota_Refusal` and `An_Unrelated_Details_Code_Stays_A_Generic_Failure`. In `AnthropicEmptyAnswerTests.cs` the two tests of a 400 for a prompt over the context window now expect the API's sentence with the key redacted; the first is renamed `A_400_For_A_Prompt_Over_The_Context_Window_Is_Sent_Once_And_Thrown_With_The_Apis_Sentence_Without_The_Key`. The 401 and 429 tests are unchanged and green.

## 2026-11-11 - A key sent over plain http is warned about

- **Asked for:** an automated audit found that AzureAIInference, AzureOpenAI, HuggingFace and Mistral accept an `http` endpoint for any host, so the provider key can travel in clear text to another machine. The owner decided to warn in the log and not to refuse the configuration.
- **What changed:** the four constructors call one shared check, `PlainHttpEndpoint.WarnIfKeyLeavesInClear`. For an `http` endpoint whose host is not `localhost`, `127.0.0.0/8` or `::1`, it logs one warning naming the provider, the scheme and the host. The provider is still built. Each constructor takes an optional logger, which the container fills, so the warning reaches the host log. OpenAI and OpenRouter accept `http` with a key on their own endpoint checks and do not warn.
- **Tests:** `tests/Scout.Llm.Tests/Providers/PlainHttpEndpointWarningTests.cs` covers the four providers with:
  - a non-loopback `http` endpoint, which gives exactly one warning;
  - a loopback `http` or an `https` endpoint, which gives none;
  - the warning's text and state, which never carry the key or the URL's user-info, port, path or query;
  - the warning in the host log through `AddScoutLlm`.

## 2026-11-11 - A Claude review that ended with no text, and the output limit

- **Asked for:** the owner asked Claude for a code review of a large pull request and got no answer. The worker logged `LLM response empty <- provider=Anthropic endpoint=unknown model=unknown (updates=157, finish=unknown, functionCalls=<seven reads>)`. The review never called `present_review_findings`.
- **What the tests established:** the tests ran the real Anthropic client over the recording handler, with no network.
  - A request that names no limit was sent the client's own default, `max_tokens: 1024`. A chat turn names `Scout:Conversation:MaxTokens`, 800 in the console host's `appsettings.json`, and the Claude call carries those 800, so the owner's review ran at 800 tokens per call.
  - The client reports the API's `stop_reason` on `ChatResponseUpdate.FinishReason`, but Semantic Kernel's bridge drops it, so every Anthropic stream logged `finish=unknown`.
  - The log line reproduces as a review that reads and then ends with no text. That happens when the last call is cut by the limit while the model thinks, which Claude Opus 5.5 always does and which counts against `max_tokens`. It also happens with `end_turn` and no text.
  - A cut in the middle of the `present_review_findings` call does not reproduce the line: the function's name would be in the list. The function loop answers the truncated call with an error result and asks the model again.
  - From the line alone, it cannot be decided which of the two endings happened. The first is the likelier one, given 800 tokens per call and a model that always thinks.
- **What changed:**
  - **The output limit:** the Anthropic client is built with an explicit default output limit, `Scout:Llm:Anthropic:Chat:MaxOutputTokens`, default 64,000. A request that names its own limit still wins: the live translator's 400, and a plain chat turn's 800. A turn whose skills declare functions now sends no limit ([[pages/history/conversation]]), and an audit batch never named one, so both get the 64,000.
  - **The stop reason is read:** `AnthropicChatClient` copies the API's `stop_reason` onto each `message_delta` update as `FinishReason`, which the gateway already reads. The log now names it, and the request label carries the Anthropic endpoint and model.
  - **No text is said in words:** an Anthropic stream that ends with no text throws `LlmNoAnswerException`, whose message is a sentence named by its stop reason, unless the turn holds an attached block such as the findings card. The pump completes the reply with that sentence.
  - **The function-call cap, corrected:** the page said 40. Semantic Kernel 1.82's `KernelFunctionInvokingChatClient` sets 128, then makes one last call without tools.
- **Tests:** `tests/Scout.Llm.Tests/Providers/Anthropic/AnthropicEmptyAnswerTests.cs`. The other paths are unchanged and their tests stay green.

## 2026-11-09 - ReadOutcome, a per-call signal for a read that did not return the content

- **Asked for:** Scout's own audit of this repository (issue "A failed file read is recorded as successful"): the audit counted a file as read when the GitHub plugin answered the read with a sentence instead of the file, and the audit must not read answer text to tell.
- **What changed:** `ReadOutcome` in `Scout.Llm.Abstractions`, shaped like `TurnAttachments`: a caller opens a scope around one function call, the read function marks it when its answer is not the content asked for, and the caller reads the mark before the scope ends. A mark stays in its own call: not the next call, not the call around it, not a call running at the same time; outside a scope it is dropped.
- **Tests:** `ReadOutcomeTests` (a mark made in the function reaches the scope around that call; of two calls at once only the one that marked is marked; a mark never reaches the call after it, the call around it or a caller outside any scope). Its users are covered on [[pages/history/audit]].

## 2026-10-22 - A provider without credit was reported as a connection error

- **Symptom:** with an OpenAI key whose account had no credit, a Discord user got an empty or partial reply ending in "(connection error)". The log showed `System.ClientModel.ClientResultException: HTTP 429 (insufficient_quota: credit_balance_exhausted)` raised from the OpenAI SDK, through Semantic Kernel's streaming chat call, into `ChatGateway.StreamChatAsync`, then `StreamPump stream failed mid-flight` and `Discord response failed`.
- **Root cause:** both stream loops in `ChatGateway` caught only Semantic Kernel's `HttpOperationException` with status 429. In Semantic Kernel 1.78 the OpenAI connector wraps errors in `HttpOperationException` on the non-streaming path only; an error raised while the stream is enumerated reaches the caller as the SDK's raw `ClientResultException`. No streaming 429 from OpenAI, or from Ollama and OpenRouter, which use the same connector, was ever recognised, so every one fell through to the pump's generic failure. The rate-limit test was green because it built an `HttpOperationException` by hand, which the real streaming path never throws.
- **What changed:** one helper in `ChatGateway`, used by both stream loops, maps a 429 from either exception type. A body carrying a billing code (`credit_balance_exhausted`, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, `organization_usage_limit_exceeded`) or the type `insufficient_quota` becomes the new `LlmQuotaExceededException` with the provider code; any other 429, or an unreadable body, becomes `LlmRateLimitException`. `StreamPump` finalises a quota refusal through `CompleteAsync` with `StreamPumpOptions.QuotaExceededMessage`, which tells the user the account has no credit or reached its spending limit and carries no retry advice, and logs one Warning with the provider code and no stack. The generic failure footer in the Discord and Slack sinks now reads "(the AI provider returned an error; see Scout logs)" instead of claiming a connection problem; Teams already said "(response interrupted)" and is unchanged.
- **Tests:** `ChatGatewayRateLimitTests` drives the real OpenAI connector through a stubbed `HttpMessageHandler` for the quota body (chat and agent paths), the throttling body, and the absence of the API key in the exception, plus a hand-made `HttpOperationException` carrying a quota body; `StreamPumpFailureTests.Quota_Exceeded_MidStream_Tells_The_User_The_Account_Has_No_Credit`; the footer assertions in `DiscordResponseSinkTests` and `SlackResponseSinkTests`.
- **Not changed:** a production client is built without a custom `HttpClient`, so the SDK's own retry policy still retries a quota 429 before it surfaces; the user sees the right message, a few seconds late. Retry policy is out of scope here.
- **Invariants:** [[pages/invariants/pluggable-boundaries]] holds for 429s; `ClientResultException` and `HttpOperationException` with that status are translated inside `Scout.Llm`, and the domain exception keeps the SDK one only as an `InnerException` typed `Exception`. Any other status still propagates as the raw SDK exception, as it did before. [[pages/invariants/secrets-never-in-source]] holds; the domain exception carries the provider code and never the key.
