# Skills - history

> Dated changes to [[pages/services/skills]]; the service page states how it works now.

## 2026-11-11 - A missing embedding model is said once, by name, without a stack

- **Asked for:** with Ollama as the AI Source and the embedding model not installed, the skill index build logged a stack trace and "running with no skills until a retry", which was false: since 2026-11-08 a failed build picks a skill by the words of the message.
- **What changed:** `SkillSelector.BuildIndexAsync` catches an `HttpRequestException` with status 404 before its generic catch, keeps the same one-minute retry gate, and logs once a Warning without the exception naming the embedding model (from the embedder's `EmbeddingGeneratorMetadata.DefaultModelId`, `unknown` when it reports none) and where to download it, Scout Desktop's AI Sources. The generic failure line now says skills are picked by the words of the message until the retry. A query embedding that gets the same 404, the model removed after the index was built, sets the query retry gate, picks by words and logs the same sentence under the same once-only flag. No other change to selection.
- **Tests:** `SkillSelectorTests.A_Missing_Embedding_Model_Is_Logged_Once_By_Name_With_The_Fix_And_No_Stack_And_Skills_Are_Picked_By_Words` (two 404 builds a minute apart, one Warning, the pick by words both times); `Repeated_Index_Failures_Log_The_Stack_Once_Then_Short_Lines` asserts the new first line; `A_Missing_Embedding_Model_On_A_Query_Is_Logged_Once_By_Name_Without_A_Stack_And_The_Pick_Is_By_Words` (the index built, two failing queries a minute apart, one Warning); `A_Failed_Index_Build_Picks_By_The_Words_Of_The_Message` green before and after. `FakeEmbeddingGenerator` gained `QueryFailure`, thrown on single-value batches only. `FakeEmbeddingGenerator` answers a settable `EmbeddingGeneratorMetadata`.

## 2026-11-11 - Four review criteria in code-review and code-audit

- **Asked for:** an audit of a repository answered 83 findings, 17 of them repeating an open issue and 11 reporting behaviour the project had recorded as deliberate, and neither skill named the shape of two real defects (a validation that could never run because the line before it already threw for that input). The owner asked for four review criteria in the two skills.
- **What changed:** both skills say a guard that cannot fire and an error reported as success are findings, that what the project records as intended is not (in the audit it goes in `known_json`), and, where they state their unchanged caps, that a finding not confirmed by reading the cited line is not reported and no findings is a valid answer. `code-audit` reads the open issues with `list_issues` when it is available and reports none of them again, putting them in `known_json` with the issue number; `GitHub.list_issues`, an existing read, joined its functions line. `code-review` rates defensive work that buys nothing a nit and an optimisation that removes an unnamed guarantee blocking. Each sentence was appended to the line already on that subject, so no line of either file moved. The audit job's batches are not offered `list_issues`; [[pages/roadmap/followups]] carries it.
- **Tests:** in `BundledSkillsTests`, one test per criterion asserting the phrase inside its section, a row per skill where both carry it, each red before the text and red again with its sentence removed.
- **Invariants:** [[pages/invariants/no-executive-writes]] holds; one existing read made callable from `code-audit`, no write added ([[pages/decisions/0054-functions-scoped-per-skill-and-job]]).

## 2026-11-10 - The review walks the owner's ten steps; naming the audit keeps it in a review conversation

- **Asked for:** the owner's ten steps of a code review, in order, with what the skill did not carry yet ([[pages/architecture/code-review-flow]]); and the regression the structural rule introduced: in a conversation carrying `code-review`, "para a auditoria do acme/shop", "pause the audit" or "continua a auditoria" lost the audit's stop, pause and start functions.
- **What changed:** the router keeps `code-audit` in a review when the message names the audit (audit, auditoria, audita and their forms) or asks for the whole repository (`SkillSelector.AsksForAnAudit`, replacing the whole-repository-only predicate of the same day). `code-review`'s body is rewritten as the ten steps, keeping every rule and call it had and adding the linked issue through `get_issue` (now on its functions line), the split remark, the edge cases and event-driven delivery, the search for existing code, magic numbers and the six-month question, error-path and behaviour-first tests, performance, "Done well" in the summary with praise never a finding, and a review asked again after new commits; marking a conversation resolved is stated as something Scout cannot do. 85 lines and 13,342 characters became 102 and 15,513.
- **Tests:** in `LlmStreamingRouterFunctionScopeTests`, the audit-naming follow-ups in both languages and two more review follow-ups; in `HostReviewTurnTests`, the same on the composed host with the audit's controls offered; in `BundledSkillsTests`, one row per added item and the order of the ten steps with the kept rules, red before the rewrite.
- **Invariants:** [[pages/invariants/review-writes-on-its-pull-request]] v1.1; no write added.

## 2026-11-10 - A review writes on its pull request, an audit opens issues, by structure

- **Asked for:** the owner's rule, that a requested code review always adds comments on the pull request and never opens issues, and that an analysis of a repository may open issues, held so that a routing mistake or a later edit cannot break it.
- **Found:** a review turn was already offered no `create_issue` or audit function, and `load_skill` already never widened a turn (the per-turn kernel is built from the request before the call). Two holes remained: a follow-up in a review conversation whose words scored `code-audit` ("look for security bugs too") replaced the carried review with the audit and its `create_issue`; and with more than one skill selected the review and the audit could run together. `code-review` also declared `comment_on_issue`, which accepted any number, while `comment_on_pull_request` already posts on the pull request's conversation.
- **What changed:** the router drops `code-audit` from a turn whose selected or carried skills hold `code-review` unless the message's own text asks for the whole repository (`SkillSelector.AsksForTheWholeRepository`, the same words as the routing fix), keeping the carried review when nothing else is left; `comment_on_issue` left `code-review`'s functions line and body. No write gate refusal was built: the turn's skills are not known at the write gate, and `create_issue` is not on a review turn's kernel at all.
- **Tests:** in `BundledSkillsTests`, the rule over the bundled files (review: pull request writes and no issue or audit function; audit: no pull request write; the `create_issue` allow-list; the review's comment through `comment_on_pull_request`); in `LlmStreamingRouterFunctionScopeTests`, the follow-ups, the two skills together, the whole-repository follow-up and the `Issues to open` marker; `HostReviewTurnTests` end to end on the Ollama connector.
- **Invariants:** new [[pages/invariants/review-writes-on-its-pull-request]]; [[pages/invariants/no-executive-writes]] holds, one write path narrowed and none added.

## 2026-11-10 - A code review of a pull request is a review, never an audit

- **Asked for:** the owner, as critical: asking for a code review opened issues in the repository; Scout should tell a review and an audit apart.
- **Root cause:** on the words path, a message that named a pull request and also said what to look for ("bugs", "segurança", "security problems", "performance") scored highest for `code-audit`, because its description carries exactly those words, rare among the skills and so heavily weighted, and carried "with or without a pull request"; its turn was offered `start_repository_audit` and `create_issue`. "analisa o PR 5" split its weight between the two skills and picked none. With embeddings nothing deterministic decided either: the cosine of the message against each description, where the audit's description is the nearer one to a request full of the audit's vocabulary. Taking the audit out of the candidates alone did not hold: some of those messages then picked no skill, and "review acme/shop#5 for performance issues" picked `github-issues`, the other skill that offers `create_issue`.
- **What changed:** `LexicalSkillIndex.ReviewOrAudit` decides a message that names a pull request before any score, and `SkillSelector` calls it on both paths, before the query is embedded: explicit whole-repository words make it `code-audit`; otherwise a review or analysis verb makes it `code-review`; either way the audit is not picked by its score. `code-audit`'s description says "never a pull request the user names" and its body's first rule hands a named pull request to `code-review`; `code-review`'s body says a review never opens an issue, and that with no pull request named it asks which one or lists the open ones.
- **Tests:** in `LexicalSkillIndexTests`, the review rows (every form of naming a pull request with each thing to look for, in English and Portuguese), the ambiguous rows and the rows without a review verb; the existing audit and none rows held before and after. In `SkillSelectorTests`, the embeddings path with the message's vector nearest the audit. In `BundledSkillsTests`, the two skill texts, and the catalog summary of `code-audit` changed with its description.
- **Invariants:** [[pages/invariants/no-executive-writes]] holds: no function or write added; the selector stays provider-agnostic ([[pages/invariants/pluggable-boundaries]]).

## 2026-11-08 - A skill declares the functions its turn may call

- **Asked for:** phase S2 of [[pages/roadmap/security-hardening]]: the model offered only the functions the current skill needs ([[pages/decisions/0054-functions-scoped-per-skill-and-job]]).
- **What changed:** the loader reads an optional `functions: Plugin.function, ...` frontmatter line into `Skill.Functions`, dropping a badly shaped entry with a Warning; the selector picks a skill that declares functions by the words of the message (`LexicalSkillIndex`) when embeddings are absent or fail, and its information line says so; `code-review`, `code-audit`, `project-improvements` and `project-vault` declare their functions, `code-audit` gains the section that starts, stops and reports the audit job and the phrases for them, and `github-issues` and `youtube-operator` are new.
- **Tests:** `SkillFileLoaderTests` (the line, no line, a bad entry), `LexicalSkillIndexTests` (sample questions in English and Portuguese, folding, the "Not for" cut, a skill without functions left to the model), four `SkillSelectorTests` for the fallback and its one-minute skip after a failed query embedding, five `BundledSkillsTests` for the skills that act; the information line's text in `No_Embeddings_Selects_Nothing_Puts_The_Catalog_In_The_Prompt_With_One_Information_Line_And_No_Retry` changed with it.

## 2026-10-22 - a failed skill index build is no longer cached until restart

- **What changed:** `SkillSelector` built its index through a `Lazy<Task<...>>` whose build caught every exception and returned an empty list, so one failed embeddings call (the owner hit a provider 429) turned skills off until the worker restarted, even after the provider recovered. The `Lazy` is replaced by a cached `Task` behind a lock: a successful build, including an empty one when no skill files exist, is cached as before; a build that throws is not, and the next attempt waits `IndexRetryInterval` (one minute, a fixed constant) on a `TimeProvider` the constructor takes as an optional parameter, defaulting to the system clock, so the DI registration is unchanged.
- **Behaviour:** the message whose build fails still gets no skills and no exception. Later messages within the interval get no skills without an embeddings call; the first message after it builds again. Concurrent first callers still share one build.
- **Tests:** `A_Failed_Index_Build_Is_Retried_After_The_Interval`, `A_Failed_Index_Build_Is_Not_Retried_Before_The_Interval` and `Concurrent_First_Calls_Build_The_Index_Once` are new in `tests/Scout.Skills.Tests/SkillSelectorTests.cs`; `SelectAsync_Builds_Index_Once_Across_Calls` holds the success cache. The test project now references `Microsoft.Extensions.TimeProvider.Testing`.
- **Not changed:** the retry interval is not configurable; it moves to `SkillsOptions` if an operator needs to tune it.
- **Invariants:** [[pages/invariants/no-executive-writes]] holds; the retry repeats the same read-only embeddings call.
