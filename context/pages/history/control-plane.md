# ControlPlane - history

> Dated changes to [[pages/services/control-plane]]; the service page states how it works now.

## 2026-11-11 - Approve together, phase 1, review round 1: a card's issue is keyed on its own, a reported group stays closed

- **Asked for:** the ten findings of the first review of phase 1 of [[pages/roadmap/approve-together]], each reproduced by a failing test before it was fixed, with the manager's decisions.
- **What changed:**
  - A card's title and body are trimmed once, then checked, stored, summarised, keyed and sent as trimmed: a body of ten characters and 300,000 spaces used to pass the check and fail the queue's payload bound with an error the desktop read as Unknown, and other padding was another key (`A_Padded_Title_And_Body_Are_Trimmed_Once_Then_Validated_Stored_Summarised_And_Keyed_As_Trimmed`).
  - The repository name rule ends in `\z`, in `CardIssuesService` and in the GitHub plugin's `GitHubNames`: `$` also matched before a trailing newline, so `acme/shop` followed by a newline passed (`Each_Refusal_Fires_On_Its_Own_Input_And_Queues_And_Logs_Nothing`, `A_Repository_Name_Is_Letters_Digits_Dots_Hyphens_Or_Underscores`).
  - A worker's write request with an empty or whitespace group id or repository is queued as one without the field, never in a group no set call can name (`A_Blank_Group_Id_And_Repository_Are_Treated_As_Absent_So_The_Action_Is_Queued_In_No_Group`).
  - A group with the worker's report is closed unless an action was asked after the report, whatever quiet spells came before; the quiet spell closes only a group without a report. A write, an eleven-minute step, a second write and the report used to read as changed for ever (the rows of `A_Group_State_Follows_Its_Rows_And_The_Clock`).
  - The pending list reads a group's state only for a group that holds a waiting action (behaviour lock: the same table, green before and after).
  - A repeated Approve set over actions already approved or executing still checks each listed digest, answering a changed one with `ChangedAfterListing` and decided false; an executed action, whose payload was cut, is answered as it stands; a repeat still needs no grant. Decided means the decision was applied, not that a send succeeded (`A_Repeated_Approve_Set_Checks_The_Digest_Of_Each_Listed_Action_Whose_Payload_Is_Whole_And_Answers_Each_Row_With_Its_Outcome`, `A_Repeated_Approve_Set_Needs_No_Grant_Because_It_Approves_Nothing`).
  - Card clicks run one at a time: a second click that arrived while the first was still logging its approvals answered them as not in the write log (`A_Second_Click_While_The_First_Is_Still_Logging_Its_Approvals_Waits_And_Answers_The_First_Click_s_Rows`).
  - The card key is per issue: the card's id and the digest of the issue's repository and trimmed title and body, on its row. `IActionQueue.EnqueueApprovedSetOnceAsync` became `EnqueueApprovedOnceEachAsync`. A later click answers an issue whose row is waiting, approved, being sent, sent or not confirmed, and queues again, approved in a new group, only an issue whose rows all failed or were rejected. Before, ten issues with one 502 could never retry the failed one from the card, and the same card with one finding edited reopened the issues already sent (`A_Second_Click_Queues_Again_Exactly_The_Issues_That_Failed_Or_Were_Rejected_And_Answers_The_Others`, `The_Same_Card_Clicked_Again_With_One_Finding_Edited_And_Then_With_One_Removed_Never_Opens_An_Issue_Already_Queued_Again`; through the real executor, `Ten_Card_Issues_With_One_Answered_502_A_Second_Click_Sends_Only_The_Failed_One_And_A_Third_Sends_Nothing`).
  - One place each: the card's bound is `ActionDecisionService.MaxGroupSize` (`CardIssuesService.MaxIssues` removed), and both services build an approval entry with `ApprovalOf` and check the log with `ApprovalsNotInLogAsync` (behaviour lock: the control-plane and executor tests, green before and after).
- **Rows written by the set-level key** (unreleased, no migration): a row whose text is still whole, waiting, approved or executing, is recognised by its card id and its text and answered (`A_Row_Keyed_By_The_Whole_Set_Is_Answered_While_Its_Text_Is_Whole_And_A_Click_Over_Such_Rows_Never_Throws`). An executed row lost its text and cannot be recognised, so a click over it queues that issue again. Nothing throws.
- **Not changed:** the worker, the desktop, the claim, the executor, the store.
- **Round 2 of the review** (same day, two findings, each reproduced by a failing test first):
  - A card issue that a worker claimed and may have sent, whose claim then lapsed across a revoke or a new grant, is rejected by the claim path with `WriteGateService.NotConfirmed` ("may already be on GitHub"), not recorded `failed: not confirmed`; round 1 treated every rejected row as retryable, so a later click queued it again and the executor sent it a second time. Such a row now answers the click, recognised by `WriteGateService.IsNotConfirmed`, built from the same two parts as the sentence whatever feature name the claim path puts between them; a row rejected before any send, for writes revoked before a claim or before the send, for an approval not in the log or for any other reason, is still queued again (`An_Issue_Whose_Claim_Lapsed_Across_A_Re_Grant_Is_Rejected_As_Maybe_On_GitHub_And_A_Later_Click_Answers_It_And_Never_Queues_It_Again`, new rows of `A_Second_Click_Queues_Again_Exactly_The_Issues_That_Failed_Or_Were_Rejected_And_Answers_The_Others`; through the real executor, `A_Card_Issue_Sent_By_A_Worker_That_Stopped_Before_Recording_It_Across_A_Re_Grant_Is_Never_Sent_Again_By_A_Later_Click`).
  - `ApproveCardIssues` answered the group of the row with the latest request time, untested on the wire and open to a tie or a clock step. The card's answer now carries the group the click queued its issues in, or the first row's when it queued none, as `ActionSetDecision.GroupId` (`A_Card_Click_That_Queues_A_Failed_Issue_Again_Answers_The_New_Group_And_Each_Row_Carries_Its_Own_Group`).
  - Two follow-ups recorded: the trailing-newline hole in six other name rules, and the verdict card's once-only enqueue that still queues a not-confirmed verdict again ([[pages/roadmap/followups]]).

## 2026-11-11 - Approve together, phase 1, commit C: the findings card's issues, the full text of one action, a ten-minute quiet close

- **Asked for:** the last of three commits of phase 1 of [[pages/roadmap/approve-together]]: the findings card's Open issues as the only approval of its issues (the owner's answer 3), and the decisions the manager took on commit B's open questions, within the owner's answer 1 ("listed, with the full text one click away, is enough").
- **What changed:**
  - `CardIssuesService` and `Features.ApproveCardIssues`, desktop token only: the card's issues are queued already approved on the declared `New issues` row, target `GitHubActions.create_issue`, with the payload and summary a chat request for the same issue queues, in one new group closed at once, one `approved` entry each; at most 50, refused whole; the GitHub plugin's own title and body bounds; the grant needed (`A_Card_s_Issues_Are_Queued_Approved_Logged_Once_Each_And_A_Second_Click_Answers_The_Same`, `Each_Refusal_Fires_On_Its_Own_Input_And_Queues_And_Logs_Nothing`).
  - `PendingAction.CardKey`, the card's id and the digest of its set, kept on the row when it is executed and its payload cut, and `IActionQueue.EnqueueApprovedSetOnceAsync`, `EnqueueApprovedOnceAsync` for a set: a second click answers the same actions; the same card queues again only once every issue failed or was rejected (`The_Same_Card_Queues_Again_Only_Once_Every_Issue_Failed_Or_Was_Rejected`); through the real executor an issue opens once across two clicks (`A_Card_s_Issue_At_The_Plugin_s_Bounds_Opens_Exactly_Once_Across_Two_Clicks`). A log that fails part way rejects what the click queued (`A_Log_Failing_Part_Way_Rejects_What_The_Click_Queued_And_The_Next_Click_Queues_Them_Again`), and a repeat never answers an issue without its approval in the log as approved (`A_Repeat_Click_Names_An_Issue_Whose_Approval_The_Log_Never_Took_And_Never_Answers_The_Set_As_Approved`).
  - `MaxListedBodyLength` 65,000 to 4,000: the list and the group call carry a preview (`ListActions_Of_500_Waiting_Actions_With_The_Largest_Payload_The_Queue_Takes_Fits_The_Desktop_Receive_Limit_With_A_Preview_Of_Each_Text`, replacing the fifty-action list test), and `Features.GetActionText` answers one action's full title and body with its digest (`Get_Action_Text_Answers_The_Full_Text_And_The_Listed_Digest_Of_An_Action_Until_It_Is_Executed`). This supersedes commit B's "Not done" on the cut text: the full text is reachable in one call, and an Approve set of a cut action is a pinned decision (`A_Set_Approves_An_Action_Whose_Listed_Text_Was_Only_A_Preview_Without_Every_Text_Being_Opened`).
  - `GroupQuietClose` two minutes to ten, the boundary rows of `A_Group_State_Follows_Its_Rows_And_The_Clock` moved to ten minutes.
  - From the branch's performance review: the preview alone did not bound the list, since 1,315 waiting actions of three-byte text at the largest preview passed 16 MiB and failed the whole call with `ResourceExhausted`. `ListPendingActions` and `GetActionGroup` now add listed text only while one answer's text stays within `FeatureMapping.MaxListedTextBytes`, 8 MiB; the rows past it are listed without their title and body and with `text_clipped` (`ListActions_Of_More_Waiting_Actions_Than_Their_Previews_Fit_Lists_Every_One_Within_The_Desktop_Receive_Limit_And_A_Row_Without_Its_Preview_Says_So_And_Is_Still_Decided`, `Get_Action_Group_Of_More_Actions_Than_Their_Previews_Fit_Returns_Every_One_Within_The_Desktop_Receive_Limit_And_A_Row_Without_Its_Preview_Says_So`). `PendingAction.PayloadDigest()` hashes from a pooled buffer instead of a new byte array per row per poll, with the digest unchanged (`The_Digest_Is_The_SHA256_Of_The_Payload_s_UTF8_Bytes_In_Lowercase_Hex`, with an empty and a multi-byte payload).
- **Why the preview:** `ListPendingActions` has no bound on the number of rows; at 65,000 characters about 85 waiting actions of three-byte text already passed the desktop's 16 MiB receive limit, which would have left the owner unable to list or decide anything (`ResourceExhausted` at 500 actions before the change).
- **Why 8 MiB:** half the 16 MiB message limit, so the other fields of every row have the other half; above the 6.4 MB of preview the 500-action list test carries, so that list still carries every text. The other fields are not bounded by it, and paging is left as a follow-up ([[pages/roadmap/followups]]).
- **Why ten minutes:** no turn time limit exists to anchor it; once phase 2's worker reports each turn's end, the quiet close covers only a worker that stopped mid-turn, and a slow local model may pause several minutes between two queued calls; single decisions and Reject all are offered meanwhile.
- **Not changed:** the worker, the claim, the lease, the pacing and the executor; the `New issues` catalog text, which still says "ask for it in chat" (phase 3).

## 2026-11-11 - Approve together, phase 1, commit B: a set is decided

- **Asked for:** the second of three commits of phase 1 of [[pages/roadmap/approve-together]]: the owner's Approve all and Reject all on the actions one request queued, bound to the ids and digests the desktop listed, and the read of one group with its text.
- **What changed:**
  - `ActionDecisionService.ApproveSetAsync` and `RejectSetAsync` decide a set under the queue's gate through the new `IActionQueue.DecideSetAsync`, one read and one write for the whole set. The state x decision table, eight states by Approve set, Reject set, the single Approve and the single Reject, pins the rows and the write-log entries of every cell (`A_Set_Or_Single_Decision_Leaves_The_Rows_And_Entries_Of_Its_Cell`, 32 rows); a changed digest approves none and names that id (`A_Payload_Changed_After_The_Listing_Approves_None_And_Answers_That_Id`); an action that joined after the listing stays pending (`An_Action_Added_After_The_Listing_Stays_Pending`); an open group refuses Approve set, a closed one takes it, a changed one takes only Reject set, as the owner answered (`An_Open_Group_Refuses_Approve_Set_A_Closed_One_Accepts_A_Changed_One_Only_Rejects`); 51 ids are refused whole for both decisions (`Fifty_One_Ids_Are_Refused_Whole_And_Nothing_Is_Logged`); a second identical call answers the same and appends nothing (`A_Second_Identical_Approve_Set_Answers_The_Same_And_Appends_Nothing`).
  - `Features.ApproveSet`, `RejectSet` and `GetActionGroup`, desktop token only (`The_Worker_Token_May_Not_Decide_Or_Read_A_Set`); `PendingAction.text_clipped` says the listed title or body was cut, on the list and on the group call (`Get_Action_Group_Returns_The_Group_s_Rows_In_Every_Status_With_Their_Text_And_Says_When_A_Text_Was_Cut`).
  - The single approval's entry, the worker's record and the verdict card's rejection of a waiting chat verdict carry the action's group id, so History can group them (`The_Owner_s_Single_Approval_Of_An_Action_Queued_In_A_Request_Is_Logged_With_That_Request_s_Group`, `The_Owner_s_Approval_And_The_Worker_s_Record_Of_An_Action_Queued_In_A_Request_Carry_That_Request_s_Group`, `A_Chat_Verdict_A_Card_Click_Replaces_Is_Logged_As_Rejected_With_The_Group_Of_The_Request_That_Asked_It`).
  - `ListPendingAsync` reads the queue once through the new `IActionQueue.ListWhereAsync`; it read it twice and threw `KeyNotFoundException` when the file changed between the reads (`A_Queue_File_That_Changes_Between_Two_Reads_Still_Lists_The_Waiting_Action_With_Its_Group_State`).
- **Why a log that fails part way is answered as a mismatch:** the queue holds the whole set approved before the first entry is appended, so a retry that answered "decided" for rows with no approval entry would read as approved actions the claim then rejects after the one-minute window; the retry names those rows with the claim's own reason instead (`An_Approval_Log_Failing_Part_Way_Hands_Out_The_Logged_And_Rejects_The_Rest_After_The_Window`).
- **Not done:** the group call does not serve the text past the bound commit A named it for: fifty full payloads do not fit the 16 MiB message, so `GetActionGroup` carries the same cut text as the list and `text_clipped`; an Approve set still approves a cut action, an open question on [[pages/invariants/no-executive-writes]].
- **Not changed:** the claim, the lease, the one second between two sends and the executor; ten actions approved as one set are still sent one by one, at most once each (`A_Worker_That_Stops_Before_Recording_The_Third_Of_Ten_Leaves_Seven_Sent_One_Not_Confirmed_None_Twice`, `The_Fifth_Of_Ten_Answered_502_Fails_Alone_And_The_Rest_Go_One_Second_Apart`, `A_Revoke_Mid_Set_Rejects_The_Unsent_And_Keeps_The_Sent`). `GroupQuietClose` stays at two minutes: the plan asked to set it just above the worker's turn time limit, and the conversation turn has none by default (`StreamPumpOptions.OverallTimeout` is null and no configuration binds it; only a Teams reply is capped, at 120 seconds, and the audit's ten-minute batch turn cannot queue a write).

## 2026-11-11 - Approve together, phase 1, commit A: groups exist and are listed

- **Asked for:** the first of three commits of phase 1 of [[pages/roadmap/approve-together]]: a group of actions one request queued exists in the control plane and the desktop's list shows it, with nothing yet deciding a set.
- **What changed:**
  - `PendingAction` gained `GroupId`, `Repository` and `GroupClosedAt`; `WriteLogEntry` gained `GroupId`, which a rejection copies from its action. Old `actions.json` rows and `writes.log` lines read unchanged (`An_Actions_File_Written_Before_Groups_Existed_Still_Reads_Every_Row`, `A_Write_Log_Line_Written_Before_Groups_Existed_Still_Reads`, green before and after).
  - The worker's `RequestWrite` carries `group_id` and `repository`, queued as sent and never read from the payload (`A_Request_With_A_Group_And_A_Repository_Queues_The_Action_In_The_Request_Group_Never_One_The_Payload_Names`); the new `WorkerGate.CloseWriteGroup` stamps the group's actions, keeps the first stamp and answers how many actions the group holds, a blank id answering `InvalidArgument` (`Closing_A_Group_Stamps_Every_Action_Of_That_Group_Id_Only_Keeps_The_First_Stamp_And_Decides_None`, `RequestWrite_Queues_The_Action_In_Its_Group_And_CloseWriteGroup_Closes_The_Group_Without_Deciding_Any_Action`); the desktop token is refused (`The_Desktop_Token_Cannot_Close_A_Group_And_The_Group_Stays_Open`), and a queue that cannot be written fails the worker's call and leaves the group open (`A_Close_The_Queue_Cannot_Write_Fails_The_Worker_Call_And_Leaves_The_Group_Open`).
  - `ListPendingActions` gives every action its group and repository and a waiting one its payload's title and body, the payload's SHA-256 digest and its group's state, derived by `ActionDecisionService.GroupStateOf` (`A_Group_State_Follows_Its_Rows_And_The_Clock`, fifteen rows).
- **Why the text is cut:** fifty waiting actions with the largest payload the queue takes, in three-byte UTF-8 text, made an answer of about 30 MB, which the host refused to send (`ResourceExhausted`, over its 16 MiB limit); the title is cut to 256 characters and the body to 65,000 (`ListActions_Of_50_Waiting_Actions_With_The_Largest_Payload_The_Queue_Takes_Fits_The_Desktop_Receive_Limit_With_The_Text_Cut_To_Its_Bound`). The full text is for commit B's group call.
- **Why a quiet spell counts as a close between two actions:** with only "the newest action is two minutes old" a late action made the newest fresh again and a closed group went back to open; taking the close as the first spell longer than two minutes keeps a group that changed after its close `changed`.

## 2026-11-11 - A project deletion and an approval of its actions no longer overlap

- **Asked for:** the automated audit's finding "Project deletion races with action approval", filed earlier the same day in [[pages/roadmap/followups]] (see "Not changed" in the entry below).
- **What changed:** `OperatorService` holds one operator-wide `SemaphoreSlim`. The deletion takes it before its open-actions read and keeps it to its end; the publish, the experiment start and the adopted winner take it before their project save and keep it to the end of their queueing, the restore of a failed queueing included. Whichever runs first, the other then sees its result: an open action refuses the deletion, a deleted project refuses the approval as not found. Nothing awaited under the gate takes it again, and the wait honours the caller's token. `OperatorService` is now `IDisposable`, releasing the gate, as the other control-plane services that own one are. The comment approvals queue actions that name no project and stay outside it. The follow-up entry is closed.
- **Tests:** `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.DeletionRace.cs`: for the publish, the experiment start and the adopted winner, a delete parked at the action queue between its open-actions read and its removal while the approval runs, and an approval parked between its save and its queueing while a delete runs. Each of the six reproduced the race before the change (the delete went through and an approved action stayed on the deleted project). A delete cancelled while it waits leaves the project, its folder and the write log as they were. The `Delete_` tests are unchanged and green before and after.

## 2026-11-11 - Findings from the second automated audit

- **Asked for:** fix the findings of an automated audit over `main` that a triage judged real in `Scout.ControlPlane`, each only after a test failed on the claimed scenario, and report the ones that did not reproduce.
- **What changed:**
  - The write log lists N entries that parse. It parses each line during the tail read, so a malformed line no longer takes one of the N places and the older entries behind it are listed (`Malformed_Log_Lines_Do_Not_Consume_The_Requested_Entry_Limit`); the existing tail-read test had pinned the old count and now expects the third entry.
  - `actions.json` and `features.json` holding the JSON literal `null` are moved aside and logged like a file that does not parse, instead of being read as empty and overwritten by the next write (`A_Queue_File_Holding_Null_Is_Moved_Aside_Like_A_Corrupt_One_And_Never_Overwritten`, `A_State_File_Holding_Null_Is_Moved_Aside_Like_A_Malformed_One_And_A_Later_Set_Never_Overwrites_It`). The same holds for `controls.json`, `local-runtimes.json` and the operator's four files, which share one read, each moved aside by its own malformed-file path (`A_Control_File_Holding_Null_Is_Moved_Aside_Like_A_Malformed_One_And_The_Queue_Starts_Empty`, `A_Config_File_Holding_Null_Is_Moved_Aside_Like_A_Malformed_One_And_A_Later_Set_Never_Overwrites_It`, `A_Projects_File_Holding_Null_Is_Moved_Aside_Like_A_Malformed_One_And_The_Store_Starts_Empty`).
  - A model pull whose 200 stream carries an `error` line fails with "Ollama /api/pull failed: <error>" instead of ending as done (`A_Pull_Stream_Error_Line_Fails_The_Pull_With_That_Error_Text`, the failing-call test of that boundary).
  - On Unix the `ollama` binary is the first file on `PATH` with an execute bit; Windows is unchanged (`A_File_On_Path_Without_An_Execute_Bit_Is_Not_Reported_As_The_Binary`, over `PathBinaryLocator.Find`, which takes the `PATH` value so the test does not change the process environment).
  - A start marks the Ollama readiness probe ready only when its status reports Ollama running and failed otherwise; a start on a machine without Ollama, or whose daemon stops answering, no longer reads as ready (`A_Start_That_Does_Not_Report_Ollama_Running_Does_Not_Mark_It_Ready`). The probe stays failed, which releases anyone waiting on it at once, and a failed probe is no longer final: a status read then checks the binary and the daemon instead of answering "Local runtime did not become ready", and a model operation asks the daemon directly as before any start, so an Ollama installed or started afterwards is seen without another start (`After_A_Start_That_Did_Not_Get_Ollama_Running_Status_And_Models_See_An_Ollama_Started_Later`). A reset to the unknown state was not used: a status read in that state still waits for the probe and answers the same stub, so it would have unblocked the model operations only.
  - A record of an approved action must name the action's own target; one naming another target is refused, logs nothing and leaves the action approved (`RecordWrite_With_An_Approved_Action_Of_Another_Target_Fails_And_Leaves_It_Approved`). Every worker path that records with an action id already sends the target the claim handed it (the GitHub executor and the YouTube action executor), so what the worker sends is unchanged.
  - A verdict card whose comments are `[null]` is refused as invalid comments instead of failing with a null reference (`A_Null_Comment_Is_Refused_As_An_Invalid_Comment_Before_Anything_Is_Queued`).
  - The YouTube disconnect purge also drops a pending comment sync request (`Delete_credentials_purge_drops_a_pending_sync_request`).
  - A project deletion whose `deleted project` entry cannot be appended puts the project back and leaves its media folder, so a local delete is never left without its record (`Delete_WhoseRecordCannotBeLogged_LeavesTheProjectAndItsMediaFolder`).
- **Not changed:**
  - Duplicate scene ids in a worker save are already refused before the scene merge, by the scene validation, as "Scene ids must be unique within a project."; the claimed crash in the merge is not reachable through the worker save.
  - The worker may still drop or rewrite an idea that is `proposed`; the comment rules protect only ideas the owner decided, as [[pages/services/control-plane]] states under the worker's comment saves.
  - The open-actions check of a project deletion and its removal share no lock, so an approval that lands between them can leave an approved action on a deleted project. It reproduces only by interleaving the two calls; a fix needs one lock over the deletion's check and removal and the approve paths' save and queueing, which no existing gate covers. Filed in [[pages/roadmap/followups]].

## 2026-11-10 - The owner's controls on a running job

- **Asked for:** Pause, Continue and Stop in Scout Desktop on a running audit, and Stop on a running test run, reaching the worker only through the control plane, each click the owner's own decision.
- **What changed:** `OwnerControlService` over `IOwnerControlQueue` (`controls.json`), the desktop's `Features.ControlJob` and the worker's `WorkerGate.NextJobControl` and `SettleJobControl`. A click is checked before it is queued, taken by the worker once with no lease, dropped and recorded as not applied after two minutes, and settled once into the write log as the owner's, with the worker's sentence.
- **Why not the action queue:** an approved action shows in Approvals while no worker has claimed it, a revoked grant rejects it, and a claim needs the approval's entry in the write log; a control is none of these, it is the owner's decision itself.
- **Once only, and never missing from the log:** a control is taken with no lease, so it is never applied twice; one taken and not settled within two minutes, whose reply was lost or whose worker stopped between the take and the settle, is recorded as `Not confirmed: …` on the next take or request, so the owner sees it was taken and looks at the job before clicking again.
- **Tests:** `OwnerControlServiceTests.cs` (validation, once only, a restart, the age limit, the record, a taken control never settled recorded as not confirmed, a store that cannot keep it), `JobControlGrpcTests.cs` over the real socket, the method rows in `TokenAuthInterceptorTests.cs`, and the worker method list pinned in `OperatorGrpcTests.cs` now naming the two new methods.
- **Review round, same day:** a control's record is appended to the write log before the control is marked settled, and a record already in the log under the control's id is not appended again, so a failed append or mark leaves the control waiting for its record and a retry ends with exactly one; a sweep that cannot read never refuses a new click; each record carries `ControlStatus` (`applied`, `not applied`, `not confirmed`, `expired`), which the worker gives with its sentence and `WriteLogEntry.control_status` carries to the desktop; an idle take is one read of `controls.json`; only controls settled more than a day ago are dropped. ADR 0052 gained a proposed amendment naming the control plane's six JSON files, pinned by `PersistenceTests`.

## 2026-11-09 - Findings from Scout's own audit of the control plane

- **Asked for:** fix the findings of Scout's audit of its own repository that a triage confirmed in `Scout.ControlPlane`, each with a test that fails without the fix, and give every finding judged not a bug a test that proves it.
- **What changed:**
  - The feature state file. One that does not parse is moved aside and read as defaults. One that cannot be opened or read now fails the call instead of reading as empty, and a set whose read failed writes nothing. Before, one transient read failure followed by any set replaced every feature's enabled state, settings and write grants.
  - `SetCredentialsAsync` fails as not persisted when the credential store answers false, as `SetupAsync` already did.
  - `SetupAsync` checks a required credential or setting against what is already stored when the request leaves it out, so a partial update need not resend a secret. It refuses a settings key the catalog does not declare.
  - `EnableAsync` deactivates the plugin when the state cannot be read or saved after it activated the plugin. A plugin that was already active stays active.
