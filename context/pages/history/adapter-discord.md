# Adapter.Discord - history

> Dated changes to [[pages/services/adapter-discord]]; the service page states how it works now.

## 2026-11-11 - The later-post log line moves to the notifier

- **Asked for:** the rework of the entry below: a log line in `DiscordOriginPoster` alone made Discord the only adapter whose successful post left a record, while Slack and local posts left none.
- **What changed:** the poster's Information line and its test are removed; `OriginNotifier`, through which every later post routes, logs one line per successful post with the channel kind and the text's length ([[pages/history/conversation]]).

## 2026-11-11 - A successful later post is logged

- **Asked for:** an automated audit of main (issue #261, "Successful origin posts have no audit log"): `DiscordOriginPoster` returned true with no log line and its callers (the action executor, the audit worker, the operator pipeline, the job-control poller) log only a failure, so a post that landed left no record. The no-executive-writes invariant counts it as a descriptive write to the originating channel, outside the write log, so the log line is its record.
- **What changed:** a post Discord accepted writes one Information line, "Posted <n> characters to the originating Discord conversation.", never the text or an id, like the failure lines. The Slack and local posters still log only failures.
- **Tests:** `A_Successful_Origin_Post_Leaves_One_Information_Log_Line_Without_Its_Text` in `DiscordOriginPosterTests.cs`, red with the line removed.

## 2026-11-10 - A start whose token is cancelled during the login never opens the gateway

- **Asked for:** a review finding on the pull request that carried the 2026-11-09 fix, continuing the issue "Startup can reconnect after shutdown": the start checked only the lifecycle's state after the login, and a cancelled start token does not change that state, so the gateway still started.
- **Cause:** the lifetime token is linked to the start token, but `StartAsync` read `IsRunning` only; the lifecycle stays started when only the start token is cancelled.
- **What changed:** under the connect gate, `StartAsync` starts the gateway only when `TryGetLifetimeToken` hands out a token that is not cancelled. When it does not and the start token is cancelled, the start runs `StopAsync`, which stops the lifecycle, drops the handler, unsubscribes the client's events and logs out through the new internal `Logout` seam, which `StopAsync` now uses in place of the client's logout, and then throws `OperationCanceledException` for the start token. When that stop fails, for example the logout throws, the start logs the failure once as a Warning through the adapter's logger and still throws the cancellation, with the adapter already stopped; before that guard the logout's exception left the start in place of the cancellation, which the host's start loop logs as a failed start during a shutdown. A plain `StopAsync` still lets such a failure escape. The host's start loop rethrows that exception while its stopping token is cancelled, so no later adapter starts and readiness is not signalled. A stop during the login with the start token not cancelled still returns normally with the gateway never started.
- **Not changed:** a start token cancelled before the start was called still logs in first and then logs out, through the same check; a login that fails escapes with its own exception, also when the start token is cancelled, and leaves the adapter armed until the host's stop or dispose; a start token cancelled after the gateway started cancels the replies in flight and leaves the client logged in, as before. The host's own stop stops the adapters before it cancels its stopping token, so a login that returns between the two still counts as a started adapter ([[pages/roadmap/followups]]).
- **Tests:** in `DiscordChatAdapterDispatchTests.cs`, `A_Start_Whose_Token_Is_Cancelled_While_The_Login_Is_Pending_Never_Opens_The_Gateway` (red before the fix with `connects should be 0 but was 1`), `A_Start_Cancelled_During_The_Login_Leaves_The_Adapter_Logged_Out_And_A_Later_Message_Undispatched`, `A_Later_Stop_And_Dispose_On_A_Cancelled_Start_Do_Not_Throw_Or_Log_Out_Again`, `A_Start_Whose_Token_Is_Cancelled_Before_It_Is_Called_Never_Opens_The_Gateway_And_Logs_Out`, `A_Start_Whose_Token_Is_Cancelled_As_The_Login_Returns_Never_Opens_The_Gateway_And_Logs_Out`, `A_Stop_And_Then_A_Cancelled_Token_During_The_Login_Fail_The_Start_With_The_Cancellation_And_Never_Open_The_Gateway`, `A_Start_Token_Cancelled_After_The_Gateway_Started_Cancels_The_Reply_In_Flight_And_Leaves_The_Client_Logged_In` the Rule I test `A_Login_Discord_Refuses_While_The_Start_Token_Is_Cancelled_Fails_The_Start_With_The_Refusal`, and the Rule I test for the stop on the cancelled path, `A_Logout_That_Fails_On_A_Cancelled_Start_Is_Logged_Once_And_The_Start_Still_Ends_With_The_Cancellation` (red before its guard with `thrown should be of type System.OperationCanceledException but was System.Net.Http.HttpRequestException`). The existing start tests are unchanged and green.

## 2026-11-09 - Messages from bots ignored, and a stop during login leaves the gateway down

- **Asked for:** Scout's own audit of this repository (issues "Startup can reconnect after shutdown" and "Other bots can trigger conversations").
- **What changed:** `ProjectInbound` takes the message's author (`IUser`) and reads its id and `IsBot` itself, carried as `InboundDiscordMessage.AuthorIsBot`, so a caller cannot leave the bot flag out, and the translator drops such a message first, with the reason `bot-author`, before the mention rule, the voice download or the access policy, so another bot's mention, direct message or voice reply never starts a conversation. `StartAsync` logs in through the internal `Login` seam, then starts the gateway through `Connect` only while the lifecycle is still running, under a gate `StopAsync` also takes around the client's stop and logout, so a stop that lands during the login leaves the gateway never started. `DiscordAdapterLifecycle` creates the lifetime token and publishes the started state under one lock, and stop takes the token under the same lock, so no reader sees the started state without its token. The dispatch seam reads the running state and the token in one step through the lifecycle's new `TryGetLifetimeToken`, as the Teams lifecycle already did: before, a message that passed the running check while a stop landed threw `Lifecycle not started.` and was logged at Error as a failed message; now it is dropped like a message after the stop. `DisposeAsync` no longer disposes the connect gate, whose wait handle nothing reads: before, a start still waiting for its login when the adapter was disposed failed with `ObjectDisposedException` from the semaphore; now it returns with the gateway never started.
- **Not changed:** a login that fails escapes `StartAsync` as before and leaves the adapter armed until the host's stop or dispose; the gateway is never started.
- **Tests:** `Another_Bots_Mention_Direct_Message_Or_Voice_Reply_Never_Starts_A_Conversation` (`DiscordMessageTranslatorTests.cs`), `ProjectInbound_Carries_Whether_The_Author_Is_A_Bot` (`DiscordInboundProjectionTests.cs`), `A_Start_No_Stop_Interrupts_Logs_In_And_Then_Starts_The_Gateway_Once`, `A_Stop_While_The_Login_Is_Pending_Leaves_The_Gateway_Never_Started`, `A_Stop_While_The_Gateway_Is_Starting_Waits_For_That_Start_Before_It_Stops_The_Client` the Rule I test `A_Login_Discord_Refuses_Fails_The_Start_And_Never_Starts_The_Gateway`, `A_Dispose_While_The_Login_Is_Pending_Leaves_The_Gateway_Never_Started_And_The_Start_Returns` and `A_Message_Caught_By_A_Stop_Is_Dropped_Quietly_And_Never_Fails`, 300 raced rounds (`DiscordChatAdapterDispatchTests.cs`), `The_Started_State_Is_Never_Visible_Before_Its_Lifetime_Token_Exists`, 10,000 raced rounds, and `The_Lifetime_Token_Is_Handed_Out_Only_While_Running_And_A_Stopped_Lifecycle_Answers_False_Without_Throwing` (`DiscordAdapterLifecycleTests.cs`). The audit's claim that a downloaded voice attachment's response is never released is answered by `The_Attachment_Stream_A_Caller_Disposes_Releases_The_Response_Body` (`DiscordVoiceMessageTests.cs`) with `The_Voice_Attachment_Stream_Is_Disposed_Once_The_Turn_Has_Read_It` in the conversation tests; no change.

## 2026-10-28 - Threads, long replies, typing, reply reference, voice messages

- **Asked for:** "improvements in the Discord chat" and "use audio to communicate - me recording".
- **What changed:** a mention in a server text channel opens a public thread on the user's message and the reply streams there (`ReplyInThreads`, default true; falls back to the channel when Discord refuses); a reply that stays in the channel is a Discord reply to the user's message; the typing indicator shows from Begin to the first streamed content; a reply longer than one embed continues in up to five messages, split at paragraphs, lines or spaces and never inside a code fence that fits a part, where before it was cut at 4,096 characters; voice messages reach the core as audio with a download delegate ([[pages/decisions/0024-voice-messages-transcribed-locally]]). The sink stopped appending its own cursor after the pump's, which showed two cursors while streaming.
- **Tests:** `DiscordReplySplitterTests`, `DiscordResponseSinkPartsTests`, `DiscordChatAdapterThreadTests`, `DiscordVoiceMessageTests`, and a typing-at-stop test in `DiscordChatAdapterDispatchTests`. `Capabilities_Are_FineGrained_4096` and `Complete_OverLimit_Body_Preserves_Head_Not_Just_Footer` were replaced, because the sink no longer caps a reply at one embed.

## 2026-10-22 - The gateway handler stops awaiting the conversation

- **Symptom:** while a reply streamed, the owner's log showed `[Discord] Gateway: A MessageReceived handler is blocking the gateway task.` Discord.Net 3.20.2 raises that warning in `DiscordSocketClient.TimeoutWrap` when an event handler outlives the configured handler timeout, and then keeps awaiting the handler to completion inside the gateway event dispatch.
- **Cause:** `OnMessageReceivedAsync` awaited the whole conversation (`handler(chatMessage, sink, lifetimeToken)`) inside the gateway event.
- **What changed:** the handler still projects, filters and logs the message exactly as before, then starts the conversation with `Task.Run` and returns. The started work keeps the old catch blocks: a cancellation on the lifetime token logs at debug, any other exception logs an error. Each conversation is tracked in a `ConcurrentDictionary` until it completes. `StopAsync` cancels the lifetime token, unsubscribes, waits for the tracked conversations bounded by 10 s and the caller's token (a timeout logs a warning), then stops and logs out the client. The filter-and-dispatch step is the internal `OnInboundAsync` seam, and `StartAsync` arms the adapter through the internal `Arm`, so tests drive both without a Discord login.
- **Behaviour:** two messages can now be in flight at once; conversation memory is already concurrency-safe, and their turns may interleave in history. Per-channel reply ordering is not guaranteed.
- **Tests:** `The_Gateway_Handler_Returns_Before_The_Conversation_Finishes`, `A_Failing_Conversation_Is_Logged_Never_Unobserved` and `Stop_Waits_For_In_Flight_Conversations` in `tests/Scout.Adapter.Discord.Tests/DiscordChatAdapterDispatchTests.cs`; the translator and projection tests are unchanged and green.
- **Not changed:** the Slack and Teams adapters. SlackNet acknowledges a legacy event handler before calling it and fans socket envelopes out through Rx `SelectMany`, so a long Slack conversation neither blocks the socket nor delays the ack. The Teams turn holds the inbound webhook request for the whole conversation, which matters only once a webhook host is wired.
- **Invariants:** [[pages/invariants/no-executive-writes]] holds (the sink is still bound to the originating channel); [[pages/invariants/pluggable-boundaries]] holds (no Discord.Net type leaves the adapter).
