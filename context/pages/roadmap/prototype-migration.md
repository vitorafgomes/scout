# Prototype migration: the desktop screens brought to the approved artboards

> Every screen of Scout Desktop looks like its approved artboard in [[pages/conventions/desktop-prototype]], in both themes and in every state the artboard shows, reached one screen per version as [[pages/decisions/0041-angular-material-in-the-renderer]] decides.

## Why now

The artboards were brought in line with the phase-2 code on 2026-11-07 and 2026-11-08, and the convention says a screen's review checks that the screen and its artboard match. Until now nobody had compared them, so nobody knew how far apart they are. This page is that comparison and the plan that follows from it. It is item F5 of [[pages/roadmap/future-improvements]].

## Scope

- **In scope:** the main window's shell (navigation, top bar, bell), Chat, quick ask, the floating button, AI Sources, Models (four tabs), Features (grid and side panel), Approvals, Meetings, Logs, Settings, the setup wizard and the five operator pages; both themes; the states each artboard's "Preview state" control shows.
- **Out of scope:** new behaviour. A migration changes how a screen looks and which components draw it. It keeps every `data-test` id and every behaviour its specs pin (ADR 0041). An artboard state the code does not have yet, such as the top bar's search field, is a feature with its own item and is listed here only so it is not mistaken for a styling gap.

## How the audit was made

- **The app:** the built app driven by the end-to-end harness of [[pages/decisions/0051-desktop-end-to-end-tests]] (private display, keyring and profile, the fake worker, the control plane pointed at a missing file). It ran at 1280 x 820, the artboard size. The wizard ran at 1100 x 760 and quick ask in its own window. Each screen was captured in dark, and in light where the top bar's theme switch reaches it.
- **The artboards:** each `.dc.html` rendered in Electron at its canvas size, in dark and light and in the states listed below. The Design runtime is not committed, so a stand-in for it was used. It fills the `{{ }}` bindings, `sc-for` and `sc-if` from the artboard's own `renderVals()`. The capture spec and the stand-in were throwaway and are not in the repository.
- **What the fake worker cannot reach:** with no AI Source and no control plane, these screens only show their empty, loading or error state: Features (the grid and its panel), Approvals, Meetings, the Speech tab's voices and the operator pages. For those screens the audit compares the state the app can reach with the artboard's matching state, and reads the rest from the artboard's markup. A difference in data, such as the number of models or which card is connected, is not counted as a design difference.

## Differences shared by every screen

S1 and S8 are bug fixes that go before version 1; S3 to S7 are fixed once, in the shell and the theme, in version 5 of the plan below. Severities: **blocking** means the screen does not read as the approved prototype; **visible** means an owner would notice it side by side; **minor** means only a careful comparison shows it.

## Risks

- **Risk:** a migration changes behaviour while it changes the look. **Mitigation:** ADR 0041's rule, which is to keep every `data-test` id, keep the component specs green before and after, and change one screen per version.
- **Risk:** the artboards and the code drift again. **Mitigation:** the convention in [[pages/conventions/desktop-prototype]] puts the artboard change in the same branch, and each version here captures the screen next to its artboard for review.
