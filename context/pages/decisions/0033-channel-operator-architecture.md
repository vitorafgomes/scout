# ADR 0033 - Channel operator architecture

> The operator's state lives in the control plane, its pipeline runs in a new C# library `Scout.Operator` inside the worker, speech and images come only from Semantic Kernel services of the AI Source already connected, and progress is posted later into the channel the request came from.

## Status

- [ ] Proposed
- [x] Accepted
- [ ] Deprecated / superseded by

Updated: 2026-11-03. Accepted on the owner's instruction to build phases 2 to 6 of [[pages/roadmap/youtube-channel-operator]] in one branch, one commit per phase: "go ahead with all the next phases, everything in a single PR".

## Context

Phase 1 ([[pages/decisions/0032-per-feature-write-permissions]]) put the write contract in the product: the `youtube` feature declares its rows, the owner grants its writes on the YouTube card, irreversible actions wait on the Review screen, and a function gate in the worker asks the control plane's `WorkerGate` before any declared write. Phases 2 to 6 build the operator itself: mandate, research, script, narration, visuals, assembly, review, publish, learning loop, experiments and comments, matching the reference project module for module except for media accounts ([[pages/roadmap/youtube-channel-operator]], parity table).

Four questions block the first line of phase 2 code, because every later phase builds on the answers.

- **Who writes the operator's state.** The desktop reaches only the control plane ([[pages/decisions/0011-backend-frontend-grpc-uds]]); the worker reaches it through `WorkerGate` with its own token. Two processes writing one file already cost the approval queue a fix (`actions.json`).
- **Where the pipeline code lives.** The owner's rule: "most of it has to be in C#".
- **How speech and images are made.** Semantic Kernel is the one LLM path ([[pages/decisions/0012-llm-communication-through-semantic-kernel]]), and the owner's rule is that media comes only from the AI Sources already connected, never a separate account. In the installed Semantic Kernel 1.78 packages only the OpenAI and Azure OpenAI connectors carry text-to-audio and text-to-image services (`AddOpenAITextToAudio`, `AddOpenAITextToImage`, `AddAzureOpenAITextToAudio`, `AddAzureOpenAITextToImage`); the Google connector (Gemini, the owner's current provider), Ollama, Mistral, HuggingFace and Azure AI Inference have none, and the ChatGPT plan path has no audio or image service.
- **How progress reaches the chat.** Today every outbound message goes through an `IResponseSink` created for one inbound message and closed at the end of the turn; nothing can post later, and no transport reference outlives the turn (`src/Scout.Conversation/Abstractions/IResponseSink.cs`, `IChatAdapter.cs`). Teams has no live hosting at all.

## Decision

- **State: the control plane is the single writer.** A new `Operator` area in `Scout.ControlPlane` owns the mandate, the video projects (topic, research, script, claims, scene list, package metadata, status, the originating chat reference) and their history, stored as JSON next to `features.json` with the same atomic-write style. The desktop reads and edits through a new `Operator` gRPC service on the desktop token; the worker reads the mandate and saves its drafts through new `WorkerGate` methods on the worker token, each checked against the `youtube` write grant like any `Write` row (amended 2026-11-03: the worker's mandate read is a read of the owner's brief and is not grant-gated; its project reads, saves and the take of the next queued project are, and so is the desktop's start of a project), and the role tests prove the worker token cannot edit the mandate, approve a package or reach the desktop's `Operator` service. Media bytes (narration, images, the MP4, Shorts, thumbnails) stay on disk under Scout's data folder in one directory per project; the control plane records their paths and checksums only. The desktop previews them through a main-process route confined to that directory; the renderer never receives an arbitrary file path.
- **Code: a new library `Scout.Operator`.** Research, script, claims, scenes, media generation, the `ffmpeg` driver, the checks, publishing, the learning loop, experiments, comments and the scheduler live in `src/Scout.Operator` with `tests/Scout.Operator.Tests`, referenced by `Scout.Host.Console`. It reaches YouTube through `Scout.Plugin.YouTube`'s client (extended with the write calls the catalog declares), the model through Semantic Kernel only, and the control plane through its own seam, `IOperatorControlPlane`, implemented in the console host over the same `WorkerGate` channel and worker token as the write gate (amended 2026-11-03: a separate seam keeps the write gate's contract to requesting and recording writes). No generic pipeline engine: concrete stages, one class each where a class is needed.
- **Media: the connected provider's Semantic Kernel services, or a local fallback.** The operator resolves `ITextToAudioService` and `ITextToImageService` from the kernel; `Scout.Llm` registers them only for providers whose installed connector offers them (OpenAI, Azure OpenAI), with the same credential the owner connected and the provider's configured models. With any other provider the operator falls back without asking for an account: narration from the bundled local Piper engine (amendment of 2026-11-03 below), else from an audio file the owner supplies or none (captions carry the script), and visuals from the owner's images and text cards `ffmpeg` renders. The capability matrix lives on [[pages/services/llm]]. A direct HTTP call to a provider's speech or image endpoint is a second LLM path and is not part of this decision; the owner decides that separately (Gemini media is the open question).
- **Progress: a proactive post into the originating channel.** When a request starts a long job, the adapter captures an opaque reference to the originating conversation (Discord channel or thread and the message replied to; Slack channel and thread timestamp; the local quick-ask session); the operator stores it with the project, and a new seam in `Scout.Conversation` lets the operator post a short progress or result message into that same conversation later. It is a descriptive write to the originating channel only, as [[pages/invariants/no-executive-writes]] already allows; Teams, which has no live hosting, gets no proactive post.
- **Write scopes come from a fresh sign-in** (amended 2026-11-03, phase 5). Google does not support incremental authorization for installed apps, and the developer policies allow only the scopes in use: the read-only sign-in keeps the read scopes, "Allow writes" runs a new browser sign-in that adds `youtube.upload` and `youtube.force-ssl` and grants writes only when every requested scope came back, and a revoke signs back in with the read scopes. Disconnecting YouTube purges the API data the control plane holds (snapshots, research candidates).
- **The operator has its own window** (owner's decision, 2026-11-03: "go ahead with its own window"). The YouTube card offers "Open YouTube operator", which opens a separate Scout Desktop window holding every operator page (mandate, projects, script and claims, scenes and previews, assembly, the feature's approval queue, reports, experiments, comments). It is a window of the desktop app, not a local web site: no port is opened, the renderer reaches the control plane only through main as every other page does, and approvals stay in the desktop. A local web site was considered and rejected: an HTTP port on the machine would be reachable by any local process or page (CSRF, DNS rebinding) and would move approvals out of the desktop.
- **YouTube quota is budgeted per day.** Since 2026-06-01 `search.list` and `videos.insert` have their own buckets of 100 calls a day each; everything else shares 10,000 units a day, with `videos.update`, `thumbnails.set`, `playlistItems.insert`, `comments.insert` and `comments.setModerationStatus` at 50 units and `captions.insert` at 400. The scheduler caps research searches and uploads per day below those buckets, and burns captions into the video instead of calling `captions.insert` by default.
- **Uploads go up private.** A video is uploaded with `privacyStatus: private` and, when scheduled, `status.publishAt`; whether an unverified Google project may publish publicly is unsettled in Google's current documentation, so public visibility is a later, separately approved `videos.update`. Amended 2026-11-03 (phase 5): YouTube's developer policies require the client to offer public, private and unlisted and every upload to follow the user's express consent, so the owner picks the privacy, the made-for-kids answer and the synthetic-media disclosure in the desktop publish dialog, and confirming that dialog is the approval of each action it lists; a schedule is only allowed with private, as `status.publishAt` requires. A publish the model queues from a chat carries none of those choices and is refused with a pointer to the desktop.
- **Experiments follow the reference's statistics.** A title or thumbnail experiment rotates its arms in sequence through `videos.update` and `thumbnails.set`, each arm an approved action, and declares a winner only on a pooled two-proportion z-test on click-through rate at z >= 1.96 with at least 1,000 impressions and 10 clicks per arm, with guardrails on average view percentage and traffic-source shift; adopting the winner is one more approved action. Impressions and click-through rate are read from the Analytics API in phase 5 and verified against the live API before the experiment code depends on them. Amended 2026-11-03 (phase 5): the Analytics API's `reports.query` has no impressions or click-through rate metric; both come only from the Reporting API's reach report (`channel_reach_basic_a1`), which needs a reporting job created once on the owner's channel (a declared `Write` row, `youtubeReporting jobs.create`) and arrives as daily files 48 to 72 hours late, so an arm runs 24 to 168 hours and the decision waits for the files covering it.

## Consequences

- **Better:** one writer for every piece of operator state; the worker can never approve its own work; the pipeline is C# end to end; no account or key beyond what the owner connected; the owner sees progress in the chat they asked from.
- **Worse:** a new project and a new gRPC service to maintain; with a provider that offers no media services the operator makes no generated images until the owner connects OpenAI or Azure OpenAI, and narrates with the bundled voices only (since the amendment of 2026-11-03; before it, no narration at all); Teams users get no progress posts.
- **Neutral but noteworthy:** `ffmpeg` is the one external tool, fetched at build time and pinned by checksum (owner's decision of 2026-11-02); the operator never writes outside its project directories under Scout's data folder.

## Alternatives considered

- **State in the worker, files on disk.** Rejected: two processes would write the same files, and the desktop cannot reach the worker (ADR 0011).
- **Pipeline in the desktop main process.** Rejected by the owner's rule that most of it is C#.
- **Grow `Scout.Plugin.YouTube` into the pipeline.** Rejected: the plugin is the YouTube client and its model functions; the pipeline orchestrates the model, media, `ffmpeg`, the control plane and the chat, which is a different responsibility with its own tests.
- **Direct HTTP to every provider's media endpoint.** Not decided here: it is a second LLM path under ADR 0012 and needs the owner's decision.

## Enforcement

- `tests/Scout.ControlPlane.Tests`: role tests that the worker token cannot reach the `Operator` service or decide a package, and that operator writes through `WorkerGate` refuse without the grant.
- `tests/Scout.Operator.Tests`: every stage with its failing-call test (Rule I) for the model, YouTube, `ffmpeg` and the control plane.
- `tests/Scout.Llm.Tests`: the media services are registered only for providers that offer them, and the write gate is proven on the Gemini and ChatGPT plan paths as well as OpenAI.
- [[pages/services/operator]] and [[pages/architecture/project-map]] describe the new project; the review gate's `boundaries` lens covers `Scout.Operator` and the new contracts.
- `tests/Scout.Operator.Tests/PiperSpeechTests.cs` and `NarrationGeneratorTests.cs`: the bundled engine runs only with its argument list and the narration on standard input, writes only in the media directory, and is chosen over the provider only when the project names one of its voices.

## Amendment 2026-11-03 (phase 7): bundled voices

The owner decided (2026-11-03) that narration must not depend on the connected provider having a speech service: Scout Desktop ships the Piper text-to-speech program (rhasspy/piper 2023.11.14-2, MIT, whose archive carries libespeak-ng under GPL-3) and British English voice models whose dataset licences allow redistribution, fetched at build time and pinned by SHA-256 like `ffmpeg`, and the worker runs it as a separate program through `IProcessRunner`, never linked into Scout. The connected provider's speech, when it has one, is still reached through Semantic Kernel only (ADR 0012), now in the voice the owner names; each project carries `narration_voice`, chosen when the owner produces it (the owner moved the choice from the channel to the video on 2026-11-03), the readiness lists the voices this machine offers, and an empty choice means the provider's speech first and the bundled default voice otherwise. Images are unchanged: generated only through the provider's Semantic Kernel image service, else the owner's files and text cards. [[pages/services/operator]] (Bundled voices), [[pages/services/llm]] (media capability matrix), [[pages/roadmap/youtube-channel-operator]] (the voice licences).

**Amendment 2026-11-03 (delegation).** On the owner's decision of 2026-11-03 (a button to delegate a project), the owner delegates each project on its own from the desktop. Delegation is the control plane, the single writer of the operator's state, chaining the project's reversible stages: `DelegateProject` queues production, or assembly when the media is ready, and the control plane stores the worker's `media_ready` save of a delegated project as `assembly_queued`, so the worker's next take assembles it; the worker is unchanged ([[pages/services/control-plane]]). It needs the owner's live `youtube` write grant like any other operator write and writes only Scout's data folder. In a delegated project unresolved claims no longer block production, only the package approval. Delegation stops at the assembled package: approving it and publishing it stay the owner's actions, the publish an approved action under [[pages/decisions/0032-per-feature-write-permissions]], and nothing starts on its own from the mandate's cadence.

## Amendment 2026-11-03 (stock pictures)

The owner decided (2026-11-03) that a scene the owner gave no picture, on a machine whose connected AI Source has no image service, gets a picture that fits its context instead of a text card. The worker searches Openverse, the openly licensed media index, with no account and no key, using two to four search terms the scene planner asks for in the same one model request, and saves the first fitting result in the project's media directory with its credit; the video's description lists every credit under `Credits`. The provider's image service, when there is one, still comes first and is still reached through Semantic Kernel only, so the media decision above stands for every AI-made picture; Openverse is a read-only fallback before the text card, never a replacement for the owner's own picture, which replaces a stock picture and clears its credit.

Only three licences are taken, the owner's rule: CC0, the public domain mark and CC BY, so no SA and no NC. CC BY needs only the credit, which the description carries. CC BY-SA is excluded because a video that scales, pads and moves a picture over narration may count as an adaptation, and ShareAlike would then require the whole video under CC BY-SA, a licence the owner does not mean to grant for a video that also carries a script, a narration and other pictures under other terms. The NC variants are excluded because a channel that earns from its videos is commercial use, and the ND variants, which the owner's rule does not name, fall outside the same three-licence filter for the same adaptation reason. The fetch is a read, declared on the YouTube feature as "api.openverse.org and the host of the picture it names" ([[pages/invariants/no-executive-writes]]); its file is written only in the media directory, refused unless it is an image of at most 20 MB, and any failure leaves the scene a text card with a note, never a failed scene. It is counted in its own budget of 100 requests a day, under the anonymous limits the API reports in its headers (20 a minute, 200 a day). The readiness carries `stock_pictures` so the desktop can say where pictures come from ([[pages/services/control-plane-contracts]]); the worker's side is in [[pages/services/operator]], the control plane's vocabulary and save check in [[pages/services/control-plane]].

**Amendment 2026-11-04 (visual brief).** On the owner's decision of 2026-11-04, each project carries the owner's visual brief, free text of at most 500 characters, and a motion preset, `still`, `gentle` or `dynamic`, both chosen on produce or delegate like the narration voice and never set by the worker; the brief reaches only the scene planner's one model request, as the style of the picture prompts and search terms, and the preset only the assembler's choice among its own constant ffmpeg filter chains, so neither adds a call leaving the process or a write ([[pages/services/control-plane]], [[pages/services/operator]]).

**Amendment 2026-11-04 (delete project).** The owner deletes a project from the desktop: the control plane removes it from its store and deletes the project's media directory, which it builds from the 32-digit project id alone, so nothing outside Scout's data folder is touched and a video already on YouTube stays there; a delete is Scout's own state and needs no grant, and a running project or one with approved or executing YouTube actions is refused ([[pages/services/control-plane]], [[pages/invariants/no-executive-writes]]).

**Amendment 2026-11-04 (voice samples).** So the owner can hear a bundled voice before choosing it, the worker makes one short Piper sample per bundled voice, free and offline, into a `voice-samples` folder the control plane gives beside the project media directories, and the readiness names each sample file; the folder is Scout's own data and needs no grant, the worker writes it only through `MediaFiles`, and the desktop plays a sample through the `voice-samples` host of `scout-media:`; the provider's voices get no sample, because each would be a paid call ([[pages/services/operator]], [[pages/services/desktop-operator]]).

**Amendment 2026-11-04 (project format).** On the owner's decision of 2026-11-04 that the way a video is made is chosen before the script ([[pages/roadmap/youtube-channel-operator]], phase 8), each project carries a format the owner picks when starting it on the desktop, stored by the control plane and never changed after, by the owner or by the worker; a project from chat, or stored before formats existed, is `generated_pictures`. Phase 8a makes two of the four formats: `generated_pictures`, the pictures of the media decision above, and `own_pictures`, where the owner attaches a picture per scene and the worker draws nothing, neither through the image service nor from Openverse, so a scene still without one is a text card with a note. The AI presenter and the owner's own video are refused until phases 8c and 8b. The visual brief of the amendment above becomes the owner's direction, at most 1000 characters, given at the start, on produce or on delegate, under the key it was stored with, and it is data in the one model request of the script writer and of the scene planner, which still offer the model no function. The owner may edit a scene's text, 1 to 700 characters, or ask for its narration again, in every format; both reset only that scene's narration and queue production, and like the other scene edits they are Scout's own state, so they need no grant and write no write-log entry. None of this adds a call leaving the process or a write outside Scout's data folder ([[pages/services/control-plane]], [[pages/services/operator]], [[pages/services/control-plane-contracts]]).

**Amendment 2026-11-04 (phase 8d): the operator from the chat.** The owner asked that the chat be able to "do everything: adjust a project and run the checks, talking with the user" ([[pages/roadmap/youtube-channel-operator]], phase 8), and left the shape to the build ("see how it is best done"). This supersedes the sentence of the project-format amendment above that a project from chat is `generated_pictures`: a project started from chat keeps the format and the direction its owner gave, under the same rules as the desktop's start, and only a project stored before formats existed reads as `generated_pictures`.

- **The owner gate narrows, the grant authorizes.** The functions that list projects, read a project's state and change it, and a format or a direction on `youtube_make_video`, answer only Scout's owner: the local quick-ask user, or an allowed chat user listed in `Scout:Access:OwnerUserIds` ([[pages/decisions/0021-allowed-users]], amendment of 2026-11-04). The conversation core sets that from the platform event for the turn; no function parameter, message text or function result can set it, so a prompt can make the model call a function but cannot make the caller the owner ([[pages/decisions/0014-per-request-identity-gating]]). It decides who may ask and never authorizes a write: the owner's YouTube write grant does, checked by the write gate before each declared function runs, by the control plane on every chat call, and by the worker's next take. The control plane cannot tell an owner's chat request from the worker's own call on the worker token: the owner identity is checked in the worker, trusted code like every other `WorkerGate` write, and the grant is the only authorization on the server's side. A topic-only `youtube_make_video`, or one with the default format `generated_pictures` and no direction, stays open to any allowed user, as before.
- **The worker token changes scenes only through the chat calls.** `WorkerGate` gains seven calls on the worker token, `ChatEditSceneText`, `ChatRegenerateNarration`, `ChatRegenerateScene`, `ChatSetSceneLocked`, `ChatReorderScenes`, `ChatProduceProject` and `ChatDelegateProject`, each the owner's desktop operation under the grant, on the request messages the desktop's `Operator` service already uses; an empty voice, direction or motion on produce or delegate keeps the project's. They are reversible writes into Scout's own data folder, declared on the `youtube` row "Scout's data folder" like `youtube_make_video`, and no new call leaves the process.
- **Chat edits are logged as such.** Each chat change writes two write-log entries, the write gate's record of the declared function, `succeeded` or `failed`, and the control plane's "<outcome> via chat" against the project, the second only when the change changed the stored project (a reorder to the order it has, or a lock of a locked scene, writes none) and, when the log cannot be appended after the change was stored, replaced by a warning in the control plane's log while the change stands; the owner's scene edits on the desktop still write none. A refusal (no grant, a locked scene, a value the control plane does not accept) stores nothing and logs nothing on the control plane's side.
- **Never from the chat:** deleting a project, attaching a file from disk, granting a write, approving an irreversible action (upload, schedule, delete a published video) and confirming a paid generation. `youtube_delete_project` and `youtube_publish_video` only say where in Scout Desktop the owner does it.
- **Read before acting, report after.** `youtube_project_state`'s description, once for every change function, tells the model to read the state, tell the owner what is missing (the grant, pending claims, text cards, the owner's pictures, failed scenes, what the connected AI Source cannot make, a format Scout does not make) and wait for the owner's word; the worker enforces the read: a change function runs only after a state read of the same project in the same conversation within 10 minutes, the conversation being the chat channel and the sender as the conversation memory keys them, so the owner confirms in the next message on every platform, and is refused before any control-plane call otherwise. Each change answers what changed and the project's new status. The state lists the readiness voices, the ids `narration_voice` takes, and cuts each scene's text at 240 characters; `youtube_scene_text`, an owner-only read, answers one scene's whole text. The topic, the direction and the scene texts are printed after a sentence that calls them data, never instructions, and topic candidates, claim texts and their sources, comments and the package description are never printed. A project the desktop started gets no progress post in the chat it is changed from; the owner asks for the state or follows it in Scout Desktop.

**Amendment 2026-11-04 (phase 8b): own video.** On the owner's decision of 2026-11-04 that the owner's own video is the whole content of its project ([[pages/roadmap/youtube-channel-operator]], phase 8), Scout makes the format `own_video`, which the project-format amendment above refused until this phase. The owner starts the project on the desktop, never from the chat, and it waits as `recording_waiting` until the owner attaches the recording: an mp4, mkv, webm or mov file of at most 8 GiB that main copies into the project's media folder, an attach that needs no grant, like a background. The worker takes the project as `transcribing` under the owner's grant, with no research and no script writer: a recording of at most 60 minutes, with a picture and a sound stream, is transcribed on this machine by the local Whisper engine of [[pages/decisions/0024-voice-messages-transcribed-locally]], and the transcript is the script, one section per segment heard with its start and end. Production makes no narration and no picture. The scene planner cuts the transcript into scenes that are consecutive clips of the recording, cut at a pause once a scene's speech has run 20 seconds and always before its speech passes 60 seconds or 700 characters; each clip runs to where the next scene's speech starts, so a pause between two scenes is carried into the clip before it, its captions shown over the silence (speech from 0 to 55 seconds and silence to 300 seconds give a first clip of 0 to 300 seconds). Assembly renders each scene as its clip with the recording's own sound and the scene's text as captions, timed evenly within the scene, and editing a scene's text changes only its captions. A caption edit on a delegated project that is assembled or approved queues its assembly again, as the hand-on of the delegation amendment does, so the new captions are assembled without the owner; on a project the owner did not delegate it goes back to media ready, as any scene edit does. The recording and its sound never leave the machine: ffmpeg takes the sound out into a WAV inside the media folder, removed afterwards, and Whisper runs in process. The transcript text goes to the connected AI Source in one model request for the title variants, the description, the tags and the chapter names. That request offers no function and marks the transcript as data, the same path the script and scene requests take. None of this adds a write outside Scout's data folder ([[pages/services/operator]], [[pages/services/control-plane]], [[pages/services/desktop-operator]], [[pages/services/transcription-whisper]]).

- **Rejected: one ffmpeg pass over the whole recording.** A caption edit would re-encode the whole video, where one segment per scene, kept while its inputs are unchanged, renders only the edited scene again.
- **Rejected: Whisper's translate task.** It writes English whatever language is spoken, and the captions and chapters must say what the recording says, in its own language.

**Amendment 2026-11-04 (phase 8c-A): the animated character.** The owner asked for "a person to speak or an animation" in the videos (2026-11-03), then for an avatar that speaks without making a video every time (2026-11-04: "is there no way to create the Avatar, which would be a person, so that it speaks? and we would not have to create the Video every time"), and chose "go with A + a spike of B" the same day: A, a character made once per project whose mouth moves with the narration, now; B, a realistic photo that is animated, as a spike first ([[pages/roadmap/youtube-channel-operator]], phase 8c).

- **The format.** `animated_character` is the fourth format a project starts in, on the desktop or from the chat, under the same rules as the others; `ai_presenter`, which needs a video model, stays refused. The project carries a presenter description of at most 300 characters, who the character is and where they are, given at the start and on produce or delegate like the direction, and one presenter picture in its media directory, made once by the connected image service from the direction and the description with a fixed cartoon style, through Semantic Kernel only and counted in the picture budget, or attached by the owner from Scout Desktop. A worker save records the picture it made, a `presenter-` file already in the media folder, only while the project has none, and never replaces, clears or renames one; `RegeneratePresenter` clears it so the next production makes it again, as a narration regeneration does for its scene, and takes the approval back. The owner marks the mouth on the picture as a box of four fractions, which replacing or regenerating the picture clears; without it the character is shown still, and without a picture, or with one Scout cannot measure, each scene is a text card with a note, never a failed scene.
- **Lip sync is local and free.** Scout Desktop bundles Rhubarb Lip Sync 1.14.0 (MIT) like ffmpeg and Piper, and the worker runs it as a separate program on the scene's narration with the language-independent phonetic recognizer, writing only a cues file, and a temporary WAV for an mp3 narration, inside the project's media folder; the cues pick one of Scout's own nine mouth shapes, overlaid on the mouth box by the assembler, so no call leaves the process and nothing is paid per video. A failure or a timeout leaves the scene still with a note. The readiness reports `lip_sync_available`.
- **Scenes.** Every scene shows the presenter picture: narration is made, regenerated and edited as in `generated_pictures`, and a scene has no picture of its own, so regenerating a scene and attaching a scene picture are refused with their sentences ([[pages/services/control-plane]]).
- **Writes.** The presenter attach, the mouth box and `RegeneratePresenter` are the owner's edits of Scout's own state on the desktop token, with no grant and no write-log entry, like the other scene edits; the replaced presenter picture, and the one `RegeneratePresenter` forgets, which is refused while the project is producing or assembling, are deleted inside the media directory only. The only call that leaves the process is the one picture request to the connected image service, the same Semantic Kernel call the scene pictures of `generated_pictures` make, counted in the same daily picture budget; the picture is saved under the youtube row "Scout's data folder", whose "images" already covers it, and the rhubarb subprocess is local. Nothing writes outside Scout's data folder ([[pages/invariants/no-executive-writes]]).

- **Rejected: hosted avatar services.** A separate account, and the narration sent to a third party, against the rule that every medium comes from the AI Source connected in Scout.
- **Rejected after the spike: a local talking-head model** that animates a realistic photo (B). The spike's licence survey (2026-11-04, research only, nothing downloaded or run) found no talking-head model that animates a portrait on CPU under licences that allow commercial use on its code, its weights and its dependencies. MuseTalk (MIT) clears the licences but moves only the mouth, needs about 4.4 GB of weights and publishes no CPU timing; Ditto and PC-Talk animate the head on CPU but depend on InsightFace detector models licensed for non-commercial research only; the 2026 releases are video diffusion sized for RTX-class GPUs. Decision: the local run of the spike is not made, and the realistic presenter from a photo stays unbuilt; the paid video model below remains the later option for it.
- **Later option: the video model.** Gemini Omni Flash is the one live candidate after OpenAI and Azure retired Sora 2; a clip per scene is paid per second and its speech from a given script is unverified, so it stays the later `ai_presenter` path ([[pages/roadmap/youtube-channel-operator]]).

**Amendment 2026-11-05 (phase 8c-B): the automatic presenter.** The owner wants the animated character made without any work from them: "the intention is that everything is created automatically if the user puts in nothing. Just the text of what they want"; a preview of the result, "to see how it turned out, and then the user says what they want to improve", "until it reaches something they like"; the prompt shown and editable, "it could show which prompt was used to generate it, so the user can edit it"; and a background of its own on every scene, "the Background should sit on each scene correctly, so each scene can have a different Background" (all 2026-11-05, [[pages/roadmap/youtube-channel-operator]], phase 8c).

- **The default format.** The mandate carries the format a project started without one is made in, `generated_pictures` until the owner chooses; a start on the desktop or from the chat with no format takes it, and a stored value Scout does not make reads as `generated_pictures`.
- **The first presenter asks for itself.** The worker save that makes an `animated_character` project script ready, with no presenter version and no presenter picture, stores the request `first`; the control plane hands every presenter request out as a job of its own, `presenting`, before any production take, and the job's save gives the project back the status it had. A delegated project therefore produces with a presenter already made, and the owner is asked for nothing.
- **Versions and the feedback loop.** Every job adds one presenter version, its picture, its 5-second preview, its prompt, the owner's feedback that asked for it, its mouth box and whether it was generated or one of Scout's own presenters; the newest becomes current unless the job was the automatic first one and the owner already attached a picture. The owner asks for another with feedback, a prompt used verbatim, or `builtin:<id>`, and makes an older version current again; nothing approves a presenter, the owner just produces or delegates. At most 10 versions are kept: the oldest one no pointer keeps is dropped and its files deleted from the media folder after the store holds the change. The owner may also remove a version made by mistake, any but the current one and never while the project is presenting, with `RemovePresenterVersion` on the desktop token: an edit of Scout's own state with no grant and no write-log entry that leaves the video and its approval as they are and deletes, the same way, the files no other version or the current presenter names ([[pages/roadmap/production-screen]], decision 7). Amendment of 2026-11-11: a presenter version is named by an id the control plane derives from its content, and `UsePresenterVersion` and `RemovePresenterVersion` take that id instead of a position; a version that is no longer there answers `NOT_FOUND` and nothing changes. Field 2 of both requests is reserved. The desktop, the worker and the control plane ship in one package, so no earlier client calls this contract. The id is a hash of the version, never stored, so a project stored before it reads the same ids ([[pages/services/control-plane]], [[pages/services/control-plane-contracts]]).
- **A picture per scene.** In `animated_character` every scene gets its own picture as in `generated_pictures`, with the presenter composited over it, so the 8c-A refusals of a scene regeneration and a scene picture in this format are lifted; the owner edits a scene's picture prompt and asks for its picture again, in both formats that make pictures.
- **The mouth is found, not guessed.** The worker finds the face and the lips on the picture with a local face landmark model and reports `face_detection_available`; the owner's box still wins when marked after ([[pages/services/operator]]).
- **Writes.** The presenter request, the version choice, the picture prompt and the picture regeneration are the owner's edits of Scout's own state on the desktop token, with no grant and no write-log entry, like a scene edit; from the chat they run under the grant and are logged via chat. Every presenter job's picture is one request of the existing declared picture call, counted in the 40 pictures a day the readiness reports as `pictures_left_today`; the face models run in the process on local files, so no call leaves it; the control plane deletes a pruned version's picture and preview, and the worker deletes, inside the same folder, the preview narration it made, a generated picture it replaced with a built-in after finding no face, and a failed preview's audio; nothing is deleted outside the media folder ([[pages/invariants/no-executive-writes]]). `RegeneratePresenter` became a presenter request with no feedback and no prompt, so it keeps the picture and the versions and deletes nothing.

- **Rejected: a heuristic mouth position** (a fixed fraction of a head-and-shoulders picture). A generated character's mouth moves with the pose and the framing, and a mouth drawn off the lips is worse than a still character.
- **Rejected: a vision model's bounding box as the only detector.** It is a paid call per version, its boxes are not repeatable, and a machine whose AI Source has no vision model would get no mouth at all; the local landmark model is free, offline and the same every time.
