# ADR 0047 - The Docker card in Features

> Docker is what lets Scout run a pull request's tests before it gives a verdict; the owner sees whether it is there, turns it on in one place, and is told about it when GitHub is turned on.

## Status

- [x] Proposed
- [x] Accepted

Updated: 2026-11-07. v1.2 on the same day, while building part 1: the switch became Scout's own setting (the grant is per feature, see Decision); Repositories and Last run ship as their empty states ("Scout lists a repository's stack the first time it reads it.", "No run yet."), and their records follow once the sandbox writes them, a follow-up of the lane that changes `src/Scout.Sandbox`. The owner, translated: "I think it would be good to have a card for Docker, which will be important for the tests we are going to run", "when the GitHub feature is turned on it should say that it would be good to turn on Docker, because it is used in the testing process among other things", and, told that nothing of it existed in the desktop, "you can fix it, because this did not exist before and we are saying to put it in".

v1.4 on the same day, part 2: the repositories' stacks and the last run come from the records the worker writes (Decision, amended). v1.5, the same day: "Download images" and a repository's Download fetch exactly the images the repositories need (Images, amended).

v1.6, 2026-11-08: every Features card became a summary of one size whose Details opens a side panel from the right, so the Docker card's sections now live in the Docker side panel and the GitHub card's "Set up Docker" opens that panel (the Features side panel) rather than scrolling to the card (The GitHub card's hint, amended).

The owner, later the same day, translated: "if the person does not have .NET, Java or something like that installed, they could not run the project locally; if you put it in a container you would run it without doing anything on the user's machine."

## Context

[[pages/decisions/0043-the-verdict-on-a-pull-request]] runs a project's tests in a disposable container through `src/Scout.Sandbox` ([[pages/services/sandbox]]), only under the GitHub feature's `Local container` row ([[pages/decisions/0032-per-feature-write-permissions]]). Nothing in the desktop said whether Docker was installed or running, which images a run needs, or how much the work folder holds; the owner found out only when a verdict said "Docker is not installed or not running."

## Decision

- **Nothing to install but Docker.** The card opens with what makes it worth turning on: each stack's SDK (.NET, Node, Bun, Python, Go, and Java with Maven or Gradle) comes inside a pinned image, so Scout runs a project's tests on a machine that has none of them installed.
- **A Docker card in Features, beside GitHub.** It is not a feature of its own and declares no new function the model can call; it is the place where the owner sees and prepares what the GitHub feature's container runs need.
- **State.** Main runs `docker version --format '{{json .}}'` (the configured `docker` path, a subprocess, a declared read) when Features opens and when the owner presses Refresh, never on a timer. The card shows Not installed (with a link to Docker's install guide), Installed but not running, or Running with the server version. A run that times out (5 s) or fails reads as not running, with the reason in the log.
- **The switch is Scout's own on/off for Docker runs** (amended in v1.2). "Run a project's tests in isolated containers" writes the public vault key `sandbox.enabled`; main passes `SCOUT__SANDBOX__ENABLED=true` to the worker only while it is on, and restarts a running worker when it changes. The host's sandbox adapter (`src/Scout.Host.Console/SandboxRunnerAdapter.cs:11`) reads `Scout:Sandbox:Enabled` and, while it is not true, answers `Ran=false` with "Docker runs are off in Scout Desktop; turn them on in Features, Docker." without calling the runner. A run still needs the GitHub feature's write grant as well (ADR 0043), and the card says so: "Runs also need GitHub's write permission in its card." The switch is disabled until GitHub is connected; while Docker is not running it can still be turned on, and the card says runs wait for Docker.
  - Why not the `Local container` row, as v1.0 said: the write grant is per feature (`SetWriteGrantRequest { id, granted, confirm_writes }`, `FeaturesService.SetWriteGrantAsync`, and the gate's `if (!state.Granted)` in `src/Scout.ControlPlane/WriteGate/WriteGateService.cs:344`), so a switch on that row would grant or revoke every GitHub write. A grant per row would be a change to ADR 0032 and the control plane; the owner's own setting gives the card its switch without one.
- **What Scout uses Docker for**, shown on the card in the words of ADR 0043: a pull request's own tests before a verdict, when no check ran them or the review asks for one; the project's tests only, never Scout's own code; the network on only to restore packages and off during the tests; one disposable container per run, deleted after it; 20 minutes at most.
- **Images.** The card lists the pinned images grouped by stack (.NET, Node, Bun, Python, Go, Java (Maven), Java (Gradle)), each group with how many are present (`docker image inspect`, a read) and its own Download, which runs `docker pull` of that stack's missing references, one at a time, with progress (amended in v1.2: there are 20 images and Docker Hub limits anonymous pulls; amended in v1.3: 33 images, the .NET, Node, Python and Go groups now holding one image per version the sandbox runs ([[pages/services/sandbox]]), and the Java images are several hundred MB each, so nothing pulls all of them). "Download images" fetches only the images the repositories Scout has read need; until that list exists it stays disabled and says so. Built in v1.5: one pinned image per repository record that Docker lacks, each once, one at a time with its progress, a repository whose version Scout refuses skipped, the first failure stopping the rest; disabled while Docker is not running and when nothing is missing, then saying "Every image your repositories need is downloaded." (`ui/packages/renderer/src/app/features/docker-card.component.ts:1226`). Each image goes through main's `pullImage(reference)` (`ui/packages/main/src/docker/docker.ts:314`), the stack pull's loop for one pinned reference, which refuses any other reference before calling `docker`. A pull answered with 429 or `toomanyrequests` says "Docker Hub is limiting downloads; try again later." Every pull writes only into Docker's own image store, starts only from the owner's click, and is logged. The pinned list has one source, `src/Scout.Sandbox/SandboxStacks.cs`; main's copy is pinned to it by a test that reads that file, so the two cannot drift.
- **Work folder.** Main owns the path, .NET's `LocalApplicationData/Scout/sandbox` on each OS (`XDG_DATA_HOME` or `~/.local/share` on Linux, `~/Library/Application Support` on macOS, `%LOCALAPPDATA%` on Windows), and passes it to the worker as `Scout:Sandbox:WorkDirectory`, so both read the same folder. The card shows the path and its size; "Clear" deletes the folder's contents after a confirmation and never runs while a container run is in progress.
- **Each repository's stack, known on access.** There is no place where the owner types a stack. The owner, translated: "we already know it when we access the repository, so we would already know what we need to work with". When Scout takes a repository snapshot (a review, a verdict or an audit), it runs the sandbox's own detection on it (the manifests and the declared versions, read as text, never by running the build) and keeps the answer per repository under Scout's data folder: the stack, the declared versions, the pinned image a run would use, or the sentence saying why none would run. The card lists each known repository with that answer and whether its image is downloaded, with "Download" for a missing one (that image only, since v1.5); a version Scout does not support shows there before any pull request asks for a verdict.
  - Built in v1.4. The record lives **beside the snapshots**, `<github-snapshots>/<owner>__<repo>.stack.json`, one per repository, rewritten each time a snapshot of it is taken or reused (`src/Scout.Plugin.GitHub/RepositorySnapshotStore.cs:189`). Not in the work folder: "Clear" deletes the work folder's contents and refuses while a folder in it is younger than 21 minutes, so a record there would vanish with the run logs and a folder for it would block Clear after every snapshot. Main reads the folder as the sibling of the work folder, `LocalApplicationData/Scout/github-snapshots` (`githubSnapshotsFolder`, `ui/packages/main/src/docker/docker.ts:225`), the worker's default; a `Scout:Plugins:GitHub:SnapshotsDirectory` set outside Scout Desktop is not seen by the card.
  - The detection is the sandbox's own (`DockerSandboxRunner.Detect`, `src/Scout.Sandbox/DockerSandboxRunner.cs:168`), reached by the GitHub plugin through `IStackDetector` (`src/Scout.Plugin.GitHub/Abstractions/IStackDetector.cs:8`), which the host implements (`src/Scout.Host.Console/StackDetectorAdapter.cs:10`), so neither library references the other. It runs whether Docker runs are on or off: it reads files and runs nothing.
  - The record: `repository`, `commit`, `stack`, `image` (by digest), `runs` (the tool and version in the image, "Node 20.20.2"), `declared` (each declared version with its file, `.nvmrc` asks for `Node 20`; a Gradle project can declare a JDK and a Gradle version), `refusal` (the sentence, with `image` null), `detectedAt`. A detection or a write that fails is logged and changes neither the snapshot nor the review (`src/Scout.Plugin.GitHub/GitHubActionsPlugin.cs:702`).
- **Last run.** The card shows the newest run: repository, pull request, stack, result and duration, from a small record the sandbox writes beside each run's log under the work folder.
  - Built in v1.4: `<id>.run.json` beside `<id>.log` (`src/Scout.Sandbox/DockerSandboxRunner.cs:254`), with `repository` and `pullRequest` (which `run_pull_request_tests` now passes), `stack`, `image`, `result` (`passed`, `failed`, a failed restore included, or `notRun` with `reason`, such as the 20-minute limit or a work folder Docker cannot see), `exitCode`, `durationSeconds` and `finishedAt`. Only a run that reached its work folder writes one: Docker missing, no snapshot or no stack leave no log and no record, and neither do Docker runs off in Scout Desktop or no runtime configured, which never reach the sandbox. "Clear" deletes the records with the logs, and the card says "No run yet." again. A record that cannot be written is logged and the run's result is unchanged.
- **Sections the owner can hide** (v1.2, the owner, translated: "the Docker card must have the option to hide things so everything is not always open"). The header (the opening sentence, the status chip, Refresh) and the switch always show; what Scout uses Docker for, the images, the repositories, the work folder and the last run are each a section that closes to a one-line summary ("Images: 3 of 5 downloaded", "Work folder: 184 MB", "Repositories: none read yet"). They start closed, except the images while Docker runs and one is missing; the owner's choice per section is remembered in the renderer's storage, and storage that cannot be read or written falls back to that default.
- **The GitHub card's hint.** While GitHub is connected and Docker is not running or Docker runs are off, the GitHub card shows: "Turn on Docker to let Scout run a pull request's tests in an isolated container before it gives a verdict.", with "Set up Docker", which scrolls to the Docker card (amended in v1.6: it opens the Docker side panel, the Features side panel, with the focus on its close button; there is no card to scroll to, since the card is a one-size summary).

- **Later, more run kinds.** The owner, translated: "Docker would be for when you want to run something; if nothing is installed on the machine it is easier to do it straight in Docker". Docker is the one place Scout runs anything, never the host. Other run kinds (building, linters and analyzers, reproducing a reported bug) are F19 on [[pages/roadmap/future-improvements]], each with its own ADR under the same container rules; this ADR ships the card and the tests run of ADR 0043 only.

## Consequences

- **Better:** the owner learns Docker matters at the moment GitHub is turned on, sees its state in one place, and can pull the images before the first verdict instead of during it.
- **Worse:** main gains a `docker` subprocess (state, image presence, pull) and one owner-triggered write into Docker's image store; each call needs its failing-call test (Rule I).

## Tests the lane ships

- main: the three states from `docker version` (exit 0 with a server version, exit non-zero with a client only, the command missing), a timeout read as not running (Rule I), image presence from `docker image inspect`, a pull that fails midway reported in a sentence and the rest not started, Clear refused during a run, the work-folder path passed to the worker.
- the pinned list equal to `SandboxStacks.cs`.
- worker: Docker runs off answers the sentence and never calls the runner; on, the run goes through (`tests/Scout.Host.Console.Tests/HostSandboxCompositionTests.cs`).
- part 2 (v1.4): the sandbox's detection per stack and its refusals (`tests/Scout.Sandbox.Tests/SandboxDetectionTests.cs:63`), the run record for each result kind and its failed write (`tests/Scout.Sandbox.Tests/SandboxRunRecordTests.cs:48`, `:129`), the stack record on a snapshot taken, reused and refused, and a failed detection or write logged with the snapshot and the run unchanged (`tests/Scout.Plugin.GitHub.Tests/GitHubActionsPluginStackRecordTests.cs:53`, `:120`), the host's detector and the repository and number reaching the run's record (`tests/Scout.Host.Console.Tests/HostSandboxCompositionTests.cs:163`, `:186`), main's reads with malformed records skipped and none read as empty (`ui/packages/main/test/docker.test.ts:532`), and the card's rows (`ui/packages/renderer/src/app/features/docker-card.component.spec.ts:584`, `:954`); v1.5: `pullImage` refusing an unpinned reference with no `docker` call, its 429 and failure rows (`ui/packages/main/test/docker.test.ts:695`), and Download images over records, missing images and Docker running, the exact images it pulls, and a row pulling only its own image (`ui/packages/renderer/src/app/features/docker-card.component.spec.ts:831`, `:584`). v1.6: "Set up Docker" switching the side panel to Docker with the focus on its close button (`ui/packages/renderer/src/app/features/github-connect.component.spec.ts:1337`).
- renderer: the card's states, the switch writing `sandbox.enabled` and restarting a running worker, the sections' defaults, toggles, remembered choices and summaries, the confirmation before Clear, the GitHub hint shown for every combination of GitHub connected or not, Docker not installed, not running or running, and Docker runs on or off.
