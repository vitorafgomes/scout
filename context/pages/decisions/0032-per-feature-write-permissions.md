# ADR 0032 - Features declare what they write, and the owner grants each one

> A Scout feature says exactly which reads and which writes it performs; the owner turns each feature on in the desktop and, for a write that cannot be undone, approves each action there; the model and the chat can only ask, never grant.

## Status

- [ ] Proposed
- [x] Accepted
- [ ] Deprecated / superseded by

Updated: 2026-11-10. Accepted on the owner's decision while planning a YouTube channel operator: "before, we only did reads, but there can be things that read and write", "we can have different features and each one has a different permission", "creating content for a channel has to do a lot of things".

## Context

Scout was founded read-only: [[pages/decisions/0009-descriptive-vs-executive-writes]] permitted descriptive writes (content a human or agent reads and decides on, posted in the originating channel) and forbade executive writes (anything that mutates code, infrastructure, configuration, data or the host), with boundary cases defaulting to forbidden; [[pages/invariants/no-executive-writes]] carries the rule into the code and the review gate's `read-only` lens checks every change against it. That contract made the first plugins safe to ship fast: GitHub, Kubernetes and YouTube ([[pages/decisions/0030-youtube-plugin-read-only-with-browser-sign-in]]) are GET-only, and the only host writes so far are Scout's own configuration and its own installation ([[pages/decisions/0031-desktop-self-update]]).

The next product the owner wants is a channel operator in the shape of `darkzOGx/youtube-automation-agent`: research, script, narration, visuals, an assembled video, a review step, upload and scheduling on YouTube, comment handling and a learning loop over the channel's analytics. Most of that is production of files on the owner's machine and reads of YouTube; two steps are executive writes to an external system (upload, schedule) and more will follow (replying to comments, title and thumbnail experiments). A product that stops one step before publishing is not what the owner asked for.

The control plane already carries the seed of the answer: every feature in the catalog declares a `WriteClass` (`None`, `Descriptive`, `Executive`) and a scope matrix of the calls it makes, and the owner enables features one by one on the Features screen ([[pages/services/control-plane]], [[pages/services/desktop-ui]]). Until now every feature declared `None`.

## Decision

- **Scout is a chatops assistant whose features may read and write; each feature declares which.** The catalog entry of a feature is its contract: `WriteClass` (`None`, `Descriptive` or `Executive`) and a scope matrix with one row per call it makes, marked `read`, `write` or `write (irreversible)`. A feature that performs a write it did not declare is a bug the review gate rejects. Rule A of the team rules becomes: every call that leaves the process is declared by its feature; undeclared writes never ship.
- **The owner grants write permission per feature, in the desktop.** A feature with `WriteClass.Descriptive` or `Executive` starts disabled and shows its write rows on the Features screen before the owner enables it; enabling is the grant. Reads never need a grant beyond the credential the feature uses. The grant lives with the feature state in the control plane, never in a chat.
- **Irreversible writes ask for a per-action approval, in the desktop.** Uploading or scheduling a video, deleting anything, publishing a comment reply, changing a live title or thumbnail: each such action is queued with what will be done, and runs only after the owner approves it on a review screen of the desktop. The queue is visible, approvals are logged, and an approval covers one action. Reversible writes under a granted feature (a draft saved to Scout's own folder, a scheduled job the owner can cancel) run without a per-action prompt and are logged.
  - Amended 2026-11-07 on the owner's request (translated: "if the person asks for a code review and it is approved by the bot, it must show in the chat for them to approve, not make them go to another menu"): an action waiting for approval is also shown as a card in the chat and in the quick-ask window, with Approve and Reject. It is still the owner's click in the desktop, on the same `scout:actions.approve` and `scout:actions.reject` channels as the Approvals screen; Approve is never focused by default and sends once. Once an action is decided anywhere it leaves every window's waiting cards and the Approvals count, and shows only as history and as the outcome on the card where it was decided ([[pages/services/desktop-quick-ask]], Approval cards; [[pages/services/desktop-ui]], Approvals). The model and the chat message still cannot approve.
  - Amended 2026-11-08 on the owner's decision ("ok for all", decision E of the Settings and Features review): revoking a feature's writes rejects the actions of that feature that have not started, those still waiting in Approvals and those approved but not yet claimed by a worker, with the reason "writes were revoked", so none is left approvable or approved but never run (the approved ones on the manager's decision of the same day; a YouTube action already approved keeps the operator's own revoke reason). Every call that clears the grant does it: Revoke writes, disabling the feature, deleting its credentials and an enable whose activation fails.
  - Amended 2026-11-08 on the manager's decisions of the Approvals review: **an approval needs the grant.** The owner's Approve is refused while the feature holds no grant, and an action asked before the current grant began is rejected with "asked before writes were granted; ask again" and the approval refused, because no worker would ever run it. **The grant is read once more just before an irreversible action is sent**: between the worker's claim and the call that cannot be undone, the worker asks the control plane whether the grant the action was asked under still holds; when it does not, the control plane rejects the action with "writes were revoked" and nothing is sent, and a check that cannot be answered sends nothing either. The same read runs before every irreversible call of the YouTube operator, an upload, a thumbnail, an experiment arm, a reply and a hold. An action a worker claimed before the current grant, or while no grant is left at all, and never finished is rejected, "Scout was running it when writes were revoked and it never finished; ask again", once its 30-minute claim lapses, so it never stays running forever. An approval turned into such a rejection keeps its card in the chat and the quick-ask window as Rejected with that reason (manager default; the owner may override).
  - Amended 2026-11-08 after an audit turn opened 58 issues in about 25 minutes under the GitHub grant alone (the owner, translated: "it is still opening issues for everything"): **a new issue is irreversible.** An issue notifies the repository's watchers and stays in its history even when closed, so GitHub's `New issues` row is `write (irreversible)`: every `create_issue` call, asked in chat or by an audit card's Open issues, is queued with its arguments (title, body, labels) as the action's payload and waits for the owner's approval of that one issue, on its card in the chat, the quick-ask window or Approvals; a turn that asks for N issues leaves N cards and opens none on its own. An approved issue is opened by the worker's GitHub executor from that payload, through the same checks the function applies (`GitHubWriteRunner`, `src/Scout.Plugin.GitHub/GitHubWriteRunner.cs:21`; dispatched at `src/Scout.Host.Console/GitHubActionExecutor.cs:154`), after the grant is read once more, and recorded with the issue's link and the login that signed it; a refusal, a GitHub failure or a timeout is recorded as failed with its reason and the issue is never handed to a worker again.
  - Amended 2026-11-09 on the owner's report that the same turn also flooded a pull request with comments (31 on one pull request): **a comment is irreversible too.** A comment on a pull request's conversation or on an issue, and a reply to a review comment, notify everyone following the thread the moment they exist, so GitHub's `Pull request comments` and `Issue comments` rows are `write (irreversible)`: every `comment_on_pull_request`, `comment_on_issue` and `reply_to_review_comment` call is queued with its arguments as the action's payload and waits for the owner's approval of that one comment, and the executor posts it exactly as asked after the approval, by the same runner and under the same grant read. The model is told the call is queued, never a URL, and the bundled skills tell it to say so and never to ask again for the same finding or comment ([[pages/services/skills]]). The tests line of an approved verdict is still posted by the executor as part of that verdict.
  - Amended 2026-11-09 on the owner's decision of that day: **a review is irreversible too, and the click on Post is its approval.** A review notifies the pull request's author and everyone following it the moment it exists, so GitHub's `Pull request reviews` row is `write (irreversible)` (`src/Scout.ControlPlane/Features/FeatureCatalog.cs:100`). The owner's click on Post on a review card is the owner's approval of that one review, as a click on Approve or Request changes already was for a verdict ([[pages/decisions/0043-the-verdict-on-a-pull-request]]): the card sends the chosen comments to the control plane on the verdict's channel as the verdict `comment`, never through the model, and the control plane queues the review already approved, with its payload, on the reviews row, logs the approval and answers the same action to a second click on that pull request and commit (`src/Scout.ControlPlane/WriteGate/PullRequestVerdictService.cs:178`); the worker's executor posts it once, as a review that only comments, after reading the grant once more, and records its link and signer or the reason it failed, which the card shows (`src/Scout.Host.Console/GitHubActionExecutor.cs:155`, `src/Scout.Plugin.GitHub/GitHubWriteRunner.cs:89`). A `submit_pull_request_review` call by the model never posts: it is queued with its arguments and waits for the owner's Approve on its card, like an issue (`src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:136`). With this no GitHub write runs under the grant alone; what still does is Scout's own data folder and the local container. Tests: `tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs:76` (a model call posts nothing and leaves one card), `tests/Scout.ControlPlane.Tests/WriteGate/PullRequestVerdictServiceTests.cs:75` (the click queues it approved once, on the reviews row; a second click answers the same action), `tests/Scout.Host.Console.Tests/GitHubActionExecutorTests.cs:149` (posted as comments only, link and signer recorded), `:171` (a 502 recorded as failed with the reason), `ui/packages/renderer/src/app/core/review-findings.component.spec.ts:419` and `ui/packages/main/test/ipc-github-verdict.test.ts:160` (the card and main).
  - Amended 2026-11-09 (same lane): **nothing rides into an approved action beside what the function takes.** The payload queued with an irreversible call carries only the arguments of the function's own parameters (`src/Scout.Llm/Guard/WriteGateFilter.cs:131`); an argument the model adds that the function does not declare is left out. Before this a chat `give_pull_request_verdict` call carrying an undeclared `testsLine` was queued with it, and the executor posted that line as a comment once the owner approved the verdict, a comment the owner never saw (`tests/Scout.Llm.Tests/Guard/WriteGateCompositionTests.cs:91`, `tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs:241`).
  - Amended 2026-11-10 (same lane, after its review): **an approved action is sent at most once, and when Scout cannot know whether it was sent it does not send it again and says so.** For a feature that declares that its worker cannot tell whether a claimed, unrecorded action was sent (`UnrecordedClaimMayHaveBeenSent`, `src/Scout.ControlPlane/Features/FeatureMetadata.cs:49`; GitHub, `src/Scout.ControlPlane/Features/FeatureCatalog.cs:154`), the shared claim records an action whose claim lapsed with no write in the log as failed, saying it may already be on GitHub and to look there before asking again, and never hands it out again (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:179`; `tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs:163` over the five GitHub rows). It is one claim with one order of checks, joined with the amendment of 2026-11-09 below: a write already in the log settles the action as executed; else the lapsed claim of such a feature is failed as not confirmed; else the action is handed out, and only with its approval in the log (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:519`). YouTube does not declare it: its lapsed claim with no record is handed out again, as the branch had it, and the duplicate risk stays open there ([[pages/roadmap/followups]]). Before this such an action was handed out again after 30 minutes and a worker that had restarted sent it a second time. The worker now runs the approved actions one after the other until none is left or one cannot be recorded, then waits for its 10-second tick, so twenty approved issues no longer take twenty ticks (`src/Scout.Host.Console/GitHubActionExecutor.cs:59`; `tests/Scout.Host.Console.Tests/GitHubActionExecutorTests.cs:530`, `:604`). The summary on the owner's card lists only the function's own parameters (`src/Scout.Llm/Guard/WriteGateFilter.cs:122`; `tests/Scout.Llm.Tests/Guard/WriteGateFilterTests.cs:174`). Main refuses Stop for a turn that queues a card's issues, as it already refused a new question and Clear (`ui/packages/main/src/quick-ask/quick-ask.ts:1364`; `ui/packages/main/test/quick-ask.test.ts:264`).
  - Amended 2026-11-10 (closing round of the same lane): the same sentence is used when such a claim lapsed across a revoke or a new grant, where the action was rejected with "it never finished; ask again" although it may be on GitHub (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:124`; `tests/Scout.ControlPlane.Tests/Integration/ApprovalsGrpcTests.cs:148`, `:176`). A failure to write the not-confirmed record, in the log or in the queue, fails the claim, hands out nothing and leaves the action executing until its next lease (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:551`, `:583`). The executor sends approved actions at least one second apart, so a batch of approved issues or comments does not reach GitHub as a burst (`src/Scout.Host.Console/GitHubActionExecutor.cs:64`; `tests/Scout.Host.Console.Tests/GitHubActionExecutorTests.cs:530`), and a review the model asks for with a card's commit added to its arguments stays its own waiting action that a later Post on the card neither adopts nor approves, because the queued payload keeps only the function's parameters (`tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs:218`). The worker's executor keeps no note of what it sent, since an action reaches it once; the proof that a write a worker sent and never recorded is not sent again is over the real queue (`tests/Scout.Host.Console.Tests/GitHubIssueApprovalTests.cs:163`). The review card names what a click writes to, the repository, the pull request and the first seven characters of the commit, beside Post, Approve and Request changes (`ui/packages/renderer/src/app/core/review-findings.component.ts:1132`; `ui/packages/renderer/src/app/core/review-findings.component.spec.ts:591`).
- **The model and the chat can only request.** No chat message, no system prompt and no function result can grant a permission or approve an action. A function the model can call that performs an executive write first checks that its feature holds the grant and, when the action is irreversible, enqueues it for approval instead of running it; the model is told the action is waiting for the owner. Scout's local quick-ask window counts as chat. Amended 2026-11-08: so main accepts a grant only from the main window; a grant asked from the quick-ask or the operator window is refused.
- **Every write is logged** with the feature, the action, the target, the time and who approved it, in Scout's own logs and on the desktop's Logs screen, and a feature's recent writes are visible on its card.
  - Amended 2026-11-08: **every decision is logged too.** The owner's approval reads `approved`, or `approved: <reason>` with a reason; the owner's rejection `rejected` or `rejected: <reason>`; each rejection a cleared grant causes, each stale card verdict swept aside and each claimed action rejected by the checks above gets its own `rejected: <reason>` entry, so the History tab of Approvals shows every outcome.
  - Amended 2026-11-09: **a logged write is never handed out again and never rejected as never finished.** Before a claim hands an action to a worker, and before a claimed action is rejected, the control plane looks the action's id up in the write log; an entry that is not the owner's approval is the record of the attempt, so the action is marked executed with that outcome. A write log that cannot be read hands out nothing. **An approval that cannot be logged rejects its action:** when the YouTube operator queues an action already approved (a publish, an experiment's switches, an adopted winner, a hold, a reply) and the `approved` entry cannot be appended, the action is rejected with "its approval could not be logged; approve it again", the rejection is logged when the log takes it, and the project or the comment returns to what it was, so the owner approves again. **An approved action is handed to a worker only when its approval is in the write log:** the claim hands out nothing without it. The approval is saved in the queue and logged right after, so for one minute after the approval the claim leaves an action whose entry is not there yet approved, for the next poll; one still without it after that minute is rejected, "its approval is not in the write log; approve it again", and the rejection logged, so an approval the log never took cannot run. That also covers the Approve of a waiting action and a card verdict, which do not reject on their own when the entry cannot be appended.
  - Amended 2026-11-12 (issue #323): **a reversible write is in the write log before it runs.** For a `write` row the gate appends a `started` entry and answers its id with `allowed`; when that entry cannot be appended the request fails and the write does not run; the worker's record carries that id and appends how the write ended; a `started` entry with no record 30 minutes later is listed as `not confirmed: Scout stopped before it recorded how this ended, so it may have run`, and nothing sends that write again. A record that fails while the worker runs still leaves the function's result and one Warning; it now leaves the `started` entry too.
- **Credentials follow the grant.** A credential with write scopes (a YouTube token with `youtube.upload`, a GitHub token that can write) is requested only when a feature that needs it is granted, with the scope named on the card; a read-only feature keeps read-only scopes. Amended 2026-11-08: a grant never outlives the account it was given for; any change or loss of the feature's credential revokes it, for GitHub as for YouTube; a revoke the control plane cannot take at that moment is kept by main and sent again as soon as the control plane is back, and until then the feature never counts as granted for the worker; a write scope requested for a grant the control plane then does not record is dropped again. The owner allow-list ([[pages/decisions/0021-allowed-users]]) still gates who can make Scout act, and a write-capable feature answers only listed users.
- **The guard adapts.** The read-only guard in the LLM path ([[pages/services/llm]]) stops refusing write intents outright and instead refuses writes for which no granted feature exists, naming the feature to enable.
  - Amended 2026-11-02 on the owner's decision ("you can fix item 1"): the guard only pre-filters the request; with any grant it lets every request through, and it fails open. Enforcement moves to the moment the model calls a function: a function declares only its feature and catalog scope row, and every call to it asks the control plane, which consults the catalog and the live grant and answers allowed, queued or refused. Only allowed runs the function; a control plane that cannot be reached means no write.
- **What stays forbidden.** Writes to the host filesystem outside Scout's own folders, except the reviewed local writes on local models that the amendment of 2026-11-11 below rules (a feature that produces files writes under Scout's data directory and offers an export the owner clicks); any write by a feature without the grant; any approval that did not come from the desktop; writes in a chat other than the originating channel; secrets in source ([[pages/invariants/secrets-never-in-source]]).

## Consequences

- **Better:** Scout can be the channel operator the owner wants, and later other write-capable features, without a new founding debate each time: the catalog entry says what a feature does, the owner decides per feature, and the review gate has a precise thing to check. The audit trail is part of the product.
- **Worse:** the project's one-line promise changes from "it never writes" to "every write is declared, granted and logged"; the README, the project site and the pipeline's `read-only` lens all need the new wording, and every existing page that cites the absolute rule needs a date and a pointer here. A granted feature with a bug can write where it should not; the per-action approval limits that to reversible writes, and the logs make it visible.
- **Neutral but noteworthy:** GitHub and Kubernetes keep `WriteClass.None` and change nothing. Amended 2026-11-02 on the owner's decision ("everything has to stay inside the same feature"): `youtube` is the one feature of the channel operator and declares its read, write and irreversible rows under `WriteClass.Executive` ([[pages/roadmap/youtube-channel-operator]]); the plugin itself stays GET-only until the write rows are implemented. The desktop's self-update ([[pages/decisions/0031-desktop-self-update]]) and the own-configuration writes are unchanged and remain outside the feature grants.

## Alternatives considered

- **Keep Scout read-only and stop before upload** (the owner publishes from YouTube Studio). Rejected by the owner: "creating content for a channel has to do a lot of things".
- **One global switch "allow writes".** Rejected: it grants everything at once; the owner asked for a permission per feature.
- **Approval through the chat** (reply "yes" to publish). Rejected: anyone on the allow-list, or a prompt injection in a message Scout reads, could approve; the desktop is the only surface the owner alone controls.

## Amendment: one decision for a set of actions the owner was shown

**Proposed 2026-11-10, accepted by the owner on 2026-11-11** with the five answers recorded on [[pages/roadmap/approve-together]]. The code still approves one action per decision until that plan's phases land. The plan for the code is [[pages/roadmap/approve-together]]; the design is drawn in `context/prototypes/desktop/Main.dc.html` (the approval strip above the Chat composer, Approval states Group waiting to Group changed, and the findings card, Findings card states) and `context/prototypes/desktop/Review.dc.html` (Approvals, the Group states).

The owner, 2026-11-10, translated: "we are creating 10 issues or adding 10 comments on a pull request; there should be a way to approve everything at once. Even more so if the person is sent the list beforehand of everything that will be sent: there is no reason to approve one by one afterwards." The place he means is the strip in the Chat titled "Waiting for your approval".

### What happens today for a batch of ten

- **Ten issues from an audit card wait twice.** The card's Open issues is not an approval: it sends a chat question carrying the chosen issues behind a marker (`ui/packages/renderer/src/app/core/review-findings.component.ts:1222`, built at `ui/packages/renderer/src/app/core/review-findings.ts:137`), the `code-audit` skill tells the model to call `create_issue` once per issue (`src/Scout.Skills/skills/code-audit.md:56`), and each call passes the write gate (`src/Scout.Llm/Guard/WriteGateFilter.cs:56`) and is queued as pending (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:359`); the component says so (`ui/packages/renderer/src/app/core/review-findings.component.ts:1207`). The owner then sees ten cards in the strip (`ui/packages/renderer/src/app/core/approval-strip.component.ts:40`), each titled "Open an issue on acme/shop" (`ui/packages/renderer/src/app/core/pending-approvals.store.ts:104`), and ten rows in Approvals (`ui/packages/renderer/src/app/review/review.component.ts:141`), each approved by its own call with one id (`src/Scout.ControlPlane/WriteGate/ActionDecisionService.cs:361`).
- **Ten comments chosen on a review card are one action, already approved by Post.** The card's Post goes on the verdict channel, never through the model, as one review with the chosen comments on their lines, queued already approved (`ui/packages/renderer/src/app/core/review-findings.component.ts:1212`, `src/Scout.ControlPlane/WriteGate/PullRequestVerdictService.cs:178`). Ten separate comments exist only when the model calls `comment_on_pull_request` ten times, and then they are ten pending actions like the issues.
- **The owner does not see the text he approves.** The card's summary shows the values of the declared summary arguments only, the owner, the repository and the title for an issue and the owner, the repository and the number for a comment (`src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:137`, `:141`), so a comment's card names `body` and shows none of it; the payload that holds the text is handed only to the worker (`src/Scout.ControlPlane/Actions/PendingAction.cs:51`) and neither the desktop's action (`ui/packages/shared/src/ipc-contract.ts:682`) nor the control plane's message (`src/Scout.ControlPlane.Contracts/protos/features.proto:129`) carries it. The target the card shows is the function, `GitHubActions.create_issue`, not the repository (`src/Scout.Llm/Guard/WriteGateFilter.cs:52`).

### The rule

- **The unit of approval stays what the owner was shown.** One decision may cover a set of actions only when the desktop listed every action of the set before the decision: its kind, its target (the repository, the issue or pull request number, the commit when it has one) and the text that will be written, reachable in full. The decision covers exactly the listed actions, never one listed after it.
- **Listed, with the full text one click away, counts as shown.** This is the one place the rule relaxes "shown in full". A set is listed one line per action, the kind, the target and the first line of the text, and each line opens in place to the complete text that will be written (the title and body of each issue, the body of each comment), with one control that opens every line at once so the whole set can be read by scrolling. Approve all is offered once the list has been shown; it does not wait until every line was opened, and the lines the owner did not open stay marked as not opened. The same holds for the findings card, whose full issue text is behind its "See how the issues read" preview (`ui/packages/renderer/src/app/core/review-findings.component.ts:443`). Variants for the owner: the weaker one counts the card's summary alone as shown, with no full text in the desktop, which is what a single action has today; the stronger one enables Approve all only after every line was opened or the set was scrolled through with every line open. The recommendation is the rule as written: the stronger variant measures clicks and scrolling, not reading, and teaches the owner to open lines without reading them, while the rule as written already shows more than a single action shows today (the first line on every line, the full text one click away, where today no comment text is shown at all).
- **The set is fixed at the moment of the decision.** The decision carries the id of every action listed and a digest of each one's payload as the desktop received it; the control plane approves the set only when every id is still pending, belongs to the same group, and its payload still has that digest, and otherwise approves none and answers which did not match. An action added to the group after the listing, or a text changed after it, is not covered and waits on its own. A group grows while the request that makes it still runs, since the model queues its actions seconds apart: that is normal, the list updates as they arrive, the group says Scout is still queuing and how many so far, and Approve all is not offered until the request has ended and the group is closed; the listing that binds is the one shown after the close. A closed group that then changes, an action joining it or a payload whose digest no longer matches, is not normal: it says so and offers only per-action decisions from then on. A group that only shrank, because an action of it was decided in another window, is listed again with the new count. Nothing in the queue rewrites a pending payload today (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:98`, rewritten only once executed, `:536`), and a closed group takes no new action, so the digest and the closed-group check are defence in depth against a later writer, a changed `actions.json` or a bug in the close.
- **Each action is still its own row and its own write.** An approved set is N actions in the queue and N `approved` entries in the write log, each with its action id and the group's id; the claim, the at-most-once rule, the grant read before each send, the second between two GitHub writes (`src/Scout.Host.Console/GitHubActionExecutor.cs:64`) and the failure handling are those of a single action, unchanged. One that fails does not stop or roll back the others; the group then shows each action as sent, waiting or failed, with the reason. An approval entry the log does not take leaves that action to the existing one-minute check, which rejects it as "its approval is not in the write log; approve it again", so a log that fails part way through a set shows as part sent and part rejected, never as sent without its entry.
- **The owner can still decide one by one.** Each line keeps its own Approve and Reject once opened; after one is decided the foot reads "Approve the other 9". Reject all stands beside Approve all; Approve all is never focused by default, names the count, and sends once.
- **A group is one request, one feature and one repository, at most 50 actions.** A group is the actions one request queued (one chat turn, or one click on a findings card) on one feature and one repository; a request that touches two repositories makes two groups, so a header always names one place. Fifty is the most findings a card can carry (`ui/packages/renderer/src/app/core/review-findings.ts:14`), so a card can never make a set over the bound; a group over 50, which only a model turn can make (an audit turn once opened 58 issues), offers per-action decisions only and says why, because a request that size is itself the sign of a turn gone wrong.
- **A decision on the findings card in the desktop is the approval of exactly those actions.** Open issues on an audit card, as Post already does on a review card, sends the chosen issues, each title and body as the card's preview renders them, from the desktop to the control plane, never through the model; the control plane queues them already approved as one group, logs one `approved` entry per issue, and answers the same actions to a second click on the same card. They are not queued a second time in Approvals; they appear in History and the write log like every write. The card states what the click writes ("Open 6 issues on acme/shop") and that it is the approval ("This sends them now. Nothing else to approve."), then shows each issue's progress. The chat in Discord, Slack or Teams can never approve: actions asked there queue for the desktop, grouped as above.
- **The model can propose a set, never approve one.** Its calls in one turn form one group; the group's id comes from the turn the worker runs, never from a function argument, so the model cannot place an action in another request's group. It cannot mark a set approved, extend one after it was listed, or call anything that approves: no kernel function decides, and the set decision is a desktop channel answered only from the main and quick-ask windows, behind the control plane's token.

### Where this bends the rules above, and why

- **"An approval covers one action"** (the Decision, irreversible writes) becomes "an approval covers the actions it was shown". Acceptable: ten identical cards in a row are approved by reflex, which is the approval the rule meant to prevent; one decision on a listed, fixed set, with each text one click away, asks the owner for more attention, not less. Each action keeps its own log entry, claim and outcome.
- **The payload "handed only to the worker"** (`src/Scout.ControlPlane/Actions/PendingAction.cs:51`) is also shown to the desktop, the owner's own window, so the owner can read what will be written; it is still never part of the summary, never logged and never sent to a chat adapter. This strengthens a single action's approval too.
- **The audit card loses its second look.** Today an issue is chosen on the card and approved again in Approvals; with this rule the card's click is the only approval. This is what the owner asked for, and it matches the review card's Post since 2026-11-09.
- **What this weakens:** one click can now cause up to 50 irreversible writes where it caused one, so a mistaken click reaches further; and with the listing relaxation the owner may approve a text whose fifth line he never read, such as a link a prompt injection put into a comment the model wrote. The bound, the fixed set, the count on the button, Reject all and the per-line marks limit it; the owner decides whether that is enough (questions in [[pages/roadmap/approve-together]]).

### Alternatives considered

- **Keep per-action approval only.** Rejected as the only path: it is the approval fatigue the owner reports, and it does not show the text either. Kept as the fallback: a single action, a changed group and a group over the bound are decided one by one; a changed group keeps Reject all, since a rejection writes nothing (the owner's answer of 2026-11-11).
- **Trust this conversation for N minutes.** Rejected: it covers actions no one has listed yet, the model can fill the window, and it is a grant by another name, which only the Features screen gives.
- **Approve by feature** (everything GitHub queued). Rejected: it covers actions the owner never saw and is the global switch this ADR rejected, narrowed to one feature.
- **Approve by repository.** Rejected for the same reason; the repository is kept only as a bound on a group.

## Amendment: local models through the control plane are a reviewed local write

Decided by the owner on 2026-11-11 (issue #293). The control plane's `Models` service downloads and deletes a model of the local Ollama server, and its `Providers` service starts and stops a server Scout itself started. These change the owner's computer outside Scout's own folders and belong to no feature, so no grant and no approval queue applies to them. They are the same class as the desktop's own model download and delete ([[pages/architecture/desktop-models-system]], Writes): a reviewed local write on the owner's click.

- Only the desktop token reaches them; the worker token is refused by service.
- Nothing the model can call reaches them: the control plane declares no function for the model, and the worker holds no client for these services.
- A download logs one line when it starts and one when it ends; a delete logs one line saying how it ended. Each names the model. They are lines of the control plane host's log, not entries of the write log, which records writes made under a feature's grant.
- The desktop does not call `Models` today and does not keep the host's output. The change that makes the desktop call it keeps that output first.
- A new caller, or a new operation of this class, amends this section before it is written.
- Amended 2026-11-12: **the desktop's unload of Scout's own Ollama models is of this class.** The owner, 2026-11-11, translated: "when I stop using the Ollama service it should stop running on the machine".
