# Decisions

- [[pages/decisions/0001-platform-priority|ADR-001 - Chat platform rollout order]] - Decision on the rollout order of chat platforms: Discord first, then Slack and Teams, to limit the surface area of the first release.
- [[pages/decisions/0002-license-mit|ADR-002 - License choice (MIT)]] - Decision to release Scout under the MIT license, and what the license choice affects.
- [[pages/decisions/0003-shouldly-migration|ADR-003 - Shouldly over FluentAssertions]] - Decision to migrate test assertions from FluentAssertions to Shouldly after FluentAssertions moved to a commercial license.
- [[pages/decisions/0004-web-stack-angular|ADR - Web stack is Angular]] - Decision to use Angular for Scout's web surfaces.
- [[pages/decisions/0005-scout-desktop-m1-scope|Scout Desktop M1 scope and deferrals]] - Plan 5 bootstrapped Scout Desktop end-to-end. This ADR captures the technical decisions made during M1 and the explicit deferrals, so post-M1 work can build on the same foundation without rediscovery.
- [[pages/decisions/0006-models-screen-task-based|Models screen restructured by task (Transcription / Analysis / Translation)]] - Decision to restructure the Models screen around tasks (Transcription, Analysis, Translation) instead of a single Ollama model picker.
- [[pages/decisions/0007-ai-sources-screen|AI Sources screen for inference backend discovery]] - Decision to add an AI Sources screen for discovering inference backends, complementing the task-based Models screen.
- [[pages/decisions/0008-local-models-real-downloads|Real downloads for local models (Ollama pull + HF Whisper GGML)]] - The first iteration of \"Manage Downloaded Models\" used mocked state: clicking Download just flipped a flag in localStorage.
- [[pages/decisions/0009-descriptive-vs-executive-writes|Descriptive vs executive writes - refining the read-only invariant]] - Refines Scout's read-only invariant by distinguishing descriptive writes from executive writes.
- [[pages/decisions/0010-scout-host-kernel-accessor|ScoutHost.ResolvedKernel accessor for dynamic plugin registration]] - Decision to add a ResolvedKernel accessor on ScoutHost to support dynamic plugin registration.
- [[pages/decisions/0011-backend-frontend-grpc-uds|Backend-frontend transport - gRPC over Unix domain socket / named pipe]] - Scout's desktop app is Electron (Node main process + Angular renderer). The .NET backend runs as a supervised child process (sidecar).
- [[pages/decisions/0012-llm-communication-through-semantic-kernel|All LLM communication routes through Semantic Kernel (Scout.Llm gateway)]] - Decision that all LLM communication in Scout routes through Semantic Kernel.
- [[pages/decisions/0013-conversation-core-streaming-sink|Conversation core - cumulative streaming sink and pump-owned drive loop]] - Decision on the conversation core's cumulative streaming sink and pump-owned streaming across chat platforms.
- [[pages/decisions/0014-per-request-identity-gating|ADR - Per-request identity and disclosure gating (SelfInfo Path B)]] - Plugins run inside a singleton Semantic Kernel with singleton KernelPlugin instances, so they had no way to know *who* was asking or *where*.
- [[pages/decisions/0015-cloud-llm-providers-by-api-key|ADR 0015 - Cloud LLM providers configured by API key from the desktop]] - The AI Sources screen configures OpenAI and Gemini by API key stored in the OS keychain and passed to the worker as environment variables; subscription sign-in is not supported.
- [[pages/decisions/0016-jev-read-only-guard|ADR 0016 - TypeSafe's Jev as a read-only guard in front of the model]] - When a TypeSafe key is set, Jev judges each latest user message, in the context of the turns before it, before the model runs and Scout refuses the ones that ask it to change something; with no key nothing changes.
- [[pages/decisions/0017-provider-connect-disconnect|ADR 0017 - Connect and disconnect cloud LLM providers, one key per provider]] - Each cloud provider keeps its own API key, checked against the provider's model list before it is stored; a stored key can be removed, and removing the one in use switches Scout to another connected cloud provider or to None, never to Ollama.
- [[pages/decisions/0018-chatgpt-plan-sign-in|ADR 0018 - ChatGPT plan through Sign in with ChatGPT]] - The ChatGPT Plus card signs in through OpenAI's official browser flow for open-source local apps; the desktop owns the tokens and the worker answers through the Responses API inside Semantic Kernel.
- [[pages/decisions/0019-github-app-device-flow|ADR 0019 - GitHub through a read-only GitHub App and the device flow]] - The desktop connects GitHub through a read-only GitHub App with the device flow, or with a token the owner pastes; one credential at a time, held by main.
- [[pages/decisions/0020-kubernetes-from-local-kubeconfig|ADR 0020 - Kubernetes from the kubeconfig on this computer, with consent per context]] - Scout reads the owner's own kubeconfig in place, only for the contexts the owner ticks, through a GET-only plugin with no logs, secrets, exec or watch.
- [[pages/decisions/0021-allowed-users|ADR 0021 - Only allowed users can use Scout once an owner credential is connected]] - The conversation core answers only the platform user ids the owner lists in the desktop app; with an empty list it refuses everyone once GitHub, Kubernetes or the ChatGPT plan is connected, and answers everyone otherwise. The owner can add a user by sending a one-time code to the bot in a direct message.
- [[pages/decisions/0022-discord-setup-from-the-bot-token|ADR 0022 - Discord setup from the bot token]] - The desktop sets up the Discord bot from the pasted bot token alone: it reads the application, turns on Message Content, and adds the bot to a server through a plain bot invite.
- [[pages/decisions/0023-slack-setup-from-a-manifest|ADR 0023 - Slack is set up from a prefilled app manifest and two pasted tokens]] - The desktop opens Slack's app creation flow prefilled with Scout's Socket Mode manifest; the owner pastes the bot token and the app-level token, main checks both with Slack and keeps them in main-only vault keys, and the worker gets them as the two keys SlackOptions binds.
- [[pages/decisions/0024-voice-messages-transcribed-locally|ADR 0024 - Voice messages are transcribed locally, after the allow-list]] - A Discord voice message is downloaded and transcribed on the owner's machine by a local Whisper model, only after the sender passes the allow-list and within 25 MB and 5 minutes, and the transcript is answered like typed text.
- [[pages/decisions/0025-teams-inbound-endpoint|ADR 0025 - Teams reaches the worker through one validated loopback endpoint behind a persistent dev tunnel]] - Scout receives Teams activities on a single POST /api/messages route bound to 127.0.0.1 in the worker, exposed by an owner-created persistent dev tunnel, registered as a Teams-managed bot, with Bot Framework JWT validation by a maintained SDK that cannot be switched off.
- [[pages/decisions/0026-live-voice-conversation|ADR 0026 - Live voice conversation in Discord through Discord.Net, local speech, allowed speakers only]] - Scout joins a Discord voice channel only on an allowed user's command, uses Discord.Net with libdave for DAVE, drops audio from non-allowed speakers before any buffering, transcribes and speaks locally, and hands each utterance to the conversation core as an ordinary chat message.
- [[pages/decisions/0027-desktop-presence|ADR 0027 - Scout stays resident on the desktop: tray, keep running, start at login, notifications]] - Closing the window hides Scout to the system tray and keeps the worker running; the owner can start Scout at login with --hidden; three native notifications; without a tray Scout keeps the old quit-on-close behaviour.
- [[pages/decisions/0028-local-quick-ask-assistant|ADR 0028 - Quick ask: talk to Scout from the operating system, over the worker's stdio]] - A global shortcut opens a small desktop window where the owner types or holds Space to talk; main writes one JSON request per line to the worker's stdin and reads the reply as SCOUT_LOCAL lines on stdout, and the conversation core trusts that message as the local owner.
- [[pages/decisions/0029-project-site-and-releases|ADR 0029 - Project site on GitHub Pages and desktop packages as GitHub Releases]] - A static one-page site in docs/ on the main branch describes Scout and links to the latest release; a version tag builds the desktop packages on three runners and publishes them as a GitHub Release with the gh CLI; the tag is the only source of the version.
- [[pages/decisions/0030-youtube-plugin-read-only-with-browser-sign-in|ADR 0030 - YouTube plugin: read-only over the official APIs, signed in from the desktop through the browser]] - Scout reads YouTube through the Data API v3 (and, in a later phase, the Analytics API v2) with plain HTTP GETs; the owner signs in from the desktop through the system browser with OAuth 2.0 and PKCE, or pastes an API key for public data; tokens live in the desktop keychain vault and reach the worker through a 0600 token file; the plugin never posts, uploads, edits or schedules anything on YouTube; the write rows the catalog entry declares since ADR 0032 are implemented in later phases of the channel operator.
- [[pages/decisions/0031-desktop-self-update|ADR 0031 - Scout Desktop updates itself only on the user's click, and only its own installation]] - The desktop may replace its own executable with a GitHub Release the user chose by clicking Update and restart; the model and the worker never reach that path; macOS and .deb keep a download link until signing or a package repository exist.
- [[pages/decisions/0032-per-feature-write-permissions|ADR 0032 - Features declare what they write, and the owner grants each one]] - Scout is no longer read-only by definition. Each feature declares the reads and writes it performs; the owner grants a feature's write permission in the desktop, irreversible actions ask for a per-action approval there, every write is logged, and a chat message or the model can never grant a permission or skip an approval. Supersedes the absolute prohibition of ADR 0009; keeps its classification.
- [[pages/decisions/0033-channel-operator-architecture|ADR 0033 - Channel operator architecture: state in the control plane, pipeline in Scout.Operator, media through the connected AI Source, progress back to the originating channel]] - The YouTube channel operator keeps its state (mandate, video projects, scenes, packages) in the control plane as the single writer, runs its pipeline in a new C# library Scout.Operator inside the worker, generates speech and images only through Semantic Kernel services of the connected provider (local fallbacks otherwise), and reports progress later into the channel the request came from.
- [[pages/decisions/0034-live-transcription-on-the-local-adapter|ADR 0034 - Live transcription on the local adapter: PCM16 chunks in, partial and final text out]] - The desktop streams 16 kHz PCM16 microphone chunks to the worker over the local adapter's stdin as listen, audio and stop requests; the worker cuts utterances with an RMS energy check, decodes cumulative windows of the utterance, the first at 0.75 s and then every 0.6 s, greedily for partial text, dropping a window while the model is busy, re-decodes each ended utterance with a beam of 5 for its final text, and shares the one loaded Whisper model with voice messages.
- [[pages/decisions/0035-screenshot-attached-to-a-question|ADR 0035 - A screenshot attached to a question: one JPEG on the ask line, an image part for a provider that can see, a plain sentence otherwise]] - The quick-ask window may attach one screenshot the owner captured to the next text or voice question; the worker accepts it only as a JPEG of at most 3 MB on the ask line, sends it to the connected AI source as an image part of the user message when that source can read images, and otherwise answers with one sentence saying it cannot, without calling the model; the picture is never stored and never logged.
- [[pages/decisions/0036-text-read-from-a-screenshot-by-a-local-ocr-program|ADR 0036 - Text read from a screenshot by a local OCR program: the bundled tesseract on the JPEG bytes, through standard input and output]] - The quick-ask window may ask the worker to read the text on a screenshot; the worker answers a read request by running the bundled tesseract on the JPEG bytes through standard input and output, with the languages from the app's locale, a 3 s budget and a 5,000-character cap, and registers the reader only when the program and its language data are on the configured paths; the image and the text are never stored and never logged.
- [[pages/decisions/0037-meetings-kept-locally-in-sqlite|ADR 0037 - Meetings kept locally in SQLite: only when the owner keeps one, under Scout's data folder, deleted with VACUUM]] - A meeting, its transcript lines with their translations and the questions the owner asked during it, is stored only when the owner chooses Keep this meeting, in one SQLite file under Scout's data folder named by Scout:Meetings:DbPath; it is listed, exported to Markdown and deleted from the desktop, a delete scrubs the text with secure_delete, VACUUM and a WAL checkpoint, and nothing of it is ever sent anywhere or logged.
- [[pages/decisions/0038-code-quality-assistant-on-the-write-gate|ADR 0038 - The code quality assistant: GitHub reads and writes on the write gate, CodeQA superseded by Knowledge]] - Code review and project improvements come from two skills over the GitHub plugin: reads of one pull request, its comments, one issue and one file now; a posted review and an opened issue later as irreversible writes under the github feature's grant, with the GitHub App widened to Pull requests and Issues read & write. The retired Scout.Plugin.CodeQA is superseded by Scout.Knowledge and stays under src/old.
- [[pages/decisions/0039-repository-snapshot-under-the-data-folder|ADR 0039 - A repository snapshot under Scout's data folder, read locally and searched by the Knowledge index]] - A review or an audit takes the repository at one commit from GitHub's tarball into Scout/github-snapshots, a declared write of the github feature; the three repository reads then serve from it and the Knowledge index searches it as the project owner/repo.
- [[pages/decisions/0040-review-findings-as-cards-in-chat|ADR 0040 - The review's findings as cards in the chat, posted as one review from the cards]] - A code review answered in chat carries its findings as a fenced scout-findings JSON block; Scout Desktop renders them as cards with Yes, No and Edit, Yes to all and Post, and posting is one question to the worker carrying the chosen comments after a marker, which the code-review skill turns into one submit_pull_request_review call under the GitHub grant.
- [[pages/decisions/0041-angular-material-in-the-renderer|ADR 0041 - Angular Material as the renderer's component library and theme]] - Scout Desktop's renderer adopts Angular Material 22 and the CDK: one global theme built from the palette the owner approved on the 2026-11-06 prototypes, app-level CSS variables mapped to the Material system tokens, a snackbar service for notices, and the screens migrating to Material components one per version; no Tailwind, no Bootstrap, no icon font from the network.
- [[pages/decisions/0042-audit-as-a-job-with-saved-progress|ADR 0042 - The audit as a job with saved progress]] - A whole-repository audit is a job Scout drives in batches with its progress, the files read and the findings saved in SQLite under the data folder, so it covers the repository across turns and restarts without asking the model to remember or the owner to say continue.
- [[pages/decisions/0043-the-verdict-on-a-pull-request|ADR 0043 - The verdict on a pull request, with the project's tests in an isolated container]] - Scout comments on pull requests and issues, replies to review comments, and approves a pull request or requests changes as a declared write the owner approves per action, and the verdict carries the project's tests: the pull request's check runs first, then the project's own test command run in a disposable container on the owner's machine under fixed isolation rules.
- [[pages/decisions/0044-scout-acts-on-github-as-its-own-app|ADR 0044 - Scout acts on GitHub as its own App, when the owner chooses it]] - An optional identity: the owner creates a GitHub App of their own from the desktop with GitHub's manifest flow, installs it, and Scout's reviews, verdicts and issues then show as that App's bot instead of the owner; without it, Scout keeps acting through the owner's sign-in as today.
- [[pages/decisions/0045-theme-and-notification-center|ADR 0045 - The desktop's theme switch and notification center]] - Scout Desktop gets a light, dark or system theme chosen from a sun, moon and monitor switch in a new top bar, and a bell that collects what Scout does in the background, what it wrote on GitHub, and where the owner was mentioned or a review of Scout's got a comment, read from GitHub every five minutes.
- [[pages/decisions/0046-ai-source-usage-on-the-cards|ADR 0046 - What each AI Source card says about usage]] - Every AI Source card shows the tokens Scout itself used today and this month, counted in the gateway from each answer's usage; OpenRouter also shows the money left and its reset from its key endpoint and the real cost per answer; a ChatGPT plan shows when its usage limit was reached; every other figure the provider does not report reads 'Not reported by the provider' with a link to its own usage page.
- [[pages/decisions/0047-the-docker-card|ADR 0047 - The Docker card in Features]] - Features gets a Docker card beside GitHub: Docker's state read by main with `docker version`, Scout's own on/off for Docker runs as its switch (a run also needs the GitHub write grant), the pinned images with a download the owner clicks, the work folder with its size and a confirmed Clear, and the last run; the GitHub card says when Docker would let Scout run a pull request's tests.
- [[pages/decisions/0048-claude-as-an-ai-source|ADR 0048 - Claude as an AI Source]] - AI Sources gets a Claude API card: the owner's Anthropic API key, the official Anthropic C# SDK behind Semantic Kernel as one more provider, models listed from the Models API, usage counted from each answer. A Claude Pro or Max subscription sign-in is not offered, because Anthropic does not allow third-party apps to offer claude.ai login without its approval.
- [[pages/decisions/0049-provider-logos-on-the-ai-source-cards|ADR 0049 - Provider logos on the AI Source cards]] - Every provider card on AI Sources shows its owner's official logo, unmodified, from a local file, in the owner's light and dark variants where it publishes them; Settings > About names each owner. The owner chose this knowing OpenAI, Google, Anthropic and Microsoft give no permission for this use and the repo is public; a logo is removed at once if its owner asks.
- [[pages/decisions/0050-read-aloud-and-conversation-mode|ADR 0050 - Read aloud and conversation mode]] - The desktop chat and quick ask can read Scout's answers aloud, sentence by sentence as they stream, with the voice of the connected AI Source when it has one or Scout's local voice otherwise; and a conversation mode listens, sends on a pause, reads the answer aloud and listens again until the owner stops it.
- [[pages/decisions/0051-desktop-end-to-end-tests|ADR 0051 - Desktop end-to-end tests]] - Playwright drives the built desktop app through Electron, on an isolated profile per test, with a fake worker that speaks the real line protocol and no request leaving the machine; Linux CI runs it under xvfb in a job of its own.
- [[pages/decisions/0052-persistence-behind-stores-on-entity-framework|ADR 0052 - Persistence behind one store per use case, on Entity Framework Core with SQLite]] - Each persistence use case sits behind its own store interface named with the Store suffix; the store implementations reach SQLite through Entity Framework Core only, the DbContext never leaves the store's project, the schema comes from EF migrations applied on the store's first call, a file an older build wrote is deleted and created again, and an ArchTest keeps SQLite, Entity Framework and SQL text inside the stores.
- [[pages/decisions/0053-electron-fuses-and-ipc-sender-check|ADR 0053 - Electron fuses and the IPC sender check]] - The packaged desktop ships with the fuses that make it a Node runtime off and cookie encryption, asar integrity and asar-only loading on, and keeps the file protocol privileges its renderer loads with; the write-granting channels answer only the main window's own page, and the action decisions only the main, quick-ask and operator windows'.
- [[pages/decisions/0054-functions-scoped-per-skill-and-job|ADR 0054 - Functions scoped per skill and per job]] - A turn is offered only the functions its skills or its job declare: a skill names them on a functions line of its frontmatter, the chat with no skill gets a general set of every read and no write, a job declares its set in code, and a call to anything else never runs and is logged.
- [[pages/decisions/0055-pull-request-review-as-a-job-in-batches|ADR 0055 - The pull request review as a job in batches]] - When a pull request's answer leaves any diff out, code-review starts a review job: an audit_job row of kind review with its pull request number, run by the audit worker before any audit, in batches cut by Scout from the head commit's patches, each batch a closed read-only turn, bounded, checked before it starts, and ending in one scout-findings card through present_review_findings with the verdict and the read line computed by code.
