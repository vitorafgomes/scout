# Scout performs descriptive writes only

> Scope change on 2026-11-02 ([[pages/decisions/0032-per-feature-write-permissions]]), applied 2026-11-03: a feature may declare writes in the catalog; it runs them only after the owner grants it in the desktop, each irreversible action only after the owner approves that action there, and every write is logged. An undeclared write stays forbidden. The `youtube` feature is the first write-capable one (the channel operator, [[pages/decisions/0033-channel-operator-architecture]]); its section below says how its writes are held. Every other feature is still read-only as described.

> Every write Scout makes is content a person or another agent reads and decides on (a chat reply, an issue body); no code path may mutate code, infrastructure, configuration or data on the host or in a connected system.

## The gap (closed 2026-11-08)

Until 2026-11-08 nothing in code stopped a plugin from exposing a write function: the kernel takes every `KernelPlugin` registered in DI (`src/Scout.Llm/LlmServiceCollectionExtensions.cs:133`), and every chat turn was offered all of them with automatic function choice. Since 2026-11-02 a function declared with `AddWriteFunction` is gated at the call by the control plane (the write gate below); an undeclared one was not.

Since [[pages/decisions/0054-functions-scoped-per-skill-and-job]] (phase S2 of [[pages/roadmap/security-hardening]]) no turn is offered the whole kernel. The chat's turn gets the general set, every read and no write (`src/Scout.Conversation/Routing/ChatFunctions.cs:12`), plus the functions its skills declare on their `functions` line; the audit batch gets the six reads its job declares; the Project Expert agent gets the turn's set and holds none of its own (`src/Scout.Knowledge/ProjectExpertAgentFactory.cs:66`). One helper builds each turn's kernel, a copy of the shared one with only the declared functions and the shared filters, the write gate among them (`src/Scout.Llm/KernelScope.cs:19`; the direct path `src/Scout.Llm/ChatGateway.cs:197`, the agent path `:264`, the audit `src/Scout.Audit/AuditBatchRunner.cs:177`). A call the model makes to anything else never runs and is logged by name. A skill that declares a write is selected only from the message's own text, never from a transcript, screen text or other context (`src/Scout.Conversation/Routing/LlmStreamingRouter.cs:99`, `tests/Scout.Conversation.Tests/Routing/LlmStreamingRouterFunctionScopeTests.cs:270`), and the skills a conversation carries expire with its memory's idle time. `tests/Scout.Host.Console.Tests/FunctionDeclarationTests.cs:66` fails when a kernel function is declared by neither the general set, a skill nor a job, `:86` when the general set holds a write or misses a read, and `:95` when a skill other than `code-review`, `code-audit`, `project-improvements`, `github-issues` and `youtube-operator` declares a write or a write is declared by none. What remains: a write function a plugin adds and also lists in an acting skill's `functions` line is offered on that skill's turns, gated only if it is also declared with `AddWriteFunction`; the declaration catalog test (`tests/Scout.Host.Console.Tests/WriteDeclarationCatalogTests.cs:13`) checks the declared ones, and review checks the rest.

## Why this exists

Scout answers questions in shared chat channels. A model that can call a mutating tool turns a prompt in a public channel into a change on a real system. The README states the rule as "never writes"; [[pages/decisions/0009-descriptive-vs-executive-writes]] refines it to descriptive versus executive writes.

## Scope

- **Applies to:** every `KernelPlugin` the host registers, the GitHub client, the Kubernetes clients, the chat adapters, and the control plane.
- **Does not cover:** Scout's own state (below), and replies posted to the chat platform, which are descriptive writes by definition. That includes the allowed-users refusal ("Scout only answers its configured users." or the setup text), which goes through the same sink to the originating channel only and is the one thing a refused message causes ([[pages/decisions/0021-allowed-users]], `src/Scout.Conversation/ConversationConductor.cs:132`). The allow-list decides who gets replies; it never authorizes a write. The pairing reply ("Paired. Scout will answer you from now on." or "That pairing code is not valid. Check the code in Scout's Settings and send it again.") is the same kind of reply, in the direct message it answers. The `SCOUT_PAIRED=<userId>` line it causes goes to the desktop's own supervisor on stdout, and the id lands in Scout's own vault, which is Scout's own state (`src/Scout.Conversation/ConversationConductor.cs:205`).

The renderer asks only after the owner's click saved a provider other than Ollama while Ollama, or no saved provider, was in use (`ui/packages/renderer/src/app/core/llm-config.store.ts:371`; `ui/packages/renderer/src/app/core/llm-config.store.spec.ts:942`); no worker path, function or chat message reaches it. The owner deferred the server controls on 2026-11-11, so Scout does not stop the server, which the computer runs and other programs may use; Scout asks Ollama to unload only the models Scout uses. Nothing is deleted, and each model is logged by name in main's log (`ui/packages/main/src/ipc/llm.ts:195`, `:198`). It is listed with the local writes (`ui/packages/shared/test/ipc-contract.test.ts:907`).

## Known exceptions and tensions with the README

- **Token scope (reopened 2026-10-23 for pasted tokens).** The catalog asked for a `repo`-scope token and listed "Create issues"; it now lists only the GitHub App's read permissions (`src/Scout.ControlPlane/Features/FeatureCatalog.cs:48`, `tests/Scout.ControlPlane.Tests/Features/FeatureCatalogTests.cs:25`). A host configured with `Scout:Plugins:GitHub:Token` still gets whatever scopes that token carries. An earlier plugin had `create_issue` under `src/old/`, which is outside `Scout.slnx` and not built. The desktop "Use a token" method accepts any token the owner pastes, including a classic token with `repo` scope, and hands it to the worker as `SCOUT__PLUGINS__GITHUB__TOKEN`; the card warns when the scope header lists a write scope, and read-only for that method rests on the GET-only client ([[pages/decisions/0019-github-app-device-flow]], `ui/packages/main/test/oauth-github-token.test.ts:133`).
- **Host mutation by the control plane (ruled 2026-11-11).** `Scout.Host.ControlPlane` can pull and delete Ollama models (`src/Scout.Host.ControlPlane/Services/ModelsGrpcService.cs:22,59`; `src/Scout.ControlPlane/Providers/OllamaApiClient.cs:166`) and start and kill the Ollama process (`src/Scout.ControlPlane/Providers/OllamaProviderService.cs:204`, launched with both control-plane tokens scrubbed from its environment at `:197`; `src/Scout.ControlPlane/Providers/SystemProcessLauncher.cs:161`). These are driven by the desktop UI over an authenticated local socket (`src/Scout.Host.ControlPlane/ControlPlaneServiceRegistration.cs:38`), never by the model. [[pages/decisions/0032-per-feature-write-permissions]] rules on them in its amendment of 2026-11-11: they are a reviewed local write on the owner's click, the class of the desktop's own model download and delete, outside the feature grant and the approval queue because they belong to no feature, and a stop refuses a server Scout did not start. Only the desktop token reaches them, nothing the model can call reaches them, and a download logs one line at its start and one at its end and a delete one line saying how it ended, to the control plane host's log, not the write log (Where it is held, Local models through the control plane). The desktop does not call `Models` today and discards the host's output; the change that makes it call `Models` keeps that output first.
- **Quick ask (local adapter).** The local adapter writes `SCOUT_LOCAL` reply lines to the worker's stdout, and the desktop shows them only in the owner's own quick-ask window and Chat screen, which share one conversation held in main (`src/Scout.Adapter.Local/LocalEventWriter.cs:25`, `ui/packages/main/src/quick-ask/quick-ask.ts:745`). Those windows are the originating channel, so the reply is a descriptive write like any chat reply. Reading the owner's microphone while Space or the button is held, and the line main writes to the worker's stdin, are reads the owner starts on their own machine; the quick-ask shortcut is Scout's own configuration. The adapter adds no LLM-invocable function, plugin operation or control-plane command ([[pages/decisions/0028-local-quick-ask-assistant]]). Keeping a meeting and deleting one come only from the `keep` and `delete` requests the desktop writes to the worker's stdin after the owner's click; no chat text, function result or `KernelFunction` reaches `IMeetingStore`, and the store references no network assembly ([[pages/decisions/0037-meetings-kept-locally-in-sqlite]], `tests/Scout.Meetings.Tests/SqliteMeetingStoreTests.cs:466`, `tests/Scout.Adapter.Local.Tests/LocalChatAdapterTests.cs:1092`).
- **Own Discord application flag.** The desktop wizard sends one PATCH to Scout's own Discord application to turn on the limited Message Content intent, keeping every other flag (`ui/packages/main/src/discord/discord-setup.ts:94`). The owner starts it from the wizard; no LLM-invocable function or worker path reaches it. [[pages/decisions/0022-discord-setup-from-the-bot-token]] classifies it as Scout's own configuration, not an executive write.
- **Own startup entry.** The desktop registers Scout as a login item on macOS and Windows and writes `~/.config/autostart/scout.desktop` on Linux (`ui/packages/main/src/shell/login-item.ts:56`, `:76`), when the owner turns on "Start Scout when I log in" in Settings, refreshes an existing entry at start-up to Scout's own current executable (`ui/packages/main/src/shell/login-item.ts:102`, because an AppImage update can rename the file), and deletes that one file when it is turned off (`:90`). No worker path, LLM-invocable function or chat message reaches it. [[pages/decisions/0027-desktop-presence]] classifies it as Scout's own configuration, not an executive write.
- **Own installation (ADR 0031).** On the user's click of Update and restart, the desktop main process lets `electron-updater` replace the AppImage it runs (only when `APPIMAGE` and `APPDIR` are set and the executable lives inside `APPDIR`) or run the Windows installer, for a release GitHub published whose checksum matched and whose version equals the notice shown; the worker is stopped and the single-instance lock released first. No background download, no install on quit, no path from the worker, an LLM-invocable function or a chat message: the only trigger is the `scout:update.install` channel of the renderer, and `ui/packages/main/test/update-notice.test.ts` pins the options, the order and the failure paths. [[pages/decisions/0031-desktop-self-update]].
- **Own state.** Scout writes `features.json`, with the approval queue `actions.json`, the write log `writes.log` and the channel operator's `mandate.json`, `projects.json` and `comments.json` beside it (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:42`, `:41`, `:43`), `local-runtimes.json` (`src/Scout.ControlPlane/Features/FeatureStateStoreOptions.cs:24`, `src/Scout.ControlPlane/Providers/JsonFileLocalRuntimeConfigStore.cs:138`), the vector database (`src/Scout.Knowledge/KnowledgeServiceCollectionExtensions.cs:105`) and `meetings.db`, created with its schema on the store's first call, which the host makes right after readiness, and created again when a build before Entity Framework left it, only when it holds no table Scout did not create; a meeting is written to it only when the owner keeps one (`src/Scout.Meetings/SqliteMeetingStore.cs:46`, deleted with its text scrubbed at `:156` and `:173`, [[pages/services/meetings]]) under the user's local application data directory. This is Scout's own config, index and the meetings the owner chose to keep.

## Change protocol

To add a write function: declare its row in the feature catalog ([[pages/decisions/0032-per-feature-write-permissions]]), register it with `AddWriteFunction` so the write gate asks the control plane on every call, add a test that the function's body never runs on `queued` or `refused`, and name the function on the `functions` line of the skill that calls it, or in the job's own list ([[pages/decisions/0054-functions-scoped-per-skill-and-job]]); `tests/Scout.Host.Console.Tests/FunctionDeclarationTests.cs` fails until both are done.
