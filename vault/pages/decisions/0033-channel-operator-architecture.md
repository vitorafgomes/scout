# ADR 0033 - Channel operator architecture

> The operator's state lives in the control plane, its pipeline runs in a new C# library `Scout.Operator` inside the worker, speech and images come only from Semantic Kernel services of the AI Source already connected, and progress is posted later into the channel the request came from.

## Status

- [ ] Proposed
- [x] Accepted
- [ ] Deprecated / superseded by

Updated: 2026-11-03. Accepted on the owner's instruction to build phases 2 to 6 of [[pages/roadmap/youtube-channel-operator]] in one branch, one commit per phase: "pode seguir com todas as proximas fases tudo em um unico PR".

## Context

Phase 1 ([[pages/decisions/0032-per-feature-write-permissions]]) put the write contract in the product: the `youtube` feature declares its rows, the owner grants its writes on the YouTube card, irreversible actions wait on the Review screen, and a function gate in the worker asks the control plane's `WorkerGate` before any declared write. Phases 2 to 6 build the operator itself: mandate, research, script, narration, visuals, assembly, review, publish, learning loop, experiments and comments, matching the reference project module for module except for media accounts ([[pages/roadmap/youtube-channel-operator]], parity table).

Four questions block the first line of phase 2 code, because every later phase builds on the answers.

- **Who writes the operator's state.** The desktop reaches only the control plane ([[pages/decisions/0011-backend-frontend-grpc-uds]]); the worker reaches it through `WorkerGate` with its own token. Two processes writing one file already cost the approval queue a fix (`actions.json`).
- **Where the pipeline code lives.** The owner's rule: "a maior parte tem que ser em C#".
- **How speech and images are made.** Semantic Kernel is the one LLM path ([[pages/decisions/0012-llm-communication-through-semantic-kernel]]), and the owner's rule is that media comes only from the AI Sources already connected, never a separate account. In the installed Semantic Kernel 1.78 packages only the OpenAI and Azure OpenAI connectors carry text-to-audio and text-to-image services (`AddOpenAITextToAudio`, `AddOpenAITextToImage`, `AddAzureOpenAITextToAudio`, `AddAzureOpenAITextToImage`); the Google connector (Gemini, the owner's current provider), Ollama, Mistral, HuggingFace and Azure AI Inference have none, and the ChatGPT plan path has no audio or image service.
- **How progress reaches the chat.** Today every outbound message goes through an `IResponseSink` created for one inbound message and closed at the end of the turn; nothing can post later, and no transport reference outlives the turn (`src/Scout.Conversation/Abstractions/IResponseSink.cs`, `IChatAdapter.cs`). Teams has no live hosting at all.

## Decision

- **State: the control plane is the single writer.** A new `Operator` area in `Scout.ControlPlane` owns the mandate, the video projects (topic, research, script, claims, scene list, package metadata, status, the originating chat reference) and their history, stored as JSON next to `features.json` with the same atomic-write style. The desktop reads and edits through a new `Operator` gRPC service on the desktop token; the worker reads the mandate and saves its drafts through new `WorkerGate` methods on the worker token, each checked against the `youtube` write grant like any `Write` row (amended 2026-11-03: the worker's mandate read is a read of the owner's brief and is not grant-gated; its project reads, saves and the take of the next queued project are, and so is the desktop's start of a project), and the role tests prove the worker token cannot edit the mandate, approve a package or reach the desktop's `Operator` service. Media bytes (narration, images, the MP4, Shorts, thumbnails) stay on disk under Scout's data folder in one directory per project; the control plane records their paths and checksums only. The desktop previews them through a main-process route confined to that directory; the renderer never receives an arbitrary file path.
- **Code: a new library `Scout.Operator`.** Research, script, claims, scenes, media generation, the `ffmpeg` driver, the checks, publishing, the learning loop, experiments, comments and the scheduler live in `src/Scout.Operator` with `tests/Scout.Operator.Tests`, referenced by `Scout.Host.Console`. It reaches YouTube through `Scout.Plugin.YouTube`'s client (extended with the write calls the catalog declares), the model through Semantic Kernel only, and the control plane through its own seam, `IOperatorControlPlane`, implemented in the console host over the same `WorkerGate` channel and worker token as the write gate (amended 2026-11-03: a separate seam keeps the write gate's contract to requesting and recording writes). No generic pipeline engine: concrete stages, one class each where a class is needed.
- **Media: the connected provider's Semantic Kernel services, or a local fallback.** The operator resolves `ITextToAudioService` and `ITextToImageService` from the kernel; `Scout.Llm` registers them only for providers whose installed connector offers them (OpenAI, Azure OpenAI), with the same credential the owner connected and the provider's configured models. With any other provider the operator falls back without asking for an account: narration from the bundled local Piper engine (amendment of 2026-11-03 below), else from an audio file the owner supplies or none (captions carry the script), and visuals from the owner's images and text cards `ffmpeg` renders. The capability matrix lives on [[pages/services/llm]]. A direct HTTP call to a provider's speech or image endpoint is a second LLM path and is not part of this decision; the owner decides that separately (Gemini media is the open question).
- **Progress: a proactive post into the originating channel.** When a request starts a long job, the adapter captures an opaque reference to the originating conversation (Discord channel or thread and the message replied to; Slack channel and thread timestamp; the local quick-ask session); the operator stores it with the project, and a new seam in `Scout.Conversation` lets the operator post a short progress or result message into that same conversation later. It is a descriptive write to the originating channel only, as [[pages/invariants/no-executive-writes]] already allows; Teams, which has no live hosting, gets no proactive post.
- **Write scopes come from a fresh sign-in** (amended 2026-11-03, phase 5). Google does not support incremental authorization for installed apps, and the developer policies allow only the scopes in use: the read-only sign-in keeps the read scopes, "Allow writes" runs a new browser sign-in that adds `youtube.upload` and `youtube.force-ssl` and grants writes only when every requested scope came back, and a revoke signs back in with the read scopes. Disconnecting YouTube purges the API data the control plane holds (snapshots, research candidates).
- **The operator has its own window** (owner's decision, 2026-11-03: "pode seguir com a janela própria"). The YouTube card offers "Open YouTube operator", which opens a separate Scout Desktop window holding every operator page (mandate, projects, script and claims, scenes and previews, assembly, the feature's approval queue, reports, experiments, comments). It is a window of the desktop app, not a local web site: no port is opened, the renderer reaches the control plane only through main as every other page does, and approvals stay in the desktop. A local web site was considered and rejected: an HTTP port on the machine would be reachable by any local process or page (CSRF, DNS rebinding) and would move approvals out of the desktop.
- **YouTube quota is budgeted per day.** Since 2026-06-01 `search.list` and `videos.insert` have their own buckets of 100 calls a day each; everything else shares 10,000 units a day, with `videos.update`, `thumbnails.set`, `playlistItems.insert`, `comments.insert` and `comments.setModerationStatus` at 50 units and `captions.insert` at 400. The scheduler caps research searches and uploads per day below those buckets, and burns captions into the video instead of calling `captions.insert` by default.
- **Uploads go up private.** A video is uploaded with `privacyStatus: private` and, when scheduled, `status.publishAt`; whether an unverified Google project may publish publicly is unsettled in Google's current documentation, so public visibility is a later, separately approved `videos.update`. Amended 2026-11-03 (phase 5): YouTube's developer policies require the client to offer public, private and unlisted and every upload to follow the user's express consent, so the owner picks the privacy, the made-for-kids answer and the synthetic-media disclosure in the desktop publish dialog, and confirming that dialog is the approval of each action it lists; a schedule is only allowed with private, as `status.publishAt` requires. A publish the model queues from a chat carries none of those choices and is refused with a pointer to the desktop.
- **Experiments follow the reference's statistics.** A title or thumbnail experiment rotates its arms in sequence through `videos.update` and `thumbnails.set`, each arm an approved action, and declares a winner only on a pooled two-proportion z-test on click-through rate at z >= 1.96 with at least 1,000 impressions and 10 clicks per arm, with guardrails on average view percentage and traffic-source shift; adopting the winner is one more approved action. Impressions and click-through rate are read from the Analytics API in phase 5 and verified against the live API before the experiment code depends on them. Amended 2026-11-03 (phase 5): the Analytics API's `reports.query` has no impressions or click-through rate metric; both come only from the Reporting API's reach report (`channel_reach_basic_a1`), which needs a reporting job created once on the owner's channel (a declared `Write` row, `youtubeReporting jobs.create`) and arrives as daily files 48 to 72 hours late, so an arm runs 24 to 168 hours and the decision waits for the files covering it.

## Consequences

- **Better:** one writer for every piece of operator state; the worker can never approve its own work; the pipeline is C# end to end; no account or key beyond what the owner connected; the owner sees progress in the chat they asked from.
- **Worse:** a new project and a new gRPC service to maintain; with a provider that offers no media services the operator makes no generated images until the owner connects OpenAI or Azure OpenAI, and narrates with the bundled voices only (since the amendment of 2026-11-03; before it, no narration at all); Teams users get no progress posts.
- **Neutral but noteworthy:** `ffmpeg` is the one external tool, fetched at build time and pinned by checksum (owner's decision of 2026-11-02); the operator never writes outside its project directories under Scout's data folder.

## Alternatives considered

- **State in the worker, files on disk.** Rejected: two processes would write the same files, and the desktop cannot reach the worker (ADR 0011).
- **Pipeline in the desktop main process.** Rejected by the owner's rule that most of it is C#.
- **Grow `Scout.Plugin.YouTube` into the pipeline.** Rejected: the plugin is the YouTube client and its model functions; the pipeline orchestrates the model, media, `ffmpeg`, the control plane and the chat, which is a different responsibility with its own tests.
- **Direct HTTP to every provider's media endpoint.** Not decided here: it is a second LLM path under ADR 0012 and needs the owner's decision.

## Enforcement

- `tests/Scout.ControlPlane.Tests`: role tests that the worker token cannot reach the `Operator` service or decide a package, and that operator writes through `WorkerGate` refuse without the grant.
- `tests/Scout.Operator.Tests`: every stage with its failing-call test (Rule I) for the model, YouTube, `ffmpeg` and the control plane.
- `tests/Scout.Llm.Tests`: the media services are registered only for providers that offer them, and the write gate is proven on the Gemini and ChatGPT plan paths as well as OpenAI.
- [[pages/services/operator]] and [[pages/architecture/project-map]] describe the new project; the review gate's `boundaries` lens covers `Scout.Operator` and the new contracts.
- `tests/Scout.Operator.Tests/PiperSpeechTests.cs` and `NarrationGeneratorTests.cs`: the bundled engine runs only with its argument list and the narration on standard input, writes only in the media directory, and is chosen over the provider only when the project names one of its voices.

## Amendment 2026-11-03 (phase 7): bundled voices

The owner decided (2026-11-03) that narration must not depend on the connected provider having a speech service: Scout Desktop ships the Piper text-to-speech program (rhasspy/piper 2023.11.14-2, MIT, whose archive carries libespeak-ng under GPL-3) and British English voice models whose dataset licences allow redistribution, fetched at build time and pinned by SHA-256 like `ffmpeg`, and the worker runs it as a separate program through `IProcessRunner`, never linked into Scout. The connected provider's speech, when it has one, is still reached through Semantic Kernel only (ADR 0012), now in the voice the owner names; each project carries `narration_voice`, chosen when the owner produces it (the owner moved the choice from the channel to the video on 2026-11-03), the readiness lists the voices this machine offers, and an empty choice means the provider's speech first and the bundled default voice otherwise. Images are unchanged: generated only through the provider's Semantic Kernel image service, else the owner's files and text cards. [[pages/services/operator]] (Bundled voices), [[pages/services/llm]] (media capability matrix), [[pages/roadmap/youtube-channel-operator]] (the voice licences).

**Amendment 2026-11-03 (delegation).** On the owner's decision of 2026-11-03 (a button to delegate a project), the owner delegates each project on its own from the desktop. Delegation is the control plane, the single writer of the operator's state, chaining the project's reversible stages: `DelegateProject` queues production, or assembly when the media is ready, and the control plane stores the worker's `media_ready` save of a delegated project as `assembly_queued`, so the worker's next take assembles it; the worker is unchanged ([[pages/services/control-plane]]). It needs the owner's live `youtube` write grant like any other operator write and writes only Scout's data folder. In a delegated project unresolved claims no longer block production, only the package approval. Delegation stops at the assembled package: approving it and publishing it stay the owner's actions, the publish an approved action under [[pages/decisions/0032-per-feature-write-permissions]], and nothing starts on its own from the mandate's cadence.

## Amendment 2026-11-03 (stock pictures)

The owner decided (2026-11-03) that a scene the owner gave no picture, on a machine whose connected AI Source has no image service, gets a picture that fits its context instead of a text card. The worker searches Openverse, the openly licensed media index, with no account and no key, using two to four search terms the scene planner asks for in the same one model request, and saves the first fitting result in the project's media directory with its credit; the video's description lists every credit under `Credits`. The provider's image service, when there is one, still comes first and is still reached through Semantic Kernel only, so the media decision above stands for every AI-made picture; Openverse is a read-only fallback before the text card, never a replacement for the owner's own picture, which replaces a stock picture and clears its credit.

Only three licences are taken, the owner's rule: CC0, the public domain mark and CC BY, so no SA and no NC. CC BY needs only the credit, which the description carries. CC BY-SA is excluded because a video that scales, pads and moves a picture over narration may count as an adaptation, and ShareAlike would then require the whole video under CC BY-SA, a licence the owner does not mean to grant for a video that also carries a script, a narration and other pictures under other terms. The NC variants are excluded because a channel that earns from its videos is commercial use, and the ND variants, which the owner's rule does not name, fall outside the same three-licence filter for the same adaptation reason. The fetch is a read, declared on the YouTube feature as "api.openverse.org and the host of the picture it names" ([[pages/invariants/no-executive-writes]]); its file is written only in the media directory, refused unless it is an image of at most 20 MB, and any failure leaves the scene a text card with a note, never a failed scene. It is counted in its own budget of 100 requests a day, under the anonymous limits the API reports in its headers (20 a minute, 200 a day). The readiness carries `stock_pictures` so the desktop can say where pictures come from ([[pages/services/control-plane-contracts]]); the worker's side is in [[pages/services/operator]], the control plane's vocabulary and save check in [[pages/services/control-plane]].

**Amendment 2026-11-04 (visual brief).** On the owner's decision of 2026-11-04, each project carries the owner's visual brief, free text of at most 500 characters, and a motion preset, `still`, `gentle` or `dynamic`, both chosen on produce or delegate like the narration voice and never set by the worker; the brief reaches only the scene planner's one model request, as the style of the picture prompts and search terms, and the preset only the assembler's choice among its own constant ffmpeg filter chains, so neither adds a call leaving the process or a write ([[pages/services/control-plane]], [[pages/services/operator]]).

**Amendment 2026-11-04 (delete project).** The owner deletes a project from the desktop: the control plane removes it from its store and deletes the project's media directory, which it builds from the 32-digit project id alone, so nothing outside Scout's data folder is touched and a video already on YouTube stays there; a delete is Scout's own state and needs no grant, and a running project or one with approved or executing YouTube actions is refused ([[pages/services/control-plane]], [[pages/invariants/no-executive-writes]]).

**Amendment 2026-11-04 (voice samples).** So the owner can hear a bundled voice before choosing it, the worker makes one short Piper sample per bundled voice, free and offline, into a `voice-samples` folder the control plane gives beside the project media directories, and the readiness names each sample file; the folder is Scout's own data and needs no grant, the worker writes it only through `MediaFiles`, and the desktop plays a sample through the `voice-samples` host of `scout-media:`; the provider's voices get no sample, because each would be a paid call ([[pages/services/operator]], [[pages/services/desktop-operator]]).
