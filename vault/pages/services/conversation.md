## Responsibility

Owns the adapter contract, message and response shapes, routing, per-channel memory, the streaming edit loop and the voice-message flow (limits, download through the adapter's delegate, transcription through `IAudioTranscriber`). Does not own a speech model ([[pages/services/transcription-whisper]]) nor platform SDK calls ([[pages/services/adapter-discord]], [[pages/services/adapter-slack]], [[pages/services/adapter-teams]]) nor model access ([[pages/services/llm]]).

## How it works

```mermaid
sequenceDiagram
    participant A as IChatAdapter
    participant C as ConversationConductor
    participant R as LlmStreamingRouter
    participant G as IChatGateway
    participant P as StreamPump
    A->>C: HandleAsync(message, sink)
    C->>R: Route(message)
    R-->>C: ChatResponse (lazy stream)
    C->>P: RunAsync(response, sink)
    P->>R: enumerate
    R->>G: StreamAsync(request with skills and history)
    P->>A: sink.UpdateAsync / CompleteAsync
```

`Route` defers all work to enumeration (`src/Scout.Conversation/Routing/LlmStreamingRouter.cs:59`). History is written only after a stream completes without error, so a failed turn never enters memory (`:102`). What enters is the user's text and the assembled reply text only (`:106`): the functions the model called, the files it read and the blocks a function attached are not stored. The store is in the worker's memory (`src/Scout.Conversation/Memory/InMemoryConversationMemoryStore.cs:21`), so it is empty after a restart; the defaults are 6 turns replayed, 8,000 characters at most and a 30-minute idle expiry (`src/Scout.Conversation/Memory/ConversationMemoryOptions.cs:22`, `:28`, `:34`). A multi-turn task such as a whole-repository audit cannot rely on it; [[pages/roadmap/gap-plan]] G4 and [[pages/roadmap/future-improvements]] F1 replace it with a project memory on disk. Failures reach the user through `sink.FailAsync` (`src/Scout.Conversation/ConversationConductor.cs:172`).

- **Local owner:** a message with `IsLocalOwner` set skips both the pairing check and the allow-list (`src/Scout.Conversation/ConversationConductor.cs:110`, `:125`) and goes straight to voice handling and routing; the flag is kept when a voice message is rewritten to its transcript (`:147`). Trust comes from the local adapter's stdin transport, never from the user id: a chat message with the user id `local-owner` is refused like any other ([[pages/decisions/0028-local-quick-ask-assistant]]).
- **Pairing:** first of all, a message whose trimmed text is `pair` in any case, one or more spaces and six digits is a pairing attempt; so is a message of exactly six digits, but only in a direct message while a code is pending (`src/Scout.Conversation/ConversationConductor.cs:110`, pending check at `:182`). Outside a direct message, six bare digits are an attempt only when they are exactly the pending code (`src/Scout.Conversation/ConversationConductor.cs:189`); other bare digits in a channel, or any with no code pending, are an ordinary message and never count as a wrong code. It succeeds once per process, only in a direct message, only with the configured unexpired `PairingCode` and only when an `IPairingSignal` is registered (`:192`). The correct code sent outside a direct message, bare or as `pair <code>`, or five wrong codes, burn it for the process, and the signal's `Burned` is called (`:219`). The signal gets the sender id, and the reply is "Paired. Scout will answer you from now on."; any failure replies "That pairing code is not valid. Check the code in Scout's Settings and send it again." Nothing is routed either way, and the log line carries the channel id and the outcome only. The sender still goes through the allow-list on the next message, until the desktop adds the id and restarts the worker ([[pages/decisions/0021-allowed-users]]).
- **Allowed users:** next, after the pairing check, `HandleAsync` checks `ChatMessage.UserId` with `AccessPolicy` (`src/Scout.Conversation/Access/AccessPolicy.cs:9`, registered as a singleton from `Scout:Access` and injected into the conductor, which reads the pairing code and its expiry from the same instance, without them ever changing who is allowed; the Discord adapter uses the same instance to decide whether to open a thread) against `Scout:Access` (`src/Scout.Conversation/ConversationConductor.cs:125`, rule at `:330`). A sender outside a non-empty list gets "Scout only answers its configured users."; with an empty list and `RequireAllowList` set, everyone gets "Scout is not set up for anyone yet. If you are the owner, open the Scout desktop app, go to Settings, choose Pair from chat and send the 6-digit code here in a direct message."; otherwise the message is routed as before. A refusal is `BeginAsync` then `CompleteAsync` with that text, no router, pump, model or plugin call, and one Information log line with the channel id only. The desktop sets `RequireAllowList` when an owner credential is connected ([[pages/decisions/0021-allowed-users]]).
- **Progress before the text** (ADR 0013 amendment of 2026-11-06): `IResponseSink.ProgressAsync` with a default that ignores it (`src/Scout.Conversation/Abstractions/IResponseSink.cs:36`); the conductor enters `TurnProgress` with the sink's `ProgressAsync` for the turn (`src/Scout.Conversation/ConversationConductor.cs:156`), so the kernel's `ActivityFilter` ([[pages/services/llm]]) tells the chat which function the model is calling; `VoiceReplySink` forwards it (`src/Scout.Conversation/Streaming/VoiceReplySink.cs:25`). Tests: `tests/Scout.Conversation.Tests/ConversationConductorTests.cs:48`.
- **Blocks a function hands to the reply** ([[pages/decisions/0040-review-findings-as-cards-in-chat]] v1.1): the conductor begins `TurnAttachments` ([[pages/services/llm]], `src/Scout.Llm/Abstractions/TurnAttachments.cs:9`) beside `TurnProgress` (`src/Scout.Conversation/ConversationConductor.cs:157`); on the normal completion the pump takes the blocks, removes from the model's text every fenced block that opens like an attached one (its opening line to its closing fence, or to the end of the text when unclosed), so a model that still writes its own `scout-findings` fence leaves exactly one block in the reply and keeps the prose around it, and the final text becomes that trimmed text, a blank line and each block in the order attached (`src/Scout.Conversation/Streaming/StreamPump.cs:173`, `:195`). A block always arrives whole: the blocks that fit the chat's body length go in, a block that does not fit whole is dropped, and the model's text is cut to what the kept blocks leave, with the usual tail-preserving marker (`src/Scout.Conversation/Streaming/StreamPump.cs:210`), so on Slack's 3,000 characters the review's prose is cut, never the JSON; when no block fits, the prose gets the whole length as before. Without an attached block the model's text is left as it is. Interim updates never carry a block; a failed, timed-out, cancelled, rate-limited, quota, sign-in or vision turn appends nothing, and the blocks die with the turn. At most four blocks of 64,000 characters each; a block whose first line matches an attached one replaces it. Memory keeps the streamed tokens only, so the block never enters the history. Tests: `tests/Scout.Conversation.Tests/Streaming/StreamPumpTests.cs:296`, `:313`, `:330`, `:348`, `:366`, `:379`, `:395`, `:408`, `tests/Scout.Conversation.Tests/ConversationConductorTests.cs:64`, `tests/Scout.Llm.Tests/Abstractions/TurnAttachmentsTests.cs:8`.
- **Voice messages:** after the allowed-users check, a message with `Audio` opens the sink and is transcribed before routing (`src/Scout.Conversation/ConversationConductor.cs:135`, `:236`). With no `IAudioTranscriber` the reply is exactly "Voice messages need a Whisper model. Download one in the Scout app under AI Sources, Local Models." and nothing is downloaded. A reported size over 25 MB or duration over 5 minutes is refused before the download (`:245`, `:249`); the download reads at most 25 MB and refuses more (`:309`), and the whole download, body included, is cancelled after 30 s (`AudioDownloadTimeout`, `:258`), because the HTTP client's own timeout stops at the response headers. A failed or timed-out download, a failed transcription and an empty transcript each complete the reply with a fixed sentence, logged with the channel id only (`:264`, `:288`, `:295`), and a transcriber busy with a recording with "Scout is transcribing a recording right now; try the voice message again in a few minutes." (`:54`, `:280`, `tests/Scout.Conversation.Tests/ConversationConductorVoiceTests.cs:217`); a successful transcription logs the transcript length and the duration in ms, never the text. Otherwise the transcript becomes the message text, so the router, memory and model see what was said, and the sink is wrapped in `VoiceReplySink` (`src/Scout.Conversation/Streaming/VoiceReplySink.cs:10`), which prefixes every rendered body with `> (voice) ` and the transcript's first 200 characters on one line, and turns the pump's Begin into a no-op because the reply is already open ([[pages/decisions/0024-voice-messages-transcribed-locally]]).
- **Origin and later posts:** `HandleAsync` enters `ChatOrigin` with the message's `OriginReference`, its conversation key, and whether the sender is the owner, `IsLocalOwner` or `AccessPolicy.IsOwner` (`src/Scout.Conversation/Access/AccessPolicy.cs:48`), an allowed id also listed in `OwnerUserIds`, compared ordinally after trimming, before anything else runs and leaves it when the turn ends (`src/Scout.Conversation/ConversationConductor.cs:106`); both come from the platform event, never from the message text or a function parameter, so a prompt can make the model call a function but cannot make the caller the owner; the value lives in an `AsyncLocal`, so a function the model calls while the reply streams reads its own turn's reference and owner flag and never another concurrent turn's, and the caller sees null and not the owner after the turn. The voice rewrite keeps the reference (`:147`). `OriginNotifier` splits a reference at its first colon and hands the rest to the poster whose `Kind` is the prefix: `discord`, `slack` or `local` ([[pages/services/adapter-discord]], [[pages/services/adapter-slack]], [[pages/services/adapter-local]]). A null or empty reference, no prefix, a prefix no running adapter registered (Teams registers none) or a poster that throws returns false with a Warning that carries no reference contents; it never throws for a closed or missing channel, and only a cancellation of the caller's own token propagates (`src/Scout.Conversation/OriginNotifier.cs:18`). Each poster caps the text to its platform's limit. Rules: the reference is never shown to the model or logged, and `ChatMessage`'s generated `ToString` omits it (`src/Scout.Conversation/Abstractions/ChatMessage.cs:66`); the target of a later post comes only from a reference an adapter captured (through `ChatOrigin.Current` or stored with the job), never from an argument the model supplies; the post is plain text into that same conversation, a descriptive write ([[pages/invariants/no-executive-writes]]).
- **Sign-in required:** an `LlmSignInRequiredException` from the provider completes the reply with `StreamPumpOptions.SignInRequiredMessage` (`src/Scout.Conversation/Streaming/StreamPumpOptions.cs:63`, caught at `src/Scout.Conversation/Streaming/StreamPump.cs:140`), so the chat user is told to sign in again instead of seeing a generic error.
- **Quota or usage limit:** an `LlmQuotaExceededException` completes the reply with `StreamPumpOptions.QuotaExceededMessage`, except that the code `subscription_sharing_usage_limit_exceeded`, the ChatGPT plan's usage limit for apps, completes it with `StreamPumpOptions.PlanUsageLimitMessage`, "The ChatGPT plan reached its usage limit for apps like Scout; try again later, or choose another AI Source in Scout Desktop." (`src/Scout.Conversation/Streaming/StreamPumpOptions.cs:56`, chosen at `src/Scout.Conversation/Streaming/StreamPump.cs:130`; `tests/Scout.Llm.Tests/ChatGatewayEmptyReplyLogTests.cs:193`), whether the plan refused with an HTTP 429 or ended a stream with that code ([[pages/services/llm]]).
- **A picture on the message** ([[pages/decisions/0035-screenshot-attached-to-a-question]]): the router copies `ChatMessage.Image` to `ChatRequest.Image` as a `ChatImage` of the same bytes and MIME type (`src/Scout.Conversation/Routing/LlmStreamingRouter.cs:84`), so no Semantic Kernel type enters this project; memory keeps the turn's text only, never the picture. The voice rewrite keeps the image with the transcript (`src/Scout.Conversation/ConversationConductor.cs:147`). When the provider cannot read images the gateway throws `LlmVisionUnavailableException` before any call, and the pump completes the reply with `StreamPumpOptions.VisionUnavailableMessage`, "The connected AI source cannot look at pictures; ask it in words or connect one that can." (`src/Scout.Conversation/Streaming/StreamPumpOptions.cs:70`, caught at `src/Scout.Conversation/Streaming/StreamPump.cs:151`), instead of answering as if no picture had been sent. `ChatMessage`'s `ToString` prints `Image = <n> bytes` or `null`, never the bytes (`src/Scout.Conversation/Abstractions/ChatMessage.cs:75`).
