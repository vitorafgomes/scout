# Desktop operator window

> The part of [[pages/services/desktop-ui]] where the owner runs the YouTube channel operator; the pipeline is the worker's ([[pages/services/operator]]) and its state the control plane's ([[pages/decisions/0033-channel-operator-architecture]]).

## To change here, read

- [[pages/decisions/0033-channel-operator-architecture]] - the operator's state lives in the control plane; these pages read and edit it there, hold no pipeline logic, and live in their own desktop window, not a local web site.
- [[pages/decisions/0032-per-feature-write-permissions]] - the owner's YouTube write grant gates a start, a production, an assembly, a publish and an experiment; the approval of a package, its publish settings, a proposal decision and an adoption are the owner's, in the desktop. The grant itself needs the upload scopes on the Google sign-in ([[pages/services/desktop-ui]], YouTube connection).
- [[pages/services/operator]] - the worker side: the stages, and the `ffmpeg` and font paths it binds under `Scout:Operator`.
- [[pages/services/control-plane]] - the rules behind every refusal these pages show.
- [[pages/roadmap/youtube-channel-operator]] - phases 2 to 5.

## Operator window

The YouTube channel operator has its own window of the desktop app, not a local web site ([[pages/decisions/0033-channel-operator-architecture]]): no port is opened, its pages reach the control plane only through main like every other page, and approvals stay in the desktop.

- **Opening.** "Open YouTube operator" on the YouTube card (see YouTube connection) calls `scout:operator.window` (`ui/packages/shared/src/ipc-contract.ts:73`), handled by `registerOperatorWindow` (`ui/packages/main/src/operator/operator-window.ts:39`, called at `ui/packages/main/src/main.ts:717`). The first call creates the window; while it exists, a second call restores it if minimised, shows it and focuses it, and never opens a second one. After the owner closes it, the next call makes a new one.
- **Window.** 1400 x 900, at least 960 x 640, resizable, titled "Scout - YouTube operator"; the page's own `<title>` does not replace it (`ui/packages/main/src/operator/operator-window.ts:94`). It loads `index.html#/operator`, or the dev server's `/#/operator` in development, and shows once ready.
- **Hardening.** The main window's `webPreferences`: context isolation, no Node integration, sandbox, web security, no insecure content, no experimental features, and the same preload (`ui/packages/main/src/operator/operator-window.ts:78`). Every `window.open` is denied (`:89`) and every navigation is blocked and logged (`:90`). It runs in the default session, so the CSP main sets on every response (`ui/packages/main/src/main.ts:159`, `:173`) and the microphone rule apply to it unchanged.
- **Place.** The bounds are stored as JSON under the main-only vault key `operator.window` (`ui/packages/main/src/vault/safe-storage-vault.ts:22`) when the window is moved or resized (Electron emits those events on macOS and Windows), when it closes, and when Scout quits (`ui/packages/main/src/operator/operator-window.ts:98`, `:100`, `:123`). Read once at start, they are restored only when their top-left corner lies in the work area of a current display (`:88`); otherwise the window opens at the default size. A vault that cannot be read or written is logged with the error code only and never stops the window.
- **Closing with the app.** `dispose` saves the place, destroys the window and removes the handler (`ui/packages/main/src/operator/operator-window.ts:123`); `disposeAll` calls it on quit (`ui/packages/main/src/main.ts:231`), so the tray's Quit and closing the main window with keep running off still quit Scout and take the operator window with them. Closing the operator window alone never quits Scout while the main window or the tray keeps it running.
- **Pages.** `sc-operator-shell` (`ui/packages/renderer/src/app/operator/operator-shell.component.ts:10`) has its own left navigation, Production, Assembly, Reports, Experiments and Approvals (`ui/packages/renderer/src/app/operator/operator-shell.component.ts:13`), and none of the main window's sidebar, wizard shell or update bar. Production, Assembly, Reports and Experiments are described below. Approvals is the Review screen filtered to `youtube` (see Review); an action the worker is running has the status `executing` and shows an "Executing" badge instead of Approve and Reject (`ui/packages/renderer/src/app/review/review.component.ts:57`), though today's host lists only `pending` actions in `ListPendingActions`, so an executing one does not reach the list yet; because the filter runs after the last 50 writes are loaded, it can show fewer than 50 YouTube writes when other features wrote more recently. Main pushes `scout:actions.changed` and `scout:features.changed` to every window, so the operator window hears both. The main window's sidebar no longer has Production: Features is followed by Review (`ui/packages/renderer/src/app/shell/post-connect-shell.component.ts:43`).

## Production

The Production page (route `operator/production` in the operator window, see Operator window above, `ui/packages/renderer/src/app/app.routes.ts:86`) is the desktop side of the channel operator ([[pages/roadmap/youtube-channel-operator]] phases 2 and 3, [[pages/decisions/0033-channel-operator-architecture]]). It reads and edits the operator's state in the control plane and holds no pipeline logic; the worker researches, writes the script and makes the media. `ui/packages/renderer/src/app/production/production.component.ts:690` has five parts:

- **What Scout can make** (`:62`) - the readiness the worker last reported, read once on open from `scout:operator.readiness` (`:925`): "Narration: available" or "not available", "Generated pictures: available" or "not available", the provider ("none" when empty), "YouTube: signed in" or "not signed in", and each note. Before the worker reports, the control plane answers all false with the note "The Scout worker has not reported yet."
- **Mandate** (`:86`) - objective, audience, up to five pillars, cadence, language, voice and style, blocked topics as a comma list, the target metric (Views, Watch hours, Subscribers or Engagement, stored as `views`, `watch_hours`, `subscribers`, `engagement`, `:38`) and the target value. Save sends every field trimmed, the filled pillars only and the blocked topics split on commas to `scout:operator.saveMandate` (`:752`), then shows "Saved <yyyy-MM-dd HH:mm>". With no mandate saved: "The operator needs a mandate before it makes a video: what the channel is for, who it is for and its language. Fill it in and save it." A refused save shows the reason.
- **Make a video** - a topic and the button, disabled under 3 characters; `scout:operator.startProject` with the trimmed topic, then the queued project's topic and status under the field (`:777`). Without the owner's YouTube write grant the control plane refuses the start, and the reason, "The owner has not allowed youtube to write; allow it on the Features screen of Scout Desktop.", shows under the field.
- **Projects** - the last 50 from `scout:operator.projects`, newest created first (`:960`), each with its topic, status badge and updated time. Empty: "No videos yet. Ask for one above, or ask Scout in chat."
- **Project detail** (`:259`), on a click, from `scout:operator.project`: the error if the pipeline failed, the topic candidates (title, fit as a percentage, reason), the script (hook, sections with heading and narration, call to action, title variants, description, tags, chapters) and the claims (text, risk, status, the owner's note, source URLs). Each with its own empty state. Supported and Unsupported send that status to `scout:operator.decideClaim`; Waive opens a note field and "Waive claim" stays disabled until the note has text, then sends `waived` with the trimmed note (`:806`). A source URL is shown as text with a Copy button (`:327`), never as a link: the URLs come from the model and the web, and `scout:app.openExternal` allows only a fixed list of hosts.
- **Scenes** (`:391`), in the project detail. On a `script_ready` or `media_ready` project (`:29`), or a `failed` one with a script, as the control plane allows (`:825`), "Produce video media" sends the project id to `scout:operator.production` (`:852`); while any claim is `pending` it stays disabled and says "<n> claim(s) is/are still pending; decide every claim before producing the video." (`:832`), and a refusal shows the control plane's reason. A `producing` project shows "<n> of <m> scenes ready" (`:415`). The scenes are listed by their `order` (`:423`), each with its narration, "Picture prompt: ...", the status badge (`planned`, `generating`, `ready`, `failed`), "Audio: generated | your file | none · Picture: generated | your file | text card", its error in the failure style only on a `failed` scene (`:437`) and otherwise as a plain note (`data-test` `scene-note-<id>`, `:440`), so a fallback note on a `ready` scene does not read as a failure, an image preview, alt text "Picture of scene <order>" with the 1-based order (`:448`), and an audio player with controls when the scene has a file (`:447`, `:455`), and Lock or Unlock, Move up, Move down (off at the ends), Regenerate (off on a locked scene), Attach audio and Attach image. Move sends every scene id in the new order to `scout:operator.sceneOrder` (`:874`); Lock sends the flipped flag to `scout:operator.sceneLock` (`:864`); Regenerate sends the scene to `scout:operator.sceneRegeneration` (`:883`); Attach sends the project id, the scene id and `audio` or `visual` to `scout:operator.sceneMedia` and nothing else (`:889`). Each answer replaces the project in the detail and the list; a refusal shows its reason under the scenes, and a closed file dialog changes nothing.

The screen loads the mandate and the readiness once, and the list on open and every 10 s while it is open (`:25`, `:956`). The list carries whole projects, so each refresh takes the selected project's detail from it and reads that project with `scout:operator.project` only when it is no longer in the list; a click on a project reads it once. A failed load shows the error above the sections and keeps the last list and project.

In main, `registerOperatorHandlers` (`ui/packages/main/src/ipc/operator.ts:157`, wired at `ui/packages/main/src/main.ts:623`) validates before calling the control plane, with the control plane's own messages: the objective and the language are required, at most 5 pillars of at most 80 characters (`:111`); a topic is 3 to 200 characters after trimming (`:249`); a claim is `supported`, `unsupported` or `waived`, and `waived` needs a note (`:267`); the project list asks for at most 200; a scene order lists every scene id once (`:102`); a lock is `true` or `false`; an attach names ids of letters, digits, `-` and `_` only and the kind `audio` or `visual` (`:362`). A refusal reaches the renderer as `operator/invalid-request`. The client calls the twenty-one `scout.controlplane.v1.Operator` rpcs, the four of the Assembly page and the four of publishing and learning included, on the desktop token (`ui/packages/main/src/control-plane/client.ts:669`); it loads `operator.proto` with the other protos (`:594`), maps `INVALID_ARGUMENT` to `ControlPlaneInvalidArgumentError` (`control-plane/invalid-argument`), `PERMISSION_DENIED` to `ControlPlanePermissionDeniedError` (`control-plane/permission-denied`) and `NOT_FOUND` to `ControlPlaneNotFoundError` (`control-plane/not-found`), each carrying the control plane's message (`ui/packages/shared/src/errors.ts:132`, `:139`, `:146`), and answers a mandate with no `updated_at`, or a `NOT_FOUND`, as no mandate (`ui/packages/main/src/control-plane/client.ts:732`); a scene's and the readiness's absent optional fields arrive as `null` (`:536`, `:553`). The DTOs are `MandateDto`, `OperatorProjectDto` with its `scenes`, `ClaimDecisionRequest`, `SceneDto`, `SceneMediaRequest` and `ReadinessDto` (`ui/packages/shared/src/ipc-contract.ts:555`, `:615`, `:797`, `:762`, `:824`, `:836`).

**Owner files.** The renderer never sends or receives a path. On `scout:operator.sceneMedia` main asks the control plane for the project's media directory (`GetMediaDirectory`, main only), opens the native file dialog filtered to the kind's extensions (`chooseWithDialog`, `ui/packages/main/src/operator/media.ts:229`, wired at `ui/packages/main/src/main.ts:627`), and `copyOwnerMedia` (`ui/packages/main/src/operator/media.ts:186`) refuses another extension (audio mp3, wav, m4a, ogg; pictures png, jpg, jpeg, webp), a folder, audio over 100 MB and a picture over 20 MB (`:44`, `:51`), then copies the file into that directory as `owner-<scene>-<12 hex>.<ext>` without overwriting (`:209`). Only that name goes to `AttachSceneMedia`; when the control plane refuses it, main deletes the copy (`ui/packages/main/src/ipc/operator.ts:383`). A failed copy reaches the renderer as `operator/media-unavailable` with a message that names no path; a closed dialog answers `{ project: null }`.

**Previews.** Main registers the `scout-media` scheme as standard, secure and streaming, without `bypassCSP`, before the app is ready (`ui/packages/main/src/operator/media.ts:12`, `ui/packages/main/src/main.ts:263`), and serves `scout-media://<projectId>/<fileName>`, any query string ignored (`ui/packages/main/src/main.ts:629`, `ui/packages/main/src/operator/media.ts:120`): the project id must be letters, digits, `-` and `_` (`:57`), the decoded file name a plain name of at most 120 characters with no separator, no `..`, no leading dot and a known media extension (`:64`); the directory comes from `GetMediaDirectory` and must be absolute, and main keeps it 60 s per project id so a page of previews makes one gRPC call, forgetting it on any error (`:75`, `:172`); the real path of the file, after symlinks, must sit directly in the real directory on every request (`:86`). Anything else, a missing project included, is a 404. The file is streamed, never read whole: without a `Range` header the answer is 200 with the content type, `Content-Length` and `Accept-Ranges: bytes`; one byte range (`bytes=a-b`, `bytes=a-`, `bytes=-n`) is a 206 with `Content-Range` and its `Content-Length` (`:92`, `:163`); a range that starts past the end, ends before it starts or asks for no bytes is a 416 with `Content-Range: bytes */<size>` (`:148`); a `Range` header that is not one byte range is ignored. The renderer builds the URL from the project id and the file name in the DTO, with `?v=<updatedAt>` encoded so a regenerated or attached file with the same name is fetched again (`ui/packages/renderer/src/app/production/production.component.ts:848`). The content security policy allows `scout-media:` for `img-src` and is the only `media-src`, in the header main sets (`ui/packages/main/src/main.ts:159`, `:173`) and in the page's meta tag (`ui/packages/renderer/src/index.html:10`).

## Assembly

The worker renders; the control plane decides what is allowed. `AssemblyComponent` (`ui/packages/renderer/src/app/assembly/assembly.component.ts:704`):

- **Picker** (`:67`) - a select of the last 50 projects whose status is `media_ready`, `assembly_queued`, `assembling`, `assembled`, `approved` or `failed` (`:25`), newest created first, each as "<topic> (<status>)", after "Choose a video". With none: "No video is ready for assembly yet. Produce its media on the Production page."
- **Assemble video** (`:84`) - enabled on a `media_ready` or `assembled` project, or a `failed` one with at least one scene and every scene `ready` (`:787`), the control plane's own rule; it sends the project id to `scout:operator.assembly` (`:890`) and a refusal shows the control plane's reason. While the project is `assembly_queued` the page says "Queued for assembly; the Scout worker starts it next.", while `assembling` "Assembling the video, its Shorts and its thumbnail." (`:91`, `:95`).
- **Package**, once the owner first asked for assembly: the package error in the failure style (`:106`), the video in a `<video controls>` (`:114`), each Short with its own player and its hook (`:129`), and the thumbnail with the alt text "Thumbnail of the video" (`:142`), each read through `scout-media` with `?v=<updatedAt>` so a new render with the same name is fetched again (`:876`). "No Shorts yet." while there are none.
- **Checks** (`:152`) - a table of each check the worker ran: its name, a `pass`, `warn` or `fail` badge, its detail. "No checks yet." while there are none.
- **Metadata**, on an `assembled` or `approved` project - the title with a "<n> / 100" counter of the trimmed text (`:189`), the description with "<n> / 5000", the tags as chips with a remove button each and a field whose Enter or "Add tag" adds one, with "<n> / 500" over all tags counted YouTube's way, the control plane's count, two more for a tag with a space and a comma between tags (`:211`, `:753`). "Save metadata" (`:254`) stays disabled while the title is empty or a limit is broken (`:758`) and sends the trimmed title and description and the tags to `scout:operator.packageMetadata` (`:894`). The form takes the package's title, description and tags when another project is chosen and whenever the package's metadata changes, never on a refresh that leaves it as it was (`:936`), so unsaved edits survive the polling. Saving on an approved package returns it to `assembled` without its approval; the page shows the project the control plane returns.
- **Media rights** - the checkbox "I own or have the rights to every image, recording and music in this video" (`:269`), enabled only on an `assembled` package whose rights are not confirmed; ticking it sends the project id to `scout:operator.mediaRights`. Once confirmed it stays ticked and disabled; a failed confirmation unticks it and shows the reason (`:905`).
- **Approve package** (`:298`) - disabled while any reason holds, each listed above it (`:289`, built at `:800`): "The video is not assembled.", "Confirm the media rights first.", "<n> check failed." or "<n> checks failed.", "1 claim is not supported or waived." or "<n> claims are not supported or waived.". Otherwise it sends the project id to `scout:operator.packageApproval`; an approved package shows "Approved <yyyy-MM-dd HH:mm>" (`:283`) and no button. A refusal shows the control plane's reason.

The page loads the list on open and every 10 s while it is open (`:23`, `:950`); a failed load shows the error above the picker and keeps the last list.

## Media tools

Scout Desktop ships the `ffmpeg` the worker assembles with, and the font it draws captions and text cards with; the worker measures media with `ffmpeg` itself, so no `ffprobe` is shipped.

- **Pinned table.** `ui/build/media-tools.json:1` names, per bundled target, the archive URL, its SHA-256 and its top folder, and the fonts with theirs. `ffmpeg` is `n9.0.2-39-g7adfbe40dc`, the LGPL static build of BtbN/FFmpeg-Builds release `autobuild-2026-10-31-12-59`, the last October 2026 build (BtbN keeps the last build of each month for two years and deletes daily builds after 14 days), for `linux-x64` and `win32-x64`, with the SHA-256 of the release's `checksums.sha256`; the configure line in both binaries enables `libopenh264`, `libvpx`, `libopus` and `libfreetype` and not `gpl` (read from the files, never run). The fonts are Noto Sans Regular and Bold (hinted TTF) and their SIL Open Font License 1.1 text, from `notofonts/notofonts.github.io` at commit `e408cf09bf2042e9fe0d7d22789c29510e876359`, with the SHA-256 computed on download.
- **Fetch.** `ui/build/scripts/fetch-media-tools.mjs:87` runs inside `package:all`, after the Google client step and before the worker publish (`ui/package.json:23`), so every `dist` script has the files before electron-builder runs; it targets the machine's `<platform>-<arch>`, or the target given as its argument (`:142`). Each download lands in `ui/build/media-cache/` only when its SHA-256 matches the table (`:40`): a mismatch or an error status fails the build and keeps nothing. Only `bin/ffmpeg` and `LICENSE.txt` are extracted (`:23`), with the system `tar`, on Windows the `tar.exe` of System32, which reads zip (`:70`), into `ui/packages/main/resources/media-tools/<platform>-<arch>/`, `ffmpeg` made executable outside Windows (`:130`), with a `NOTICE.txt` naming the version, the release, the archive's SHA-256 and the FFmpeg source of the build (`:56`); the fonts and `OFL.txt` go to `ui/packages/main/resources/fonts/` on every target, macOS included, before the archive step (`:96`). Nothing is downloaded or extracted again when the notice and the files are in place and the fonts match (`:115`); the notice no longer names `ffprobe`, so a folder fetched before is extracted once more. A target the table has no archive for, macOS, gets the fonts only and no `media-tools` folder (`:107`). The cache and both output folders are gitignored; `fetch-media-tools.d.mts` types the script for its tests.
- **Packaged.** electron-builder copies both folders as resources `media-tools` and `fonts` (`ui/build/electron-builder.yml:49`, `:53`) and keeps them out of the app archive, so the binaries ship once (`:27`, `:28`).
- **Worker environment.** `resolveMediaTools` (`ui/packages/main/src/worker/resolve-binary.ts:101`) looks under the resources folder when packaged and under `ui/packages/main/resources` in development, and answers each path only when its file exists. `buildEnv` always sets `SCOUT__OPERATOR__FFMPEGPATH` and `SCOUT__OPERATOR__FONTPATH` (`ui/packages/main/src/worker/build-env.ts:95`), empty for what was not bundled, and main passes the resolved paths at every worker start (`ui/packages/main/src/main.ts:511`). The supervisor drops any inherited spelling of the two keys (`ui/packages/main/src/worker/supervisor.ts:389`), so only the desktop's values reach the worker. The worker reads an empty program path as `ffmpeg` on the system path, then `/opt/homebrew/bin/ffmpeg`, then `/usr/local/bin/ffmpeg`, and an empty font path as no font ([[pages/services/operator]]).
- **macOS.** BtbN publishes no LGPL macOS build, so no `ffmpeg` is bundled: the worker runs the one on the system path, or the Homebrew or `/usr/local/bin` one when the app was started without the shell's path, with the bundled Noto Sans as its font. That ffmpeg must have every filter the assembly uses (`gblur` and `drawtext` among them); the readiness note names the first one missing.
- **CI.** `release.yml` and `ui-ci.yml` cache `ui/build/media-cache` keyed by the hash of `ui/build/media-tools.json` on every OS, so macOS caches the fonts (`.github/workflows/release.yml:100`, `.github/workflows/ui-ci.yml:121`); the fetch itself runs in the existing Package step.
- **Licences.** `LICENSE.txt` beside the programs is the archive's (GNU LGPL version 3), `NOTICE.txt` names where the source of that exact build is, and `OFL.txt` sits beside the fonts. A new build is a new table row: the tag, URL, SHA-256, folder, version and source change together, and the cache key with them.

## Invariants

- [[pages/decisions/0033-channel-operator-architecture]] - `scout:operator.window` opens or focuses Scout's own operator window and changes nothing else; the other twenty `scout:operator.*` channels change only the control plane's own operator state (the mandate, a queued project, a claim decision, a production request, the scene order, a lock, a regeneration request, an attached file name, an assembly request, the package metadata, the media-rights confirmation, the package approval, the owner's publish settings, a proposal decision, an experiment start and an adoption) and, for `sceneMedia`, write one file the owner chose into that project's media directory under Scout's data folder; none calls YouTube, a model or anything outside Scout; approving a package uploads nothing, and publishing, starting an experiment and adopting a winner hand the control plane the owner's decision, after which the upload, the thumbnail and each arm or winner change run as approved actions the worker performs through the write gate ([[pages/services/operator]]); the desktop never calls YouTube's write API. The channel names pass the contract test's write-verb scan without an allow-list entry (`ui/packages/shared/test/ipc-contract.test.ts`, `ui/packages/main/test/ipc-operator.test.ts`).
- [[pages/invariants/no-executive-writes]] - the media tools are fetched at build time by the packaging script only, from pinned URLs whose SHA-256 is checked before anything is kept; nothing at run time downloads or replaces them, and neither the worker nor chat can reach the script.
- [[pages/invariants/secrets-never-in-source]] - the fetch needs no credential and the worker environment gains three paths, none secret.
