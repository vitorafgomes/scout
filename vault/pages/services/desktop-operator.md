# Desktop operator window

> The part of [[pages/services/desktop-ui]] where the owner runs the YouTube channel operator; the pipeline is the worker's ([[pages/services/operator]]) and its state the control plane's ([[pages/decisions/0033-channel-operator-architecture]]).

## To change here, read

- [[pages/decisions/0033-channel-operator-architecture]] - the operator's state lives in the control plane; these pages read and edit it there, hold no pipeline logic, and live in their own desktop window, not a local web site.
- [[pages/decisions/0032-per-feature-write-permissions]] - the owner's YouTube write grant gates a start, a production, an assembly, a publish, an experiment, a comment sync request, a draft request, a reply approval, a hold and using an idea; the approval of a package, its publish settings, a proposal decision, an adoption, each reply and each hold are the owner's, in the desktop. The grant itself needs the upload scopes on the Google sign-in ([[pages/services/desktop-ui]], YouTube connection).

## Operator window

The YouTube channel operator has its own window of the desktop app, not a local web site ([[pages/decisions/0033-channel-operator-architecture]]): no port is opened, its pages reach the control plane only through main like every other page, and approvals stay in the desktop. Its `scout:operator.*` channels are listed on [[pages/services/desktop-channels]].

- **Opening.** "Open YouTube operator" on the YouTube card (see YouTube connection) calls `scout:operator.window` (`ui/packages/shared/src/ipc-contract.ts:79`), handled by `registerOperatorWindow` (`ui/packages/main/src/operator/operator-window.ts:39`, called at `ui/packages/main/src/main.ts:745`). The first call creates the window; while it exists, a second call restores it if minimised, shows it and focuses it, and never opens a second one. After the owner closes it, the next call makes a new one.
- **Window.** 1400 x 900, at least 960 x 640, resizable, titled "Scout - YouTube operator"; the page's own `<title>` does not replace it (`ui/packages/main/src/operator/operator-window.ts:94`). It loads `index.html#/operator`, or the dev server's `/#/operator` in development, and shows once ready.
- **Hardening.** The main window's `webPreferences`: context isolation, no Node integration, sandbox, web security, no insecure content, no experimental features, and the same preload (`ui/packages/main/src/operator/operator-window.ts:78`). Every `window.open` is denied (`:89`) and every navigation is blocked and logged (`:90`). It runs in the default session, so the CSP main sets on every response (`ui/packages/main/src/main.ts:162`, `:176`) and the microphone rule apply to it unchanged.
- **Place.** The bounds are stored as JSON under the main-only vault key `operator.window` (`ui/packages/main/src/vault/safe-storage-vault.ts:22`) when the window is moved or resized (Electron emits those events on macOS and Windows), when it closes, and when Scout quits (`ui/packages/main/src/operator/operator-window.ts:98`, `:100`, `:123`). Read once at start, they are restored only when their top-left corner lies in the work area of a current display (`:88`); otherwise the window opens at the default size. A vault that cannot be read or written is logged with the error code only and never stops the window.
- **Closing with the app.** `dispose` saves the place, destroys the window and removes the handler (`ui/packages/main/src/operator/operator-window.ts:123`); `disposeAll` calls it on quit (`ui/packages/main/src/main.ts:232`), so the tray's Quit and closing the main window with keep running off still quit Scout and take the operator window with them. Closing the operator window alone never quits Scout while the main window or the tray keeps it running.
- **Pages.** `sc-operator-shell` (`ui/packages/renderer/src/app/operator/operator-shell.component.ts:10`) has its own left navigation, Production, Assembly, Reports, Experiments, Comments and Approvals (`ui/packages/renderer/src/app/operator/operator-shell.component.ts:10`), and none of the main window's sidebar, wizard shell or update bar. Production, Assembly, Reports, Experiments and Comments are described below. Approvals is the Review screen filtered to `youtube` (see Review); an action the worker is running has the status `executing` and shows an "Executing" badge instead of Approve and Reject (`ui/packages/renderer/src/app/review/review.component.ts:57`), though today's host lists only `pending` actions in `ListPendingActions`, so an executing one does not reach the list yet; because the filter runs after the last 50 writes are loaded, it can show fewer than 50 YouTube writes when other features wrote more recently. Main pushes `scout:actions.changed` and `scout:features.changed` to every window, so the operator window hears both. The main window's sidebar no longer has Production: Features is followed by Review (`ui/packages/renderer/src/app/shell/post-connect-shell.component.ts:43`).

## Production

- **Replies** (`:203`) - each approved, publishing, posted or failed reply with its approved text: "Waiting to publish", "Publishing", the link `https://www.youtube.com/watch?v=<video id>&lc=<reply id>` with both ids encoded (`:653`), opened through `scout:app.openExternal`, whose allow-list checks only the protocol and the host `www.youtube.com` (`ui/packages/main/src/ipc/app.ts:29`), or the reply's error. A reply waiting to publish and a hold waiting to run each have Cancel (`:220`, `:334`), which sends `dismiss` to `scout:operator.commentDecision`, so the control plane cancels the approved action and marks the comment dismissed; a publishing reply has none, because the control plane refuses it there, and a refusal shows its reason.
- **Other comments** (`:253`) - the rest that are new and not spam, with Draft (`draft`) and Dismiss; a comment the owner asks a draft for moves to Questions and requests.
- **Quarantine** (`:292`) - the quarantined comments, with Not spam (`not_spam`) and Hold on YouTube, whose dialog lists `comments.setModerationStatus: hold for review on YouTube` (`:437`) before "Confirm and hold" sends `hold`; a hold waiting for the worker shows "Waiting to hold", a held one "Held for review on YouTube", and a hold that failed its error with Dismiss (`:59`).
- **Audience ideas** (`:366`) - each proposed idea's text, with "Make a video" (`use` true) and Dismiss (`use` false) on `scout:operator.ideaDecision` (`:622`).

Every comment's text, author and theme reaches the page through Angular interpolation only, never `innerHTML`; there is no avatar, no author link and no change to the content security policy. Main does not write the reply or the hold: it hands the owner's decision to the control plane, which records it and queues the one approved action the worker runs ([[pages/decisions/0032-per-feature-write-permissions]]).

In main, `scout:operator.comments` and `scout:operator.commentSync` take nothing; `scout:operator.commentDecision` refuses a decision other than `draft`, `dismiss`, `not_spam` and `hold` ("A comment is decided as draft, dismiss, not_spam or hold.") and a comment id that does not match `^[A-Za-z0-9_.-]{1,100}$` after trimming ("'<id>' is not a comment id.", `ui/packages/main/src/ipc/operator.ts:118`, `:156`); `scout:operator.replyApproval` takes the same id and a text of 1 to 1000 characters after trimming ("A reply is 1 to 1000 characters.") and forwards the trimmed text; `scout:operator.ideaDecision` needs an idea id and a boolean `use` ("An idea is used or dismissed."), all before the control plane (`:766` to `:788`). Every other rule, a control character in a reply among them, is the control plane's, and its refusal reaches the renderer unchanged. The client calls `ListComments`, `RequestCommentSync`, `DecideComment`, `ApproveReply` and `DecideIdea` with the operator error mapping above (`ui/packages/main/src/control-plane/client.ts:969`); `toComments` (`:695`) maps every absent optional field, the approved text, the reply id, the error, the decision time, an idea's project id and the sync's three times, to `null`. Every channel of the client, to Providers, Features and Operator, sends and receives gRPC messages of up to 16 MB (`:403`), the size the worker and the control plane allow, because a full comments view at the caps, 1000 comments of up to 2000 characters with their drafts and replies, passes gRPC's 4 MB default. The DTOs are `AudienceCommentDto`, `AudienceIdeaDto`, `CommentsViewDto`, `CommentDecisionRequest`, `ReplyApprovalRequest` and `IdeaDecisionRequest` (`ui/packages/shared/src/ipc-contract.ts:788`, `:809`, `:818`, `:828`, `:834`, `:839`).
