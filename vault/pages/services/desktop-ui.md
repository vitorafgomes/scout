# Desktop UI

> Onboards a chat bot, stores its secrets, launches and supervises the .NET worker, and manages local models; it never calls the LLM itself.

## Responsibility

Owns: first-run wizard that sets up the Discord bot from its token, the Slack setup, the GitHub sign-in and its token refresh, the YouTube sign-in and its token refresh, finding the owner's kubeconfig and keeping the contexts the owner allowed, the credential vault, worker lifecycle and log streaming, detection of installed chat clients and local inference backends, Ollama and Whisper model downloads, the tray, keep running and start at login, packaging.

Also owns the quick-ask window: the global shortcut that opens it, the microphone capture and WAV encoding in the renderer, and the questions main writes to the worker's stdin ([[pages/services/adapter-local]] answers them).

Also owns the lifecycle of [[pages/services/host-control-plane]] and the gRPC client the Features, Review and Production screens use to reach it.

Does not own: any conversation, LLM call or plugin; those live in [[pages/services/host-console]] and behind it.

## Layout

Four Bun packages under `ui/packages/`:

| Package | Role | Built with |
|---|---|---|
| `shared` | IPC channel names, request and response types, `VaultKey` union, the version compare and download pick | type-only |
| `main` | Electron main process: IPC handlers, vault, supervisor, Discord REST calls, OAuth loopback (ChatGPT sign-in), tray | `bun build` to ESM |
| `preload` | Context bridge that exposes the typed channels to the renderer | `bun build` to CJS |
| `renderer` | Angular 22 app: wizard, chat, sources, features, production, review, llm, logs and settings screens | `ng build` |

Packaging: `ui/build/scripts/publish-worker.sh:14` lists the two hosts, `Scout.Host.Console` and `Scout.Host.ControlPlane`, and publishes each self-contained single-file per RID into the same `ui/build/worker/<rid>/` folder (`publish-worker.ps1` does the same). `ui/build/electron-builder.yml:40` copies `src/Scout.ControlPlane.Contracts/protos/*.proto` into `resources/protos`, because the client loads the protos at runtime. The electron-builder config targets AppImage and deb on Linux, dmg on macOS, nsis on Windows, and names every package `Scout-Desktop-<version>-<os>-<arch>.<ext>` without a space (`ui/build/electron-builder.yml:7`), because GitHub rewrites spaces in release asset names. A version tag such as `v1.2.3` runs `.github/workflows/release.yml`, which writes the tag's version into `ui/package.json` on the runner (the repository keeps a placeholder `0.0.1`), builds the AppImage, the deb, the Apple silicon dmg and the Windows installer and publishes them as a GitHub Release with one `SHA256SUMS-<os>.txt` per platform; the project site links to them ([[pages/decisions/0029-project-site-and-releases]], [[pages/runbooks/release]]). The control-plane host runs with the worker folder as its working directory, so it also reads the console host's `appsettings.json`; no section overlaps today (the console reads `Scout:Llm`, the control plane `Scout:Providers`, `Scout:Features` and `Scout:LocalRuntime`).

## How it works

```mermaid
sequenceDiagram
    participant R as Renderer (Angular)
    participant P as Preload bridge
    participant M as Main (Electron)
    participant V as safeStorage vault
    participant D as Discord REST
    participant W as Scout.Host.Console
    R->>P: scout:discord.checkToken(token)
    P->>M: ipcMain.handle
    M->>D: GET /applications/@me (Bot token)
    D-->>M: application id and name
    M->>V: encryptString(discord.bot-token, discord.client-id)
    M-->>R: application and bot names, never the token
    R->>P: scout:worker.start
    P->>M: ipcMain.handle
    M->>V: get(VaultKey) for every key
    M->>W: spawn(binary, env SCOUT__ADAPTERS__DISCORD__BOTTOKEN ...)
    W-->>M: stdout SCOUT_READY
    M-->>R: scout:worker.events (running)
    W-->>M: stderr log lines
    M-->>R: scout:worker.events (log)
```

The vault to environment mapping is `ui/packages/main/src/worker/build-env.ts`; at app start `migrateLegacyApiKey` (`ui/packages/main/src/worker/build-env.ts:190`, called from `ui/packages/main/src/main.ts:291`) moves a legacy shared cloud key into the active provider's own slot; the binary is resolved per platform and packaging mode in `ui/packages/main/src/worker/resolve-binary.ts:38`. Crash handling is a bounded restart policy with backoff (`ui/packages/main/src/worker/supervisor.ts:161`); a crash after which no restart is scheduled carries `gaveUp: true`. `stop()` cancels a scheduled restart and resolves at once when no worker process is alive, so Quit exits during the backoff or after a crash (`ui/packages/main/src/worker/supervisor.ts:331`).

## Control plane

At app start `ui/packages/main/src/main.ts:575` calls `connectControlPlane` (`ui/packages/main/src/control-plane/launcher.ts:231`). It launches the host through `launchControlPlane`, waits up to 10 s for the socket file (`ui/packages/main/src/control-plane/launcher.ts:190`), then opens the gRPC client with the protos from `resolveProtoDir` (`ui/packages/main/src/worker/resolve-binary.ts:70`): `resources/protos` when packaged, the source tree otherwise. Any failure on the way, whether a missing binary, a host that exits, a socket that never appears, an insecure socket directory or `win32`, becomes `ControlPlaneUnavailableError` on the client promise and one `warn` log line; the app keeps running. A failure after the spawn kills the host it started, and a host that exits mid-session closes the client so later calls fail at once. `before-quit` closes the client and kills the host (`ui/packages/main/src/shell/app-lifecycle.ts:140`, `ui/packages/main/src/main.ts:219`). There is no restart: a host that dies stays down until the app restarts.

The launcher mints two tokens: the desktop token, which only the host and the main process hold, and a worker token for the host's WorkerGate service ([[pages/services/host-control-plane]]). Neither is set on the main process's own environment. While the host is launched, `connection.workerGate()` gives the socket path and the worker token; `null` when the launch was unsupported or failed or the host exited (`ui/packages/main/src/control-plane/launcher.ts:268`).

The Features IPC handlers (`ui/packages/main/src/ipc/features.ts:60`) call that client: list, set credentials, setup, delete credentials, enable and disable map one to one onto the `scout.controlplane.v1.Features` RPCs, and the client maps the wire messages onto the `FeatureDto` shapes in `ui/packages/shared/src/ipc-contract.ts`. What the owner sees:

- **Control plane not running:** "The Scout control plane is not running, so features cannot be shown." (`ui/packages/renderer/src/app/features/features.component.ts:46`).
- **Running:** the GitHub, Kubernetes and YouTube cards, and under the grid two notes: "GitHub, Kubernetes and YouTube are used by the chat bot once connected." and "A feature that writes lists its write permissions on its card and writes only after you allow them; actions that cannot be undone wait for you on the Review screen." (`ui/packages/renderer/src/app/features/features.component.ts:88`). All three cards show a main-owned connection instead of the control-plane toggle and credential dialog, so no card in the catalog reaches `Enable` today; the host would answer `UNIMPLEMENTED` (it registers `NullFeatureActivator`), which the client maps to `ControlPlaneNotImplementedError` and a card would show as "Turning this feature on is not available yet." See [[pages/roadmap/followups]]. The YouTube card also carries the write permissions, see Write permissions below.

**Error codes across IPC.** Electron forwards only the message of an error thrown in an `ipcMain.handle` handler; a `code` property set in main never reaches the renderer (checked on Electron 41.3.0: the renderer receives `Error invoking remote method '<channel>': Error: <message>` with no `code`). The Features handlers therefore write the code into the message through `encodeIpcErrorMessage` (`ui/packages/shared/src/errors.ts:260`), and the store reads it back with `readIpcError` (`ui/packages/shared/src/errors.ts:268`). The other handlers still rely on the `code` property, so their code-based renderer branches never fire in the running app; see [[pages/roadmap/followups]].

The Providers handlers still call the worker over HTTP through `ui/packages/main/src/worker/http-client.ts:43`, whose endpoint comes from a `SCOUT_HTTP=` stdout line (`ui/packages/main/src/worker/log-stream.ts:18`) that only the retired `src/old/Scout.Host.Worker` printed, so the Providers screen still shows its unavailable state. The main process also still pulls Ollama models (`ui/packages/main/src/ipc/llm-pull.ts`) and downloads Whisper weights (`ui/packages/main/src/ipc/whisper.ts`) itself, from Node. At every worker start `findBestWhisperModel` (`ui/packages/main/src/worker/whisper-model.ts:13`) picks `ggml-large-v3-turbo.bin`, else `ggml-large-v3.bin`, from `userData/whisper-models`, skipping an empty file, and `buildEnv` passes it as `SCOUT__TRANSCRIPTION__MODELPATH` (`ui/packages/main/src/worker/build-env.ts:88`), nothing when none is installed, so Discord voice messages are transcribed locally ([[pages/decisions/0024-voice-messages-transcribed-locally]]). A model downloaded while the worker runs is used from the next worker start.

## Write permissions

[[pages/decisions/0032-per-feature-write-permissions]] on the desktop side. The client maps each scope row's `access` (0 read, 1 write, 2 irreversible) and the feature's `write_class` (0 none, 1 descriptive, 2 executive), `granted` and `granted_at` onto `FeatureScopeRowDto.access` and `FeatureDto.writeClass`, `granted`, `grantedAt` (`ui/packages/shared/src/ipc-contract.ts:447`, `:456`; `ui/packages/main/src/control-plane/client.ts:189`); an unknown value maps to the stricter `irreversible` or `executive`.

- **The card.** A feature whose `writeClass` is not `none` shows a Permissions block under its connection (`ui/packages/renderer/src/app/features/feature-card.component.ts:49`): one line per scope row with a `read`, `write` or `irreversible` badge, and "Write permission: not granted" or "Write permission: granted on <yyyy-MM-dd>". Today that is the YouTube card only; the catalog declares `youtube` as `executive`. On a connection card the block offers "Allow writes", disabled until the card is connected (a Google sign-in or a key), and, once granted, "Revoke writes" (`:85`, `:95`).
- **Write-verb allow-list.** Two channels carry "write" in their names and are allowed by the contract test's write-verb scan (`ui/packages/shared/test/ipc-contract.test.ts`): `scout:writes.list` reads the log of writes Scout already made and changes nothing; `scout:features.writeGrant` records the owner's grant or revocation in Scout's own feature state and calls no external system.
- **The grant.** "Allow writes" opens `sc-write-confirmation-dialog` (`ui/packages/renderer/src/app/features/write-confirmation-dialog.component.ts:99`), which lists the write rows only and says "Scout will be allowed to perform these writes on your behalf. Actions marked irreversible will still wait for your approval, one by one, on the Review screen." with Cancel and "Allow these writes"; it reuses the credential dialog's `DIALOG_STYLES` (`ui/packages/renderer/src/app/features/credential-dialog.component.ts:14`). Only "Allow these writes" calls `scout:features.writeGrant` with `{ granted: true, confirmWrites: true }`, which maps onto the `SetWriteGrant` rpc; "Revoke writes" sends `{ granted: false, confirmWrites: false }` with no dialog (`ui/packages/renderer/src/app/features/features.component.ts:209`, `ui/packages/renderer/src/app/core/features.store.ts:93`). Main forwards `granted` and `confirmWrites` only when they are the boolean `true` (`ui/packages/main/src/ipc/features.ts:155`).
- **A toggle feature.** The same dialog guards the toggle of a write-capable feature that has no main-owned connection: turning it on opens the dialog and only "Allow these writes" calls `scout:features.enable` with `confirmWrites: true`; cancelling leaves the checkbox off, because the card resets the checkbox to the feature's state before it asks (`ui/packages/renderer/src/app/features/feature-card.component.ts:115`, `ui/packages/renderer/src/app/features/features.component.ts:201`). A read-only feature toggles as before, with `confirmWrites: false`.
- **A refusal.** The control plane answers `FAILED_PRECONDITION` "Confirm the writes of <id> before enabling it" or "... before granting them", followed by the write rows. The client turns exactly that message into `ControlPlaneWriteConfirmationError` (`control-plane/write-confirmation-required`, `ui/packages/shared/src/errors.ts:125`, `ui/packages/main/src/control-plane/client.ts:405`); a `FAILED_PRECONDITION` for missing credentials stays as it was. The card shows the message.
- **Credentials follow the grant.** Any change or loss of the YouTube credential revokes the `youtube` write grant on the control plane before the worker restarts: sign-out and removing the only API key (`ui/packages/main/src/ipc/youtube.ts:64`, `:74`), a completed sign-in, a saved key and Google refusing the saved sign-in on refresh (`ui/packages/main/src/oauth/google-auth.ts:319`, `:217`, `:486`). The revoke is best-effort (`ui/packages/main/src/ipc/youtube.ts:17`): a control plane that does not answer is logged with the error code only and never blocks the credential change. Once the control plane confirms a revoke, main pushes `scout:features.changed` to every window (`ui/packages/main/src/ipc/youtube.ts:28`, `ui/packages/main/src/main.ts:363`, `ui/packages/shared/src/ipc-contract.ts:55`), and `FeaturesStore` reloads the features on it (`ui/packages/renderer/src/app/core/features.store.ts:45`), so the YouTube card stops showing writes allowed without the owner reopening the screen (`ui/packages/main/test/ipc-youtube.test.ts:206`, `ui/packages/renderer/src/app/core/features.store.spec.ts:103`); a revoke that failed pushes nothing. Deleting a feature's credentials restarts the worker so the revoked grant leaves it (`ui/packages/main/src/ipc/features.ts:111`). The owner allows writes again after reconnecting.
- **The worker.** At every worker start `readGrantedWriteFeatures` (`ui/packages/main/src/worker/build-env.ts:138`) lists the features and `buildEnv` passes the granted ids as `SCOUT__FEATURES__GRANTEDWRITES`, comma-separated, and always sets it, empty when nothing is granted, so a value inherited from the desktop's environment cannot grant writes (`:89`); the worker's guard reads it. A worker started while the control plane is still connecting waits for its client up to 10 s, the same bound as the socket wait, and then gets the grants (`ui/packages/main/src/worker/build-env.ts:151`, `ui/packages/main/src/main.ts:472`, `ui/packages/main/test/worker-build-env.test.ts:884`); one that does not connect in that time, is not launched, or does not answer starts with no grants and one `warn` line (`ui/packages/main/test/worker-build-env.test.ts:908`). A grant, a revocation, and enabling or disabling a write-capable feature restart a running worker so the guard sees the change (`ui/packages/main/src/main.ts:591`). An enable with `confirmWrites: true` that fails restarts it too, because the host clears the grant when the activation fails (`ui/packages/main/src/ipc/features.ts:129`, `ui/packages/main/test/ipc-features.test.ts:261`). The host records a grant on `Enable` only after the feature's activation succeeds, so the phase 1 "not available yet" answer leaves no grant behind. The same `buildEnv` always sets `SCOUT__WORKERGATE__SOCKETPATH` and `SCOUT__WORKERGATE__TOKEN` from `workerGate()` (`ui/packages/main/src/worker/build-env.ts:90`, `ui/packages/main/src/main.ts:476`), empty strings while the control plane is not launched, so values inherited from the desktop's environment cannot point the worker elsewhere; the worker asks the control plane through that gate before a declared write ([[pages/services/host-console]]). Overwriting the exact upper-case names is not enough on its own, because the worker's configuration reads a key in any casing, with ':' or '__', and with a `DOTNET_` prefix: the supervisor builds the child environment from `workerInheritableEnv(process.env)` (`ui/packages/main/src/worker/supervisor.ts:212`, `:396`), which drops every inherited key that normalizes (lower case, ':' to '__', a leading `dotnet_` or `aspnetcore_` removed) to `scout__workergate__*`, `scout__features__grantedwrites`, `scout_controlplane_token` or `scout_controlplane_worker_token`, and then applies `buildEnv`'s values (`ui/packages/main/test/worker-supervisor.test.ts:357`). The worker's environment never carries `SCOUT_CONTROLPLANE_TOKEN` or `SCOUT_CONTROLPLANE_WORKER_TOKEN`, and no value in it holds the desktop token (`ui/packages/main/test/worker-build-env.test.ts:969`); the empty values are pinned at `:949`. A worker started before the host is launched gets the empty gate, like the grants above, until its next start.

### Update notice

Scout Desktop tells the owner when a newer release is on GitHub Releases and shows what is new. Where the package can replace itself (an AppImage or the Windows installer) the bar offers Update and restart; elsewhere it offers Download. Nothing is downloaded or installed until the user clicks ([[pages/decisions/0031-desktop-self-update]]).

- **Check.** `registerUpdateNotice` (`ui/packages/main/src/update/update-notice.ts:131`, called at `ui/packages/main/src/main.ts:525`) schedules the first check 10 s after start and then one every 24 hours (`ui/packages/main/src/update/update-notice.ts:467`, `ui/packages/main/src/update/update-notice.ts:382`), while "Check for new versions" is on. A check (`ui/packages/main/src/update/update-notice.ts:374`) is one unauthenticated `GET https://api.github.com/repos/vitorafgomes/scout/releases/latest` with `Accept: application/vnd.github+json` and `User-Agent: Scout-Desktop/<version>`, nothing else, and a 15 s timeout (`ui/packages/main/src/update/update-notice.ts:218`); only one runs at a time. A development build (`app.isPackaged` false) never fetches and never schedules.
- **Decision** (`ui/packages/main/src/update/update-notice.ts:246`). The tag loses a leading `v` and is compared with `app.getVersion()` by `compareVersions` (`ui/packages/shared/src/version.ts:20`): numeric major.minor.patch, a prerelease below its release, anything unparseable as 0.0.0. A newer release that is neither a draft nor a prerelease, and not the version stored under `update.skipped-version`, becomes the notice: both versions, the release body as plain text, the release page and the download for this machine from `pickDownload` (`ui/packages/shared/src/version.ts:34`): the AppImage when `APPIMAGE` is set, otherwise the deb on Linux, the dmg whose name carries the arch on macOS, the exe on Windows, and the release page when no asset matches. The notice also carries `canInstall` (see Install). The notice goes on `scout:update.notice` to every window and to the tray; anything else clears it.
- **Result.** `update.last-check` keeps `{ at, result }`, the result being `up-to-date`, `available <version>`, `skipped <version>`, `error <kind>` with kind `http <status>`, `network`, `timeout` or `parse`, or `error install <kind>` after a failed install (see Install). A failed check is logged at info, leaves the notice as it was and never throws.
- **Install.** `canInstall` is `canSelfUpdate` (`ui/packages/main/src/update/update-notice.ts:62`) with an updater given: a packaged build on Windows, or on Linux with `APPIMAGE` set and the running executable inside the mount `APPDIR` names, so an `APPIMAGE` a `.deb` Scout inherited from another AppImage program never counts. `main.ts` passes `electron-updater`'s `autoUpdater` (dependency `electron-updater` ^6.8.12 in `ui/packages/main/package.json`) only in that case and `null` otherwise, so the updater is never constructed on macOS, in a `.deb` or in a development build (`ui/packages/main/src/main.ts:541`). The `Updater` interface (`ui/packages/main/src/update/update-notice.ts:43`) is the part of `AppUpdater` Scout uses. `scout:update.install` (`ui/packages/main/src/update/update-notice.ts:444`) does nothing while an install runs, and answers a `failed` progress when there is no notice or the package cannot update itself. Otherwise `install` (`ui/packages/main/src/update/update-notice.ts:309`) sets `autoDownload`, `autoInstallOnAppQuit` and `allowPrerelease` to false and no other option, so no token or header is configured (`ui/packages/main/src/update/update-notice.ts:338`), then runs `checkForUpdates`. If the updater offers a version other than the notice's, nothing is downloaded, the bar says "The release changed; check again" and the normal check runs again (`ui/packages/main/src/update/update-notice.ts:343`). Otherwise `downloadUpdate` runs, and electron-updater verifies the SHA-512 from `latest-linux.yml` or `latest.yml`. `quitAndInstall(false, true)` runs only after the download resolved and `update-downloaded` fired (`ui/packages/main/src/update/update-notice.ts:350`). Before it, `installing` is broadcast and `prepareForRestart` is awaited for at most 10 s (`ui/packages/main/src/update/update-notice.ts:289`); past that the restart goes ahead and a warning is logged. `main.ts` wires it (`ui/packages/main/src/main.ts:546`) to the lifecycle's `prepareForRestart`, which stops the worker through `stopWorker` (`ui/packages/main/src/shell/app-lifecycle.ts:87`), the same stop `before-quit` uses, so a stop in progress is never started twice and a worker started again later is stopped again on quit, and then calls `app.releaseSingleInstanceLock()`, so the new version can take the lock while the old process is still exiting. When the updater cannot apply the update (`apply`), `recoverFromFailedRestart` takes the lock again and starts the worker again if it was running before. An error or a rejection maps to a kind (`ui/packages/main/src/update/update-notice.ts:72`): `checksum` ("The download did not match the release; nothing was installed"), `no asset` (no `latest*.yml` for this platform), `http <status>`, `timeout`, `network`, `incomplete` (no `update-downloaded`) or `apply` (the updater could not replace the file). The kind becomes a `failed` progress and `error install <kind>` in `update.last-check`, logged at warn; the notice stays. The updater listeners are removed when the install ends and on `dispose`.
- **Progress.** `scout:update.progress` carries `UpdateProgress` (`ui/packages/shared/src/ipc-contract.ts:843`) to every window: `checking`, then `downloading` with percent, bytes and total, at most once per whole percent, then `ready`, then `installing`, or `failed` with a message.
- **What the AppImage update writes.** electron-updater replaces the file `APPIMAGE` names. When that name carries a version, such as `Scout-Desktop-0.1.0-linux-x86_64.AppImage`, it deletes the old file and writes the new one under the release's name in the same folder, then starts it. On the next start, `refreshLoginEntry` (`ui/packages/main/src/shell/login-item.ts:102`) rewrites the start-at-login entry when it names another executable, so a renamed AppImage keeps starting at login; with start at login off nothing is written. The Windows update runs the NSIS installer (not silent) and starts Scout again.
- **Bar.** `sc-update-notice` (`ui/packages/renderer/src/app/shell/update-notice.component.ts:60`) sits above the page in the post-connect shell (`ui/packages/renderer/src/app/shell/post-connect-shell.component.ts:105`), with `role="status"`: "Scout <latest> is available. You have <current>.", a "Release notes" link, then Update and restart when `canInstall` (`ui/packages/renderer/src/app/shell/update-notice.component.ts:82`) or Download otherwise, Later and Skip this version, and a "What's new" disclosure. While an install runs the buttons are disabled and a progress row (`ui/packages/renderer/src/app/shell/update-notice.component.ts:119`) shows "Checking the release", "Downloading <n>%" with a `<progress>` bar, or "Restarting to install". A failure shows its message with `role="alert"`, the buttons come back, and Download appears next to Update and restart as a secondary button (`ui/packages/renderer/src/app/shell/update-notice.component.ts:88`), so the file can still be fetched by hand. The notes are split into paragraphs on blank lines, lists from `- ` or `* ` lines and headings from `# ` lines, with the `**` around a leading label dropped (`ui/packages/renderer/src/app/shell/update-notice.component.ts:28`), and only ever interpolated as text, so an HTML tag in a release body shows as text. Release notes and Download go through `scout:app.openExternal` and its `github.com` allow-list. Later clears the notice for this run only, so the next daily check shows it again; Skip this version stores the version and clears the notice.
- **Tray.** While a notice exists the tray menu has "Update available: <version>" after Open Scout, which opens the window, and the tooltip ends with " - update available" (`ui/packages/main/src/tray/tray.ts:78`, `:85`).
- **Settings, Desktop.** "Check for new versions" (on by default, `update.check-enabled`) and "Last check: <date> · <result>" with Check now (`ui/packages/renderer/src/app/wizard/settings/settings.component.ts:223`, `:514`); turning the check off cancels the timer and turning it on schedules the first check again, for the session even when the vault cannot store the choice (a warning is logged instead of an error reaching Settings); a vault read that fails at start is logged at warn and the check stays on. A development build shows "Update checks run only in the installed app." instead.

- [[pages/invariants/pluggable-boundaries]] - the UI reaches the console worker only through environment variables, stdout markers and quick-ask JSON lines on stdin, and the control plane only through gRPC; no .NET type crosses, and `@grpc/grpc-js` stays under `ui/packages/main/src/control-plane/` (ADR 0011: the renderer never sees it).
