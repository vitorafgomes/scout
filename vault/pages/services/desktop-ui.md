# Desktop UI

> Onboards a chat bot, stores its secrets, launches and supervises the .NET worker, and manages local models; it never calls the LLM itself.

## Responsibility

Owns: first-run wizard that sets up the Discord bot from its token, the Slack setup, the GitHub sign-in and its token refresh, the YouTube sign-in and its token refresh, finding the owner's kubeconfig and keeping the contexts the owner allowed, the credential vault, worker lifecycle and log streaming, detection of installed chat clients and local inference backends, Ollama and Whisper model downloads, the tray, keep running and start at login, packaging.

Also owns the quick-ask window: the global shortcut that opens it, the microphone capture and WAV encoding in the renderer, the one-frame screenshot and the display-media rule that answers it, and the questions main writes to the worker's stdin ([[pages/services/adapter-local]] answers them).

Also owns the lifecycle of [[pages/services/host-control-plane]] and the gRPC client the Features and Review screens and the operator window use to reach it.

Does not own: any conversation, LLM call or plugin; those live in [[pages/services/host-console]] and behind it.

## Layout

Four Bun packages under `ui/packages/`:

| Package | Role | Built with |
|---|---|---|
| `shared` | IPC channel names, request and response types, `VaultKey` union, the version compare and download pick | type-only |
| `main` | Electron main process: IPC handlers, vault, supervisor, Discord REST calls, OAuth loopback (ChatGPT sign-in), tray | `bun build` to ESM |
| `preload` | Context bridge that exposes the typed channels to the renderer | `bun build` to CJS |
| `renderer` | Angular 22 app: wizard, chat, sources, features, review, meetings, llm, logs and settings screens, and the operator window's production, assembly and approvals pages | `ng build` |

Packaging: `ui/build/scripts/publish-worker.sh:14` lists the two hosts, `Scout.Host.Console` and `Scout.Host.ControlPlane`, and publishes each self-contained single-file per RID into the same `ui/build/worker/<rid>/` folder (`publish-worker.ps1` does the same). `ui/build/electron-builder.yml:44` copies `src/Scout.ControlPlane.Contracts/protos/*.proto` into `resources/protos`, because the client loads the protos at runtime. `package:all` also fetches the pinned `ffmpeg` and fonts into the resources the package ships, checking each SHA-256 ([[pages/services/desktop-operator]]). The electron-builder config targets AppImage and deb on Linux, dmg on macOS, nsis on Windows, and names every package `Scout-Desktop-<version>-<os>-<arch>.<ext>` without a space (`ui/build/electron-builder.yml:7`), because GitHub rewrites spaces in release asset names. A version tag such as `v1.2.3` runs `.github/workflows/release.yml`, which writes the tag's version into `ui/package.json` on the runner (the repository keeps a placeholder `0.0.1`), builds the AppImage, the deb, the Apple silicon dmg and the Windows installer and publishes them as a GitHub Release with one `SHA256SUMS-<os>.txt` per platform; the project site links to them ([[pages/decisions/0029-project-site-and-releases]], [[pages/runbooks/release]]). The control-plane host runs with the worker folder as its working directory, so it also reads the console host's `appsettings.json`; no section overlaps today (the console reads `Scout:Llm`, the control plane `Scout:Providers`, `Scout:Features` and `Scout:LocalRuntime`).

## How it works

```mermaid
sequenceDiagram
    participant R as Renderer (Angular)
    participant P as Preload bridge
    participant M as Main (Electron)
    participant V as safeStorage vault
    participant D as Discord REST
    participant W as Scout.Host.Console
    R->>P: scout:discord.checkToken(token)
    P->>M: ipcMain.handle
    M->>D: GET /applications/@me (Bot token)
    D-->>M: application id and name
    M->>V: encryptString(discord.bot-token, discord.client-id)
    M-->>R: application and bot names, never the token
    R->>P: scout:worker.start
    P->>M: ipcMain.handle
    M->>V: get(VaultKey) for every key
    M->>W: spawn(binary, env SCOUT__ADAPTERS__DISCORD__BOTTOKEN ...)
    W-->>M: stdout SCOUT_READY
    M-->>R: scout:worker.events (running)
    W-->>M: stderr log lines
    M-->>R: scout:worker.events (log)
```

The vault to environment mapping is `ui/packages/main/src/worker/build-env.ts`; at app start `migrateLegacyApiKey` (`ui/packages/main/src/worker/build-env.ts:213`, called from `ui/packages/main/src/main.ts:322`) moves a legacy shared cloud key into the active provider's own slot; the binary is resolved per platform and packaging mode in `ui/packages/main/src/worker/resolve-binary.ts:38`. Crash handling is a bounded restart policy with backoff (`ui/packages/main/src/worker/supervisor.ts:161`); a crash after which no restart is scheduled carries `gaveUp: true`. `stop()` cancels a scheduled restart and resolves at once when no worker process is alive, so Quit exits during the backoff or after a crash (`ui/packages/main/src/worker/supervisor.ts:331`).

## Control plane

At app start `ui/packages/main/src/main.ts:400` calls `connectControlPlane` (`ui/packages/main/src/control-plane/launcher.ts:231`), before the YouTube sign-in starts, so a revoke it sends at start reaches the host, and before the worker supervisor exists. It launches the host through `launchControlPlane`, waits up to 10 s for the socket file (`ui/packages/main/src/control-plane/launcher.ts:190`), then opens the gRPC client with the protos from `resolveProtoDir` (`ui/packages/main/src/worker/resolve-binary.ts:70`): `resources/protos` when packaged, the source tree otherwise. Any failure on the way, whether a missing binary, a host that exits, a socket that never appears, an insecure socket directory or `win32`, becomes `ControlPlaneUnavailableError` on the client promise and one `warn` log line; the app keeps running. A failure after the spawn kills the host it started, and a host that exits mid-session closes the client so later calls fail at once. `before-quit` closes the client and kills the host (`ui/packages/main/src/shell/app-lifecycle.ts:140`, `ui/packages/main/src/main.ts:241`). There is no restart: a host that dies stays down until the app restarts.

The launcher mints two tokens: the desktop token, which only the host and the main process hold, and a worker token for the host's WorkerGate service ([[pages/services/host-control-plane]]). Neither is set on the main process's own environment. While the host is launched, `connection.workerGate()` gives the socket path and the worker token; `null` when the launch was unsupported or failed or the host exited (`ui/packages/main/src/control-plane/launcher.ts:268`).

The Features IPC handlers (`ui/packages/main/src/ipc/features.ts:62`) call that client: list, set credentials, setup, delete credentials, enable and disable map one to one onto the `scout.controlplane.v1.Features` RPCs, and the client maps the wire messages onto the `FeatureDto` shapes in `ui/packages/shared/src/ipc-contract.ts`. What the owner sees:

- **Control plane not running:** "The Scout control plane is not running, so features cannot be shown." (`ui/packages/renderer/src/app/features/features.component.ts:47`).
- **Running:** the GitHub, Kubernetes, YouTube and Desktop cards, and under the grid two notes: "GitHub, Kubernetes and YouTube are used by the chat bot once connected." and "A feature that writes lists its write permissions on its card and writes only after you allow them; actions that cannot be undone wait for you on the Review screen." (`ui/packages/renderer/src/app/features/features.component.ts:89`). All three cards show a main-owned connection instead of the control-plane toggle and credential dialog, so no card in the catalog reaches `Enable` today; the host would answer `UNIMPLEMENTED` (it registers `NullFeatureActivator`), which the client maps to `ControlPlaneNotImplementedError` and a card would show as "Turning this feature on is not available yet." See [[pages/roadmap/followups]]. The YouTube card also carries the write permissions, see Write permissions below. A `desktop` feature from the control plane ("This computer", no credentials, the read rows Screen and Microphone, no write; `FeatureId` `'desktop'`, `ui/packages/shared/src/ipc-contract.ts:462`) shows its display name and description with Connected and no toggle, no credential action and no allowed-users warning, because its reads need no grant and the local owner skips the allow-list (`ui/packages/renderer/src/app/features/features.component.ts:78`, `:190`; [[pages/decisions/0032-per-feature-write-permissions]], [[pages/decisions/0021-allowed-users]]). Its read rows are chips under Reads: the card shows its Reads chips whenever the feature declares reads and the Permissions block only for a feature that writes (`ui/packages/renderer/src/app/features/feature-card.component.ts:110`).

**Error codes across IPC.** Electron forwards only the message of an error thrown in an `ipcMain.handle` handler; a `code` property set in main never reaches the renderer (checked on Electron 41.3.0: the renderer receives `Error invoking remote method '<channel>': Error: <message>` with no `code`). The Features handlers therefore write the code into the message through `encodeIpcErrorMessage` (`ui/packages/shared/src/errors.ts:260`), and the store reads it back with `readIpcError` (`ui/packages/shared/src/errors.ts:268`). The other handlers still rely on the `code` property, so their code-based renderer branches never fire in the running app; see [[pages/roadmap/followups]].

The Providers handlers still call the worker over HTTP through `ui/packages/main/src/worker/http-client.ts:43`, whose endpoint comes from a `SCOUT_HTTP=` stdout line (`ui/packages/main/src/worker/log-stream.ts:18`) that only the retired `src/old/Scout.Host.Worker` printed, so the Providers screen still shows its unavailable state. The main process also still pulls Ollama models (`ui/packages/main/src/ipc/llm-pull.ts`) and downloads Whisper weights (`ui/packages/main/src/ipc/whisper.ts`) itself, from Node. At every worker start `chooseWhisperModel` (`ui/packages/main/src/worker/whisper-model.ts:102`, called at `ui/packages/main/src/main.ts:515`) picks a verified model from `userData/whisper-models` (see Whisper models below), and `buildEnv` passes it as `SCOUT__TRANSCRIPTION__MODELPATH` (`ui/packages/main/src/worker/build-env.ts:99`), nothing when none is verified, so Discord voice messages and live listening are transcribed locally ([[pages/decisions/0024-voice-messages-transcribed-locally]]). A model downloaded while the worker runs is used from the next worker start.

- **Token file**: `<userData>/youtube-token.json` as `{"access_token": ..., "expires_at": <unix ms>}`, mode `0600`, written to a `.tmp` file then renamed (`ui/packages/main/src/oauth/google-auth.ts:659`); a failed write keeps the session and is retried on the next refresh tick (`ui/packages/main/test/oauth-google.test.ts:631`). - **Refresh** (`ui/packages/main/src/oauth/google-auth.ts:488`): every minute and when the system wakes from sleep, through one serial queue, once less than 5 minutes remain, with the client secret; Google's answer usually has no new refresh token, so the first one is kept. `invalid_grant` ends the session: the token file goes first, the vault entry second (`:639`), and the card says "Google no longer accepts the saved sign-in. Sign in with Google again." A 5xx or a network failure keeps the session for the next check.
- **Disconnect** (`ui/packages/main/src/oauth/google-auth.ts:212`): a best-effort `POST oauth2.googleapis.com/revoke` of the refresh token, then the token file, then the vault entry; if the file cannot be removed the owner stays connected and sees "Could not remove the YouTube token file, so Scout is still connected. Try Disconnect again." On a pasted key, Disconnect calls `clearApiKey`, which removes only the key. Connect and disconnect call `restartWorkerIfRunning` (`ui/packages/main/src/ipc/github.ts:15`). Once the sign-out has removed the session, or the key that was the only credential is gone, main also calls the control plane's `DeleteCredentials('youtube')` so it deletes the YouTube data it keeps (`ui/packages/main/src/ipc/youtube.ts:32`, `:104`, `:115`); a sign-out that could not remove the token file deletes nothing, and a control plane that does not answer is logged with the error code only and never fails the Disconnect.
- **Allow writes** (`ui/packages/main/src/oauth/google-auth.ts:164`): Scout signs in for reads only and asks for more only when the owner allows YouTube's writes, because Google offers installed apps no incremental authorization. After the write confirmation, `scout:features.writeGrant` with `granted: true` runs main's check for the feature before `SetWriteGrant` (`ui/packages/main/src/ipc/features.ts:157`, wired by `youTubeWriteGrantHooks`, `ui/packages/main/src/ipc/youtube.ts:43`, `ui/packages/main/src/main.ts:633`), and so does `scout:features.enable` with `confirmWrites: true` (`ui/packages/main/src/ipc/features.ts:127`). When the stored session lacks `youtube.upload` or `youtube.force-ssl`, as with a read-only sign-in, a key or no connection, main runs the same PKCE loopback sign-in with `youtube.readonly`, `yt-analytics.readonly`, `youtube.upload` and `youtube.force-ssl` (`:30`) and waits for it, the card's Allow writes button busy meanwhile; the grant reaches the control plane only once the new session holds both write scopes. A cancelled or refused sign-in grants nothing; when the owner unticks a permission on Google's page, nothing is granted; if Google granted one write scope without the other, that token is revoked at Google and the session cleared, and a sign-in with the read scopes only opens, so the worker's token file never carries a write scope while writes are off (`ui/packages/main/src/oauth/google-auth.ts:177`); a grant with neither write scope keeps the read-only sign-in as it is; the card says "Google did not grant youtube.force-ssl, so writes stay off. Click Allow writes again and allow every permission on Google's page." naming each scope missing.
- **Revoke writes** (`ui/packages/main/src/oauth/google-auth.ts:185`): `SetWriteGrant(false)` first, then, when the session holds a write scope, the token is revoked at Google, the token file and the session are removed, the worker restarts, and a new sign-in with the read scopes only opens in the browser (`ui/packages/main/src/ipc/features.ts:162`); if the owner cancels it, denies it on Google's page, lets it time out, or the browser cannot be opened, YouTube stays signed out with Sign in with Google, and because that is a revocation made in the app, main then calls `DeleteCredentials('youtube')` the same best-effort way Disconnect does (`ui/packages/main/src/ipc/youtube.ts:43`, `:47`); a read-only sign-in that succeeds keeps the data. A failure of that step is logged with its code and the revoked grant is still returned.
- **Use an API key** (`ui/packages/main/src/oauth/google-auth.ts:230`): a password field, Save and the link "Create a key in Google Cloud Console" (`https://console.cloud.google.com/apis/credentials`, allowed in `ui/packages/main/src/ipc/app.ts:12`). Main checks the key with one public `GET youtube/v3/channels?part=id&forHandle=youtube&key=...` (`:463`): 200 stores it under `youtube.api-key`; a 400 or 403 stores nothing and says why, from the reasons in Google's error body (`ui/packages/main/src/oauth/google-auth.ts:724`): `API_KEY_INVALID` "Google does not recognise this API key. Copy it again from Google Cloud Console credentials."; `SERVICE_DISABLED` or `accessNotConfigured` "The YouTube Data API v3 is not enabled for this key's project. Enable it in Google Cloud Console and try again in a minute." followed by the project (`projects/<n>`) when Google names it; `API_KEY_SERVICE_BLOCKED` or `forbidden` "This key's restrictions do not allow the YouTube Data API v3. Edit the key's API restrictions in Google Cloud Console."; `quotaExceeded` "YouTube's daily quota for this key is spent; it resets at midnight Pacific time."; any other reason the generic "Google rejected this API key. Check that the YouTube Data API v3 is enabled for it." with the reason identifier in parentheses. Google's own message text is never shown. No message, log line or status carries the key.
- **Pending:** "Waiting for the browser..." and Cancel, which aborts the listener and releases the port without an error; a connected card whose status is pending shows the same line and Cancel above the connected buttons (`ui/packages/renderer/src/app/features/youtube-connect.component.ts:44`). Revoke writes reaches it, because the grant change pushes `scout:features.changed` after the read-only sign-in has started; Allow writes does not: nothing is pushed while its sign-in waits, so the card offers no Cancel then, and the wait ends when the owner finishes or denies on Google's page, or after the 5-minute sign-in timeout.
- **Connected:** "Connected to <channel title>" and "Signed in with Google", with "Google access: <scopes>" listing the granted scopes by their short names, such as `youtube.readonly` (`ui/packages/renderer/src/app/features/youtube-connect.component.ts:30`, `:308`); the card reads its status again on `scout:features.changed` (`:272`), so the scopes change when writes are allowed or revoked; or "Connected with an API key" and "Public data only.", then "Open YouTube Studio" (`https://studio.youtube.com/channel/<channel id>`, or `https://studio.youtube.com/` without a channel id), "Open channel" (`https://www.youtube.com/channel/<channel id>`, only with a channel id; the status carries `channelId` from the session) and Disconnect; both links go through `scout:app.openExternal`, whose allow-list has `studio.youtube.com` and `www.youtube.com` (`ui/packages/main/src/ipc/app.ts:13`).
- **Open YouTube operator:** in every state, enabled only while the card is connected (`ui/packages/renderer/src/app/features/youtube-connect.component.ts:171`); it calls `scout:operator.window` (see Operator window) and shows a refusal under the card (`:326`).
- **Failed:** the reason above Sign in with Google, for example "Google could not finish the sign-in (HTTP 503). Sign in again in a moment." or "The Google sign-in was cancelled or timed out. Click Sign in with Google to try again."

Like the GitHub card, it sits in the Features grid and is hidden with the grid when the control plane is not running.

## Discord setup

The wizard needs only the bot token ([[pages/decisions/0022-discord-setup-from-the-bot-token]]). Its three steps are the routes `provision` (open the Developer Portal), `token` and `oauth` (add the bot to a server). All Discord HTTP lives in `ui/packages/main/src/discord/discord-setup.ts`, which takes `fetch` as a parameter so tests can fake it:

- `checkBotToken` reads `GET /applications/@me` (`:62`).
- `enableMessageContent` adds `GATEWAY_MESSAGE_CONTENT_LIMITED` to the existing flags with one PATCH when the application is in under 100 servers. It returns the portal bot page otherwise (`:77`).
- `inviteUrl` builds a `scope=bot` invite with the permissions integer `309237730304` from six named constants, including Create Public Threads for the reply thread per conversation (`:27`, `:52`).
- `listGuilds` reads `GET /users/@me/guilds` (`:109`).

The handlers in `ui/packages/main/src/ipc/discord.ts` work as follows:

- The token arrives once through `scout:discord.checkToken` (`:61`).
- That handler stores the token as `discord.bot-token` and the application id as `discord.client-id` (`:75`). When the application differs from the stored one, it first deletes `discord.guild-id` and `discord.guild-name`. A token that replaces a different stored token restarts a running worker.
- The other handlers read the token from the vault, so the renderer never sends it again and never receives it.

The `token` step continues only once Message Content is on. The `oauth` step polls the bot's servers every 3 s, at most 100 times, until a new one appears. It then stores `discord.guild-id` and `discord.guild-name` (`ui/packages/renderer/src/app/wizard/oauth-install/oauth-install.component.ts:280`, stored at `:239`). The invite opens only after the first server list has loaded, so a server the bot was already in is never taken for the new one.

- [[pages/invariants/local-first-default]] - the only network call for transcription is the model download from `huggingface.co/ggerganov/whisper.cpp`, and a download is kept only at the pinned size and SHA-256; its only writes are the model, its `.partial` and its `.sha256` sidecar under `userData/whisper-models` (`ui/packages/main/test/ipc-whisper.test.ts`, `ui/packages/main/test/worker-whisper-model.test.ts`).
- [[pages/invariants/no-executive-writes]] - the update check is one unauthenticated GET of public release metadata that carries only the version in the User-Agent and no credential, and its only writes are Scout's own `update.*` vault keys. The one write to Scout's own installation is Update and restart: on the user's click only, through `scout:update.install`, which the worker and the model cannot reach, with the updater's automatic download and install off and no token set ([[pages/decisions/0031-desktop-self-update]], `ui/packages/main/test/update-notice.test.ts`).
- [[pages/decisions/0032-per-feature-write-permissions]] - the desktop is the only approval surface: a write grant and an action decision reach the control plane only through the Features and Review screens over the token-authenticated socket, and the channels that carry them change Scout's own feature state and approval queue, nothing outside Scout (`ui/packages/main/test/ipc-features.test.ts`, `ui/packages/renderer/src/app/review/review.component.spec.ts`). The worker holds only its own token, which the host lets reach the WorkerGate service and nothing else, so it can ask for a write but never grant or approve one (`ui/packages/main/test/control-plane-integration.test.ts:174`).
- [[pages/decisions/0033-channel-operator-architecture]] - the operator window and its `scout:operator.*` channels change only Scout's own operator state and media folder, see [[pages/services/desktop-operator]].
- [[pages/invariants/no-executive-writes]] - a meeting is written only to the worker's meetings database in Scout's own data folder, and only when the owner ticks Keep this meeting and clicks Done; an export is written only to the file the owner picks in the save dialog; a delete runs only on the owner's confirm. The renderer never sends or receives a path, and nothing of a meeting leaves the machine (`ui/packages/main/test/quick-ask.test.ts`, the meetings block; [[pages/decisions/0037-meetings-kept-locally-in-sqlite]]).
- [[pages/invariants/pluggable-boundaries]] - the UI reaches the console worker only through environment variables, stdout markers and quick-ask JSON lines on stdin, and the control plane only through gRPC; no .NET type crosses, and `@grpc/grpc-js` stays under `ui/packages/main/src/control-plane/` (ADR 0011: the renderer never sees it).
