## Responsibility

Owns the provider and feature domain services, the write gate and the channel operator's state, with no transport. [[pages/services/host-control-plane]] exposes them over gRPC. It does not run in the chat host ([[pages/services/host-console]]); the chat host reaches it only through the WorkerGate service, as a gRPC client, and shares no code path with it.

The daemon is launched with both control-plane tokens, the desktop's `SCOUT_CONTROLPLANE_TOKEN` and the worker's `SCOUT_CONTROLPLANE_WORKER_TOKEN`, removed from the child environment (`src/Scout.ControlPlane/Providers/OllamaProviderService.cs:200`, `:201`); the code carries no comment about the worker token, and `tests/Scout.ControlPlane.Tests/Security/CallerTokensTests.cs:58` keeps its literal in step with the host's. The credential store falls back to `InMemoryCredentialStore` (`src/Scout.ControlPlane/ControlPlaneServiceCollectionExtensions.cs:69`) and the activator to `NullFeatureActivator` (`:70`), which makes `Enable` answer not-yet-implemented (`src/Scout.ControlPlane/Features/FeaturesService.cs:270`). No `IFeatureCredentialValidator` implementation exists outside `src/old`.

**Write grants.** A feature whose matrix has a `Write` or `IrreversibleWrite` row needs the owner's confirmation of those rows. `EnableAsync` checks it after the credentials and before the activator (`src/Scout.ControlPlane/Features/FeaturesService.cs:263`), so even with the confirmation the default activator still ends in not-yet-implemented; a successful enable records `Granted` and `GrantedAt` (`:283`), and a failed activation clears them (`:294`). A connection card with no toggle, such as YouTube, grants through `SetWriteGrantAsync` (`src/Scout.ControlPlane/Features/FeaturesService.cs:308`): granting needs the confirmation, revoking does not, a feature without write rows is a validation error, and `Enabled` is left alone. `DisableAsync` and `DeleteCredentialsAsync` reset the state and so revoke the grant (`src/Scout.ControlPlane/Features/FeaturesService.cs:346`, `:240`). `FeatureState` keeps `Granted` and `GrantedAt` (`src/Scout.ControlPlane/Features/IFeatureStateStore.cs:11`); the JSON store writes them only while granted, so a state file without them reads as not granted (`src/Scout.ControlPlane/Features/JsonFileFeatureStateStore.cs:172`). The worker learns the grants at start from `SCOUT__FEATURES__GRANTEDWRITES`, set by the desktop ([[pages/services/llm]]).

**Approval queue and write log.** `JsonFileActionQueue` keeps every action in `actions.json` beside `features.json`; enqueue, list, find and each decision run their read, check and write under one gate (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:308`), so two approvals of one action let one through and the other fails as already decided. The worker never writes the file: it enqueues through the WorkerGate service, so every writer is the control-plane process. A decision records the status, `DecidedAt` and the owner's reason when one was given, on an approval as on a rejection. `ExecuteAsync` moves an `Approved` action to `Executed` under the same gate and fails with `PendingActionNotApprovedException` for any other status, an executed one included (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:265`); before the move it runs the caller's record, and a record that throws leaves the action approved (`:268`). `MarkExecutedAsync` is `ExecuteAsync` with nothing to record (`:241`). An executed action is no longer pending. Every write of the file drops rejected actions whose `DecidedAt` is more than 30 days old and executed ones approved more than 90 days ago, and keeps pending and approved actions whatever their age (`:371`, `tests/Scout.ControlPlane.Tests/Actions/ActionQueueTests.cs:175`); an executed action is aged from its approval, the only time the queue keeps for it. A queue file that does not parse is moved aside to `actions.json.corrupt-<UTC yyyyMMddHHmmss>` and logged once as a warning naming both paths, and the queue starts empty (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:354`); the move never overwrites, so a second corruption within the same second fails the call instead of losing the first file. Only malformed content is moved aside (`:352`): a file that cannot be opened or read (an `IOException` or `UnauthorizedAccessException`) fails the call and stays where it is, so a transient lock never empties the queue (`tests/Scout.ControlPlane.Tests/Actions/ActionQueueTests.cs:158`). `JsonLinesWriteLog` appends one line per write to `writes.log` and lists the last N newest first, skipping and logging a line that does not parse with its number counted from the end of the file. The list reads only the tail: it seeks back from the end in 4096-byte blocks (`src/Scout.ControlPlane/Actions/JsonLinesWriteLog.cs:20`, `:131`), carries a line cut by a block boundary into the next block (`:193`), and stops once it has N non-blank lines; blank lines are skipped and not counted, a malformed line counts toward N, and the first line of the file and a last line without a newline are read (`tests/Scout.ControlPlane.Tests/Actions/WriteLogTests.cs:87`, `:107`).

**Write gate.** `WriteGateService` is what the worker reaches through the WorkerGate service ([[pages/services/host-control-plane]]); it never grants a permission and never decides an action. `RequestAsync` looks the scope up among the catalog rows of the feature by exact, case-sensitive scope text (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:233`) and answers, in order: an unknown feature or a scope the feature does not declare is `Refused` with "<scope> is not declared by <feature>"; a `Read` row is `Refused` with "<scope> is a read"; a feature whose state is not `Granted` is `Refused` with "The owner has not allowed <feature> to write; allow it on the Features screen of Scout Desktop."; a `Write` row is `Allowed` with an empty reason; an `IrreversibleWrite` row enqueues a pending action (feature, the scope as the action, target, summary) and is `Queued` with its id and "Waiting for the owner's approval on the Review screen of Scout Desktop." (`:109`). The grant is read from the state store on every request (`:99`), so a grant or a revocation on the Features screen applies to the next request without a restart. `RecordAsync` appends a `WriteLogEntry` with the time, feature, scope, target and outcome; it refuses an undeclared scope or a read row, refuses an `IrreversibleWrite` row recorded without an action id with "<scope> is irreversible; it is recorded only with an action the owner approved.", even under the grant (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:148`), and reads the grant live like a request (`:154`): a reversible `Write` row without it is refused with the same "has not allowed" text, and an irreversible one with "The owner revoked <feature>'s write permission before this action ran.", even when the owner approved the action before revoking; an approved action no worker claimed is refused and logs nothing (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:291`), while an action a worker claimed (`executing`) already ran on YouTube, so it is logged once with its outcome followed by " after revoke", approved by `owner`, marked executed under the queue's gate, and then refused, so it is never handed out again (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:179`, `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:268`). With an action id it requires an action the owner approved for the same feature and scope (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:171`), then, inside the queue's `ExecuteAsync` (`:207`), looks the action id up in the write log, reading it back with `ListSinceAsync` only to the first entry older than the action's request (`:211`, `src/Scout.ControlPlane/Actions/JsonLinesWriteLog.cs:72`, `tests/Scout.ControlPlane.Tests/Actions/WriteLogTests.cs:53`), appends the entry with `ApprovedBy` `owner` when it is not there (`:212`), and only then marks the action executed. A failed append leaves the action approved, so the worker's retry records it once (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:309`); a failed mark after the append is reported to the caller with the log line kept and the action still approved, and the next record finds the line, marks the action executed and is refused with "Action '<id>' is already recorded in the write log." (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:198`, `tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:330`). A second record with the same action id, sequential or concurrent, fails as not approved, so an approval covers one write. So every logged irreversible write carries the owner as its approver; the WorkerGate service answers each refusal with `FailedPrecondition` and the log is left untouched.

**Operator state.** The control plane is the only writer of the channel operator's state ([[pages/decisions/0033-channel-operator-architecture]]); the desktop reaches it through the `Operator` gRPC service and the worker through seven operator methods of `WorkerGate` ([[pages/services/host-control-plane]]). `JsonFileOperatorStore` keeps the mandate in `mandate.json` and every project, in creation order, in `projects.json`, both beside `features.json`. `UpdateProjectsAsync` reads the list, runs the caller's check-and-change and writes the list back under one gate (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:30`, `:140`); when the change throws or answers null, nothing is written (`:149`). A file that does not parse is moved aside to `<name>.corrupt-<UTC yyyyMMddHHmmss>`, never overwritten, logged once as "Operator file at <path> is malformed; moved it to <aside> and started empty", and read as empty (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:228`, `:232`); a file that cannot be opened fails the call and stays where it is. A `projects.json` written before scenes existed reads with no scenes.

The desktop side: `GetMandateAsync` answers the empty mandate when none is saved. `SaveMandateAsync` trims every field, drops blank pillars and blocked topics, stamps `UpdatedAt`, and refuses an empty objective or language, more than 5 pillars or a pillar over 80 characters, joining the messages ("The objective is required.", "At most 5 pillars.", "Each pillar is at most 80 characters.", "The language is required."). The mandate carries no narration voice: the owner moved that choice from the channel to the video on 2026-11-03, so it is the project's (Production and scenes, below); a mandate file saved before then still loads, its voice ignored, and the next save drops it (`tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.cs:122`). `ListProjectsAsync` returns the newest first; a limit of 0 or less means 50 and at most 200 are returned. `StartProjectAsync` trims the topic, refuses one outside 3 to 200 characters ("The topic must be 3 to 200 characters."), then asks the write gate for the `youtube` grant like a worker save and, without it, refuses with the gate's text as `OperatorWriteRefusedException` (`src/Scout.ControlPlane/Operator/OperatorService.cs:169`), which the desktop receives as `PERMISSION_DENIED`; with it, it queues a project with status `queued` and origin `desktop`. `DecideClaimAsync` takes `supported`, `unsupported` or `waived`, anything else being "A claim is decided as supported, unsupported or waived.", needs a note for `waived` ("A waived claim needs a note saying why."), and stamps the claim's `DecidedAt`, which marks it as the owner's decision. An unknown project or claim is `OperatorNotFoundException`. No desktop method returns a project's `OriginReference` (`src/Scout.ControlPlane/Operator/OperatorService.cs:1607`).

The worker side: `SaveProjectFromWorkerAsync`, `GetProjectForWorkerAsync`, `ListProjectsForWorkerAsync` and `NextQueuedProjectAsync` first ask `WriteGateService.RequestAsync` for the `youtube` feature's `Write` row "Scout's data folder", so the grant is read live and a refusal carries the gate's own text, "The owner has not allowed youtube to write; allow it on the Features screen of Scout Desktop." (`src/Scout.ControlPlane/Operator/OperatorService.cs:1786`). The mandate read is not gated: it is a read of the owner's brief. The two reads return what the desktop sees, owner-decided claims with their status and note included, with the desktop's limit rules except that a worker list returns up to 5000 projects, so its data hygiene reaches older ones, and without the origin reference on the wire, so the worker can send an owner's decision back unchanged. A save then refuses, as `OperatorValidationException`, a status other than `researching`, `scripting`, `script_ready`, `producing`, `media_ready`, `assembling`, `assembled` or `failed`, a claim without an id, duplicate claim ids and a claim status outside `pending`, `unsupported`, `supported` and `waived` (`:255`, `:1655`), a scene that breaks the scene rules below (`:256`), and a package that breaks the package rules below; and, as `OperatorTamperingException`, a claim the worker marks `supported` or `waived` unless the stored claim already has that status (`:1675`), a claim the owner decided that comes back changed in text, status, note, risk or source links (the links compared in order) or does not come back (`:1689`), a different topic or origin on an existing project (`:297`), and a scene change only the owner may make (`:303`). On a project the owner queued for production again (`production_queued`), every worker save is refused, a `failed` one included; on any other project the store no longer holds as `producing`, because the owner regenerated a scene or produced it again between the worker's read and its save, a save that sends `producing` or `media_ready`, or whose merged scenes differ from the stored ones, is refused as `OperatorTamperingException`, `FAILED_PRECONDITION` on the wire, with "The project is no longer producing."
