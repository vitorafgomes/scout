## Responsibility

Owns the provider and feature domain services, the write gate and the channel operator's state, with no transport. [[pages/services/host-control-plane]] exposes them over gRPC. It does not run in the chat host ([[pages/services/host-console]]); the chat host reaches it only through the WorkerGate service, as a gRPC client, and shares no code path with it.

The daemon is launched with both control-plane tokens, the desktop's `SCOUT_CONTROLPLANE_TOKEN` and the worker's `SCOUT_CONTROLPLANE_WORKER_TOKEN`, removed from the child environment (`src/Scout.ControlPlane/Providers/OllamaProviderService.cs:200`, `:201`); the code carries no comment about the worker token, and `tests/Scout.ControlPlane.Tests/Security/CallerTokensTests.cs:58` keeps its literal in step with the host's. The credential store falls back to `InMemoryCredentialStore` (`src/Scout.ControlPlane/ControlPlaneServiceCollectionExtensions.cs:69`) and the activator to `NullFeatureActivator` (`:70`), which makes `Enable` answer not-yet-implemented (`src/Scout.ControlPlane/Features/FeaturesService.cs:270`). No `IFeatureCredentialValidator` implementation exists outside `src/old`.

**Write grants.** A feature whose matrix has a `Write` or `IrreversibleWrite` row needs the owner's confirmation of those rows. `EnableAsync` checks it after the credentials and before the activator (`src/Scout.ControlPlane/Features/FeaturesService.cs:263`), so even with the confirmation the default activator still ends in not-yet-implemented; a successful enable records `Granted` and `GrantedAt` (`:283`), and a failed activation clears them (`:294`). A connection card with no toggle, such as YouTube, grants through `SetWriteGrantAsync` (`src/Scout.ControlPlane/Features/FeaturesService.cs:307`): granting needs the confirmation, revoking does not, a feature without write rows is a validation error, and `Enabled` is left alone. `DisableAsync` and `DeleteCredentialsAsync` reset the state and so revoke the grant (`src/Scout.ControlPlane/Features/FeaturesService.cs:345`, `:240`). `FeatureState` keeps `Granted` and `GrantedAt` (`src/Scout.ControlPlane/Features/IFeatureStateStore.cs:11`); the JSON store writes them only while granted, so a state file without them reads as not granted (`src/Scout.ControlPlane/Features/JsonFileFeatureStateStore.cs:172`). The worker learns the grants at start from `SCOUT__FEATURES__GRANTEDWRITES`, set by the desktop ([[pages/services/llm]]).

**Approval queue and write log.** `JsonFileActionQueue` keeps every action in `actions.json` beside `features.json`; enqueue, list, find and each decision run their read, check and write under one gate (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:167`), so two approvals of one action let one through and the other fails as already decided. The worker never writes the file: it enqueues through the WorkerGate service, so every writer is the control-plane process. A decision records the status, `DecidedAt` and the owner's reason when one was given, on an approval as on a rejection. `MarkExecutedAsync` moves an `Approved` action to `Executed` under the same gate and fails with `PendingActionNotApprovedException` for any other status, an executed one included (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:109`); an executed action is no longer pending. A queue file that does not parse is moved aside to `actions.json.corrupt-<UTC yyyyMMddHHmmss>` and logged once as a warning naming both paths, and the queue starts empty (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:213`); the move never overwrites, so a second corruption within the same second fails the call instead of losing the first file. Only malformed content is moved aside (`:211`): a file that cannot be opened or read (an `IOException` or `UnauthorizedAccessException`) fails the call and stays where it is, so a transient lock never empties the queue (`tests/Scout.ControlPlane.Tests/Actions/ActionQueueTests.cs:156`). `JsonLinesWriteLog` appends one line per write to `writes.log` and lists the last N newest first, skipping and logging a line that does not parse.

**Write gate.** `WriteGateService` is what the worker reaches through the WorkerGate service ([[pages/services/host-control-plane]]); it never grants a permission and never decides an action. `RequestAsync` looks the scope up among the catalog rows of the feature by exact, case-sensitive scope text (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:177`) and answers, in order: an unknown feature or a scope the feature does not declare is `Refused` with "<scope> is not declared by <feature>"; a `Read` row is `Refused` with "<scope> is a read"; a feature whose state is not `Granted` is `Refused` with "The owner has not allowed <feature> to write; allow it on the Features screen of Scout Desktop."; a `Write` row is `Allowed` with an empty reason; an `IrreversibleWrite` row enqueues a pending action (feature, the scope as the action, target, summary) and is `Queued` with its id and "Waiting for the owner's approval on the Review screen of Scout Desktop." (`:96`). The grant is read from the state store on every request (`:86`), so a grant or a revocation on the Features screen applies to the next request without a restart. `RecordAsync` appends a `WriteLogEntry` with the time, feature, scope, target and outcome; it refuses an undeclared scope or a read row, refuses a reversible `Write` row while the feature is not granted, with the same "has not allowed" text, read live like a request (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:129`), refuses an `IrreversibleWrite` row recorded without an action id with "<scope> is irreversible; it is recorded only with an action the owner approved.", even under the grant (`src/Scout.ControlPlane/WriteGate/WriteGateService.cs:135`), and with an action id it requires an action the owner approved for the same feature and scope (`:146`), then marks it executed before appending (`:161`), recording `ApprovedBy` `owner`; a second record with the same action id, sequential or concurrent, fails as not approved, so an approval covers one write. So every logged irreversible write carries the owner as its approver; the WorkerGate service answers each refusal with `FailedPrecondition` and the log is left untouched.

**Operator state.** The control plane is the only writer of the channel operator's state ([[pages/decisions/0033-channel-operator-architecture]]); the desktop reaches it through the `Operator` gRPC service and the worker through seven operator methods of `WorkerGate` ([[pages/services/host-control-plane]]). `JsonFileOperatorStore` keeps the mandate in `mandate.json` and every project, in creation order, in `projects.json`, both beside `features.json`. `UpdateProjectsAsync` reads the list, runs the caller's check-and-change and writes the list back under one gate (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:26`, `:132`); when the change throws or answers null, nothing is written (`:141`). A file that does not parse is moved aside to `<name>.corrupt-<UTC yyyyMMddHHmmss>`, never overwritten, logged once as "Operator file at <path> is malformed; moved it to <aside> and started empty", and read as empty (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:170`, `:174`); a file that cannot be opened fails the call and stays where it is. A `projects.json` written before scenes existed reads with no scenes.

The desktop side: `GetMandateAsync` answers the empty mandate when none is saved. `SaveMandateAsync` trims every field, drops blank pillars and blocked topics, stamps `UpdatedAt`, and refuses an empty objective or language, more than 5 pillars or a pillar over 80 characters, joining the messages ("The objective is required.", "At most 5 pillars.", "Each pillar is at most 80 characters.", "The language is required."). `ListProjectsAsync` returns the newest first; a limit of 0 or less means 50 and at most 200 are returned. `StartProjectAsync` trims the topic, refuses one outside 3 to 200 characters ("The topic must be 3 to 200 characters."), then asks the write gate for the `youtube` grant like a worker save and, without it, refuses with the gate's text as `OperatorWriteRefusedException` (`src/Scout.ControlPlane/Operator/OperatorService.cs:143`), which the desktop receives as `PERMISSION_DENIED`; with it, it queues a project with status `queued` and origin `desktop`. `DecideClaimAsync` takes `supported`, `unsupported` or `waived`, anything else being "A claim is decided as supported, unsupported or waived.", needs a note for `waived` ("A waived claim needs a note saying why."), and stamps the claim's `DecidedAt`, which marks it as the owner's decision. An unknown project or claim is `OperatorNotFoundException`. No desktop method returns a project's `OriginReference` (`src/Scout.ControlPlane/Operator/OperatorService.cs:768`).

The worker side: `SaveProjectFromWorkerAsync`, `GetProjectForWorkerAsync`, `ListProjectsForWorkerAsync` and `NextQueuedProjectAsync` first ask `WriteGateService.RequestAsync` for the `youtube` feature's `Write` row "Scout's data folder", so the grant is read live and a refusal carries the gate's own text, "The owner has not allowed youtube to write; allow it on the Features screen of Scout Desktop." (`src/Scout.ControlPlane/Operator/OperatorService.cs:946`). The mandate read is not gated: it is a read of the owner's brief. The two reads return what the desktop sees, owner-decided claims with their status and note included, with the desktop's limit rules and without the origin reference on the wire, so the worker can send an owner's decision back unchanged. A save then refuses, as `OperatorValidationException`, a status other than `researching`, `scripting`, `script_ready`, `producing`, `media_ready`, `assembling`, `assembled` or `failed`, a claim without an id, duplicate claim ids and a claim status outside `pending`, `unsupported`, `supported` and `waived` (`:214`, `:796`), a scene that breaks the scene rules below (`:221`), and a package that breaks the package rules below; and, as `OperatorTamperingException`, a claim the worker marks `supported` or `waived` unless the stored claim already has that status (`:816`), a claim the owner decided that comes back changed in text, status, note, risk or source links (the links compared in order) or does not come back (`:830`), a different topic or origin on an existing project (`:257`), and a scene change only the owner may make (`:262`). On a project the owner queued for production again (`production_queued`), every worker save is refused, a `failed` one included; on any other project the store no longer holds as `producing`, because the owner regenerated a scene or produced it again between the worker's read and its save, a save that sends `producing` or `media_ready`, or whose merged scenes differ from the stored ones, is refused as `OperatorTamperingException`, `FAILED_PRECONDITION` on the wire, with "The project is no longer producing." (`:272`), and the owner's change stays; the worker stops on those words ([[pages/services/operator]]). Each save that succeeds appends one `WriteLogEntry` to `writes.log` as a reversible write under [[pages/decisions/0032-per-feature-write-permissions]]: feature `youtube`, action "Scout's data folder", the project id as target, outcome `saved <status>`, no approver (`:913`); a refused save appends nothing. An empty id creates a project of origin `chat` that stores the origin reference; an existing project keeps its topic, origin, creation time, owner decisions and reference. `NextQueuedProjectAsync` takes the oldest `queued` project and moves it to `researching`; when none is queued, the oldest `production_queued` project and moves it to `producing`; when neither waits, the oldest `assembly_queued` project and moves it, and its package, to `assembling` (`:726`, `:350`); when none of those waits, the oldest project left in `researching`, `scripting`, `producing` or `assembling` whose `UpdatedAt` is more than 15 minutes old, back in `researching` or, for `producing` and `assembling`, in the same status (`:54`, `:732`); the pipeline saves at every stage, so a live run is never that stale, and a run a worker shutdown cut short is taken again. It moves the project with a fresh `UpdatedAt` inside one `UpdateProjectsAsync`, so two callers never take the same project, appends `saved <status>` for it to the write log, and returns it with its reference. It first reads the list outside the store's write path and returns null when nothing waits, and the change answers null under the gate when another caller took it first, so an idle poll never rewrites `projects.json`.

**Production and scenes.** `ProduceProjectAsync` asks the write gate for the `youtube` grant like `StartProjectAsync`, then refuses, as `OperatorValidationException`, a project that is not `script_ready`, `media_ready`, or `failed` with a script, so a run that failed, planning included, is produced again (`src/Scout.ControlPlane/Operator/OperatorService.cs:379`) ("Only a project with its script ready, its media ready, or a failed one with a script goes to production; this one is <status>.") and one with claims still `pending` ("1 claim is still pending; decide it before production.", "<n> claims are still pending; decide them before production."), and otherwise sets `production_queued` and clears the project's error (`src/Scout.ControlPlane/Operator/OperatorService.cs:393`). The owner's scene edits change Scout's own state, not anything the model wrote, so they need no grant; each answers the project without its origin reference and `NOT_FOUND` for an unknown project or scene ("Unknown scene '<id>' in project '<id>'."). `ReorderScenesAsync` takes the scene ids in the owner's order, refuses anything but every scene exactly once ("The new order must name every scene of the project exactly once."), and numbers them from 1. `SetSceneLockedAsync` sets `Locked`. `RegenerateSceneAsync` refuses a locked scene ("Scene '<id>' is locked; unlock it before regenerating it."), otherwise sets the scene to `planned` without its error, clears the audio file, the visual file and the duration where the source is not `owner` (the source names stay), keeps the owner's media, and sets the project to `production_queued`. `AttachSceneMediaAsync` takes `audio` or `visual` ("Media is attached as audio or visual."), checks the file name, requires the file to be in the project's media directory already ("'<name>' is not in the project's media folder; copy it there first."), sets that source to `owner` with the name, sets the duration to 0 for the owner's audio, unknown until it is measured, and sets the scene `ready` without its error once it has a visual and its audio is decided (`src/Scout.ControlPlane/Operator/OperatorService.cs:512`). A visual is a visual file, or a `text_card` production chose; decided audio is an audio file, or `AudioSource` `none` production chose. Production chose them only on a scene it saved `ready`; on a `planned` or `failed` scene the planner's `none` and `text_card` are placeholders, so an image attached there leaves the scene as it was and the next run still makes its narration.

A media file name is a plain name: not empty, at most 120 characters, no leading dot, no `..`, no backslash, no character the platform forbids in a file name (the folder separator among them), and an audio extension `.mp3`, `.wav`, `.m4a`, `.ogg` or a visual one `.png`, `.jpg`, `.jpeg`, `.webp`, compared without case (`src/Scout.ControlPlane/Operator/SceneRules.cs:31`); it is checked wherever a name is accepted, from the desktop's attach and from a worker save. The media directory is `<folder of features.json>/operator/<project id>`; the id must be 32 hex digits, the store's own id format, so no path can escape (`src/Scout.ControlPlane/Operator/OperatorService.cs:876`), the project must exist, and the folder is created with the default permissions of its parent; when it cannot be created (a file in the way, no permission) the `IOException` propagates, which `OperatorMapping.Guard` does not map, so the desktop receives gRPC `UNKNOWN`. The desktop's `GetMediaDirectoryAsync` and the worker's `GetMediaDirectoryForWorkerAsync`, which needs the grant, return its absolute path.

A worker save checks the scenes it sends: ids present and unique, `Status` one of `planned`, `generating`, `ready`, `failed`, `AudioSource` one of `generated`, `owner`, `none`, `VisualSource` one of `generated`, `owner`, `text_card`, a duration not below 0, and every file name (`src/Scout.ControlPlane/Operator/SceneRules.cs:56`). When the project has no scenes the worker adds its own, none locked and none with an `owner` source. Once scenes exist it can neither add nor drop one, and a worker that claims an `owner` source the stored scene does not have is refused; each of those is `OperatorTamperingException`. Otherwise the save is merged with the stored scenes, in their stored order (`src/Scout.ControlPlane/Operator/SceneRules.cs:95`): the worker sets a scene's status, error, generated sources and files, duration, narration and visual prompt, and what the owner owns comes from storage whatever the worker sends, the `Order` and `Locked` of every scene, a locked scene whole (`:119`), and the owner's audio or visual with its file (`:127`, `:137`). The duration of an owner audio stays the worker's only when the worker sent that same owner file; else the stored one stays. So an owner reorder, lock or attach between the worker's read and its save never fails the run.

**Assembly and the package.** `AssembleProjectAsync` asks the write gate for the `youtube` grant like `ProduceProjectAsync`, then refuses, as `OperatorValidationException`, a project that is not `media_ready`, `assembled` or `failed` ("Only a project with its media ready, an assembled one, or a failed one with every scene ready is assembled; this one is <status>."), one without scenes ("The project has no scenes to assemble.") and one with a scene not `ready` ("1 scene is not ready; regenerate it or attach its media before assembly.", "<n> scenes are not ready; regenerate them or attach their media before assembly."); otherwise it sets `assembly_queued`, clears the project's error and starts the package again (`src/Scout.ControlPlane/Operator/OperatorService.cs:586`): status `assembly_queued`, no video, Shorts, thumbnail, checks, duration or error, rights not confirmed, not approved, and the title, description and tags kept, with `MetadataEdited`, only when the owner edited them, else empty for the worker to fill (`src/Scout.ControlPlane/Operator/PackageRules.cs:34`). The package's own status is `assembly_queued`, `assembling`, `assembled`, `approved` or `failed`; the owner sets `assembly_queued` and `approved`, the worker the other three.

A worker save that carries a package is checked first (`src/Scout.ControlPlane/Operator/PackageRules.cs:44`): a status in that set, no duration, Shorts duration or Shorts start below 0, a title, description and tags within YouTube's limits once any of them is written (empty, the package is still unwritten), every check named with a result `pass`, `warn` or `fail`, and safe file names, the video and each Shorts cut `.mp4`, the thumbnail `.png` or `.jpg`, under the scene file name rule (`src/Scout.ControlPlane/Operator/SceneRules.cs:31`). A worker cannot start a project already `assembling` or `assembled` or with a package (`src/Scout.ControlPlane/Operator/OperatorService.cs:229`). The merge (`src/Scout.ControlPlane/Operator/PackageRules.cs:91`) keeps the stored package when the worker sends none, so a save from a stage that does not know the package leaves it as it is; otherwise the worker's package stands, and it is `OperatorTamperingException` when the worker confirms the rights ("Only the owner confirms the media rights of project '<id>'."), sets or changes `ApprovedAt` ("Only the owner approves the package of project '<id>'."), sends `assembly_queued` or `approved` the store does not hold ("Only the owner sets the package of project '<id>' to <status>."), changes `MetadataEdited` ("Only the owner edits the package metadata of project '<id>'."), or changes the title, description or tags once the owner edited them ("The owner edited the package metadata of project '<id>'; the worker may not change it."). Until then the worker sets them. A save that sends `assembling` or `assembled`, or a package that differs from the stored one, its lists compared item by item (`:128`), is refused with "The project is no longer assembling." unless the store holds the project as `assembling` and the save leaves the scenes as stored, and every worker save on a project the store holds as `assembly_queued` or `approved` is refused with the same words (`src/Scout.ControlPlane/Operator/OperatorService.cs:266`), so a stale run never overwrites a new assembly or the owner's approval. This check comes before the production one, so an assembler whose project the owner sent back to production, by regenerating a scene, reads "no longer assembling", the words it stops on ([[pages/services/operator]]). A save that reports `assembled` needs the package's video file, and every file it names, the video, the thumbnail and each Shorts cut, must be in the project's media directory ("An assembled package needs its video file.", "'<name>' is not in the project's media folder.", `:278`, `src/Scout.ControlPlane/Operator/PackageRules.cs:143`).

The owner's package edits need a package ("Project '<id>' has no package yet; assemble it first.", `src/Scout.ControlPlane/Operator/OperatorService.cs:914`) and answer the project without its origin reference. `EditPackageMetadataAsync` trims the title, description and each tag and refuses, joining the messages, a title outside 1 to 100 characters, a description over 5000, a tag outside 1 to 100 and tags over 500 characters together, YouTube's limits, the tags counted YouTube's way, two more for a tag with a space and a comma between tags, as the worker counts them ("The title is 1 to 100 characters.", "The description is at most 5000 characters.", "Each tag is 1 to 100 characters.", "The tags are at most 500 characters together.", `src/Scout.ControlPlane/Operator/PackageRules.cs:160`, `:218`); it is allowed on an `assembled` or `approved` project ("Only the metadata of an assembled or approved package is edited; this one is <status>."), sets `MetadataEdited`, and sends an approved package back to `assembled` without its `ApprovedAt`; the rights confirmation stays. It runs the `metadata` and `discoverability` checks again over the owner's values, the project's topic and the mandate's pillars, with the worker's rules and sentences, and drops the worker's two: `metadata` fails outside YouTube's limits, `discoverability` warns when the title shares no word of three letters or more with the topic or the pillars, or the description has no `0:00` chapter line (`src/Scout.ControlPlane/Operator/OperatorService.cs:628`, `src/Scout.ControlPlane/Operator/PackageRules.cs:188`); the other checks stay, so the approval reads checks that match the metadata it approves. `ConfirmMediaRightsAsync` sets `RightsConfirmed` on an `assembled` project only ("Media rights are confirmed on an assembled package; this one is <status>."); a new assembly clears it. Neither needs the grant, like the scene edits. `ApprovePackageAsync` asks the write gate for the grant, refuses a project that is not `assembled` ("Only an assembled package is approved; this one is <status>."), then refuses, joining every cause, a package whose rights are not confirmed ("Confirm the media rights first."), one with a failed check ("1 check failed.", "<n> checks failed.") a project with a claim neither `supported` nor `waived` ("1 claim is not supported or waived.", "<n> claims are not supported or waived."), and metadata outside YouTube's limits, with the same sentences as the edit (`src/Scout.ControlPlane/Operator/OperatorService.cs:689`); otherwise it sets the project and the package `approved` with `ApprovedAt` and appends a write-log entry, outcome `approved package`, approved by `owner` (`src/Scout.ControlPlane/Operator/OperatorService.cs:660`, `:703`).

An owner scene edit that changes the video, an attach, a regenerate or a reorder into a new order, on an `assembled` or `approved` project takes the approval back (`src/Scout.ControlPlane/Operator/OperatorService.cs:770`, `src/Scout.ControlPlane/Operator/PackageRules.cs:174`): the package goes back to `assembled` without its rights confirmation or `ApprovedAt`, and the project to `media_ready`, or to `production_queued` for a regenerate as before. The package files stay on disk, but neither the rights nor the approval can be given again until the owner assembles the project again. The same edit on a project `assembly_queued` or `assembling` sends the project and the package back to `assembly_queued`, the project to `production_queued` for a regenerate, so a running assembly reads that it is no longer assembling and its save is refused with those words, and the next take assembles the edited scenes. A lock or unlock, and a reorder into the order the scenes already have, do not change the video: they leave the status, the rights and the approval as they are, anywhere (`src/Scout.ControlPlane/Operator/OperatorService.cs:427`, `:442`).

**Readiness.** `ReportReadinessAsync` stores the worker's latest report in `readiness.json`, its `ReportedAt` replaced by the control plane's time; it needs no grant, because it describes the worker and writes only that file. A report that cannot be written fails as `OperatorStoreException` (`src/Scout.ControlPlane/Operator/OperatorExceptions.cs:44`) "Scout could not save the worker's readiness report in its data folder." and the earlier report stays readable (`src/Scout.ControlPlane/Operator/OperatorService.cs:720`); the host answers it `FAILED_PRECONDITION` with that sentence ([[pages/services/host-control-plane]]), so the worker logs the real reason. `GetReadinessAsync` answers the report or, before the first one, every flag false, no provider and the note "The Scout worker has not reported yet.".
