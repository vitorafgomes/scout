# Scout performs descriptive writes only

> Scope change on 2026-11-02 ([[pages/decisions/0032-per-feature-write-permissions]]), applied 2026-11-03: a feature may declare writes in the catalog; it runs them only after the owner grants it in the desktop, each irreversible action only after the owner approves that action there, and every write is logged. An undeclared write stays forbidden. The `youtube` feature is the first write-capable one (the channel operator, [[pages/decisions/0033-channel-operator-architecture]]); its section below says how its writes are held. Every other feature is still read-only as described.

> Every write Scout makes is content a person or another agent reads and decides on (a chat reply, an issue body); no code path may mutate code, infrastructure, configuration or data on the host or in a connected system.

## The gap

Nothing in code stops a plugin from exposing a write function. The kernel takes every `KernelPlugin` registered in DI (`src/Scout.Llm/LlmServiceCollectionExtensions.cs:126`) and offers all of their functions to the model with `FunctionChoiceBehavior.Auto()` (`src/Scout.Llm/ChatGateway.cs:360`, `src/Scout.Knowledge/ProjectExpertAgentFactory.cs:84`). There is no allow-list, no read-only marker on a function, and no test that fails when a write function appears. Read-only holds today because the write methods do not exist. The optional request guard below judges what the user asks for, not what a function can do, so it does not close this gap.

Since 2026-11-02 a function declared with `AddWriteFunction` is gated at the call by the control plane (the write gate below); an undeclared function is still not gated, so the gap remains for any write function nobody declares.

## Why this exists

Scout answers questions in shared chat channels. A model that can call a mutating tool turns a prompt in a public channel into a change on a real system. The README states the rule as "never writes"; [[pages/decisions/0009-descriptive-vs-executive-writes]] refines it to descriptive versus executive writes.

## Scope

- **Applies to:** every `KernelPlugin` the host registers, the GitHub client, the Kubernetes clients, the chat adapters, and the control plane.
- **Does not cover:** Scout's own state (below), and replies posted to the chat platform, which are descriptive writes by definition. That includes the allowed-users refusal ("Scout only answers its configured users." or the setup text), which goes through the same sink to the originating channel only and is the one thing a refused message causes ([[pages/decisions/0021-allowed-users]], `src/Scout.Conversation/ConversationConductor.cs:137`). The allow-list decides who gets replies; it never authorizes a write. The pairing reply ("Paired. Scout will answer you from now on." or "That pairing code is not valid. Check the code in Scout's Settings and send it again.") is the same kind of reply, in the direct message it answers. The `SCOUT_PAIRED=<userId>` line it causes goes to the desktop's own supervisor on stdout, and the id lands in Scout's own vault, which is Scout's own state (`src/Scout.Conversation/ConversationConductor.cs:204`).

## Where it is held

- `src/Scout.Plugin.GitHub/Abstractions/IGitHubClient.cs:7` declares four read methods and no others; the interface comment says no create, merge, push or comment operation exists by design.
- `src/Scout.Plugin.GitHub/GitHubClient.cs:140` and `:157` are the only HTTP calls, both `GetAsync`.
- `src/Scout.Plugin.GitHub/GitHubPlugin.cs:29,51,76,101` expose `list_repositories`, `list_pull_requests`, `list_issues`, `get_repository`.
- `src/Scout.Skills/SkillsPlugin.cs:27,40` (`list_skills`, `load_skill`) and `src/Scout.Knowledge/ProjectKnowledgePlugin.cs:26,41,53` (`search_project`, `find_symbol`, `list_projects`) only read.
- `src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:44` registers nothing when neither a token nor a token file is set.
- **Request guard, when a TypeSafe key is set** ([[pages/decisions/0016-jev-read-only-guard]]). `src/Scout.Llm/LlmServiceCollectionExtensions.cs:183` replaces the kernel's chat service with `ReadOnlyGuardChatCompletionService`; `src/Scout.Llm/Guard/ReadOnlyGuardChatCompletionService.cs:89` asks TypeSafe's Jev whether the latest user message, read with up to 12 messages before it, asks for a change and, at or above the threshold, returns a refusal without calling the model (`:76` streaming, `:61` non-streaming). It fails open: a TypeSafe error logs a Warning and the request reaches the model (`:123`). With no key it is not registered. Since [[pages/decisions/0032-per-feature-write-permissions]] the refusal applies only while no feature holds a write grant: the desktop passes the granted feature ids as `SCOUT__FEATURES__GRANTEDWRITES` (empty when none), and with any grant the guard lets the request through without calling TypeSafe ([[pages/services/llm]]). Since 2026-11-02 the guard is a pre-filter: the any-grant pass-through and the fail-open above are bounded by the write gate below, which a declared write cannot pass without the control plane's `allowed`. The guard protects function-calling turns; the live translator offers no function (settings with a 400-token cap and no function choice, no kernel), so it has nothing to reach and bypasses the guard on the provider's own chat service (`src/Scout.Llm/LlmServiceCollectionExtensions.cs:173`, `tests/Scout.Llm.Tests/LiveTranslatorTests.cs:116`).
- **Write gate at the function call** ([[pages/decisions/0032-per-feature-write-permissions]], 2026-11-02). A function registered with `AddWriteFunction` declares its feature and catalog scope row; `src/Scout.Llm/LlmServiceCollectionExtensions.cs:129` puts `WriteGateFilter` on the shared kernel, and every invocation of a declared function, on the direct chat path and the Project Expert agent path, asks the control plane through `IWriteGate` before it runs (`src/Scout.Llm/Guard/WriteGateFilter.cs:33`). Only `allowed` runs it, and its outcome is recorded; `queued` and `refused` never run it, and neither does a gate that fails or misses its deadline (fail closed). The worker reaches the control plane over the desktop's Unix socket with the session token (`src/Scout.Host.Console/GrpcWriteGate.cs:15`); without both values a closed gate refuses every write (`src/Scout.Host.Console/HostComposition.cs:89`). The first declared write is the channel operator's `youtube_make_video` (`src/Scout.Operator/OperatorServiceCollectionExtensions.cs:51`), feature `youtube`, scope "Scout's data folder" ([[pages/services/operator]]); a refused or failed start throws, so the gate records it `failed`, never `succeeded` (`tests/Scout.Host.Console.Tests/HostOperatorTurnTests.cs:73`). An undeclared function is not gated.
- Kubernetes is strict read-only ([[pages/decisions/0009-descriptive-vs-executive-writes]], [[pages/decisions/0020-kubernetes-from-local-kubeconfig]]). `src/Scout.Plugin.Kubernetes/KubernetesPlugin.cs:68` to `:176` expose `list_contexts`, `list_namespaces`, `list_pods`, `describe_pod`, `list_deployments` and `list_events`, each a list or read call; no log, secret, config map, exec, attach, port-forward, proxy or watch call exists, and a context the owner did not allow is refused before a client is built (`src/Scout.Plugin.Kubernetes/KubernetesPlugin.cs:244`). Because the library concatenates the namespace and pod name into the request path, a value that is not a DNS-1123 Kubernetes name is refused before any request (`src/Scout.Plugin.Kubernetes/KubernetesPlugin.cs:223`), so model input cannot turn a GET on a pod into a GET on secrets or a service proxy. The owner's credentials may allow writes, so read-only rests on the plugin unless the owner uses the read-only `view` user the card recommends.
- **Later progress posts** ([[pages/decisions/0033-channel-operator-architecture]], 2026-11-03). A post made after the turn ended, through `IOriginNotifier` (`src/Scout.Conversation/OriginNotifier.cs:18`), is the same descriptive write to the originating channel as a reply: one plain-text message into the conversation the request came from, which the adapter captured as `ChatMessage.OriginReference` at turn time. That it lands in the originating channel is a convention on the caller, not enforced: `PostAsync` accepts any reference string, and `discord:<channel id>` reaches any channel the bot can see. The guarantee rests on every caller taking the reference from `ChatOrigin.Current` or from the job state that stored it, and on no model-callable function taking a reference as a parameter; nothing in code stops a function from forwarding a model-supplied string ([[pages/services/conversation]]).
- Through the desktop sign-in the GitHub token belongs to a GitHub App with read-only permissions, so GitHub itself refuses a write whatever the code does ([[pages/decisions/0019-github-app-device-flow]]) This holds for the browser method only; a token the owner pastes is capped by its own grant, and read-only then rests on the GET-only client alone.
- YouTube reads go through a read client that is GET-only by construction ([[pages/decisions/0030-youtube-plugin-read-only-with-browser-sign-in]]): it sends only `GET`s to `googleapis.com` through plain `HttpClient`, its three phase 1 functions (`youtube_channel_overview`, `youtube_recent_videos`, `youtube_video_stats`) read channels, playlist items and videos, and while writes are not granted the sign-in asks for `youtube.readonly` and `yt-analytics.readonly` only, so Google refuses a write whatever the code does. The desktop's OAuth code exchange, refresh and revoke are POSTs to Google's token endpoints: authentication of Scout itself, the same class as [[pages/decisions/0018-chatgpt-plan-sign-in]] and [[pages/decisions/0019-github-app-device-flow]], never a write to a system of record. The channel operator's `youtube_make_video` is the one declared write next to them: it saves a video project into Scout's own state through the control plane and calls no YouTube write; `youtube_video_status` reads the latest projects from the same state and is a read ([[pages/decisions/0033-channel-operator-architecture]]).
- YouTube writes (from 2026-11-03) run only as owner-approved actions. The owner's publish or experiment confirmation in the desktop creates the approved actions (`src/Scout.ControlPlane/Operator/OperatorService.cs:1930`, refused without the grant: `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:58`); the worker's executor takes only what the control plane hands out (`src/Scout.Operator/ActionExecutor.cs:126`), and the control plane hands out nothing for a feature without the live grant (`src/Scout.ControlPlane/Operator/OperatorService.cs:1610`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:505`) and claims each action under a lease so it runs once (`src/Scout.ControlPlane/Actions/JsonFileActionQueue.cs:119`). The executor is idempotent per action, so a crash between the upload and the record never uploads twice (`tests/Scout.Operator.Tests/ActionExecutorTests.cs:389`), and a publication found `uploading` after a worker restart, the upload's fate unknown, is failed with a pointer to YouTube Studio instead of uploaded again (`tests/Scout.Operator.Tests/ActionExecutorTests.cs:574`), and a record after the owner revoked is refused and the change on YouTube is shown, never repeated: an action already running is logged once as run after the revoke and never handed out again (`tests/Scout.ControlPlane.Tests/WriteGate/WriteGateServiceTests.cs:268`); the executor saves the video id, or an arm's timing, before it records, records a write YouTube took even when that save is refused, and records it once "after revoke", never as failed and never repeated (`tests/Scout.Operator.Tests/ActionExecutorTests.cs:406`, `tests/Scout.Operator.Tests/ActionExecutorTests.cs:428`, `tests/Scout.Operator.Tests/ActionExecutorTests.cs:447`). A revoke or a disconnect rejects every approved YouTube action first, and an action approved or claimed before the current grant is never handed out again (`src/Scout.ControlPlane/Operator/OperatorService.cs:1864`), so a stale approval never runs under a later grant (`src/Scout.ControlPlane/Operator/OperatorService.cs:1621`, `tests/Scout.ControlPlane.Tests/Operator/OperatorServiceTests.Publication.cs:698`). The write client is separate from the read client and is never offered to the model; the model's `youtube_publish_video` queues nothing and points to the desktop. Write scopes exist only while writes are granted ([[pages/decisions/0030-youtube-plugin-read-only-with-browser-sign-in]]). Comment replies and holds (from 2026-11-03) follow the same path: the owner's approval of one reply or one hold on the desktop's Comments page creates one approved action on `comment:<id>` (`src/Scout.ControlPlane/Operator/CommentService.cs:56`, `:131`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:94`, `:131`), a comment target is never read as a project (`src/Scout.ControlPlane/Operator/OperatorService.cs:1859`), and the worker can neither change the reply text the owner approved nor undo an owner decision on a comment (`src/Scout.ControlPlane/Operator/CommentRules.cs:65`, `src/Scout.ControlPlane/Operator/CommentService.cs:209`, `tests/Scout.ControlPlane.Tests/Operator/CommentServiceTests.cs:179`, `tests/Scout.Operator.Tests/ActionExecutorTests.cs:665`, `:678`).
- The operator's stock pictures (2026-11-03) are a read: `OpenversePictures` (`src/Scout.Operator/OpenversePictures.cs:77`) sends a `GET` to `api.openverse.org` and one `GET` for the picture the result names, https only, no redirects followed (`src/Scout.Operator/OpenversePictures.cs:241`, `src/Scout.Operator/OperatorServiceCollectionExtensions.cs:39`), never another method, without an account, a key or any credential; the YouTube feature declares it as the `Read` row "api.openverse.org and the host of the picture it names" (`src/Scout.ControlPlane/Features/FeatureCatalog.cs:138`, `tests/Scout.Host.Console.Tests/WriteDeclarationCatalogTests.cs:40`). - The owner's changes from the chat (2026-11-04, phase 8d, [[pages/decisions/0033-channel-operator-architecture]]) are writes to Scout's own state, and two checks hold them. The owner identity narrows who may ask: only the local quick-ask user or an allowed chat user listed in `Scout:Access:OwnerUserIds`, set for the turn from the platform event and never from a function parameter, and anyone else is refused before any control-plane call (`tests/Scout.Operator.Tests/YouTubeOperatorPluginTests.cs:354`). The worker also runs a change only after a state read of the same project in the same conversation, the chat channel and the sender as the conversation memory keys them, within 10 minutes (`tests/Scout.Operator.Tests/YouTubeOperatorPluginTests.cs:614`, `:625`). ## Known exceptions and tensions with the README

- **Token scope (reopened 2026-10-23 for pasted tokens).** The catalog asked for a `repo`-scope token and listed "Create issues"; it now lists only the GitHub App's read permissions (`src/Scout.ControlPlane/Features/FeatureCatalog.cs:48`, `tests/Scout.ControlPlane.Tests/Features/FeatureCatalogTests.cs:20`). A host configured with `Scout:Plugins:GitHub:Token` still gets whatever scopes that token carries. An earlier plugin had `create_issue` under `src/old/`, which is outside `Scout.slnx` and not built. The desktop "Use a token" method accepts any token the owner pastes, including a classic token with `repo` scope, and hands it to the worker as `SCOUT__PLUGINS__GITHUB__TOKEN`; the card warns when the scope header lists a write scope, and read-only for that method rests on the GET-only client ([[pages/decisions/0019-github-app-device-flow]], `ui/packages/main/test/oauth-github-token.test.ts:133`).
- **Host mutation by the control plane.** `Scout.Host.ControlPlane` can pull and delete Ollama models (`src/Scout.Host.ControlPlane/Services/ModelsGrpcService.cs:22,59`; `src/Scout.ControlPlane/Providers/OllamaApiClient.cs:168`) and start and kill the Ollama process (`src/Scout.ControlPlane/Providers/OllamaProviderService.cs:205`, launched with both control-plane tokens scrubbed from its environment at `:198`; `src/Scout.ControlPlane/Providers/SystemProcessLauncher.cs:173`). These are driven by the desktop UI over an authenticated local socket (`src/Scout.Host.ControlPlane/ControlPlaneServiceRegistration.cs:41`), never by the model. They mutate the host, so ADR 0009 must rule on whether they fall outside this invariant.
- **Quick ask (local adapter).** The local adapter writes `SCOUT_LOCAL` reply lines to the worker's stdout, and the desktop shows them only in the owner's own quick-ask window and Chat screen, which share one conversation held in main (`src/Scout.Adapter.Local/LocalEventWriter.cs:25`, `ui/packages/main/src/quick-ask/quick-ask.ts:548`). Those windows are the originating channel, so the reply is a descriptive write like any chat reply. Reading the owner's microphone while Space or the button is held, and the line main writes to the worker's stdin, are reads the owner starts on their own machine; the quick-ask shortcut is Scout's own configuration. The adapter adds no LLM-invocable function, plugin operation or control-plane command ([[pages/decisions/0028-local-quick-ask-assistant]]). Keeping a meeting and deleting one come only from the `keep` and `delete` requests the desktop writes to the worker's stdin after the owner's click; no chat text, function result or `KernelFunction` reaches `IMeetingStore`, and the store references no network assembly ([[pages/decisions/0037-meetings-kept-locally-in-sqlite]], `tests/Scout.Meetings.Tests/SqliteMeetingStoreTests.cs:281`, `tests/Scout.Adapter.Local.Tests/LocalChatAdapterTests.cs:779`).
- **Own Discord application flag.** The desktop wizard sends one PATCH to Scout's own Discord application to turn on the limited Message Content intent, keeping every other flag (`ui/packages/main/src/discord/discord-setup.ts:94`). The owner starts it from the wizard; no LLM-invocable function or worker path reaches it. [[pages/decisions/0022-discord-setup-from-the-bot-token]] classifies it as Scout's own configuration, not an executive write.
- **Own startup entry.** The desktop registers Scout as a login item on macOS and Windows and writes `~/.config/autostart/scout.desktop` on Linux (`ui/packages/main/src/shell/login-item.ts:56`, `:76`), when the owner turns on "Start Scout when I log in" in Settings, refreshes an existing entry at start-up to Scout's own current executable (`ui/packages/main/src/shell/login-item.ts:102`, because an AppImage update can rename the file), and deletes that one file when it is turned off (`:90`). No worker path, LLM-invocable function or chat message reaches it. [[pages/decisions/0027-desktop-presence]] classifies it as Scout's own configuration, not an executive write.
- **Own installation (ADR 0031).** On the user's click of Update and restart, the desktop main process lets `electron-updater` replace the AppImage it runs (only when `APPIMAGE` and `APPDIR` are set and the executable lives inside `APPDIR`) or run the Windows installer, for a release GitHub published whose checksum matched and whose version equals the notice shown; the worker is stopped and the single-instance lock released first. No background download, no install on quit, no path from the worker, an LLM-invocable function or a chat message: the only trigger is the `scout:update.install` channel of the renderer, and `ui/packages/main/test/update-notice.test.ts` pins the options, the order and the failure paths. [[pages/decisions/0031-desktop-self-update]].
- **Own state.** Scout writes `features.json`, with the approval queue `actions.json`, the write log `writes.log` and the channel operator's `mandate.json`, `projects.json` and `comments.json` beside it (`src/Scout.ControlPlane/Operator/JsonFileOperatorStore.cs:40`, `:39`, `:41`), `local-runtimes.json` (`src/Scout.ControlPlane/Features/FeatureStateStoreOptions.cs:24`, `src/Scout.ControlPlane/Providers/JsonFileLocalRuntimeConfigStore.cs:129`), the vector database (`src/Scout.Knowledge/KnowledgeServiceCollectionExtensions.cs:107`) and, when the owner keeps a meeting, `meetings.db` (`src/Scout.Meetings/SqliteMeetingStore.cs:67`, deleted with its text scrubbed at `:252` and `:274`, [[pages/services/meetings]]) under the user's local application data directory. This is Scout's own config, index and the meetings the owner chose to keep.

## Change protocol

To add a write function: declare its row in the feature catalog ([[pages/decisions/0032-per-feature-write-permissions]]), register it with `AddWriteFunction` so the write gate asks the control plane on every call, and add a test that the function's body never runs on `queued` or `refused`. A test that fails when an undeclared write function reaches the kernel is still open.
