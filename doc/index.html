Read-only ChatOps Assistant

Scout

Scout is an open-source ChatOps assistant that describes and answers work for humans in chat. It surfaces information about your systems — repositories, issues, cloud health, indexed project knowledge — and never executes mutating operations against external systems. It is built on Microsoft Semantic Kernel and .NET 10, with pluggable LLM providers (local-first via Ollama), pluggable chat adapters, and pluggable feature plugins.

Microsoft Semantic Kernel .NET 10 Ollama (local-first) Discord · Slack · Teams adapters Streaming-first
The descriptive-write / read-only invariant. No feature may execute against an external system. Plugins declare capabilities classified by WriteClass (None / Descriptive / Executive); executive writes are forbidden, and the registry enforces the invariant at startup. PluginCapabilities.IsReadOnly has no setter, so a write-capable state is literally unrepresentable in the type system. Replies are bound only to the originating channel/thread.

What you get

  • A streaming-first conversation core that drives per-turn LLM responses to any chat platform through a single cumulative-text sink contract.
  • A provider-agnostic LLM gateway (IChatGateway) over Semantic Kernel — no SK or connector SDK types leak to consumers.
  • Retrieval capabilities: a vector-backed RAG knowledge store and an embedding-driven skills library that shape each turn.
  • Read-only feature plugins (GitHub) exposed to the LLM as Semantic Kernel function calls.
  • A control plane for managing local LLM runtimes (Ollama / LM Studio), models, and feature credentials over a secure local gRPC transport.

The per-turn message flow

Every inbound chat message follows the same streaming pipeline. A platform adapter normalises the event into a ChatMessage and a channel-bound IResponseSink, the conductor wraps the turn in telemetry, the router selects skills and calls the gateway, and the gateway streams tokens (optionally invoking read-only feature plugins as Semantic Kernel function calls) back through the sink to the originating channel only.

Tokens stream back through StreamPump → IResponseSink, which accumulates cumulative text (never deltas) and emits a single terminal Complete or Fail. Feature plugins (GitHub, Knowledge, Skills) contribute Semantic Kernel functions that the model may call mid-stream; retrieval grounds the answer with citations. Memory is written back only on clean completion.

Cross-cutting invariants

Streaming-first everywhere (IAsyncEnumerable<string>; blocking calls drain the stream internally). Cycle-safe DI: the embedder is built outside the kernel to break the Kernel → KernelPlugin → IEmbeddingGenerator → Kernel loop. Self-gating: adapters and plugins register only when configured, so an unconfigured host still starts. Distributed tracing via ScoutActivitySource.

LLM Providers — Configuration

Scout.Llm exposes a provider-agnostic gateway (IChatGateway) and an ILlmProviderFactory abstraction. Exactly one provider is selected per run via the Scout:Llm:Provider key; its matching options block under Scout:Llm supplies the chat and embedding settings. All blocks bind to LlmOptions — the single source of truth for both chat and embeddings.

Provider selection

Set the active provider with the Scout:Llm:Provider key. Valid values (each maps to an ILlmProviderFactory.Name):

Ollama Gemini OpenAI OpenRouter AzureOpenAI Mistral HuggingFace AzureAIInference
Security — never commit API keys

API keys must never live in the tracked appsettings.json. Use one of:

  • appsettings.Development.json — gitignored; fine for local runs.
  • user-secrets — dotnet user-secrets set "Scout:Llm:<Provider>:ApiKey" "<key>" (e.g. Scout:Llm:OpenAI:ApiKey).
  • environment variable — Scout__Llm__<Provider>__ApiKey (double-underscore segment separator), e.g. Scout__Llm__OpenAI__ApiKey.

The tracked appsettings.json should hold non-secret structure only (endpoints, model names) with empty key strings.

Caveats

Chat model must be tool-capable. Function-calling for search_project and find_symbol only works when the selected chat model supports tools. For HuggingFace and OpenRouter this is route-/model-dependent — pick a model that advertises tool use (for Ollama, run a tool-capable model such as qwen2.5, not gemma3).

Changing the embeddings model requires re-indexing. Embedding vectors are model-specific, so switching the embeddings Model (or its dimensions) invalidates stored vectors — re-index every configured project before querying again.

Project Knowledge — Configuration

Scout.Knowledge answers questions about local repositories by indexing them into a vector store and grounding the agent on the result. Projects come from two sources under Scout:Projects, both optional: explicit entries (Items) and auto-discovered repositories scanned from parent directories (Roots). The plugin and the Project Expert agent register only when at least one project is configured (Items or Roots), so an unconfigured host still starts.

Items — explicit projects

Pin a project by name and repository path. Explicit items are authoritative: they win on name collision (case-insensitive) with anything auto-discovered. 

"Scout": {
  "Projects": {
    "Items": [
      { "Name": "messaging-explorer", "RepoPath": "/home/vitor/WorkSpace/Dev/messaging-explorer" }
    ]
  }
}

Roots — auto-discovery

List parent directories; Scout scans their immediate child directories and registers each one that looks like a repository. A child qualifies when any of these markers is present:

.git *.sln *.slnx *.csproj package.json go.mod pyproject.toml Cargo.toml

A discovered project's Name is the directory name and its RepoPath is the directory path. Discovery does directory listing only — no embedding and no indexing at startup; a project is lazily indexed on its first search and skipped on later queries once stored. The list_projects kernel function returns the merged, searchable set (auto-discovered plus explicit). 

// Items and Roots can be combined; Items win on name collision.
"Scout": {
  "Projects": {
    "Roots": [
      "/home/vitor/WorkSpace"
    ],
    "Items": [
      { "Name": "messaging-explorer", "RepoPath": "/home/vitor/WorkSpace/Dev/messaging-explorer" }
    ]
  }
}

Changing the embeddings model requires re-indexing. Embedding vectors are model-specific, so switching the embeddings Model (or its dimensions) invalidates stored vectors. The optional file-watch re-indexing (Scout:Projects:Watch) applies to explicit Items only.

Adapters — Configuration

Each chat adapter binds its settings from Scout:Adapters and is self-gating: it activates only when its credentials are present, and an unconfigured host still starts. Inject every token via environment variables or .NET User Secrets — never commit a token to appsettings.json.

Environment variable mapping

Config keys use : as the path separator. The equivalent environment variable replaces each separator with a double underscore and upper-cases the name, e.g. Scout:Adapters:Discord:BotToken → SCOUT__ADAPTERS__DISCORD__BOTTOKEN.

Discord

Scout connects as a bot over the Gateway. You need a single bot token and the Message Content privileged intent so the bot can read message text.

discord.com/developers/applications New Application → Bot Reset Token Message Content Intent OAuth2 → bot scope

Create the application in the Developer Portal, add a bot and reveal its token, enable the Message Content Intent under the bot's Privileged Gateway Intents, then use the OAuth2 URL Generator (bot scope, with View Channels / Send Messages / Read Message History) to invite the bot to your server. The bot token is the only key Scout reads. 

"Scout": {
  "Adapters": {
    "Discord": {
      "BotToken": ""     // secret → user-secrets / env
    }
  }
}

Slack

Scout uses Socket Mode, so no public URL is required. It needs two tokens: a bot token (xoxb-) for Web API calls and an app-level token (xapp-) to open the Socket Mode connection.

api.slack.com/apps Socket Mode → connections:write Bot Token Scopes Event Subscriptions Install to Workspace

Create an app from scratch, enable Socket Mode and generate an app-level token with the connections:write scope (the xapp- value). Add the bot token scopes you need (e.g. app_mentions:read, chat:write, channels:history), subscribe to bot events such as app_mention under Event Subscriptions, then install to the workspace and copy the Bot User OAuth Token (xoxb-). Both tokens are required for the adapter to start. 

"Scout": {
  "Adapters": {
    "Slack": {
      "BotToken":      "",    // xoxb- → Web API calls
      "AppLevelToken": ""     // xapp- → Socket Mode (connections:write)
    }
  }
}

Microsoft Teams

Scout authenticates as an Azure Bot using its App (client) id and, for a single- or multi-tenant bot, a client secret. A user-assigned managed-identity bot may leave the password empty.

portal.azure.com Azure Bot App registration Certificates & secrets Teams channel

Create an Azure Bot (or register an app under Microsoft Entra ID → App registrations) and copy its Microsoft App ID. Under the app registration's Certificates & secrets, create a client secret for AppPassword (leave empty for managed identity). For a single-tenant bot, copy the Directory (tenant) ID into TenantId; leave it empty for a multi-tenant bot. Finally enable the Teams channel on the Azure Bot resource. 

"Scout": {
  "Adapters": {
    "Teams": {
      "AppId":       "",    // Microsoft App (bot) id
      "AppPassword": "",    // client secret (empty for managed identity)
      "TenantId":    ""     // directory (tenant) id (empty for multi-tenant)
    }
  }
}

Storing secrets with User Secrets

From src/Scout.Host.Console, keep tokens out of the repository: 

// run from src/Scout.Host.Console
dotnet user-secrets init
dotnet user-secrets set "Scout:Adapters:Discord:BotToken" "<discord-bot-token>"
dotnet user-secrets set "Scout:Adapters:Slack:BotToken" "<xoxb-token>"
dotnet user-secrets set "Scout:Adapters:Slack:AppLevelToken" "<xapp-token>"
dotnet user-secrets set "Scout:Adapters:Teams:AppId" "<app-id>"
dotnet user-secrets set "Scout:Adapters:Teams:AppPassword" "<client-secret>"

LLMGateway & providers

Scout.Llm

Active

Streaming-first LLM gateway over Semantic Kernel with pluggable providers.

Responsibility

Provides the abstract chat completion surface (IChatGateway) for Scout's conversation loop. Routes requests through Semantic Kernel, supports pluggable LLM providers (Ollama today), exposes both streaming (primary) and blocking completion APIs, and integrates an optional ChatCompletionAgent for tool-grounded responses. Shields consumers from SK and provider SDK types.

ILlmProviderFactory
Abstraction for pluggable providers; each factory wires SK services and a standalone embedder without a kernel dependency.
OllamaLlmProviderFactory
Concrete Ollama provider; uses the OpenAI connector for chat (via /v1) and the native Ollama connector for embeddings.

Dependencies
Scout.Conversation
Where it fits

Sits below the conversation loop (Scout.Conversation): receives a ChatRequest, yields streaming content via IChatGateway.StreamAsync, and integrates function-calling through Semantic Kernel plugins contributed by feature modules. Provides embeddings for grounding services (e.g. project knowledge). Local-first (Ollama) by default.

Notable

Streaming-first invariant: all consumers use StreamAsync; CompleteAsync drains it internally so there is one code path. Provider abstraction has no SK or connector SDK dependencies in public types. Cycle-safe DI: the embedder factory creates a standalone generator outside the kernel to break the plugin→kernel→embedder cycle. Persona binding on the agent path via KernelArguments; SystemPrompt on the direct chat path. Ollama/OpenAI-compatible wiring; SKEXP0010 / SKEXP0070 suppressions scoped to the factory only.

Scout.Llm (Ollama Provider)

Active

Semantic Kernel abstraction layer with pluggable LLM providers, Ollama-native.

Responsibility

The primary LLM gateway abstraction that decouples the rest of Scout from provider implementations. It defines a streaming-first chat API (IChatGateway), pluggable provider interfaces (ILlmProviderFactory), and a composition root that wires Semantic Kernel services. The Ollama provider integrates chat completion (via the OpenAI connector to Ollama's /v1 endpoint for function-calling) and embeddings (native Ollama connector), with strict validation and cycle-safe DI to prevent kernel construction loops.

IChatGateway
Primary chat API; routes requests through the shared kernel via agent or direct path, yielding content chunks as they arrive.
ChatGateway
Streaming-first implementation; translates provider-agnostic ChatRequest to SK primitives; supports function-calling and optional agent routing.
ILlmProviderFactory
Pluggable provider interface; registers chat/embedding services on the kernel; isolates provider connectors from the gateway.
OllamaLlmProviderFactory
Ollama provider; OpenAI connector for chat (Ollama /v1), native Ollama connector for embeddings; validates all options upfront.
ChatRequest
Provider-agnostic request record with user message, history, persona, system prompt, temperature, max tokens.
LlmOptions / OllamaOptions
Configuration hierarchy; binds Scout:Llm; holds endpoint, chat model, embedding model, batch size, timeouts.
Dependencies
none
Where it fits

The gateway layer between the chatops composition root and the LLM providers. Every LLM call (chat, embeddings, function-calling) flows through IChatGateway to the shared Kernel, which routes to the active provider. No SK types leak beyond IChatGateway. Agent composition (optional ChatCompletionAgent) and plugin registration happen at gateway initialization.

Where it fits

The core RAG layer supporting context injection for the LLM via the shared Semantic Kernel. Scout.Skills

Active

Embedding-driven skill library for system prompt injection during LLM turns.

Responsibility

Provides a retrieval-based skills system that loads markdown behavioral instructions from disk, embeds their descriptions, and selects the most relevant skills per conversational turn via cosine similarity. Injects selected skill bodies into the system prompt to guide LLM behavior. Dual-mode: embedding-free tool-based access via SkillsPlugin (list/load for the LLM) and retrieval-driven auto-injection via SkillSelector. Avoids circular DI by separating embedding concerns from the catalog.

Key Types
ISkillCatalog
Embedding-free access to loaded skills; backs SkillsPlugin to prevent embedder re-entry cycles.
SkillSelector
Embedding-driven ranking; selects top-N skills per turn via cosine similarity with a configurable threshold.
SkillsPlugin
SK plugin exposing list_skills and load_skill functions for LLM-driven skill discovery.
SkillFileLoader
Parses markdown skill files with frontmatter (name, description) and body; handles missing/malformed files gracefully.
SkillPromptComposer
Composes the per-turn system prompt by appending selected skill bodies under labeled delimiters.
Skill
Immutable record of a skill: name, retrieval description, instructional body, source path.
SkillsOptions
Configuration (Enabled, Directory, TopN, SimilarityThreshold) with sensible code defaults.
Dependencies
none
Where it fits

The per-turn system prompt preparation layer in the conversation router. Sits between LlmStreamingRouter and the LLM, providing skill selection before the chat request is assembled. Skills auto-inject into the system prompt when enabled; dual-mode also lets the LLM discover and load skills dynamically via tool calls.

Notable

Lazy initialization for both catalog and selector means zero file I/O or embedding work during DI build — deferred to the first turn. Embedding-free ISkillCatalog decouples SkillsPlugin from the embedding generator, preventing circular DI. Graceful degradation: NoOpSkillSelector returns an empty list, never throws. Cosine similarity over ReadOnlySpan<float> with configurable thresholds. Markdown skill definitions with YAML-style frontmatter; malformed files skipped with logging.

ConversationPer-turn pipeline core

Scout.Conversation

Active

Platform-agnostic conversation core: streaming-first routing, memory, sink lifecycle.

Responsibility

The platform-agnostic heart of the chatops assistant, responsible for orchestrating per-turn message routing, streaming responses, and conversation memory. It bridges inbound platform events (via chat adapters) to the LLM gateway through a streaming-first pipeline: a conductor handles each inbound message, a router selects skills and delegates to the LLM, and a stream pump drives cumulative token output to a channel-bound sink. It enforces Scout's descriptive-write invariant (replies only to originating channels) and provides out-of-the-box conversation history with configurable memory budgets.

Key Types
ConversationConductor
Adapter-facing handler: wraps inbound routing/streaming in an OTel activity; surfaces failures via sink.FailAsync without crashing the host.
IConversationRouter
Maps inbound ChatMessage to streaming ChatResponse; single responder for v1 (no fan-out).
LlmStreamingRouter
Routes the message to the LLM via IChatGateway, selects the most relevant skill, replays/appends conversation memory, returns a token stream.
StreamPump
Transport-agnostic stream-drive loop: opens the sink, accumulates tokens, throttles interim updates per RenderCapabilities, emits a single terminal complete/fail.
IResponseSink
Platform-specific outbound sink bound to the originating channel; cumulative-text lifecycle (Begin→Update→Complete|Fail).

Improvement Backlog & Roadmap

The work below is grouped into preconditions to verify, improvements to make, things to build, and a suggested sequencing that turns "probably works" into measured.

Preconditions

Verify these before trusting any project Q&A from the bot.

Verify before trusting
  • Tool-capable model. The deployed LLM must be tool-capable and stream tool calls over the OpenAI-compatible /v1 connector. Validate the configured model tag — "qwen3.5:9b" is likely not a real Ollama tag.
  • Fixes are committed but not deployed. The conversation-memory and grounding fixes are committed locally on feat/project-knowledge but not deployed — redeploy the bot for them to take effect.
  • Indexed and fresh. The target project must be indexed and its index fresh.

Improvements to Make

1RAG / project-answer correctness

A 4-link chain — none of the links is guaranteed. Each must hold for a correct, grounded answer.

1
Tool-call reliability
The local model must decide to call search_project. This is non-deterministic on a weak model — induce via prompt now, later via hard tool-scoping.
2
Index coverage & freshness
Verify the project is indexed, that file-watch re-index works, and that chunking quality is adequate.
3
Retrieval recall
Tune the embedder / chunking / top-K / nomic prefixes.
4
Answer faithfulness
Enforce citations and an honest "not in context"; guard against hallucination even with good context.

2Skills system

  • With ~52 skills and TopN=1 retrieval, sharpen overlapping descriptions (backend-developer vs sql, software-architect vs backend-developer, clean-architecture vs hexagonal, clean-code vs refactoring) or raise TopN.
  • Update SKILLS-ATTRIBUTION.md: redis-development is third-party; the role/language/architecture skills are authored original.
  • Measure whether injected skill bodies actually improve answers on the local model.

3Ops

  • VRAM contention. A heavy chat model starves the nomic-embed-text embedder on a single GPU — use a lighter chat model or free Ollama while indexing.

4Delivery

  • Everything is local on feat/project-knowledge (not pushed) — plan the PR.
  • The skills history (import → drop → author) could be squashed.
  • Run the production-readiness checks before opening a PR.
