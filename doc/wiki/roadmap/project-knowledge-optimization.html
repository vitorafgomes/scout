Project Knowledge Optimization — Initiative

Move Project Knowledge retrieval from dense-only cosine search to a symbol-aware, hybrid pipeline so that "where is method X" is deterministic and "find this functionality" survives fuzzy phrasing.

roadmap statusactive version 1.0 date 2026-06-01 sources vault 02-architecture/project-knowledge-optimization-roadmap.md

Why now

Project Knowledge retrieval is dense-only: SqliteProjectKnowledgeStore.SearchAsync filters on Project and runs pure cosine over nomic-embed-text. So "where is method X" depends entirely on embedding similarity — the persisted Symbol column is dead weight, never queried, and exact identifier matches are neither boosted nor guaranteed.

It is compounded by a hardcoded top-5 with no dedup: the AST chunker walks DescendantNodes() and emits the full class and each method, so the five result slots can collapse into near-duplicate spans of a single symbol. The roadmap comes out of a multi-agent workflow (scout-knowledge-optimization) that produced 33 recommendations across six dimensions, each adversarially verified against the real codebase on branch feat/project-knowledge.

Highest-leverage fix

A metadata-only exact-symbol lookup — find_symbol over the already-persisted Symbol column. It is deterministic, never misses the exact identifier, and is independent of embedding quality. The mechanism is already proven by ReplaceFileAsync, which does a filtered GetAsync over a non-indexed text column.

Scope

In scope

  • An exact-symbol retrieval line ("find a method"): find_symbol and its supporting indexer changes.
  • A hybrid retrieval line for fuzzy "functionality" queries: FTS5 keyword index fused with dense search via Reciprocal Rank Fusion (RRF).
  • Quick wins that need no reindex: configurable top-K + dedup, exposing scores, query/index embedding symmetry, and wiring dead embedding config.
  • Indexing throughput and robustness (bounded-concurrency batching, oversized-chunk handling, retry-with-backoff).

Out of scope

  • Replacing the local-first embedding model — work stays on nomic-embed-text via Ollama.
  • The Capability Engine retrieval unification — tracked separately.
  • Any change to the read-only / descriptive-write boundary — retrieval improvements do not introduce executive writes.

Status

As of 2026-06-01, this is an active, sequenced plan derived from the verified recommendation set. The note records 33 recommendations, 32 actionable, 0 already done. Sequencing is fixed (below) but no workstream item is reported as merged yet.

Verified gotchas to respect
  • IsIndexed on SqliteVec is a perf hint, not a filterability gate — filtering on non-indexed columns already works (proven by the passing ReplaceFileAsync Path test).
  • VectorSearchResult<T>.Score is a nullable double?, and with CosineDistance it is a distance (lower = nearer), not a similarity.
  • EmbeddingGeneratorBuilder.UseRetry and CreateChat referenced in some proposals do not exist — use a hand-rolled DelegatingEmbeddingGenerator / resolve IChatCompletionService from the kernel.
  • FTS5 ships inside bundle_e_sqlite3 — no LoadExtension, no new native dependency (only an explicit Microsoft.Data.Sqlite PackageReference, currently transitive).
  • DeadLetterRetrievalAcceptanceTests is env-gated/skipped (SCOUT_OLLAMA_ACCEPTANCE=1), not a unit test.

Workstreams / Phases

0Quick wins (no reindex)

Run on the existing database; ship before any schema or reindex work.

  • Configurable top-K + dedup of nested spans. ProjectKnowledgeService.cs hardcodes TopResults=5; the store SearchAsync already takes top. Add top/kind to search_project and dedup hits whose (Path, StartLine..EndLine) nest inside a higher-ranked hit.Update the NSubstitute assertions in ProjectKnowledgeServiceTests.cs.
  • Expose hit.Score (currently discarded in SqliteProjectKnowledgeStore.cs) as a ScoredChunk, render it in FormatHit, add a min-score cutoff (or native VectorSearchOptions.ScoreThreshold). Cosine score is a distance, lower = nearer.
  • Query↔index embedding symmetry: extract BuildEmbeddingInput from ProjectIndexer.cs and add a BuildQueryInput (nomic search_query: / search_document:). Query-side only, so no reindex; gate on the model name.
  • Wire dead embedding config: MaxBatchSize/HttpTimeoutSeconds/ExpectedDimensions are validated then ignored in OllamaLlmProviderFactory.cs. Set HttpClient.Timeout; assert vector length == ExpectedDimensions (when > 0) in ProjectIndexer.BuildRecordsForFileAsync.
  • Progress + skipped-file accounting in the index summary, distinguishing a catch-path empty return from a legitimately chunk-less file in ProjectIndexer.cs.

ASymbol-search line — "find a method"

The direct deterministic answer to identifier lookups. A1 is the single next thing.

  • A1 — find_symbol: metadata-only FindSymbolAsync(project, symbol, kind?, top) via GetAsync(r => r.Project == project && r.Symbol == symbol); the service skips the embedder; exposed as [KernelFunction("find_symbol")]. No schema change, runs on the existing DB. Case-insensitivity post-filtered in memory. Foundation of hybrid's exact-match leg.
  • A2 — SymbolLower + NodeKind: ProjectIndexer.cs currently overwrites the fine kind (method/class) with a coarse code/doc. Adds case-insensitive SQL match + kind-scoped filter. Requires a one-time reindex.
  • A3 — Qualified symbols + signatures (Namespace.Type.Method(params), walking node.Parent). Bundle the reindex with A2.
  • A4 — RoslynSymbolLocator: live parse of .cs, covering all declaration kinds (struct/enum/property/ctor/local-function/delegate), never stale. Additive, no schema change; layers on A1.

BHybrid retrieval — fuzzy "functionality" queries

Keyword + dense fusion so phrasing differences stop breaking recall.

  • B5 — FTS5 + RRF (BM25 ⊕ dense, k ≈ 60), dual-written in ReplaceProjectAsync + ReplaceFileAsync. New SqliteKeywordIndex.cs; mirror the EnsureCollectionExistsAsync graceful guard. Risk: transactionality across two connections. This is the hybrid-retrieval slice proper (Phase 2 slice 2).
  • B6 — Code-aware tokenization (camel / Pascal / snake / .) applied to FTS content and query, so DeadLetter ↔ dead letter. Depends on B5.
  • B7 — Exact-symbol rank-0 shortcut (reuses A1) + optional LLM rerank behind a flag + retrieval config plumbing.

CIndexing throughput & robustness

Orthogonal track: improves freshness, not precision. Can run in parallel.

  • C8 — Bounded-concurrency cross-file batch embedding (Parallel.ForEachAsync degree 2-4, batch by MaxBatchSize, one final ReplaceProjectAsync). Prereq: a collision-proof Id {project}:{relPath}:{StartLine}-{EndLine}#{ordinal}.
  • C9 — Cap/split oversized chunks (a whole-class node.ToString() can exceed model context). Depends on C8's Id.
  • C10 — Member-level non-overlapping chunking (header-only type chunks + per-member body chunks) — kills duplicate spans, the biggest precision lift from chunking. Requires reindex + heavy FileChunkerTests churn.
  • C11 — Retry-with-backoff via DelegatingEmbeddingGenerator + per-input fallback; share the batch+retry path with the file watcher.

Sequencing

  1. A1 (find_symbol) first — no reindex, runs on the existing DB, unblocks A4 and B7.
  2. Bundle A2 + A3 together behind a single reindex.
  3. B5 (FTS5 + RRF) is the fuzzy "functionality" fix.
  4. Track C is orthogonal (throughput / freshness) and can proceed in parallel.

Risks

  • Two-connection transactionality (B5). Dual-writing the dense store and the new FTS5 keyword index across two connections can leave them out of sync on partial failure; mirror the existing graceful guard and test the failure path.
  • Reindex cost (A2/A3, C10). Several of the higher-value items require a one-time full reindex and heavy churn in FileChunkerTests — schedule them as a bundle, not piecemeal.
  • GPU contention (operational). A heavy chat model (qwen3.5:9b) starves the embedder on the same GPU, stalling indexing and per-query embedding. Use a lighter chat model (e.g. qwen2.5:7b) or ensure GPU headroom for nomic-embed-text to coexist.
  • API-shape assumptions. Some proposals lean on members that do not exist (EmbeddingGeneratorBuilder.UseRetry, CreateChat); building against them blindly fails — use the hand-rolled / kernel-resolved alternatives.
  • Score-sign confusion. With CosineDistance, lower means nearer; treating the nullable double? as a similarity inverts ranking and cutoffs.
