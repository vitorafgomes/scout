Capability Engine — Initiative

Unify "skills" (guidance) and "personas" (who answers and the tool posture) into one retrieval engine over a typed markdown library, so a single embedding pass per turn picks the persona and the skills.

roadmap statusactive version 1.0 date 2026-06-01 sources vault 02-architecture/capability-engine-PLAN.md

This page is the plan and status view of the initiative. The design — the engine shape, the selection mechanics, and the rejected multi-agent alternative — lives in Architecture · Capability Engine. The initiative supersedes the older skills-subsystem improvement roadmap and the multi-agent-versus-skill-routing exploration, folding both into a single engine.

Why now

Scout already has two retrieval-shaped subsystems heading in the same direction. The Scout.Skills subsystem retrieves and auto-injects markdown guidance, and the agent path carries a single hard-coded persona (ProjectExpertAgentFactory.Instructions). Without unification these would drift into two indexes, two embedding passes per turn, two config sections, two selectors, and two lifecycle stores — duplicated cost on a local model that is already tight on VRAM. Folding guidance and persona into one typed library means one index, one message embedding per turn, one batch index build, one config section, one selector, one lifecycle store, and one log line.

The chosen shape is "Pattern B": one agent with a dynamic persona selected by embedding routing, not multi-agent orchestration. Multi-agent orchestration was rejected for the local model and deferred to a future model upgrade. Picking one engine now keeps every persona body as a migration asset: nothing written today is wasted if the project later graduates to a handoff orchestration.

Scope

In scope

  • A behaviour-neutral templated persona agent, where the default persona equals today's ProjectExpertAgentFactory.Instructions so behaviour stays byte-identical until routing is wired.
  • A unified CapabilitySelector that refactors the existing SkillSelector, with one index over all capability name + description entries.
  • A typed markdown format with frontmatter type: persona | skill (defaulting to skill for back-compat), name, description as the retrieval key, optional tools, and a body.
  • One config section Scout:Capabilities replacing the separate skills options.
  • Per-turn selection of top-1 persona (with a general-assistant fallback that is never null) plus top-N skills above threshold.
  • Shipping starter personas (general-assistant, code-analyst, kubernetes-specialist) and retyping the seven existing skills to type: skill.

Out of scope (deferred)

  • Hard tool scoping via FunctionChoiceBehavior.Auto(functions: subset) from a capability's tools — that is Step 3, optional and later. For now tools is parsed and ignored.
  • Graduating to HandoffOrchestration with one agent per persona — Step 4, only on a model upgrade.
  • Pushing or deploying the branch; this work stays local on feat/project-knowledge until the team decides.

Status

As of 2026-06-01, the initiative is active and partially landed on the feat/project-knowledge branch (not pushed). The plan is marked ready-to-execute in the vault.

  • Step 0 — gate fix — done. Commit d61f785: ChatGateway.StreamAgentAsync now passes the composed prompt through AgentInvokeOptions.AdditionalInstructions, so the agent path no longer discards request.SystemPrompt.
  • Foundations in place. The Skills subsystem already exists with SkillFileLoader, SkillSelector/ISkillSelector, SkillPromptComposer, SkillCatalog/SkillsPlugin, seven skill markdown files, and wiring into LlmStreamingRouter. The verified Semantic Kernel 1.77.0 agent APIs needed for the persona template exist.
  • Step 1 and Step 2 — pending. The templated persona agent and the CapabilitySelector refactor are specified but not yet implemented.
  • Baseline health. Tests green (~524), zero warnings, clean build via dotnet build Scout.slnx and dotnet test Scout.slnx.

Workstreams / Phases

Step 1 — Templated persona agent (behaviour-neutral)

Introduce the persona-template machinery, shipped first as its own commit, with the default persona equal to today's instructions so behaviour does not change until Step 2 wires routing.

  • Add Persona to ChatRequest (agent path maps to KernelArguments["persona"]; direct path becomes a leading system message).
  • Rebuild ProjectExpertAgentFactory.Create as a templated ChatCompletionAgent over {{$persona}}, defaulting the argument to Instructions.
  • StreamAgentAsync sets AgentInvokeOptions when persona or system prompt are non-empty; StreamChatAsync composes both into one system message.
  • Tests: default persona renders identical to Instructions; persona-as-argument; persona and additional instructions coexist; direct-path composition; existing agent and router tests stay green.
Step 2 — Unified capability engine

Refactor SkillSelector into CapabilitySelector over one typed library, proving the unification: one index, one message embed per turn, one index batch, one config section, one selector, one lifecycle store, one log line.

  • Move the seven skill markdown files into a single capabilities/ folder and update the csproj content glob.
  • Extend SkillFileLoader to parse type and tools; introduce Capability, CapabilityType, ICapabilitySelector, CapabilitySelection, and NoOpCapabilitySelector.
  • CapabilitySelector: one lazy index over all name + description; embed the message once; one cosine pass; persona = top-1 above threshold else fallback; skills = top-N above threshold; one log line; never throws.
  • Filter SkillCatalog/SkillsPlugin to type: skill so personas are not surfaced as skills.
  • Unify config into Scout:Capabilities; swap DI and LlmStreamingRouter to ICapabilitySelector; delete the old skill-selector types after migration.
  • Ship personas general-assistant, code-analyst, kubernetes-specialist and retype existing skills.
  • Tests: loader parsing; selector ranking/threshold/top-N; fallback persona never null; embedder-throws returns fallback; index built once; single embed per turn; prefixes applied; catalog excludes personas; router forwards persona; DI resolves cycle-free.
Step 3 — Hard tool scoping (optional, later)

Use the selected capability's tools to scope function choice and reduce tool overload on a 9B-class model.

  • Thread an AllowedTools list through ChatRequest.
  • Apply FunctionChoiceBehavior.Auto(functions: subset) from the selected capability's tools.
Step 4 — Multi-agent graduation (future)

Only on a model upgrade: map each persona roughly one-to-one onto a ChatCompletionAgent under HandoffOrchestration. Persona content authored now is the migration asset.

  • Promote personas to agents under orchestration.
  • Reuse existing persona bodies unchanged.

Risks

  • Model tag validity. The chat model must be a real, tool-capable Ollama tag that streams tool calls over the OpenAI-compatible /v1 connector; speculative tags such as qwen3.5:9b must be confirmed against ollama list before relying on them.
  • VRAM contention. A heavy chat model starves nomic-embed-text on a single GPU, stalling the indexing and selection embeds. Use a lighter chat model or free Ollama while indexing.
  • Accidental duplication. Cloning a separate persona selector would break the unification (two of every resource). The plan requires refactoring SkillSelector in place, not cloning it.
  • DI construction cycle. The selector must depend on the cycle-safe embedding generator from the provider factory, not the shared kernel, and must not be a KernelPlugin, or it reintroduces a construction cycle through project knowledge.
  • Tool overload. Roughly eleven tools offered to a 9B model degrade function-calling; until Step 3 scopes tools, behaviour depends on the model coping with the full set.
  • Config and content paths. Scout:Projects:Items are local { Name, RepoPath } paths, not owner/repo strings, and the console host appsettings is skip-worktree with a local token — both must be left untouched.
