Current Focus & Backlog

Turn "probably works" into measured: verify the preconditions, build the end-to-end acceptance test, then fix whichever link of the RAG chain the test exposes as broken.

roadmap statusactive version 1.0 date 2026-06-01 sources doc/index.html roadmap section; vault 01-overview/pending-work.md

Why now

The core platform, the eight pluggable LLM providers, the Skills library, and the Project Knowledge RAG path are all in place, and the conversation-memory and grounding fixes are committed. What is not in place is any measured guarantee that an end-user question against an indexed project produces a correct, grounded answer. The chain from "user asks" to "bot cites the right file" has four independent links, and none of them is currently verified end to end. The focus of this cycle is to close that gap with an acceptance test, then repair whatever the test shows is broken.

A second pressure point is delivery. Everything below sits locally on the feat/project-knowledge branch and has not been pushed, so the fixes that exist only take effect after the branch lands and the bot is redeployed.

Scope

In scope

  • Verifying the RAG preconditions (tool-capable model, deployed fixes, fresh index).
  • An end-to-end acceptance test for the ask → search_project → cite flow against Ollama.
  • Correctness improvements across the four-link RAG chain.
  • Skills-system tuning (retrieval, attribution, measured value).
  • GitHub grounding so get_repository resolves a sensible default project.
  • Planning the PR off feat/project-knowledge and running production-readiness checks.

Out of scope (this cycle)

  • Executive writes. The gated-write milestone (PR-gated proposals + allowlist) is decided but not built, and remains separate.
  • Remote private-repo deep analysis beyond what the existing GitHub plugin already supports.
  • The backend ↔ frontend gRPC split (a future desktop concern).

Status

As of 2026-06-01:

Committed locally, not deployed

The conversation-memory and grounding fixes are committed on feat/project-knowledge but not deployed — the bot must be redeployed for them to take effect. Eight LLM providers are selectable via Scout:Llm:Provider and the Llm test suite is green. The Skills library is curated. Nothing on this branch has been pushed.

Verify before trusting project Q&A
  • Tool-capable model. The deployed LLM must be tool-capable and stream tool calls over the OpenAI-compatible /v1 connector. Validate the configured model tag — "qwen3.5:9b" is likely not a real Ollama tag.
  • Fixes committed but not deployed. The conversation-memory and grounding fixes live on feat/project-knowledge and only matter after a redeploy.
  • Indexed and fresh. The target project must be indexed and its index fresh.

Workstreams / Phases

1RAG / project-answer correctness

A four-link chain — none of the links is guaranteed. Each must hold for a correct, grounded answer.

1
Tool-call reliability
The local model must decide to call search_project. Non-deterministic on a weak model — induce via prompt now, later via hard tool-scoping.
2
Index coverage & freshness
Verify the project is indexed, that file-watch re-index works, and that chunking quality is adequate.
3
Retrieval recall
Tune the embedder, chunking, top-K, and nomic prefixes.
4
Answer faithfulness
Enforce citations and an honest "not in context"; guard against hallucination even with good context.

2Skills system

  • With ~52 skills and TopN=1 retrieval, sharpen overlapping descriptions (backend-developer vs sql, software-architect vs backend-developer, clean-architecture vs hexagonal, clean-code vs refactoring) or raise TopN.
  • Update SKILLS-ATTRIBUTION.md: redis-development is third-party; the role / language / architecture skills are authored original.
  • Measure whether injected skill bodies actually improve answers on the local model.

3Ops

  • VRAM contention. A heavy chat model starves the nomic-embed-text embedder on a single GPU — use a lighter chat model or free Ollama while indexing.

4Things to build

  • End-to-end acceptance test for the ask → search_project → cite flow (real, against Ollama) — turns "probably works" into measured.
  • Capability Engine. A unified persona + skill embedding-retrieval engine ("Pattern B"), currently stashed; finishing it makes the role skills act as personas and cleans selection. Step 3 = hard per-persona tool-scoping (also helps link #1); Step 4 = HandoffOrchestration once the model is upgraded.
  • GitHub grounding. get_repository has no default repo — ground it on the configured project or add a list_projects affordance.
  • Answer-faithfulness / citation-enforcement mechanism (chain link #4).
  • Indexing quality. Chunking strategy plus verified incremental re-index.
  • Backend ↔ frontend gRPC over a Unix socket / named pipe (future desktop split).

5Delivery

  • Everything is local on feat/project-knowledge (not pushed) — plan the PR.
  • The skills history (import → drop → author) could be squashed.
  • Run the production-readiness checks before opening a PR (boundaries: LLM HTTP, memory store, knowledge store, GitHub).
  • Redeploy the bot so the conversation-memory and grounding fixes take effect live.

Suggested sequencing

  1. Verify preconditions — model tool-capable, deploy, index.
  2. Build the e2e test for ask → search → cite.
  3. Fix whichever link the test shows broken — most likely #1, tool-calling.
  4. GitHub grounding — small, high value.
  5. Finish the Capability Engine.
  6. Skill retrieval tuning + attribution.
  7. More skills + hard tool-scoping.

Risks

  • Weak local model. Tool-calling is non-deterministic on a small model; the deployed tag must be confirmed tool-capable over /v1 before any project Q&A is trusted.
  • Silent staleness. An out-of-date index or an undeployed branch makes the bot answer confidently from wrong context — the acceptance test exists to catch this.
  • Single-GPU contention. A heavy chat model and the embedder competing for VRAM can degrade or stall indexing.
  • Test coverage gaps. Provider tests cover wiring and validation only; boundary-failure tests (LLM timeout / 5xx) and a real-skills parse guard are still owed before the PR per the production-readiness bar.
  • Unmerged work. All of this lives unpushed on one branch; the longer it sits, the larger the eventual review and the higher the merge risk.
