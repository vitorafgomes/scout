Wiki/Services/Scout.Knowledge

Scout.Knowledge

The project knowledge RAG subsystem: it chunks a local repository, embeds the chunks into a local SQLite vector store, and exposes retrieval to the model as the search_project Semantic Kernel plugin.

service statusactive version 1.0 date 2026-06-01 sources src/Scout.Knowledge/; README; vault project-knowledge-rag.md

Responsibility

Scout.Knowledge lets a user ask Scout, in natural language, about a configured software project and get an answer grounded in that project's real code and in-repo documentation, with citations to the source files. It walks each configured repository, chunks every indexable file, embeds the chunks through the shared Scout.Llm embedding generator, and stores the result in a local SQLite vector store via sqlite-vec. Retrieval is surfaced to the language model as a Semantic Kernel plugin and steered by a dedicated Project Expert chat agent.

It does not own the LLM connection (that is Scout.Llm), and it never writes to any external system: every operation reads from disk and the local database only, in line with the read-only No Executive Writes invariant. Indexing is lazy — a project is indexed on first resolution, not at startup — so building the DI graph performs no embedding work.

Public contract

  • ProjectKnowledgePlugin — the Semantic Kernel plugin (registered under the plugin name ProjectKnowledge). It exposes three [KernelFunction]s to the model: search_project, find_symbol, and list_projects.
  • IProjectKnowledgeStore — persistence and similarity search over indexed chunks: InitializeAsync, HasProjectAsync, ReplaceProjectAsync, ReplaceFileAsync, SearchAsync (top-K cosine), and FindSymbolAsync (metadata-only name lookup).
  • ProjectKnowledgeService — turns a project question into a citation-tagged context string; never throws, returning a clean status message on empty input, no results, or failure.
  • ProjectResolutionService — resolves a project name to a ProjectEntry and lazily indexes it on first use; merges discovered roots with explicit items (explicit wins on name collision).
  • AddProjectKnowledge(services, configuration) — the composition root: binds Scout:Projects, registers the store, chunker, indexer, and service, and gates the plugin plus agent on having at least one configured project.

Key types

ProjectKnowledgePlugin
SK plugin exposing search_project (semantic), find_symbol (name lookup), and list_projects to the LLM for function-calling.
ProjectKnowledgeService
Embeds the question, runs top-K retrieval, and formats hits into a citation-tagged context block. Returns clean messages, never throws into the kernel.
IProjectKnowledgeStore / SqliteProjectKnowledgeStore
Vector store contract and its sqlite-vec backed implementation over the project_chunks collection; a single local .db file, no external service.
ProjectIndexer
Walks a repo, chunks each file, embeds the chunks (with a contextual File: … | symbol | lines prefix), and replaces the project's chunk set in the store.
FileChunker / IChunker
Roslyn AST chunker for C# (method / class / record / interface boundaries); a 100-line window fallback for every other language and for files with no member declarations.
ChunkRecord
One stored chunk: id, project, path, kind, symbol, start/end line, content, and a 768-dimension cosine-distance embedding.
ProjectResolutionService / ProjectDiscoveryService
Resolve a name to a repo and lazily index on first use; discover repositories under root directories by .git or project markers.
ProjectWatchService
Opt-in BackgroundService that watches each configured repo and re-indexes changed files file-by-file after a debounce window.
ProjectExpertAgentFactory
Builds the single ChatCompletionAgent "Project Expert" over the shared kernel, grounded on the configured project names with automatic function-calling.

Invariants

  • No Executive Writes — every operation reads from disk and the local SQLite store; nothing here writes to an external system.
  • Local-First Default — embeddings use the shared (Ollama-by-default) generator and the vector store is a local file under the host's local application data directory; no cloud dependency.
  • Pluggable Everything — projects are supplied by configuration (explicit Items or scanned Roots); the plugin and agent only register when at least one project is configured.
  • Shouldly-Only Tests — the test project asserts with Shouldly throughout.

Hot spots

  • ProjectKnowledgePlugin.cs:26 & :41 — the search_project and find_symbol [KernelFunction] declarations the model calls; both delegate straight to the service.
  • ProjectKnowledgeService.cs:46 — SearchAsync: validates input, resolves (and lazily indexes) the project, embeds the question, runs top-5 retrieval, and formats hits; the whole retrieval path is wrapped in a try/catch returning a clean string.
  • ProjectKnowledgeService.cs:136 — FormatHit: builds the [path:start-end symbol] citation header prepended to each chunk's content.
  • ProjectResolutionService.cs:73 — ResolveAsync: lazy first-use indexing; an unknown project or a failed first-use index returns null instead of throwing.
  • SqliteProjectKnowledgeStore.cs:98 — SearchAsync calls EnsureCollectionExistsAsync first so a never-indexed project degrades to zero results instead of a "no such table" exception.
  • SqliteProjectKnowledgeStore.cs:47 — ReplaceProjectAsync: gathers the project's current ids by a filtered scan and deletes them by key before upsert, so chunks for deleted code are removed (not merely overwritten).
  • ProjectIndexer.cs:105 — BuildEmbeddingInput: the contextual prefix (File: … | symbol | lines a-b) prepended to each chunk before embedding.
  • FileChunker.cs:13 — language switch: .cs goes through the Roslyn AST path, everything else through the 100-line window fallback.
  • KnowledgeServiceCollectionExtensions.cs:74 — the configured-projects gate; the plugin and Project Expert agent are only registered when Items or Roots is non-empty.
  • ChunkRecord.cs:41 — the embedding vector is fixed at 768 dimensions with cosine distance, matching nomic-embed-text.

Scout.Host.Console Scout.Conversation

The embedding generator is resolved from DI rather than from the shared kernel, which keeps the knowledge graph from forming a construction cycle through Scout.Llm. The console host also drives the one-shot index <project> command directly against the indexer; see Index a Project.

Configuration

All keys live under Scout:Projects. Projects come from explicit Items, from repositories discovered under Roots, or both; explicit items win on a name collision. File-watch is opt-in.

# appsettings.json (excerpt)
"Scout": {
  "Projects": {
    "Items": [
      { "Name": "cegos-buddy", "RepoPath": "/abs/path/to/cegos-buddy" }
    ],
    "Roots": [ "/home/me/WorkSpace" ],
    "Watch": {
      "Enabled": false,
      "DebounceMilliseconds": 750
    }
  }
}
  • Scout:Projects:Items — array of { Name, RepoPath } entries; default empty.
  • Scout:Projects:Roots — directories scanned at startup for repositories (by .git or a project marker such as *.sln/*.csproj/package.json); default empty.
  • Scout:Projects:Watch:Enabled — enable incremental file-watch re-indexing; default false (and only honoured when Items is non-empty).
  • Scout:Projects:Watch:DebounceMilliseconds — quiet window before a changed file is re-indexed; default 750.

The vector database lives at the host's local application data directory under Scout/project-knowledge.db (Linux: ~/.local/share/Scout/project-knowledge.db). Indexable files are .cs .ts .tsx .js .jsx .py .json .yml .yaml (code) and .md .txt (doc); bin obj .git node_modules dist .vs segments are skipped.

Testing footprint

  • Unit tests in tests/Scout.Knowledge.Tests/ cover the chunker, file filter, indexer, resolution and discovery services, the plugin and service contracts, the SQLite store, the options validator, and the watch service. Assertions use Shouldly per the testing convention.
  • SqliteProjectKnowledgeStoreTests.cs exercises the store boundary directly, including the never-indexed degrade-to-empty guard, replace-then-search, and per-file replace semantics.
  • DeadLetterRetrievalAcceptanceTests.cs is an opt-in end-to-end retrieval test gated on SCOUT_OLLAMA_ACCEPTANCE=1; it no-ops (skips) when Ollama is unreachable so plain CI stays green.
  • The store, embedding, and filesystem boundaries each have failure-path coverage (unindexed project, embed/parse failure isolated per file, watcher error re-arm) per Production Readiness.
