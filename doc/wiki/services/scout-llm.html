Scout.Llm

The streaming-first LLM gateway: every chat completion and embedding in Scout flows through one shared Semantic Kernel, behind a provider-agnostic contract.

service statusactive version 1.0 date 2026-06-01 sources src/Scout.Llm/; README; vault 2026-05-28-llm-communication-through-semantic-kernel.md

Responsibility

Scout.Llm owns all communication with the language model. It wraps Microsoft Semantic Kernel behind a small, streaming-first IChatGateway so that no other project ever references a provider SDK or a Semantic Kernel type directly. It selects exactly one of eight provider implementations at startup from Scout:Llm:Provider, builds a single shared Kernel, and exposes chat completion plus an embedding generator from it.

It does not own conversation state or routing (that is Scout.Conversation), nor does it decide which plugins exist — feature modules contribute KernelPlugin instances that the gateway folds onto the shared kernel for function-calling.

Public contract

  • IChatGateway — StreamAsync (the primary path) and CompleteAsync (drains the stream into one string). No Semantic Kernel types appear in the signature, so consumers stay provider-agnostic.
  • ILlmProviderFactory — Name, AddToKernel(builder), and CreateEmbeddingGenerator(). One implementation per provider folder.
  • AddScoutLlm(services, configuration) — the composition root: binds Scout:Llm, picks the provider, builds the shared kernel, and registers the gateway.

Key types

IChatGateway
Primary chat API. Streaming-first; StreamAsync yields content chunks, CompleteAsync drains them.
ChatGateway
internal sealed implementation over IChatCompletionService. Routes through a ChatCompletionAgent when one is registered; otherwise the direct chat path.
ILlmProviderFactory
Registers a provider's SK services on the kernel builder and builds a standalone embedder.
ChatRequest
Provider-agnostic request: user message, persona, system prompt, prior history, optional temperature and max tokens.
LlmRateLimitException
Domain translation of an HTTP 429 from any provider, raised mid-stream.

Invariants

  • Streaming-First — StreamAsync is the canonical path; CompleteAsync is just a drain so there is one code path.
  • Local-First Default — the default provider is Ollama, so contributors run Scout without paid credentials.
  • Pluggable Everything — the active provider is chosen by configuration; unknown names fail fast at startup.

Hot spots

  • ChatGateway.cs:55 — StreamAsync: validates the request, logs the target, and yields chunks from either the agent or direct path.
  • ChatGateway.cs:253 — BuildSettings: always enables FunctionChoiceBehavior.Auto() so kernel plugins are offered to the model; temperature and max tokens forwarded only when set.
  • ChatGateway.cs:147 & :225 — the HTTP 429 → LlmRateLimitException translation, kept inside a try with the yield outside it.
  • LlmServiceCollectionExtensions.cs:54 — the provider switch; the default arm throws InvalidOperationException for an unknown provider.
  • LlmServiceCollectionExtensions.cs:117 — the embedding generator is resolved straight from the factory, not the shared kernel, to avoid a DI construction cycle through project knowledge.

Configuration

All keys live under Scout:Llm. The active provider block must be populated; others may be empty.

# appsettings.json (excerpt)
"Scout": {
  "Llm": {
    "Provider": "Ollama",
    "Ollama": {
      "Endpoint": "http://localhost:11434",
      "Chat": { "Model": "llama3.1" },
      "Embeddings": { "Model": "nomic-embed-text" }
    }
  }
}

Testing footprint

  • Unit tests in tests/Scout.Llm.Tests/ cover request validation, the 429 translation, settings construction, and provider selection. Assertions use Shouldly per the testing convention.
  • Boundary failure tests (provider timeout, 5xx) are required before any change here per Production Readiness.
