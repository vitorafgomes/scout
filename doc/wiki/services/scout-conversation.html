Scout.Conversation

The platform-agnostic conversation core: it owns the streaming drive loop once, renders through a thin per-platform sink, and replays bounded per-channel/per-user history so the bot remembers across turns.

service statusactive version 1.0 date 2026-06-01 sources src/Scout.Conversation/; vault 2026-05-29-conversation-core-streaming-sink.md

Responsibility

Scout.Conversation is the transport-agnostic heart of the chat pipeline. It takes a normalized inbound ChatMessage from whatever adapter is active, routes it to a streaming response, and pumps that response into a channel-bound sink — all in one shared drive loop so every new platform reuses the same throttling, truncation, finalization, and rate-limit behaviour. Ownership is inverted relative to the archived design: adapters provide a sink, the core drives it.

It also owns short-term conversation memory: a bounded, in-process history keyed by channel + user, replayed into each request and written back only when a turn completes cleanly. It does not talk to any model directly — it consumes Scout.Llm's IChatGateway, never a Semantic Kernel type — and it registers no adapter; the host adds exactly one (Discord today) on top.

Public contract

  • IConversationRouter — Route(ChatMessage) -> ChatResponse. Always non-null and always streaming; v1 has a single responder.
  • IResponseSink — the cumulative outbound contract: BeginAsync, UpdateAsync (full cumulative text, never a delta), and exactly one terminal CompleteAsync or FailAsync. Adapters implement this; the core never sees a channel handle.
  • IChatAdapter — inverted adapter: StartAsync(handler, ct) normalizes platform events to ChatMessage, builds a sink bound to the originating channel only, and invokes the handler.
  • ConversationConductor.HandleAsync — the adapter-facing handler that wires route + pump together inside an OpenTelemetry activity and guarantees failures surface through the sink, never as a host crash.
  • IConversationMemoryStore / IConversationKeyProvider — load a bounded oldest-first history snapshot and atomically append a completed user/assistant pair.
  • AddScoutConversation(services, configuration) — composition root: registers router, pump, conductor, key provider, and the in-memory store. Registers no adapter.

Key types

ConversationConductor
sealed handler matching Func<ChatMessage, IResponseSink, CancellationToken, Task>. Routes, pumps, wraps in a conversation.handle activity, and converts any routing/lifecycle failure into a sink FailAsync.
LlmStreamingRouter
IConversationRouter for v1. Defers all work (skill selection, history load, request build, streaming) to enumeration; consumes IChatGateway.StreamAsync, never the raw chat-completion service.
StreamPump
Transport-agnostic drive loop. Owns the response lifecycle once: opens the sink, accumulates a cumulative buffer, throttles interim updates, then issues a single terminal Complete or Fail. Contains no platform-specific code.
IResponseSink / RenderCapabilities
Cumulative outbound contract plus the capability record (FineGrainedEdit, MaxBodyLength, SupportsInterimCitations, EditIntervalFloor, MaxResponseDuration) that the pump uses to adapt cadence and length without knowing the platform.
ChatMessage / ChatResponse / Citation
Chat-transport DTOs. ChatMessage is validated at construction; ChatResponse is streaming-first (IAsyncEnumerable<string> tokens + non-null citations) with a FromText single-element fallback.
InMemoryConversationMemoryStore
RAM-only, per-conversation history over a ConcurrentDictionary with a per-entry lock and lazy TTL eviction. Explicitly NOT a durable write boundary — history is lost on restart by design.

Invariants

  • Streaming-First — ChatResponse.Tokens is always an IAsyncEnumerable<string>; the pump's await foreach is the single code path, and FromText models a complete string as a one-element sequence.
  • No Executive Writes — the sink is bound to the originating channel only and exposes no API to post elsewhere; the descriptive-write boundary is enforced by construction. The memory store is RAM-only and persists nothing.
  • Pluggable Everything — the core registers no adapter; the host plugs in exactly one IChatAdapter, and the sink contract is shaped against the least-capable platform (Teams) so any adapter fits.
  • Shouldly-Only Tests — the conversation test suite asserts with Shouldly and uses FakeTimeProvider for deterministic cadence and TTL.

Hot spots

  • StreamPump.cs:48 — RunAsync: the single drive loop. Begin, the await foreach over ChatResponse.Tokens, cumulative buffering, throttled interim updates, then exactly one terminal call.
  • StreamPump.cs:106 — the LlmRateLimitException arm: a model 429 finalizes via CompleteAsync with a friendly user-facing message (logged at info, no stack), distinct from the generic mid-stream failure that goes to FailAsync (StreamPump.cs:120).
  • StreamPump.cs:140 — LinkTimeout: a TimeProvider-backed CTS folds min(OverallTimeout, MaxResponseDuration); FailAsync deliberately runs on CancellationToken.None so finalization is not torn down by the same cancellation.
  • LlmStreamingRouter.cs:65 — Route returns immediately; all work is deferred to StreamWithToken so the gateway is not invoked until the pump enumerates.
  • LlmStreamingRouter.cs:103 — write-back guard: history is appended only after the stream completes without exception or cancellation and produced non-empty text, so a failed/partial turn never poisons history.
  • InMemoryConversationMemoryStore.cs:51 & :72 — per-entry lock (entry.Gate) on both Load and Append so same-key access serializes while different keys never contend; FIFO pair-eviction at InMemoryConversationMemoryStore.cs:84.
  • ConversationConductor.cs:61 — the catch-all that routes a routing/sink failure through sink.FailAsync (and swallows a secondary sink failure) rather than crashing the host.
  • ConversationKeyProvider.cs:18 — channel + user joined with the ASCII unit separator (U+001F) so neither id can collide into the other's slot.

Configuration

Router options bind from Scout:Conversation; memory options from Scout:Conversation:Memory. With Memory:Enabled false the router neither loads nor writes history and the pipeline stays behavior-neutral. 

# appsettings.json (excerpt)
"Scout": {
  "Conversation": {
    "SystemPrompt": "You are Scout, a read-only chatops assistant. Answer concisely.",
    "Memory": {
      "Enabled": true,
      "MaxTurns": 6,
      "MaxReplayedChars": 8000,
      "IdleTtl": "00:30:00"
    }
  }
}

Testing footprint

  • Unit tests live in tests/Scout.Conversation.Tests/: StreamPumpTests and StreamPumpFailureTests (cadence, truncation, 429-to-Complete, mid-stream Fail, timeout, cancellation), InMemoryConversationMemoryStoreTests (FIFO eviction, char budget, TTL, concurrent same-key append), LlmStreamingRouterMemoryTests (turn-2 replay, failed-stream no-poison, disabled neutrality, cross-user isolation), and ConversationConductorTests.
  • Determinism comes from injecting FakeTimeProvider into the pump and store; assertions use Shouldly per the testing convention.
  • The streaming gateway and each platform sink are external boundaries: failure-injection tests (gateway-throws-mid-stream, 429 retry, cancellation, timeout) are mandatory per Production Readiness.
