Scout.Adapter.Teams

The Microsoft Teams chat adapter: a webhook-push IChatAdapter that translates inbound Bot Framework activities into Scout chat messages and streams answers back as a sequence of typing activities the Teams client stitches into one bubble.

service statusactive version 1.0 date 2026-06-01 sources src/Scout.Adapter.Teams/; README

Responsibility

Scout.Adapter.Teams binds Scout's platform-agnostic conversation core to Microsoft Teams. It implements IChatAdapter on top of the Microsoft Bot Framework: it translates each inbound Teams Activity into a Scout ChatMessage, builds an IResponseSink bound to the originating conversation, and invokes the handler supplied by Scout.Conversation.

The defining wrinkle is the transport shape. Discord and Slack open a socket and pull events; Teams is webhook-push and has no outbound connection of its own. The Azure Bot Service relays each inbound activity as an HTTPS POST to a messaging endpoint the host exposes (for example POST /api/messages), so there is nothing to "connect" in StartAsync. The adapter only arms a lifetime token and stores the handler; the live webhook host then forwards each turn into ProcessActivityAsync, the unit-testable seam between the HTTP host and this project.

It does not own conversation state, routing, or the LLM call — those belong to Scout.Conversation and Scout.Llm. It also deliberately does not register the Bot Framework webhook plumbing (the CloudAdapter, the IBot, and the ASP.NET endpoint), because that needs real Azure; this project wires only the adapter, translator, and sink seam.

Public contract

  • TeamsChatAdapter — the IChatAdapter implementation. Name returns "Teams"; StartAsync arms the lifetime token and stores the handler; StopAsync trips the token so in-flight turns unwind; ProcessActivityAsync(turnContext, ct) is the per-turn entry point the webhook host calls.
  • TeamsMessageTranslator — TryTranslate(inbound, out chatMessage): a pure decision over an InboundTeamsMessage. No Bot Framework types cross its public boundary, so the accept/ignore logic is testable without constructing SDK primitives.
  • AddTeamsAdapter(services, configuration) — the composition root. Binds TeamsOptions from Scout:Adapters:Teams and registers the adapter as an IChatAdapter only when an App id is present; otherwise it is a clean no-op.
  • ITeamsActivitySender — the transport seam the sink sends through. Production binds it to an ITurnContext; tests bind a delegate via DelegateTeamsActivitySender.

Key types

TeamsChatAdapter
sealed IChatAdapter/IDisposable. Arm/stop lifecycle plus the ProcessActivityAsync turn seam; per-turn work runs under try/catch linked to the lifetime token.
TeamsAdapterLifecycle
internal sealed start/stop state with a lifetime token that trips on stop. Re-startable after stop (webhook-push has no socket to re-login); start while running is rejected.
TeamsMessageTranslator
Pure partial translator. Skips non-messages, bot self-echoes, and empties; strips the bot's own <at> mention; requires an explicit mention in group chats, implicit in 1:1.
InboundTeamsMessage
record projection of the fields the translator needs, so the translator stays pure and trivially testable while the live adapter maps a real Activity into it.
TeamsResponseSink
IResponseSink over the Teams streaming protocol: informative typing → cumulative streaming typing → one final message. Owns its own 429 backoff and 403 fallback.
TeamsTransportException
Transport-neutral failure carrying just status + Teams error code, so the sink reacts to IsRateLimited (429) and IsContentStreamNotAllowed (403) without SDK types.
TeamsOptions
Settings bound from Scout:Adapters:Teams: AppId, AppPassword, TenantId. Secrets are injected, never committed.

Invariants

  • Pluggable Everything — Teams is one interchangeable IChatAdapter alongside Discord and Slack; the host loads it only when configured, otherwise AddTeamsAdapter is a no-op.
  • Streaming-First — the sink streams a growing bubble via cumulative typing activities; UpdateAsync always carries the full cumulative text, never a delta.
  • No Executive Writes — a reply is sent only into the conversation the message came from (the descriptive-write boundary); the sink is bound to the originating ITurnContext and writes nowhere else.
  • Secrets Never Committed — AppPassword and the App id are injected via environment variables or User Secrets / Key Vault; TeamsOptions documents this and the adapter never logs them.

Hot spots

  • TeamsChatAdapter.cs:58 — the self-gate: the constructor throws ArgumentException when AppId is empty, so an adapter that reached construction is always configured.
  • TeamsChatAdapter.cs:107 — ProcessActivityAsync: the seam the webhook host calls per turn; reads the handler + lifetime token atomically, links a per-turn token, translates, and dispatches.
  • TeamsChatAdapter.cs:140 — the sink is built with streamingSupported: !inbound.IsGroup, so group chats and channels render final-only.
  • TeamsChatAdapter.cs:160 — BuildSink: binds the send to turnContext.SendActivityAsync and maps the SDK's ErrorResponseException to TeamsTransportException via TeamsErrorMapper.
  • TeamsAdapterLifecycle.cs:38 — TryGetLifetimeToken: reads the running guard and token under one lock so a turn racing StopAsync sees a clean shutdown rather than the LifetimeToken throw.
  • TeamsMessageTranslator.cs:54 — the group rule: a group/channel message is accepted only when it mentions the bot, mirroring Discord's guild rule; 1:1 chats are implicitly addressed.
  • TeamsMessageTranslator.cs:107 — ProjectInbound: maps a real Activity into InboundTeamsMessage, deriving IsGroup from the conversation account flag or groupChat/channel type.
  • Streaming/TeamsResponseSink.cs:247 — SendWithResilienceAsync: a 429 backs off once on the injected clock and retries; other transport errors propagate to the caller.
  • Streaming/TeamsResponseSink.cs:235 — HandleContentStreamNotAllowed: a 403 ContentStreamNotAllowed cancels streaming for the rest of the run and lets one final message carry the answer.
  • Streaming/TeamsResponseSink.cs:287 — the final activity carries a final streaminfo entity only when a stream was actually opened and not canceled, keeping the streamSequence monotonic.
  • TeamsServiceCollectionExtensions.cs:36 — the registration self-gate: an empty AppId short-circuits before any service is added, so an unconfigured host still starts.

Configuration

All keys live under Scout:Adapters:Teams (constant ConfigSection in TeamsServiceCollectionExtensions). An empty AppId disables the adapter. Secrets are injected via environment variables (double-underscore separator) or User Secrets / Key Vault and are never committed or logged. 

# appsettings.json (excerpt) — values injected, not committed
"Scout": {
  "Adapters": {
    "Teams": {
      "AppId": "",
      "AppPassword": "",
      "TenantId": ""
    }
  }
}
SCOUT__ADAPTERS__TEAMS__APPID SCOUT__ADAPTERS__TEAMS__APPPASSWORD SCOUT__ADAPTERS__TEAMS__TENANTID

AppPassword and TenantId may be empty for a single-tenant or user-assigned managed-identity bot, or for a multi-tenant bot respectively. Live hosting needs the Bot Framework webhook plumbing — a CloudAdapter, an IBot forwarding turns to ProcessActivityAsync, and a POST /api/messages endpoint — which requires real Azure and is intentionally not wired by this project.

Testing footprint

  • Unit tests live in tests/Scout.Adapter.Teams.Tests/ (granted via InternalsVisibleTo in the csproj). Assertions use Shouldly per the testing convention.
  • The translator is a pure class over InboundTeamsMessage, so accept/ignore rules (non-message, bot self-echo, empty-after-strip, group no-mention, mention stripping) are exercised without any SDK primitive.
  • The lifecycle is extracted so start/stop, the re-start-after-stop allowance, and the TryGetLifetimeToken race are unit-testable without an HTTP host.
  • The sink sends through ITeamsActivitySender, so the full streaming lifecycle — cumulative-text invariant, 429 backoff/retry on a fake clock, 403 ContentStreamNotAllowed fallback, group final-only mode, and citation rendering — is tested without Azure or a network, satisfying Production Readiness boundary-failure coverage.
