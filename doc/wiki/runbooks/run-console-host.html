Run the Console Host

Run this when you want Scout live in chat: Scout.Host.Console starts the configured chat adapters and the conversation worker so messages on Discord, Slack, or Teams reach the LLM.

runbook statusactive version 1.0 date 2026-06-01 sources README Running the Console Host

When to run this

Scout.Host.Console is the main runnable host. Start it when you want the bot answering questions in a chat platform: it boots the configured chat adapters and the conversation worker, then keeps running until you stop it. This is the long-running, interactive mode — distinct from the one-shot index <project> command, which indexes a configured project and exits without starting any adapters (see Index a Project).

Because every adapter is self-gating, you do not have to configure all three platforms. Provide credentials for the platforms you want, leave the rest empty, and the host starts only the adapters whose credentials are present.

Preconditions

  • .NET SDK 10.0.100 or later is installed. The version is pinned in global.json with rollForward: latestMinor.
  • The solution builds. If you have not built yet, follow Build & Test first.
  • An LLM provider is reachable. With the default Ollama provider, Ollama must be running locally at http://localhost:11434 (see Local Models).
  • At least one chat adapter has credentials — otherwise the host starts with no adapters. Adapters self-gate on: Discord Scout:Adapters:Discord:BotToken, Slack Scout:Adapters:Slack:BotToken, Teams Scout:Adapters:Teams:AppId.
  • Secrets are supplied out-of-band — never committed. Use .NET User Secrets or environment variables in development; inject via environment variables or a secrets manager in production (see Secrets Handling).

Steps

1. Configure providers and credentials

The host reads configuration from src/Scout.Host.Console/appsettings.json and applies any environment-variable overrides on top of it. All keys live under the Scout: prefix. A minimal local-first setup keeps the default Ollama provider and supplies one adapter token: 

# src/Scout.Host.Console/appsettings.json (excerpt)
"Scout": {
  "Llm": {
    "Provider": "Ollama",
    "Ollama": {
      "Endpoint": "http://localhost:11434",
      "Chat": { "Model": "llama3.1" },
      "Embeddings": { "Model": "nomic-embed-text" }
    }
  },
  "Adapters": {
    "Discord": { "BotToken": "" },
    "Slack":   { "BotToken": "", "AppLevelToken": "" },
    "Teams":   { "AppId": "", "AppPassword": "", "TenantId": "" }
  }
}

2. Override secrets at run time (do not commit them)

Keep tokens out of the tracked appsettings.json. Environment variables override file values and use a double underscore (__) as the section separator, mapping each : in a configuration key to __: 

# environment-variable overrides (double-underscore separator)
Scout__Adapters__Discord__BotToken=<discord-bot-token>
Scout__Adapters__Slack__BotToken=xoxb-...
Scout__Adapters__Slack__AppLevelToken=xapp-...
Scout__Adapters__Teams__AppId=<microsoft-app-id>

The same pattern overrides any key — for example Scout__Llm__Provider to switch providers, or Scout__Llm__OpenAI__ApiKey for a cloud provider. In development you may instead use .NET User Secrets, which are layered the same way.

3. Start the host

Run from the repository root:

# start adapters + conversation worker (long-running)
dotnet run --project src/Scout.Host.Console

The process stays in the foreground. Each adapter is self-gating: if its credentials are absent the adapter is skipped and the host continues with the remaining ones — a missing token disables one platform but does not stop startup.

Verification

  • The process starts and remains running (it does not exit immediately like the one-shot index command).
  • Adapters with credentials come up; adapters without credentials are skipped rather than failing the host.
  • Send a message to the bot in a configured platform and confirm a streamed reply arrives. Responses stream token-by-token, per the Streaming-First invariant.
  • If you switched providers, confirm the active provider name was picked up from Scout:Llm:Provider (an unknown name fails fast at startup, per Pluggable Everything).

Rollback

There is no persistent state to undo for the run itself — conversation history is per-channel, per-user and held in memory by Scout.Conversation, so it is discarded when the process stops. To take Scout off a chat platform, stop the foreground process (Ctrl+C) and clear or blank that platform's token; on the next start the adapter self-gates off. Any project knowledge written during a separate index run is independent of this host process.
