Build & Test

Run this when you need a clean local verification of the Scout backend — before opening a PR, after a fresh clone, or to reproduce a CI failure with the exact commands CI uses.

runbook statusactive version 1.0 date 2026-06-01 sources README Build and Test; global.json

When to run this

  • After a fresh clone, or when switching branches, to confirm the backend solution restores, compiles, and tests green.
  • Before opening a PR — the test pass is the minimum gate for the backend.
  • To reproduce a CI failure locally: these are the exact commands run by .github/workflows/ci.yml, so a local pass should match CI.

This runbook covers the backend solution only (Scout.slnx, everything under src/). The Electron Desktop UI under ui/ has its own toolchain (Bun) and its own CI pipeline (.github/workflows/ui-ci.yml); see Desktop Packaging for that path.

Preconditions

  • .NET SDK 10.0.100 or later installed. The version is pinned in global.json with rollForward: latestMinor, so a newer 10.0.x SDK is accepted but an older one is not.
  • You are at the repository root, where Scout.slnx and global.json live. Running dotnet here lets global.json select the SDK.
  • Network access for the restore step, so NuGet can pull packages on a cold cache.
  • No secrets are required to build or test. Tests do not call live providers; adapters and plugins are self-gating and stay disabled without credentials.

Confirm the SDK that global.json resolves before you start:

# from the repo root
dotnet --version
# expect 10.0.100 or a later 10.0.x (latestMinor roll-forward)

Steps

Run the three commands in order, from the repository root. These match the README "Build and Test" section verbatim.

  1. Restore packages. Pulls every NuGet dependency for the solution so the next steps run offline. 
    dotnet restore
  2. Build in Release, without re-restoring. --no-restore reuses step 1, and --configuration Release matches CI. 
    dotnet build --configuration Release --no-restore
  3. Run the test suite against the built output. --no-build reuses step 2, so this fails fast if step 2 did not run or is stale. 
    dotnet test --configuration Release --no-build

The flags are intentional: each step layers on the previous one (restore → build → test) so work is never repeated and a mismatch surfaces immediately. Tests assert with Shouldly per the testing convention.

Verification

  • dotnet restore finishes with no error and reports the restored projects.
  • dotnet build --configuration Release --no-restore reports Build succeeded with zero errors.
  • dotnet test --configuration Release --no-build reports all tests passed and a zero exit code.
  • A green local run on the same SDK should mirror CI, since .github/workflows/ci.yml runs these same three commands.

Only src/ is part of the build. Code under src/old/ and tests/old/ is deprecated legacy code and is excluded, so failures there are not relevant to this runbook.

Rollback

Build and test are read-only operations: they do not mutate source, configuration, or any external system, so there is nothing to undo. If a run leaves stale build artifacts behind, clear them and start the sequence again from step 1. 

# discard build outputs, then re-run the sequence
dotnet clean --configuration Release
dotnet restore
