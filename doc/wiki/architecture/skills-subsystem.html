Skills Subsystem

Skills are markdown process guides that nudge Scout's behavior. The subsystem reaches the model through two independent paths over the same files: an embedding-driven auto-injection path that splices the most relevant skill into the per-turn system prompt, and a tool-based list/load path the model can call itself. Both load lazily, never throw, and degrade to "no skills" on any failure.

What a skill is

A Skill is a single markdown file with a --- frontmatter fence carrying required name and description keys, a closing fence, then a non-empty body. SkillFileLoader parses it into the record Skill(Name, Description, Body, SourcePath) (Skill.cs:15). The description is the retrieval signal — it gets embedded and cosine-matched against the user message — while the body is the instruction text that ends up in the prompt. Malformed files (no fences, missing keys, empty body) are skipped with a warning; parsing never throws (SkillFileLoader.cs:63).

Files live under src/Scout.Skills/skills/ and are copied to the build output, where they are resolved relative to AppContext.BaseDirectory unless an absolute Directory is configured (SkillSelector.cs:123, SkillCatalog.cs:58). The catalog is derived from the Superpowers project (MIT) per SKILLS-ATTRIBUTION.md.

Two surfaces over one catalog

The same markdown files back two registrations, wired in AddScoutSkills when Enabled is true (SkillsServiceCollectionExtensions.cs:43):

Auto-injection (embedding path) — ISkillSelector → SkillSelector. Embeds skill descriptions, ranks them against the message by cosine similarity, and returns the top matches. Needs the embedding generator. Used by the conversation router to compose the system prompt.
Tool path (model-driven) — ISkillCatalog → SkillCatalog, fronted by SkillsPlugin. Exposes list_skills and load_skill as Semantic Kernel functions the model can call. Embedding-free, so the shared kernel can aggregate it without re-entering the embedder.

The split is deliberate: the tool path depends only on the loader and options (ISkillCatalog.cs:9), never on the embedding generator. Because the Scout.Knowledge embedder is itself built from the shared kernel, letting the kernel-aggregated SkillsPlugin touch the embedder would close a DI construction cycle. The embedding-free catalog breaks it.

Selection pipeline (embedding path)

The index is built once, lazily, on the first SelectAsync call and cached for the process lifetime, so DI build and host startup do zero file I/O, embedding, or network work (SkillSelector.cs:42).

→
cosine vs. index
VectorMath.Cosine
→

  • Empty/whitespace messages short-circuit to no skills (SkillSelector.cs:53).
  • The index embeds descriptions only today (SkillSelector.cs:100); the message is embedded as the query (SkillSelector.cs:66).
  • Each candidate is scored with VectorMath.Cosine, which returns 0 on length mismatch or zero-magnitude vectors (VectorMath.cs:15).
  • Candidates below SimilarityThreshold are dropped; the rest are ordered by descending score and capped at TopN (SkillSelector.cs:71).
  • Any exception in selection or index build is logged and treated as "no skills" — the conversation is never poisoned (SkillSelector.cs:81, :114).

Prompt composition

Selected skills are folded into the system prompt by SkillPromptComposer.Compose: the base prompt is returned unchanged when nothing is selected, otherwise each skill body is appended under a # Relevant skill: <name> delimiter (SkillPromptComposer.cs:18).

Known weakness: the delimiter uses a Markdown # heading that collides with the skills' own headings, and the bodies are injected verbatim with no framing. The roadmap's move F replaces it with a structured <skills><skill name="…"> wrapper plus a budget and dedup-by-name once more than one skill can be injected.

Tool path

SkillsPlugin exposes two Semantic Kernel functions over the embedding-free catalog. Every call returns a clean, non-empty string and never throws back into the kernel (SkillsPlugin.cs:14):

list_skills
Returns one name: description line per skill, or "No skills available." when the catalog is empty (SkillsPlugin.cs:27).
load_skill(name)
Case-insensitive exact-name lookup returning the skill body, or a clean not-found message pointing back at list_skills (SkillsPlugin.cs:40).

The plugin is registered as a KernelPlugin named "Skills" via KernelPluginFactory.CreateFromObject (SkillsServiceCollectionExtensions.cs:63), which the shared kernel aggregates for function-calling. See Semantic Kernel Plugin.

Configuration

All keys bind from Scout:Skills (SkillsOptions.cs:11); code defaults make the feature work with no section present.

# appsettings.json (excerpt)
"Scout": {
  "Skills": {
    "Enabled": true,
    "Directory": "skills",
    "TopN": 1,
    "SimilarityThreshold": 0.55
  }
}
  • Enabled (default true) — when false, only NoOpSkillSelector is registered and the tool plugin is not aggregated (SkillsServiceCollectionExtensions.cs:67, NoOpSkillSelector.cs:7).
  • Directory (default skills) — relative paths resolve under AppContext.BaseDirectory (SkillsOptions.cs:20).
  • TopN (default 1) — maximum skills injected per turn (SkillsOptions.cs:23).
  • SimilarityThreshold (default 0.55) — minimum cosine score to select (SkillsOptions.cs:28).

The gate: auto-injection was a silent no-op

The improvement roadmap's critical finding is that, on the shipped config, the composed prompt never reached the model when a project was configured. With a project active, ChatGateway routes through the agent path, which invoked the agent with options: null and never referenced request.SystemPrompt. The base persona plus the injected skill body — both built into SystemPrompt — were discarded every turn; the response used only the agent's own Instructions. Embedding-based skills auto-injection was effectively dead whenever a project was set.

Gate fix (do first). Pass request.SystemPrompt into the agent invocation via AdditionalInstructions, guarding null/empty so the agent's own Instructions still apply. This is the hard dependency for the entire auto-inject roadmap and is shared with the one-agent / dynamic-persona routing direction.

The right lever per model

The roadmap splits work by which model drives each decision, so effort lands where it pays off:

weak embedder (nomic-embed-text) drives selection task prefixes · name-aware indexing · threshold calibration
capable chat model drives everything downstream LLM classification fallback · calling list_skills/load_skill · absorbing larger bodies

Selection quality is therefore tuned at the embedder (asymmetric search_query: / search_document: prefixes, embedding name+description rather than description alone, recalibrating the 0.55 threshold once per-turn scores are logged), while richer behaviors (a system-prompt clause telling the model the tools exist, an LLM-driven selection fallback) depend on the capable model and on the gate fix.

Improvement roadmap (ordered)

A. Gate fix — agent path honors SystemPrompt via AdditionalInstructions. Do first; unblocks everything below.
D. Card, not full body — inject a condensed Name+Description card with a "load via load_skill" pointer; load_skill becomes the single source of the multi-KB body, resolving the auto-inject / tool double-surfacing.
Logging — log per-turn selection (top skill, score, threshold, runner-up; names and scores only, never message text). Prerequisite evidence for retuning the threshold and TopN.
C. Descriptions as retrieval keys — rewrite descriptions as embedding keys (remove literal quotes such as the one in brainstorming.md:3), sequenced with name+description indexing and prefixes.
B. Body rewrite — re-author bodies for read-only chatops, dropping write/exec/subagent imperatives that contradict Scout's persona; update attribution to "adapted from".
E. LLM-driven fallback — cheap embedding pre-filter, then one classification call in the grey zone, built as an ISkillSelector decorator to avoid the kernel-to-embedder DI cycle; gated by config.
F. Structured delimiter — replace #-heading framing with <skills> wrapper plus byte budget and dedup-by-name; matters once TopN > 1.
G. Lifecycle — collapse the two directory/file-load implementations into one shared store, then operator-triggered hot reload. Lowest payoff; do last.

Sequencing: A (gate) first, then D (card mode) to stop dumping multi-KB bodies, then logging to get real scores, then C plus name/description indexing and prefixes tuned from those scores, then B (body rewrite); E when selection robustness is wanted. Full detail in the Skills Subsystem roadmap.

Why skills, not multi-agent routing

A companion analysis asked whether Scout should grow a specialized agent per request type via multi-agent orchestration. The verdict is a false binary: the recommended middle is one agent, many personas, deterministic embedding routing — reusing the very SkillSelector / VectorMath.Cosine machinery the skills subsystem already provides. A "specialist" becomes a skill-like markdown record whose description is the routing signal.

  • Local model can't pay for handoff orchestration — multi-agent triage turns routing into a tool-calling problem and stacks nested inferences, exactly where open-weight models fall off. Embedding routing moves the decision out of the model into a tunable cosine threshold.
  • Latency on one GPU punishes hops — the one-agent path adds zero extra LLM calls beyond a near-free local embedding.
  • Maximum reuse — the selector, cosine math, file loader, and prompt composer are already built; no new packages, no prerelease orchestration runtime.

Resilience & observability

  • Every public path returns empty or a clean string on failure: the selector (SkillSelector.cs:81), the loader (SkillFileLoader.cs:31), and the plugin functions (SkillsPlugin.cs:32) all degrade gracefully so skills can never break a conversation.
  • Index and catalog build lazily under LazyThreadSafetyMode.ExecutionAndPublication, so files load exactly once on first use (SkillSelector.cs:44, SkillCatalog.cs:31).
  • Per-turn selection logging is a roadmap item, not yet shipped — without it the threshold and TopN cannot be retuned from evidence. OTel spans/metrics are dropped today (no exporter registered); ILogger works, the Meter path does not.
