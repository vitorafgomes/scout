Desktop Provisioning UI

Scout Desktop is the Electron desktop shell that lowers the install friction of the read-only chatops bot: it walks a user through provisioning a bot per chat platform, discovers local inference backends and downloads models into them, and supervises the .NET worker as a child process. It is a thin operator console around the same Scout runtime, not a second product.

knowledge statusactive version 1.0 date 2026-06-01 sources vault 02-architecture/electron-provisioning-ui.md, desktop-models-system.md; ui/README.md

Why it exists

The original install story for a contributor was five manual steps per platform: create the app in a developer portal, enable the bot and copy the token, build an OAuth2 install URL, drop the token into configuration, and run the worker. For an OSS chatops bot chasing wide adoption, that is high friction — especially for a user who wants to "just try it" on Discord, Slack, and Teams side by side.

The Desktop UI collapses that to a wizard-with-deep-links. It cannot be true one-click: the feasibility study established that end-to-end automated provisioning is only possible on Slack (via the App Manifest API), that Discord is blocked on a human-only Developer Portal step, and that Teams requires tenant-admin policy and a public HTTPS endpoint that conflicts with running locally. The wizard automates everything that policy permits and deep-links the rest.

Detection is polish, not a gate. A chat client being installed only hints that the user might use that platform; provisioning a bot never requires the desktop client, since a web session is enough for all three. Detection surfaces a "detected on this machine" badge rather than blocking the flow.

Per-platform feasibility

The line between automatable and manual cuts differently per platform. This shapes every wizard.

PlatformAutomatableIrreducibly manualRunning mode
Discord OAuth2 install URL construction; authorize → install to guild via the local callback. App + Bot creation in the Developer Portal; token copy-paste; intent toggles. No public creation API, and the ToS forbids scraping the portal. Gateway WebSocket (outbound). No inbound endpoint.
Slack App creation via apps.manifest.create; workspace install; bot + app-level token capture. One-time app configuration token generated on api.slack.com. There is no OAuth flow that mints it. Socket Mode WebSocket (outbound). No public HTTPS endpoint needed.
Teams Manifest publish + install via Graph (with admin-consented scopes). Azure Bot Service + Entra app registration; tenant "Upload custom apps" toggle. Deferred for V1. HTTPS webhook — structurally at odds with local-only Scout.

Slack is the closest to one-click (~4 clicks), Discord is a deep-link wizard (~6 clicks), and Teams is not a viable end-user install flow for V1 and is kept as a future topic.

Stack

The renderer framework is fixed to Angular — no React, Vue, Svelte, or Solid anywhere in Scout's web surfaces (see the Angular web-stack ADR). The shipped layers are:

Bun 1.3+ — workspace toolchain: install, scripts, and tests. It is the dev toolchain, not the runtime inside the packaged app.
Electron 41 — desktop shell. Main process in ESM, sandboxed preload bridge.
Angular 21 — renderer with zoneless change detection, Signals-first, standalone components using the new @if/@for control flow.
.NET 10 — the Scout.Host.Worker spawned as a supervised child process.
electron-builder — cross-platform packaging: NSIS, DMG, AppImage, deb.
Bun is the toolchain, not the runtime. The Electron main process owns the lifecycle of the packaged app and executes main.js under Electron's own runtime; the renderer runs in V8 under Chromium. Bun only runs at install/build/test time. Code that assumes bun:* built-ins at runtime would break the moment the app is packaged. Node is not required to build or test the UI — .nvmrc is guidance only.

Process & workspace layout

The UI is a Bun workspace under ui/ split into four packages. The main process resolves the preload from packages/preload/dist/preload.cjs and the renderer from packages/renderer/dist/browser/index.html in production, or http://localhost:4200 when NODE_ENV=development.

Main-process responsibilities

  • Platform detection — thin per-OS modules (detect/windows, detect/macos, detect/linux) exporting predicates like isDiscordInstalled(). Windows uses the uninstall registry, App Paths, AppX packages, and URI schemes; macOS uses Launch Services / Spotlight and bundle ids; Linux walks .desktop files and package managers. No mature cross-platform library exists, so Scout rolls its own.
  • Local OAuth callback — the main process is the redirect target on http://localhost:<port> and exchanges the authorization code for token info. The callback port is fixed (not random) because Discord and Slack require redirect URIs to be pre-registered; http://127.0.0.1:53682/callback is the registered Discord redirect.
  • Token storage — Electron safeStorage (OS keychain: Keychain / DPAPI / libsecret), not the unmaintained keytar. On Linux without a desktop keyring it falls back to plaintext-equivalent encryption; that state must be surfaced to the user as a warning.
  • Worker supervision — the worker is published single-file and self-contained per RID, shipped as extraResource so it lives outside the ASAR archive (binaries inside ASAR cannot be spawned). The main process spawns it with configuration passed via env vars, monitors stdout/stderr, restarts on crash, and terminates it on quit.

Models subsystem (AI Sources → Models)

Beyond bot provisioning, Desktop manages local inference. The post-connect UI separates two layers: AI Sources (where models come from) feeds Models (which model handles which task).

  • AI Sources (/sources) shows Ollama / LM Studio status; a card drills into Manage Downloaded Models (/sources/local-models).
  • The user downloads a model; on first download of a kind it is auto-selected so the user is never left with a downloaded-but-unselected model.
  • Models (/llm, route name kept for compat) then surfaces it for per-task selection (transcription, analysis; translation is "coming soon").

LocalModelsStore (providedIn: 'root') is the single source of truth, persisted to localStorage['scout:local-models']. It tracks downloaded catalog ids and the selected model per kind. The static catalog in core/local-models.catalog.ts is a frozen array of LocalModelCatalogEntry records — Whisper GGML variants (transcription) and Qwen / Gemma Ollama models (analysis). LlmComponent, LlmConfigStore, and TranscriptionConfigStore are orphan code pending a cleanup PR.

Download flow (Ollama example)

Downloading Qwen 2.5 3B maps the catalog id to an Ollama tag, streams the pull over IPC, and reconciles store state:

onDownload('qwen-3-vl-2b') ollamaTagFor → 'qwen2.5:3b' bridge.llmPullOllamaModel(endpoint, tag, requestId) main: ensureOllamaIdentity() POST /api/pull (stream) per-chunk NDJSON → pullOllamaProgress event finishDownload → store.markDownloaded (auto-select if first of kind)

Whisper downloads follow the same shape: whisperVariantFor resolves the GGML variant, the main process streams the Hugging Face file into a .partial, derives progress from Content-Length (capped at 99), then renames to the final .bin and emits 100.

The read-only invariant in the renderer

Scout's no executive writes rule reaches all the way into the desktop shell. Every IPC channel either reads remote APIs the user runs on their own machine, or writes only to the user's own filesystem — nothing mutates an external service.

  • Ollama and Whisper models live on the user's own disk; nothing leaves the machine through these handlers.
  • External URL navigation (Download Ollama, Download LM Studio) goes through appOpenExternal, which validates against a main-process allow-list before calling shell.openExternal.
  • Each write channel carries a justification comment in the IPC contract test, asserted against the allow-list.

Build, test & packaging

  • Install & dev — bun install from ui/; dev runs the Angular dev server (HMR on 4200) in one terminal and the built preload + main under Electron in another.
  • Test — bun run test covers shared + main + preload + renderer; .NET tests run separately via dotnet test Scout.slnx.
  • Package — bun run dist[:linux|:mac|:win] emits artifacts under ui/build/dist/. AppImage is always produced on Linux builds — a release invariant. All artifacts in-repo are UNSIGNED and must not be distributed as official releases until signing and notarisation are set up.
  • CI — .github/workflows/ui-ci.yml runs on Ubuntu, macOS, and Windows for every push to main and every PR touching ui/** or the .NET worker: lint, typecheck, test, publish the worker binary, package unsigned artifacts.

What is not built yet

  • Actual transcription / inference — downloads are real, but the .NET worker does not yet load these files.
  • The worker reading LocalModelsStore.selected on spawn; it still pulls llm.* keys from the vault, decoupled from this screen.
  • Cloud providers (the five cards on the right of AI Sources).
  • Teams provisioning — deferred until clear user demand, given the Azure subscription + tenant-admin prerequisites.
