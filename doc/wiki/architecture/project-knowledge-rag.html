Wiki/Architecture/Project Knowledge RAG

Project Knowledge RAG

Ask Scout, in natural language, about a software project — its architecture, business rules, or how something is implemented — and get an answer grounded in that project's real code and in-repo documentation, with citations to the source files. The retrieval-augmented pipeline lives in the Scout.Knowledge project: it chunks a repository, embeds the chunks into a local SQLite-vec store, and exposes search to the model through the Project Expert agent.

knowledge statusactive version 1.0 date 2026-06-01 sources vault 02-architecture/project-knowledge-rag.md, project-knowledge-rag-phase1-plan.md; src/Scout.Knowledge/

What it is

Project Knowledge is a local-first RAG layer on top of the existing Ollama embedding generator from Scout.Llm. There is no external vector service and no dependency on any human knowledge base: each project is self-contained in its own repository, and "docs" means in-repo markdown (README, *.md, *.txt). The vault is the human knowledge base, not a runtime source.

A configured (or auto-discovered) repository is walked, chunked at semantic boundaries, embedded, and stored in a SQLite file. At question time the Project Expert ChatCompletionAgent calls the search_project tool, which embeds the question, runs a per-project cosine search, and returns a citation-tagged context block. The agent composes a grounded, streamed answer and cites the source files. Everything stays read-only — Project Knowledge never mutates the repositories it indexes.

Phase 1 vs. shipped. The original design (vault project-knowledge-rag.md) scoped a knowledge graph, graph-boost retrieval, and incremental file-watch as deferred work; Phase 1 (vault project-knowledge-rag-phase1-plan.md) shipped the index → embed → store → retrieve → cite path. The current code adds two pieces beyond Phase 1: an opt-in file-watch re-indexer (ProjectWatchService) and a metadata-only symbol lookup (find_symbol). The knowledge graph with transitive-closure boost and BM25 + reranking remain roadmap items.

Layers

Agent & plugin — the ProjectKnowledgePlugin exposes search_project, find_symbol, and list_projects as kernel functions; the Project Expert agent is the chat responder that calls them.
Retrieval — ProjectKnowledgeService turns a question into a citation-tagged context string: embed the question, search the store, format the hits.
Resolution & discovery — ProjectResolutionService merges configured projects with repositories auto-discovered under configured roots and lazily indexes a project on first use; ProjectDiscoveryService finds repositories by listing directories only.
Indexing — ProjectIndexer walks the repo, FileChunker chunks each file (Roslyn for C#, line windows otherwise), and chunks are embedded in batches; an opt-in ProjectWatchService re-indexes single files as they change.
Storage — SqliteProjectKnowledgeStore persists ChunkRecord rows in a local SQLite-vec file with cosine similarity over a 768-dim vector.

Indexing pipeline

Indexing is the write side. It runs from the index <project> console subcommand, from lazy first-use resolution, or per file from the watcher. The shape is the same: enumerate, chunk, embed, store.

walk repo
skip bin/obj/.git/node_modules/dist/.vs
→
chunk file
Roslyn AST (C#) or 100-line windows
→
embed batch
context prefix + chunk text → Ollama
→
replace rows
delete project's stale ids, upsert fresh
  • Enumerate. ProjectIndexer recurses the repo and keeps only indexable files. The include/skip predicate is shared so the indexer and the watcher agree on which files count and how relative paths are spelled — code extensions .cs/.ts/.tsx/.js/.jsx/.py/.json/.yml/.yaml, doc extensions .md/.txt, with segments bin obj .git node_modules dist .vs skipped (ProjectFileFilter.cs:10, :20, :27).
  • Chunk. FileChunker parses C# with Roslyn and emits a chunk per method, class, record, and interface declaration with 1-based start/end lines (FileChunker.cs:15). Any non-C# file — or a C# file with no member declarations — falls back to fixed 100-line windows (FileChunker.cs:9, :41, :44), so a file never produces zero chunks.
  • Embed. Each chunk is prefixed with a context line (File: {relPath} | {kind}:{symbol} | lines {s}-{e}) before embedding, then the whole file's inputs are embedded in one batch via IEmbeddingGenerator (ProjectIndexer.cs:105, :69). The dimension must match the model — nomic-embed-text is 768 (ChunkRecord.cs:41).
  • Store. The full project's records are handed to ReplaceProjectAsync (ProjectIndexer.cs:35), which drops the project's existing rows then upserts the new set so chunks for deleted code are removed, not just overwritten (SqliteProjectKnowledgeStore.cs:47).

Per-file failures are isolated: a file that fails to read, chunk, or embed is logged and skipped, and indexing continues with the rest (ProjectIndexer.cs:91).

Retrieval pipeline

Retrieval is the read side, triggered by the model calling search_project during a chat turn.

question
+ project name
→
resolve
known? lazily index on first use
→
embed question
→
cosine top-5
filtered to one project
→
cited context
[path:start-end symbol]
  • Resolve. ResolveAsync looks the name up in the merged project map; an unknown name returns null and a clean "Unknown project" message. A known-but-unindexed project is indexed on first use, and a first-use indexing failure also returns null without throwing (ProjectResolutionService.cs:73).
  • Embed & search. ProjectKnowledgeService.SearchAsync embeds the question and runs store.SearchAsync for the top 5 hits, filtered to the resolved project (ProjectKnowledgeService.cs:46, :11). The store ensures the (possibly empty) collection exists first, so a never-indexed project degrades to zero results instead of a "no such table" exception (SqliteProjectKnowledgeStore.cs:98).
  • Format with citations. Each hit is rendered as a citation header [path:start-end symbol] followed by the chunk content, joined into one block (ProjectKnowledgeService.cs:136). No hits yields a clean "No indexed content found" message naming the project (ProjectKnowledgeService.cs:70).

The tools the model sees

ProjectKnowledgePlugin registers three kernel functions. The plugin is added to the kernel only when at least one project is configured or discovered, so the model never offers a tool that would search an empty index.

search_project
Semantic search over a project's code and docs; embeds the question and returns cited context. The primary grounding path. (ProjectKnowledgePlugin.cs:26)
find_symbol
Metadata-only lookup of a class/method/interface by name — exact matches before partial, no embedding. Preferred for "where is X" questions. (ProjectKnowledgePlugin.cs:41)
list_projects
Lists the project names the agent can search (discovered roots plus explicit items). (ProjectKnowledgePlugin.cs:53)

The Project Expert agent

ProjectExpertAgentFactory builds the single ChatCompletionAgent that responds in chat. Its instructions tell it to use search_project only for project questions, to cite the source files when context grounds the answer, to say so plainly when context does not cover the question, and to answer general or conversational questions directly without the tool (ProjectExpertAgentFactory.cs:11).

  • The persona is rendered through a Semantic Kernel prompt template variable so a per-turn persona can override the default; the variable allows raw content because SK would otherwise HTML-encode characters such as the apostrophe in the instructions (ProjectExpertAgentFactory.cs:67).
  • When projects are configured, the default persona is extended with their names so the model defaults to a real project instead of any example in the tool schema and never invents a project name (ProjectExpertAgentFactory.cs:26, :38).
  • The agent is created with FunctionChoiceBehavior.Auto() so kernel functions are offered to the model on every turn (ProjectExpertAgentFactory.cs:82).

Resolution & discovery

Projects reach the agent two ways, merged into one case-insensitive map built once at construction — explicit items win on name collision (ProjectResolutionService.cs:34):

  • Explicit items — entries under Scout:Projects:Items, each a { Name, RepoPath } (ProjectsOptions.cs:30).
  • Auto-discovery — repositories found directly under each configured root in Scout:Projects:Roots. A child directory counts as a repository when it has a .git entry, a marker file (package.json, go.mod, pyproject.toml, Cargo.toml), or a .sln/.slnx/.csproj (ProjectDiscoveryService.cs:13, :84). Discovery lists directories only — it never reads file contents and never writes (ProjectDiscoveryService.cs:5).

Indexing is deferred to first resolution rather than run at startup, so building the DI graph costs no embedding work (ProjectResolutionService.cs:6).

Incremental file watch (opt-in)

ProjectWatchService is a hosted background service, registered only when Scout:Projects:Watch:Enabled is true and at least one explicit project is configured (KnowledgeServiceCollectionExtensions.cs:94). It does no I/O in its constructor; watchers are armed in ExecuteAsync, so registering it cannot hang startup (ProjectWatchService.cs:48).

  • A FileSystemWatcher per repo enqueues created, changed, deleted, and renamed paths that pass the same indexable filter; a debounce window (default 750 ms) batches them before draining (ProjectWatchService.cs:62, :132, ProjectsOptions.cs:25).
  • On drain, a changed file is re-chunked and re-embedded and ReplaceFileAsync swaps just that file's rows; a deleted file degenerates to a pure delete (ProjectWatchService.cs:189, SqliteProjectKnowledgeStore.cs:73).
  • Per-file re-index failures are logged and skipped; a watcher error triggers a single re-arm attempt before the project stops watching (ProjectWatchService.cs:178, :116).

Storage record

SqliteProjectKnowledgeStore wraps one SQLite-vec collection of ChunkRecord over a local file — no external service (SqliteProjectKnowledgeStore.cs:7). The record carries the id, project (indexed for per-project filtering), repo-relative path, kind (code/doc), symbol, start/end lines, content, and the 768-dim cosine embedding (ChunkRecord.cs:6). 

# appsettings.json (excerpt)
"Scout": {
  "Projects": {
    "Roots": [ "/home/me/WorkSpace" ],
    "Items": [
      { "Name": "cegos-buddy", "RepoPath": "/home/me/WorkSpace/cegos-buddy" }

The vector database file project-knowledge.db is created under the host's local application data directory (KnowledgeServiceCollectionExtensions.cs:22, :102).

Error handling & boundaries

Project Knowledge touches two external boundaries — the embedding generator and the SQLite-vec store — so every entry point degrades to a clean string and never throws into the kernel (per Production Readiness).

  • Unknown or empty project / question → a plain status message, not an exception (ProjectKnowledgeService.cs:51, :57).
  • Embed or search failure → logged warning and a "Could not search project" message; the host stays up (ProjectKnowledgeService.cs:78).
  • Never-indexed project → the store ensures the empty collection exists first, so search and symbol lookup return zero results rather than "no such table" (SqliteProjectKnowledgeStore.cs:98, :118).
  • Per-file index failure → isolated and logged; the rest of the repo still indexes (ProjectIndexer.cs:91).
