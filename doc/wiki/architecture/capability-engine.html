Capability Engine

Skills and personas are the same mechanism — retrieval over a typed markdown library — applied to two layers of context. The Capability Engine collapses them into one index, one embedding pass per turn, and one config section. Each turn it selects the persona that answers (top-1) and the skills that guide the reasoning (top-N), then injects both into the same agent invocation.

knowledge statusactive version 1.0 date 2026-06-01 sources vault 02-architecture/capability-engine-architecture.md, capability-engine-PLAN.md

The unification

A capability is a markdown file with frontmatter type: persona | skill, name, description (the retrieval key), optional tools, and a body. The two types differ only in what they answer and how they are injected:

persona
WHO answers + tool posture. Selected top-1 above threshold, else a general-assistant fallback. Injected through the agent's {{$persona}} template via AgentInvokeOptions.KernelArguments["persona"].
skill
HOW to reason. Selected top-N above threshold. Injected via AgentInvokeOptions.AdditionalInstructions — the path the gate fix opened.

Both share one loader, one embedding index, one cosine pass per turn, one config block, one lifecycle store, and one log line. The engine is a single Lazy<Task<index>> over every capability description; per turn it runs one cosine pass over the single message embedding and partitions the ranked results by type.

Why one engine, not two. The temptation is to clone the skill selector into a parallel persona selector. That would double the embedding indexes, the per-turn embeds, the index-build passes, the config sections, the selectors, and the log lines. Unifying keeps each of those at exactly one.

  • The message is embedded once, prefixed search_query: for the nomic asymmetric scheme.
  • A single cosine pass ranks every capability; the results are partitioned by type.
  • Persona = the highest-scoring persona at or above PersonaThreshold, else the general-assistant fallback (never null).
  • Skills = the type==skill entries at or above SkillThreshold, ranked, capped at SkillTopN.
  • The composer folds persona body into ChatRequest.Persona and the composed skill text into ChatRequest.SystemPrompt.
  • The selector never throws; on any failure it returns the fallback persona and an empty skill list.

Injection at the gateway

The two layers land on the agent through two distinct slots, which is why both must coexist in one invocation. On the agent path, ChatGateway.StreamAgentAsync builds an AgentInvokeOptions only when a persona or system prompt is present: the persona binds via KernelArguments["persona"] (only when non-empty) and the system prompt rides AdditionalInstructions (only when non-empty); both empty leaves options null so the agent's default persona applies.

Persona slot — KernelArguments["persona"] renders into the agent's {{$persona}} template. ChatGateway.cs:200.
Skills slot — AdditionalInstructions = request.SystemPrompt surfaces as a second system message. ChatGateway.cs:203.
Direct path — when no agent is registered, persona then system prompt are joined by a blank line into a single system message. ChatGateway.cs:103.

Foundation already landed

The first two steps of the plan are in main; the unified selector (Step 2) is the remaining work.

Step 0 — gate fix (d61f785). ChatGateway.StreamAgentAsync now passes the composed prompt via AgentInvokeOptions.AdditionalInstructions. Before this the agent path discarded request.SystemPrompt every turn, so skills and persona were dead on the live config. ChatGateway.cs:166.
Step 1 — templated persona agent (behavior-neutral). ChatRequest.Persona exists (ChatRequest.cs:23); ProjectExpertAgentFactory builds a templated agent with Template = "{{$persona}}" and a default Arguments["persona"] equal to today's grounded instructions, so behavior is identical until routing wires in. ProjectExpertAgentFactory.cs:67.
Step 2 — unified capability engine. Refactor SkillSelector into CapabilitySelector, move the markdown library under capabilities/, collapse config into Scout:Capabilities, and swap the router to ICapabilitySelector. Not yet built.

SK 1.77.0 API anchors

The design is pinned to types verified against the resolved Semantic Kernel 1.77.0 assemblies:

  • AgentInvokeOptions — settable KernelArguments and AdditionalInstructions. (ChatCompletionAgentInvokeOptions does not exist.)
  • ChatCompletionAgent(PromptTemplateConfig, IPromptTemplateFactory) constructor.
  • KernelPromptTemplateFactory (in Microsoft.SemanticKernel.Core).
  • PromptTemplateConfig.SemanticKernelTemplateFormat.
  • Agent.Arguments get/set; a per-invoke AgentInvokeOptions.KernelArguments overrides the agent's defaults when instructions are rendered.

Step 2 design — the unified selector

The current Skills subsystem already has the right shape: one lazy index, one cosine pass, never-throws. Step 2 generalises it rather than cloning it.

  • File format. SkillFileLoader gains type (unknown → skill with a warning, so existing files stay valid) and tools parsing, returning a Capability(Type, Name, Description, Body, SourcePath, Tools) with enum CapabilityType { Skill, Persona }. All fence, empty-body, and skip-malformed rules carry over from SkillFileLoader.cs:79 onward.
  • Engine. SkillSelector → CapabilitySelector: one Lazy<Task<index>> (ExecutionAndPublication) over every name+description in one batch embed; SelectAsync embeds the message once, runs one cosine pass, then partitions by type. Returns CapabilitySelection(Capability Persona, IReadOnlyList<Capability> Skills) where Persona is never null. The lazy pattern already guarantees zero file I/O at DI build and host startup (SkillSelector.cs:44).
  • Catalog. SkillCatalog / SkillsPlugin (list_skills / load_skill) filter to Type==Skill so personas are never surfaced as skills.
  • Composer. SkillPromptComposer.Compose(SystemPrompt, selection.Skills) → ChatRequest.SystemPrompt; selection.Persona.Body → ChatRequest.Persona.
  • Router. LlmStreamingRouter swaps ISkillSelector for ICapabilitySelector and forwards both Persona and composed SystemPrompt on the per-turn ChatRequest.
Cycle safety. The selector depends on IEmbeddingGenerator<string, Embedding<float>> resolved from the provider factory, not the shared kernel, and it is not a KernelPlugin. Both choices keep it out of the DI construction cycle that runs through project knowledge.

Configuration

Step 2 collapses the current Scout:Skills block into one Scout:Capabilities section.

Capability library

Step 2 ships the first personas alongside the retyped skills, all under one folder:

general-assistant (persona, fallback) code-analyst (persona) kubernetes-specialist (persona) the existing skills, retyped type: skill

The 7 reference skills are unchanged apart from the added type: skill line, preserving back-compat. The csproj Content Include moves from skills\**\*.md to capabilities\**\*.md.

Tool scoping

  • Now (soft). The persona body instructs which tools to use or avoid. Zero plumbing.
  • Later (hard, Step 3). FunctionChoiceBehavior.Auto(functions: subset) built from the selected Capability.Tools, threaded via a new ChatRequest.AllowedTools. Addresses the tool overload a 9B local model suffers when offered the full set.

Fold-ins applied to the single engine

  • nomic asymmetric prefixes (search_query: / search_document:) applied at the selector call site, since the connector returns a raw IEmbeddingGenerator.
  • Embed name+description, not description alone (EmbedNameAndDescription).
  • One per-turn log line — persona name and score plus each skill name and score — as the tunability seam.
  • Card-vs-full-body injection mode (default full body) and a future hot-reload that invalidates one Lazy.

The escape hatch (Step 4)

This is Pattern B: one agent, dynamic persona, embedding routing — deliberately not multi-agent orchestration, which was rejected for the local model (no GroupChat/Magentic, no deep handoff chains, route with embeddings not LLM triage). If the chat model is later upgraded, each persona maps roughly 1:1 to a ChatCompletionAgent under HandoffOrchestration. The persona content is the migration asset, so nothing written today is wasted.

What to avoid on a local model

  • No GroupChat or Magentic orchestration; no deep handoff chains.
  • Keep roughly 3–5 tools per persona; route with embeddings, not LLM triage.
  • Validate the chat model tag — confirm it is real, tool-capable, and streams tool calls over the OpenAI-compatible /v1 connector.
  • The heavy chat model can starve nomic-embed-text on a single GPU; use a lighter chat model or free Ollama while indexing.
