Commit & PR Policy

Every change reaches main through a branch and a Pull Request, the human who requested the work is the sole author, and no commit or PR ever attributes authorship to an AI tool.

convention statusactive version 1.0 date 2026-06-01 sources obsidian-vault/scout/CLAUDE.md; CONTRIBUTING.md

The rule

Scout has one path to main: a feature branch and a Pull Request. There are no direct pushes to main — not for docs, not for chores, not for a one-line fix. The commit history that lands is composed of atomic commits, one concern each. The author of every commit is the human who requested the work, and nothing in the commit or PR may credit an AI tool as author, co-author, or contributor.

  • Branch for every change. Use a typed slug: feat/<slug>, fix/<slug>, chore/<slug>, or docs/<slug>.
  • Atomic commits. One concern per commit; do not bundle a refactor with a feature or a format pass with logic.
  • PR against main. Push the branch and open the PR with gh pr create; fill in the repository template.
  • The PR body confirms the read-only invariant — that the change introduces no executive writes against external systems.
  • Merge only after CI passes and, when required, review is complete.
  • No force-push to main, ever. No force-push to a feature branch once review has started.
  • The human is the author. If a commit template would auto-append AI attribution, strip it before committing.
Absolute rule. Never add Claude — or any AI tool — as co-author, author, or contributor. This covers commit trailers (Co-Authored-By:, Signed-off-by: Claude), commit-message footers ("Generated with Claude Code"), PR descriptions, PR authors / reviewers / assignees, and source-file headers or comments. There is no exception.

Rationale

  • The PR is the gate that protects the read-only invariant. Scout is a read-only assistant: no contribution may introduce write operations against external systems. A direct push bypasses the review where that invariant is checked, so every change is forced through a PR whose body restates the invariant.
  • Atomic commits keep history auditable. One concern per commit means a reviewer — and a future bisect — can reason about each change in isolation, and a single bad commit can be reverted without unpicking unrelated work.
  • Human authorship is a provenance and licensing concern. Scout ships under MIT; by opening a PR the contributor confirms they have the right to contribute the code. Authorship must therefore name the human who is making that attestation, never a tool.
  • No AI attribution keeps the record clean. Source files carry no AI-attribution comments or marketing headers, and the same discipline extends to commits and PRs so the project's metadata stays honest and free of vendor noise.

Examples

Workflow for a change — including docs, chores, and one-line fixes:

branch feat/<slug> atomic commits push branch gh pr create vs main CI + review merge
Do — branch, commit atomically, open a PR. 
# branch off main
git switch -c fix/rate-limit-message

# one concern, human is the author, no AI trailer
git commit -m "fix: translate provider 429 to LlmRateLimitException"

git push -u origin fix/rate-limit-message
gh pr create --base main --fill
Don't — push to main, or attach AI attribution. 
# never push straight to main
git push origin main

# never credit an AI tool as author or co-author
git commit -m "feat: add Slack adapter

Co-Authored-By: Claude <noreply@anthropic.com>
Generated with Claude Code"

Both the project CLAUDE.md and CONTRIBUTING.md name the same branch prefixes. The vault adds docs/<slug> for documentation-only changes; CONTRIBUTING.md lists feat, fix, and chore for external contributors. Either way, the branch is typed and the PR targets main.

Bootstrap exception. The two initial commits — chore: bootstrap repository and chore: add OSS project baseline — pre-date this policy and remain on main directly. Every commit after them follows the branch-and-PR flow. This is the only carve-out.

Enforcement

  • Quality gates before the PR opens. Run dotnet format until clean and dotnet test until green. For external contributors, CONTRIBUTING.md states the same: run dotnet format and dotnet test before pushing.
  • Reviewer agents per change surface. architect-reviewer for any change touching Scout.Core or plugin contracts; code-reviewer for any new plugin or adapter; security-auditor for any change touching credentials, token handling, or external API calls.
  • Production-readiness for external boundaries. A change touching HTTP, DB, broker, cache, filesystem, or cloud APIs runs the production-readiness-checks skill before the PR — see Production Readiness.
  • PR body restates the invariant. The template asks the author to confirm the change introduces no executive writes; CONTRIBUTING.md warns that PRs which break the read-only invariant will not be merged.
  • Merge is CI-gated. Merge only after CI passes and any required review is complete; no force-push to main under any circumstance.
  • Issue first for non-trivial work. Open an issue describing the change before starting anything non-trivial; small fixes (typos, obvious bugs) may go straight to a PR.
