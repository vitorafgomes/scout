Testing

Scout tests are unit tests written with Shouldly assertions; dotnet test must be green before any PR, and reviewer agents gate the change.

convention statusactive version 1.0 date 2026-06-01 sources obsidian-vault/scout/CLAUDE.md; ADR 0003

The rule

Scout uses unit tests and asserts with Shouldly. The convention has three non-negotiable parts that every change must satisfy before it can land on main:

  • Shouldly for every assertion — never FluentAssertions. This applies to every test project. New code uses Shouldly from the first line. If FluentAssertions is found, it is migrated in a dedicated chore/tests-shouldly-migration PR rather than mixed with feature work.
  • A green test run before the PR. dotnet format must be clean and dotnet test must be green before opening a PR against main.
  • Reviewer-agent gates. The change passes the relevant reviewer agents — architect-reviewer, code-reviewer, and security-auditor — depending on what it touches.

The Shouldly-only side of this convention is also recorded as a hard project invariant and as ADR 0003.

Rationale

  • License. Shouldly is MIT. FluentAssertions flipped to a commercial license in v8 (January 2025); the first five Scout test projects had started on the last permissive release, v6.12.1. Never allowing FluentAssertions in is the cheapest way to avoid a future license debate.
  • Consistency. One assertion library per codebase. Two frameworks in the same suite is immediate cognitive overhead and a code-review tax for every PR that touches tests.
  • API parity is close enough. Every assertion FluentAssertions v6 expressed has a Shouldly equivalent; a few fluent chains break into two asserts, but no expressivity is lost.

A green dotnet test gate keeps main always-shippable, and the reviewer-agent gates catch architecture, plugin-contract, and credential-handling regressions that unit tests alone do not cover.

Examples

Do — assert with Shouldly. 
// tests/.../Usings.cs
global using Shouldly;

// in a test
result.Provider.ShouldBe("Ollama");
chunks.ShouldNotBeEmpty();
Don't — pull in FluentAssertions. 
// forbidden — never add this using or the package
global using FluentAssertions;

result.Provider.Should().Be("Ollama");

Directory.Packages.props lists Shouldly 4.3.0 and does not list FluentAssertions; every test csproj references Shouldly and every tests/.../Usings.cs carries global using Shouldly;.

Shouldly gotchas to know

  • Shouldly refuses null actuals on ShouldContain over string?. Tests asserting on nullable messages use the null-forgiving operator on the asserted side.
  • ShouldThrowAsync<T>() returns Task<T>. Code that needs to inspect the thrown exception captures the awaited result: var ex = await act.ShouldThrowAsync<T>(); ex.Message.ShouldContain(...).

Where this shows up in practice

Service pages document their own testing footprint against this convention — for example, Scout.Llm unit-tests request validation, the HTTP 429 translation, settings construction, and provider selection, all with Shouldly assertions.

Enforcement

The quality gates that must pass before opening a PR against main:

  • dotnet format clean — style is auto-checked first.
  • dotnet test green — the full suite must pass.
  • architect-reviewer — runs on any change touching Scout.Core or plugin contracts.
  • code-reviewer — runs on any new plugin or adapter.
  • security-auditor — runs on any change touching credentials, token handling, or external API calls.

For any change that touches an external boundary (HTTP, DB, message broker, cache, filesystem, cloud APIs), the Production Readiness bar adds at least one test per boundary that simulates that call failing. The day-to-day commands for the format/test loop live in the Build & Test runbook.
