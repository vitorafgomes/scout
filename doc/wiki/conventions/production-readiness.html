Wiki/Conventions/Production Readiness

Production Readiness

Before a PR adds or modifies code that touches an external boundary, it must ship at least one test that simulates that boundary call failing.

convention statusactive version 1.0 date 2026-06-01 sources obsidian-vault/scout/CLAUDE.md

The rule

Any pull request that adds or modifies code touching an external boundary must run the production-readiness-checks skill before it is opened against main. An external boundary is any call that leaves the process: HTTP, a database, a message broker, a cache, the filesystem, or a cloud API. The minimum bar is concrete and non-negotiable.

  • One failure test per boundary. For every boundary the change touches, there must be at least one test that drives the dependency into a failure mode — a timeout, a 5xx response, or a connection reset — and asserts the code's behaviour under that failure.
  • Run the skill, not just the unit tests. Standard happy-path unit tests do not satisfy this rule. The reference playbook is playbooks/failure-testing.md inside the production-readiness-checks skill.
  • Boundary cases default to required. If you are unsure whether a change crosses a boundary, treat it as if it does and add the failure test.

Boundaries in scope

HTTP Database Message broker Cache Filesystem Cloud APIs

Rationale

Scout talks to a lot of things it does not control: LLM providers over HTTP, chat platforms, a local vector store, the filesystem when indexing a project, and GitHub for descriptive writes. Every one of those calls can time out, return a 5xx, rate-limit, or have its socket reset midway — and the failure path is exactly the code that never runs in a green happy-path test suite.

  • Failure paths are the untested paths. A passing unit suite proves the success branch works; it says nothing about the timeout branch, which is where production incidents are born.
  • Streaming widens the blast radius. Scout is streaming-first, so a provider can fail mid-stream, after chunks have already been emitted. The IChatGateway already translates an HTTP 429 into a domain LlmRateLimitException raised inside the stream — exactly the kind of behaviour a failure test must pin down.
  • Cheap to add, expensive to omit. A single fault-injection test is small. The bug it catches — a swallowed exception, an unbounded retry, a leaked handle — is not.

Examples

The patterns below describe intent, not literal test code. Apply the matching playbook from the skill.

Do — simulate the provider returning 5xx mid-stream. A change to Scout.Llm that touches the HTTP path to an LLM provider ships a test that makes the provider respond with a 500 (or a 429) while streaming, and asserts the gateway surfaces the failure as a domain exception rather than swallowing it or hanging.
Do — drive the filesystem boundary into failure when indexing. A change to Scout.Knowledge project indexing adds a test where a file read fails (missing file, permission denied) and asserts the indexer fails the single item without aborting the whole run or corrupting the store.
Don't — ship a boundary change with only happy-path tests. A PR that adds a new HTTP call to a cloud API but tests only the 200 response does not meet the bar. The 5xx, timeout, and reset behaviour is undefined, and that is precisely what reaches production.
Don't — assert "no exception" and call it covered. A test that runs the failure scenario but only checks that nothing threw hides the real question: what did the code do with the failure? Assert the observable outcome — the domain exception, the retry count, the partial result — per the failure-testing playbook.

Enforcement

This convention sits on top of the standard Scout quality gates. Before opening a PR against main, the following must hold:

  • dotnet format is clean.
  • dotnet test is green.
  • The production-readiness-checks skill has been run for any change touching an external boundary, and the per-boundary failure tests are present and passing.
  • The security-auditor agent reviews any change touching credentials, token handling, or external API calls.
  • The architect-reviewer agent reviews changes to Scout.Core or plugin contracts; the code-reviewer agent reviews any new plugin or adapter.

Reviewers should treat a missing failure test on a boundary-touching PR as a blocking change request, not a nit. Where Scout already documents a service's boundary surface, its Testing footprint section should state that the failure tests are required here — see, for example, the note on Scout.Llm. Projects may strengthen this rule in their own context but may never relax it below the one-test-per-boundary minimum.
