Wiki/Overview/Vision

Vision

Scout is a chat bot that answers recurring operational and codebase questions from inside the team's existing chat platform, by reading from integrated systems. It never writes.

Chat-native Read-only by contract LLM optional Pluggable everything Local-first

The problem

Engineering teams spend time answering recurring operational and business questions in chat — questions whose answers are deterministic and already live in cloud-provider status APIs, source repositories, and pipelines. Reaching those answers, though, requires context, access, and often a developer acting as the intermediary. Typical questions look like:

  • "Is prod Azure up?"
  • "What is the status of our AWS RDS cluster?"
  • "How is the checkout flow implemented in the monolith?"
  • "Which service owns this endpoint?"

What Scout is

Scout is a chat bot that:

  • Runs inside the team's existing chat platform — Slack, Discord, or Teams — one at a time, any combination over time.
  • Accepts natural-language or slash-command queries.
  • Reads from integrated systems (cloud providers, GitHub, Azure DevOps) to answer.
  • Uses an LLM — local (Ollama) or hosted (Azure OpenAI / OpenAI) — to compose answers when retrieval is involved.
  • Never writes. All integrations are read-only by contract.

The read-only stance is the load-bearing invariant of the whole project. It is formalised as No Executive Writes and decided in ADR 0009 — Descriptive vs Executive Writes: plugins may perform descriptive writes (content a human must read and decide to act on), but never executive writes that mutate code, infrastructure, configuration, or data without a human gate.

What Scout is not

Not a ticketing bot
It does not create issues, send emails, or notify people.
Not incident-response
It does not page, escalate, or trigger runbooks.
Not a code generator
It answers questions about code; it does not modify it.
Not an LLM wrapper
The LLM is an optional composition layer; several plugins work without one.

Target users

  • Business users who need to ask questions about the product or codebase without context-switching to developer tooling.
  • On-call engineers who want a faster surface for status checks than logging into cloud portals.
  • New team members who need to self-serve onboarding questions about the codebase.

Success criteria for V1

  • A team can install Scout on Discord.
  • Both reference plugins ship and work against real integrations:
    • CloudStatus returns current health for Azure, AWS, Oracle Cloud, and Kubernetes clusters.
    • CodeQA answers natural-language questions about a configured GitHub repository, with citations to source files.
  • The LLM provider is swappable between Ollama and a hosted option (Azure OpenAI or OpenAI) via configuration only, no code changes — see Pluggable Everything.
  • All external calls are demonstrably read-only (audited in code review).
  • The plugin system proves its extensibility by hosting two domains that share no code beyond the KernelPlugin contract.

Non-goals for V1

  • Slack and Teams adapters — planned for V1.1 and V1.2 per ADR 0002 — Platform Priority. See Adapter.Slack and Adapter.Teams.
  • Multi-repo indexing in CodeQA — V1 supports one configured GitHub repository.
  • Azure DevOps integration in CodeQA — GitHub only for V1.
  • Multi-tenant hosting.
  • Web UI or admin dashboard. When a web surface is eventually built post-V1, the stack is Angular (latest stable, Signals-first, standalone components) — no alternatives considered, per ADR 0004 — Web Stack Angular.

How the vision maps to the system

The product principles above translate directly into architectural invariants and the service catalog. The LLM layer that "composes answers when retrieval is involved" is Scout.Llm, kept provider-agnostic and local-first. The chat platforms are pluggable chat adapters, and each integrated system is a feature Semantic Kernel plugin. For the full picture, see the High-Level & Per-Turn Flow.
