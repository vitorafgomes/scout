Project Snapshot

Scout is a read-only chatops assistant for Discord, Slack, and Microsoft Teams. It answers operational and development questions in chat by querying GitHub, searching indexed local repositories, and calling a configurable LLM provider — and it never writes to any external system.

This page is the five-minute answer to "what is Scout?". Read it first, then follow the links into Vision, the high-level architecture, and the individual service pages.

read-only chatops .NET 10 Semantic Kernel local-first (Ollama) Discord · Slack · Teams 8 LLM providers MIT license pre-alpha

What Scout is

Scout is a chat bot that runs inside a team's existing chat platform and answers natural-language or slash-command queries by reading from integrated systems. Today it answers by querying GitHub, by searching indexed local repositories through vector similarity, and by composing answers through a configurable LLM provider. Every integration is read-only by contract.

Equally important is what Scout is not: it is not a ticketing bot, not an incident-response tool, and not a code-generation bot. The LLM is an optional composition layer rather than the product — some plugins return deterministic answers without one. The read-only stance is the single hardest rule in the codebase; see No Executive Writes and Descriptive vs Executive Writes.

How it is built

Scout is a .NET 10 solution (Scout.slnx). All active source lives under src/; anything under src/old/ and tests/old/ is deprecated legacy code that is not part of the build. Microsoft Semantic Kernel is the orchestration core: chat completions and embeddings flow through one shared kernel, and feature modules contribute KernelPlugin instances for function-calling. See the architecture overview in High-Level & Per-Turn Flow.

.NET 10
SDK 10.0.100 or later, pinned in global.json with rollForward: latestMinor. No .NET 8/9 artifacts.

Pluggable everything

Three axes of the system are swappable by configuration alone, with no code change: the LLM provider, the chat adapter, and the feature plugins. This is a project invariant — see Pluggable Everything and Local-First Default.

LLM providers (select with Scout:Llm:Provider)

Ollama (default)OpenAIAzureOpenAIAzureAIInference GeminiMistralHuggingFaceOpenRouter

Ollama is the default so contributors can run Scout without paid credentials, defaulting to http://localhost:11434 with chat model llama3.1 and embedding model nomic-embed-text. The gateway lives in Scout.Llm; the design is recorded in ADR 0012.

The active services

Eleven backend projects make up the running system. The core pipeline (LLM gateway, conversation, adapters, project knowledge RAG, skills) builds and tests pass on CI.

Scout.Llm
LLM gateway. Wraps Semantic Kernel with a streaming-first IChatGateway; selects one of eight providers at startup.
Scout.Conversation
Platform-agnostic conversation core. Per-channel, per-user in-memory history; routes messages through the gateway with streaming.
Scout.Knowledge
Project knowledge RAG. Chunks local repo files, stores embeddings in SQLite via sqlite-vec, exposes a search_project plugin. Auto-discovery and optional file-watch re-indexing.
Scout.Skills
Retrieval-based skills. Loads markdown skill files, selects the most relevant per turn by cosine similarity, injects it into the system prompt; also a Skills plugin.
Scout.Plugin.GitHub
Read-only GitHub plugin. Exposes list_repositories, list_pull_requests, list_issues, get_repository. Self-gates on Scout:Plugins:GitHub:Token.
Scout.ControlPlane
Domain services for the control plane: provider management, feature catalog, credential store, runtime configuration. Contracts shipped as gRPC/Protobuf.
Adapter.Discord
Discord chat adapter. Self-gates on Scout:Adapters:Discord:BotToken.
Adapter.Slack
Slack adapter using Socket Mode (no public URL). Self-gates on Scout:Adapters:Slack:BotToken.
Adapter.Teams
Microsoft Teams adapter. Self-gates on Scout:Adapters:Teams:AppId.
Host.Console
Main runnable host. Starts configured adapters and the conversation worker; handles the one-shot index <project> command.
Host.ControlPlane
ASP.NET Core host for the control-plane gRPC service. Talks to the Desktop UI over a Unix domain socket or named pipe.

Each chat adapter is self-gating: if its credentials are absent, the adapter is skipped and the host continues with the remaining ones. There is no public TCP port between the backend and the Desktop UI — the link is a Unix domain socket on Linux/macOS or a named pipe on Windows; see ADR 0011.

The read-only invariant

Scout enforces read-only access at the design level. The GitHub plugin exposes only listing and retrieval functions, and no adapter, plugin, or knowledge operation writes to any external system. CONTRIBUTING.md treats this as a hard invariant: any PR introducing a write operation will not be merged. The project draws a precise line between descriptive writes — content another agent must read and decide to act on — and executive writes, which mutate code, infra, configuration, or data without a human gate. Executive writes are forbidden, and boundary cases default to forbidden.

  • No Executive Writes — the hard, codebase-wide rule.
  • Descriptive vs Executive Writes — the full classification and per-plugin allow-list.
  • ADR 0009 — the decision that records the split.

Where things live

  • Backend source: src/ (solution Scout.slnx); the runnable host is src/Scout.Host.Console.
  • Desktop UI: ui/ — an Electron application built with Angular and packaged with electron-builder.
  • Configuration: all keys under the Scout: prefix; secrets via .NET User Secrets or environment variables, never committed. See Secrets Never Committed.
  • Project-knowledge database: ~/.local/share/Scout/project-knowledge.db on Linux (%LOCALAPPDATA%/Scout/ on Windows).
  • Documentation: ADRs and specs live in the Obsidian vault under obsidian-vault/scout/, not in the source repo.

Status

Scout is pre-alpha. The core pipeline builds and passes tests on CI; the Desktop UI has its own CI pipeline (running on Ubuntu, macOS, and Windows) but is not yet in a release state. For the current picture of what is done and what is pending, see Status & Pending Work and the Current Focus & Backlog.
