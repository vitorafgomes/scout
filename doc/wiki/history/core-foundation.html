Wiki/History/Core Foundation

Core Foundation (2026-04)

Plan 1 turned an empty repository into a buildable .NET 10 solution with the contracts, the read-only plugin registry, and the first Ollama provider that everything since has been built on top of.

reference statusarchived version 1.0 date 2026-04-21 sources vault sessions/2026-04-21-core-foundation.md
This is a historical record of the foundational build, archived as written. The code shapes described here are the starting point, not today's structure: the single Scout.Core library was later split into the per-feature services you see in the nav, and the test stack was migrated off FluentAssertions. Read it as the origin story, then follow the cross-links for the current state.

What changed

The session scaffolded the Scout solution from nothing and delivered it across five small, independently mergeable pull requests against a protected main. Each PR was CI-green with unit tests before merge.

PR 1 · scaffold PR 2 · contracts PR 3 · plugin registry PR 4 · Ollama provider PR 5 · host facade
  • Solution scaffold — Scout.sln, a shared Directory.Build.props (.NET 10, C# 13, nullable, TreatWarningsAsErrors), central package versions in Directory.Packages.props, and a Scout.Core class library plus a Scout.Core.Tests xUnit project. First green CI.
  • Chat contracts — the ChatMessage and ChatResponse records and the IChatAdapter interface that adapters would later implement.
  • Plugin contracts — PluginCapabilities (read-only by default; constructing a write-capable instance throws) and the IScoutPlugin interface that builds a Semantic Kernel KernelPlugin.
  • Plugin registry — PluginRegistry rejects any plugin that does not declare PluginCapabilities.ReadOnly (raising ReadOnlyViolationException) and rejects duplicate names, enforcing the read-only invariant at registration time.
  • LLM provider — ILlmProviderFactory plus the first implementation, OllamaLlmProviderFactory, wiring Semantic Kernel's Ollama chat-completion connector from LlmOptions.
  • Host facade — ScoutHost (the entry point adapters call), ScoutHostBuilder for DI composition, ScoutOptions, and a ScoutActivitySource for OpenTelemetry traces. V1 behavior was a static handshake; intent routing was explicitly deferred to a later plan.

Why

The goal was a buildable library that proved the core abstractions and the read-only security posture before any external integration existed — no Discord, no feature plugins, only unit tests with in-memory fakes. Three principles drove the design and survive in today's services:

  • Read-only by construction. Rather than trust plugins to behave, the registry refuses to load anything that declares write capability, so the invariant fails fast at startup instead of at runtime. This is the seed of No Executive Writes.
  • Pluggable everything. The LLM provider was hidden behind ILlmProviderFactory from day one, with the active provider chosen from configuration — see Pluggable Everything.
  • Local-first default. Ollama was the first and default provider so contributors could run Scout with no paid credentials — see Local-First Default.

Splitting the work into five focused PRs through a protected main was deliberate: each one mergeable on its own, each one CI-green, none mixing concerns. That branch-and-PR discipline became the standing workflow for the project.

Outcome

  • A buildable .NET 10 solution with a green test suite and green CI for the first time.
  • The core contracts — ChatMessage, ChatResponse, IChatAdapter, PluginCapabilities, IScoutPlugin — that all later adapters and plugins implement.
  • A PluginRegistry that enforces the read-only invariant at registration, with a deliberate write-capable fake proving the rejection path.
  • An LLM provider abstraction with Ollama as the working default, ready for hosted providers to be added later.
  • A ScoutHost facade observably alive end-to-end, with OpenTelemetry tracing in place from the start.

The plan's own "what comes after" section set up the next three deliverables: a Discord adapter (Plan 2), a CloudStatus feature plugin (Plan 3), and a CodeQA RAG plugin (Plan 4) — each on its own branch and plan file.

Services affected

Everything in this build originally lived inside a single Scout.Core library. As the project grew, those responsibilities were extracted into the dedicated services that exist today:

Scout.Llm Scout.Conversation Scout.ControlPlane
  • The ILlmProviderFactory + Ollama work is the direct ancestor of Scout.Llm, which now hosts the provider abstraction behind a streaming-first gateway and ships eight providers.
  • The ScoutHost handshake and message-handling entry point evolved into the routing and conversation handling now owned by Scout.Conversation.
  • The chat-adapter contract opened the door for the Discord, Slack, and Teams adapters that followed.

Lessons

  • Enforce invariants in code, not in review. Baking read-only enforcement into PluginCapabilities and PluginRegistry meant the security posture could not silently regress; a violating plugin simply fails to load.
  • Small PRs against a protected main scale. Five mergeable, single-concern PRs kept CI honest and made each step reviewable. The discipline stuck and is now codified in the Commit & PR Policy.
  • A single core library is a fine start, not a fine end. Putting contracts, host, registry, and provider in one Scout.Core was the right move for a first buildable artifact, but the responsibilities were later split into the per-feature services in the nav as the surface area grew.
  • Test-stack choices age. This build standardised on FluentAssertions and NSubstitute. FluentAssertions later went commercial-licensed, so the project migrated every test to Shouldly — see Shouldly-Only Tests and ADR 0003. Pin and revisit third-party test dependencies, not just runtime ones.
  • Ship a minimal but observable host. The V1 static handshake plus OpenTelemetry tracing proved the end-to-end path was alive before any real feature existed, deferring intent routing without leaving the host untestable.
