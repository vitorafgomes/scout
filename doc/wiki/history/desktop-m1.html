Desktop M1 (2026-04)

Milestone 1 delivered a Discord-only desktop provisioning wizard — an Electron shell driving an Angular 21 renderer that detects chat clients, stores the bot token in safeStorage, runs the OAuth2 install over a loopback server, and supervises a bundled .NET worker — shipping unsigned, cross-platform builds while deliberately deferring signing, Slack, and Teams provisioning.

reference statusarchived version 1.0 date 2026-04-23 sources vault sessions/2026-04-23-scout-desktop-m1.md
This is a historical record of a closed milestone. The plan it summarises was active in April 2026 and is preserved here as a retrospective. For the current shape of the provisioning UI, see Desktop Provisioning UI; for scope and deferrals as a decision, see ADR 0005.

What changed

M1 introduced a new top-level ui/ folder as a sibling of the existing src/ (.NET backend) and tests/ trees — a Bun-managed monorepo whose packages are main (Electron main process), preload, renderer (the Angular 21 application), and shared (pure TypeScript IPC contract consumed by all three). The deliverable was a guided wizard that takes a contributor from launch to a running Discord bot without touching a config file.

The work shipped as a fourteen-PR sequence on main (#29 through #42), each green on its own CI job:

1 bootstrap workspace 2 shared IPC contract 3 main shell 4 preload bridge 5 renderer shell 6 client detection 7 safeStorage vault 8 Discord OAuth loopback 9 wizard screens 10 worker supervisor 11 worker publish pipeline 12 packaging 13 CI matrix 14 README + ADR

The major capabilities that landed:

  • Hardened Electron shell. A single BrowserWindow with contextIsolation: true, nodeIntegration: false, sandbox: true, and a strict CSP. The renderer has no Node, no filesystem, and no child_process — only the preload-exposed API surface.
  • Typed IPC contract. Every renderer↔main channel is namespaced scout:* with request/response types in the shared package. No channel exposes a write capability to any external system.
  • Cross-platform client detection. Discord detected on Windows, macOS, and Linux; Slack and Teams are detection-only badges. Each subprocess probe has a 2-second timeout and a failure test.
  • safeStorage secret vault. The bot token is encrypted to <userData>/vault.enc via Electron safeStorage; cleartext never touches disk and the renderer can write/check existence but never decrypt.
  • OAuth2 loopback install. A single-shot Node HTTP server bound strictly to 127.0.0.1:53682 handles the Discord authorize callback, with a main-generated single-use state verified on /callback.
  • Supervised .NET worker. The packaged app spawns Scout.Host.Worker as a child process with exponential-backoff restarts, line-buffered log streaming over scout:worker.events, and a graceful SIGTERM→SIGKILL shutdown that always reaps the child on quit.
  • Unsigned cross-platform packaging. electron-builder produces a Windows NSIS installer, macOS DMGs (arm64 + x64), a Linux AppImage, and a .deb, all driven by a three-OS GitHub Actions matrix.

Why

Scout had a working .NET backend but no on-ramp for a non-technical operator to stand up a bot. The console host required hand-editing configuration and managing a long-lived process. M1's goal was to make provisioning a Discord bot a guided, repeatable, secure flow on a real desktop, while keeping the project's hard constraints intact.

  • Read-only invariant preserved end-to-end. No IPC channel initiates a write against Discord or any external API. The single outbound network call in the main process is the OAuth2 token exchange — authentication, not a user-data write. All runtime traffic happens in the .NET worker under the descriptive-write enforcement of No Executive Writes.
  • Secrets never in the renderer or on disk in cleartext. safeStorage was chosen over keytar (unmaintained) and raw libsecret (Linux packaging pain). On a Linux box with no keyring, isEncryptionAvailable() returns false and the UI surfaces a banner rather than silently writing plaintext.
  • Local-first stayed the default. The worker launches with SCOUT__LLMPROVIDER=Ollama so a fresh install runs without paid credentials, consistent with Local-First Default.
  • Discord-first, deliberately narrow. Per platform priority, only the Discord wizard was built end-to-end; Slack and Teams were scoped to detection only to keep the milestone shippable.
  • Angular 21 with Signals. The renderer bootstraps zoneless with a signal-based store, in line with the web-stack decision.

Outcome

As of the 2026-04-24 status checkpoint, implementation was in flight with PRs #29 through #42 merged on main — covering the full fourteen-PR breakdown plus a SingletonLock stale-PID recovery fix (#42) that lets a crashed instance relaunch cleanly. The intended end-to-end happy path was: launch → welcome → provision → token paste → OAuth install → worker launch → ready.

Shipped in M1
  • Bun workspace + shared IPC contract
  • Hardened main shell & typed preload bridge
  • Angular 21 zoneless renderer + six wizard screens
  • Client detection across three OSes
  • safeStorage vault + Discord OAuth loopback
  • Worker supervisor + per-RID publish pipeline
  • Unsigned packaging + three-OS CI matrix
  • SingletonLock stale-PID recovery (#42)
Deferred to post-M1 backlog
  • Signing / notarization / electron-updater
  • Slack wizard (apps.manifest.create)
  • Teams provisioning (detection only; policy-blocked)
  • Renderer / main OpenTelemetry
  • Discord adapter ID-redaction (accepted as Info-level logging for now)

The full list of scope and deferrals was recorded as an ADR. The plan note was to stay active until the final documentation PR landed, then flip to deprecated once M1 closed.

Services affected

M1 was almost entirely net-new desktop tooling around the existing backend; the services it touched or depends on:

Adapter.Discord Host.Console
  • Scout.Host.Worker — the .NET 10 single-file, self-contained binary published per RID (win-x64, osx-arm64, osx-x64, linux-x64) and shipped as electron-builder extraResources outside the ASAR so it can be spawned. The desktop shell is its supervisor.
  • Adapter.Discord — the only adapter wired through the wizard; the worker launches with SCOUT__CHATADAPTER=Discord. ID-redaction in this adapter was the one accepted gap.
  • Host.Console — the pre-existing entry point that the desktop worker pipeline mirrors; the desktop app is an alternative front door, not a replacement.

A companion .NET change (feat/worker-ready-signal, out of desktop scope) was flagged to add a SCOUT_READY stdout signal in ScoutWorker.cs so the supervisor could confirm the worker had connected before showing the ready screen.

Lessons

  • The IPC contract is the spine. Putting every renderer↔main type in one shared package, and forbidding any write-capable channel, kept the read-only invariant enforceable by code review rather than convention. It is the single source of truth for the boundary.
  • Pick the runtime model deliberately. Bun is dev-only; Electron's bundled Node executes main.ts at runtime. This was flagged as the highest-severity open question and addressed with a lint rule forbidding the Bun global inside the main and preload packages.
  • Boundary failure tests paid off. Every external boundary — keychain unavailable, Discord token endpoint 4xx/5xx/timeout, loopback port-in-use, state mismatch, worker binary missing or hanging on shutdown — got an explicit failure test, matching the production-readiness bar of at least one failing-path test per boundary.
  • Ship unsigned, then sign. Deferring code signing, notarization, and auto-update kept the milestone deliverable; releases were labelled "UNSIGNED BUILD" with a documented xattr -d com.apple.quarantine workaround for macOS rather than blocking on certificates.
  • Detection that never blocks. Treating a missing or undetected client as SKIP/LINK rather than an error meant the wizard worked even when Discord desktop was not installed — a web session is enough.
  • Stale locks bite packaged apps. The SingletonLock stale-PID recovery fix was the one item discovered late and folded in (#42), a reminder that single-instance handling needs crash-recovery testing.
