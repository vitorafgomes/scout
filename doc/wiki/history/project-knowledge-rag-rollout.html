Project Knowledge RAG Rollout

Phase 1 of Project Knowledge shipped Scout's first retrieval-augmented feature: a new Scout.Knowledge service that indexes a configured repository into a local SQLite-vec store and lets a single Project Expert agent answer questions grounded in the project's own code and docs, with citations.

reference statusarchived version 1.0 date 2026-05-30 sources vault 02-architecture/project-knowledge-rag-phase1-plan.md
Historical record. This page is a retrospective of a completed rollout and is kept archived. It documents what shipped in Phase 1 and why; the living design lives in Project Knowledge RAG and the active service in Scout.Knowledge. Deferred work moved to the Project Knowledge Optimization roadmap.

What changed

The rollout introduced a brand-new project, Scout.Knowledge, holding the whole chunk → embed → store → retrieve pipeline plus the SK plugin and agent that surface it to chat. The Phase 1 plan ran as a single branch (feat/project-knowledge) and was sequenced as a TDD task chain, each task a failing test first, then the implementation, then a commit.

  • New Scout.Knowledge project + options. Added the project, its test project, and a ProjectsOptions model bound to the Scout:Projects configuration section — each entry is just a Name and a RepoPath.
  • SQLite-vec vector store. An IProjectKnowledgeStore backed by Microsoft.SemanticKernel.Connectors.SqliteVec: a local file, no service. ChunkRecord carries the per-chunk metadata and a 768-dimension embedding (matching nomic-embed-text), with cosine distance and a per-project filter on search.
  • Roslyn + line-fallback chunker. FileChunker parses C# with the Roslyn AST, emitting one chunk per class / record / interface / method; every other file type falls back to fixed 100-line windows. Files that yield no member declarations also fall back to line windows so a file never produces zero chunks.
  • Indexer. ProjectIndexer walks the repo, skips bin obj .git node_modules dist, chunks each allowed file, batch-embeds via the shared Ollama IEmbeddingGenerator, and replaces the project's chunk set in the store. Per-file failures are isolated so one bad file does not abort the index.
  • Retrieval + citations. A retrieval service embeds the question, runs a project-filtered top-K cosine search, and formats hits as a citation-tagged context block (path:startLine-endLine + content). Unknown / unindexed / empty projects and any store failure return a clean message — the path never throws into the kernel.
  • ProjectKnowledge SK plugin + Project Expert agent. The plugin exposes search_project as a kernel function; a ChatCompletionAgent named "Project Expert" with automatic function-calling becomes the chat responder, instructed to always ground answers in retrieved context and cite sources.
  • index <project> console subcommand + DI wiring. Scout.Host.Console -- index <name> indexes one configured project and exits without starting adapters. AddProjectKnowledge binds options and registers the store, chunker, indexer, retrieval service, plugin, and agent into the shared kernel composition.

Why

The goal was to let a user ask Scout, in natural language, about a software project — its architecture, business rules, and how something is implemented — and get an answer grounded in that project's real code and in-repo documentation, with citations to source files. The design deliberately mirrors the reference implementation studied for it (an incremental-AST + vector-store + Ollama-embeddings approach), adopting its contextual-embedding trick of prefixing each chunk with a File: x | class: Y | lines: a-b header before embedding.

A correction baked into the design from the start: there is no dependency on the Obsidian vault. Each project is self-contained in its own repo, and "docs" means in-repo markdown (README, *.md, a docs/ folder). The vault is the human knowledge base, not a runtime source.

Phase 1 was scoped tight on purpose. The full design called for a knowledge graph, file-watch incremental indexing, tree-sitter languages, and graph-boosted hybrid retrieval — all heavy, all interdependent. The plan named those the highest-risk parts and explicitly phased them out: foundation first (dense retrieval over a local store), graph and watcher later.

Phased scope

Shipped (Phase 1)
SQLite-vec store, Roslyn + line chunker, repo indexer, dense top-K project-filtered retrieval with citations, search_project plugin, Project Expert agent, index subcommand, DI + config.
Deferred (later plans)
Knowledge graph + graph-boost retrieval; file-watch incremental indexing; tree-sitter for TS / Python; BM25 + cross-encoder reranking; agent cross-session memory.

Outcome

The pipeline landed end to end. The flow that the rollout established is:

walk repo chunk (Roslyn / line windows) context prefix + embed (Ollama) upsert to SQLite-vec question → embed → project-filtered top-K cited context → Project Expert (streaming)
  • Indexing is operated out-of-band by the console subcommand, so a long index walk never blocks chat.
  • Retrieval is project-scoped: search is filtered to one configured project by name, and an unknown or unindexed name yields a plain message rather than an error.
  • The answer path stays streaming-first — the agent streams its grounded reply through the existing conversation sink, so the new responder did not break the established contract.
  • Manual acceptance was the gate beyond unit tests: add a real repo path under Scout:Projects, run index <name>, then ask the project a question in chat and confirm a grounded, cited answer arrives via the search_project tool with a tool-capable model.
Phase 1 was the foundation, not the finished feature. The store wrapper and indexer were built to be extended — later work added per-file replacement, symbol lookup, project listing, auto-discovery and a file-watch service on top of this base. Those evolutions are tracked under Project Knowledge Optimization and reflected in the current Scout.Knowledge page.

Services affected

Scout.Knowledge Scout.Llm Scout.Conversation Host.Console Scout.Plugin.GitHub
  • Scout.Knowledge — created by this rollout; owns the chunker, store, indexer, retrieval service, plugin, and agent factory.
  • Scout.Llm — reused as the embedding source: the indexer and retrieval use the existing Ollama IEmbeddingGenerator, and the Project Expert agent runs on the shared kernel.
  • Scout.Conversation — its streaming responder path was rewired so the Project Expert agent answers, while the IAsyncEnumerable<string> → sink contract stayed unchanged.
  • Host.Console — gained the index <project> subcommand and the AddProjectKnowledge registration.
  • Scout.Plugin.GitHub — the existing function-calling kernel composition is what the new plugin folds into; the Project Expert agent carries both the GitHub plugin and search_project.

Lessons

  • Preview connectors leak diagnostics — plan to suppress them. The SqliteVec connector and the basic ChatCompletionAgent emit experimental SKEXP diagnostics; the plan called out reading the exact code from the first build error and adding it to <NoWarn> rather than fighting it ad hoc.
  • Embedding dimensions are a hard contract. The vector record is locked to 768 dimensions to match nomic-embed-text; a mismatch is a runtime failure, so the dimension lives next to the embedding field as an explicit constant.
  • Resolve the embedder outside the kernel. Reusing the shared kernel's embedding everywhere risked a DI construction cycle through project knowledge; the foundation took the embedder straight from the provider factory instead — the same lesson the Scout.Llm composition root records.
  • Re-index correctness needs a deletion strategy. Deterministic chunk ids ({project}:{path}:{startLine}) make upserts idempotent, but chunks from deleted code linger unless the project's rows are cleared first — Phase 1 chose whole-project replacement and explicitly noted per-file deletion as follow-up work.
  • Boundaries must degrade, never crash. Per the Production Readiness rule, every external boundary — embed, store, retrieval — returns a clean message on failure and isolates per-file errors during indexing, keeping the host alive.
  • Phase aggressively when risk is concentrated. Knowledge graph + incremental + file-watch was correctly identified as the heaviest, most coupled work; deferring it kept Phase 1 shippable and let the foundation prove out before the expensive parts.
