Conversation Memory Fix

A development-time fix: Scout forgot everything between turns and parroted a stale example project name, so we gave it bounded per-conversation memory and grounded the agent on the projects it is actually configured to search.

reference statusarchived version 1.0 date 2026-05-30 sources vault 02-architecture/conversation-memory-fix-PLAN.md
Historical record. This page documents a fix that was planned and executed against the feat/project-knowledge branch on 2026-05-30. It is kept for traceability; the behaviour it describes is now the baseline. See Scout.Conversation for the current shape.

What changed

The fix landed as three atomic commits and split cleanly into two independent problems: a grounding hotfix in Scout.Knowledge, and per-conversation memory threaded through Scout.Llm and Scout.Conversation.

Commit 1 — grounding hotfix Commit 2 — history contract + gateway seeding Commit 3 — memory store + router wiring + write-back

Commit 1 — ground the agent on configured projects

  • The [Description(...)] attributes on the project parameter in ProjectKnowledgePlugin were neutralised so no concrete project name leaks into the tool schema the model sees.
  • The e.g. "cegos-buddy" example in the ProjectsOptions XML doc was removed (doc-only).
  • ProjectExpertAgentFactory moved from a static const Instructions to a BuildInstructions(configuredProjects) form that appends the real configured project names into the agent's default instructions, with a graceful fallback to base instructions when the list is empty.
  • KnowledgeServiceCollectionExtensions passes the already-bound configured names into the new factory overload — no new dependency edge.

Commit 2 — history contract and gateway seeding (behaviour-neutral)

  • New ConversationTurn abstraction in Scout.Llm: a ConversationRole enum (User/Assistant) plus a ConversationTurn(Role, Text) record.
  • ChatRequest gained a History property defaulting to empty — replayed oldest-first before the current user message; empty means single-turn, byte-identical to prior behaviour.
  • ChatGateway replays prior turns on both paths: the direct path adds them after the system message and before the current user message; the agent path seeds a ChatHistory and constructs a ChatHistoryAgentThread from it, with a duplicate guard so the current user message is not seeded twice.

Commit 3 — bounded in-memory store, router wiring, atomic write-back

  • New ConversationMemoryOptions under Scout:Conversation:Memory — Enabled (default true), MaxTurns (6 turn-pairs), MaxReplayedChars (8000, newest-first), IdleTtl (30 minutes).
  • IConversationKeyProvider derives the conversation key as channel + user ($"{ChannelId}{UserId}"), isolating the policy in one place so it can evolve later without touching adapters.
  • InMemoryConversationMemoryStore over a ConcurrentDictionary: a bounded Load (trimmed to MaxTurns and MaxReplayedChars, newest kept, oldest-first), an atomic pair Append with FIFO eviction, per-entry locking so same-key writes serialise while different keys never contend, an injected TimeProvider, and lazy TTL eviction on access. It is documented as in-process RAM only, not a durable write boundary.
  • LlmStreamingRouter loads history at enumeration (preserving deferral), accumulates streamed tokens into a StringBuilder while forwarding them unchanged, and appends the user/assistant pair only after the stream completes cleanly with a non-empty reply.

Why

The deployed bot was effectively stateless. The pipeline ran adapter → ConversationConductor → LlmStreamingRouter → ChatGateway, and the gateway built a fresh ChatHistory (direct path) or ChatHistoryAgentThread (agent path) for every request. ChatRequest carried no history at all, so context was discarded between turns.

A second, independent defect made the symptom worse: the project parameter's [Description(...)] attribute included a concrete example — cegos-buddy — which is serialised into the tool schema the model reads. The model parroted that example, while the project Scout was actually configured to search (messaging-explorer, via Scout:Projects:Items) was never injected into the agent's instructions.

Design constraints honoured. The conversation key is channel + user, so no ChatMessage field changed and no adapter rippled. The memory store sits inside Scout.Conversation over the Scout.Llm abstractions only — no edge into Scout.Knowledge or the kernel, so the dependency graph stays cycle-safe by construction. Write-back is atomic and conditional on clean stream completion, so a failed or cancelled stream never poisons history.

Outcome

  • Memory restored. A turn-2 request now carries the turn-1 user/assistant pair in ChatRequest.History; the first turn starts empty.
  • Grounding fixed. The configured project name appears in the agent's rendered default persona, and the stale cegos-buddy example no longer reaches the model — a regression lock test asserts the description attributes never contain it.
  • Behaviour-neutral until wired. Commits 1 and 2 were verified byte-identical to the baseline where history is empty; only commit 3 turns memory on, gated by configuration.
  • Streaming intact. The router forwards every token unchanged while accumulating in parallel; the streaming-first IAsyncEnumerable<string> path is preserved.
  • No poisoned history. A failed stream leaves the store empty — verified by test — because the append only runs after a normal, non-empty completion.

Tests were written first (TDD) across Scout.Knowledge.Tests, Scout.Llm.Tests, and Scout.Conversation.Tests, covering grounding regression, behaviour-neutral seeding, FIFO/char-budget/TTL eviction, concurrent same-key append safety, cross-user isolation on a shared channel, and the failed-stream no-poison guarantee. The composition-cycle and host-composition smoke tests stayed green.

Services affected

Scout.Knowledge Scout.Llm Scout.Conversation
  • Scout.Knowledge — grounding hotfix: plugin description neutralised, agent factory builds instructions from configured project names.
  • Scout.Llm — new ConversationTurn abstraction, ChatRequest.History, and history replay in ChatGateway on both the direct and agent paths.
  • Scout.Conversation — memory options, key provider, in-memory store, and router wiring with atomic write-back.

Lessons

  • Tool descriptions are prompt surface. Parameter [Description] attributes are serialised into the schema the model reads; a throwaway example in a doc string became a behaviour the bot exhibited in production. Keep concrete names out of tool descriptions.
  • Inject grounding where the data already lives. Baking configured project names into the agent's default instructions kept the fix inside Scout.Knowledge DI, where ProjectsOptions was already in scope — no cross-module edge, no DI cycle, no persona plumbing through the router.
  • Make new state opt-in and behaviour-neutral first. Splitting the change so the history contract and gateway seeding were byte-identical to the baseline (empty history) let the risky store land last, behind a config flag.
  • Write-back must be conditional. Persisting the turn pair only on clean stream completion means a failed or cancelled response can never corrupt the conversation, and the test for it was non-negotiable.
  • Keep the memory boundary honest. The store is documented as in-process RAM, not a durable write boundary — a durable/persisted store was explicitly left out of scope to avoid introducing a new write boundary in this fix.

Explicitly out of scope

  • A durable/persisted store (it would introduce a new write boundary).
  • Channel + thread group memory (would require a ChatMessage.ThreadId field and a three-adapter ripple).
  • The Capability Engine (a separate, then-stashed effort).
