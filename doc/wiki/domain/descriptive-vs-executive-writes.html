Descriptive vs Executive Writes

Scout partitions every write it could make against an external system into two classes: a descriptive write produces content another agent must read and decide to act on (a GitHub issue, a PR comment), and an executive write mutates code, configuration, infrastructure, or data with immediate effect — descriptive writes are permitted, executive writes are forbidden.

domain statusactive version 1.0 date 2026-06-01 sources ADR 0009; obsidian-vault/scout/CLAUDE.md

Meaning in this project

Scout is a read-only chatops assistant: it describes work for humans and other agents, and it does not execute work against external systems. The original read-only invariant stated this as a single bar — no plugin, adapter, or integration may write to any external system at all. As the plugin ecosystem grew, that single bar conflated two materially different kinds of write, so ADR 0009 refined it into the two named classes below.

Descriptive write
Permitted. Produces content another agent must later read and decide to act on. Does not, by itself, mutate code, configuration, infrastructure, data, or any executable state. Example: creating a GitHub issue, commenting on a PR, posting in the originating chat channel.
Executive write
Forbidden. Mutates code, configuration, infrastructure, or data in a way that takes effect immediately without a human gate. Example: committing or pushing code, merging a PR, kubectl apply, a cloud-API mutation, a database INSERT.

The intuition the user holds for Scout is exactly this split: describe work, never execute it. A descriptive write cannot break production on its own — it is a description of intent that a human reviewer, a CI pipeline, or a developer decides whether to act on. An executive write, once taken, cannot be intercepted by a human in the loop without an explicit rollback; that is the case the invariant exists to prevent.

Classify by effect, not by API surface. The class of a write is determined by what it does to the world, not by the verb on the API. Adding a comment to a PR is descriptive even though it is a write, because the comment is content for humans. Creating a Kubernetes ConfigMap is executive even though it resembles "just text", because it mutates cluster state. When in doubt, a plugin author must default to forbidden and seek explicit approval.

Where it lives

Owned by

This is a project-wide security invariant, not a single service's concern. It is enforced at design time across every plugin and adapter. The canonical, model-facing surface today is Scout.Plugin.GitHub, which is the first integration whose write classification matters in practice.

Referenced by

Scout.Plugin.GitHub No Executive Writes Semantic Kernel Plugin Chat Adapter

Key attributes

  • Descriptive writes are permitted. Per ADR 0009: creating a GitHub issue (title, body, labels), posting a comment on a PR or issue, adding a purely organisational label (e.g. triage, bug), and posting a message in the originating chat channel (already permitted by the chat adapter contract).
  • Executive writes are forbidden. Committing or pushing code; merging, closing, or approving a PR; editing repository settings, webhooks, secrets, or branch protection; any kubectl apply/delete/exec/scale/patch/rollout/cordon/drain; any cloud-API mutation; database INSERT/UPDATE/DELETE/DDL; host filesystem writes outside Scout's own config directory; and email or external notifications outside the originating chat.
  • Boundary cases default to forbidden. A descriptive write whose effect indirectly mutates state is reclassified as executive — for example, creating a GitHub issue with a label that triggers a CI workflow is executive, and requires explicit per-repository user consent.
  • Content hygiene is a separate concern. The line is conceptually sharper than it is enforceable. A descriptive write that leaks credentials in plain text is still a leak even though it mutates no state; plugin authors must treat secrets and PII as their own concern on top of this split.
  • Classified per function, in code review. There is no automated classifier. Each new plugin function must be tagged descriptive or executive at design review, and PRs that introduce executive writes must be rejected.
  • Class changes need a new ADR. Changing the permitted class for any existing plugin function (for example, proposing any Kubernetes write — descriptive or otherwise) requires a separate ADR. Scout.Plugin.Kubernetes remains strict read-only for the foreseeable future.

Related terms

  • Semantic Kernel Plugin — a plugin exposes KernelFunctions to the model; each function is the unit that gets classified descriptive or executive.
  • Chat Adapter — posting into the originating channel is a descriptive write already permitted by the adapter contract.
  • LLM Provider — the provider drives function-calling; the write-class split constrains which functions are safe to offer.

Code references

ADR 0009 permits descriptive writes (for example a future CreateIssue), but the shipped GitHub plugin is still strict read-only — descriptive writes are sanctioned by the decision yet not yet implemented in code. The current surface therefore demonstrates the executive-write prohibition in full and the descriptive-write allowance only by absence.

  • src/Scout.Plugin.GitHub/GitHubPlugin.cs:7 — class summary: "Read-only GitHub plugin… Listing only: no create, merge, or push operations exist by design." The only KernelFunctions are list_repositories, list_pull_requests, list_issues, and get_repository.
  • src/Scout.Plugin.GitHub/Abstractions/IGitHubClient.cs:3 — interface summary: "Read-only access to GitHub data… Listing only: no create, merge, push, or comment operations exist by design." No write method is declared on the client contract.
  • obsidian-vault/scout/CLAUDE.md — the project rules state the descriptive/executive split as the security invariant and link to ADR 0009 for the full classification and per-plugin allow-list.
