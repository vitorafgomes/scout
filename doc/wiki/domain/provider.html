LLM Provider

An LLM Provider is a single ILlmProviderFactory implementation that wires one model backend's chat-completion and embedding services onto Scout's shared Semantic Kernel; Scout ships eight, exactly one is active per run, and Ollama is the default.

domain statusactive version 1.0 date 2026-06-01 sources src/Scout.Llm/Providers/; README providers list

Meaning in this project

A provider is the adapter between a concrete model backend (Ollama, OpenAI, Gemini, …) and Scout's provider-agnostic LLM layer. Each one is a class that implements ILlmProviderFactory and lives in its own folder under src/Scout.Llm/Providers/. The factory does two things: it registers the backend's chat-completion and embedding services on the kernel builder via AddToKernel, and it can build a standalone embedding generator via CreateEmbeddingGenerator.

Exactly one provider is active per process. The composition root reads Scout:Llm:Provider, switches on that name, and registers the matching factory; an unrecognised name throws at startup rather than silently falling back. Because the active factory is the only place that references a connector package, the rest of Scout never sees a provider SDK or a Semantic Kernel connector type — it talks only to IChatGateway.

Provider is a backend selector, not a per-request routing knob. The choice is made once, at startup, from configuration; switching providers means changing config and restarting, not changing a request field.

Where it lives

Owned by

Scout.Llm

The ILlmProviderFactory abstraction sits in src/Scout.Llm/Abstractions/, every implementation under src/Scout.Llm/Providers/<Name>/, and the selection switch in LlmServiceCollectionExtensions.cs. Connector dependencies stay confined to the factory files so the abstraction layer remains connector-free.

Referenced by

Scout.Conversation Scout.Knowledge Scout.Skills

These consumers never name a provider. They resolve IChatGateway (chat) or IEmbeddingGenerator<string, Embedding<float>> (embeddings) from DI; the active provider is whatever the composition root selected.

Key attributes

  • One contract — every provider implements ILlmProviderFactory: Name, AddToKernel(builder), and CreateEmbeddingGenerator().
  • One active at a time — the composition root switches on Scout:Llm:Provider and registers a single factory; there is no per-request provider switching.
  • Self-validating — each factory validates its own options block in the constructor (endpoint shape, model names, batch/timeout/dimension bounds) and throws ArgumentException on bad values, so misconfiguration fails fast at startup.
  • Connector-confined — the connector package and any SKEXP* experimental-API suppressions live only inside the factory file; consumers see only stable types.
  • Standalone embedder — CreateEmbeddingGenerator() builds the embedder from a throwaway kernel so it carries no dependency on the shared kernel, which would otherwise form a DI construction cycle through project knowledge.
  • Unknown name fails fast — the default arm of the selection switch throws InvalidOperationException listing the supported provider names.
  • Local-first default — LlmOptions.Provider defaults to "Ollama", so contributors run Scout without paid credentials.

Related terms

  • Semantic Kernel Plugin — feature modules contribute KernelPlugin instances that are folded onto the same shared kernel the active provider populates.
  • Chat Adapter — the inbound side (Discord, Slack, Teams) feeding messages to the gateway; the provider is the outbound model side.
  • Project Knowledge — the main consumer of the provider's embedding generator for retrieval.
