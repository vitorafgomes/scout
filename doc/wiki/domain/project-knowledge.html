Wiki/Domain/Project Knowledge

Project Knowledge

A configured local repository that Scout has chunked, embedded, and stored so the language model can answer questions about its code and docs by vector similarity, with citations to the source files.

domain statusactive version 1.0 date 2026-06-01 sources src/Scout.Knowledge/; vault project-knowledge-rag.md

Meaning in this project

"Project Knowledge" is Scout's local Retrieval-Augmented Generation (RAG) corpus. A configured project is a named local repository; indexing walks that repository, splits each file into chunks, embeds every chunk with the shared Ollama embedding generator, and persists the chunks in a local SQLite vector store. At chat time the search_project Semantic Kernel function embeds the user's question and returns the nearest chunks for one project, each tagged with its file path and line range so the model can cite where an answer came from.

The corpus is built purely from in-repo content — source files plus in-repo markdown (README, *.md, a docs/ folder). There is no dependency on the Obsidian vault or any external service; the whole knowledge database is a single file on the host. Project Knowledge is a read-only lens over a repository: indexing reads files, it never writes to them.

Items vs Roots

A project enters the corpus two ways, both under Scout:Projects:

  • Items — an explicit list of { Name, RepoPath } entries. The name is what the user and the model refer to in queries and tool calls; RepoPath is the absolute path to the repository root.
  • Roots — directories scanned at startup; each repository found under a root becomes a discovered project named after its folder.
  • Collision rule — discovered roots are merged first, then explicit Items are layered on top, so an explicit item always wins on a name collision. The merged, sorted name list is what list_projects reports and what the Project Expert agent is grounded on.

Where it lives

Owned by

Scout.Knowledge

Referenced by

Scout.Llm Scout.Conversation Host.Console

Scout.Knowledge owns the domain end to end: the chunker, the indexer, the SQLite-vec store, the retrieval service, the ProjectKnowledge Semantic Kernel plugin, and the Project Expert agent. It builds on Scout.Llm only for the shared embedding generator, which is injected directly rather than pulled from the kernel to avoid a DI construction cycle.

Key attributes

  • Chunk record — the stored unit is a ChunkRecord: Id ("{project}:{path}:{startLine}"), Project (filterable), Path, Kind ("code" or "doc"), Symbol, 1-based StartLine/EndLine, Content, and a 768-dimension Embedding with cosine distance.
  • Chunking — C# files are chunked at member boundaries (method, class, record, interface) with the Roslyn AST; every other file type, and any C# file with no member declarations, falls back to fixed 100-line windows so a file never produces zero chunks.
  • Embedding context prefix — each chunk is embedded with a prefix line File: {path} | {kind}:{symbol} | lines a-b prepended to the chunk text, so the file and symbol identity is part of the vector.
  • Indexable scope — code extensions .cs .ts .tsx .js .jsx .py .json .yml .yaml and doc extensions .md .txt; segments bin obj .git node_modules dist .vs are skipped.
  • Persistence — one SQLite-vec collection project_chunks in project-knowledge.db under the host's local application data directory (Linux: ~/.local/share/Scout/). No external vector service.
  • Lazy indexing — discovery is directory-listing only at startup; a project is indexed on its first resolution. If the store already has the project, indexing is skipped; if first-use indexing fails, resolution returns null instead of throwing.
  • Replace semantics — re-indexing a project (or a single file under the file watcher) gathers the existing rows by filtered scan, deletes them by key, then upserts the fresh set, so chunks for code that no longer exists are removed rather than left stale.
  • Optional incremental watch — opt-in (default off) per-file re-indexing with a debounce quiet window (default 750 ms); only activates when watch is enabled and at least one explicit project item is configured.
  • Never throws into the kernel — empty input, unknown project, no indexed content, and retrieval failure all return a clean status string to the model, never an exception.

Retrieval surface

The plugin exposes three Semantic Kernel functions to the model:

search_project
Embeds the question and returns the top 5 cosine matches for one project as citation-tagged context blocks.
find_symbol
Metadata-only lookup by symbol name (no embedding): case-insensitive exact matches first, then partial (contains) matches, default top 10.
list_projects
Returns the merged, sorted set of project names (discovered roots plus explicit items) the agent can search.

Related terms

  • Semantic Kernel Plugin — Project Knowledge is surfaced to the model as a KernelPlugin built from ProjectKnowledgePlugin, registered only when at least one project is configured.
  • Skill — distinct from a Skill: skills are markdown injected into the system prompt; Project Knowledge functions are tool-callable plugin functions the model can invoke.
  • LLM Provider — the same provider supplies the embedding generator that indexing and retrieval share (Ollama by default, nomic-embed-text at 768 dimensions).
