Semantic Kernel Plugin

A Semantic Kernel plugin is a named bundle of [KernelFunction] methods that the language model can call by name during a turn; Scout folds every registered plugin onto the one shared kernel so the model gains those tools through function-calling.

domain statusactive version 1.0 date 2026-06-01 sources src/Scout.Plugin.GitHub/; src/Scout.Llm/LlmServiceCollectionExtensions.cs

Meaning in this project

In Scout, a plugin is the Semantic Kernel concept: a KernelPlugin built from an ordinary C# class whose methods carry the [KernelFunction] attribute. Each such method becomes a tool the model can choose to invoke. Scout builds exactly one shared Kernel in AddScoutLlm, and every plugin contributed by a feature module is added to that kernel's plugin collection. When the chat gateway runs a turn with automatic function choice enabled, the model sees the catalogue of plugin functions and may call one, supplying the typed arguments.

A plugin is the project's mechanism for executable capability: the model does not just read text, it can act through a function whose body is real .NET code. The current reference plugin is Scout.Plugin.GitHub, which surfaces read-only GitHub listing functions. By design the GitHub plugin is listing-only — there is no create, merge, push, or comment function — which keeps it inside the No Executive Writes invariant: a tool call observes and describes, it never mutates remote state.

Feature modules are self-gating. A module registers its KernelPlugin only when configured (the GitHub plugin needs a token); when off it contributes nothing, so the shared kernel starts with whatever subset of plugins the host has enabled. The gateway never enumerates plugins by name — it simply folds in every KernelPlugin the DI container can resolve.

Where it lives

Owned by

Scout.Plugin.GitHub

Each feature module owns its own plugin class and the DI extension that registers it. The GitHub module owns GitHubPlugin and AddGitHubPlugin; future modules follow the same shape.

Referenced by

Scout.Llm

Scout.Llm is the consumer side. Its composition root resolves every registered KernelPlugin from DI and adds it to the shared kernel's Plugins collection, after which the chat gateway offers them to the model. Scout.Llm does not decide which plugins exist; it only collects whatever the host registered.

Key attributes

  • Built from a plain class — KernelPluginFactory.CreateFromObject(new GitHubPlugin(...), "GitHub") wraps a normal object into a named KernelPlugin; the name ("GitHub") namespaces its functions.
  • Functions are attributed methods — each callable method carries [KernelFunction("list_repositories")] plus a [Description(...)]; parameters carry their own [Description(...)] so the model knows what to pass.
  • Invoked via function-calling — the model selects a function by name and supplies arguments; this only happens because the gateway enables automatic function choice when building chat settings.
  • Folded onto the shared kernel — all plugins live on the single Kernel from AddScoutLlm; there is no per-plugin kernel.
  • Self-gating registration — a module contributes its plugin only when configured (GitHub requires a non-empty token), so an unconfigured host still starts with no plugin registered.
  • Tool calls never throw into the kernel — GitHubPlugin catches transport and API failures and returns a clean, non-empty string instead of propagating an exception back to the model.
  • Read-only by design — the reference plugin exposes listing and overview functions only, honouring No Executive Writes.

Related terms

  • Skill — the contrast case. A Skill is markdown guidance retrieved and injected into the system prompt; Semantic Kernel never sees it as a callable function. A Plugin is the opposite: real code the model invokes via function-calling. Skills shape how the model answers; plugins give it actions it can take.
  • LLM Provider — the provider builds the chat-completion service on the same shared kernel that carries the plugins, so function-calling support depends on choosing a tool-capable model.
  • Project Knowledge — itself surfaced to the model as a kernel plugin; the cycle note in AddScoutLlm exists because the project-knowledge plugin depends on the embedder while the kernel is still under construction.
  • Descriptive vs Executive Writes — the rule that bounds what a plugin function is allowed to do; reference plugins stay descriptive.
