Chat Adapter

A chat adapter is the per-platform I/O connector that normalises an inbound chat message into Scout's platform-agnostic conversation core and streams the reply back out — and it disables itself automatically when its credentials are absent.

domain statusactive version 1.0 date 2026-06-01 sources src/Scout.Adapter.*; README adapters

Meaning in this project

An adapter is Scout's seam against a specific chat platform — Discord, Slack, or Microsoft Teams. Each one implements a single inverted contract, IChatAdapter, defined in the conversation core. The adapter owns everything platform-specific: the SDK, the connection model, the message shapes, and the rate-limit quirks. Everything above the adapter — routing, history, the LLM call — works only against the normalised ChatMessage and the IResponseSink the adapter hands it, so the core never references a platform SDK type.

The contract is deliberately inverted: the adapter does not return a value. On StartAsync it receives a handler delegate and, for each inbound message addressed to the bot, it (1) translates the platform event into a ChatMessage, (2) builds an IResponseSink bound to the originating channel only, and (3) invokes the handler with both. The conversation core then drives the sink to stream the answer. The adapter is the only place that knows how to talk to the platform; the rest of Scout stays platform-agnostic.

Each adapter is self-gating: its DI registration extension reads its credential from configuration and, when that credential is blank, the call is a clean no-op — no adapter is registered and the host still starts with whatever other adapters are configured. This is what lets a contributor run Scout with only Ollama and a single chat platform wired up.

Where it lives

Owned by

Scout.Adapter.Discord Scout.Adapter.Slack Scout.Adapter.Teams

Contract & consumers

Scout.Conversation Scout.Host.Console

The IChatAdapter / IResponseSink / ChatMessage contracts are defined in Scout.Conversation's Abstractions namespace; the three concrete adapters depend on it but never on each other. Scout.Host.Console calls each adapter's Add<Platform>Adapter extension at startup and starts whichever ones registered.

Key attributes

  • One contract, one method of entry. Every adapter implements IChatAdapter with a Name ("Discord" / "Slack" / "Teams"), a StartAsync(handler, ct) that begins receiving events, and a StopAsync(ct).
  • Inbound normalisation through a pure translator. A dedicated *MessageTranslator turns the platform payload into a ChatMessage and decides whether the message is even for Scout. No SDK type crosses that boundary, so the decision logic is unit-testable without the SDK.
  • Addressing rules per platform. Discord replies only when the bot is explicitly @-mentioned in a guild channel; DMs need no mention. Self-authored messages are always dropped so the bot never answers itself.
  • Outbound streaming via a channel-bound sink. Each adapter builds an IResponseSink tied to the originating channel and the core drives BeginAsync → UpdateAsync* → CompleteAsync/FailAsync. UpdateAsync always receives the FULL cumulative text, never a delta, so even Teams (which cannot edit a message) works.
  • Descriptive-write boundary. A reply may write only where the message came from. The sink is bound to the originating channel (and thread, on Slack/Teams) at construction; the adapter cannot post anywhere else.
  • Transport resilience lives in the sink. Each sink owns its own rate-limit handling — Discord backs off once on a RateLimitedException and retries; Teams backs off on a 429 and treats a 403 stream-not-allowed as a cancel. The platform-agnostic pump never sees these.
  • Self-gating registration. AddDiscordAdapter needs a bot token; AddSlackAdapter needs both a bot token and an app-level token; AddTeamsAdapter needs an App id. A missing credential makes the call a no-op rather than an error.
  • Connection model differs, contract does not. Discord opens a gateway socket, Slack uses Socket Mode (no public URL), and Teams is webhook-push (the host exposes POST /api/messages and forwards each turn to ProcessActivityAsync). All three present the same IChatAdapter upward.
  • Single-login lifecycle. A small lifecycle state machine arms a lifetime CancellationToken on start and trips it on stop, so in-flight conversations unwind on host shutdown. Discord/Slack reject a restart after stop; Teams is re-startable.

Related terms

  • Descriptive vs Executive Writes — the adapter's channel-bound sink is the descriptive-write boundary: it may write back only where the message came from, never elsewhere.
  • LLM Provider — the other pluggable boundary: a provider is chosen once per process, whereas any subset of adapters can be active at the same time.
  • Semantic Kernel Plugin — adapters carry messages in and out; plugins are what the model can call mid-turn. An adapter never exposes a plugin.
