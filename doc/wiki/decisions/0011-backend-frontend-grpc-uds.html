ADR 0011 — Backend/Frontend gRPC over UDS

The Scout desktop backend-frontend transport is gRPC over a Unix domain socket (Linux/macOS) or a named pipe (Windows) with a per-session token — no TCP port — replacing the loopback HTTP + SSE design.

adr statusaccepted version 1.0 date 2026-05-28 sources vault 06-decisions/2026-05-28-backend-frontend-grpc-uds.md

Status

  • Accepted — 2026-05-28. The .NET server side is implemented and tested; the Node/Electron client side remains a follow-on phase.

Context

Scout's desktop app is Electron — a Node main process plus an Angular renderer. The .NET backend runs as a supervised child process (sidecar). The two must talk: the UI is a control panel (provider lifecycle, features, model management, vault), and several flows are inherently streaming — Ollama and Whisper model-pull progress, worker and provider status events.

The pre-restructure design used:

  • Loopback TCP HTTP — Kestrel bound to 127.0.0.1:<port> with a LoopbackOnlyMiddleware defence-in-depth filter.
  • SSE (text/event-stream) for streaming pull progress.
  • A hand-written ipc-contract.ts duplicating request/response shapes that also exist in C#.

Weaknesses this decision deliberately leaves behind:

  • A loopback TCP port is reachable by any process running as the same user. The middleware is a band-aid: it cannot stop another local process from connecting to the port. This is the main security weakness.
  • Contract drift — the TypeScript and C# shapes are maintained by hand in two places.
  • SSE is text-concatenation streaming, one-directional and fragile.

The restructure mandates streaming-first, and the user asked explicitly for a more performant and more secure transport — not a port of the old one.

Decision

Backend-frontend transport is gRPC over a Unix domain socket (Linux/macOS) or a named pipe (Windows) — no TCP port. The topology routes the renderer through the Electron main process, which is the sole gRPC client and broker to the backend: 

# transport topology
Angular renderer ──contextBridge IPC──▶ Electron main ──gRPC over UDS/pipe──▶ .NET backend
 (sandbox, contextIsolation,            (sole gRPC client,                   (no TCP port)
  no nodeIntegration)                    broker to renderer)
What the transport does
  • Transport: Kestrel binds a UDS / named pipe, not a port. The socket file lives in the user's runtime directory with 0600 permissions; the Windows named pipe is ACL'd to the current user.
  • Auth handshake: the backend mints a per-session token at spawn and hands it to the Electron main process out-of-band (inherited fd / env), never on disk in a world-readable place. Main sends it as gRPC metadata on every call — defence-in-depth even if socket permissions are misconfigured.
  • Contracts: .proto files are the single source of truth, with codegen for both C# (Grpc.AspNetCore) and TypeScript. This eliminates the hand-maintained ipc-contract.ts drift.
  • Streaming: streaming flows (model-pull/download progress, provider/worker status/events) are gRPC server-streaming RPCs. Bidirectional streaming is available if a future flow needs it.
  • Renderer boundary: the renderer never touches the socket. The Electron main process is the only gRPC client and re-exposes a minimal, allow-listed surface via contextBridge with contextIsolation, sandbox, and no nodeIntegration. High-volume streams reach the renderer over a MessagePort (MessageChannelMain) rather than ipcRenderer event spam, for backpressure and throughput.
What this decision removes
  • No loopback TCP port and no LoopbackOnlyMiddleware band-aid.
  • No SSE text-concatenation streaming.
  • No hand-written ipc-contract.ts duplicated across TS and C#.
  • No socket access from the renderer; only the main process holds the gRPC client.

Consequences

Better

  • No network-reachable surface. The whole "other local process connects to the port" class of attack disappears; filesystem permissions plus a session token gate access.
  • Performance. UDS avoids the TCP/IP stack; HTTP/2 multiplexing and protobuf binary framing beat loopback HTTP/JSON plus SSE.
  • One contract. .proto codegen kills TS/C# drift.
  • Streaming is native, matching the streaming-first mandate, rather than an SSE remedy.

Worse

  • gRPC dependency + codegen on both sides (Grpc.AspNetCore in .NET, a gRPC / proto toolchain in the Electron build) — more moving parts than raw HTTP. Mitigation: codegen is wired into the build and the proto surface is small (control-panel commands plus a few streams).
  • UDS on Windows needs the named-pipe path; the transport abstraction must branch per-OS at bind time. Kestrel supports both, but it is two code paths.
  • gRPC-over-UDS from Node requires a gRPC client that targets a UDS/pipe address; the chosen Node gRPC library must be verified for this at implementation time (fallback: a thin local HTTP/2-over-UDS shim, or stdio JSON-RPC).

Operational

  • Per Scout CLAUDE.md quality gates, the PR introducing this transport runs security-auditor (new IPC boundary and token handling) and architect-reviewer (cross-process contract surface).
  • Production readiness: the socket/pipe is an external boundary, so it needs at least one failure-injection test — backend not yet listening, socket disappears mid-stream, token rejected — per Production Readiness and playbooks/failure-testing.md.

Alternatives

Loopback TCP HTTP + SSE (the old design)

Rejected. The open local port is the security weakness this decision exists to remove, SSE is a weaker streaming primitive than gRPC server-streaming, and the hand-written TypeScript contract drifts from C#.

stdio JSON-RPC (Electron spawns the backend, talks over stdin/stdout)

The most secure and lowest-dependency option: no socket and no port, just the private parent-child pipe, unreachable by any other process. Rejected as the primary choice because the streaming protocol (framing, multiplexing, backpressure) must be hand-rolled and binary/high-volume payloads are awkward. It remains the fallback if the gRPC/UDS dependency surface proves too heavy.

WebSocket over UDS

Full-duplex and streaming-friendly, but loses REST/contract ergonomics and requires a bespoke message-envelope protocol. gRPC gives typed contracts plus streaming without the hand-rolled envelope.

Status / sequencing

Decision accepted. The .NET server side — the gRPC-over-UDS/named-pipe host (Scout.Host.ControlPlane), the .proto contracts (Scout.ControlPlane.Contracts), the ported control-plane domain services (Scout.ControlPlane), and the per-session token interceptor — is implemented and tested on feat/scout-llm-gateway alongside the conversation core and the Discord/Slack/Teams adapters (security audit and code review passed, findings fixed). The Node/Electron gRPC client, the Windows named-pipe spike, the TypeScript codegen, MessagePort streaming, and the ui/ rewiring remain a follow-on phase.

This replaces the loopback-HTTP + SSE + hand-written ipc-contract.ts approach from the archived Scout.Host.Worker, frozen under src/old/.
