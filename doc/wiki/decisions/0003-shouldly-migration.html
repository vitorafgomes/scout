ADR 0003 — Shouldly over FluentAssertions

Every test in every Scout project uses Shouldly; FluentAssertions is forbidden, and any FluentAssertions code found on sight is migrated in a dedicated chore PR.

adr statusaccepted version 1.0 date 2026-04-21 sources vault 06-decisions/2026-04-21-shouldly-migration.md

Status

  • Accepted — 2026-04-21. Standardises the assertion library across every Scout test project. Codified in Shouldly-Only Tests and the testing convention.

Context

The first five test projects — Core, Ollama, Discord, CloudStatus, and CodeQA — all started on FluentAssertions 6.12.1, the last permissive release before the library flipped to a commercial license in v8 (January 2025).

Pinning v6 defers the problem but does not solve it. Any future upgrade walks straight into a licensing cliff, and the moment anyone adds a new test project, mixing two assertion libraries in the same suite becomes a latent code smell. The user set the rule directly: "never use FluentAssertions, we should use Shouldly".

Decision

Every test in every project owned by the user uses Shouldly. New code uses Shouldly from the first line; FluentAssertions is forbidden and any FluentAssertions code found on sight gets migrated in a dedicated chore PR.

Required — Shouldly everywhere
  • Directory.Packages.props lists Shouldly 4.3.0.
  • Every test csproj references Shouldly.
  • Every tests/.../Usings.cs carries global using Shouldly;.
Forbidden — FluentAssertions
  • Directory.Packages.props does not list FluentAssertions.
  • No global using FluentAssertions; in any Usings.cs.
  • No new test may introduce a FluentAssertions assertion.
Migration is its own PR

Migration runs on a dedicated branch (chore/tests-shouldly-migration) and is never mixed with feature work, so the diff stays purely mechanical and reviewable as a no-behavior-change rewrite.

Rationale

  • License. Shouldly is MIT. FluentAssertions v8+ is commercial. The cheapest way to avoid a future license debate is to never allow it in.
  • Consistency. One assertion library per codebase. Two frameworks in the same test suite is immediate cognitive overhead and a code-review tax for every PR touching tests.
  • API parity is close enough. Every assertion FluentAssertions v6 expressed has a Shouldly equivalent (see the pattern-mapping table in the migration PR). A few fluent chains break into two asserts; no expressivity is lost.

Consequences

Better

  • PR #22 applied the migration — 37 files and 206 assertions rewritten with zero behavior change.
  • The rule is codified in three places: obsidian-vault/scout/CLAUDE.md (project-level rule), the global memory feedback_shouldly_not_fluentassertions.md (applies to every user repo), and a note on the Shouldly PackageVersion line in Directory.Packages.props explaining why FluentAssertions was removed.

Worse

  • Shouldly refuses null actuals on ShouldContain over string?. Tests asserting on nullable messages (e.g. StatusReport.Message) must use the null-forgiving operator on the asserted side.
  • ShouldThrowAsync<T>() returns Task<T>. Code that inspects the thrown exception's fields has to capture the awaited result: var ex = await act.ShouldThrowAsync<T>(); ex.Message.ShouldContain(...).

Alternatives considered

  • Stay on FluentAssertions v6 forever — rejected. The pin defers the problem but does not solve it. A contributor pulling Directory.Packages.props into a future project would happily upgrade to v8.
  • NUnit / xUnit built-ins (Assert.Equal, etc.) — rejected. Too verbose for collection and exception cases; Shouldly's fluent-by-value style is significantly easier to read.
  • AwesomeAssertions (FluentAssertions fork) — rejected. Forks of newly-commercial libraries have short lifespans; Shouldly has a stable track record and broad adoption in .NET OSS.
