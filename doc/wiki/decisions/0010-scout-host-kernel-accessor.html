Wiki/Decisions/0010

ADR 0010 — Scout Host Kernel Accessor

Expose a single public read-only ResolvedKernel property on ScoutHost so the Features feature can register and unregister plugins on the live kernel at runtime, instead of opening up kernel construction or splitting the tool surface.

adr statusaccepted version 1.0 date 2026-05-23 sources vault 06-decisions/2026-05-23-scout-host-kernel-accessor.md

Status

  • Accepted — 2026-05-23. Option A approved by the user; lands in the Features feature foundation phase (branch feat/features, Phase 1).

Context

Scout.Core.Hosting.ScoutHost builds its Semantic Kernel lazily inside BuildKernel(). The resulting Kernel is stored in a private Lazy<Kernel> and is not registered in the DI container. Today every IScoutPlugin is registered statically at startup through PluginRegistry, which feeds BuildKernel() once; nothing in the worker mutates kernel.Plugins after host construction.

The Features feature — see ADR 0009 for the broader context, and the upcoming Scout.Plugin.GitHub and Scout.Plugin.Kubernetes work — needs to add and remove KernelPlugin instances at runtime, in response to the user flipping toggles on the Features screen. The new worker-side IFeatureKernelRegistrar must therefore reach the same Kernel that LlmFallbackRouter already consumes, and mutate its Plugins collection.

Three reachable designs were on the table. The user approved Option A.

Decision

Add a single public read-only property on Scout.Core.Hosting.ScoutHost:

/// <summary>
/// The runtime Semantic Kernel built lazily on first access. Stable
/// reference for the lifetime of the host; safe to retain and mutate
/// .Plugins from external callers that own the synchronisation.
/// </summary>
public Kernel ResolvedKernel => _kernel.Value;

The accessor returns the same instance BuildKernel() already returns to internal consumers. First access forces the lazy initialisation; all subsequent calls return the cached reference.

Permitted — read and synchronised mutation
  • Reading ResolvedKernel to obtain the single shared, lifetime-stable Kernel reference.
  • Mutating ResolvedKernel.Plugins only through IFeatureKernelRegistrar.
Forbidden — concurrent or out-of-band mutation

External mutation of ResolvedKernel.Plugins outside IFeatureKernelRegistrar. KernelPluginCollection is not thread-safe for concurrent mutation, so all register/unregister operations must funnel through the registrar.

Boundary — single chokepoint

IFeatureKernelRegistrar serialises register/unregister operations behind a SemaphoreSlim(1, 1). It is the single chokepoint that guarantees safe mutation of the shared kernel's plugin collection.

Consequences

Better

  • One-line public-API addition on Scout.Core. Minimal blast radius; existing consumers are untouched.
  • Backwards compatible. Internal callers keep using their private path; the accessor is purely additive.
  • Single source of truth for the LLM's tool surface. Static IScoutPlugin plugins and dynamic Features plugins share one kernel, one plugin collection, one function-calling decision tree.
  • Cheap to retract. If a future Option B refactor lands, the accessor can become [Obsolete] and consumers migrate one by one.

Worse

  • External mutation of internal state. The Kernel is conceptually internal to ScoutHost, and exposing it as a property lets any consumer mutate .Plugins without going through the registrar. Mitigation: the registrar is the only documented mutator in this PR, the accessor's XML doc cites it, and the architect-reviewer agent is required on the PR by Scout's quality gate.
  • Surface area on a stable type. Future refactors that change how the kernel is built (e.g. multi-kernel routing per chat session) must either keep this accessor honest or deprecate it deliberately.

Alternatives

Option B — register Kernel in DI
Register Kernel in the DI container from AddScout, so every consumer injects it directly and the lazy hoop disappears. Cleaner long-term, but rejected for Phase 1: it ripples through LlmChatServiceCollectionExtensions (which builds a throwaway kernel at registration time to extract IChatCompletionService), forces every IScoutPlugin to be revisited for construction-order assumptions, and explodes the PR scope from "Features foundation" to "kernel injection refactor" with no user-visible change. Revisit when the next non-trivial kernel consumer lands.
Option C — separate dynamic-kernel container
Plugins added by the Features feature live in their own KernelPluginCollection, queried alongside the static one. Rejected: it forces plugin authors to learn two parallel registration paths, complicates LlmFallbackRouter (which looks at a single kernel for function calling), and splits one conceptual namespace — "the LLM's tool surface" — into two for no user-visible benefit.

Enforcement

  • The PR introducing this accessor (feat/features Phase 1) must run the architect-reviewer agent because it touches Scout.Core. The agent is wired into Scout's PR-template quality gates and the reviewer-author flow.
  • Scout.Core.Tests gains one assertion: ResolvedKernel returns the same non-null instance on first and second access (idempotency).
  • Internal callers may eventually migrate to read through ResolvedKernel for consistency, but that is non-blocking cleanup.
  • Quality gate 3 of the PR template requires architect-reviewer for any change touching Scout.Core contracts, the plugin registry, the LLM provider abstraction, or the chat adapter abstraction.
