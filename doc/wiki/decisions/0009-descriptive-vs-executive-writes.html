Wiki/Decisions/0009

ADR 0009 — Descriptive vs Executive Writes

Partition Scout's external-system writes into two classes: descriptive writes that another agent must read and act on are permitted; executive writes that mutate state without a human gate are forbidden.

adr statusaccepted version 1.0 date 2026-05-23 sources vault 06-decisions/2026-05-23-descriptive-vs-executive-writes.md; obsidian-vault/scout/CLAUDE.md

Status

  • Accepted — 2026-05-23. Refines, does not supersede, the original read-only invariant. Codified in No Executive Writes.

Context

Scout began with a single-bar read-only invariant: no plugin, adapter, or integration may write to an external system. That was correct for a chatops assistant that reads logs and surfaces context. As the plugin ecosystem grew (GitHub, Kubernetes, future integrations), the single bar conflated two very different kinds of write:

  • Writes that describe work for a human or another agent to act on — a GitHub issue, a PR comment, a TODO line.
  • Writes that execute work themselves — a commit, a kubectl apply, a merge, a deploy, a database mutation.

The first kind is materially safer: an issue Scout files cannot break production on its own; it is a description of intent that a reviewer, pipeline, or developer decides to act on. The forcing function was the GitHub plugin needing CreateIssue so a user can file a backlog item from chat.

Decision

External-system writes are partitioned into two classes, determined by their effect, not their API surface.

Descriptive writes — permitted

Produce content another agent must later read and decide to act on. They do not, by themselves, mutate code, configuration, infrastructure, data, or any executable state.

  • Creating a GitHub issue (title, body, labels)
  • Commenting on a GitHub PR or issue
  • Adding a purely organisational label (e.g. triage, bug)
  • Posting a message in the originating chat channel
Executive writes — forbidden

Mutate code, configuration, infrastructure, or data in a way that takes effect immediately without a human gate.

  • Committing or pushing code to any branch
  • Merging, closing, or approving a PR
  • Editing repo settings, webhooks, secrets, branch protection
  • kubectl apply / delete / exec / scale / patch / rollout / cordon / drain
  • Any cloud-API write (S3 put, RDS modify, Lambda update, IAM mutation)
  • Database INSERT / UPDATE / DELETE / DDL
  • Host filesystem writes outside Scout's own config directory
  • Email or external notifications outside the originating chat
Boundary cases — default to forbidden

When unsure, a plugin author defaults to forbidden and seeks explicit approval. Creating an issue with a label that triggers a CI workflow is executive (it indirectly mutates state). A Kubernetes ConfigMap is executive even though it resembles "just text". A PR comment is descriptive even though it is a write, because it is content for humans.

Consequences

Better

  • Unlocks high-value functions (CreateIssue, CommentOnPullRequest) without breaking the guarantee that matters most: Scout never breaks production by itself.
  • Gives plugin authors a vocabulary to classify their own write paths at design review.
  • Aligns the invariant with how the user thinks about Scout: "describe work, never execute it".

Worse

  • The line is sharper conceptually than it is enforceable — a descriptive write that leaks credentials in plain text is still a leak. Content hygiene stays a separate concern.
  • No automated classifier: each new plugin function must be tagged descriptive or executive in code review, and PRs introducing executive writes are rejected.

Enforcement

  • No Executive Writes — the invariant page with the enforcement sites and the per-plugin allow-list.
  • Scout.Plugin.GitHub — permitted descriptive writes (CreateIssue, future CommentOnPullRequest, AddIssueLabel); forbidden executive writes (MergePullRequest, CreateBranch, PushCommit, repo settings).
  • Scout.Plugin.Kubernetes remains strict read-only; any proposed Kubernetes write requires a separate ADR.
  • The Features screen ships a per-plugin badge indicating which write classes each plugin may perform.
