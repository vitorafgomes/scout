ADR 0004 — Web Stack: Angular

All web UI for Scout uses Angular — latest stable — with Signals as the reactivity model, standalone components, the new control flow, and the Angular CLI for builds.

adr statusaccepted version 1.0 date 2026-04-22 sources vault 06-decisions/2026-04-22-web-stack-angular.md

Status

  • Accepted — 2026-04-22.

Context

Scout will eventually need web surfaces. The first is the Electron provisioning UI renderer (see Desktop Provisioning UI); a future admin dashboard, status page, or hosted control plane may follow.

Without an explicit framework choice locked in early, contributors would ship PRs using whichever web framework is convenient (React, Vue, Svelte, Solid). Each additional framework multiplies onboarding cost, build-tooling surface, component-library decisions, and testing infrastructure. A single-framework rule now is cheaper than untangling a mixed codebase later.

The project owner has already standardized on Angular across other projects and wants Scout aligned. This ADR makes that choice explicit and enforceable.

Decision

All web UI for Scout uses Angular — latest stable (currently 21.2.9 at the time of this ADR; track the latest stable in angular/angular releases). The conventions below apply to every Angular codepath in the project.

Required conventions

  • Signals as the reactivity model. State flows through signal(), computed(), and effect(). RxJS is reserved for actual stream semantics — cancellation, debouncing, HTTP.
  • Standalone components only. No NgModule boilerplate; new code uses standalone: true (the Angular 21 default) with explicit imports arrays.
  • New control flow. Templates use @if, @for, @switch, @defer.
  • Zoneless change detection when feasible. At minimum avoid zone.js-only reactivity; prefer provideZonelessChangeDetection() as soon as the runtime allows it for the project.
  • Angular CLI (ng) for builds. ng build, ng test, ng generate are the canonical commands, invoked through bun run scripts where the package-manager boundary allows. The Angular CLI owns the bundler pipeline (currently esbuild under the hood).

Forbidden

  • BehaviorSubject-only patterns for component state.
  • Structural directives *ngIf, *ngFor, *ngSwitch in new code; existing ones (none yet) migrate on sight.
  • bun build for the renderer bundle — the Angular CLI owns that pipeline.
  • Any other web framework (React, Vue, Svelte, Solid, plain Web Components).

Consequences

Better

  • Single stack, single onboarding path. New contributors learn one framework, one CLI, one testing story.
  • Consistency with the owner's other projects. Code-review patterns, linter configs, and muscle memory carry across.
  • Clear rejection criterion in CI. Any PR introducing React, Vue, Svelte, Solid, or any other web framework is automatically out of scope and can be closed on framework choice alone.
  • Signals-first code ages well. Angular is explicitly moving toward a zoneless, Signals-based future; starting there avoids a later migration.

Worse

  • Angular's npm-centric tooling may friction against Bun. Some schematics historically shell out to npm, and peer-dependency resolution assumes npm semantics. The ng + Bun interop is flagged as a to-verify item; any npm-only escape hatch (e.g. a package-lock.json shim) is documented in the provisioning note.
  • Heavier runtime than Svelte or Solid. For a desktop Electron renderer this is largely irrelevant (no cold network payload, no SEO budget), but a real cost for any eventual public-facing web surface.
  • Ecosystem narrower for Electron-specific Angular patterns. React has broader Electron tutorial coverage; expect to write thin integration glue ourselves.
  • Contributors may still ship non-Angular PRs. CI and review must reject non-Angular web code explicitly — add a lint rule or a pre-PR check if drift appears.

Alternatives

  • React. Largest ecosystem, best Electron tutorial coverage, richest component-library surface. Rejected: the owner has standardized on Angular, and Scout needs no React-specific library Angular cannot match.
  • Vue. Good DX, reasonable Electron support. Rejected on the same ecosystem-split grounds as React, with a smaller upside.
  • Svelte / SvelteKit. Smallest runtime, most ergonomic template syntax. Rejected: the bundle-size advantage is irrelevant for an Electron renderer (payload is local, startup is dominated by Chromium), and the ecosystem-split cost dwarfs the gain.
  • Solid. Signals-first by design, fast, small. Rejected for the same ecosystem reason; Angular 21's Signals model covers the same reactivity story within the chosen stack.
  • No framework / plain TypeScript + Web Components. Rejected: the productivity delta vs. a full framework is too large for the scope Scout anticipates (provisioning wizard today, admin dashboard tomorrow).

Enforcement

  • PRs introducing any non-Angular web framework are out of scope and closed on framework choice alone.
  • New components must be standalone with explicit imports; templates use the new control flow only.
  • Renderer bundling goes through the Angular CLI; bun build is not used for the renderer.
  • If non-Angular drift appears, add a lint rule or a pre-PR check to reject it mechanically.
