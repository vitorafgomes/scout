Wiki/Decisions/0002

ADR 0002 — Platform Priority

Implement Scout's chat adapters sequentially, in order of integration friction: Discord first, then Slack, then Microsoft Teams.

adr statusaccepted version 1.0 date 2026-04-21 sources vault 06-decisions/2026-04-21-platform-priority.md

Status

  • Accepted — 2026-04-21. Sets the rollout order for the three target chat platforms; the IChatAdapter abstraction stays in place from V1 so later platforms slot in without touching Core.

Context

Scout must eventually support Slack, Discord, and Microsoft Teams. Supporting all three at once would triple the surface area of the first release — three SDKs, three auth models, three message-rendering layers — without improving core value. The three platforms differ sharply in how much ceremony it takes to stand up even a "hello world" bot, so the rollout order is decided by integration friction rather than perceived market preference.

The friction profile of each platform, lowest to highest:

Discord
Bot token is a single string created by clicking through the Developer Portal. Discord.Net is a mature, well-documented .NET SDK. No app review, no workspace admin, no tenant consent. Testable on a personal server in minutes.
Slack
Requires a Slack App, OAuth scopes, and either Socket Mode (dev) or a public HTTPS endpoint (prod). SDK option is SlackNet (community, actively maintained). Distribution beyond a single workspace requires review.
Microsoft Teams
Requires Microsoft.Bot.Framework plus an Azure Bot Service registration, a Teams app manifest, and admin consent inside the target tenant. The most ceremony to stand up even a minimal bot.

Decision

Adapters ship sequentially, ordered by integration friction. The order is fixed and the abstraction layer must precede it.

Rollout order — lowest friction first
  • Discord — first. Single-string bot token, mature Discord.Net SDK, no review or consent, tested on a personal server in minutes.
  • Slack — second. Slack App with OAuth scopes; Socket Mode for dev or a public HTTPS endpoint for prod; SlackNet SDK; review needed beyond one workspace.
  • Microsoft Teams — third. Microsoft.Bot.Framework, Azure Bot Service registration, Teams app manifest, and tenant admin consent.
Abstraction precedes platform two and three

The first release targets Discord only, but the IChatAdapter abstraction must already be in place so Slack and Teams slot in without changing Scout.Core. Any chat feature that only makes sense on one platform (for example, Block Kit-specific interactions) goes behind a capability flag on the adapter, never in Core.

Consequences

Better

  • The first release carries a single SDK, auth model, and rendering layer instead of three, keeping V1 scope tight.
  • Discord's zero setup friction lets contributors run and test the bot in minutes, which matters for an OSS project.
  • Forcing the IChatAdapter abstraction in from V1 means Slack and Teams land additively, without reworking Core.

Worse

  • Documentation and onboarding examples for V1 assume Discord; a second onboarding guide is added when Slack ships.
  • Slack and Teams users wait through the rollout order — they are not first-class until their adapter lands.
  • Platform-specific interactions must be gated behind capability flags rather than expressed directly, adding a small amount of indirection per feature.

Alternatives considered

  • Teams first — rejected. Highest integration cost, narrowest contributor base, tied to Microsoft 365 licensing.
  • All three in parallel — rejected. Forces the adapter abstraction to stabilise before Core has shipped, and triples V1 scope.
  • Slack first — rejected. Slack is a plausible second choice, but Discord has zero setup friction for contributors, which matters for an OSS project.
