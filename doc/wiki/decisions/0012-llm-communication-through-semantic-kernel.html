Wiki/Decisions/0012

ADR 0012 — LLM Communication through Semantic Kernel

Every model call — chat completion and embeddings — is registered on and resolved from a Semantic Kernel through the single Scout.Llm gateway; no gateway code constructs a provider SDK client directly for inference.

adr statusaccepted version 1.0 date 2026-05-28 sources vault 06-decisions/2026-05-28-llm-communication-through-semantic-kernel.md

Status

  • Accepted — 2026-05-28. First project of the restructure; supersedes the throwaway-kernel registration hack noted in ADR 0010 — Host Kernel Accessor. Realised in the Scout.Llm gateway.

Context

Scout's stated goal is that all model communication flows through Microsoft Semantic Kernel (the "Semantic Kernel is the hub" direction). The pre-restructure code only partially honoured this:

  • Chat completion went through SK correctly. LlmFallbackRouter, the agent router, and the CodeQA LlmComposer all consumed IChatCompletionService, and OllamaLlmProviderFactory registered it via builder.AddOllamaChatCompletion(...).
  • Embeddings bypassed SK entirely. Scout.Llm.Ollama.OllamaEmbedder constructed an OllamaSharp.OllamaApiClient directly and consumed it via Microsoft.Extensions.AI.IEmbeddingGenerator. Its own XML comment cited the experimental SKEXP0070 status of the SK Ollama connector as the reason to avoid the kernel. Embedding generation is model communication, so this violated the rule.
  • Configuration had two sources of truth for "where is Ollama": chat read Scout:Llm (Endpoint + Model), while embeddings read CodeQAOptions.Embeddings.BaseUrl + Model. Two endpoints, drift-prone.
  • The chat completion service was built ad hoc: LlmChatServiceCollectionExtensions built a throwaway kernel at registration time purely to extract IChatCompletionService (the negative consequence noted in ADR 0010).

The restructure archives the previous source tree under src/old/ and rebuilds fresh. The first new project is the single gateway for all chat + LLM communication.

Decision

Introduce src/Scout.Llm as the sole gateway for LLM communication. Every model call — chat completion and embeddings — is registered on and resolved from a Semantic Kernel. No gateway code constructs a provider SDK client directly for inference.

Through the kernel — mandatory
  • Scout.Llm.Abstractions.ILlmProviderFactory exposes void AddToKernel(IKernelBuilder builder) which registers both chat completion and embedding generation. A provider configures its full capability surface atomically; consumers always get a fully-wired kernel.
  • OllamaLlmProviderFactory.AddToKernel — chat via builder.AddOllamaChatCompletion(chatModel, endpoint) (stable surface); embeddings via builder.AddOllamaEmbeddingGenerator(embeddingModel, endpoint), which registers the stable Microsoft.Extensions.AI.IEmbeddingGenerator<string, Embedding<float>> into the kernel's service provider.
  • Single configuration source Scout:Llm: one Ollama.Endpoint shared by chat and embeddings; models split per role (Chat.Model, Embeddings.Model). A chat model and an embed model legitimately differ, but they share one endpoint/provider.
  • AddScoutLlm builds one shared Kernel singleton from the active provider factory and exposes IChatCompletionService and IEmbeddingGenerator resolved from it, replacing the throwaway-kernel hack.
Forbidden

No gateway code news a provider SDK client (e.g. OllamaSharp.OllamaApiClient) for inference. Building an IEmbeddingGenerator in user code and adding it via builder.Services.AddSingleton is rejected: it is "through the kernel's DI container" but not "through SK's connector" — hollow compliance.

SKEXP0070 acceptance — scoped boundary

AddOllamaEmbeddingGenerator (and the alpha Ollama connector generally) carries the experimental SKEXP0070 attribute. It is accepted under a scoped #pragma warning disable SKEXP0070 / restore around the registration calls only — two private helpers in OllamaLlmProviderFactory.

The consumed type (IEmbeddingGenerator<string, Embedding<float>>) is stable, so no experimental surface leaks to consumers, and LlmServiceCollectionExtensions needs no suppression at all. This is strictly better than the previous state, which suppressed SKEXP0070 project-wide and still bypassed the kernel.

Consequences

Better

  • Rule is structurally enforced. Embeddings can no longer bypass SK because the only embedding entry point is the kernel registration. A registration test asserts IChatCompletionService and IEmbeddingGenerator both resolve from the built kernel — the regression guard for the original violation.
  • One source of truth for the Ollama endpoint, at config and at runtime (one shared Kernel).
  • Provider isolation. Only Providers/Ollama/ touches the alpha connector; a future Scout.Llm.AzureOpenAI is an additive provider with no churn to the abstraction layer or consumers — preserves the Pluggable Everything invariant.

Worse

  • Experimental dependency in the build. SKEXP0070 is accepted. Mitigation: scoped suppression, stable consumed type, this ADR, and the alpha connector version is pinned in Directory.Packages.props (Microsoft.SemanticKernel.Connectors.Ollama 1.74.0-alpha). If the connector API drifts, the fallback is AddOllamaTextEmbeddingGeneration (ITextEmbeddingGenerationService, also SKEXP0070, still kernel-routed).
  • Gateway carries connector packages. Expected: Scout.Llm is the LLM project, so the old "keep Scout.Core free of the alpha package" rationale for a separate Scout.Llm.Ollama project no longer applies. The split returns only when a second provider lands.

Alternatives considered

Register externally-built IEmbeddingGenerator into the kernel DI
Build an OllamaApiClient/IEmbeddingGenerator in user code and add it via builder.Services.AddSingleton. Rejected: still news the provider SDK client — the exact pattern being eliminated. Through DI, but not through SK's connector: hollow compliance.
Keep the old bespoke IEmbedder facade
The old IEmbedder (batching, dimension validation, input-order guarantees) was a CodeQA-plugin concern. Rejected for the gateway: it re-wraps and hides the SK type. The gateway exposes the SK-native IEmbeddingGenerator; CodeQA, when rebuilt, can wrap it with its own batching/validation policy as a consumer.
Separate AddChatToKernel + AddEmbeddingsToKernel
Rejected: invites partially-configured kernels and pushes capability composition up into the host. A provider that genuinely lacks embeddings should surface as a missing kernel service (caught by a startup smoke check), not as an abstraction split.

Enforcement

  • Registration test. Asserts that both IChatCompletionService and IEmbeddingGenerator resolve from the built kernel — the regression guard for the original embeddings-bypass-SK violation.
  • Mandatory failure-injection test on the HTTP boundary. The factory accepts an injectable HttpClient (test seam) driven by a stub HttpMessageHandler returning 500 / timeout / dropped connection; the call must surface a failure rather than hang or return silent empty results. See Production Readiness.
  • PR quality gates (Scout CLAUDE.md): architect-reviewer (defines the new LLM provider abstraction) and security-auditor (external API boundary).
  • Scope guard. Daemon lifecycle / model-management (/api/tags, /api/pull, /api/delete) is NOT inference and stays out of this gateway; it remains direct HTTP in the worker's provider-management layer.
