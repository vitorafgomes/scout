Wiki/Decisions/0007

ADR 0007 — AI Sources Screen

Add a dedicated AI Sources screen at /sources that surfaces local inference runtimes, gates a single entry point to manage downloaded models, and stakes out disabled cloud-provider card slots — without committing to credential handling yet.

adr statusaccepted version 1.0 date 2026-05-16 sources vault 06-decisions/2026-05-16-ai-sources-screen.md

Status

  • Accepted — 2026-05-16. Connection-badge semantics for Ollama / LM Studio were reverted the same day from a models-count check back to a daemon-reachability check.

Context

The Models screen is organised around tasks — Transcription, Analysis, Translation — and assumes a model has already been downloaded somewhere. It does not surface the lower layer: where models live, whether a local runtime is installed at all, and where the user will plug in cloud credentials in the future.

A separate top-level screen is needed to:

  • Detect and surface the state of local inference runtimes (Ollama, LM Studio).
  • Provide a single entry point to "Manage Downloaded Models".
  • Stake out card slots for future cloud providers (ChatGPT Plus, OpenAI API, Google Gemini, OpenRouter, Custom API) without committing to credential handling yet.

The reference UX comes from competitor desktop apps that use a similar "AI Providers" pane. Scout's variant is named AI Sources to avoid the direct name collision and to imply "where do models come from" more neutrally.

Decision

Routing and navigation

  • A new route /sources renders SourcesComponent, with a new side-nav item "AI Sources" placed above Models in PostConnectShellComponent. The remaining nav items (Models, Status, Logs, Settings) keep their existing order.
  • Tradeoff: one extra left-rail entry buys a clear separation between "connections" (Sources) and "task selection" (Models).

Layout

  • A single page with a filter chip group (All / Local / Cloud) in the top-right and two sections: "Local & On-Device" (3 cards) and "Cloud APIs" (5 cards).
  • The filter toggles section visibility via a signal<FilterKind>. No virtualised grid — eight cards is the natural ceiling; more would force a redesign.
  • Cards are data-driven from localCards / cloudCards arrays in the component. Each CardModel declares id, kind, title, description, iconPath, primaryAction, an optional secondary link, primaryIsScan, and disabled. Card variations become an interface bump rather than a forked component.

Connection badge semantics

Ollama / LM Studio — the badge reads Connected when the IPC scan (llmListOllamaModels / llmListLmStudioModels) returns 200, regardless of how many models the user has pulled. A reachable daemon counts as installed.
Local Models (the wrapper card for locally-managed Whisper + LLM models) — the badge reads Connected only when a local runtime is reachable and LocalModelsStore.selected has a value for at least one kind. "Connected" therefore means the user has something usable, not just an installed daemon. Tradeoff: both checks must be true, which can confuse a user who installed Ollama but has not yet picked a model; the "Manage" button gating below mitigates this.
Cloud cards — always Not Connected in this iteration.

The first version coupled the runtime badge to models.length > 0 and confused users who had a fresh install with zero models; this was reverted on 2026-05-16 back to daemon reachability.

"Manage Downloaded Models" gating

  • Enabled iff Ollama or LM Studio is reachable (runtimeReachable computed). Clicking navigates to /sources/local-models, the screen built in ADR 0008.
  • When disabled, the tooltip reads "Install Ollama or LM Studio to manage downloaded models."
  • The button is enabled even when no model is downloaded — intentional, since the screen behind it is precisely where the user goes to download one.

Initial scans and external links

  • Initial scans on mount: ngOnInit fires onScan('ollama') and onScan('lm-studio') in parallel; a scan re-runs on the user's explicit click. Cost: one extra HTTP request per supported runtime at app open — acceptable for two endpoints.
  • External links ("Download Ollama", "Download LM Studio") render as buttons (not <a>) and route through bridge.appOpenExternal({ url }). Under the renderer's CSP the renderer cannot navigate to arbitrary URLs; the main process is the only place allowed to call shell.openExternal, and the URL allow-list lives there. Cost: one extra IPC hop per click.

Cloud card slots (visual only)

ChatGPT Plus, OpenAI API, Google Gemini, OpenRouter, and Custom API all render with the same visual treatment but carry disabled: true on their primary actions, with a "Coming soon" tooltip. Each card uses the icon and description copy verbatim from the reference UX; wiring real auth flows requires per-provider work that is out of scope for this ADR.

Consequences

Better

  • Clear separation of concerns: Sources answers "where do models come from / is a runtime installed", Models answers "which model runs each task".
  • Daemon-reachability badges give honest feedback to fresh installs with zero models pulled.
  • New card variants are an interface change to CardModel, not a new component, keeping the grid uniform.
  • Cloud providers have reserved, visible slots, signalling the roadmap without shipping half-built auth.
  • External navigation goes through the main-process allow-list, respecting the renderer CSP.

Worse

  • One more left-rail entry to scan for the user.
  • The Local Models badge needs two conditions to be true, which can read as "disconnected" to a user who installed a runtime but has not selected a model.
  • Two extra HTTP scan requests fire on every app open.
  • One extra IPC hop per external-link click.

Deferrals

  • LM Studio scan retrying — the scan runs once on mount and once on explicit click; no automatic re-scan on focus or after a delay.
  • Cloud provider wiring — API-key storage, OAuth for ChatGPT Plus, and endpoint validation for Custom API stay out of scope; all five cloud cards remain disabled until per-provider ADRs land.
  • Filter persistence — the filter selection is not persisted across app restarts; it defaults to "All".

Open questions

  • Should the LM Studio scan be allowed when Ollama is also reachable? Today both run in parallel and the badges are independent. If a user has both up but only wants one, this is visual noise but causes no functional issue.
