Wiki/Decisions/0013

ADR 0013 — Conversation Core Streaming Sink

Introduce a platform-agnostic conversation core that owns the stream-drive loop once and renders through a thin per-platform sink whose contract is designed against the least-capable platform, so the routing layer never knows any platform's capabilities.

adr statusaccepted version 1.0 date 2026-05-29 sources vault 06-decisions/2026-05-29-conversation-core-streaming-sink.md

Status

  • Accepted — 2026-05-29. Implemented for the conversation core plus the Discord reference adapter on branch feat/scout-llm-gateway (131 tests green). Slack and Teams adapters implement this same IResponseSink as the next parallel workstream.

Context

Scout is multi-platform chatops: Discord today, Slack and Teams next. The streaming-first mandate means every assistant response streams to the chat surface as tokens arrive. Each platform renders a growing message differently:

  • Discord (Discord.Net) — post an embed, then ModifyAsync repeatedly. Fine-grained edit.
  • Slack (SlackNet) — chat.update repeatedly. Edit, but with different rate limits.
  • Teams (Microsoft.Bot.Framework) — the least capable. Updates must carry cumulative text (not deltas), roughly 1 request per second, a 2-minute stream cap, citations only on the final message, 1:1 chats only, and no fine-grained edit of interim content.

In the archived design (src/old/), the stream-drive loop — the await foreach over tokens plus throttle, truncate, finalize, and rate-limit retry — lived inside each adapter's poster (Scout.Adapter.Discord/Streaming/EmbedEditThrottler.cs and DiscordEmbedReplyPoster.cs). Every new platform would re-implement that loop. Routing also returned a dual-mode ChatResponse (plain XOR streaming) that each adapter had to branch on.

Decision

Introduce src/Scout.Conversation, a platform-agnostic core that owns the stream-drive loop once and renders through a thin per-platform sink. The sink contract is designed against the Teams least-common-denominator so the routing layer never knows a platform's capabilities.

Outbound sink — IResponseSink (cumulative)

RenderCapabilities Capabilities { get; }
Task BeginAsync(CancellationToken ct);
Task UpdateAsync(string cumulativeText, CancellationToken ct);   // CUMULATIVE, not a delta
Task CompleteAsync(string finalText, IReadOnlyList<Citation> citations, CancellationToken ct);
Task FailAsync(string finalTextSoFar, string reason, CancellationToken ct);
  • Lifecycle: exactly one Begin, zero or more monotonic-cumulative Update calls, then exactly one terminal Complete or Fail.
  • UpdateAsync takes cumulative text precisely because Teams forbids deltas; Discord and Slack re-render the whole body anyway, so cumulative costs them nothing. This single decision is what lets the router and pump stay capability-ignorant.
  • RenderCapabilities exposes FineGrainedEdit, MaxBodyLength, SupportsInterimCitations, EditIntervalFloor, and MaxResponseDuration (the Teams 2-minute cap, declared by the sink).

The drive loop — StreamPump (owned once)

StreamPump.RunAsync(ChatResponse, IResponseSink, ct) owns: Begin, the await foreach over ChatResponse.Tokens, cumulative buffering, throttled UpdateAsync at a cadence derived from Capabilities (Discord ~750ms, Teams ~1s floor), tail/head truncation to MaxBodyLength, and the terminal Complete/Fail. Capability-driven degradation: a non-fine-grained, non-interim sink gets final-only rendering. The pump is the single caller and is transport-agnostic — it contains no platform-specific code.

Inverted IChatAdapter

Task StartAsync(Func<ChatMessage, IResponseSink, CancellationToken, Task> handler, CancellationToken ct);
Task StopAsync(CancellationToken ct);
string Name { get; }

The adapter normalizes inbound platform events to ChatMessage, constructs an IResponseSink bound to the originating channel only, and invokes the handler with a lifetime-linked cancellation token. The core (ConversationConductor) routes and pumps. Ownership is inverted: adapters provide a sink, the core drives it. The descriptive-write invariant is enforced by construction — the sink exposes no API to post outside its channel, and the core never sees a channel handle.

Routing and composition

  • IConversationRouter.Route(ChatMessage) -> ChatResponse — non-null, always streaming. v1 has one responder, LlmStreamingRouter, which consumes IChatGateway (not IChatCompletionService directly), staying Semantic Kernel-free.
  • ChatResponse redesigned to (IAsyncEnumerable<string> Tokens, IReadOnlyList<Citation> Citations) plus FromText for the forced-non-streaming path. The plain-XOR-streaming union is gone.
  • ChatMessage, ChatResponse, Citation, and IChatAdapter relocated from Scout.Llm.Abstractions to Scout.Conversation.Abstractions — they are chat-transport, not LLM, concerns. Scout.Conversation depends on Scout.Llm; never the reverse.
  • ConversationConductor wraps route plus pump in an OpenTelemetry activity and guarantees a routing or streaming failure surfaces as FailAsync, never a host crash.
Owned by the core (once)
  • The stream-drive loop: begin, token await foreach, cumulative buffering, throttle.
  • Truncation to MaxBodyLength and capability-driven final-only degradation.
  • Folding the Teams MaxResponseDuration as min(OverallTimeout, MaxResponseDuration).
  • Terminal Complete/Fail ordering and failure surfacing as FailAsync.
Owned by the transport sink (per platform)

429/5xx detection and backoff live in the sink that owns the platform SDK's typed exception — for example DiscordResponseSink catches Discord.Net's RateLimitedException and applies Retry-After backoff. The pump simply calls UpdateAsync; a transient interim failure is swallowed and the buffer retained. This keeps the core free of platform-specific rate-limit reflection.

Consequences

Better

  • One drive loop. Slack and Teams sinks implement only Begin/Update/Complete/Fail plus Capabilities; the pump, router, and conductor are unchanged. Verified by a final-only-degradation test for the non-edit path.
  • Teams fits without touching the core. MaxResponseDuration lets the Teams sink declare its 2-minute cap; the pump folds it as min(OverallTimeout, MaxResponseDuration), mirroring the EditIntervalFloor fold. Cumulative semantics are the contract default.
  • Streaming-first end to end, a Semantic Kernel-free router, correct layering, and no dependency cycle.
  • Descriptive-write boundary enforced by construction, not by convention.

Worse

  • Cumulative re-send cost. Edit-based platforms re-transmit the full body per update. Bounded by the throttle cadence and MaxBodyLength; acceptable.
  • Capability surface must stay honest. New platforms must set RenderCapabilities correctly or get wrong cadence/degradation. Mitigation: the capability contract is small and documented, and per-sink tests assert behavior.

Operational

  • The pump's OverallTimeout now bounds BeginAsync and the terminal CompleteAsync (timeout-linked token), important for non-edit platforms whose only write is the terminal call. FailAsync runs on CancellationToken.None so finalization is not torn down by the same cancellation.
  • Each platform transport is an external boundary: mandatory failure-injection tests (429 retry, 5xx drop, gateway-throws-mid-stream, cancellation) — present for Discord, required for Slack and Teams when built, per Production Readiness.
  • Quality gates run: architect-reviewer (cross-cutting contracts) and code-reviewer (each adapter). Both passed for the conversation core plus Discord reference adapter (APPROVE-WITH-NITS; the four architecture majors were fixed).

Alternatives

  • Per-adapter drive loop (the old design). Rejected: every platform re-implements throttle/truncate/finalize/retry; the bug surface multiplies.
  • Delta-based sink updates. Rejected: Teams requires cumulative text; delta-first would force a Teams-specific re-accumulation layer and leak Teams into the core.
  • Rate-limit handling in the core pump (duck-typed reflection). Tried in the first cut and rejected on review — it was Discord-shaped, would not detect Slack/Teams HTTP-header 429s, and pulled System.Reflection into a platform-agnostic type. Moved into the sink.
  • A core SinkLifecycleGuard decorator. Deferred (YAGNI): each sink enforces its own Begin/Update/terminal ordering for v1; revisit if a third-party sink author needs the invariant for free.
