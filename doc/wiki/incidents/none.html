Production Incidents

Scout is pre-alpha. It has not been deployed to production, so there are no production incidents to report. This page exists to hold that register and to define what an entry will look like once one is needed.

incident statusstub version 1.0 date 2026-06-01 sources README Status (pre-alpha)

Current state

The README describes Scout's status as pre-alpha: the core pipeline — the LLM gateway, conversation core, chat adapters, project-knowledge RAG, and skills — builds and passes its tests on CI, while the Desktop UI has its own CI pipeline but is not yet in a release state. Nothing is running in a production environment, and no operator has been paged. This register is therefore empty by design.

No production incidents recorded. Because Scout has never been deployed for live use, there is no severity history, no on-call rotation, and no post-incident review backlog. When the first production deployment happens, this page becomes the index of incident reports; until then it is intentionally a stub.

What an incident page will contain

When Scout reaches a state where it serves live traffic, each incident gets its own report appended here. The structure below is the template a future entry is expected to follow.

  • Severity & status — an at-a-glance classification (for example SEV1–SEV4) and whether the incident is active, mitigated, or resolved.
  • Summary — one or two sentences stating user-visible impact and the affected surface (an adapter, the LLM gateway, project-knowledge indexing, and so on).
  • Timeline — detection, escalation, mitigation, and resolution timestamps, with who acted at each step.
  • Root cause — the underlying defect or condition, traced to a specific component and, where possible, a commit or configuration change.
  • Follow-ups — concrete remediations: regression tests, guardrails, documentation, and links to the conventions or invariants that should have caught it.

Why incidents should be rare here

Scout's design narrows the blast radius before deployment is even on the table. It is a read-only assistant — no adapter, plugin, or knowledge operation writes to an external system — so a malfunction cannot corrupt downstream data. Adapters are self-gating on their credentials, and an unknown LLM provider fails fast at startup rather than mid-flight. These properties mean the most likely failure modes are degraded answers, not destructive actions.

The closest thing so far

During development Scout has fixed defects that, in a deployed system, would have been incident-worthy. The clearest example is the conversation-memory gap: the assistant was answering without grounding on the configured project and without per-conversation history. That was diagnosed and resolved as a development-time defect — not a production incident — and is written up in Conversation Memory Fix. It is a useful reference for the kind of root-cause-and-follow-up narrative a real incident report would carry.
