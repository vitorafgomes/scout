Shouldly-Only Tests

Every test assertion in every Scout test project must use Shouldly. No test may reference FluentAssertions, and Directory.Packages.props must never list it.

invariant statusactive version 1.0 date 2026-06-01 sources obsidian-vault/scout/CLAUDE.md; ADR 0003; Directory.Packages.props

Why this exists

The first five test projects all started on FluentAssertions 6.12.1 — the last permissive release before the library flipped to a commercial license in v8 (January 2025). Pinning v6 defers the licensing problem but does not solve it: any future upgrade walks into a licensing cliff, and the moment anyone adds a new test project the codebase risks running two assertion libraries side by side. Shouldly is MIT-licensed and stays that way, so the cheapest way to avoid a future license debate is to never allow FluentAssertions back in.

One assertion library per codebase. Two frameworks in the same suite is immediate cognitive overhead and a code-review tax on every PR that touches tests. Shouldly's fluent-by-value style also reads more clearly than xUnit built-ins for collection and exception cases.

Scope

Applies to

  • Every test project under tests/ — all assertions express their expectations through Shouldly.
  • The central package manifest Directory.Packages.props, which lists Shouldly and must not list FluentAssertions.
  • Every test csproj, which references Shouldly (version pinned centrally), and every Usings.cs / per-file using, which imports Shouldly — never FluentAssertions.

Does not cover

  • Which test framework runs the tests — Scout uses xUnit (Assert.* for lifecycle, Shouldly for value assertions).
  • Mocking — that is NSubstitute, an orthogonal choice.
  • Test strategy or coverage targets — see the Testing convention and Production Readiness for those.

Where it is enforced

The rule is written down in three places and reflected in the test source itself.

  • obsidian-vault/scout/CLAUDE.md:40 — the project rule: "Test assertions use Shouldly — never FluentAssertions," with the note that FluentAssertions v8+ is commercial while Shouldly stays MIT.
  • ADR 0003 (obsidian-vault/scout/06-decisions/2026-04-21-shouldly-migration.md:34) — the formal decision: every test in every project uses Shouldly; FluentAssertions is forbidden; migration happens in a dedicated chore/tests-shouldly-migration PR, never mixed with feature work. See 0003 Shouldly Migration.
  • Directory.Packages.props:57 — the single PackageVersion Include="Shouldly" Version="4.3.0" entry. There is no FluentAssertions entry; the comment at Directory.Packages.props:55 records why it was removed.

Because the repository uses central package management (ManagePackageVersionsCentrally at Directory.Packages.props:3), each test csproj references Shouldly without a version — for example tests/Scout.ControlPlane.Tests/Scout.ControlPlane.Tests.csproj:15, tests/Scout.Host.Console.Tests/Scout.Host.Console.Tests.csproj:11, and tests/Scout.Skills.Tests/Scout.Skills.Tests.csproj:11 all carry a bare <PackageReference Include="Shouldly" />.

How it is verified

There is no custom analyzer gating this invariant today; it is enforced by the package manifest, the import statements, and review. A grep over the repository confirms the current state:

  • All ten test projects reference Shouldly via <PackageReference Include="Shouldly" />: Adapter.Discord, Adapter.Slack, Adapter.Teams, ControlPlane, Conversation, Host.Console, Knowledge, Llm, Plugin.GitHub, and Skills.
  • Shouldly is imported either as a global using or per file. Examples: tests/Scout.Llm.Tests/Usings.cs:2 and tests/Scout.Conversation.Tests/Usings.cs:2 carry global using Shouldly;; projects without a global using import it per file, e.g. tests/Scout.ControlPlane.Tests/Security/SessionTokenTests.cs:3 and tests/Scout.Skills.Tests/SkillSelectorTests.cs:3.
  • The only textual match for FluentAssertions in the entire repository is the explanatory comment at Directory.Packages.props:55-56 — there is no package reference and no import anywhere.

A CI guard (a banned-symbols / grep check that fails the build on any FluentAssertions reference) is not yet in place. Until one exists, this invariant relies on the central manifest plus reviewer attention. Adding the guard is an open hardening item.

Known exceptions

  • Shouldly refuses null actuals on ShouldContain over string?. Tests asserting on nullable messages use the null-forgiving operator on the asserted side — this is a usage adaptation, not an exception to the rule.
  • ShouldThrowAsync<T>() returns Task<T>; code that needs to inspect the thrown exception captures the awaited result (var ex = await act.ShouldThrowAsync<T>(); ex.Message.ShouldContain(...)).
  • xUnit's own Assert APIs remain valid for test lifecycle and framework-level checks — the rule governs value assertions, not the test framework.
  • No FluentAssertions exception is permitted anywhere. There is no grandfathered code: the migration PR removed all of it.

Change protocol

Relaxing or reintroducing FluentAssertions would reverse an accepted ADR and a global user rule; it is not a casual change.

  • New tests use Shouldly from the first line. Do not add FluentAssertions to a csproj or a Directory.Packages.props entry under any circumstance.
  • If FluentAssertions is found on sight, migrate it in a dedicated chore/tests-shouldly-migration PR — never mixed with feature work. ADR 0003 records the precedent migration: 37 files, 206 assertions rewritten, zero behavior change.
  • Changing the rule itself requires superseding ADR 0003 with a new ADR under 06-decisions/, updating obsidian-vault/scout/CLAUDE.md, and landing the manifest change on main via a PR from a branch — never a direct push.
