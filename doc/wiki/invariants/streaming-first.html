Wiki/Invariants/Streaming-First

Streaming-First

Every assistant response must be produced as an IAsyncEnumerable<string> token stream; no code path may render a completion by any means other than draining that single stream.

invariant statusactive version 1.0 date 2026-06-01 sources src/Scout.Llm/Abstractions/IChatGateway.cs; src/Scout.Conversation/Streaming/; ADR 0013

Why this exists

Scout is a multi-platform chatops assistant — Discord today, Slack and Teams next. A streaming-first contract is what lets the assistant edit a growing message as tokens arrive instead of making a user wait for the full completion. More importantly, it is the single decision that keeps the system one code path instead of two divergent ones (a "plain" reply and a "streaming" reply that every consumer would have to branch on).

The contract starts at the gateway. IChatGateway.StreamAsync is documented as "the primary path", and CompleteAsync exists only for "the rare caller that needs the whole text at once" — it drains StreamAsync into a single string "so there is one code path." Non-streaming is never a separate implementation; it is the streaming path read to its end.

ADR 0013 carries the same rule into the conversation core. The outbound ChatResponse body is "always an async token sequence"; a complete string is modelled as a one-element sequence via FromText, again "so the stream-drive loop has a single code path regardless of the responder." The router never returns a dual-mode union — the plain-XOR-streaming type from the archived design was deleted.

Scope

Applies to

  • The LLM gateway contract: any new method that returns a model completion must stream, or must be a documented drain over a streaming method.
  • The conversation core: IConversationRouter.Route returns a ChatResponse whose Tokens is "always streaming, never a Task and never null."
  • Every outbound sink: IResponseSink renders cumulative text as tokens accumulate, so platform adapters are driven by the stream rather than buffering and posting once.
  • The single drive loop, StreamPump, which owns the await foreach over tokens for all platforms.

Does not cover

  • Embedding generation — embeddings are a one-shot vector call, not a chat completion, and are out of scope of this invariant.
  • Per-platform rate-limit and retry behaviour, which lives in each sink (the transport), not in the streaming core. See ADR 0013.
  • Configuration, provider selection, or kernel construction — those belong to Pluggable Everything and Local-First Default.

Where it is enforced

The invariant is enforced by the shape of the contracts, not by a runtime check. The relevant declarations:

  • IChatGateway.cs:16 — StreamAsync returns IAsyncEnumerable<string>; the XML doc marks it "The primary path."
  • IChatGateway.cs:22 — CompleteAsync returns Task<string> and is documented as draining StreamAsync "into a single string so there is one code path."
  • Abstractions/ChatResponse.cs:23 — Tokens is the IAsyncEnumerable<string> body; the type doc states the body is "always an async token sequence."
  • Abstractions/ChatResponse.cs:35 — FromText wraps a complete string as a single-element sequence for "the rare responder that produces the whole text at once," keeping the union out of the type.
  • Abstractions/IConversationRouter.cs:12 — Route returns a non-null streaming ChatResponse directly (not a Task), so routing is always streaming-shaped.
  • Routing/LlmStreamingRouter.cs:65 — the v1 responder builds its body from IChatGateway.StreamAsync via a deferred IAsyncEnumerable; the gateway is not invoked until the pump enumerates.
  • Abstractions/IResponseSink.cs:29 — UpdateAsync receives the full cumulative text on every call, so a sink is driven by the stream's progress rather than posting once at the end.
  • Streaming/StreamPump.cs:77 — the single await foreach over response.Tokens that drives every platform; StreamPump.cs:48 is the one entry point (RunAsync).

The drive loop is owned exactly once. StreamPump is "transport-agnostic" and contains no platform-specific code (StreamPump.cs:8); each adapter implements only the thin sink, so a new platform cannot reintroduce a buffer-then-post shortcut without bypassing the pump entirely.

How it is verified

The streaming behaviour has direct unit coverage in tests/Scout.Conversation.Tests/, using Shouldly per the testing convention.

  • Streaming/StreamPumpTests.cs:56 — RunAsync_FineGrained_FollowsLifecycle_AndCompletes: the full Begin → Update* → Complete lifecycle over a token stream.
  • Streaming/StreamPumpTests.cs:72 — interim updates are cumulative and monotonic with a cursor glyph, confirming the sink is fed the growing buffer, not deltas.
  • Streaming/StreamPumpTests.cs:133 — RunAsync_FinalOnly_Degradation_Skips_Interim_Updates: a non-edit sink still consumes the same stream and emits a single terminal Complete.
  • Streaming/StreamPumpTests.cs:153 — an empty stream completes with the configured placeholder, so the single-path contract holds even with zero tokens.
  • Streaming/StreamPumpFailureTests.cs:81 — a mid-stream throw finalizes via FailAsync with the partial buffer and no Complete (boundary failure injection).
  • Streaming/StreamPumpFailureTests.cs:103 — caller cancellation mid-stream propagates without forcing a terminal edit.
  • Streaming/StreamPumpFailureTests.cs:123 — a 429 mid-stream finalizes via Complete with a friendly message, logged quietly.
  • Routing/LlmStreamingRouterTests.cs:10 — the v1 router is exercised as a streaming responder over the gateway.

Known exceptions

  • CompleteAsync / ChatResponse.FromText. These are the only sanctioned non-streaming entry points, and both are defined in terms of the stream: CompleteAsync drains it, FromText wraps a string as a one-element sequence. They are conveniences, not a second implementation.
  • Final-only rendering on weak platforms. A sink whose RenderCapabilities has neither FineGrainedEdit nor SupportsInterimCitations accumulates silently and emits a single terminal Complete (StreamPump.cs:63, :86). It still consumes the same token stream — only the visible edits are skipped.
  • Embeddings. Vector generation is a one-shot call and is explicitly outside this invariant.

Change protocol

  • Any new way to obtain a model completion must return IAsyncEnumerable<string>, or be a thin drain over an existing streaming method — never a parallel buffered implementation.
  • Do not reintroduce a dual-mode response union (plain XOR streaming). ADR 0013 removed it deliberately; resurrecting it requires a superseding ADR.
  • New platform adapters implement IResponseSink and let StreamPump drive them. Do not add a per-adapter await foreach over tokens — that loop lives once in the pump.
  • Any change to the pump, the router, or the sink contract crosses an external boundary; ship at least one boundary-failure test (timeout, 5xx/429, mid-stream throw, cancellation) per the Production Readiness convention.
  • Changes touching IChatGateway or the conversation contracts go through the architect-reviewer gate before a PR against main.
