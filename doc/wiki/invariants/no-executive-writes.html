Wiki/Invariants/No Executive Writes

No Executive Writes (Read-Only)

No feature, adapter, plugin, or knowledge operation may perform an executive write — any action that mutates code, configuration, infrastructure, or data without a human gate.

invariant statusactive version 1.0 date 2026-06-01 sources ADR 0009; README read-only invariant; CONTRIBUTING.md; src/Scout.Plugin.GitHub/

This is the single most important invariant in Scout. Scout is positioned as a read-only chatops assistant: it answers operational and development questions by querying GitHub, searching indexed local repositories, and calling an LLM — and it never writes to any external system. The descriptive vs. executive write distinction (formalised in ADR 0009) refines what "read-only" means as the plugin ecosystem grows: it cleanly separates writes that describe work for a human or another agent to act on from writes that execute work themselves. This page covers the half of that split that is non-negotiable: executive writes are forbidden.

Why this exists

An executive write is an action that, once taken, takes effect immediately and cannot be intercepted by a human in the loop without an explicit rollback. The original invariant existed because Scout reads logs, surfaces context, and must never mutate the environment it observes. The guarantee that matters most to the user is plain: Scout never breaks production by itself.

Per ADR 0009, executive writes are actions that mutate code, configuration, infrastructure, or data without a human gate. Concrete examples the ADR forbids:

  • Committing or pushing code to any branch.
  • Merging, closing, or approving a pull request.
  • Editing repository settings, webhooks, secrets, or branch protection.
  • kubectl apply, delete, exec, scale, patch, rollout, cordon, drain.
  • Any write against a cloud API (S3 put, RDS modify, Lambda update, IAM mutation).
  • Database INSERT, UPDATE, DELETE, or DDL.
  • Modifying files on the host filesystem outside Scout's own config directory.
  • Sending email or external notifications outside the originating chat.

Scope

Applies to

  • Every Semantic Kernel plugin exposed to the LLM for function-calling.
  • Every chat adapter (Discord, Slack, Teams) — an adapter may reply in the originating channel but not write elsewhere.
  • The Project Knowledge subsystem — it reads and indexes local repository files; it never writes back to them.
  • Any future integration or feature module that touches an external boundary.

Does not cover

  • Descriptive writes — creating a GitHub issue, commenting on a PR, or posting a chat message in the originating channel are governed by ADR 0009, not forbidden by this page. See the domain page for the full classification.
  • Scout's own local state — the project-knowledge SQLite database and Scout's own config directory are internal, not external systems.
  • Content hygiene — a descriptive write that leaks a secret is still a problem, but that is a separate concern from the executive-write boundary (ADR 0009, "Negative" consequences).

Where it is enforced

The invariant is enforced at the design level: the write capability simply does not exist in the code. The reference enforcement point is the GitHub plugin, which exposes only listing and retrieval functions and has no create, merge, push, or comment path at all.

  • src/Scout.Plugin.GitHub/GitHubPlugin.cs:29 — list_repositories, a [KernelFunction] that only reads.
  • src/Scout.Plugin.GitHub/GitHubPlugin.cs:51 — list_pull_requests; lists open PRs, never opens or merges them.
  • src/Scout.Plugin.GitHub/GitHubPlugin.cs:76 — list_issues; lists open issues, never creates or closes them.
  • src/Scout.Plugin.GitHub/GitHubPlugin.cs:101 — get_repository; fetches an overview for describing a project. These four are the complete declared function surface; the class comment at GitHubPlugin.cs:7-13 states "Listing only: no create, merge, or push operations exist by design."
  • src/Scout.Plugin.GitHub/Abstractions/IGitHubClient.cs:3-6 — the client contract itself is documented "Listing only: no create, merge, push, or comment operations exist by design."
  • src/Scout.Plugin.GitHub/GitHubClient.cs:140 & :157 — the only transport calls are _http.GetAsync(...). There is no PostAsync, PutAsync, PatchAsync, or DeleteAsync anywhere in the plugin.
  • src/Scout.Plugin.GitHub/GitHubServiceCollectionExtensions.cs:52-53 — the PAT is consumed only as a Bearer credential on a read client; README.md:128 notes "Read-only scopes are sufficient," so the token itself need not carry write permission.

The invariant is also documented as a hard project rule:

  • README.md:161-163 — the "Read-only invariant" section: "The GitHub plugin exposes only listing and retrieval functions. No adapter, plugin, or knowledge operation writes to any external system."
  • CONTRIBUTING.md:7-10 — "No contribution may introduce write operations against external systems… This is a security invariant, not a preference — PRs that break it will not be merged."

How it is verified

Enforcement is structural rather than runtime, so verification focuses on the declared capability surface of the LLM-facing plugin.

  • tests/Scout.Plugin.GitHub.Tests/GitHubPluginMetadataTests.cs:20-30 — Exposes_Expected_Function asserts the plugin exposes exactly list_repositories, list_pull_requests, list_issues, and get_repository. No write function name is in the set, so the LLM has no executive write to call. Assertions use Shouldly per the testing convention.
  • The hard merge gate in CONTRIBUTING.md:7-10 is the primary control for new code: any PR that adds a write path is rejected in review.
  • There is no automated classifier for descriptive vs. executive writes — ADR 0009 ("Negative") is explicit that each new plugin function must be tagged descriptive or executive by hand at code-review time. A test that scans for forbidden HTTP verbs across all plugins is not present today and would be a reasonable hardening step.

Known exceptions

There are no exceptions for executive writes. The only writes Scout is permitted to perform are descriptive, and even those are gated per-plugin by ADR 0009:

  • A chat adapter posting a reply in the originating channel is the one always-permitted write; it is descriptive, not executive.
  • The GitHub plugin is permitted descriptive writes per ADR 0009 (future CreateIssue, CommentOnPullRequest, AddIssueLabel) but is forbidden executive writes (MergePullRequest, CreateBranch, PushCommit, repo settings, webhooks). As of this writing the shipped plugin exposes none of the descriptive write functions either — it is still listing-only.
  • Boundary cases default to forbidden. The class of a write is determined by its effect, not its API surface: creating an issue whose label triggers a CI workflow is executive (it indirectly mutates state); a Kubernetes ConfigMap is executive even though it "looks like text." Any Kubernetes write — descriptive or otherwise — requires a separate ADR (ADR 0009, "Operational").

Change protocol

  • This invariant cannot be relaxed by a PR alone. Any change that would introduce a write path — even a descriptive one for a new plugin — must first be classified per ADR 0009 and recorded.
  • Introducing an executive write requires reversing this invariant, which means a new ADR in obsidian-vault/scout/06-decisions/ that supersedes ADR 0009, plus updates to README.md and CONTRIBUTING.md. Per the project rules a change of write class for any existing plugin function also requires a new ADR.
  • New descriptive write functions must be tagged descriptive at design review and surfaced on the per-plugin write-class badge described in ADR 0009 before merge.
  • Touching the plugin contract or registry is itself an architectural change requiring an ADR per the commit & PR policy; reviewers should treat any new external-boundary write as failing the CONTRIBUTING.md gate by default.
