Wiki/Invariants/Pluggable Everything

Pluggable Everything

Every LLM provider, chat adapter, and plugin must be swappable by configuration alone and self-gate on its own credentials; no code path may name a second provider for the same role, and an unknown provider name must fail fast at startup.

invariant statusactive version 1.0 date 2026-06-01 sources src/Scout.Llm/LlmServiceCollectionExtensions.cs; adapters; README

Why this exists

Scout has to run identically for a contributor with nothing installed and for an operator wired into paid cloud LLMs, Discord, Slack, Teams, and GitHub at once. The way it reconciles those two worlds is to make every external integration a slot filled by configuration, never by a code change. The composition root picks exactly one LLM provider from Scout:Llm:Provider, and each adapter and plugin decides for itself whether to register based on whether its credentials are present.

Two properties fall out of this rule. First, a host with no tokens still starts cleanly — every optional integration is a no-op, so a fresh checkout boots without secrets. Second, a typo in the provider name is caught at startup instead of producing a half-wired kernel: the provider switch has no silent fallback, only a default arm that throws. Together they keep the system honest about what is actually configured.

Scope

Applies to

  • LLM providers — the eight implementations behind ILlmProviderFactory, selected by Scout:Llm:Provider. Exactly one is active per process.
  • Chat adapters — Discord, Slack, and Teams, each registered as an IChatAdapter only when its credentials are configured.
  • Semantic Kernel plugins — feature modules such as the GitHub plugin that contribute a KernelPlugin to the shared kernel when, and only when, enabled.

Does not cover

  • Conversation routing and history, which are owned by Scout.Conversation and are not swappable per-config in the same sense.
  • The read-only stance itself — that is the separate No Executive Writes invariant. Pluggability never licenses a write path.
  • Embedding-vs-chat split within a single provider; that is provider-internal configuration, not a provider swap.

Where it is enforced

The enforcement points are concentrated in three DI composition roots, one per integration kind.

LLM provider selection

  • LlmServiceCollectionExtensions.cs:48 — the active provider name is read from Scout:Llm:Provider; when blank it falls back to the LlmOptions default rather than guessing.
  • LlmServiceCollectionExtensions.cs:54 — the switch (provider) dispatches to exactly one Add<Provider>LlmProvider() registration. Each case is the sole registration site for that provider.
  • LlmServiceCollectionExtensions.cs:80 — the default arm throws InvalidOperationException with the full list of supported names. This is the fail-fast point: an unknown provider never reaches kernel construction.
  • LlmServiceCollectionExtensions.cs:96 — every KernelPlugin registered by a feature module is folded onto the shared kernel; a self-gated module that registered none contributes nothing here.
// LlmServiceCollectionExtensions.cs — the switch and its fail-fast default
switch (provider)
{
    case "Ollama":          services.AddOllamaLlmProvider();          break;
    case "Gemini":          services.AddGeminiLlmProvider();          break;
    // ... OpenAI, OpenRouter, AzureOpenAI, Mistral, HuggingFace, AzureAIInference
    default:
        throw new InvalidOperationException(
            $"Unknown LLM provider '{provider}'. Supported providers: ...");
}

Default provider

  • LlmOptions.cs:16 — Provider defaults to "Ollama". This is the fallback used when the configuration key is absent, which is what makes the Local-First Default invariant hold without any secrets.

Adapter self-gating

  • DiscordServiceCollectionExtensions.cs:29 — reads Scout:Adapters:Discord:BotToken; :30 returns early when it is null or whitespace, so no IChatAdapter is registered for an unconfigured Discord.
  • Slack and Teams follow the same shape, gating on Scout:Adapters:Slack:BotToken and Scout:Adapters:Teams:AppId respectively (per the README adapter table).
// DiscordServiceCollectionExtensions.cs — credential self-gate
var botToken = configuration.GetSection(ConfigSection).GetValue<string>("BotToken");
if (string.IsNullOrWhiteSpace(botToken))
{
    return services; // clean no-op: unconfigured host still starts
}

Plugin self-gating

  • GitHubServiceCollectionExtensions.cs:37 — reads Scout:Plugins:GitHub:Token; :38 returns early when blank, so neither the typed IGitHubClient nor the KernelPlugin is registered.
  • GitHubServiceCollectionExtensions.cs:56 — only when a token is present does the module register the "GitHub" KernelPlugin the LLM can invoke. That plugin is then picked up by the kernel loop at LlmServiceCollectionExtensions.cs:96.

How it is verified

  • Provider selection — the README states the gateway "selects one of eight provider implementations at startup from Scout:Llm:Provider", and the eight cases in the switch match the documented value list exactly. The default arm enumerates the same eight names, so drift between docs and code is visible.
  • Unit tests for provider selection and the fail-fast behaviour live with the gateway; Scout.Llm notes provider selection among the cases covered by tests/Scout.Llm.Tests/, with assertions in Shouldly per the testing convention. A dedicated test asserting the exact InvalidOperationException message for an unknown name was not separately verified for this page.
  • Adapter and plugin self-gating is structural: the early-return guards are the only registration gate, so a host with empty tokens cannot register an adapter or plugin even by mistake. Boundary failure tests for newly touched integrations are required before merge per Production Readiness.

Known exceptions

  • One LLM provider at a time. The switch activates a single provider per process. Running two LLM backends side by side is out of scope; switching means restarting with a different Scout:Llm:Provider value.
  • Ollama default is intentional, not a hard-coded provider. The default at LlmOptions.cs:16 is still overridable by configuration; it is a sensible fallback, not a bypass of the swap rule.
  • OpenRouter embeddings. OpenRouter serves no embeddings, so its options block points embeddings at a separate OpenAI-compatible host. This is intra-provider configuration, not a second provider, and does not violate the one-active-provider rule.

Change protocol

  • Adding a provider — add a new case to the switch in LlmServiceCollectionExtensions.cs, a matching Add<Provider>LlmProvider() registration, a provider folder under src/Scout.Llm/Providers/, and an options class on LlmOptions. Update the default arm's supported-names message and the README provider list in the same change.
  • Adding an adapter or plugin — follow the self-gating shape: bind options, read the gating credential, return early when blank, and only then register the IChatAdapter or KernelPlugin. Never register unconditionally.
  • Never introduce a silent fallback. An unknown or misconfigured provider must keep failing fast; do not replace the throw with a default-to-Ollama branch.
  • Because every change here touches an external boundary (LLM HTTP, chat platform, GitHub API), include at least one boundary failure test per Production Readiness, and keep secrets out of tracked config per Secrets Never Committed.
