Wiki/Invariants/Secrets Never Committed

Secrets Never Committed

No real credential — bot token, API key, app password, or PAT — may ever be committed to tracked source. Secrets live in .NET User Secrets during development, in environment variables (or a secrets manager) in production, and only in gitignored files locally.

invariant statusactive version 1.0 date 2026-06-01 sources obsidian-vault/scout/CLAUDE.md; README Configuration; .gitignore

Why this exists

Scout integrates with several external systems that each require a credential: Discord, Slack, and Teams bot tokens; per-provider LLM API keys; and a GitHub Personal Access Token. Every adapter and plugin is self-gating — it reads its credential from configuration and silently skips when the value is empty. That convenience makes it dangerously easy to drop a working token straight into appsettings.json "just to test", then commit it.

A leaked token is an immediate, irreversible exposure: anyone with read access to the repository history can drive the bot, call the model on the project's budget, or read private repositories through the PAT. The project's own instructions state the rule plainly — secrets use "User Secrets in dev, env vars in prod. Never in source." (obsidian-vault/scout/CLAUDE.md:39). The README repeats it as a hard requirement of the configuration model: "Secrets must never be committed" (README.md:86).

This rule has been violated in practice. The tracked src/Scout.Host.Console/appsettings.json:31 currently carries a live-looking Discord BotToken value, while every other secret field in the same file is left as an empty string. The base appsettings.json is committed, so any value placed there is published. It must be reset to "" before the next commit and the exposed token rotated.

Scope

Applies to

  • All chat-adapter credentials: Scout:Adapters:Discord:BotToken, Scout:Adapters:Slack:BotToken, Scout:Adapters:Slack:AppLevelToken, Scout:Adapters:Teams:AppId, Scout:Adapters:Teams:AppPassword, Scout:Adapters:Teams:TenantId (README Configuration, lines 117–122).
  • Every LLM provider key, e.g. Scout:Llm:OpenAI:ApiKey and Scout:Llm:AzureOpenAI:ApiKey (README.md:96, README.md:98).
  • The GitHub plugin token Scout:Plugins:GitHub:Token — read-only scopes are sufficient, but it is still a secret (README.md:128).
  • Every tracked appsettings*.json across all hosts and projects, plus any other file under version control.

Does not cover

  • Placeholder or empty values committed to the base appsettings.json to document a key's shape (an empty string disables the corresponding adapter or plugin by design).
  • Non-secret configuration such as the Ollama endpoint, model names, temperature, or token caps.
  • Files that git never tracks (see the enforcement list below) — local secrets there are expected.

Where it is enforced

Enforcement is layered: configuration design keeps secrets out of source, and .gitignore catches the files that legitimately hold real values locally.

  • .gitignore:15–:22 — the Secrets block ignores *.env, .env, .env.*, secrets.json, appsettings.Development.json, appsettings.Local.json, and *.bkp backups. Real local tokens belong in one of these.
  • .gitignore:20 — appsettings.Development.json is the intended home for development credentials; it is verified ignored (git check-ignore matches it).
  • README Configuration (README.md:86) — documents the contract: User Secrets or environment variables in dev, environment variables or a secrets manager in prod.
  • README Running the Console Host (README.md:72) — environment-variable overrides use the double-underscore separator, e.g. Scout__Adapters__Discord__BotToken, so a secret can be supplied at runtime without ever touching a file.
  • obsidian-vault/scout/CLAUDE.md:39 — the project rule; :54 additionally requires the security-auditor agent on any change touching credentials or token handling.
Gap: the base appsettings.json is not in .gitignore (and cannot be — it ships sensible non-secret defaults). Nothing mechanical stops a token being typed into it, which is exactly how the Discord value at appsettings.json:31 leaked. Until a CI secret-scan or pre-commit hook exists, the only guard is review discipline.

How it is verified

There is no automated secret-scanning test in the repository at this time, so enforcement is currently manual. The verifiable mechanisms in place are:

  • git check-ignore appsettings.Development.json exits 0 — the gitignore rule is real, not aspirational.
  • Inspecting the tracked appsettings.json: every secret field except the leaked Discord token is an empty string, confirming the empty-placeholder pattern is the intended committed state.
  • Quality gate (obsidian-vault/scout/CLAUDE.md:54): the security-auditor agent must review any change that touches credentials or token handling before a PR.

A dedicated guard is pending: a CI secret-scan (or a git diff pre-commit hook that reverts non-empty token fields in tracked appsettings.json to "") would make this invariant self-enforcing instead of review-dependent.

Known exceptions

  • Empty-string placeholders. Committing a key with an empty value documents the configuration surface and, by the self-gating design, disables that adapter or plugin. This is not a secret and is allowed.
  • Gitignored local files. appsettings.Development.json, appsettings.Local.json, and any .env file may hold real tokens because git never tracks them.
  • No exception permits a real credential in any tracked file. Boundary cases default to forbidden.

Change protocol

  1. Never paste a real token into a tracked file. Use dotnet user-secrets for the console host, or set an environment variable such as Scout__Adapters__Discord__BotToken at runtime.
  2. If a local file is the only option, put the value in appsettings.Development.json (gitignored) — never in the base appsettings.json.
  3. Before every commit, run git diff over tracked appsettings*.json and confirm all secret fields are "". Revert any non-empty token.
  4. If a secret has already been committed: treat it as compromised. Reset the field to "", rotate the credential at the provider, and consider history rewrite if the leak is recent and unpushed.
  5. Any change touching credentials or token handling goes through the security-auditor agent and lands on main via a PR (never a direct push) per the commit-and-PR policy.
  6. Strengthening this invariant (adding a secret-scan or pre-commit hook) is itself a change — propose it through the normal branch-and-PR flow.
